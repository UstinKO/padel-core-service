# GIT_WORKFLOW.md — процесс работы над задачами в padel-core-service

Как Claude Code должен вести git-flow при реализации задач в этом репозитории.

**Два режима:**
- **Обычная интерактивная сессия** (пользователь просто просит что-то сделать) — действуют правила §1–7 ниже без исключений: без push, без PR.
- **Автономный SDD-конвейер** (`/develop-feature`, роль Architect + агенты Analyst/Developer/Tester из `.claude/agents/`) — работает по [.claude/commands/develop-feature.md](commands/develop-feature.md) и имеет отдельное, явно ограниченное исключение из §7 — см. §8.

Если сомневаешься, в каком ты режиме — ты в обычном. Исключение действует только внутри `/develop-feature`.

---

## 1. Источник задачи

Каждая фича/фикс должна быть привязана к GitHub issue в `UstinKO/padel-core-service`. Если issue ещё нет — сначала завести её (см. `CODE_REVIEW.md` про то, что должно быть в описании), согласовать план с пользователем, и только потом переходить к коду.

Для неоднозначных или крупных задач (несколько путей реализации, затрагивает несколько модулей, есть архитектурный выбор) — сначала провести анализ и предложить план на согласование пользователю. Не начинать писать код, пока план не подтверждён явно.

---

## 2. Ветка

- Всегда создаётся от актуального `master`.
- Именование: **`feature/LFPT-<номер issue>`**, где `<номер issue>` — это номер GitHub issue как есть, без искусственного перенумерования и без замены на внутренний тикет-номер.
  - Пример: issue `#190` → ветка `feature/LFPT-190`.
- Ветку создаёт пользователь сам (или явно просит создать). Claude не создаёт и не переключает ветки самостоятельно без запроса.

---

## 3. Реализация

- Изменения делать минимальные и точно соответствующие issue — не расширять scope без необходимости (см. `CODE_REVIEW.md`, YAGNI).
- Если реализация подразумевает выбор между несколькими вариантами (например, DB-миграция vs. эвристика без миграции) и issue явно оставляет это на усмотрение реализующего — сделать разумный выбор самостоятельно и коротко объяснить его в commit message; не устраивать отдельный раунд согласования на каждую техническую деталь.

---

## 4. Локальная проверка — обязательна перед коммитом

Порядок:

1. **Компиляция**: `./mvnw compile -DskipTests` (или полный `./mvnw verify`, если нужны тесты).
2. **Тесты**: `./mvnw verify` — требует локальный PostgreSQL (обычно уже поднят через `docker compose up -d` в фоне на машине разработчика). Креды по умолчанию в `application.yml` (`postgres/root`) **не совпадают** с реальными кредами контейнера `padel-postgres` — узнать актуальные: `docker inspect padel-postgres` (или переменные окружения контейнера), передать явно: `DB_USERNAME=... DB_PASSWORD=... ./mvnw verify`.
3. **Ручная/browser-проверка, если применимо**:
   - Если в проекте уже запущен dev-инстанс (например, из IntelliJ с DevTools) — не поднимать второй инстанс параллельно (конфликт порта 8080). Проверить `lsof -nP -iTCP:8080 -sTCP:LISTEN`, при необходимости просто пересобрать (`./mvnw compile`) — DevTools сам перезапустит контекст на изменённых классах.
   - Если своего инстанса нет — поднять через `./mvnw spring-boot:run` с переменными окружения из `.env` (обратить внимание на возможные `\r` в файле — прогнать через `sed 's/\r$//'` при необходимости) и `LOG_PATH`, указывающим на существующую директорию (по умолчанию `LOG_PATH` в проде — `/app/logs`, локально такой директории нет).
   - Для UI-изменений — реальный проход в браузере (Playwright/chromium-cli), а не только визуальный код-ревью шаблона.
   - Для API/бэкенд-изменений — прямой вызов эндпоинта (`curl`) и, где уместно, сверка результата с прямым запросом к БД (`docker exec ... psql`).
4. **Тестовые данные**: если для проверки нужен тестовый аккаунт (например, для проверки flow, требующего логина) — **никогда не менять пароль существующего реального аккаунта** без явного разрешения пользователя. Создавать одноразовый тестовый аккаунт с известным паролем и удалять его (и связанные с ним данные) после проверки.

Если что-то из локальной проверки невозможно (например, флоу требует реального SMTP-письма или другого внешнего сервиса, который небезопасно триггерить в тесте) — явно сказать об этом в отчёте пользователю, а не тихо промолчать.

---

## 5. Коммит

- Коммит делает Claude, **после** того как локальная проверка прошла успешно.
- Сообщение коммита:
  - Первая строка: `LFPT-<номер issue>: <краткое описание на русском>`
  - Тело: что сделано и почему (кратко, по существу — не пересказ диффа построчно)
  - Последняя строка: `Closes #<номер issue>`
  - Далее: `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>` (или актуальная модель)
- **Claude НЕ делает `git push` и не создаёт Pull Request.** Это всегда делает пользователь сам.

---

## 6. Ревью и доработки

- После коммита пользователь сам пушит ветку, создаёт PR и проводит ревью.
- Если у пользователя есть замечания — он сообщает их Claude, Claude вносит правки **новыми коммитами** в ту же ветку (не переписывает историю через `--amend`/`rebase`, если явно не попросили).
- Если замечаний нет — пользователь сам сливает PR.

---

## 7. Что Claude не делает без явного запроса

- Не пушит в удалённый репозиторий.
- Не создаёт и не мержит Pull Request.
- Не меняет пароли/креды существующих аккаунтов (тестовых или реальных) без предупреждения и явного согласия.
- Не удаляет и не создаёт ветки без запроса пользователя.
- Не деплоит на сервер и не применяет изменения на продакшен-сервере по SSH без отдельного согласования (см. `SECURITY.md` — серверные изменения nginx/CrowdSec/etc идут отдельным процессом, не через этот git-flow).

Это правило по умолчанию для обычных сессий. Единственное исключение — §8.

---

## 8. Исключение: автономный SDD-конвейер (`/develop-feature`)

Запуск команды `/develop-feature` — явный запрос пользователя на автономную реализацию по спеке, поэтому внутри неё правило §7 "не пушит, не создаёт PR" **снимается частично**, при соблюдении всех условий ниже:

- Ветку создаёт и worktree поднимает только сам конвейер (`isolation: "worktree"` на шаге Analyst), не отдельные агенты по своей инициативе.
- Push и `gh pr create` делает **только роль Architect** (главный агент конвейера), и только после того, как прошли все гейты: спека `approved` без открытых бизнес-вопросов → Developer → Tester → собственная сверка Architect с критериями приёмки спеки. Ни Analyst, ни Developer, ни Tester не пушат и не открывают PR сами.
- **Merge PR по-прежнему делает пользователь.** Конвейер не мержит, не деплоит — это неизменная часть правила §7, исключения не имеет.
- Любой бизнес-вопрос (не технический), возникший на любом шаге — остановка конвейера и вопрос пользователю, не самостоятельное решение ни одним агентом.
- Формат коммитов и PR — как в §5, с уточнениями в `develop-feature.md` (PR-описание строится из фиче-спеки).

Если `/develop-feature` не запускалась — весь этот пункт не действует, работает обычное §7 целиком.

**Запуск через Telegram** (с LFPT-328, 2026-08-20) — тот же конвейер, тот же режим `cloud`, только триггер другой: сообщение в теме "AI Разработка" вместо ручного "Run now"/терминала. Все правила выше применяются без исключений — push и PR по-прежнему только Architect, мерж/деплой по-прежнему только пользователь. Механика и специфика (роль отправителя architect/customer, обработка гейта на открытые вопросы без возможности синхронно спросить) — `develop-feature.md`, раздел "Точка входа: Telegram". Бот отдельный (`@padel_core_ai_bot`) — не переиспользует игровой бот `TelegramService`/`TelegramBotPoller` (`CLAUDE.md`), разные назначения, разные креды. Relay (`scripts/telegram-relay/`) — вне git, живёт как systemd-сервис на проде; секреты (токен бота, токен API-триггера роутины) — только в `.env` на сервере и в переменных окружения самой роутины, никогда в репозитории.

### Уведомления

Architect сообщает о готовом PR прямо в чате (терминальный режим) или итоговым сообщением в Telegram-тему (режим Telegram, через `sendMessage` с секретами окружения роутины). Использован отдельный бот/токен для конвейера — не путать с игровым Telegram-ботом для игроков (`TelegramService`/`TelegramBotPoller` в `CLAUDE.md`) — разные назначения, разные креды.
