# CODE_REVIEW.md — стандарты качества кода в padel-core-service

Чек-лист, которым Claude Code должен руководствоваться при написании и самопроверке кода в этом репозитории — до коммита. Это тот же набор критериев, который сам проект ставит в чек-листах issue (см. примеры в трекере: #132, #176–#180, #187–#190) — здесь он собран в одном месте, чтобы не переизобретать его в каждой задаче.

---

## 1. Соответствие ТЗ — прежде всего

- Реализация должна закрывать **именно то**, что написано в issue — не больше и не меньше.
- Если в issue есть чек-лист "Что нужно сделать" — каждый пункт должен быть либо реализован, либо явно объяснено, почему пункт не применим.
- Если issue оставляет техническое решение на усмотрение реализующего (например, "выбрать вариант (a) или (b)") — выбрать самостоятельно, кратко обосновать в commit message, не устраивать лишний раунд вопросов.
- Не добавлять функциональность, не запрошенную в issue, "заодно" — заводить отдельную задачу вместо расширения scope.

## 2. DRY — не дублировать

- Перед тем как писать новую логику — проверить, нет ли уже похожего кода в проекте (`grep`/поиск по сервису), который можно переиспользовать или обобщить.
- Конкретные прецеденты в этом проекте:
  - Батчинг club/registration-count запросов — переиспользовать `TournamentService.mapToDtoWithDetails(List<Tournament>)` и `mapToDtoWithBatchedData(...)`, не писать новый N+1 цикл.
  - Гостевые/guest-плейсхолдер игроки — переиспользовать `TestTournamentController.resolveOrCreateGuestPlayer(...)`.
  - Rate-limiting — переиспользовать существующие Bucket4j/Guava-cache паттерны в `RateLimitFilter`, не изобретать параллельный механизм.
- Если один и тот же чек по бизнес-правилу нужен в двух местах — выносить в общий метод/сервис, а не копипастить.

## 3. KISS / YAGNI

- Не переусложнять: если задача решается простым методом/полем — не вводить новый слой абстракции, интерфейс, паттерн проектирования ради одного места использования.
- Не проектировать под гипотетическое будущее использование, которого не просили.
- Явно указанные в issue пункты вроде "не добавляем async туда, где и так быстро" — соблюдать буквально: сначала измерение (`@Timed`), потом оптимизация, а не наоборот.

## 4. SOLID

- Один класс/метод — одна ответственность. Не смешивать бизнес-логику с маппингом, логирование — не бизнес-логика.
- Не ломать LSP/ISP ради удобства: если меняется сигнатура публичного метода — проверить всех вызывающих (`grep` по проекту), не полагаться на то, что "наверное, больше никто не вызывает".
- Зависимости — через конструктор (`@RequiredArgsConstructor`, уже принятый в проекте стиль), не через `new` внутри сервисов.

## 5. Consistency — единый стиль проекта

- Язык домена смешанный (см. `CLAUDE.md`): поля entity — на испанском (`nombre`, `fechaInicio`), комментарии и логи — на русском. Не смешивать по-другому.
- Весь маппинг entity ↔ DTO — только через MapStruct-мапперы (`mapper/`), никогда вручную в контроллере/сервисе.
- Новые read-методы, которые могут быть "медленными" по паттернам проекта (список турниров, батч-операции) — покрывать `@Timed` по аналогии с уже размеченными методами (`TournamentService`, `EmailService`), с осмысленным `name`/`tags`.
- Ориентир по размеру: методы не длиннее ~30 строк, вложенность не больше 2 уровней, функциональный стиль (stream/Collectors) при работе с коллекциями — если это не в ущерб читаемости.
- Не добавлять лишнее логирование "на всякий случай" — только то, что реально нужно для диагностики.

## 6. Известные архитектурные ловушки в этом проекте

- **Self-invocation ломает Spring AOP.** `@Timed`/`@TrackErrors`/`@Async` — proxy-based аспекты. Вызов `this.someMethod()` изнутри того же класса **не проходит через прокси** — аннотация будет молча нерабочей. Если метод вызывается только изнутри своего же класса — не вешать на него `@Timed`, это создаст обманчивую, всегда пустую метрику. Если нужно и внешний, и внутренний вызов — таймить внешний публичный метод, а не внутренний хелпер.
- **`@Async` + другие аспекты — порядок важен.** Если на методе одновременно `@Async` и `@Timed`/`@TrackErrors`, а у обычных `@Aspect`-классов не задан `@Order` (по умолчанию `LOWEST_PRECEDENCE`) — есть риск, что `@Timed` замерит только постановку задачи в очередь, а не реальное выполнение. Проверять эмпирически (временным тестом, не оставлять его в коммите), а не полагаться на предположение.
- **Nginx конфиг и Spring Boot rate-limit должны быть согласованы.** Лимиты в `RateLimitFilter` — последний рубеж, не единственный; nginx-зоны должны быть строже или сопоставимы, иначе вся нагрузка ложится на JVM.
- **`@Value` не биндит YAML-списки.** `@Value("${some.key:}")` на `List<String>`, где `some.key` в YAML оформлен как список (`- item1\n- item2`), НЕ резолвится — Spring Boot разворачивает такой список только в индексированные ключи Environment (`some.key[0]`, `some.key[1]`...), а не в один ключ `some.key`. Property тихо падает на default (обычно пустая строка/список), **без исключения** — баг незаметен, пока кто-то не заметит, что фича не работает (нашли на живой жалобе пользователя, issue #200: allowlist легитимных email-доменов из #84 никогда не читался, `@Value` возвращал `[]`). Для YAML-списков — `@ConfigurationProperties` или `Binder.get(environment).bind(key, Bindable.listOf(String.class))`, не `@Value`.

## 7. Самопроверка перед коммитом (то, что делал бы `/code-review`)

Пройтись по итоговому diff и явно ответить себе:
- Нет ли скопированного куска кода, который стоило вынести в общий метод?
- Нет ли метода/аннотации, которые выглядят рабочими, но не будут вызываться в реальном потоке выполнения (self-invocation, неправильный bean scope и т.п.)?
- Совпадает ли обработка edge-кейсов (пустой список, null, DOBLES vs INDIVIDUAL модальность и т.п.) с уже существующими соседними методами?
- Останутся ли комментарии актуальными (не описывают ли они то, что и так понятно из кода — по правилам CLAUDE.md комментарии должны объяснять "почему", а не "что")?
- Проходит ли `./mvnw verify` и, где применимо, ручная проверка (см. `GIT_WORKFLOW.md`, п.4)?

## Где искать паттерны для переиспользования

Прежде чем писать новый код — полезно проверить:
- `TournamentService.java` — батчинг, маппинг с деталями, работа с DOBLES/INDIVIDUAL модальностью.
- `EmailService.java` — конвенции `@Timed`/`@TrackErrors`, паттерн отправки писем.
- `mapper/` — все MapStruct-мапперы, конвенции именования DTO-методов.
- `TestTournamentController.java` — паттерны работы с гостевыми/guest-игроками, паттерны JDBC-запросов там, где не используется JPA.
