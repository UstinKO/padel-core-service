# 1‑Padel · мобильное приложение

Одна кодовая база Expo/React Native для iOS и Android. Первый инкремент подключает публичное расписание и детали событий к серверу сайта.

## Что реализовано

- Экран событий получает JSON из `/api/public/tournaments`, карточка — из `/api/public/tournaments/{id}`.
- Форматы, цена с валютой, время клуба, заполненность в игроках/парах, резерв, условия отмены и ссылка на конкретное событие.
- Фильтры, обновление, загрузка, пустой список и ошибки; интерфейс ES/RU/EN.
- Компактные карточки с датой, временем, названием формата, ценой и наличием мест. Нижняя панель фильтров: пол → уровень → формат → участие, предварительный счётчик, применение, сброс и удаление отдельных меток. Отдельный фильтр «Есть места». Уровни берутся из настоящего расписания с учётом выбранного пола; C9/C8 подходит обеим категориям, мероприятия для всех уровней тоже включены. В деталях — сворачиваемое описание и закреплённая панель цены/записи.
- В обычном режиме приложение не подменяет сбой сервера примерами.
- Вкладка организатора пока остаётся явно обозначенной локальной демонстрацией.


## Вход и «Мои мероприятия» (LFPT-0638)

Клиент работает с API, задеплоенным в LFPT-0637 (`docs/auth-flow.md`, `docs/endpoints/player-contact.md`). Исходный вариант из архива заказчика был написан под другой серверный patch (`/api/mobile-auth/*`, `/api/mobile/*`). Его не применяли, модуль `src/auth.ts` переписан под существующий сервер.

- Почта/пароль: `POST /api/auth/login`, обновление токена — `POST /api/auth/refresh`, профиль — `GET /api/auth/me`. Аккаунт организатора (`OwnerDto`) личных записей не получает: показывается сообщение, что нужен аккаунт игрока.
- Google (только веб-версия): переход на `/oauth2/authorization/google?client=app`, сервер возвращает на `/app/#accessToken=...&refreshToken=...&expiresIn=...`. Клиент сразу убирает токены из адресной строки. В нативном приложении вход через Google пока недоступен: вернуть токены из браузера некуда.
- «Мои мероприятия»: `GET /api/players/me/tournaments`. Предстоящие — со статусом записи и позицией в листе ожидания, история — только турниры (сервер не отдаёт статус записи для прошедших). Отменённые записи сервер не возвращает. Запись (LFPT-0660) и отмена (LFPT-0666) индивидуальных записей — в приложении; парная регистрация/отмена — на сайте.
- Анонимный или просроченный запрос к `/api/**` сервер не отклоняет `401`, а редиректит на `/login`. Клиент запрашивает с `redirect: 'manual'` и считает такой ответ истёкшей сессией.

Сессия (LFPT-0646): refresh-токен переживает закрытие/повторное открытие — в браузере через `localStorage` (только на HTTPS/`localhost`, `mobile-app/src/sessionStore.ts`), в нативном приложении — в Expo SecureStore, как и раньше. Access-токен в обоих случаях только в памяти, не персистится. Логаут удаляет сохранённый refresh-токен. Пароль не сохраняется.

## Сборка и проверка

```bash
pnpm install --frozen-lockfile
pnpm test && pnpm typecheck
pnpm build:site   # пересобирает ../src/main/resources/static/app (раздаётся на https://1-padel.com/app/)
```

Готовая сборка в `src/main/resources/static/app/` коммитится вместе с исходниками: сервер собирается Maven без Node. После правки исходников — пересобрать и закоммитить её.


## Индивидуальная запись из приложения (LFPT-0660)

Кнопка записи в деталях KING_OF_COURT, AMERICANO + INDIVIDUAL, PADEL_CLINIC, CANCHA_ABIERTA открывает IndividualBookingScreen. Парные мероприятия остаются на существующем сайте. Реальный POST `/players/tournaments/{id}/register` выполняется только после явного подтверждения пользователя и свежей проверки события, своих записей и контакта. ID игрока клиент не передаёт: используется Bearer-сессия. POST/PATCH не повторяются автоматически.

Существующая запись, CONFIRMED и WAITLIST различаются. Сохраняется позиция ожидания из ответа сервера. При изменении цены/условий/формата/мест подтверждение сбрасывается. После тайм-аута доступна сверка своей заявки, без повторного POST. Пока результат неоднозначен, повторная отправка из этой модели запрещена. При смене аккаунта старый экран не может отправить заявку от нового игрока.

WhatsApp/Telegram можно добавить через существующий PATCH `/api/players/me/contact`. При needLevel предлагается профиль сайта: узкого JSON API изменения уровня пока нет. Уровневые ограничения не дублируются на клиенте. Публичные данные не считаются гарантией места: итог даёт ответ сервера.

Выбор мероприятия перед Google сохраняется как ID в sessionStorage на 30 минут. После входа открывается экран проверки этого события; запись автоматически не создаётся. Хранилище сессии и SecureStore из LFPT-0646 сохранены.

Изолированная проверка того же экрана: `/?screen=individual-booking-test`. Это отдельная модель с вымышленными данными, без запросов записи на сайт. В ней доступны четыре формата, резерв, существующая запись, контакт, уровень, изменение цены и обрыв связи. Не использовать этот режим как доказательство реальной регистрации на проде.

Известные границы: проверка цены/условий перед POST не является атомарной серверной фиксацией цены. У API нет idempotency key: защита от повторов опирается на отсутствие автоматического повтора, сверку своих записей и серверную уникальность регистрации. После закрытия/перезагрузки клиента память о неоднозначном POST теряется, но новый вход в экран сначала проверяет существующую запись. Парные ветки в этот инкремент не входят (не изменилось — см. ниже).

## Индивидуальная отмена записи из приложения (LFPT-0666)

Симметрично записи (LFPT-0660): у активной (`CONFIRMED`/`WAITLIST`) регистрации на `KING_OF_COURT`/`AMERICANO` (modality `INDIVIDUAL`)/`PADEL_CLINIC`/`CANCHA_ABIERTA` в «Моих мероприятиях» есть действие «Отменить запись», открывающее компактную панель подтверждения прямо в карточке (`CancelBookingPanel.tsx`) — без отдельного полноэкранного перехода, в отличие от экрана записи. Парная (`DOBLES`) отмена остаётся на сайте.

Панель при открытии выполняет свежую проверку мероприятия и собственной регистрации (переиспользует `individualBooking.load()`), показывает дедлайн отмены и финансовые условия, требует явного согласия (чекбокс) перед подтверждением. Реальная отмена — ровно один `POST /players/tournaments/{id}/cancel` (Bearer-сессия, как и у записи). Изменение значимых полей мероприятия **или собственного статуса регистрации** (`WAITLIST` ↔ `CONFIRMED`, смена позиции в листе ожидания — LFPT-0675) между проверкой и подтверждением сбрасывает согласие (`individualBooking.cancellationQuote()`, отдельная от `bookingQuote()` сверка именно для отмены); повторное нажатие и обрыв связи не создают второй запрос (`individualBooking.cancel()`/`reconcileCancellation()`, те же `pending`/`uncertain`-защиты, что и у записи).

Сервер не возвращает неактивную (отменённую) регистрацию ни в `upcoming`, ни в `historical` «Моих мероприятий» — после успешной отмены мероприятие просто исчезает из списка при следующем обновлении, поэтому панель сама показывает явное подтверждение отмены, не полагаясь на последующее состояние списка. Отмена `CONFIRMED`-регистрации может сразу подтвердить следующего игрока в листе ожидания — существующая серверная логика (`TournamentService.cancelRegistration()`), в приложении не отображается синхронно.
