# Запрос на доработку

## Что нужно сделать

Провести предварительный анализ перехода тяжёлого в сопровождении монолита к многомодульному монолиту с гексагональной архитектурой. Исходно владелец видит пять модулей: DTO с генерацией из OpenAPI JSON, турнирные движки, БД и миграции, сервисный слой, контроллеры и эндпоинты. Создать в docs папку для анализа, ADR и плана, завести задачу на подготовку документации и декомпозиции.

Уточнение владельца: переход выполняется поэтапно; каждая реализованная задача должна сохранять работу приложения целиком.

## Где это происходит

Внутренняя архитектура padel-core-service. Подготовительная задача: [LFPT-1041](https://github.com/UstinKO/padel-core-service/issues/1041).

## Зачем это нужно

Упростить поддержку и изолировать изменения, не прерывая развитие и использование приложения.

## Кто это увидит/использует

Команда разработки. Игроки и организаторы должны сохранять существующие возможности на каждом этапе.

## Насколько срочно

Срок не задан; сейчас запрошены анализ и подготовка, а не перенос приложения.

## Примеры / референсы

Гексагональная архитектура и перечисленные пять модулей — исходное направление владельца. Техническая проверка соответствия и альтернативы входят в анализ.

## Есть ли ограничения

Не менять бизнес-правила. Каждая будущая задача оставляет приложение работоспособным. Реализация миграции, мерж и деплой не поручены. Создание GitHub issues и публикация подготовленной документации в PR поручены явно.

## Согласование владельца 13.11.2026

Количество модулей не ограничено пятью; готовы рассмотреть обоснованное предложение. Приняты разделение API/domain/entity, практичный Spring в application с приоритетом транзакций/ACID, OpenAPI → Java DTO и исключение record для generated-классов; результат генерации не коммитится. Микросервисная инфраструктура сейчас не создаётся. Нужен небольшой давно не менявшийся пилот и отдельная e2e-задача со скриптами и ручными нажатиями до/после. Переезд хранения/БД — поздно либо в согласованное окно Swarm; точный вид переезда уточняется. Семь модулей и PlayoffMatchingEngine пока предложены, не приняты владельцем.

## Финальное подтверждение направления 13.11.2026

Владелец принял архитектуру семи модулей и PlayoffMatchingEngine как пилот. Поручено обновить документы, дополнить отсутствующие, детально проанализировать код и сформировать первую фазу/пул задач. Выделение БД/хранения в новый модуль — отдельная поздняя задача: в согласованном окне Swarm либо в конце многомодульного перехода. Физический перенос PostgreSQL не следует автоматически из Maven-переноса.

## Завершение подготовки

Владелец поручил завершить подготовительную задачу и опубликовать документы в PR после проверки отсутствия чувствительных данных. Подготовка охватывает согласованные решения и подробную первую фазу; последующие срезы декомпозируются по результатам пилота. Закрытие #1041 выполняется через Closes в описании PR при мерже, без закрытия реализационных задач.
