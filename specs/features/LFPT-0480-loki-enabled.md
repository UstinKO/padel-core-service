## Контекст / зачем

Основная конфигурация Logback безусловно подключает Loki к логгеру `com.padle.core`,
хотя свойство `logging.loki.enabled` по умолчанию равно `false`.
Фоновые ошибки отправки в недоступный Loki могут накапливаться в общем `LoggerContext`
и приводить к падению последующей инициализации логирования Spring Boot.
Обычные тесты используют отдельный `logback-test.xml`, поэтому успешный полный Maven-прогон
сам по себе не проверяет исправность основной конфигурации.

## Связь с MASTER.md

Задача относится к инфраструктуре логирования. Роли, бизнес-сценарии и инварианты
[MASTER.md](../MASTER.md) не меняются. Обновление мастер-спецификации не требуется.

## Требования

### Функциональные

- При `logging.loki.enabled=false` или отсутствии свойства Loki-аппендер не создаётся,
  не запускается и не подключается; сетевых обращений к Loki нет.
- При значении `true` к `com.padle.core` подключён ровно один запущенный Loki-аппендер.
- Выключатель действует независимо от профиля при использовании `logback-spring.xml`,
  включая `prod` и `production`. Сам production-профиль не включает Loki.
- `preview` сохраняет отдельную конфигурацию `logback-preview.xml` и существующее отключение Loki.
- При явной переинициализации логирования с переходом `true → false` прежний аппендер
  останавливается; сообщения после завершения переинициализации в Loki не отправляются.
- Ошибки действительно включённого, но недоступного Loki не подавляются.
- Подключения остальных аппендеров, уровни логирования и `additivity` сохраняются.

### Нефункциональные

- Не добавлять Janino, новые зависимости и обновления библиотек: в проекте уже используется Logback 1.6.5.
- Сохранить URL, авторизацию, параметры пакетирования, метки, формат сообщения и маскировку данных Loki.
- Сохранить Java release 17; сборку запускать установленным JDK 21 через переменные текущего процесса.
- Регрессионный тест основной конфигурации не требует PostgreSQL и внешних сервисов.
- Новых пользовательских строк и точек входа нет; изменения ES/RU/EN не требуются.
- Не включать реальные реквизиты, секреты и приватные адреса в тестовые отчёты.

## Вне скоупа

## Изменения в системе

### Конфигурация логирования

В `src/main/resources/logback-spring.xml`:

1. Сохранить `springProperty` для `LOKI_ENABLED`, источник `logging.loki.enabled`,
   `scope="context"`, `defaultValue="false"`.
2. Удалить безусловные ссылки на `LOKI` из общего логгера `com.padle.core`
   и профильного блока `prod,production`.
3. После профильных настроек и объявления свойств Loki разместить на уровне `<configuration>`
   условие `ch.qos.logback.core.boolex.PropertyEqualityCondition` с ключом `LOKI_ENABLED`
   и значением `true`. Элемент `<condition>` располагается перед `<if>`.
4. Внутрь `<if><then>` перенести существующее определение аппендера `LOKI` целиком,
   затем добавить `<logger name="com.padle.core">` с единственной ссылкой на этот аппендер.
   В дополнительном объявлении логгера не задавать `level` и `additivity`.
5. Не вкладывать условие внутрь `<logger>` или `<appender>`.

Синтаксис условия описан в [документации Logback](https://logback.qos.ch/manual/configuration-conditional.html).
Приложение сохраняет умолчание `false`, Docker Compose — `${LOKI_ENABLED:-true}`.

### Регрессионные тесты

Добавить `LokiLoggingConfigurationTest` в существующий пакет тестов логирования.
Явно загружать `classpath:logback-spring.xml` через Spring Boot LoggingSystem
с заданными Environment и профилями, без запуска приложения, сканирования компонентов,
автоконфигурации БД и фоновых бизнес-задач. Проверка только XML-текста недостаточна.

Каждый сценарий выполнять в дочерней JVM, используя Java из текущего `java.home`.
Повторные инициализации одного сценария выполнять внутри одной дочерней JVM.
Не перенастраивать `LoggerContext` JVM общего тестового набора.

| Сценарий | Профили | Ожидаемый результат |
|----------|---------|---------------------|
| Свойство отсутствует | Каждый вариант из матрицы ниже | Loki отключён; проверяется XML `defaultValue` |
| `false` | Каждый вариант из матрицы ниже | Loki не подключён, HTTP-запросов нет |
| `true` | Каждый вариант из матрицы ниже | Ровно один запущенный Loki-аппендер; контрольное сообщение доставлено |
| Две инициализации с `false` | Без активного профиля и `prod` | Обе успешны, ошибок Loki нет |
| Явная переинициализация `true → false` | Без активного профиля и `prod` | Старый аппендер остановлен, новые сообщения не отправляются |

Матрица: без активного профиля, явный `default`, `dev`, `development`, `test`, `staging`,
`prod`, `production`. Отсутствие активного профиля проверять отдельно от явного `default`.

Перед изменением XML зафиксировать фактические подключения, уровни и `additivity`
для проверяемых профилей. После исправления проверять их сохранение, исключив намеренно
изменённое подключение Loki; не подменять фактическое поведение намерениями из комментариев XML.

Для сетевых проверок использовать встроенный HTTP-сервер на `127.0.0.1` со свободным портом,
обрабатывать `/loki/api/v1/push` и отвечать `204`. При `true` проверять получение уникального
контрольного сообщения, а не просто любого запроса; учитывать фактический формат тела запроса Loki4j.
При выключенном Loki оставлять сервер доступным и проверять нулевой счётчик обращений.

Тестовый batch timeout — `100` мс. При выключенном Loki наблюдать отсутствие запросов
не менее `500` мс после контрольного логирования, дополнительно проверять отсутствие подключённого
аппендера и ошибок. Ожидание доставки ограничить 10 секундами, выполнение каждого дочернего
процесса — 30 секундами. Логи и вывод процессов направлять во временный каталог;
вывод не должен блокировать дочерний процесс из-за заполнения pipe.

Передавать локальный URL явно; исключить влияние внешних переменных Loki, авторизации
и настроек JVM. В сценарии отсутствующего свойства действительно не задавать значение,
а не подставлять `false`. Серверы, контексты и собственные процессы закрывать в `finally`.
При таймауте завершать только созданный тестом процесс и показывать его диагностику.

До исправления XML запустить новый тест и сохранить результат ожидаемого падения
из-за подключённого Loki при `false`. После исправления тот же тест должен пройти.
Не очищать `StatusManager` вручную ради прохождения проверки и не подавлять исключения инициализации.

## Критерии приёмки

- [ ] Новый тест загружает основную конфигурацию через Spring Boot и воспроизводимо падает на исходном XML при `false`.
- [ ] После исправления вся матрица отсутствующего свойства и `false` проходит: Loki не запускается и HTTP-запросов нет.
- [ ] Вся матрица `true` проходит: подключён один запущенный аппендер, уникальное контрольное сообщение доставлено локальной заглушке.
- [ ] Две последовательные инициализации с `false` проходят в одном `LoggerContext` без ERROR-статусов.
- [ ] При явном переходе `true → false` сохранённый экземпляр аппендера остановлен, новое контрольное сообщение не доставляется.
- [ ] Остальные подключения аппендеров, уровни и `additivity` соответствуют исходной конфигурации.
- [ ] Целевой прогон нового и существующих тестов логирования проходит.
- [ ] Полный `mvnw.cmd verify` проходит на отдельной PostgreSQL с выключенным Loki; `TelegramTestControllerSecurityTest` проходит в общем наборе.
- [ ] `docs-drift.py`, тесты `automation/telegram-relay`, `check-agent-migration.py` и `git diff --check` проходят.

## Edge cases

- `prod` и `production` не обходят выключатель; `dev` и `development` проверяются отдельно.
- Тест не наследует включение Loki и реальные реквизиты из локального окружения.
- Переинициализация действительно повторно применяет XML, а не пропускается механизмами Boot.
- При переходе `true → false` сначала дождаться доставки первого сообщения, затем выполнить
  штатную переинициализацию и начать проверку новых сообщений: ранее накопленный батч
  не должен искажать счётчик выключенного состояния.
- Структурная проверка отсутствия аппендера дополняет ограниченное по времени сетевое наблюдение.
- Маскировка и штатная диагностика ошибок включённого Loki сохраняются.
- Миграция данных и изменение поведения существующих записей не требуются.
