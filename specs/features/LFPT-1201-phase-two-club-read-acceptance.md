## Контекст / зачем

Первый после движка небольшой срез — публичное чтение клубов. Последовательность отделяет проверку генерации, границу application, wire-контракт и независимую приёмку.

## Связь с MASTER.md

Бизнес-правила, роли и публичные данные сохраняются. Новых пользовательских строк, внутреннего HTTP и изменения БД нет.

## Требования

## Цель
Независимая приёмка read-сценария и generated Club DTO на конечном jar после двух backend-переносов. UI не перерабатывается. Исходные и итоговые результаты сравниваются на синтетических данных в отдельном preview.

## Критерии приёмки
- [x] Зафиксированы SHA/jar, отдельный baseline HTTP/JSON для двух клубных GET и результаты backend verify/границ модулей. Не переносить PASS пилота движка как результат этого среза.
- [x] Реальным браузером проверены список/карточка клуба, ссылки из каталога/карточки события и фильтр клуба; desktop/mobile, deep link/refresh, пустой список, неизвестный/неактивный клуб и nullable публичные поля.
- [x] Сохранены порядок, RU/ES/EN, canonicalUrl, ProblemDetail/HTTP/headers, роли/session/CSRF/JWT и прежние потребители контрактов; в UI не попадают JPA/персональные служебные данные.
- [x] Общий legacy/API/React/Expo smoke конечного артефакта и проверяемый rollback пройдены. Expo оболочка не считается рабочим расписанием: API должен получить фактический 200; ограничение preview оформляется отдельно, без production-ослабления защиты.
- [x] Состояние после restart/возврата прежнего jar сохранено. Изменяющие сценарии общего smoke используют отдельные данные, не сбрасывают сохранённый ручной стенд #1045.
- [x] Ручные действия владельца, действия агента, автоматизация и принятые ограничения перечислены раздельно; найденные дефекты вынесены по слоям, вывод о продолжении переноса основан на фактах.

## Общие гарантии
Java release 17; бизнес-правила MASTER, HTTP/JSON/WS, ES/RU/EN, права и данные сохраняются. Изменений БД/Liquibase и production-переключения UI нет. Один слой и отдельный PR. Каждый реализационный PR самостоятельно сохраняет работоспособность приложения: корневой ./mvnw verify на отдельном PostgreSQL, smoke конечного jar/образа, legacy/API/React/Expo, проверка возврата на предыдущий артефакт. Runtime и доступы не публикуются; pipeline:ready, мерж и деплой подготовкой не разрешаются.

## Изменения в системе

### API
Существующие GET /api/public/clubs и /api/public/clubs/{id}; контракт сохраняется. В приёмке endpoints и production-код не меняются.

### БД
Без миграций/переноса данных. PostgreSQL и Liquibase принадлежат поздней #1051.

### UI
Без изменения пользовательского интерфейса; потребители — React ClubPages/Catalogue/EventPage и API discovery.ts. Результаты приёмки приведены в phase-2/acceptance.md.

## Edge cases

Пустой список, неизвестный/неактивный ID, нечисловой ID, nullable поля, порядок nombre/id, отказ БД, base URL с завершающим /, внешние OpenAPI $ref, неподдерживаемый тип генератора, старая вкладка клиента и возврат прежнего jar.

## Открытые вопросы

Бизнес-вопросов нет. Технические решения принимаются по результатам кода/пробы и фиксируются в ADR; совместимость не объявляется заранее.
