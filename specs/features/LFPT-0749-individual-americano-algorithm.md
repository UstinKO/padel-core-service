# LFPT-0749: Fix алгоритм индивидуального Americano — равномерное распределение соперников и кортов, автопроверка расписания

## Статус
approved

## Источник
Клиентский запрос [specs/requests/LFPT-0749-individual-americano-algorithm.md](../requests/LFPT-0749-individual-americano-algorithm.md), issue [#749](https://github.com/UstinKO/padel-core-service/issues/749). Telegram-сообщение (для reply): 5614.

## Контекст / зачем

Текущий алгоритм генерации раундов индивидуального Americano (`AmericanoService`) имеет два независимых пути генерации:

- **Full** (`buildFullAmericano`) — применяется только когда `N == courts*4` (все играют каждый раунд, без bye). Партнёрские пары строит методом круга (`buildCirclePairs`) — это классический round-robin 1-factorization, он **математически корректен**: для чётного `N` даёт `N-1` раундов, где каждая пара партнёров встречается ровно один раз, без повторов. Это уже закрывает требование 2.1 ТЗ и не нуждается в переписывании.
- **Flex** (`buildFlexAmericano`) — произвольный `N`, с bye. Партнёрские пары каждого раунда ищутся жадным поиском с 500 случайными попытками (`findFlexMatchArrangement`), без гарантий.

**Найденная причина жалобы (турнир №127, 20/5/19 — это ровно случай Full: `20 == 5*4`):**

1. Группировка уже построенных партнёрских пар по матчам/кортам (`pairPartnersIntoMatches`, используется в обоих путях) — это однопроходный **жадный** алгоритм без возврата: он обрабатывает пары по порядку и для каждой жадно выбирает "лучшую" оставшуюся пару-соперника по сумме уже накопленных встреч. Жадность без перебора не гарантирует глобальный минимум отклонения — на реальных данных пары легко расходятся на 1/3 встречи вместо идеальных 2/2 (требование 2.2 нарушается).
2. **Распределение по кортам отсутствует как шаг алгоритма вообще.** Номер корта — это просто порядковый индекс матча в списке (`courtNumber(c + 1)`), без какой-либо связи с историей, кто на каком корте уже играл. Отсюда жалоба на неравномерные серии на одном корте (требование 2.3) — баг, а не "почти правильно работающий" код.
3. `isFullAmericanoPossible` допускает `N`, кратное `courts*4` (несколько "залов" сразу), но `buildFullAmericano` тут же откатывается на Flex, если `N != courts*4` — расхождение проверки и реализации (не влияет на репортнутый баг 20/5/19, но это дефект консистентности, фиксируется тем же рефакторингом).

## Связь с MASTER.md

Фича не меняет `specs/MASTER.md` — там Americano описан только на уровне "все играют со всеми, индивидуальный рейтинг" (раздел "Форматы турниров"), без деталей алгоритма генерации раундов. Инвариант не меняется.

## Решение (архитектура алгоритма)

Текущий код (`buildFullAmericano`, `buildFlexAmericano`, `buildCirclePairs`, `pairPartnersIntoMatches`, `findFlexMatchArrangement`, `greedyPairMatch`, `shuffleEqualGroups`, `selectPlayersForRound` — порядка 350 строк в `AmericanoService`, который уже превышает ориентир 500 строк на сервис, CODE_STYLE.md §6.1) выносится в новый компонент **`AmericanoScheduleEngine`** — чистая функция без Spring/JPA-зависимостей (CODE_STYLE.md §6.2), легко покрываемая unit-тестами без контекста Spring. `AmericanoService` вызывает его и маппит результат (индексы игроков) на сущности, как и раньше.

Единый алгоритм на раунд (без разделения на Full/Flex — ветвление остаётся только в выборе способа построения партнёрских пар):

1. **Выбор активных игроков раунда.** Если `N <= courts*4` — играют все (без bye, это все 5 обязательных конфигураций из ТЗ). Иначе — модифицированная версия текущего `selectPlayersForRound` (ротация по минимуму bye/давности bye/сыгранных матчей — логика не менялась, уже разумная).
2. **Партнёрские пары раунда:**
   - Если активный состав не меняется между раундами (`N <= courts*4`, самый частый и весь обязательный по ТЗ случай) — метод круга (`buildCirclePairs`, без изменений): математическая гарантия нулевых повторов партнёров на полном цикле `N-1` раундов.
   - Если активный состав разный от раунда к раунду (bye) — минимальное по весу совершенное паросочетание (см. ниже) по накопленному счётчику партнёрств вместо жадного 500-попыточного поиска.
3. **Группировка партнёрских пар раунда в матчи (кто кому соперник).** Вместо однопроходной жадности — **точный** поиск минимального по весу совершенного паросочетания на графе "партнёрская пара — партнёрская пара" (вес ребра = сумма уже накопленных встреч между игроками двух пар). Размер графа мал (`courts*2 ≤ 12` для всех конфигураций ТЗ) — решается битмаск-ДП за миллисекунды, даёт провально-оптимальную на каждом шаге группировку (требование 2.2) вместо приближённой.
4. **Назначение кортов — отдельный шаг** (как и предлагает заказчик в ТЗ, п.2.3 "рекомендуется отдельным этапом"): минимальное по стоимости назначение "матч → корт" тем же битмаск-ДП (размер — число кортов, ≤ 6 для всех конфигураций ТЗ). Стоимость = Σ по 4 игрокам матча (счётчик визитов игрока на этот корт + штраф, если это будет 3-й подряд матч игрока на этом же корте). Закрывает требование 2.3, которое в текущем коде не реализовано вообще.
5. Обновление счётчиков (партнёры/соперники/корты/bye) и переход к следующему раунду.

Для `N`, не кратного `courts*4` (есть bye) — п.2.1 ТЗ формально недостижим для **всех** пар (не все 19 партнёров у каждого — pigeonhole), поэтому для этого случая гарантия "0 повторов" не математическая, а наилучшая по истории (минимальный вес на каждом шаге); тест-план (см. ниже) это не проверяет как hard-constraint — только для 5 обязательных конфигураций (все без bye) требование 2.1 проверяется как строгий инвариант.

### Автопроверка расписания — `AmericanoScheduleValidator`

Новый компонент, чистая функция: принимает сгенерированное расписание (раунды/матчи), возвращает `AmericanoScheduleReport`:
- `partnerCounts: Map<пара игроков, количество>`, `partnerRepeats` (пары > 1), `playersWithoutPartner` (для полного цикла);
- `opponentCounts` (мин/макс/среднее на пару);
- `courtVisits` (на игрока на корт), `maxConsecutiveSameCourt` (на игрока), `courtsNeverVisited`;
- `roundViolations` — список нарушений **обязательных** условий (игрок дважды в раунде, не 4 уникальных игрока в матче, число матчей раунда не равно `min(courts, активные/4)`).

`roundViolations` — hard: непустой список означает баг генератора, `AmericanoService.generateRounds` в этом случае бросает `InvalidStateException` (а не тихо сохраняет мусор — требование 2.4/2.5 ТЗ). Для случая без bye (`N % (courts*4) == 0`, все обязательные конфигурации ТЗ) `partnerRepeats > 0` **тоже** hard — это означало бы регрессию метода круга, такого не должно произойти математически.

### FULL/FLEX — сохраняется как есть

`AmericanoConfigDto.generationMode` (AUTO/FULL/FLEX) и `AmericanoFormatType` на UI (`admin/americano/tournament.html` — зелёный/оранжевый баннер) не меняются: `verifyFormat()` после генерации по-прежнему размечает результат как FULL (все пары партнёров покрыты ровно 1 раз) или FLEX, `isFullAmericanoPossible` остаётся условием для режима `FULL`/`AUTO`. `previewRounds()` в `AmericanoViewController`/`AmericanoApiController` — без изменений сигнатур, использует тот же `AmericanoScheduleEngine` вместо дублирующей копии логики (сейчас код `previewRounds` в `AmericanoService` почти буквально повторяет `buildFlexAmericano` — устраняется дублирование, CODE_REVIEW.md §2).

## Требования

### Функциональные

- Партнёрские пары без bye (`N == courts*4`, обязательные конфигурации 8/2/7, 12/3/11, 16/4/15, 20/5/19, 24/6/23) — 0 повторов на полном цикле `N-1` раундов, проверено валидатором как hard-constraint.
- Группировка пар в матчи и назначение кортов — через точные битмаск-ДП алгоритмы (не жадность, не случайный поиск).
- Корты: для каждого игрока визиты на корты максимально равны (для конфигураций ТЗ — разница не больше 1 между самым и самым редко посещаемым кортом за полный цикл), не более 2 подряд матчей на одном корте, если это достижимо без нарушения п.1-3 ТЗ.
- Соперники: для конфигураций ТЗ (без bye) — среднее 2 встречи на пару (математически доказано: `N·(N-1) / C(N,2) = 2`); алгоритм минимизирует отклонение от 2 на каждом шаге, тестами проверяется фактический разброс (min/max).
- `AmericanoService.generateRounds` бросает `InvalidStateException` при нарушении hard-constraints валидатора — расписание не сохраняется.
- Существующие сохранённые раунды/матчи других турниров не пересчитываются и не меняются — фикс затрагивает только генерацию **новых** расписаний (вызывается из `initializeAmericanoTournament` и `previewRounds`, оба — только для турниров, которые ещё не инициализированы или explicit preview).

### Нефункциональные

- Производительность: генерация одной конфигурации (включая валидацию) — не более нескольких секунд, 100 последовательных генераций в тесте — разумное время (десятки секунд, не минуты); никаких зависаний (используются только детерминированные точные алгоритмы на малых графах — без случайного перебора без ограничения попыток, в отличие от текущего кода).
- i18n: новых пользовательских строк не добавляется (сообщение `buildFormatMessage` уже локализовано как общий текст сервиса — не меняется по содержанию, только источник данных).
- Безопасность: новой точки входа данных от пользователя нет — `AmericanoConfigDto` уже существующий вход, валидация параметров (`courts >= 1`, `totalRounds >= 1`, `N >= 4`) — как и раньше.

## Вне скоупа

- Team Americano / Team Playoff / King of Court / bracket-турниры — не трогаем (другой сервис, `TeamAmericanoService`).
- Фронтенд (шаблоны `admin/americano/*.html`, JS) — поведение баннера FULL/FLEX не меняется, новый UI не требуется (чисто backend-фикс алгоритма). Отдельная фронт-задача не нужна.
- Миграция/пересчёт расписаний уже существующих/проводимых турниров — явно запрещено условием заказчика.
- Полная математическая гарантия равномерности соперников/кортов для bye-конфигураций (переменный активный состав раунда) — лучшее по истории на каждом шаге, не глобальный оптимум по всему турниру; ТЗ сам явно требует не постулировать достижимость идеала для произвольного N.
- Специальные правила "не сводить двух последних без соперника" для 10/14 команд — это из другого (парного/плейофф) ТЗ в `.claude/commands/americano-para.md` (issue #81), не относится к индивидуальному Americano.

## Критерии приёмки

- [ ] Для каждой из 5 конфигураций (8/2/7, 12/3/11, 16/4/15, 20/5/19, 24/6/23) — минимум 100 независимых генераций, 100% проходят валидатор без нарушения hard-constraints (п. "Партнёры", "Раунды" спеки) — unit-тест.
- [ ] Для тех же конфигураций — ноль повторов партнёрских пар в каждой из 100 генераций (математическая гарантия метода круга подтверждена тестом, не просто предположение).
- [ ] Для тех же конфигураций — средняя и максимальная разница между мин/макс количеством встреч соперников по всем 100 генерациям заметно меньше, чем у наивного жадного алгоритма (baseline-сравнение в тесте или явный numeric threshold, например max-min ≤ 2 в среднем) — регрессионный тест против жалобы "соперники совсем не равномерны".
- [ ] Для тех же конфигураций — ни один игрок не имеет более 2 подряд матчей на одном корте ни в одной из 100 генераций (или явно задокументированная редкая погрешность с численным порогом) — тест на корты.
- [ ] 100 генераций на каждую конфигурацию выполняются без зависаний — тест укладывается в разумный таймаут (например, суммарно < 60 секунд на все конфигурации).

- [ ] Существующие тесты `AmericanoServiceByePlayersTest` и другие Americano-тесты продолжают проходить без изменений (убедиться, что публичное поведение `getRound`/`getRounds` не затронуто рефакторингом).

## Edge cases

- `N < 4` — уже отбрасывается раньше (`initializeAmericanoTournament`, `playerCount < 4`), не меняется.
- `totalRounds > N - 1` (больше раундов, чем позволяет полный цикл без bye) — повторы партнёров математически неизбежны (pigeonhole); алгоритм не падает, продолжает минимизировать повторы по истории (не hard-constraint за пределами `N-1` раундов) — явно не покрывается тестом на "0 повторов", только базовым тестом на отсутствие зависаний/корректность раунда.
- `courts * 4 > N` при `N` не кратном `4` — часть кортов не используется часть раундов (меньше матчей, чем кортов) — уже было (`playersPerRound` считает по максимуму), сохраняется.
- Повторный вызов `previewRounds` на тот же турнир — чистая функция, детерминированного seed нет (как и раньше, допускается разный результат при каждом вызове — не требование ТЗ, ТЗ не просит детерминизм).
