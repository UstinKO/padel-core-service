# LFPT-0562: Feature форма «Agregar equipo» Team Playoff — поиск игрока вместо ID, быстрое создание нового (frontend)

## Статус
approved

## Источник
Клиентский запрос [specs/requests/LFPT-0561-manual-team-add-search.md](../requests/LFPT-0561-manual-team-add-search.md) (Telegram, пересланное сообщение от Evgeny_754, `telegram_launch_message_id: 5060`). GitHub issue [#562](https://github.com/UstinKO/padel-core-service/issues/562). Зависит от бэкенд-задачи [#561](https://github.com/UstinKO/padel-core-service/issues/561) (поиск игрока, создание нового с дедупом по телефону, видимость команды в оплатах) — спека [LFPT-0561-manual-team-add-search-backend.md](LFPT-0561-manual-team-add-search-backend.md).

## Контекст / зачем

Бэкенд (#561) добавляет поиск игрока и поддержку создания нового профиля для обоих слотов команды. Но форма «Agregar equipo» на `admin/americano/tournament-playoff.html` (блок `#addTeamForm`) до сих пор требует вводить числовые `player1Id`/`player2Id` — без UI-поиска этим механизмом физически неоткуда воспользоваться. Цель — заменить два числовых поля на поиск с автодополнением и переключатель "новый игрок", чтобы координатор клуба мог добавить пришедшую на месте команду за 20–30 секунд, не зная ID.

## Связь с MASTER.md

Не затрагивает инвариантов `specs/MASTER.md` — UI-слой над механизмом поиска/создания игрока из #561. Доступ не меняется: форма видна тем же ролям, что и сейчас (`SUPER_ADMIN, ADMIN, ORGANIZER, CLUB_ADMIN`, см. `TeamPlayoffViewController`).

## Требования

### Функциональные

1. **Замена числовых полей ID на поиск, для каждого игрока команды независимо.** В форме `#addTeamForm` (`admin/americano/tournament-playoff.html`, `teams/add`) сейчас: `player1Id` (number, required), `player2Id` (number, optional), `player2Name`/`player2Phone` (текст, fallback для player2). Переработать на два одинаковых блока "Игрок 1" и "Игрок 2", в каждом:
   - поле поиска (имя/фамилия или телефон) → запрос к новому эндпоинту `GET .../players/search?query=...` (#561) с debounce (не на каждое нажатие клавиши — после паузы в наборе, ~300мс, по аналогии с другими автодополнениями в проекте, если есть, иначе разумный дефолт);
   - выпадающий список найденных игроков (имя, телефон) — выбор заполняет скрытое поле `playerXId` этого слота и визуально показывает, что игрок выбран (например, замена поля поиска на карточку "Иван Петров, +54 9 ..." с возможностью сбросить выбор и искать снова);
   - если нужного игрока нет в списке — переключатель/кнопка «Новый игрок» открывает поля имя, фамилия, телефон для этого слота; при отправке формы эти поля уходят как данные для создания нового игрока (а не как `id`).
2. **Оба слота работают одинаково и независимо** — поддержаны все 4 комбинации из клиентского запроса (оба существующих / 1-й существующий-2-й новый / наоборот / оба новых); выбор режима для игрока 1 не ограничивает выбор режима для игрока 2 (сейчас `player1Id` — всегда обязательный существующий ID, это ограничение снимается здесь на уровне UI вслед за бэкендом).
3. **Явная индикация режима слота.** Видно, какой из двух режимов (поиск/новый) активен для каждого игрока — не оставлять оба набора полей видимыми одновременно без подсказки, какой из них будет использован при сохранении (путает, особенно если и поиск, и поля нового игрока заполнены одновременно).
4. **Остальные поля формы не меняются.** `registrationSource`, `hasPaid`/`attended` (чекбоксы), `adminComment` — как есть, без изменений разметки/поведения.
5. **Поведение после сохранения — как сейчас.** POST на `teams/add`, редирект на страницу Team Playoff, flash-сообщение об успехе/ошибке (`ra.addFlashAttribute`) — не меняется.
6. **Нет JS-ошибок и валидация перед отправкой.** Если для какого-то из двух слотов не выбран ни существующий игрок, ни заполнены все три поля нового игрока (имя, фамилия, телефон) — не отправлять форму, показать понятную подсказку (аналогично существующему `required` на текущем `player1Id`, но адаптировано к новому UI).

### Нефункциональные
- i18n: новые пользовательские строки формы (placeholder поиска, текст переключателя "Новый игрок"/"Выбрать существующего", подсказки "не выбран игрок" и т.п.) — новые ключи в namespace `admin.playoff.form.*` (по аналогии с существующими `admin.playoff.form.player1_id`, `admin.playoff.form.player2_name` и т.д.) во все три `messages_{es,ru,en}.properties`. Существующие ключи `admin.playoff.form.player1_id`, `player2_id`, `player2_name`, `player2_phone` и их `placeholder.*` — заменяются/перестают использоваться там, где поля убраны; не оставлять неиспользуемые ключи, если они больше нигде не нужны (проверить `grep` по шаблонам перед удалением).
- Безопасность: новой точки входа данных, кроме уже предусмотренной бэкендом (#561), нет — JS только формирует запросы к существующему (после #561) эндпоинту поиска и обычную отправку формы.
- Производительность: debounce на поиск, чтобы не слать запрос на каждый символ.

## Вне скоупа
- Сам поиск/создание/дедуп на сервере — реализован в [#561].
- Изменение любых других форм (страница оплат, тестовая страница `/test/tournaments`) — не трогается.
- Применение такого же поиска к форме редактирования уже существующей команды (`teams/{teamId}/update`) — явно не запрошено клиентом (запрос описывает только сценарий **добавления** новой команды), вне скоупа.

## Изменения в системе

### API
Нет новых эндпоинтов со стороны фронтенда — использует `GET .../players/search` и `POST .../teams/add` из [#561].

### БД
Нет.

### UI
- `src/main/resources/templates/admin/americano/tournament-playoff.html` — блок `#addTeamForm`: замена полей `player1Id`/`player2Id`/`player2Name`/`player2Phone` на два одинаковых блока поиска/создания игрока.
- Новый JS-файл (например `static/js/team-playoff-player-search.js`) — debounce-поиск, рендер списка найденных игроков, переключение режимов поиск/новый для каждого слота, валидация перед отправкой.
- `src/main/resources/i18n/messages_es.properties`, `messages_ru.properties`, `messages_en.properties` — новые ключи для UI поиска/создания игрока, удаление более не используемых (если убедились, что не используются больше нигде).

## Критерии приёмки
- [ ] На странице `/tournaments/team-playoff/admin/{tournamentId}` в форме «Agregar equipo» для каждого из двух игроков — поле поиска вместо числового ID.
- [ ] Ввод части имени/фамилии существующего активного игрока показывает его в выпадающем списке; выбор заполняет скрытый ID этого слота.
- [ ] Ввод телефона существующего игрока находит его так же, как поиск по имени.
- [ ] Если игрок не найден — переключатель «Новый игрок» открывает поля имя/фамилия/телефон для этого слота.
- [ ] Форма отправляется и создаёт команду для всех 4 комбинаций: оба существующих / 1-й существующий + 2-й новый / 1-й новый + 2-й существующий / оба новых (ручная проверка в браузере, Playwright).
- [ ] Попытка отправить форму без выбора игрока и без заполненных полей нового игрока хотя бы для одного слота — блокируется на клиенте с понятной подсказкой.
- [ ] Ручной прогон: от открытия формы до успешного сохранения команды с двумя новыми "с улицы" игроками — укладывается в заявленные клиентом 20–30 секунд (без необходимости искать/вводить ID).
- [ ] Новые i18n-строки присутствуют и не пустые во всех трёх `messages_{es,ru,en}.properties`; страница под `Accept-Language: ru` не показывает испанских строк для нового UI.
- [ ] `./mvnw verify` зелёный; регрессии на остальной части страницы Team Playoff (список команд, квалификация, плей-офф) нет.

## Edge cases
- Поиск возвращает 0 результатов — явно показать "ничего не найдено" с подсказкой создать нового игрока, не оставлять пустой список без объяснения.
- Пользователь выбрал существующего игрока, затем передумал — должна быть возможность сбросить выбор и снова ввести поисковый запрос или переключиться в режим "новый игрок".
- Медленный/ошибочный ответ эндпоинта поиска (сеть, 500) — не ломать форму целиком; показать, что поиск недоступен, оставить возможность переключиться в режим "новый игрок" как запасной вариант.
- Мобильная/узкая ширина экрана (админка используется и с телефона на месте турнира, см. клиентский сценарий "добавить на месте") — блоки поиска для двух игроков не должны разъезжаться/перекрываться на маленьком экране.
- `#562` смержен раньше `#561` (backend не готов) — поле поиска обращается к несуществующему эндпоинту; это ожидаемое промежуточное состояние при раздельном мерже (как и в прецеденте LFPT-0541/0542), устраняется мержем #561.

## Открытые вопросы
Нет. Одно техническое решение принято архитектором самостоятельно (аналогично `GIT_WORKFLOW.md §3`):
1. Поиск — одно текстовое поле на слот (ищет и по имени, и по телефону одним запросом, как и сам backend-эндпоинт #561), а не два отдельных поля "искать по имени"/"искать по телефону" — проще для пользователя ("просто начни печатать"), не требует от координатора заранее решать, чем он ищет.
