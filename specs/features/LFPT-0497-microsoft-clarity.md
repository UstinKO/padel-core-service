# LFPT-0497: Feature подключение Microsoft Clarity на сайте 1-padel.com

## Контекст / зачем
Заказчику нужна аналитика поведения посетителей сайта 1-padel.com (session recordings, heatmaps — где задерживаются, что нажимают, где возникают UX-проблемы) через Microsoft Clarity, Project ID `yu4n92bsuy`. Проверено `grep` по `src/main/resources` (templates + static/js) на `clarity.ms|clarity(` — в проекте Clarity ещё не подключена.

В проекте уже есть аналогичная интеграция стороннего веб-аналитического тега — Google Analytics 4 (issue #468, PR #470, `templates/fragments/analytics.html`). Эта спека переиспользует то же архитектурное решение (один fragment + явное подключение в `<head>` нужных страниц + расширение CSP + расширение `cookie-consent.js`), не изобретая параллельный механизм (`CODE_REVIEW.md` §2 DRY).

## Связь с MASTER.md
Не затрагивает бизнес-инварианты MASTER.md — чисто техническая интеграция стороннего веб-аналитического сервиса в публичный UI. Изменений в MASTER.md не требуется.

## Важные архитектурные находки (определяют реализацию)

1. **Та же архитектура фрагмента, что и у GA4.** `templates/fragments/analytics.html` уже существует (`th:fragment="ga4"`, LFPT-0468) и уже подключён (`th:replace`) во все страницы, которые нужны по этому запросу. Решение: добавить в тот же файл второй `th:fragment="clarity"`, подключить его вторым `th:block` сразу после `ga4` на тех же страницах — не создавать отдельный файл-фрагмент.
2. **Запрос у́же, чем список GA4 (23 страницы).** Заказчик явно ограничил зону: "главная страница, страницы турниров и процесс записи [регистрации]". Конкретный список (технический выбор, не бизнес-вопрос — GIT_WORKFLOW.md §3):
   - Главная: `index.html`.
   - Турниры (список + все форматы просмотра): `torneos.html`, `tournament-details.html`, `king-of-court-view.html`, `tournaments/americano/view.html`, `tournaments/americano/ranking.html`, `tournaments/team-americano/view.html`, `tournaments/team-playoff/view.html`.
   - Процесс регистрации/записи: `registro.html` (форма создания аккаунта игрока), `waitlist-confirmation.html` (лист ожидания), `accept-pair.html` (подтверждение парной регистрации).
   - Итого 11 страниц. **Не включены** (в отличие от GA4): `clubs/**`, `ranking.html` (глобальный рейтинг, не турнир), `login.html`, `players/dashboard.html`, `players/perfil.html`, юридические страницы, error-страницы, `/admin/**`, `/test/**` — заказчик их не упомянул, расширять зону самостоятельно не нужно (YAGNI).
3. **Consent Mode Google ≠ Consent API Clarity.** У GA4-фрагмента паттерн "грузим `gtag.js` сразу, но `consent: denied` по умолчанию" работает, потому что Google Consent Mode документированно поддерживает такой режим из коробки. У Clarity официальный `clarity("consent")`/`clarity("consent", false)` API **не гарантирует** аналогичное поведение "по умолчанию запрещено" без дополнительной настройки на стороне личного кабинета Clarity (`Settings → Behavior → Require consent`) — а туда у конвейера нет доступа (сторонний SaaS, учётных данных нет, см. "Вне скоупа"). Решение: не полагаться на настройку кабинета — тег и скрипт `clarity.ms/tag/...` **не вставляются в DOM вообще**, пока явно не получено согласие (`cookieConsent=accepted`, либо `customized` + `analyticsConsent=true`); как только согласие получено (есть cookie при заходе на страницу, либо пользователь только что нажал "Принять"/сохранил настройки) — скрипт вставляется динамически через JS. Это даёт гарантию "нет согласия → нет Clarity" независимо от настроек кабинета.
4. **CSP блокирует `clarity.ms` без доработки**, как и `googletagmanager.com` в LFPT-0468. `SecurityConfig.java`: `script-src` — добавить `https://www.clarity.ms`; `connect-src` — добавить `https://www.clarity.ms https://*.clarity.ms` (Clarity шлёт события на поддомены, официальная рекомендация Microsoft). Та же логика включения в этот же PR (не отдельная backend-задача) — однострочная правка, без неё фича физически не работает (обоснование — `GIT_WORKFLOW.md` §3, прецедент LFPT-0468).
5. **Маскирование PII — точечная настройка кабинета Clarity недостижима из кода.** Microsoft Clarity предлагает два независимых механизма маскирования: (a) уровень проекта в личном кабинете (`Settings → Masking`, режимы Strict/Balanced/Relaxed) — недостижим конвейеру (нет доступа к clarity.microsoft.com); (b) атрибуты `data-clarity-mask="true"` / `data-clarity-unmask="true"` прямо в HTML — работают независимо от настроек кабинета, задаются в шаблонах проекта. Решение: на каждой из 11 инструментированных страниц добавить `data-clarity-mask="true"` на тег `<body>` — это маскирует **весь** текстовый контент страницы в записи (включая имена участников турнира, приветствие "Hola, {nombre}" в хедере, поля формы регистрации, email/телефон/Telegram в формах и подтверждениях) без необходимости точечно искать каждое место, где отображается персональная информация, и без риска пропустить один из них. Консервативный выбор (маскируется больше, чем строго необходимо) — оправдан, т.к. задача заказчика прямо про приватность ("скрыты в записях посещений"), а точечная разметка конкретных полей на 11 разных шаблонах была бы хрупкой (новое поле с PII на странице в будущем — и маскирование придётся не забыть продублировать).
6. **Сайт — multi-page, без SPA-переходов** (подтверждено в LFPT-0468, не изменилось) — повторный учёт визита при переходе между страницами не актуален, как и в GA4-кейсе.

## Требования

### Функциональные

- Второй `th:fragment="clarity"` в `templates/fragments/analytics.html`. Project ID `yu4n92bsuy` выносится в `application.yml` как `app.analytics.clarity-id` (аналогично `app.analytics.ga4-id`), не хардкодится в шаблоне.
- Фрагмент определяет глобальную функцию `window.initClarity()`, которая (один раз, с защитой от повторного вызова) вставляет официальный скрипт Clarity (`c[a]=c[a]||function(){...}; t.src="https://www.clarity.ms/tag/"+i; ...`) с Project ID из Thymeleaf-свойства.
- При загрузке страницы фрагмент сам проверяет cookie `cookieConsent`/`analyticsConsent` (та же логика, что в GA4-фрагменте): если согласие уже дано (`accepted`, либо `customized` + `analyticsConsent=true`) — сразу вызывает `initClarity()`. Если согласия нет — ничего не делает (скрипт `clarity.ms` не загружается вовсе).
- `cookie-consent.js` (`updateAnalyticsConsent`): при переходе согласия в `granted=true` — если `window.initClarity` определена и Clarity ещё не инициализирована, вызвать `initClarity()` (запускает трекинг без перезагрузки страницы, по аналогии с `gtag('consent','update',...)`); если доступен `window.clarity`, дополнительно вызвать `clarity("consent")` (явное согласие по Clarity Consent API — задел на случай, если в будущем в кабинете включат `Require consent`). При переходе в `granted=false` — если `window.clarity` определена (Clarity уже успела загрузиться на этой странице ранее), вызвать `clarity("consent", false)`.
- `<body data-clarity-mask="true">` на всех 11 страниц из п.2 находок — маскирование текста страницы в записи Clarity независимо от настроек кабинета.
- Фрагмент `clarity` подключается (`th:replace="~{fragments/analytics :: clarity}"`) в `<head>` тех же 11 страниц, сразу после существующего `th:block` с `ga4`.
- `SecurityConfig.java`: CSP `script-src` дополняется `https://www.clarity.ms`; `connect-src` дополняется `https://www.clarity.ms https://*.clarity.ms`.

### Нефункциональные
- i18n: новых пользовательских строк нет (тег работает без видимого UI-текста) — пункт не применим.
- Безопасность/приватность: новая точка данных, уходящих во внешний сервис (Microsoft). Персональные данные защищены двумя слоями — (1) тег не грузится без согласия пользователя (п.3 находок), (2) весь текст маскируется атрибутом `data-clarity-mask` (п.5 находок) независимо от настроек кабинета Clarity.
- Project ID — не секрет (виден в исходном коде любой публичной страницы после загрузки тега), но вынесен из шаблона в конфигурацию для единообразия с `app.analytics.ga4-id`/`app.recaptcha.site-key`.

## Вне скоупа
- **Усиление режима маскирования в личном кабинете Clarity** (`Settings → Masking → Strict`) и **подтверждение того, что визиты реально появляются в кабинете Clarity** (clarity.microsoft.com) — действия заказчика после деплоя, за пределами возможностей конвейера: нет учётных данных/доступа к стороннему SaaS-кабинету. Код-часть задачи (п.5 находок) снижает риск независимо от того, выставит заказчик Strict или нет, но не заменяет его собственную проверку кабинета.
- Распространение на страницы вне явно указанного списка (`clubs/**`, `ranking.html`, `login.html`, личный кабинет игрока, юридические страницы, `/admin/**`, `/test/**`) — заказчик их не запросил (см. находку 2).
- Heatmaps/дополнительные Clarity-виджеты, кастомные Clarity-теги (`clarity("identify", ...)`, `clarity("event", ...)`) — заказчик попросил только базовую установку тега.
- Распространение баннера cookie-consent на страницы, где он сейчас не подключён (только `index.html`, известный пробел из LFPT-0468, issue #469) — не создаётся и не усугубляется этой задачей.

## Edge cases
- Пользователь уже отклонил cookies (`cookieConsent=rejected`) → на любой инструментированной странице тег не грузится вовсе, без сетевого запроса к `clarity.ms` (сильнее, чем GA4-подход с cookieless-режимом — у Clarity такого режима нет, поэтому полный лазy-load, см. находку 3).
- Cookie `cookieConsent` отсутствует вовсе (страница открыта напрямую, баннер ещё не показан/не на этой странице) → тег не грузится, как и при отказе — ожидаемое поведение "нет согласия = нет трекинга".
- Пользователь принимает cookies на `index.html`, затем переходит на `torneos.html` в той же сессии (cookie уже `accepted`) → на `torneos.html` тег загружается сразу при открытии страницы (fragment сам проверяет cookie при каждой загрузке), без повторного баннера.
- Если на странице уже вызван `initClarity()` (согласие было при загрузке) и теоретически в будущем на той же странице без перезагрузки сработает `updateAnalyticsConsent(true)` повторно — повторной вставки `<script>` не происходит (защита от двойной инициализации внутри `initClarity()`).
