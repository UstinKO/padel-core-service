# LFPT-0680: Feature подсказки существующего партнёра при ручном вводе и расширенный поиск в модалке регистрации пары (frontend)

## Статус
approved

## Источник
Клиентский запрос [specs/requests/LFPT-0679-poisk-partnera-podskazki.md](requests/LFPT-0679-poisk-partnera-podskazki.md) (Telegram, `telegram_launch_message_id: 5384`, отправитель customer). GitHub issue [#680](https://github.com/UstinKO/padel-core-service/issues/680). Зависит от бэкенд-задачи [#679](https://github.com/UstinKO/padel-core-service/issues/679) / [LFPT-0679-poisk-partnera-backend.md](LFPT-0679-poisk-partnera-backend.md) (расширение `GET /api/players/search` поиском по телефону/Telegram) — уже реализована и закоммичена в базовой ветке `feature/LFPT-0679`, от которой создана эта ветка.

## Контекст / зачем

Модалка парной регистрации (`tournament-details.html`, режим `WITH_PARTNER`) предлагает основной поиск партнёра (`partnerSearch`) и, если он не помог, ручной ввод (`manualPartnerFields`: имя/фамилия/телефон/email). Ручной ввод никак не проверяет, не зарегистрирован ли такой человек уже — пользователь может создать дублирующийся профиль партнёра, даже если тот уже есть в базе. Бэкенд (#679) уже умеет искать по телефону и Telegram — здесь это доводится до пользователя: обновляется текст подсказки основного поиска и добавляются ненавязчивые подсказки во время ручного ввода.

## Связь с MASTER.md

Не меняет инварианты и флоу парной регистрации (`specs/MASTER.md` § «Флоу парной регистрации») — при выборе существующего игрока из подсказки используется тот же механизм, что и выбор из основного поиска (`existingUserId` в `PartnerRegistrationDto`), новая регистрация не создаётся.

## Требования

### Функциональные

1. **Текст подсказки основного поиска.** `modal.partner.search.placeholder` (`src/main/resources/i18n/messages_{es,ru,en}.properties`):
   - RU: «Имя, фамилия, телефон или Telegram»
   - ES: «Nombre, apellido, teléfono o Telegram»
   - EN: «First name, last name, phone or Telegram»

   Остальные строки секции (`modal.partner.search.label`, `.hint`) не меняются — поиск уже работает по мере ввода (`tournament-details.js`, debounce 300мс, мин. 2 символа), бэкенд уже расширен (#679).

2. **Подсказки при ручном вводе** (`static/js/tournament-details.js`, секция `manualPartnerFields`: поля `partnerFirstName`, `partnerLastName`, `partnerPhone`). При вводе в любое из этих трёх полей (debounce 400мс, минимум 2 непробельных символа для имени/фамилии, минимум 4 цифры для телефона — не дёргать поиск на короткий нечисловой/слишком короткий ввод) — независимый запрос к уже существующему `GET /api/players/search?query=...&tournamentId=...` со значением именно этого поля (не комбинируя поля в одну строку: фамилия ищется сама по себе, даже если по имени ничего не нашлось — п.4 клиентского запроса). Результаты всех трёх полей объединяются по `id` (без дублей) в один список подсказок.
3. **Отображение подсказок.** Если список не пуст — показать компактный ненавязчивый блок под `manualPartnerFields` с заголовком «Возможно, ваш партнёр уже зарегистрирован» (новый i18n-ключ) и списком найденных: имя + фамилия, уровень (`nivelJugador`), если есть — **без** email и телефона (приватность, п.5 клиентского запроса; в отличие от основного `partnerSearchResults`, который уже показывает email — тот список не трогаем, это существующее поведение вне скоупа задачи). Блок не перекрывает и не блокирует поля ввода (как и `partnerSearchResults`, но встроен в поток страницы под `manualPartnerFields`, а не абсолютным попапом — ручной ввод не прерывается кликом вне поля).
4. **Выбор из подсказки.** Клик по найденному игроку — переиспользовать существующую `selectPartner(player)` (`tournament-details.js`): заполняет `selectedPartnerId`, скрывает `manualPartnerFields` (а с ним и блок подсказок). Не писать отдельную логику выбора.
5. **Если совпадений нет** — блок подсказок просто не показывается (`display:none`), ручной ввод продолжается без дополнительных подтверждений (п.6 клиентского запроса).
6. **Сброс** — при очистке формы (`clearSelectedPartner`, закрытие модалки) блок подсказок скрывается и очищается вместе с остальными полями.
7. **Не трогать** режимы `SEARCH` («Ищу партнёра») и `ADD_LATER` («Добавлю партнёра позже») — подсказки только в `WITH_PARTNER` → `manualPartnerFields`.

### Нефункциональные

- **i18n**: новый ключ (заголовок блока подсказок) — во все три `messages_{es,ru,en}.properties`; текст плейсхолдера основного поиска — там же, см. п.1.
- **Debounce и минимальная длина** — как в п.2, чтобы не дёргать `/api/players/search` на каждое нажатие клавиши (технические требования клиентского запроса, п.8). Отдельный rate-limit на фронте не нужен — защита от перебора уже на бэкенде (#679, общий лимит `/api/**`).
- **Мобильная раскладка** — блок подсказок — обычный блочный элемент в потоке формы (не `position:fixed`, как `partnerSearchResults`), поэтому не требует отдельного позиционирования/пересчёта при скролле; проверяется вживую Playwright в узком вьюпорте (Tester).
- **Безопасность**: новых точек входа данных пользователя эта задача не добавляет — переиспользуется существующий авторизованный эндпоинт.

## Вне скоупа

- Любые изменения `PlayerRepository`/`PlayerService`/`GET /api/players/search` — сделаны в #679, здесь не трогаются.
- Изменение отображения результатов основного поиска (`partnerSearchResults` — уже показывает email) — не запрошено, не трогаем.
- Добавление поля Telegram/email в форму ручного ввода партнёра — клиентский запрос упоминает это условно («если такие поля есть»); в текущей форме такого поля нет, вводить его не просили отдельно — не добавляем.
- Режимы «Ищу партнёра» (`SEARCH`) и «Добавлю партнёра позже» (`ADD_LATER`).
- Жёсткая серверная защита от дублей при самом создании партнёра — отдельная будущая задача (явное ограничение клиентского запроса).

## Изменения в системе

### API
Нет новых/изменённых эндпоинтов — используется существующий `GET /api/players/search` (расширен в #679).

### БД
Нет изменений.

### UI
- `src/main/resources/templates/tournament-details.html` — новый блок подсказок под `manualPartnerFields` (разметка, изначально скрыт).
- `src/main/resources/static/js/tournament-details.js` — обработчики ввода на `partnerFirstName`/`partnerLastName`/`partnerPhone` (debounce, запрос, объединение результатов, рендер блока подсказок, переиспользование `selectPartner`), сброс блока в `clearSelectedPartner`.
- `src/main/resources/i18n/messages_{es,ru,en}.properties` — обновлён `modal.partner.search.placeholder`, добавлен ключ заголовка блока подсказок.

## Критерии приёмки

- [ ] Плейсхолдер поля основного поиска на ru/es/en показывает новый текст («Имя, фамилия, телефон или Telegram» и переводы).
- [ ] При вводе имени (≥2 символа) в ручные поля — если есть похожий зарегистрированный игрок, появляется блок «Возможно, ваш партнёр уже зарегистрирован» с его именем/фамилией/уровнем.
- [ ] При вводе фамилии — поиск срабатывает независимо от результата по имени (в т.ч. если по имени совпадений не было).
- [ ] При вводе телефона (≥4 цифр) — обнаруживаются совпадения по телефону (используя расширенный бэкенд-поиск #679).
- [ ] Блок подсказок не показывает email/телефон найденных игроков.
- [ ] Клик по подсказке — заполняет `selectedPartnerId`, скрывает ручные поля и блок подсказок, итоговая отправка формы использует `existingUserId`, как и выбор из основного поиска.
- [ ] Если совпадений нет — блок не отображается, ручной ввод и отправка формы работают как раньше (регрессия).
- [ ] Режимы «Ищу партнёра» и «Добавлю партнёра позже» не изменились.
- [ ] Страница проверена в браузере (Playwright, мобильный вьюпорт) — блок подсказок читается, не перекрывает поля ввода.
- [ ] `./mvnw verify` зелёный (бэкенд уже покрыт в #679, здесь — отсутствие регрессий на старых автотестах).

## Edge cases

- Пользователь вводит имя, получает подсказки, затем меняет фамилию — список подсказок обновляется (не остаётся «застрявшим» от предыдущего ввода).
- Пользователь выбирает партнёра из основного поиска (`partnerSearch`), а не из ручных подсказок — `manualPartnerFields` и блок подсказок скрываются, как и сейчас (`selectPartner`).
- Очень быстрый ввод (несколько символов подряд) — debounce 400мс гасит промежуточные запросы, в выдаче остаётся актуальный результат последнего запроса (та же логика, что уже работает в `partnerSearch` с `searchDebounceTimer`, но отдельный таймер на подсказки, чтобы не конфликтовать с debounce основного поля).
- Два совпадения с одинаковым именем+фамилией, но разным уровнем — оба показываются в списке подсказок как разные карточки (различаются по уровню/id).

## Открытые вопросы

Нет. Технические решения, не требующие бизнес-согласования (`GIT_WORKFLOW.md` §3):
1. **Отдельный debounce-таймер для подсказок**, не общий с `partnerSearch` — чтобы ввод в одном поле не отменял ожидающий запрос другого; клиентский запрос не уточняет механику, это стандартная практика при нескольких независимых полей.
2. **Минимум 4 цифры для срабатывания поиска по телефону при ручном вводе** — совпадает с порогом, который уже определён на бэкенде (#679) для той же ветки запроса; дублирование порога на фронте — только чтобы не слать заведомо «пустой» запрос, бэкенд всё равно это же проверяет.
