# LFPT-0465: Feature раннее формирование первого этапа плей-офф Team Playoff — не ждать завершения квалификации

## Статус
approved

## Источник
Клиентский запрос `specs/requests/LFPT-0465-playoff-early-stage.md` (Telegram, тема "AI Разработка", переслано от Evgeny_754) → issue [#465](https://github.com/UstinKO/padel-core-service/issues/465).
Telegram-сообщение (для reply): 4751

## Контекст / зачем

Координатор турнира Team Playoff хочет готовить сетку плей-офф заранее, не дожидаясь, пока ВСЕ команды закончат оба квалификационных матча — чтобы не простаивали свободные корты, пока несколько команд ещё доигрывают квалификацию.

**Важная находка (Analyst, расследование регрессии):** заявка сформулирована как "раньше работало, теперь кнопки нет". Проверка истории `TeamPlayoffService.initPlayoff()`/гейта `isQualificationDone()` и условия кнопки в шаблоне (`ranking.finished and not playoffStarted`) показала, что это условие идентично с самого первого коммита фичи (`74f8318`, T1 эпика #252) — кода, реально сломавшего эту логику, не существует. Более того, на похожем турнире заказчику уже объясняли это как осознанное поведение (issue #298, 2026-08-11: *"плей-офф создаётся явным вызовом initPlayoff(), не лениво... отдельного фикса не требует"*) — заказчик тогда с этим согласился.

Таким образом это **не регрессия, а новая фича** — обобщение уже существующего в проекте механизма "TBD-слот, дозаполняемый по мере результатов" (сейчас используется только для play-in → 1/4 финала при 9-16 командах, `initPlayoffWithPlayIn`/`tryFormNextPlayoffStage`) на самый первый этап плей-офф.

## Связь с MASTER.md

Не затрагивает инварианты `specs/MASTER.md` — чисто внутренняя механика формата Team Playoff (не упомянут там отдельно, см. "Форматы турниров" → Team Americano/Team Playoff).

## Требования

### Функциональные

1. **Гейт доступности кнопки "Начать плей-офф" ослаблен**, но только для случая, когда число команд — точная степень двойки (8 или 16: `largestPowerOf2(total) == total`, что покрывает прямо заявленный кейс 8 команд):
   - кнопка доступна, если квалификация начата И хотя бы 2 команды уже отыграли оба квалификационных матча (`matchesPlayed >= 2`) — т.е. есть хотя бы одна потенциальная готовая пара;
   - НЕ требует, чтобы ВСЕ команды закончили оба матча.
2. **Для 9-15 команд (нужен play-in) гейт НЕ меняется** — остаётся требование полного завершения квалификации (см. "Вне скоупа" — почему).
3. **Частичное формирование этапа:** при вызове `initPlayoff()` до полного завершения квалификации (случай п.1):
   - команды, уже закончившие оба матча ("определившиеся"), сразу разбиваются на пары существующим движком посева (`PlayoffMatchingEngine`, `REMATCH_FIRST` — без изменений в приоритетах);
   - если число определившихся команд нечётное — последняя по рейтингу определившаяся команда временно остаётся в пуле "неопределившихся" (будет сопоставлена позже, при дозаполнении);
   - оставшиеся позиции этапа (нужные, чтобы в сумме получилось `n/2` матчей первого этапа — ровно столько же, сколько при обычном полном посеве) создаются как заглушки "TBD vs TBD" (`status = PENDING`, без команд) — по аналогии с уже существующим `createTbdPlayoffRounds` для будущих стадий;
   - раунд этапа создаётся со статусом `IN_PROGRESS` сразу, даже если часть матчей — заглушки (реальные матчи уже можно назначать на корты).
4. **Автоматическое дозаполнение:** когда последняя "неопределившаяся" команда доигрывает оба квалификационных матча (момент, когда квалификация становится полностью завершённой — тот же триггер, что сейчас переводит раунд квалификации в `COMPLETED`, `tryAutoCompleteQualification`) — система автоматически:
   - собирает все команды, которые ещё не попали в какой-либо матч первого этапа плей-офф;
   - прогоняет их через тот же движок посева (`PlayoffMatchingEngine`, `REMATCH_FIRST`);
   - заполняет оставшиеся TBD-слоты первого этапа реальными командами (по порядку корта), переводит эти матчи в `IN_PROGRESS`.
5. **Уже созданные (в том числе уже начатые/завершённые) матчи первого этапа не пересобираются и не трогаются** — дозаполнение касается только слотов с `team1Id/team2Id == null`.
6. **Дальнейшая сетка не меняется:** цепочка TBD для следующих стадий (1/2, финал — и 1/4 для 9-16 команд после play-in) создаётся как и раньше, на основе итогового размера текущей стадии (`n/2`), независимо от того, сколько матчей было реальными на момент создания. `tryFormNextPlayoffStage`/`seedNextPlayoffStage` не меняются — они уже ждут завершения ВСЕХ матчей текущей стадии, что корректно работает и для частично созданного первого этапа.
7. **Регенерация (`regeneratePlayoff`)** продолжает работать как раньше: удаляет все матчи/раунды фазы `PLAYOFF` и заново вызывает `initPlayoff()` — с учётом текущего (уже более полного к этому моменту) состояния квалификации. Поведение не меняется технически, просто `initPlayoff()` теперь умеет частичный случай.

### UI (admin/americano/tournament-playoff.html)

- Новый атрибут модели `canInitPlayoff` (вместо прямой проверки `ranking.finished` в шаблоне) — считается контроллером через `TeamPlayoffService.canInitPlayoff(tournamentId)`.
- Если квалификация полностью завершена (`ranking.finished`) — поведение и текст баннера/кнопки не меняются (старый текст "Calificación completada...").
- Если квалификация идёт, но `canInitPlayoff == true` (частичный случай) — показывается альтернативный баннер с новым текстом, поясняющим, что доступная часть сетки будет создана сейчас, а остальные пары определятся позже. Кнопка и `POST /tournaments/team-playoff/admin/{id}/init-playoff` — те же, без изменений.
- Confirm-диалог для частичного случая — отдельный текст (новый i18n-ключ), поясняющий, что часть пар будет TBD.

### Нефункциональные

- i18n: 2 новых ключа (`admin.playoff.qual.partial_hint`, `admin.playoff.confirm.start_playoff_partial`) — es/ru/en.
- Без новых точек входа данных от пользователя (эндпоинт `/init-playoff` уже существует, просто гейт ослаблен) — нет новых рисков безопасности.

## Вне скоупа

- **9-15 команд (play-in) — гейт НЕ ослабляется.** Для этого диапазона, кто идёт "напрямую в 1/4" (`direct`), а кто — в play-in (1/8), определяется позицией в итоговом рейтинге (`findPlayoffRankingByTournamentId`, сортировка по сетам/геймам), а не просто по готовности команды. Эта граница может измениться, пока квалификация не закончена — команда у границы может попасть то в `direct`, то в `playIn`. Создать её "предварительно" и потом поменять означало бы либо пересобирать уже созданные матчи (прямо запрещено заявкой — "не ломая уже созданные матчи"), либо держать заведомо неточную сетку. Технически безопасного способа частично сформировать именно эту границу без риска пересборки не нашлось за разумное время — оставляем старое поведение (полное завершение квалификации обязательно). Это разумное техническое решение (не бизнес-вопрос), принято архитектором; явно сообщается пользователю в итоговом отчёте.
- Изменение приоритетов посева/анти-реванш (`PlayoffMatchingEngine`) — не трогается.
- UI-предпросмотр посева до сохранения в БД — отдельная, более крупная тема (см. п.3 issue #298), не входит сюда.
- Ручной выбор, какая именно команда "придерживается" при нечётном числе определившихся команд, — не настраивается (всегда последняя по рейтингу, автоматически).

## Изменения в системе

### API
Без новых endpoint'ов. `POST /tournaments/team-playoff/admin/{tournamentId}/init-playoff` (существующий) теперь успешен раньше по времени (при частичной квалификации для степени-двойки числа команд).

### БД
Нет новой миграции. Используются существующие таблицы/поля (`AmericanoMatch.team1Id/team2Id == null` как признак TBD-слота — уже существующий паттерн).

### UI
- `src/main/java/.../controller/view/americano/TeamPlayoffViewController.java` — метод `viewAdmin`: новый атрибут `canInitPlayoff`.
- `src/main/resources/templates/admin/americano/tournament-playoff.html` — условие блока инициализации плей-офф + новый баннер/confirm-текст для частичного случая.
- `src/main/resources/i18n/messages_{es,ru,en}.properties` — 2 новых ключа.

### Сервис
- `src/main/java/.../service/americano/TeamPlayoffService.java`:
  - новый публичный метод `canInitPlayoff(Long tournamentId)`;
  - новый приватный хелпер `isSettled(AmericanoTeam)` (`matchesPlayed >= 2`);
  - `initPlayoff()` — гейт меняется на `canInitPlayoff(...)`;
  - `createPlayoffRound(...)` — разбивка `seeded` на settled/pending, частичный посев + TBD-заглушки на оставшиеся слоты, сохранение правильного количества слотов (`n/2`) для цепочки следующих TBD-стадий;
  - новый приватный метод `backfillFirstPlayoffStage(Long tournamentId)`;
  - `tryAutoCompleteQualification(...)` — вызывает `backfillFirstPlayoffStage(...)`, если плей-офф уже начат, сразу после того, как квалификационные раунды переводятся в `COMPLETED`.

## Критерии приёмки

- [ ] При 8 командах и неполной квалификации (например, 5 из 8 команд уже отыграли оба матча) кнопка "Начать плей-офф" видна в админке.
- [ ] Клик по кнопке создаёт этап 1/4 финала: реальные матчи между уже определившимися командами (с назначенными кортами, доступные для ввода результата) + TBD-заглушки на оставшиеся позиции — так, чтобы итоговое число матчей этапа было ровно 4 (для 8 команд).
- [ ] Дальнейшие стадии (1/2, финал) созданы как TBD-цепочка той же длины, что и раньше (регрессия по размеру цепочки не допускается).
- [ ] Когда оставшиеся команды доигрывают квалификацию (последняя команда заканчивает 2-й матч) — TBD-слоты первого этапа автоматически заполняются реальными командами, без дополнительного действия координатора.
- [ ] Уже созданные/начатые матчи первого этапа (реальные, не TBD) не изменяются в процессе дозаполнения.
- [ ] Регрессия: при полностью завершённой квалификации (старый сценарий) поведение `initPlayoff()` и результат посева идентичны версии до этой фичи (существующий regression-тест `TeamPlayoffEndToEndTest.fullTournament_satisfiesAllInvariants` для N=8..16 проходит без изменений).
- [ ] 9-16 команд (play-in): кнопка "Начать плей-офф" остаётся недоступной до полного завершения квалификации — поведение не изменилось (явное, задокументированное ограничение, см. "Вне скоупа").
- [ ] i18n: новые строки присутствуют во всех трёх файлах (es/ru/en), в UI отображается корректный текст в зависимости от локали браузера.
- [ ] `./mvnw verify` зелёный.

## Edge cases

- Все 8 команд ещё не начали квалификацию (`qualStarted == false`) — кнопка не показывается (как и раньше, `canInitPlayoff` требует `isQualificationStarted`).
- Ровно 1 команда определилась (остальные 7 — нет) — `canInitPlayoff == false` (нужно минимум 2 определившиеся команды, иначе нет ни одной реальной пары — создавать стадию целиком из TBD бессмысленно).
- Нечётное число определившихся команд (например, 5 из 8) — 2 пары формируются сразу, 5-я (последняя по рейтингу) команда ждёт пару среди TBD вместе с оставшимися тремя неопределившимися — при дозаполнении 4 команды (5-я определившаяся + 3 ещё доигрывающих) рассаживаются по 2 оставшимся TBD-слотам через тот же движок.
- Координатор нажимает "Переформировать плей-офф" (`regeneratePlayoff`) пока есть TBD-слоты и ни один реальный матч этапа не завершён — старое поведение: все матчи/раунды фазы `PLAYOFF` удаляются, `initPlayoff()` вызывается заново с учётом текущего (более полного) состояния квалификации.
- Координатор правит счёт уже сыгранного квалификационного матча (`submitQualResult` с откатом) после того, как команда уже попала в реальный матч первого этапа как "определившаяся" — её посевные данные (`matchesWon`) в уже созданном матче не пересчитываются автоматически (как и в полностью законченном сценарии до этой фичи — известное поведение, чинится через `regeneratePlayoff`, см. issue #298 п.2). Не входит в скоуп этой фичи.
- 2 команды всего, обе определились сразу после первого же квалификационного раунда (`total == 2` — вырожденный случай) — `n = 2`, этап = `FINAL`, работает как обычный путь (settled.size()==2, 0 TBD).
