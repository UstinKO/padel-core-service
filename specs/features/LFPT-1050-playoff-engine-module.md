Перенести только подтверждённый PlayoffMatchingEngine, его нейтральные вложенные типы и существующий unit-тест в padel-tournament-engines. TeamPlayoffService, JPA, транзакции, history и UI остаются в legacy bootstrap.

## Требования

### Функциональные

#### Цель
Перенести только подтверждённый PlayoffMatchingEngine, его нейтральные вложенные типы и существующий unit-тест в padel-tournament-engines. TeamPlayoffService, JPA, транзакции, history и UI остаются в legacy bootstrap.

#### Реализация
- Сохранить package com.padle.core.padelcoreservice.service.americano на пилоте, чтобы структурный перенос не смешивать с массовым rename/import-рефакторингом. Публичный Java API/record/enum/signature сохраняется.
- Удалить только Spring @Component/import из движка, создать один @Bean в конфигурации bootstrap. Service получает прежний тип конструктором; runtime ровно один экземпляр/bean.
- Движок и unit-тест физически убрать из корневого src, не оставить shadow-копию. Engines зависит только от JDK и test-библиотек, без Spring/JPA/DTO; проверить dependency tree/compiled imports.
- Сохранить перечисление всех разбиений, лексикографические приоритеты, порядок входа и результата при равенстве, warning/allConstraintsSatisfied/null и пустой/нечётный вход. Никаких оптимизаций/новых бизнес-правил.
- Потребителей seedPlayoffPairs (REMATCH_FIRST), play-in/early/backfill и seedNextPlayoffStage (STRENGTH_FIRST) не переписывать; способы сохранения, @ConductChange, @Transactional и WS остаются прежними.
- Архитектурная проверка охватывает только перенесённую границу, legacy не объявляется уже соответствующим архитектуре. Проверка падает на запрещённой зависимости; выбрать минимальный совместимый инструмент.

#### Критерии приёмки
- [ ] Все 8 исходных unit-тестов выполняются в engines без Spring/БД; равные входы дают прежние результаты.
- [ ] В boot jar движок находится в библиотеке engines, без дубликата в BOOT-INF/classes и без Spring-зависимостей в engine.
- [ ] Реальный Spring-контекст имеет ровно один bean и действующий сервисный вызов.
- [ ] Root verify, Team Playoff integration, history/security/stale и общий smoke проходят на отдельной БД.
- [ ] Повтор исходной автоматизированной UI-матрицы и runtime/release rollback выполнен до готовности этого PR; #1045 независимо завершает расширенную ручную приёмку.
- [ ] Схема/пути Liquibase, API/UI/WS, алгоритм, транзакции и исходные данные не изменены.
- [ ] Документы отражают частичную реализацию: 2 дочерних модуля, root legacy и согласованные будущие 7; список временных мостов обновлён.

#### Вне объёма
#509 (общий TeamPlayoffService рефакторинг), остальные движки, OpenAPI generator, новые application/persistence/web/integrations модули, переезд PostgreSQL и Swarm.


### Нефункциональные




Каждый PR самостоятельно оставляет приложение работоспособным: корневая полная сборка/verify, отдельный PostgreSQL для integration, smoke итогового jar/образа, действующие MVC/API/React/Expo, rollback. Реальные пользовательские БД/уведомления не используются. Java release 17, бизнес-правила и JSON/WS не меняются. Один слой и отдельный PR; без pipeline:ready, автомержа и деплоя в рамках подготовки. Документация — docs/modular-monolith/, спека с настоящим LFPT-номером.

Пилот сохраняет пути db/changelog, схему/данные/подключение. Временный root legacy src имеет одного владельца и один путь компиляции.

## Вне скоупа

Выделение persistence, физический перенос БД/Swarm, новые бизнес-правила, внутренний HTTP/микросервисы, полный рефакторинг TeamPlayoffService (#509), остальные движки и API codegen.

## Изменения в системе

### API

Внешний HTTP/WS контракт без изменений.

### БД

Нет Liquibase и production-изменений данных. Синтетические fixtures только в своей тестовой среде.

### UI

Внешний UI без изменений; browser/API smoke необходим по границе задачи.

### Документация

docs/modular-monolith/phase-1/ и актуальные карта/команды/пути по затронутой области; docs/Home.md, docs/architecture.md и .agents/PROJECT.md при реализации сборочных изменений. Фактическое состояние не подменяется будущими семью модулями.

## Edge cases

Равная стоимость/порядок перечисления, три приоритета, пустой/нечётный вход, play-in/TBD/backfill, no-show, stale pair/version, чужой клуб, rollback/history/after-commit. Для сборки: CWD тестов, один main/repackage/bean, frontend один раз, модульные отчёты, явный runtime jar, отсутствие shadow-класса. Применимость — по матрице и конкретному изменению; недостижимый из UI вход не получает выдуманную кнопку.

## Открытые вопросы

Неразрешённых бизнес-вопросов нет. Точные fixtures/ожидаемые результаты и дефекты фиксируются исходными #1047/#1048; технический выбор внутри согласованной границы выполняется по анализу, без изменения поведения.
