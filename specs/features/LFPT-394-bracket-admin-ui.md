# LFPT-394: Admin-UI для генерации и просмотра сетки Bracket-турниров (CANCHA_ABIERTA)

## Статус
approved

## Источник
GitHub issue [#394](https://github.com/UstinKO/padel-core-service/issues/394) (прямой технический вход, роль `architect`) — `specs/requests/` не создавался, постановка уже техническая.

## Контекст / зачем
Формат "Открытый Корт" (`TournamentType.CANCHA_ABIERTA`, `BracketService`) можно создать и укомплектовать участниками, но довести до результатов через админку невозможно: на странице деталей турнира нет ни кнопки генерации сетки, ни ссылки на управление матчами, а прямой переход на `GET /admin/tournaments/{id}/matches` (на который редиректят существующие `POST .../generate` и `POST .../{matchId}`) падает `404 NoResourceFoundException` — такого `@GetMapping` не существует ни в одном контроллере. В отличие от Americano и King of Court, у Bracket-формата никогда не было своего admin-шаблона.

## Связь с MASTER.md
Затрагивает раздел "Форматы турниров" — Bracket уже описан там как существующий формат с сущностью `Match`; эта фича не меняет ни один инвариант `MASTER.md`, только закрывает технический пробел в UI (домен `BracketService`/`AdminMatchController` уже существовал и не менялся по бизнес-логике). Пункт "Платежи фиксируются вручную" косвенно подтверждает общий паттерн проекта — админ вручную вводит результаты, без внешней системы; та же модель применена здесь.

## Требования

### Функциональные
1. **Новая страница `GET /admin/tournaments/{tournamentId}/matches`** (новый метод в `AdminMatchController`, шаблон `admin/tournaments/matches.html`), доступная тем же ролям и с той же проверкой доступа, что и остальные admin-действия над турниром (`TournamentAccessService.assertCanManageTournament`, как в существующих `POST`-методах этого контроллера).
2. **Если сетка ещё не сгенерирована** (`BracketService.getTournamentBracket(id)` возвращает пустой список) — страница показывает:
   - список подтверждённых регистраций турнира (`status == CONFIRMED`, `TournamentService.getRegistrationsByTournament`) в виде чекбоксов (имя/фамилия игрока);
   - форму `POST /admin/tournaments/{tournamentId}/matches/generate` (эндпоинт уже существует, не меняется) с чекбоксами `name="playerIds"`;
   - если подтверждённых регистраций меньше 2 — форма скрыта, вместо неё информационное сообщение;
   - клиентская JS-проверка: нечётное количество выбранных игроков блокирует отправку с предупреждением (существующий `BracketService.generateInitialBracket` при нечётном `numPlayers` молча теряет последнего через целочисленное деление `numPlayers / 2` — сервис не меняется, но UI не должен позволять админу случайно попасть в этот кейс не зная о нём).
3. **Если сетка уже сгенерирована** (список раундов непустой) — страница показывает раунды по порядку, в каждом — карточки матчей:
   - имена игроков (`player1NombreCompleto`/`player2NombreCompleto`), для ещё не назначенных мест — плейсхолдер "ожидает победителя предыдущего раунда";
   - если статус матча финализирован (`isFinalizado == true`) — показан итоговый счёт по сетам и имя победителя;
   - если оба игрока назначены (`player1Id` и `player2Id` не null) — форма ввода результата `POST /admin/tournaments/{tournamentId}/matches/{matchId}` (эндпоинт уже существует, не меняется) с полями `set1Equipo1/set1Equipo2/set2Equipo1/set2Equipo2/set3Equipo1/set3Equipo2/superSetEquipo1/superSetEquipo2` — форма доступна и для уже финализированных матчей (повторный ввод = исправление результата, консистентно с тем, что `MatchService.updateMatchResult` пересчитывает результат при каждом вызове).
   - форма ввода результата включает скрытое поле `ganadorId`, которое JS высчитывает на `submit` из введённых очков по тем же правилам, что и `MatchService.determinarGanador` (побеждает тот, кто выиграл больше сетов из `set1/set2/set3/superSet`; при ничьей поле остаётся пустым). Это техническое решение (см. "Изменения в системе" ниже) — без него `AdminMatchController.updateMatchResult` не сможет продвинуть победителя в следующий раунд (`bracketService.advanceWinner` использует `ganadorId` из отправленной формы, а не пересчитанный сервером результат — существующее поведение контроллера, не меняется).
4. **На странице деталей турнира** (`admin/tournaments/details.html`) для `tournament.tipo.name() == 'CANCHA_ABIERTA'` — новая карточка (по образцу `.king-card`/`.americano-card`) с одной кнопкой-ссылкой на `/admin/tournaments/{id}/matches` ("Gestionar partidos" / управлять матчами), без дублирования формы генерации на этой странице — вся логика генерации/результатов живёт на новой странице (как это уже устроено для King of Court: карточка на деталях — просто точка входа).

### Нефункциональные
- i18n: все новые пользовательские строки — в `messages.properties`, `messages_es.properties`, `messages_en.properties`, `messages_ru.properties` (ключи с префиксом `admin.tournaments.matches.*` для новой страницы, `admin.tournaments.details.bracket.*` для новой карточки на деталях — тот же паттерн, что уже применяется для `admin.tournaments.details.*` и `admin.koc.*`).
- Безопасность: новая точка входа — только `GET`, не принимает пользовательский ввод напрямую (все параметры — `@PathVariable`), защищена той же проверкой доступа, что и остальные методы `AdminMatchController`.
- Не вводит новых `@Timed`/`@Async` — простой read-only GET, не попадает под известные ловушки `CODE_REVIEW.md §6`.

## Вне скоупа
- Не меняется логика `BracketService.generateInitialBracket` (в т.ч. её поведение при нечётном числе игроков или для парных матчей, где `player3Id`/`player4Id` сейчас не заполняются) — это отдельный технический долг, не предмет этого issue.
- Не меняется логика `AdminMatchController.updateMatchResult`/`advanceWinner` на Java-уровне — используется как есть, UI подстраивается под контракт.
- Не добавляется возможность "перегенерировать" сетку или удалить уже созданные матчи — такого метода нет в `BracketService`.
- Не трогается парный (DOBLES) вариант отображения через `player3Id`/`player4Id` — раз `generateInitialBracket` их не заполняет, UI показывает только `player1`/`player2` независимо от модальности турнира (консистентно с текущим поведением сервиса).

## Изменения в системе

### API
- Новый: `GET /admin/tournaments/{tournamentId}/matches` → `admin/tournaments/matches` (Thymeleaf, не REST). Модель: `tournament` (`TournamentDto`), `bracket` (`List<List<BracketMatchDto>>` от `BracketService.getTournamentBracket`), при пустом bracket — `confirmedRegistrations` (`List<TournamentRegistrationDto>`, отфильтровано по `CONFIRMED`).
- Существующие `POST .../generate` и `POST .../{matchId}` — не меняются.

### БД
Нет изменений схемы.

### UI
- Новый шаблон `src/main/resources/templates/admin/tournaments/matches.html`.
- `admin/tournaments/details.html` — новая карточка для `CANCHA_ABIERTA` (аналог `.king-card` по структуре, без переиспользования кода — независимый блок, т.к. другого способа условной вставки в Thymeleaf для этого шаблона в проекте не используется).

## Критерии приёмки
- [ ] `GET /admin/tournaments/{id}/matches` для существующего `CANCHA_ABIERTA`-турнира без сгенерированной сетки — `200`, страница показывает форму с чекбоксами подтверждённых участников (не 404, как было).
- [ ] Отправка формы генерации с чётным числом выбранных `playerIds` → редирект на ту же страницу, `BracketService`-сетка создана (проверяется через `GET .../matches` — теперь показывает раунды) — существующий `POST /generate` не меняется, только доступен из UI.
- [ ] Попытка отправить форму генерации с нечётным числом выбранных игроков — заблокирована на клиенте (JS), форма не уходит на сервер.
- [ ] После генерации `GET /admin/tournaments/{id}/matches` показывает как минимум первый раунд с матчами, у каждого — имена обоих игроков (или "ожидает соперника" для мест без игрока).
- [ ] Отправка формы результата (сеты, где один игрок выигрывает больше сетов) для матча первого раунда → результат сохранён (`MatchService.updateMatchResult` отработал), матч показывает `FINALIZADO` и имя победителя при перезагрузке страницы.
- [ ] Если в турнире был follow-up матч следующего раунда (второй игрок как place-holder) — после ввода результата первого раунда победитель появляется в соответствующем месте следующего раунда (`advanceWinner` сработал благодаря переданному из формы `ganadorId`).
- [ ] `GET /admin/tournaments/{id}` для `CANCHA_ABIERTA`-турнира показывает новую карточку со ссылкой на `/admin/tournaments/{id}/matches` — раньше такой ссылки не было нигде в UI.
- [ ] Доступ к `GET /admin/tournaments/{id}/matches` без прав на турнир (чужой клуб для `CLUB_ADMIN`, чужой турнир для `ORGANIZER`) — отклонён так же, как и остальные методы `AdminMatchController` (`TournamentAccessService.assertCanManageTournament`).
- [ ] Все новые пользовательские строки присутствуют в `messages.properties`, `messages_es.properties`, `messages_en.properties`, `messages_ru.properties`.
- [ ] `./mvnw compile -DskipTests` и `./mvnw verify` проходят без новых ошибок/падений тестов.

## Edge cases
- Подтверждённых регистраций 0 или 1 — форма генерации не показывается, информационное сообщение вместо неё.
- Матч без обоих игроков (ожидает победителя предыдущего раунда) — форма результата не показывается, только плейсхолдер.
- Ничья по сетам при вводе результата (равное число выигранных сетов с каждой стороны) — `ganadorId` не выставляется (пусто), сервер сохраняет только очки без победителя (существующее поведение `MatchService.determinarGanador`), `advanceWinner` не вызывается — это ожидаемо, не баг новой фичи.
- Повторный ввод результата уже финализированного матча — допускается (форма остаётся доступной), пересчитывает результат и (если изменился победитель) может некорректно рассинхронизировать уже продвинутого в следующий раунд игрока — известное ограничение существующего `BracketService.advanceWinner` (не перезаписывает уже занятое место в следующем раунде), не в скоупе этого issue.

## Открытые вопросы
Нет. Технические решения (клиентский расчёт `ganadorId`, точка входа только со страницы деталей турнира, без дублирования формы генерации) приняты самостоятельно и объяснены выше — issue оставляет реализацию UI на усмотрение разработчика, бизнес-инвариантов `MASTER.md` фича не меняет.
