# LFPT-0521: Fix утечка тестового трафика в продакшен GA4/Clarity — изолировать Measurement ID от dev/cloud/test окружений

## Статус
approved

## Источник
[specs/requests/LFPT-0521-ga4-test-traffic-isolation.md](../requests/LFPT-0521-ga4-test-traffic-isolation.md), issue [#521](https://github.com/UstinKO/padel-core-service/issues/521).

Telegram-сообщение (для reply): 4937

## Контекст / зачем

Заказчик проводит аудит GA4-аналитики 1-padel.com и обнаружил аномальные сессии в отчёте за 1–9 октября (41 сессия с источником `(not set)`, сессии с referral `localhost:4200`). Один из подтверждённых технических источников шума — ID GA4/Clarity не изолированы по окружению: любой non-prod запуск приложения реально шлёт данные в боевую аналитику.

## Связь с MASTER.md

Не затрагивает бизнес-инварианты — чисто инфраструктурная/конфигурационная правка. `MASTER.md` не меняется.

## Важные находки (подтверждено анализом кода)

1. `application.yml`: `app.analytics.ga4-id: ${GA4_MEASUREMENT_ID:G-X5G4N3ND26}`, `clarity-id: ${CLARITY_PROJECT_ID:yu4n92bsuy}` — реальные боевые ID как дефолт **в базовом файле**, применяются ко всем профилям, если не переопределены.
2. Ни `application-cloud.yml`, ни (предположительно) гитигнорнутый `application-dev.yml` не переопределяют эти ключи — подтверждено `grep` по `application-cloud.yml` (нет вхождений `analytics`/`ga4`/`clarity`).
3. `docker-compose.yml`: сервис `padel-app` явно перечисляет каждую передаваемую в контейнер переменную — `GA4_MEASUREMENT_ID`/`CLARITY_PROJECT_ID` в списке нет. Значит боевой сервер и сегодня получает ID только из дефолта `application.yml`, не из `.env`/окружения контейнера.
4. `application-prod.yml` существует и уже следует паттерну "явная переменная без дефолта для секретов" (`DB_URL: ${DB_URL}` и т.п.) — но для GA4/Clarity сейчас такого профильного файла нет вообще, поведение прода полностью определяется шагом 1.
5. `templates/fragments/analytics.html` безусловно рендерит `<script src="...gtag/js?id=${ga4Id}">` и `gtag('config', ga4Id, ...)` — если `ga4Id` окажется пустой строкой, получится невалидный тег (`?id=` без значения) и бессмысленный вызов `gtag('config', '', ...)`.
6. Практическое следствие п.1–3: любой `./mvnw spring-boot:run` разработчика (локальный dev-профиль) и любая browser-проверка Tester'а в облачном конвейере `/develop-feature` (`SPRING_PROFILES_ACTIVE=cloud`, шаги которой по инструкции `.claude/agents/tester.md` явно открывают GA4-страницы и проверяют запросы к `google-analytics.com`) реально отправляют события в `G-X5G4N3ND26`. Несколько задач с GA4-страницами проходили через этот конвейер в начале октября (LFPT-0468 и последующие) — согласуется по времени с аномалиями в отчёте заказчика.
7. Конкретный источник `localhost:4200` не детектируется кодом этого репозитория напрямую (порта 4200 нет нигде в проекте — ни Angular/React-фронтенда, ни dev-сервера на этом порту) — скорее всего сторонний локальный инструмент/прокси у кого-то из команды, открывавший боевой сайт. Эта находка фиксируется отдельно в финальном отчёте архитектора как необъяснимая кодом (см. "Открытые вопросы"); текущая задача устраняет системный канал утечки (п.6), который точно воспроизводим и объясняет другую часть аномалий.

## Требования

### Функциональные

- `application.yml` (база, применяется ко всем профилям, если не переопределено): убрать боевые ID как дефолт —
  ```yaml
  app:
    analytics:
      ga4-id: ${GA4_MEASUREMENT_ID:}
      clarity-id: ${CLARITY_PROJECT_ID:}
  ```
- `application-prod.yml` (применяется только при `SPRING_PROFILES_ACTIVE=prod` — ровно то, что использует боевой сервер по умолчанию `docker-compose.yml`): задать дефолт на текущие реальные ID, чтобы поведение прода не изменилось без каких-либо действий на сервере:
  ```yaml
  app:
    analytics:
      ga4-id: ${GA4_MEASUREMENT_ID:G-X5G4N3ND26}
      clarity-id: ${CLARITY_PROJECT_ID:yu4n92bsuy}
  ```
- `templates/fragments/analytics.html`: оба фрагмента (`ga4`, `clarity`) не должны выводить вообще ничего (ни `<script>`, ни вызовы `gtag`/`clarity`-инициализацию), если соответствующий ID — пустая строка. Реализуется `th:if="${not #strings.isEmpty(ga4Id)}"` / `th:if="${not #strings.isEmpty(clarityId)}"` на корневом `th:block` каждого фрагмента.

### Нефункциональные
- Безопасность: нет новой точки входа данных пользователя — чисто конфигурационное разделение окружений.
- i18n: не применимо.
- Прод не требует никаких изменений на сервере/в `.env`/`docker-compose.yml` — дефолт в `application-prod.yml` полностью покрывает текущее поведение.

## Вне скоупа

- Выяснение точного происхождения конкретных исторических сессий `localhost:4200` в уже накопленных данных GA4 — требует доступа к сырым данным GA4 (referrer, user-agent), которого нет у конвейера; это зафиксировано как открытый пункт для заказчика (см. "Открытые вопросы" и финальный отчёт архитектора), не код.
- Любая очистка/аннотирование уже собранных в GA4 исторических данных — делается заказчиком в кабинете GA4 (data filters/annotations), не через этот репозиторий.
- Передача `GA4_MEASUREMENT_ID`/`CLARITY_PROJECT_ID` через `docker-compose.yml`/секреты сервера — не требуется этой задачей (прод работает на дефолте профиля), не делается, чтобы не трогать серверную конфигурацию без отдельного согласования (`GIT_WORKFLOW.md §7`).

## Критерии приёмки

- [ ] При поднятом приложении с `SPRING_PROFILES_ACTIVE=cloud` и без явно заданных `GA4_MEASUREMENT_ID`/`CLARITY_PROJECT_ID` — ни на одной странице в HTML-ответе нет `googletagmanager.com` и нет вставки `clarity.ms` (`curl`/`grep` по финальному HTML `index.html`, `tournament-details.html`).
- [ ] При тех же условиях, но с явно заданным `GA4_MEASUREMENT_ID=G-TEST123` в окружении — тег рендерится с этим ID (подтверждает, что оверрайд по-прежнему работает, профиль не блокирует легитимную настройку, например, для будущей отдельной test-GA4-property).
- [ ] Значение по умолчанию для `prod`-профиля (`application-prod.yml` + пустая env-переменная) эквивалентно текущему поведению — `G-X5G4N3ND26`/`yu4n92bsuy` (юнит/конфигурационная проверка, без реального прод-окружения).
- [ ] `./mvnw compile -DskipTests` и `./mvnw verify` проходят.
- [ ] Существующие тесты, завязанные на `fragments/analytics.html` (если есть), не сломаны; если тестов на фрагмент нет — не добавляется новый Spring-контекстный тест ради этого (YAGNI), проверяется вручную/Playwright по критерию выше.

## Edge cases

- `GA4_MEASUREMENT_ID` задан, а `CLARITY_PROJECT_ID` — нет (или наоборот): каждый ID проверяется независимо, фрагменты не связаны друг с другом.
- Значение переменной — строка из пробелов: не обрабатывается отдельно (не описано в запросе, едва ли реальный сценарий для ID, задаваемого вручную оператором) — считается непустым (`#strings.isEmpty` не триммит), не блокирует эту задачу.

## Открытые вопросы

Технических открытых вопросов, блокирующих реализацию, нет — решение по профилям (`prod`-дефолт, не трогать сервер) обосновано в разделе "Вне скоупа" (`GIT_WORKFLOW.md §3`, разумный технический выбор).

Отдельно для заказчика (не блокирует реализацию, часть финального отчёта, не этой спеки): происхождение конкретных исторических сессий `localhost:4200` в уже собранных данных GA4 не объясняется кодом репозитория (порта 4200 в проекте нет) — вероятно сторонний локальный инструмент у кого-то из команды, открывавший боевой домен; для точной идентификации нужен доступ к сырым данным GA4 (Explore-отчёт с разбивкой по `user agent`/`full referrer`/`hostname`), которого у конвейера нет.
