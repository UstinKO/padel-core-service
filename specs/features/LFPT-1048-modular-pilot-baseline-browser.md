implemented

## Требования

### Функциональные

#### Цель
Подготовить и выполнить исходную браузерную/скриптовую матрицу подтверждённого пилота PlayoffMatchingEngine до Maven-переноса. Это отдельная начальная задача; #1045 остаётся финальной приёмкой после переноса.

#### Что сделать
- Использовать данные backend-подготовки и существующий preview; отдельный экземпляр/БД, синтетические роли, без изменений Java и production UI.
- Дополнить docs/modular-monolith/pilot-and-e2e.md конкретными fixtures, ожидаемыми результатами, маршрутами и нажатиями.
- Автоматизировать реально существующие пути /tournaments/team-playoff/admin/{id}, init-qualification, init-playoff, regenerate-playoff; API qual/playoff-matches/{id}/result с действующими CSRF, expectedConductVersion и expectedTeam1/expectedTeam2 по фактическому контракту.
- Проверить обычные 8 команд, 9-командный play-in, 16-командный сценарий; раннее создание сетки/backfill; переходы до чемпиона, сохранение и повторное открытие, доступ другого клуба/анонима, stale/repeated действия. Unit-only случаи не имитировать придуманными UI-кнопками.
- Проверить реальную публикацию/отображение WS на действующих destinations и публичную карточку/snapshot, без изменения transport.
- Отдельно выполнить руками кнопочный проход ключевых сценариев. Playwright не считается ручной проверкой.
- Общий smoke legacy MVC, API, /web/ и /app/, login/session/CSRF/JWT по доступным текущим сценариям; новые participation-сценарии актуального master также не должны регрессировать.
- Зафиксировать SHA и результаты, команды/нажатия, доказательства без секретов, известные дефекты. Сохранить скрипты для повторного прогона C/D и #1045.

- [x] Отдельные ручные нажатия выполнены и отражены по кейсам в принятом владельцем объёме M01/M02; непроверенные пункты и перенос в #1045 перечислены.
- [x] Fixtures и тесты воспроизводимы; production Java/UI/контракты не изменены.
- [x] Исходный отчёт доступен задачам reactor, движка и #1045; принятый исходный объём не ожидает финальной e2e.


### Нефункциональные




Каждый PR самостоятельно оставляет приложение работоспособным: корневая полная сборка/verify, отдельный PostgreSQL для integration, smoke итогового jar/образа, действующие MVC/API/React/Expo, rollback. Реальные пользовательские БД/уведомления не используются. Java release 17, бизнес-правила и JSON/WS не меняются. Один слой и отдельный PR; без pipeline:ready, автомержа и деплоя в рамках подготовки. Документация — docs/modular-monolith/, спека с настоящим LFPT-номером.

Пилот сохраняет пути db/changelog, схему/данные/подключение. Временный root legacy src имеет одного владельца и один путь компиляции.

## Вне скоупа

Выделение persistence, физический перенос БД/Swarm, новые бизнес-правила, внутренний HTTP/микросервисы, полный рефакторинг TeamPlayoffService (#509), остальные движки и API codegen.

## Изменения в системе

### API

Внешний HTTP/WS контракт без изменений.

### БД

Нет Liquibase и production-изменений данных. Синтетические fixtures только в своей тестовой среде.

### UI

Production UI не меняется. Скрипты/Playwright и отдельная ручная приёмка существующих экранов.

### Документация

docs/modular-monolith/phase-1/ и актуальные карта/команды/пути по затронутой области; docs/Home.md, docs/architecture.md и .agents/PROJECT.md при реализации сборочных изменений. Фактическое состояние не подменяется будущими семью модулями.

## Edge cases

Равная стоимость/порядок перечисления, три приоритета, пустой/нечётный вход, play-in/TBD/backfill, no-show, stale pair/version, чужой клуб, rollback/history/after-commit. Для сборки: CWD тестов, один main/repackage/bean, frontend один раз, модульные отчёты, явный runtime jar, отсутствие shadow-класса. Применимость — по матрице и конкретному изменению; недостижимый из UI вход не получает выдуманную кнопку.

## Открытые вопросы

Неразрешённых бизнес-вопросов нет. Точные fixtures/ожидаемые результаты и дефекты фиксируются исходными #1047/#1048; технический выбор внутри согласованной границы выполняется по анализу, без изменения поведения.
