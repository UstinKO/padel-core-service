# Удалённое управление SDD-конвейером через Telegram

## Статус
done (2026-08-21) — все 6 этапов пройдены и подтверждены живой практикой (LFPT-328), оба хвоста (risk #7 мониторинг, risk #9 kill-switch) закрыты. Конвейер полноценно работает через Telegram на проде. Открытый вопрос №4 (research-preview без плана Б) остаётся осознанным, не блокирующим решением — не технический хвост, а постоянно пересматриваемая позиция пользователя.

## Источник
Прямая инициатива пользователя (архитектора), не клиентский запрос. Родилось из обсуждения в этом же чате: пилотные прогоны `/develop-feature` (LFPT-314, LFPT-316) на терминале, разведка возможностей Claude Code "routines" (облачные VM, `claude.ai/code/routines`) и официальной документации по безопасности (`code.claude.com/docs/en/security`).

**Почему не обычный LFPT-тикет:** это не единичный баг/фича с одним PR, а многоэтапная инициатива, часть шагов которой — действия вне репозитория (веб-интерфейс claude.ai, создание Telegram-бота, хостинг релея). Конкретные куски кода (релей, адаптация Tester-а под headless-браузер) будут оформлены отдельными LFPT-тикетами внутри соответствующих этапов, когда до них дойдёт очередь — этот файл выше по уровню, он про план в целом.

## Контекст / зачем

Сейчас `/develop-feature` запускается только из терминала на локальной машине пользователя — конвейер физически не может работать, если компьютер выключен. Цель: перенести управление конвейером в Telegram (сообщение — постановка задачи, сообщение — согласование нюансов спеки, сообщение — "задеплоено, закрывай"), а само исполнение — в облачную среду, независимую от локальной машины. Долгосрочная цель (озвучена ранее в этом чате) — постепенно убрать пользователя из цепочки реализации, оставив только ревью/деплой/саппорт.

Доступ к боту — только два человека (пользователь-архитектор и заказчик), все остальные отправители игнорируются на уровне релея.

## Архитектура (что установлено фактами, не догадками)

```
Telegram (тема "AI Разработка", группа "E.Padel - сайт")
   │
   ▼
Релей (scripts/telegram-relay/, systemd-сервис на проде 75.119.140.175, вне git)
   │  — фильтр по chat_id + message_thread_id + user_id, всё остальное молча игнорирует
   │  — маппинга "задача → session_id" НЕТ (у /fire нет параметра продолжения
   │    сессии — см. закрытый риск #8); каждое сообщение — новая независимая сессия
   ▼
Claude Code Routine `padel-env-validation` — API-триггер (bearer-токен, POST {text})
   │  claude.ai/code/routines, окружение настраивается только через веб-UI
   ▼
Изолированная облачная VM (Ubuntu 24.04, ~4 vCPU/16GB/30GB, Anthropic-managed)
   │  Docker предустановлен (Postgres для интеграционных тестов)
   │  Node/npm предустановлены (Playwright для headless QA — НЕ claude-in-chrome,
   │  тот жёстко привязан к локальному Chrome пользователя)
   │  GitHub-доступ — через secure proxy, credential заскоужен и не является
   │  реальным токеном пользователя; push ограничен рабочей веткой сессии
   ▼
GitHub (padel-core-service) → PR → пользователь ревьюит и мержит сам
   │
   ▼
Роутина сама шлёт исходящие уведомления в Telegram (curl к Bot API,
токен бота — секрет в окружении роутины)
```

Источники: `code.claude.com/docs/en/routines`, `code.claude.com/docs/en/cloud-environments.md`, `code.claude.com/docs/en/security` (см. цитаты и ссылки в переписке — не дублирую здесь целиком).

## Риски

| # | Риск | Серьёзность | Комментарий |
|---|------|-------------|-------------|
| 1 | **Docker+Postgres+Playwright в облачной песочнице не проверены под реальной нагрузкой** конвейера (Developer компилирует/тестирует, Tester поднимает приложение и гоняет headless-браузер) — есть только документальное подтверждение, что Docker и Node/Playwright *в принципе* доступны | Высокий, блокирующий | Закрывается Этапом 0 — до него дальше не идём |
| 2 | **Routines — research preview** (запущено апрель 2026) | Средний | Может меняться/ломаться без предупреждения, нет публичного SLA. Не строить на этом единственную точку отказа без плана Б |
| 3 | **Tester в облаке использует другой инструмент QA** (Playwright вместо `claude-in-chrome`) | Средний | Нужно валидировать, что качество проверки не деградирует — другой набор инструментов, другие возможности (нет реального взаимодействия с расширением браузера) |
| 4 | **Не подтверждено, покрывают ли SOC 2/ISO 27001 именно фичу routines** отдельной строкой, или это сертификация уровня всей компании | Низкий-средний, юридический | Нужна отдельная проверка на `trust.anthropic.com`, если для бизнеса это принципиально (реальные ФИО/телефоны игроков в проекте) |
| 5 | **Точный срок хранения транскриптов/логов сессии** не найден явно в документации (есть общая отсылка на Privacy Center) | Низкий | Не блокирует, но стоит иметь в виду при решении, что можно писать в промпты роутины |
| 6 | **Секреты окружения роутины (GitHub App — ок, но Telegram bot token и любые другие) — не защищены тем же proxy-механизмом**, что git-credential; это обычные env vars внутри VM | Средний | Максимально узкий скоуп токенов; НИКОГДА не класть туда прод-SSH-ключ, прод-DB креды, `SECURITY.md`/`THREATS.md` — правило зафиксировано, не полагаемся только на изоляцию платформы |
| 7 | ~~Релей — новая точка отказа, вне существующего мониторинга~~ | Закрыт (2026-08-21) | `telegram-relay-alert.service` через systemd `OnFailure=` (срабатывает, когда `StartLimitBurst` исчерпан — не на каждый единичный крэш, те тихо покрывает `Restart=always`) шлёт алерт тем же ботом в существующую тему "Инциденты и Инфа" (`message_thread_id=1951`). Полную остановку хоста сознательно не покрывает — для этого нужен внешний мониторинг с другой машины, отдельное решение при необходимости. Проверено вживую: ручной запуск `telegram-relay-alert.service` реально доставил сообщение в тему. |
| 8 | ~~Непрерывность диалога через `fire` API не подтверждена эмпирически~~ | Закрыт (2026-08-20) | **Опровергнуто документацией**, не подтверждено: у `/fire` нет параметра продолжения сессии — каждый вызов создаёт новую (см. `code.claude.com/docs/en/routines`, `platform.claude.com/docs/en/api/claude-code/routines-fire`). Дизайн релея это учитывает: маппинга "задача → session_id" нет, каждое сообщение — независимая сессия; непрерывность многодневного диалога — забота промпта роутины (Этап 3), который должен сам восстанавливать контекст из состояния репозитория (ветка/спека/PR), а не из истории чата. |
| 9 | ~~Единая точка отказа доступа: компрометация Telegram-аккаунта~~ | Закрыт (2026-08-21) | Emergency kill-switch реализован — страница `/admin/telegram-pipeline` (`ROLE_SUPER_ADMIN`, [LFPT-338](https://github.com/UstinKO/padel-core-service/pull/339)) переключает `paused` в БД (`telegram_pipeline_state_db`), relay опрашивает `GET /api/internal/telegram-pipeline/status` (общий секрет в заголовке) перед каждым `/fire` и **fail-closed**: любая неопределённость (эндпоинт недоступен, неверный секрет) трактуется как "приостановлен". Альтернативные способы (`systemctl stop telegram-relay`, `Revoke` токена роутины) остаются как запасной путь. |
| 10 | **Заказчик как второй допущенный отправитель** — его сообщения по идее должны идти через более мягкий вход (`specs/requests/`, не напрямую `specs/features/`), в отличие от технических сообщений архитектора | Низкий, но нужно явное решение | Иначе заказчик неявно получает право формулировать техническое ТЗ напрямую, минуя разбор аналитиком |
| 11 | **Стоимость/лимиты запуска роутин** не оценивались | Неизвестно | Уточнить при создании роутины на claude.ai — там обычно видно лимиты плана |
