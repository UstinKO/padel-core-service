# Удалённое управление SDD-конвейером через Telegram

## Статус
draft — есть открытые вопросы, требующие решения пользователя (см. в конце).

## Источник
Прямая инициатива пользователя (архитектора), не клиентский запрос. Родилось из обсуждения в этом же чате: пилотные прогоны `/develop-feature` (LFPT-314, LFPT-316) на терминале, разведка возможностей Claude Code "routines" (облачные VM, `claude.ai/code/routines`) и официальной документации по безопасности (`code.claude.com/docs/en/security`).

**Почему не обычный LFPT-тикет:** это не единичный баг/фича с одним PR, а многоэтапная инициатива, часть шагов которой — действия вне репозитория (веб-интерфейс claude.ai, создание Telegram-бота, хостинг релея). Конкретные куски кода (релей, адаптация Tester-а под headless-браузер) будут оформлены отдельными LFPT-тикетами внутри соответствующих этапов, когда до них дойдёт очередь — этот файл выше по уровню, он про план в целом.

## Контекст / зачем

Сейчас `/develop-feature` запускается только из терминала на локальной машине пользователя — конвейер физически не может работать, если компьютер выключен. Цель: перенести управление конвейером в Telegram (сообщение — постановка задачи, сообщение — согласование нюансов спеки, сообщение — "задеплоено, закрывай"), а само исполнение — в облачную среду, независимую от локальной машины. Долгосрочная цель (озвучена ранее в этом чате) — постепенно убрать пользователя из цепочки реализации, оставив только ревью/деплой/саппорт.

Доступ к боту — только два человека (пользователь-архитектор и заказчик), все остальные отправители игнорируются на уровне релея.

## Архитектура (что установлено фактами, не догадками)

```
Telegram (2 разрешённых user_id)
   │
   ▼
Релей (свой код, always-on хостинг — TBD)
   │  — фильтр по user_id, всё остальное молча игнорирует
   │  — хранит маппинг "задача → routine session_id" для многодневных диалогов
   ▼
Claude Code Routine — API-триггер (bearer-токен, POST {text})
   │  claude.ai/code/routines, окружение настраивается только через веб-UI
   ▼
Изолированная облачная VM (Ubuntu 24.04, ~4 vCPU/16GB/30GB, Anthropic-managed)
   │  Docker предустановлен (Postgres для интеграционных тестов)
   │  Node/npm предустановлены (Playwright для headless QA — НЕ claude-in-chrome,
   │  тот жёстко привязан к локальному Chrome пользователя)
   │  GitHub-доступ — через secure proxy, credential заскоужен и не является
   │  реальным токеном пользователя; push ограничен рабочей веткой сессии
   ▼
GitHub (padel-core-service) → PR → пользователь ревьюит и мержит сам
   │
   ▼
Роутина сама шлёт исходящие уведомления в Telegram (curl к Bot API,
токен бота — секрет в окружении роутины)
```

Источники: `code.claude.com/docs/en/routines`, `code.claude.com/docs/en/cloud-environments.md`, `code.claude.com/docs/en/security` (см. цитаты и ссылки в переписке — не дублирую здесь целиком).

## Риски

| # | Риск | Серьёзность | Комментарий |
|---|------|-------------|-------------|
| 1 | **Docker+Postgres+Playwright в облачной песочнице не проверены под реальной нагрузкой** конвейера (Developer компилирует/тестирует, Tester поднимает приложение и гоняет headless-браузер) — есть только документальное подтверждение, что Docker и Node/Playwright *в принципе* доступны | Высокий, блокирующий | Закрывается Этапом 0 — до него дальше не идём |
| 2 | **Routines — research preview** (запущено апрель 2026) | Средний | Может меняться/ломаться без предупреждения, нет публичного SLA. Не строить на этом единственную точку отказа без плана Б |
| 3 | **Tester в облаке использует другой инструмент QA** (Playwright вместо `claude-in-chrome`) | Средний | Нужно валидировать, что качество проверки не деградирует — другой набор инструментов, другие возможности (нет реального взаимодействия с расширением браузера) |
| 4 | **Не подтверждено, покрывают ли SOC 2/ISO 27001 именно фичу routines** отдельной строкой, или это сертификация уровня всей компании | Низкий-средний, юридический | Нужна отдельная проверка на `trust.anthropic.com`, если для бизнеса это принципиально (реальные ФИО/телефоны игроков в проекте) |
| 5 | **Точный срок хранения транскриптов/логов сессии** не найден явно в документации (есть общая отсылка на Privacy Center) | Низкий | Не блокирует, но стоит иметь в виду при решении, что можно писать в промпты роутины |
| 6 | **Секреты окружения роутины (GitHub App — ок, но Telegram bot token и любые другие) — не защищены тем же proxy-механизмом**, что git-credential; это обычные env vars внутри VM | Средний | Максимально узкий скоуп токенов; НИКОГДА не класть туда прод-SSH-ключ, прод-DB креды, `SECURITY.md`/`THREATS.md` — правило зафиксировано, не полагаемся только на изоляцию платформы |
| 7 | **Релей — новая точка отказа**, само не входит в существующий мониторинг (Grafana/Prometheus покрывают только сам padel-app) | Средний | Если релей упал — Telegram молчит, конвейер не запускается, и никто не узнает, пока не попробуют написать. Нужен хотя бы базовый healthcheck/алерт |
| 8 | **Непрерывность диалога через `fire` API не подтверждена эмпирически** — по документации похоже, что можно дописывать в существующую сессию, но это не проверено на практике для сценария "спека сегодня, ответ на вопрос через два дня" | Средний | Проверяется на Этапе 4 (сквозной тест) |
| 9 | **Единая точка отказа доступа**: компрометация Telegram-аккаунта одного из двух разрешённых людей = полный доступ к конвейеру (создание веток/PR от имени проекта) | Средний | Стоит явно решить, нужен ли emergency kill-switch (например, команда в самом боте "стоп всем", отзыв токена релея) |
| 10 | **Заказчик как второй допущенный отправитель** — его сообщения по идее должны идти через более мягкий вход (`specs/requests/`, не напрямую `specs/features/`), в отличие от технических сообщений архитектора | Низкий, но нужно явное решение | Иначе заказчик неявно получает право формулировать техническое ТЗ напрямую, минуя разбор аналитиком |
| 11 | **Стоимость/лимиты запуска роутин** не оценивались | Неизвестно | Уточнить при создании роутины на claude.ai — там обычно видно лимиты плана |

### Этап 0 — Валидация окружения (блокирующий, ничего дальше не делаем без него) ✅ done

Результат: [specs/done/telegram-remote-pipeline-stage0-validation.md](../done/telegram-remote-pipeline-stage0-validation.md). Docker Hub заблокирован сетевой политикой (не блокер — Postgres поднимается через предустановленный локальный сервис), `./mvnw verify` реально прошёл (50/50), Playwright подтверждён рабочим против localhost. Три поправки к плану внесены (профиль `cloud`, готовность по логу, не Docker для Postgres).

- **Я:** подготовлю точный текст промпта и (если понадобится) содержимое setup-скрипта для тестового прогона — "подними Postgres через `docker compose`, прогони `./mvnw verify`, пришли результат".
- **Ты:** создаёшь роутину на `claude.ai/code/routines` (веб-интерфейс, я туда доступа не имею), подключаешь репозиторий `padel-core-service` (GitHub App), настраиваешь окружение (сетевой доступ минимум "Trusted"), вставляешь мой промпт, жмёшь "Run now".
- **Ты:** присылаешь мне ссылку на сессию/лог прогона.
- **Я:** разбираю лог, подтверждаю или опровергаю, что Docker+Postgres реально работают в этой среде под нашей конкретной нагрузкой.

**Критерий перехода к Этапу 1:** `./mvnw verify` реально прошёл в облачной роутине с живым Postgres.

### Этап 1 — Адаптация Tester под headless-режим ✅ done

Результат: [specs/done/telegram-remote-pipeline-stage2-e2e-pilot.md](../done/telegram-remote-pipeline-stage2-e2e-pilot.md) (фактически объединился с пилотом целого конвейера — Playwright-режим `tester.md`/`developer.md` проверен не изолированно, а под реальной нагрузкой LFPT-317 в трёх раундах, включая живую регрессию через curl/Playwright и самостоятельное устранение окружных трений тестировщиком). Решение по определению режима: единый файл `tester.md` с веткой `local`/`cloud` внутри, отдельный `tester-cloud.md` не понадобился.

### Этап 2 — Telegram-бот и релей

- **Ты:** создаёшь **отдельного, нового** Telegram-бота через `@BotFather` — не переиспользовать существующий (`TelegramService`/`TelegramBotPoller`), у него другое назначение: инцидент-алерты и WARN/ERROR из логов (см. `project-telegram.md`), не управление разработкой. Разные боты — разные токены, разные креды, не смешивать зоны ответственности (см. `GIT_WORKFLOW.md §8`). Получаешь токен нового бота, узнаёшь свой `user_id` и `user_id` заказчика (например через `@userinfobot`).
- **Решено:** релей хостится на проде (`75.119.140.175`) — уже доверенный, уже под мониторингом. Деплой релея туда — отдельное согласование по `GIT_WORKFLOW.md §7`, как и любое серверное изменение, когда код будет готов.
- **Я:** пишу код релея (фильтр по двум `user_id`, маппинг "сообщение → routine session", вызов API-триггера роутины). Сообщения архитектора — прямой технический вход (как сейчас в терминале); сообщения заказчика — всегда через мягкий `specs/requests/`, с обязательным разбором Analyst-ом, без прямого попадания в `specs/features/`.

### Этап 3 — Настройка роутины и API-триггера

- **Ты:** в веб-интерфейсе создаёшь API-триггер для роутины, получаешь bearer-токен, вписываешь его и токен Telegram-бота как секреты в окружение роутины.
- **Я:** готовлю финальный промпт роутины — обвязку вокруг `/develop-feature` (роутина получает текст из Telegram, определяет отправителя — архитектор или заказчик — и стартует конвейер соответствующим входом).

### Этап 4 — Сквозной тест

- **Совместно:** проводим один реальный маленький тикет от Telegram-сообщения до задеплоенного PR, без единого захода в терминал.
- **Я:** разбираю логи, ищу швы конвейера (как это было на пилотах LFPT-314/316) и чиню их.

### Этап 5 — Перевод в рабочий режим

- **Я:** обновляю `develop-feature.md`/`GIT_WORKFLOW.md` — конвейер теперь может стартовать и из терминала, и из Telegram, оба пути равноправны.
- **Совместно:** фиксируем финальный список того, что никогда не кладём в облачное окружение (прод-SSH-ключ, прод-DB креды, `SECURITY.md`/`THREATS.md`).
