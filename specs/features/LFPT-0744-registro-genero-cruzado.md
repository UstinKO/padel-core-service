# LFPT-0744: Feature регистрация на турниры другого пола по расчётному уровню — шкала соответствия категорий C/D

## Статус
approved

## Источник
Клиентский запрос [specs/requests/LFPT-0744-registro-genero-cruzado.md](../requests/LFPT-0744-registro-genero-cruzado.md), технически оформлен в issue [#744](https://github.com/UstinKO/padel-core-service/issues/744). Расширяет #303 (правило "±1 ступень", смотри `TournamentLevelPolicy`) и опирается на уже реализованный попап "Указать уровень" (#632), который эта задача не меняет.

## Контекст / зачем

Сейчас `TournamentLevelPolicy.evaluate()` блокирует регистрацию, если `playerLevel.getGeneroAplicable() != categoriaNivel.getGeneroAplicable()` — женщина не может зарегистрироваться на мужской турнир и наоборот, независимо от того, насколько близки уровни по силе игры. Заказчик просит снять это ограничение и сравнивать уровни по единой числовой шкале, которая переводит женские категории (`D`) в эквивалент мужских (`C`): `Dn → n + 1`, `Cn → n`. Правило допуска (разница ≤ 1 расчётной ступени) не меняется — меняется только то, что сравнение больше не требует совпадения пола.

## Связь с MASTER.md

Затрагивает раздел «Ограничение по уровню (LFPT-0303)» в `specs/MASTER.md`. Текущая формулировка ("самостоятельная регистрация ... допускается только если уровень игрока отличается от категории турнира не более чем на одну ступень") остаётся верной по смыслу, но текст инварианта явно описывает сравнение только "в пределах одной шкалы" (мужской с мужской, женской с женской) — это нужно обновить, чтобы не противоречить новому поведению. MASTER.md правится в этом же PR.

## Требования

### Функциональные

1. **Единая шкала сравнения.** Ввести функцию расчётного уровня для "простых" категорий (`Nivel.isPlayerLevel(...) == true`, т.е. `C9..C4`, `D9..D6`):
   - `C9→9, C8→8, C7→7, C6→6, C5→5, C4→4`
   - `D9→10, D8→9, D7→8, D6→7`

   (Формула `Dn → n+1` для полноты распространяется и на `D5→6`, `D4→5`, но эти две категории не входят в `Nivel.isPlayerLevel` и правило на них, как и сейчас, не применяется — см. "Вне скоупа".)

2. **Новое условие допуска.** `TournamentLevelPolicy.evaluate(tipo, categoriaNivel, playerLevel)`: если применимо правило (см. п.3 "Вне скоупа" — условие `requiresLevelCheck` не меняется) и `playerLevel` указан — вердикт `ALLOWED`, если `abs(calc(playerLevel) - calc(categoriaNivel)) <= 1`, иначе `LEVEL_MISMATCH`. Проверка пола (`getGeneroAplicable()`) из условия убирается полностью — расчётная шкала уже учитывает различие полов через саму формулу.

3. **Список допустимых категорий в сообщении об ошибке.** `allowedLevelsAround(playerLevel)` пересчитывается на основе той же расчётной шкалы: все значения `Nivel`, для которых `Nivel.isPlayerLevel(...) == true` и `abs(calc(v) - calc(playerLevel)) <= 1`, независимо от пола. Из этого прямо следует, что список теперь может содержать категории обоих полов (например, для игрока `C7` в список попадёт и `D6`, т.к. `calc(D6)=7=calc(C7)`) — это ожидаемое, а не побочное поведение: сообщение должно точно отражать, что реально разрешено.

4. **Сообщение об ошибке** не упоминает пол ни в одном из трёх языков — у существующих ключей `tournament.register.level_required` / `tournament.register.level_mismatch` (es/ru/en) и так нет упоминания пола, менять тексты не нужно, только содержимое списка (п.3) станет шире.

5. **Применяется везде, где уже применяется #303**, без дополнительного кода в вызывающих местах — изменение полностью локализовано в `TournamentLevelPolicy`:
   - `TournamentService.registerPlayer()` — одиночная регистрация.
   - `DoubleTournamentRegistrationService` — парная регистрация (соло с намерением найти пару, пара с существующим партнёром по email/телефону/ID, `add-partner`). Партнёр без аккаунта на момент регистрации по-прежнему не проверяется техническими причинами (аккаунт создаётся позже с `SIN_ESPECIFICAR`) — не меняется, как и в #303.

### Нефункциональные

- i18n: новых пользовательских строк не требуется — существующие ключи (`tournament.register.level_mismatch` и т.п.) используются как есть, их смысл не завязан на пол.
- Безопасность: новой точки входа данных от пользователя нет, сервер как и раньше читает категорию игрока и турнира из БД (не из запроса клиента).
- Производительность: без изменений — расчёт `calc()` — чистая O(1) операция, замена существующего `.ordinal()` сравнения.

## Вне скоупа

- **Приоритетная регистрация с категориями "сразу в основной / только в резерв / не допускается".** Исходный запрос просит не ломать такие настройки, если они включены для мероприятия. Технически проверено (поиск по `Tournament`-entity, миграциям БД и issue-трекеру) — такого механизма в системе сейчас нет: нет полей конфигурации, нет кода. Условие запроса формально выполняется само собой (нет настроек — нечего ломать), и создание нового конфигурационного функционала приоритетной регистрации по категориям в эту задачу не входит. Если он понадобится — отдельная фича с собственной спекой.
- Диапазоны категорий (`C9_C8`, `D7_D8`, `D9_D8` и т.п.), `TODOS`, `PRINCIPIANTES`, `SUMA_*`, а также `D5`/`D4` (не входят в `Nivel.isPlayerLevel`, не назначаются игроку, см. #373/#206) — как и в #303, правило на них не действует. Формула `Dn→n+1` для `D5`/`D4` в коде не нужна, т.к. `requiresLevelCheck` их не пропускает.
- Открытые форматы (`CANCHA_ABIERTA`, `PADEL_CLINIC`) — без изменений, правило не применяется.
- Игрок с `SIN_ESPECIFICAR`/`null` — без изменений, блокировка и попап "Указать уровень" (#632) не трогаются этой задачей.
- Ручное добавление через `TestTournamentController` (JDBC, минуя `TournamentLevelPolicy`) — без изменений, не затронуто технически.
- Изменение значений `Nivel` (новых enum-констант, в т.ч. `C10`) — не создаётся; расчётный уровень — временное int-значение внутри `TournamentLevelPolicy`, не публичный API и не поле БД.
- Расчёт суммы пары для `SUMA_*` — не меняется.

## Критерии приёмки

- [ ] `TournamentLevelPolicy.evaluate()` возвращает `ALLOWED`/`LEVEL_MISMATCH` по формуле `abs(calc(player) - calc(tournament)) <= 1`, где `calc(Cn)=n`, `calc(Dn)=n+1`, без проверки `getGeneroAplicable()`.
- [ ] Эталонные пары дают указанный вердикт: D6→C7 ALLOWED; D7→C7 ALLOWED; D8→C7 LEVEL_MISMATCH; D9→C7 LEVEL_MISMATCH; D8→C9 ALLOWED; D9→C9 ALLOWED; D9→C8 LEVEL_MISMATCH; C7→D6 ALLOWED; C9→D6 LEVEL_MISMATCH; C7→C9 LEVEL_MISMATCH; C9→C7 LEVEL_MISMATCH.
- [ ] Для одинакового пола поведение не изменилось — все существующие параметризованные кейсы `TournamentLevelPolicyTest` (разрешённые и запрещённые пары одного пола) остаются зелёными без изменения ожидаемого вердикта.
- [ ] Тест, фиксирующий блокировку по одному только полу (`generoDistinto_bloqueaAunqueOrdinalEsteCerca`), заменён тестом, фиксирующим новое поведение (разные полы, близкий расчётный уровень → `ALLOWED`; разные полы, далёкий расчётный уровень → `LEVEL_MISMATCH`, но по расчёту, не по полу).
- [ ] `allowedLevelsAround(...)` для игрока одного пола корректно включает соседние категории другого пола, когда их расчётный уровень в пределах ±1 (например, для `C7` список включает `D6`).

## Edge cases

- Граница применимости: `C4` (самый слабый мужской простой уровень, расчёт 4) и `D9` (расчёт 10) — разница 6, `LEVEL_MISMATCH`, как и сейчас (просто теперь по расчётной шкале, а не по полу напрямую).
- Симметричность: правило должно давать одинаковый вердикт независимо от того, что считается "игроком", а что "турниром" — `evaluate(тип, catTorneo, catJugador)` симметрично по построению формулы (`abs(a-b) == abs(b-a)`), отдельного теста на симметрию не требуется сверх эталонных пар в прямом и обратном направлении (уже покрыты критериями приёмки).
- Партнёр без аккаунта в парной регистрации — как и в #303, не проверяется на этом шаге (аккаунт создаётся позже с `SIN_ESPECIFICAR`); это не регрессия этой задачи, поведение наследуется от #303 без изменений.
- Существующие регистрации, созданные до этой фичи при другом правиле (например, отклонённые ранее попытки) — не затрагиваются, миграции/бэкфилла не требуется, правило применяется только к новым попыткам регистрации.
