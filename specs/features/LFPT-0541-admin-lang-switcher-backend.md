# LFPT-0541: Feature механизм ручного переключения языка в админ-панели — cookie-резолвер и override (backend)

## Статус
approved

## Источник
Клиентский запрос [specs/requests/LFPT-0541-admin-lang-switcher.md](../requests/LFPT-0541-admin-lang-switcher.md) (Telegram, пересланное сообщение от Evgeny_754, `telegram_launch_message_id: 4984`). GitHub issue [#541](https://github.com/UstinKO/padel-core-service/issues/541).

Разбито на бэкенд/фронтенд (`GIT_WORKFLOW.md §1.4`) — эта спека покрывает бэкенд. Зависимая фронтенд-задача — [#542](https://github.com/UstinKO/padel-core-service/issues/542) (переключатель в шапке админ-панели).

## Контекст / зачем
Сейчас локаль (`es`/`ru`/`en`) определяется только `AcceptHeaderLocaleResolver` (`LocaleConfig.java`) — по заголовку `Accept-Language` браузера, без возможности ручного выбора (`.claude/CLAUDE.md § i18n`). Чтобы в админ-панели появился переключатель языка (#542), сначала нужен механизм, который умеет принимать ручной выбор, отдавать ему приоритет над автоопределением и сохранять его между запросами/визитами.

## Связь с MASTER.md
Не затрагивает ни один инвариант `specs/MASTER.md` — не вводит новую роль, статус, бизнес-правило. Чисто техническая инфраструктура резолвинга локали, видимая пользователю только через зависимую фронтенд-задачу.

## Требования

### Функциональные

1. **Новый `LocaleResolver`** (`config/LocaleConfig.java` или новый класс `config/CookieLocaleResolver.java` — на усмотрение реализации, по аналогии с существующим стилем проекта), заменяющий текущий `AcceptHeaderLocaleResolver`-бин:
   - `resolveLocale(request)`: если в запросе есть валидная cookie `lang` (значение ∈ `{es, ru, en}`) — вернуть соответствующую `Locale`. Иначе — делегировать существующему `AcceptHeaderLocaleResolver`-поведению (та же логика: `Accept-Language`, поддерживаемые локали `{es, ru, en}`, дефолт `es`) — **без регрессии** текущего резолвинга там, где cookie не выставлена.
   - `setLocale(request, response, locale)`: если `locale != null` и входит в `{es, ru, en}` — выставить cookie `lang` со значением языка. Если `locale == null` — удалить cookie, не выбрасывать `UnsupportedOperationException` (в отличие от `AcceptHeaderLocaleResolver`, этот метод обязателен для работы `LocaleChangeInterceptor`).
   - Cookie: `path=/`, `httpOnly=false` (нужен JS на фронтенде для подсветки активного варианта — см. #542), `secure` — **динамически** через `request.isSecure()`, не статичный флаг (известная ловушка проекта — TLS терминируется на Nginx, см. комментарий в `CookieController.addConsentCookie`, issue #123). `sameSite=Lax`. Срок жизни — достаточно большой, чтобы выбор переживал закрытие браузера и следующий вход (например 365 дней, по аналогии с `CookieController.CONSENT_MAX_AGE`).
2. **`LocaleChangeInterceptor`**, параметр `lang` (`setParamName("lang")`), зарегистрированный через `WebMvcConfigurer.addInterceptors` (новый метод в `LocaleConfig` — класс реализует `WebMvcConfigurer`, либо отдельный `@Configuration`). Перехватывает любой запрос с query-параметром `?lang=es|ru|en` **на любом URL** (не только `/admin/**` — сам резолвер/интерсептор — общая инфраструктура; то, что переключатель в UI появится только в админке на этом этапе, — требование #542, не ограничение этой задачи). Interceptor вызывает `localeResolver.setLocale(...)`, которая и запишет cookie.
3. **Невалидное значение `?lang=`** (не входит в `{es, ru, en}`) — `LocaleChangeInterceptor` не должен падать с 500; `setLocale` должен либо проигнорировать некорректное значение (не менять текущую локаль/cookie), либо откатиться на дефолт — не пропускать его в cookie как есть.

### Нефункциональные
- i18n: новых пользовательских строк в этой (backend) задаче нет.
- Безопасность: `lang` — query-параметр, значение валидируется строго по allowlist `{es, ru, en}` до использования (не идёт напрямую в cookie/лог без проверки) — защита от произвольных значений в cookie. `GET`-параметр не требует CSRF-защиты (не мутирует состояние сервера, только cookie предпочтения пользователя, аналогично `cookieConsent`).
- Производительность: резолвинг локали — на каждый запрос, как и сейчас (`AcceptHeaderLocaleResolver` уже вызывается на каждый запрос) — новый резолвер не добавляет обращений к БД/внешним сервисам, только чтение cookie/заголовка.

## Вне скоупа
- UI-переключатель, подсветка текущего языка, место в шапке — [#542].
- Хранение выбора языка в БД на уровне аккаунта (`Owner`/`PlayerPadel`) — не запрошено; клиентский запрос явно говорит про сохранение "для следующего перехода / после обновления / при следующем входе", что cookie покрывает (тот же браузер/устройство). Выбор привязан к браузеру, не к аккаунту — осознанное техническое решение (см. «Открытые вопросы»).
- Применение переключателя к публичному сайту и личному кабинету игрока — явно вне скоупа клиентского запроса, п.5.

## Изменения в системе

### API
Нет новых REST-эндпоинтов. Любой существующий GET-URL начинает понимать необязательный query-параметр `?lang=es|ru|en` (глобально, через интерсептор) — сигнатуры контроллеров не меняются.

### БД
Нет.

### UI
Нет (эта задача — backend-only; UI — [#542]).

## Критерии приёмки
- [ ] Запрос без cookie `lang` и без `?lang=` — локаль резолвится как раньше, по `Accept-Language` (регрессионная проверка на нескольких существующих страницах — публичных и админских).
- [ ] `GET` любой страницы с `?lang=ru` — ответ рендерится на `ru` (проверяется по тексту страницы), в `Set-Cookie` ответа присутствует cookie `lang=ru`.
- [ ] Повторный запрос без `?lang=`, но с cookie `lang=ru` от предыдущего ответа — локаль `ru`, `Accept-Language` игнорируется (ручной выбор приоритетнее).
- [ ] `?lang=fr` (значение вне `{es, ru, en}`) — ответ не 500, локаль откатывается на `Accept-Language`/дефолт, в cookie не записывается `fr`.
- [ ] Cookie `lang` в ответе имеет `Secure`, совпадающий с `request.isSecure()` (проверяется на `http://localhost` в cloud-окружении — `Secure` отсутствует/`false`, см. Edge cases), `SameSite=Lax`, `Max-Age` порядка года.
- [ ] `./mvnw verify` зелёный.

## Edge cases
- `cloud`/локальная проверка идёт по `http://localhost` (не HTTPS) — `request.isSecure() == false`, cookie должна выставляться без `Secure`, иначе браузер/HTTP-клиент не отправит её обратно и переключение язык сломается уже на этапе локальной проверки (это и есть причина, по которой `secure` не статичный флаг, см. Требования п.1).
- Cookie `lang` с мусорным/невалидным значением, выставленная вручную (не через `?lang=`, а напрямую в браузере) — `resolveLocale` должен относиться к ней так же строго, как и `setLocale` к `?lang=`: невалидное значение — откат на `Accept-Language`, не 500 и не попытка создать `Locale` из произвольной строки без проверки.
- Два реплики в Docker Swarm — резолвинг локали полностью stateless (cookie на клиенте, запрос к БД не делается) — конкурентного доступа/рассинхрона между репликами не возникает.
- Запрос без заголовка `Accept-Language` вообще и без cookie — текущее поведение `AcceptHeaderLocaleResolver.setDefaultLocale(es)` должно сохраниться (дефолт `es`), не должно превратиться в `null`/исключение.

## Открытые вопросы
Нет. Два технических решения приняты архитектором самостоятельно (аналогично п.3 `GIT_WORKFLOW.md` — разумный выбор с коротким обоснованием, не бизнес-вопрос):
1. **Cookie, а не хранение в БД на аккаунте.** Клиентский запрос описывает персистентность в терминах "следующий переход / обновление / следующий вход" — это именно то, что даёт постоянная cookie в том же браузере. Привязка к аккаунту (видна с любого устройства) не была запрошена и добавила бы миграцию/поле на `Owner`, не оправданное текущей формулировкой — можно добавить позже отдельной задачей, если понадобится мультиустройственная персистентность.
2. **Интерсептор регистрируется глобально (`?lang=` работает на любом URL), а не только под `/admin/**`.** Ограничивать `LocaleChangeInterceptor.addPathPatterns("/admin/**")` не даёт никакого выигрыша (сам факт наличия параметра ничего не включает сам по себе — переключатель в UI и так появится только в админке, #542), а глобальная регистрация технически проще и не создаёт двух разных путей резолвинга локали для админки и публичного сайта — один и тот же механизм, просто кнопка пока есть только в одном месте.
