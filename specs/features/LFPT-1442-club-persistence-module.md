# LFPT-1442: Feature многомодульный монолит, фаза 6 — подключить модуль хранения клубов и перенести Liquibase

## Статус
done

## Источник
[Issue #1442](https://github.com/UstinKO/padel-core-service/issues/1442). Техническая постановка по утверждённой фазе 6. Родитель [#1051](https://github.com/UstinKO/padel-core-service/issues/1051).

## Контекст / зачем
Включить первую рабочую версию padel-persistence с реальными JPA-операциями клубов и единственным набором Liquibase.

## Связь с MASTER.md
[MASTER](../MASTER.md) определяет роли, границы клубного доступа, регистрацию, турнирные состояния и хранение истории вместе с подтверждённым изменением. Сценарии сохраняют текущие инварианты. Зависимости [#1440](https://github.com/UstinKO/padel-core-service/issues/1440), [#1441](https://github.com/UstinKO/padel-core-service/issues/1441).

## Требования

### Функциональные

- Перенести Club, его единственный репозиторий, адаптеры портов и entity-маппинг в padel-persistence. Bootstrap подключает модуль обычной зависимостью.
- Перенести дерево db/changelog без изменения байтов, classpath и версии Liquibase, перенастроить Maven, Docker, CI/preview и docs-drift. Сохранить один JAR, DataSource, EntityManagerFactory и Liquibase.

### Нефункциональные
- Java release 17, JDK 21 в CI, одна транзакционная граница и один Boot JAR.
- Каждый PR проходит полный verify на отдельной PostgreSQL, артефактные и архитектурные guards, runtime/релевантный браузер и проверку совместимости предыдущего релиза.
- Сохраняются действующие права, i18n ES/RU/EN и внешние контракты. Новых пользовательских строк нет.

## Вне скоупа
Ручной релиз остаётся обычным. Физическая миграция PostgreSQL, Swarm и изменения бизнес-правил вне задачи.

## Изменения в системе

### API
Прежние MVC/HTTP/WS входы, поля, статусы и права.

### БД
Файлы db/changelog перемещаются побайтно. Тот же classpath, версия Liquibase, ID/AUTHOR/FILENAME/MD5SUM, один DataSource/EMF/Liquibase. На предыдущей схеме никаких повторов.

### UI
Действующие клиенты используют прежние данные. Приёмочные сценарии запускаются через штатные входы.

### Документация
[План фазы 6](../../docs/modular-monolith/phase-6/README.md), документация фактических границ, затронутые endpoints и техническая карта при необходимости.

## Критерии приёмки

- [x] JAR хранит один набор db/changelog. На новой БД схема создаётся, на схеме предыдущего выпуска ни один changeset не выполняется вновь.
- [x] ID/AUTHOR/FILENAME/MD5SUM и данные неизменны после нового запуска, повторного запуска и возврата прежнего JAR. Без сброса checksum и ручного изменения истории.
- [x] Клубные запросы и записи, права, браузер и репетиция штатного релиза проходят на прежнем PostgreSQL.

[Реализация и результаты проверок](../../docs/modular-monolith/phase-6/club-persistence.md).

## Edge cases
Свежая схема, схема предыдущего выпуска, повторный старт и возврат его JAR. Дубли ресурсов и bootstrap-импорты запрещены.

## Открытые вопросы
Бизнес-вопросов нет. Технические подзадачи выделяются по фактическим связям JPA и потребителям. Реальные пользовательские данные и production-сервер не используются для QA.
