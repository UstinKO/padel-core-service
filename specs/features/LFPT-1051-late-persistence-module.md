# LFPT-1051: Feature многомодульный монолит, фаза 6 — выделить хранение и миграции в padel-persistence

## Статус
approved

## Источник
[Issue #1051](https://github.com/UstinKO/padel-core-service/issues/1051), решение владельца от 27.11.2026. Порядок уточнён в [ADR-0007](../../docs/modular-monolith/adr/0007-persistence-first.md).

## Контекст / зачем
Хранение следует выделить до остальных целевых модулей. Клубный срез даёт первую работающую реализацию persistence и единое место Liquibase, затем переходят остальные связанные группы.

## Связь с MASTER.md
[MASTER](../MASTER.md) определяет роли, правила клубов, регистрации и оплат, турнирные данные и историю. Перенос сохраняет их бизнес-инварианты и результаты.

## Требования

### Функциональные

Сначала выделяем код хранения в padel-persistence, затем переносим остальные части непосредственно в целевые модули. Решение принято 27.11.2026 после фазы 5 (#1413). Первое включение модуля даёт работающий клубный JPA-срез и весь Liquibase. Граф проверяется по актуальным сущностям и потребителям, поэтому крупные работы делятся на рабочие PR перед реализацией.

Один Spring Boot JAR, один DataSource, EntityManagerFactory и Liquibase. PostgreSQL в штатном релизе использует текущий том и подключение. Физический перенос PostgreSQL обсуждается отдельной задачей из #1040 и не блокирует фазу.

Административная клубная граница и внутренние чтения независимы по постановке, пересечения фиксируются перед PR. Порядок групп регистрации/оплат и турниров уточняется по JPA-связям, без параллельного перемещения одной entity.

Подготовительная проба Spring Boot на срезе b1ddcca6 дала совпадение идентификаторов и контрольных сумм всех 109 changeset в двух упаковках одного набора из 99 файлов. Она выполнена без БД. Перед включением требуется реальный PostgreSQL-прогон конечного JAR.

### Нефункциональные
Java 17 и один Spring Boot JAR. Каждый backend PR проходит clean verify на собственной PostgreSQL, guards, реальный runtime и затронутый браузер. Независимая клиентская приёмка выполняется в #1447.

## Вне скоупа
Новые схемные и продуктовые изменения, физическая миграция PostgreSQL и Swarm. Работа использует существующее подключение и не требует отдельного окна выкатки БД.

## Изменения в системе

### API
Сохраняются действующие HTTP/WS и клиентские контракты. Web и integration потребители получают нейтральные операции application.

### БД
Liquibase и код хранения получают одного владельца, миграции перемещаются побайтно. Тот же PostgreSQL, classpath, версия Liquibase и история.

### UI
Сохраняются действующие страницы и доступ. Браузерная приёмка #1447 повторяет клубные, турнирные и смежные сценарии.

### Документация
[Фаза 6](../../docs/modular-monolith/phase-6/README.md), архитектурные решения, документация модулей, схемы и выпуска по фактическим изменениям.

## Критерии приёмки
- [ ] JPA, JDBC и Liquibase принадлежат padel-persistence. Application, web и integration-потребители работают через типизированные операции; обратных зависимостей, копий схемы и сущностей нет.
- [ ] Один набор classpath db/changelog с прежними байтами, версиями и ID/AUTHOR/FILENAME/MD5SUM. Новая БД мигрирует, прежняя и повторный старт дают ноль повторов. История сверяется после возврата прежнего JAR.
- [ ] Прежние транзакционные границы, блокировки, rollback, журнал и отправка после commit подтверждены. Независимая клиентская приёмка проходит после всех backend PR.
- [ ] Docker/CI/preview/release и проверки документации используют фактическое новое владение. Каждый PR оставляет приложение работоспособным. Данные production и параметры PostgreSQL сохраняются.

Родитель завершается после независимой приёмки #1447.

## Edge cases
Существующая схема, чистая схема, повторный старт, прежний JAR, JPA flush/lazy и конкурентные записи. Реальные данные production в этих проверках не используются.

## Открытые вопросы
Бизнес-вопросов нет. Последовательность связанных entity-групп уточняется по коду перед их реализацией.
