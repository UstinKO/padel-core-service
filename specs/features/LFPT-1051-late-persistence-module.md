## Требования

### Функциональные

#### Решение владельца и результат
Самостоятельная поздняя задача: выделить padel-persistence (JPA entities/repositories/JDBC-адаптеры/Liquibase) после подготовки портов и графа данных. Выполняется либо в согласованном окне перехода на Swarm (#1040), либо в конце многомодульной миграции #1041. Не входит в первую фазу/пилот.

#### Границы
Под «переездом в новый модуль» здесь понимается Maven-выделение кода хранения и ресурсов. Самостоятельное физическое перемещение PostgreSQL/томов/данных не включено; если оно потребуется в Swarm, создаётся отдельная инфраструктурная задача из #1040. Одно не требует другого.

#### Подготовка и реализация
- До начала: инвентарь entity-связей/потребителей и портов application, никаких циклов persistence ↔ legacy. Зависимости на будущие port-issues уточняются после следующих фаз.
- Перенести подготовленные адаптеры и ресурсы, сохраняя транзакции/ACID, блокировки, dirty checking/flush/lazy semantics, audit/outbox/after-commit.
- Classpath db/changelog/**, id/author/path/checksum существующих changeset сохраняются, Liquibase стартует один раз. Не clearCheckSums/не переписывать старые миграции/не сбрасывать схему.
- Согласованно обновить Maven resource ownership, Docker/CI/release/preview и docs-drift фактическими путями; не выбирать wildcard jar.
- Сначала репетиция новой версии приложения на прежней БД, затем при общем окне отдельное переключение инфраструктуры по runbook #1040. Раздельные SHA/артефакты/точки отката даже при одном окне.
- Зафиксировать cutover-решение и совместимость прежнего артефакта. Если нужна несовместимая схема — отдельная согласованная задача, не скрытая часть переноса.

#### Критерии приёмки
- [ ] Порты/граф данных готовы; ни application, ни controller не импортируют persistence entity/repository.
- [ ] Новая тестовая БД, существующая тестовая схема предыдущего выпуска и повторный старт проходят, прежние changeset не выполняются повторно, данные сохранены.
- [ ] Транзакционный rollback/concurrency и история/outbox проверены, только один Liquibase.
- [ ] Полная verify, итоговый jar/image smoke, UI и release rehearsal/rollback проходят.
- [ ] Физическая PostgreSQL и данные не перемещены без отдельного инфраструктурного решения.
- [ ] Записан выбор окна: Swarm или финальная фаза; доказывающие проверки и откат выполнены.

#### Зависимости
Связано с #1041 и #1040. Реализация заблокирована подготовкой графа/портов поздних фаз и выбором окна; это не обязательный предшественник пилота. Перечень настоящих port-issues дополняется после декомпозиции следующих фаз.


### Нефункциональные




Каждый PR самостоятельно оставляет приложение работоспособным: корневая полная сборка/verify, отдельный PostgreSQL для integration, smoke итогового jar/образа, действующие MVC/API/React/Expo, rollback. Реальные пользовательские БД/уведомления не используются. Java release 17, бизнес-правила и JSON/WS не меняются. Один слой и отдельный PR; без pipeline:ready, автомержа и деплоя в рамках подготовки. Документация — docs/modular-monolith/, спека с настоящим LFPT-номером.

Сохраняются идентичность/checksum/classpath старых changeset и совместимость прежнего jar.

## Вне скоупа

Физический перенос PostgreSQL/томов/данных, новая бизнес-схема, участие в ранней фазе, мерж/деплой.

## Изменения в системе

### API

Внешний HTTP/WS контракт без изменений.

### БД

Новых схемных изменений нет: перемещаются владельцы Java/ресурсов. Старые Liquibase-файлы/пути/identity/checksum сохранены. Новая/предыдущая тестовая схема проверяются отдельно.

### UI

Внешний UI без изменений; browser/API smoke необходим по границе задачи.

### Документация

docs/modular-monolith/phase-1/ и актуальные карта/команды/пути по затронутой области; docs/Home.md, docs/architecture.md и .agents/PROJECT.md при реализации сборочных изменений. Фактическое состояние не подменяется будущими семью модулями.

## Критерии приёмки

Чек-лист конкретного issue выше обязателен полностью. Дополнительно:
- [ ] Результаты привязаны к последнему SHA/артефакту; не выполненные проверки не обозначены успешными.
- [ ] После этого PR приложение работоспособно без будущего PR; неизменность поведения проверена подходящими тестами.
- [ ] docs-drift, релевантные Python suites, diff и локальное ревью пройдены.
- [ ] Документы обновлены в том же PR; для реализации один слой/отдельный PR с Closes #1051.

## Зависимости

Подготовка портов/графа данных последующих фаз; #1041/#1040 — координация, не обязательные предшественники раннего пилота.

## Edge cases

Равная стоимость/порядок перечисления, три приоритета, пустой/нечётный вход, play-in/TBD/backfill, no-show, stale pair/version, чужой клуб, rollback/history/after-commit. Для сборки: CWD тестов, один main/repackage/bean, frontend один раз, модульные отчёты, явный runtime jar, отсутствие shadow-класса. Применимость — по матрице и конкретному изменению; недостижимый из UI вход не получает выдуманную кнопку.

## Открытые вопросы

Конкретное окно (Swarm или конец миграции), готовность/номера задач портов и полный граф данных. Физическая миграция при необходимости ставится отдельно.
