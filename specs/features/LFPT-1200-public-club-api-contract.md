# LFPT-1200: Feature контракт API — подключить generated DTO к публичному чтению клубов

## Статус

approved

## Источник

[Issue #1200](https://github.com/UstinKO/padel-core-service/issues/1200), родитель [#1197](https://github.com/UstinKO/padel-core-service/issues/1197); утверждённая владельцем подготовка второй фазы. Техническая постановка без отдельного клиентского запроса.

## Контекст / зачем

Первый после движка небольшой срез — публичное чтение клубов. Последовательность отделяет проверку генерации, границу application, wire-контракт и независимую приёмку.

## Связь с MASTER.md

Бизнес-правила, роли и публичные данные сохраняются. Новых пользовательских строк, внутреннего HTTP и изменения БД нет.

## Требования

## Цель
После доказанной генерации и выделения read-сценария создать padel-api-contract и заменить HTTP DTO только двух GET /api/public/clubs и /api/public/clubs/{id} без изменения wire-контракта.

## Что сделать
Канонический OpenAPI JSON двух путей и используемых схем — в contract-модуле. Существующий public-discovery.openapi.json и его frontend/CI-потребители должны ссылаться на этот источник либо получать воспроизводимо собранное представление; две независимо редактируемые копии запрещены. Generated Java — Maven generate-sources в target, не Git. MapStruct domain → API — в текущем web-адаптере legacy bootstrap, не в application. Старый PublicClubResponse удалять только после проверки всех потребителей.

## Критерии приёмки
- [ ] Версии и параметры берутся из отчёта пробы; contract не зависит от application/engines/bootstrap/Spring MVC/Data/JPA/HTTP-клиента и не вносит Jackson 2 databind/core.
- [ ] Модели генерируются детерминированно, Java 17, Jackson 3/Jakarta; приложение имеет прежний единственный boot jar.
- [ ] Девять wire-полей Club, null/отсутствие, порядок массива, canonicalUrl и ProblemDetail/fieldErrors/HTTP/headers сохраняются по golden/интеграционным тестам на исходном и новом артефактах.
- [ ] Application не получает зависимость на API DTO; маппинг типизированный MapStruct, enum домена не импортируются contract-модулем.
- [ ] Frontend-проверки контракта и существующие потребители OpenAPI проходят после изменения владения. Прямое чтение старого JSON не ломается; каноничность проверяется автоматически.
- [ ] Корневой verify, packaging ресурсов/frontend, реальный browser smoke и возврат к прежнему jar на тех же данных проходят.

## Границы
Без новых endpoint/полей/прав, генерации серверных интерфейсов/клиентов/TS, массовой замены DTO, переноса каталога или внутренних моделей. Миграций нет.

## Общие гарантии
Java release 17; бизнес-правила MASTER, HTTP/JSON/WS, ES/RU/EN, права и данные сохраняются. Изменений БД/Liquibase и production-переключения UI нет. Один слой и отдельный PR. Каждый реализационный PR самостоятельно сохраняет работоспособность приложения: корневой ./mvnw verify на отдельном PostgreSQL, smoke конечного jar/образа, legacy/API/React/Expo, проверка возврата на предыдущий артефакт. Runtime и доступы не публикуются; pipeline:ready, мерж и деплой подготовкой не разрешаются.

## Изменения в системе

### API
Существующие GET /api/public/clubs и /api/public/clubs/{id}; контракт сохраняется. В задаче технической пробы endpoints не переключаются.

### БД
Без миграций/переноса данных. PostgreSQL и Liquibase принадлежат поздней #1051.

### UI
Без изменения пользовательского интерфейса; потребители — React ClubPages/Catalogue/EventPage и API discovery.ts. Проверки в отдельной #1201.

## Edge cases

Пустой список, неизвестный/неактивный ID, нечисловой ID, nullable поля, порядок nombre/id, отказ БД, base URL с завершающим /, внешние OpenAPI $ref, неподдерживаемый тип генератора, старая вкладка клиента и возврат прежнего jar.

## Открытые вопросы

Бизнес-вопросов нет. Технические решения принимаются по результатам кода/пробы и фиксируются в ADR; совместимость не объявляется заранее.
