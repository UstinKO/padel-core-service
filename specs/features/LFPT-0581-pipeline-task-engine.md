# LFPT-0581: Движок задач Telegram-конвейера — очередь, параллельные роутины, статусы задачи в чате

## Статус
approved

## Источник
[GitHub issue #581](https://github.com/UstinKO/padel-core-service/issues/581). Прямая постановка архитектора. Этап 3 дорожной карты «Автономный конвейер: от Telegram до прода» (локальная `docs/pipeline-autonomy.md`, §4.2–4.3). Зависит от #579 (оркестратор) и #580 (протокол роутины).

## Контекст / зачем
Relay запускал роутину на каждое сообщение мгновенно: без очереди и лимита параллельности, без повтора на `429`, с буфером сборки в памяти, без отслеживания задачи после запуска и без итога «влито на прод» (токен роутины ничего не читает, бот не видит своих сообщений). Пользователь убирает себя из ревью — ему нужен понятный статус задачи в чате от запуска до прода.

## Связь с MASTER.md
Не затрагивает бизнес-логику продукта.

## Требования

### Функциональные
1. Задача = карточка в чате; её `message_id` — номер задачи, `telegram_launch_message_id` и `Pipeline-Task`.
2. Очередь FIFO, `MAX_PARALLEL` (по умолчанию 2) одновременных сессий; слот занят от `/fire`, пока у каждой issue задачи нет живого PR с `pipeline:ready`, либо задача не встала на `pipeline:needs-input` / `pipeline:failed` / `pipeline:conflict`.
3. `/fire`: `429`/`503` — автоповтор по `Retry-After`; прочие ошибки и таймаут — статус «сбой» с кнопкой «Перезапустить».
4. Отслеживание по GitHub раз в минуту (fine-grained PAT только на чтение): поиск `"Pipeline-Task: <N>"`, метки, `Closes #`, мерж, прогоны `Deploy to Production` (по «Deploy PR #N» и merge-коммиту).
5. Статусы: в очереди → в работе → ждёт ответов / проверки пройдены — вливается → влито на прод; конфликт, деплой упал, сбой, нет движения (`STALL_HOURS`, по умолчанию 3 ч), отменена.
6. Уведомления реплаем на карточку: вопросы (комментарий `🤖 pipeline-questions`), «✅ реализована и влита на прод — можно проверять», деплой упал, конфликт после автопочинки, сбой, нет движения.
7. Реплай на сообщение задачи — продолжение (`[продолжение задачи #N]`); пока задача в работе — вторая сессия не запускается; в очереди — текст дописывается.
8. `pipeline:conflict` — один автоматический перезапуск роутины на починку, дальше — человек. После любого перезапуска старые метки (conflict / needs-input / failed) не учитываются, пока в GitHub что-то не изменится.
9. Кнопки: «❌ Отменить» (в очереди), «🔁 Перезапустить», «📋 Очередь» на пульте (с паузой и `pipeline:halt`).
10. Рубильник `/admin/telegram-pipeline` не отбрасывает задачи — держит в очереди. Белый список `user_id` не меняется.
11. Состояние в SQLite, буфер сборки в `state.json` — рестарт ничего не теряет.

### Нефункциональные
- Только стандартная библиотека Python (как relay). Код — `scripts/telegram-relay/` (вне git, прод-сервер), тесты без сети.
- Токен GitHub — только чтение; роутину запускает только движок (у роутины один токен).

## Критерии приёмки
- [ ] Три задачи подряд при `MAX_PARALLEL=2`: две запускаются, третья ждёт и стартует после освобождения слота.
- [ ] `429` → задача остаётся в очереди и запускается после `Retry-After` без участия человека.
- [ ] Рестарт relay не теряет очередь и активные задачи.
- [ ] Карточка проходит статусы до «влито на прод»; итоговое сообщение — реплаем на карточку.
- [ ] Ответ реплаем на вопросы запускает продолжение той же задачи.
- [ ] Отмена задачи в очереди и перезапуск упавшей работают кнопками.

## Edge cases
- Задача «бэк + фронт»: бэк-PR уже `ready`, фронт-issue без PR — слот занят (роутина ещё работает).
- PR только в `specs/.claude/docs` — «влито» без деплоя.
- Ссылка на картинку Telegram живёт ~час — при долгой очереди роутина картинку не скачает.
