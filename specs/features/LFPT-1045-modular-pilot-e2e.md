# LFPT-1045: Feature пилот многомодульного монолита — подготовить и выполнить сквозную приёмку

## Статус

approved

Пилот PlayoffMatchingEngine и семь модулей подтверждены владельцем. Задача теперь финальная приёмка после #1050; исходная проверка вынесена в #1048. Прогоны этой задачи ещё не выполнялись.

## Источник

[Issue #1045](https://github.com/UstinKO/padel-core-service/issues/1045), прямое уточнение владельца в [LFPT-1041](LFPT-1041-modular-monolith-analysis.md). Техническая постановка из issue, отдельный клиентский запрос не требуется.

## Контекст / зачем

Малый пилот должен показать работу модулей на реальном приложении до расширения переноса. Нужны воспроизводимая исходная проверка и повтор после, включая отдельные ручные нажатия кнопок. Дата последней правки — только один критерий выбора; стабильность подтверждается проверками.

## Связь с MASTER.md

Все правила квалификации, посева/приоритетов, результатов, истории и доступа по клубу сохраняются. Ошибку исходного поведения относительно MASTER оформить отдельно; новые бизнес-правила не вводятся.

## Требования

### Функциональные

- После подтверждения пилота дополнить [матрицу](../../docs/modular-monolith/pilot-and-e2e.md): каждый достижимый сценарий, маршрут, кнопка, роль, fixture и ожидаемое поведение.
- Получить исходный скриптовый/Playwright и отдельный ручной отчёт #1048 на фиксированном SHA до переключения пилота.
- После переноса повторить те же кейсы и проверить откат итогового jar/образа на прежней схеме/данных тестового контура.
- Приложить результаты backend unit/integration/verify из отдельной backend-задачи; production Java и UI здесь не менять.
- Сохранить по каждому кейсу SHA/артефакт, команды/нажатия, результат, безопасные доказательства, дефекты и повторный прогон.

### Нефункциональные

Синтетические данные, изолированный preview, без production/секретов/реальных уведомлений. Поведение API/HTML/WS и ES/RU/EN прежнее. Новые строки продукта не добавляются. Браузерная автоматизация не заменяет отдельный ручной проход.

## Вне скоупа

Backend-рефакторинг и перенос движка, production UI, новые правила/переводы, Swarm, физическая БД, перенос persistence/Liquibase. Эти работы отдельными задачами. Исходная задача #1048 закрывается до #1049/#1050, текущая #1045 выполняется только после #1050; циклической зависимости нет.

## Изменения в системе

### API

Нет production-изменений; скрипты вызывают существующие маршруты с действующей авторизацией/CSRF.

### БД

Нет миграций. Fixture создаётся только в собственной тестовой среде; пользовательские БД не используются.

### UI

Нет production-изменений. Playwright и ручная проверка действующего Team Playoff. Точные кнопки/пути фиксируются при подготовке.

### Документация

Матрица/отчёты в `docs/modular-monolith/`, ссылки из README/plan и backend-пилота. Уточнить инструкции запуска тестовых скриптов без публикации credentials.

## Критерии приёмки

- [ ] Матрица покрывает фактический пилот; unit-only случаи отмечены явно, недоступные кнопки не придуманы.
- [ ] Исходные скрипты/Playwright и отдельный ручной проход выполнены до переноса, SHA/результаты сохранены.
- [ ] После переноса та же матрица пройдена автоматически и вручную на итоговом артефакте.
- [ ] Полный синтетический турнир, повторные действия, серверный доступ клуба, сохранение/перезапуск и общий smoke проверены.
- [ ] Есть результаты backend unit/integration/verify, включая транзакционные проверки затронутого пути.
- [ ] Откат проверен, блокирующие регрессии устранены; ошибки/повторные проверки и ограничения отражены честно.
- [ ] Документы, ссылки, docs-drift/агентские проверки и diff проверены; production-данные/секреты отсутствуют.

## Edge cases

Пустой/нечётный вход, неизбежный реванш, равные критерии, три приоритета, повтор действия, две сессии/клиента, чужой клуб, ошибка записи, restart/rollback. Конкретные ожидания — по существующему коду/спекам, не новый бизнес-дизайн. Все unit-ветви не обязаны иметь браузерный эквивалент.

## Открытые вопросы

Неразрешённых бизнес-вопросов нет. Исходные fixtures и ожидания поставляют #1047/#1048; итоговая задача зависит от #1050. Матрица TC01–TC25 в docs/modular-monolith/phase-1/test-cases.md дополняется по фактическим исходным результатам.

## Зависимости и конкретный пул

Зависит от #1050; транзитивно #1047 → #1048 → #1049 → #1050 → #1045. Первую исходную приёмку выполняет #1048, текущая задача не дублирует её implementation. Итоговый runtime jar: padel-bootstrap/target/padel-core-service-0.0.1-SNAPSHOT.jar, immutable release/evidence — по фактическим инструкциям #1049.

## Принятый остаток ручной приёмки из #1048

13.11.2026 владелец принял для исходной #1048 ручные турниры 8/9 пар и полную автоматизированную матрицу. Это не утверждение о ручном выполнении всех кейсов. [Фактический журнал](../../docs/modular-monolith/phase-1/manual-baseline.md) сохраняет NOT_RUN для остальных ручных пунктов.

После #1050 повторить вручную весь M01–M09: в том числе 16 пар, раннюю сетку/TBD/backfill, NO_SHOW, stale/repeated действия, доступ другого клуба/анонима/CSRF, два зрителя/WS, историю/restore, restart/rollback и общий smoke. Отдельно выполнить и описать ручные технические HTTP/WS-пункты; не переносить сюда PASS из автоматизации. M01/M02 тоже повторяются на итоговом артефакте. Снятие ограничения исходной #1048 не ослабляет итоговые критерии этой задачи.
