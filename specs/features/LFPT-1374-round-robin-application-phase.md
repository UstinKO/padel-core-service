# LFPT-1374: Feature многомодульный монолит, фаза 4 — выделить чтение круговой таблицы в application

## Статус
approved

## Источник

[Issue #1374](https://github.com/UstinKO/padel-core-service/issues/1374), родитель #1041; поручение владельца подготовить следующую фазу после мержа PR #1372. Это координация дочерних задач, без реализации приложения в подготовке.

## Контекст / зачем

В engines выделены девять вычислительных классов, в application — только публичное чтение клубов. Следующий вертикальный read-срез — круговая таблица Team Americano. Остаток finalOrder отделяется как явная подготовка к application, а не повод продолжать произвольные мелкие переносы.

## Связь с MASTER.md

Круговой парный турнир, история, роли и границы доменов сохраняются. Меняется размещение ответственности, не продуктовые правила.

## Требования

### Функциональные

- Последовательность: #1375 baseline/граф → #1376 final-order engine → #1377 application read-сценарий → #1378 независимая приёмка.
- Нейтральные read-модели и порт принадлежат application, чистые вычисления engines; JPA/legacy DTO адаптируются MapStruct в bootstrap до будущих persistence/web.
- initialize и finish сохраняют композицию результата внутри прежней write-транзакции. Внешний query readOnly, propagation REQUIRED; не менять flush/isolation/историю.
- Точечно разрешить фактические engine-типы в ArchUnit/artifact guard, сохранив запрет остальных legacy-классов того же package.
- Переключить всех callers старой композиции и удалить дубликат, учесть оставшиеся адресные мосты и позднюю #1051.

### Нефункциональные

Один backend/frontend PR на каждую дочернюю задачу, Java 17, один boot jar, работоспособность после каждого PR. Сроки релиза не назначены.

## Вне скоупа

Write-сценарии/валидация/начисление, массовый перенос сервисов, generated ranking DTO, UI-переключение, физическая БД/Swarm и выделение persistence.

## Изменения в системе

### API

Существующие DTO/HTTP/MVC/WS сохраняются; переносится их внутренний источник результата.

### БД

Без миграций; порт реализует legacy JPA-адаптер в bootstrap, транзакционная семантика сохраняется.

### UI

Без нового UI. Отдельная #1378 проверяет действующих потребителей.

### Документация

[План](../../docs/modular-monolith/phase-4/README.md), [анализ](../../docs/modular-monolith/phase-4/code-analysis.md), план/навигация миграции, архитектура и PROJECT. Спецификации каждой дочерней задачи подготовлены отдельно.

## Критерии приёмки

- [ ] #1375/#1376/#1377/#1378 включены отдельными PR в порядке зависимостей, каждая прошла собственные проверки.
- [ ] В application один владелец read-композиции, собственные модели/порт; чистые вычисления без копий в legacy.
- [ ] Контракты initialize/getRanking/getTeams/finish и права/история/транзакции совпали с baseline.
- [ ] Guards запрещают JPA/DTO/остальной legacy и сохраняют единственное владение классами.
- [ ] Финальный артефакт прошёл независимые browser/runtime/возврат-проверки; остаток/мосты и ограничения зафиксированы.

## Edge cases

См. дочерние спеки: null/guest/fallback, частичные и завершённые стадии, общие места SETS, дополнительные встречи и joined write-read. Полный граф write-доменов не объявляется завершённым этой read-фазой.

## Открытые вопросы

Бизнес-вопросов нет. Конкретные модели/порт, wiring и joined write-read описаны по baseline #1375: [application-контракт](../../docs/modular-monolith/phase-4/application-contract.md). Зависимости задач сохраняются; фактический API final-order engine сверить после #1376 до включения в allowlist. Код application-среза в #1375 не переносится.
