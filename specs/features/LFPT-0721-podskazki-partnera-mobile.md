# LFPT-0721: Подсказки партнёра во всех полях формы «Новый партнёр» в 1Padel.App

## Статус
approved

## Источник
GitHub issue [#721](https://github.com/UstinKO/padel-core-service/issues/721), прямая техническая постановка архитектора — этап 1 крупного клиентского ТЗ [#713](https://github.com/UstinKO/padel-core-service/issues/713) (`specs/features/LFPT-0713-poisk-partnera-otmena-americano-usloviya.md`). Зависит от [#720](https://github.com/UstinKO/padel-core-service/issues/720) (бэкенд: нормализованная защита от дублей), ветка создана от `feature/LFPT-0720`. Pipeline-Task: 5485.

## Контекст / зачем

На сайте подсказки существующего игрока при ручном вводе партнёра (имя/фамилия/телефон/Telegram, во всех четырёх полях) уже реализованы (LFPT-0679/0680/0700/0703). В клиенте 1Padel.App (`mobile-app/`, экран `PairBookingScreen.tsx`, вкладка «новый партнёр», LFPT-0707) таких подсказок нет вообще — четыре поля (имя/фамилия/WhatsApp/Telegram) обычные `TextInput` без живого поиска; поиск существующего игрока есть только на отдельной вкладке «Есть партнёр» (`booking.searchPartners`). Заказчик явно просит подсказки «в форме «Новый партнёр» … (веб и 1Padel.App)» — веб-часть уже закрыта, остаётся мобильный клиент.

Отдельно: и на сайте, и в приложении при сбое самого запроса подсказок (`GET /api/players/search` вернул сетевую/серверную ошибку) UI тихо показывал то же самое, что и при пустом результате — заказчик прямо просит не путать эти два случая («При ошибке проверки показывать сообщение об ошибке, а не «Совпадений нет»»).

## Связь с MASTER.md

Не меняет инвариантов и флоу парной регистрации (`specs/MASTER.md` § «Флоу парной регистрации») — при выборе существующего игрока из подсказки используется тот же механизм, что и выбор из вкладки «Есть партнёр» (`existingUserId` в `PartnerPayload`), новая регистрация не создаётся.

## Требования

### Функциональные

1. **Подсказки во всех четырёх полях** вкладки «новый партнёр» (`PairBookingScreen.tsx`): имя, фамилия, WhatsApp, Telegram — независимый поиск по каждому полю через существующий `booking.searchPartners(tournamentId, query)` (тот же API, что уже использует вкладка «Есть партнёр»), debounce 400мс, минимум 2 символа для имени/фамилии/Telegram, минимум 4 цифры для WhatsApp (как на сайте, LFPT-0680).
2. **Объединение результатов** по `id` без дублей (как на сайте, `renderManualSuggestions`).
3. **Отображение**: компактный блок под полями с заголовком (новый ключ `newPartnerSuggestionsTitle`) и списком найденных — имя и фамилия (`nombreCompleto`), без email/телефона (`PartnerCandidate` и так не содержит контактов — приватность соблюдена структурой типа, LFPT-0679/0680).
4. **Выбор подсказки** — заполняет `selected` (тот же механизм, что при выборе из вкладки «Есть партнёр»: `partnerPayload()` отдаёт приоритет `selected`), очищает поля нового партнёра (имя/фамилия/WhatsApp/Telegram) и список подсказок. Выбранный партнёр показывается карточкой (имя + кнопка сброса `✕`) над вкладками — независимо от того, была ли вкладка «Есть партнёр» или «новый партнёр».
5. **Различение ошибки поиска от пустого результата** (п.6 ТЗ #713): если сам запрос `/api/players/search` завершился сетевой/серверной ошибкой — показать `t.searchError`, а не молчаливо скрыть блок/показать «нет совпадений». Применяется и к новому блоку подсказок, и к уже существующей вкладке «Есть партнёр» (`candidates`/`query`), и — для согласованности сайта и приложения (п.9 ТЗ #713) — к веб-версии (`tournament-details.js`: верхний поиск и подсказки ручного ввода; `dashboard.js`: верхний поиск), которые до этой задачи так же тихо проглатывали ошибку запроса.
6. **Не трогать** режимы «Ищу партнёра на месте» / «Добавлю партнёра позже», вкладку «Есть партнёр», добавление партнёра к уже существующей соло-заявке (`addingPartner`, только поиск существующего, без вкладки «новый партнёр» — не меняется).

### Нефункциональные

- **i18n**: новые ключи `searchError`, `newPartnerSuggestionsTitle` — `mobile-app/src/pairCopy.ts` (ru/es/en), и `details.search.error` — `src/main/resources/static/js/i18n/messages-{es,ru,en}.js` (веб).
- **Debounce и минимальная длина** — как на сайте, чтобы не дёргать `/api/players/search` на каждое нажатие (бэкенд уже защищён общим лимитом `/api/**`, LFPT-0679).
- **Безопасность**: новых точек входа данных нет — переиспользуется существующий авторизованный эндпоинт и существующий паттерн подстановки существующего игрока по ID.

## Вне скоупа

- Любые изменения `PlayerRepository`/`PlayerService`/`GET /api/players/search` — сделаны в #720, здесь не трогаются.
- Тестовый режим для пары (`/?screen=pair-booking-test`) — не создаётся (не запрошен, см. LFPT-0707 «Вне скоупа»).
- Добавление уровня (`nivelJugador`) в отображение подсказок на мобильном — на сайте показывается, но `PartnerCandidate` (мобильный тип) его не парсит; верхняя вкладка «Есть партнёр» тоже не показывает уровень — не расширяем формат одной только новой вкладки ради консистентности с сайтом, когда остальной экран его не показывает.
- Серверная защита от дублей при создании партнёра — #720, не часть этой задачи (но её эффект уже снижает шанс создания дубля даже без клика по подсказке).

## Критерии приёмки

- [ ] Ввод имени/фамилии/WhatsApp/Telegram (≥2 символов, ≥4 цифр для телефона) во вкладке «новый партнёр» показывает подсказки существующих игроков.

## Edge cases

- Пользователь вводит в несколько полей подряд быстро — debounce 400мс на каждое поле отдельно гасит промежуточные запросы (как на сайте).
- Выбор подсказки, затем очистка/повторный ввод в поля нового партнёра — `selected` остаётся, пока явно не сброшен крестиком; `partnerPayload()` продолжает отдавать приоритет `selected` (как и раньше для вкладки «Есть партнёр»), поэтому ввод в очищенные поля без сброса `selected` не создаёт новый payload из этих полей.
- Переключение вкладок/режимов (`resetChoices`) — подсказки и их ошибка полностью очищаются, как и остальные поля формы.
- Два совпадения с одинаковым именем — оба показываются в списке подсказок (различаются по `id`/карточке).
