# LFPT-0668: Feature доработка «Добавлю партнёра позже» — точный дедлайн, перевод в резерв и email-напоминания

## Статус
approved

## Источник
Клиентский запрос заказчика (Telegram): [specs/requests/LFPT-0668-dobles-agregar-pareja-luego.md](../requests/LFPT-0668-dobles-agregar-pareja-luego.md). Issue: #668.

Фронтенд-часть (отображение в админке, страницы подтверждения действий из email) — отдельная задача [LFPT-0669](LFPT-0669-dobles-agregar-pareja-luego-frontend.md) (issue #669), ветка от этой.

## Контекст / зачем

Игрок, регистрируясь на парный турнир, может выбрать «Добавлю партнёра позже» (`RegistrationStatus.SOLO_ADD_LATER`, см. `DoubleTournamentRegistrationService.registerSoloForDoubleTournament`). Сейчас фоновая проверка (`SoloRegistrationSchedulerService.expireIncompleteRegistrations`) сравнивает только календарную дату (`LocalDate.now().plusDays(1)`), не время старта турнира, и по истечении срока переводит заявку в терминальный статус `SOLO_EXPIRED` — без партнёра дальше ничего сделать нельзя, слот из общей очереди резерва выпадает навсегда. Заказчик хочет: точный дедлайн (старт − 24ч), не терять заявку (перевод в резерв вместо тупика), письма в момент перевода и за 3 часа, возможность вернуться в основной состав с учётом очереди резерва, self-service действия по ссылке из письма.

## Связь с MASTER.md

Расширяет раздел [Статусы регистрации на турнир](../MASTER.md#статусы-регистрации-на-турнир) — не меняет сам список статусов и не противоречит инвариантам, но меняет **путь** `SOLO_ADD_LATER` → `WAITLIST` (резерв) вместо `SOLO_ADD_LATER` → `SOLO_EXPIRED` (тупик). `SOLO_EXPIRED` больше не назначается новым кодом (статус остаётся в enum ради уже существующих исторических записей и не ломает старые данные — см. «Вне скоупа»). Не противоречит бизнес-правилу листа ожидания (MASTER.md: «следующий игрок из WAITLIST получает WAITLIST_INVITED») — для парных турниров место занимает уже существующий `processWaitlistForTournament`/`autoConfirmFromWaitlist` (прямое авто-подтверждение без отдельного шага 5-минутного инвайта), который эта фича переиспользует как есть, лишь исключая из выборки неполные (без партнёра) резервные заявки.

## Требования

### Функциональные

1. **Точный дедлайн.** `partnerDeadline = tournament.calculateDefaultDeadline()` (уже существует в `Tournament.java`, считает `fechaInicio+horaInicio − 24ч`, LFPT-0662) — единая точка правды, без отдельного сохранённого поля (значит пересчёт при изменении даты/времени турнира происходит сам собой, см. Edge cases).

2. **Перевод в резерв вместо `SOLO_EXPIRED`.** Новый/переписанный scheduled-метод в `SoloRegistrationSchedulerService` (заменяет `expireIncompleteRegistrations`): каждые 5 минут выбирает активные `SOLO_ADD_LATER`-регистрации, у которых `tournament.calculateDefaultDeadline().isBefore(now)`, и переводит их в `WAITLIST`:
   - `registration.moveToWaitlist(waitlistPosition)` — переиспользовать существующий метод entity (`position=null`, инвайт-поля очищаются), `waitlistPosition = registrationRepository.findMaxWaitlistPosition(tournamentId).orElse(0) + 1`.
   - `partner`/`isDoubleRegistration` не трогать — остаются `null`/`false`, это и есть признак «ожидает партнёра» (в отличие от обычной полной пары в `WAITLIST`, у которой `partner != null`).
   - Сгенерировать `partnerActionToken` (новое поле, см. «БД») и отправить письмо "перевели в резерв" (кнопка «Agregar compañero» → `{baseUrl}/torneo/{tournamentId}`, в этот момент никакой токен для самой кнопки добавления партнёра не нужен — игрок уже залогинен как владелец аккаунта; токен нужен только для двух новых self-service-ссылок, см. п.6).
   - Правило работает независимо от заполненности турнира (не проверять `cupoMax` перед переводом — перевод не зависит от наличия свободных мест).
   - Не двойной перевод: после первого перевода статус уже не `SOLO_ADD_LATER`, повторная выборка метода его не находит — естественная защита, доп. флаг не нужен.

3. **Если регистрация создаётся уже после дедлайна** (`tournament.calculateDefaultDeadline().isBefore(now)` в момент самого `registerSoloForDoubleTournament` с `dto.getSoloType()=ADD_LATER`) — создавать регистрацию сразу в `WAITLIST` (с `waitlistPosition`, `partnerActionToken`), минуя `SOLO_ADD_LATER`, и в этом же вызове синхронно отправить то же письмо "перевели в резерв" (не ждать следующий тик планировщика).

4. **Письмо "перевели в резерв"** (новый шаблон `templates/email/partner-deadline-reserve.html`, пример текста — в клиентском запросе, п.4): тема/текст про «инскрипсьон traslada a la lista de reserva», одна кнопка «Agregar compañero» → `{baseUrl}/torneo/{tournamentId}`. Данные: имя клуба, дата/время турнира (как в `partner-data-reminder.html`/`PartnerDataReminder`).

5. **Повторное напоминание за 3 часа** — новый scheduled-метод (каждые 5 минут), окно `[start − 3ч15мин, start − 2ч45мин)` вокруг точного `start.minusHours(3)` (аналог окна в существующем 48h-напоминании, но на минутах, а не на сутках — точность важна именно здесь по условию задачи). Кандидаты: `status = WAITLIST`, `partner IS NULL`, `isActive = true`, `finalReminderSent = false` (новое поле), турнир `DOBLES`. Письмо `templates/email/partner-final-reminder.html` — кнопки «Agregar compañero» (→ `{baseUrl}/torneo/{tournamentId}`), «Confirmar inscripción» (→ `{baseUrl}/reserva/accion/confirmar?token={partnerActionToken}`) и «No puedo participar» (→ `{baseUrl}/reserva/accion/cancelar?token={partnerActionToken}`, см. п.6). После отправки — `finalReminderSent = true`.
   - Третья кнопка «Confirmar inscripción» — в клиентском запросе явно упомянута в общем списке действий (п.8 запроса: «подтвердить актуальность заявки»), но не показана в примере текста письма из п.5 запроса. Решение разработчика (техническая деталь, не бизнес-правило): добавить её сюда третьей кнопкой — на 24-часовое письмо (п.4) не добавлять, там актуальность подтверждать рано, достаточно одной кнопки «Agregar compañero».

6. **Self-service действия по токену** (без логина, по аналогии с `waitlistConfirmationToken`/`/waitlist/confirm`):
   - `GET /reserva/accion/confirmar?token=X` — находит регистрацию по `partnerActionToken`, проверяет что она ещё `WAITLIST`+`partner IS NULL`+`isActive`; действие **без изменения состояния** — просто фиксирует факт отклика (ничего в заявке не меняет, в т.ч. не отправляет повторных писем) и отдаёт страницу-подтверждение (шаблон — фронт-задача #669). Решение разработчика: заказчик не описал, что технически должно произойти при «подтверждении актуальности» кроме самого факта ответа — реализовать как no-op-подтверждение (идемпотентно), без придумывания скрытой бизнес-логики.
   - `GET /reserva/accion/cancelar?token=X` — страница подтверждения отмены (фронт #669, без немедленной отмены по одному клику — требование запроса "подтвердить отмену на сайте").
   - `POST /reserva/accion/cancelar` (`token`) — находит регистрацию по токену, если она ещё активна и в резерве без партнёра — отменяет (`registration.cancel(reason)`, `reason = "No puede participar (desde email)"`), переиспользовать существующую логику отмены парной регистрации, см. `PlayerDashboardController.cancelDoubleRegistration` / сервис, который она вызывает — не дублировать бизнес-правила отмены, вызвать тот же сервисный метод (если сигнатура требует `PlayerPadel`/аутентифицированного игрока — завести отдельный публичный метод в том же сервисе, принимающий `TournamentRegistration` напрямую, без дублирования самой логики отмены).
   - Оба роута — новый контроллер (например `ReserveActionController` в `controller/`, backend-пакет) или метод в существующем `PartnerRegistrationController` (он уже отвечает за публичные redirect-действия по токену для парной регистрации) — на усмотрение разработчика, любой вариант не противоречит пакетной структуре `CLAUDE.md`.
   - Истечение токена не требуется — токен действителен, пока заявка в допустимом для действия состоянии (аналогично тому, что `waitlistConfirmationToken` не имеет отдельного TTL, годность определяется состоянием заявки).

7. **Возврат в основной состав после добавления партнёра** (происходит в `DoubleTournamentRegistrationService.addPartnerToSoloRegistration` и в `confirmPartnerRegistration`):
   - Текущая проверка в `addPartnerToSoloRegistration` (`soloReg.getStatus() != RegistrationStatus.SOLO_ADD_LATER` → ошибка) должна **также** принимать `status == WAITLIST && partner == null && !isDoubleRegistration` (резервная заявка без партнёра) — иначе после перевода в резерв добавить партнёра станет невозможно.
   - Ветка **до дедлайна** (`status == SOLO_ADD_LATER`) — поведение не меняется (слот уже учтён при регистрации, партнёр с аккаунтом → сразу `CONFIRMED`, без аккаунта → `PARTNER_INVITED`).
   - Ветка **после перевода в резерв** (`status == WAITLIST`), партнёр найден (аккаунт существует): **не подтверждать сразу** — выставить оба ряда (основной + партнёр) в `WAITLIST` с `waitlistPosition = registrationRepository.findMaxWaitlistPosition(tournamentId).orElse(0) + 1` (т.е. в конец очереди резерва — независимо от прежней позиции неполной заявки, ровно требование заказчика «не получать преимущество перед полноценными парами»), сохранить, затем вызвать `TournamentService.processWaitlistForTournament(tournamentId)` (пакетно-видимый `protected`-метод — вызов из `DoubleTournamentRegistrationService`, тот же пакет `service`, легален без изменения модификатора доступа). Этот существующий метод сам решит: если место свободно и очередь дошла — подтвердит (сценарий А из запроса), если места нет или уже есть пары перед ней — оставит в резерве (сценарии Б/В).
   - Партнёр без аккаунта (ветка приглашения по email) — выставляется `PARTNER_INVITED` как обычно; при подтверждении по токену (`confirmPartnerRegistration`) — см. следующий пункт, тот же метод обслуживает оба происхождения (обычная парная регистрация и резервная) одинаково, он и сейчас не различает их.
   - **Правка `confirmPartnerRegistration`**: сейчас при `availableSpots > 0` метод *всегда* ставит `CONFIRMED` немедленно, не проверяя, есть ли в резерве уже сформированные пары, ожидающие места раньше — это и есть пробел сценария В из запроса («незавершённая заявка не должна получать преимущество перед уже готовыми парами»), причём не только для резервного пути, а и для обычной регистрации нового партнёра по инвайту (тот же метод обслуживает оба случая). Исправление: в обеих ветках (`availableSpots > 0` и `<= 0`) всегда ставить `WAITLIST` с `waitlistPosition = findMaxWaitlistPosition(...)+1` (т.е. в конец очереди), затем вызывать `processWaitlistForTournament(tournamentId)` — он подтвердит немедленно, если место свободно и очередь дошла, иначе оставит в резерве. Это небольшое, но осознанное изменение существующего метода (не только резервного пути) — обосновано тем же инвариантом справедливой очереди, что и просит заказчик; коротко отразить в commit message.

8. **Админ-панель** — различение «ожидает партнёра» (`WAITLIST` + `partner == null`) и «пара сформирована» (`WAITLIST` + `partner != null`) для резервных заявок — реализует фронт-задача #669 на основе того, что эта фича уже делает технически доступным (никаких новых полей для самого различения не нужно).

9. **Доп. правила по письмам:**
   - Не слать 24ч/3ч письма, если партнёр уже добавлен (`partner != null`) или регистрация отменена (`!isActive`/`status == CANCELLED`) — фильтруется прямо в выборке кандидатов (`status = WAITLIST/SOLO_ADD_LATER` уже исключает оба случая).
   - Не слать повторно одинаковые письма — 24ч-письмо отправляется один раз в момент самого перевода (событие, не поллинг), 3ч-письмо — защищено `finalReminderSent`.
   - Пересчёт дедлайна при изменении даты/времени турнира — автоматический, так как дедлайн не хранится (п.1).

10. **i18n.** Все новые пользовательские строки (оба письма, страницы confirm/cancelar из фронт-задачи) — в `messages_{es,ru,en}.properties`, по конвенции существующих писем (см. `# --- partner-data-reminder.html ---` в файлах i18n).

### Нефункциональные
- Производительность: оба новых scheduled-метода — по аналогии с существующими в `SoloRegistrationSchedulerService`, объём данных на одну итерацию мал (активные `SOLO_ADD_LATER`/резервные заявки одного турнира), фильтрация точного времени — в Java (`Stream`), не в JPQL (сравнение `LocalDate`/`LocalTime` из разных колонок в JPQL избыточно сложно и негибко для точности в минутах) — выбрать все активные кандидаты статусом, отфильтровать по `tournament.calculateDefaultDeadline()`/`start.minusHours(3)` в сервисе.
- i18n — см. п.10 выше.
- Безопасность: новые публичные GET/POST-эндпоинты принимают только `token` (непредсказуемый, генерируется как и другие токены проекта — `UUID`-based, см. `generatePartnerToken()`); отмена по токену — только если заявка ещё в допустимом состоянии, повторный вызов безопасен (идемпотентно для уже отменённой — не бросает 500, см. Edge cases).

## Вне скоупа
- `SOLO_SEARCH` (вариант «ищу пару на месте») — этот флоу не трогаем, дедлайн/резерв/напоминания только для `SOLO_ADD_LATER`.
- Удаление/переименование статуса `SOLO_EXPIRED` из enum и миграция существующих исторических записей с этим статусом — не трогаем, новый код его больше не назначает, но старые записи остаются как есть (не ломаем историю).
- Telegram-бот/мини-приложение/WhatsApp для тех же действий (п.8 запроса явно оставляет это на будущее) — только сайт.
- Интеграция "подтвердить актуальность" с каким-либо автоматическим действием сверх фиксации отклика — заказчик не описал, что сверх этого должно произойти (см. п.6).

## Критерии приёмки
- [ ] Турнир старт воскресенье 15:00 → `calculateDefaultDeadline()` возвращает субботу 15:00 (точное время, не календарную дату).
- [ ] `SOLO_ADD_LATER`-регистрация, дедлайн ещё не наступил → статус не меняется, письма не шлются.
- [ ] Дедлайн наступил (now ≥ deadline) → статус переходит в `WAITLIST`, `partner`/`isDoubleRegistration` остаются пустыми, `waitlistPosition` выставлен в конец очереди, слот в основном составе освобождён (другая пара из листа ожидания может его занять через обычный `processWaitlistForTournament`).
- [ ] В момент перехода отправлено письмо `partner-deadline-reserve` с кнопкой добавления партнёра.
- [ ] Регистрация `SOLO_ADD_LATER` создаётся, когда до старта уже меньше 24ч → сразу создаётся в `WAITLIST` (не временно в основном составе), письмо отправлено синхронно.
- [ ] За 3 часа до старта, партнёр так и не добавлен — отправлено письмо `partner-final-reminder` с тремя кнопками (добавить партнёра / подтвердить / не смогу); повторный тик планировщика не шлёт письмо дважды (`finalReminderSent`).
- [ ] Партнёр добавлен (существующий аккаунт) после перевода в резерв, свободное место есть и очередь пуста — пара переходит в `CONFIRMED` автоматически (сценарий А).
- [ ] Свободных мест нет — пара остаётся в `WAITLIST`, уже с `partner != null` (сценарий Б).
- [ ] В резерве уже есть другая полностью сформированная пара с более ранней позицией — вновь сформированная пара не подтверждается впереди неё, встаёт в конец очереди готовых пар (сценарий В).
- [ ] `GET /reserva/accion/cancelar?token=X` с валидным токеном резервной (без партнёра) заявки → страница подтверждения, сама заявка не отменена.
- [ ] `POST /reserva/accion/cancelar` с тем же токеном → заявка `CANCELLED`, `isActive=false`, место окончательно свободно; повторный `POST` с тем же токеном — не 500, корректно отрабатывает отмену уже отменённой заявки (без изменения состояния повторно).
- [ ] `GET /reserva/accion/confirmar?token=X` — не меняет состояние заявки, отдаёт страницу подтверждения.
- [ ] Партнёр уже добавлен до истечения 3-часового окна → письмо `partner-final-reminder` не отправляется.
- [ ] Регистрация отменена до 24ч/3ч-проверки → ни одно из новых писем не отправляется.
- [ ] Изменение даты/времени турнира после перевода заявки в резерв, но до истечения нового дедлайна — пересчёт происходит сам собой (дедлайн не хранится), 3-часовое окно считается от нового времени.
- [ ] Все новые строки — в `messages_es/ru/en.properties`; страница под `Accept-Language: ru` не показывает испанский текст.
- [ ] `python3 .github/bin/docs-drift.py` — 0 расхождений; `docs/endpoints/double-registration.md`, `docs/database-architecture.md`, `.claude/CLAUDE.md` обновлены.

## Edge cases
- Турнир `INDIVIDUAL` (не `DOBLES`) — вся эта логика не применяется (`SOLO_ADD_LATER` существует только для `DOBLES`, уже так в текущем коде — `registerSoloForDoubleTournament` отдельно проверяет `Modalidad.DOBLES`).
- Токен `partnerActionToken` переиспользуется в обоих новых письмах (не генерируется заново для второго) — ссылка из первого письма остаётся рабочей и после отправки второго.
- `POST /reserva/accion/cancelar` с несуществующим/уже использованным токеном для уже `CANCELLED`-заявки — не 500, человеко-читаемая страница/ответ ("уже отменено" или аналог), не кидать `TournamentRegistrationException` как 500.
- Партнёр добавлен **ровно** в момент тика 3-часового планировщика (race) — `finalReminderSent`/фильтр `partner IS NULL` защищают от отправки письма уже ненужной заявке, но если оба события случились почти одновременно — письмо может уйти с небольшой задержкой до следующего обновления партнёра; не страшно для акцептанса, явно упомянуть в отчёте тестировщика, если воспроизведено.
- Удаление турнира/отмена турнира целиком, пока заявка в резерве без партнёра — вне скоупа (уже покрывается существующей логикой отмены турнира, если она есть; не добавлять новую).

## Открытые вопросы
Нет — все пункты клиентского запроса покрыты выше; решения по техническим деталям, оставленным на усмотрение реализующего (третья кнопка в 3-часовом письме, no-op для "подтвердить актуальность", исправление `confirmPartnerRegistration` для общей справедливости очереди), приняты и обоснованы в соответствующих пунктах "Требования" — см. `GIT_WORKFLOW.md §3`.
