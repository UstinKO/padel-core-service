# LFPT-0561: Feature поиск и создание игрока в форме «Agregar equipo» Team Playoff — без ID, видимость в оплатах (backend)

## Статус
approved

## Источник
Клиентский запрос [specs/requests/LFPT-0561-manual-team-add-search.md](../requests/LFPT-0561-manual-team-add-search.md) (Telegram, пересланное сообщение от Evgeny_754, `telegram_launch_message_id: 5060`). GitHub issue [#561](https://github.com/UstinKO/padel-core-service/issues/561).

Разбито на бэкенд/фронтенд (`GIT_WORKFLOW.md §1.4`) — эта спека покрывает бэкенд. Зависимая фронтенд-задача — [#562](https://github.com/UstinKO/padel-core-service/issues/562) (поиск в UI формы «Agregar equipo»), спека [LFPT-0562-manual-team-add-search-frontend.md](LFPT-0562-manual-team-add-search-frontend.md).

## Контекст / зачем

Единственное место в проекте, где координатор добавляет команду в парный турнир вручную, по ID — форма «Agregar equipo» на странице `/tournaments/team-playoff/admin/{tournamentId}` (`TeamPlayoffViewController.addTeam` → `TeamPlayoffService.addTeam`, `TeamPlayoffTeamRequest`). Сейчас:

- `player1Id` — **обязательный** числовой ID, игрок должен уже существовать в базе.
- `player2Id` — опциональный числовой ID; если не указан, игрок 2 сохраняется как свободный текст (`player2Name`/`player2Phone`) — это не настоящий профиль `PlayerPadel`, он не регистрируется в системе турнира.
- Команда создаётся как запись `AmericanoTeam` напрямую, **без** `TournamentRegistration`. Страница «Оплаты и посещаемость» (`PaymentService.getPaymentManagementData`) читает исключительно `TournamentRegistration` (`status IN (CONFIRMED, PARTNER_INVITED)`) — команда, добавленная через текущий `addTeam`, туда не попадает, несмотря на то, что `hasPaid`/`attended` физически хранятся в `AmericanoTeam`.

Сотрудники клуба и сами игроки не знают числовые ID — нужен поиск по имени/телефону/email вместо ввода ID, с возможностью тут же создать нового игрока, без дублей по телефону, и с тем, чтобы добавленная так команда вела себя как зарегистрировавшаяся через сайт (в т.ч. была видна на странице платежей).

## Связь с MASTER.md

Не вводит новую роль, статус или инвариант `specs/MASTER.md`. Опирается на существующий инвариант §«Обязательное условие для регистрации» — `PlayerPadel.hasValidContact()` (валидный `+54`-телефон либо Telegram) — новый игрок, созданный через эту форму, должен ему удовлетворять, как и любой другой зарегистрированный игрок. Также опирается на §«Флоу парной регистрации» — результат этой фичи (пара `TournamentRegistration`, `CONFIRMED`) должен быть неотличим от обычной парной регистрации через сайт.

## Требования

### Функциональные

1. **Поиск игрока.** Новый read-only эндпоинт под `/tournaments/team-playoff/admin/{tournamentId}` (например `GET .../players/search?query=...`), доступный тем же ролям, что и остальная админка Team Playoff (`SUPER_ADMIN, ADMIN, ORGANIZER, CLUB_ADMIN`, `tournamentAccessService.assertCanManageTournament`). Ищет среди **активных** игроков (`activo = true`, по аналогии с `TestTournamentController.searchPlayers`) по подстроке в имени, фамилии (можно по отдельности или по полному имени) и телефону; если практично в том же запросе — также по email. Возвращает ограниченный список (как в существующем паттерне — `LIMIT 20`) через DTO (`record`, не `Map<String, Object>` — см. `CODE_STYLE.md`), маппинг — через `mapper/` (MapStruct) либо проекция прямо в `record` через JPQL-конструктор, без ручного заполнения `Map` в контроллере/сервисе.
2. **Независимый выбор режима для каждого из двух игроков команды.** Сейчас только `player2` может быть "новым" (и то не как настоящий профиль) — `player1` обязан существовать. Переработать так, чтобы **оба** слота команды поддерживали два режима независимо:
   - *существующий* — передаётся `id` найденного игрока;
   - *новый* — передаются данные для создания (`nombre`, `apellido`, `telefono`).

   Должны работать все 4 комбинации из клиентского запроса (п.5): оба существующих / первый существующий-второй новый / наоборот / оба новых.
3. **Дедупликация по телефону при создании нового игрока.** Перед созданием — поиск активного игрока с тем же `telefono` (`PlayerRepository.findByTelefono`, уже существует). Если найден — использовать его профиль, не создавать дубль (как и в уже принятом в проекте паттерне `TestTournamentController.resolveOrCreateGuestPlayer` — см. `CODE_REVIEW.md §2`, этот метод явно указан как образец для переиспользования гостевых/walk-in игроков).
4. **Данные нового игрока — минимум, достаточный для `hasValidContact()`.** Клиентский запрос прямо просит не требовать больше полей, чем нужно: `nombre`, `apellido`, `telefono`. Поля, обязательные в системе ради целостности данных, но не нужные пользователю формы (уникальный `email` — `NOT NULL UNIQUE` в `PlayerPadel`, пароль), генерируются автоматически и не показываются в форме — по аналогии с существующим гостевым паттерном (placeholder-email, placeholder password hash). `telefono` — обязателен для нового игрока этой формы (без него новый профиль не удовлетворяет `hasValidContact()`, а значит не может участвовать в турнире) и проверяется тем же форматом телефона `+54`, что и обычная регистрация (`RegistroRequestDto` / валидация телефона на сайте) — не более мягкая/другая валидация.
5. **Видимость в «Оплаты и посещаемость» — через полноценную регистрацию, а не напрямую через `AmericanoTeam`.** Вместо (или в дополнение к) прямого создания `AmericanoTeam`, как делает нынешний `addTeam(...)`, новый флоу должен для обоих игроков (найденных или только что созданных) создать пару `TournamentRegistration` (`isDoubleRegistration = true`, `status = CONFIRMED`, `mainPlayerId`/`partner` — по той же модели, что и обычная парная регистрация с сайта, см. `DoubleTournamentRegistrationService.registerWithExistingPartner` как референс для формы двух записей регистрации на одну пару), а затем собрать из неё команду — переиспользуя существующий `TeamPlayoffService.addTeamFromRegistration(tournamentId, registrationId, hasPaid, attended)` (уже используется кнопкой «Agregar equipo» на странице платежей, `PaymentManagementController`/`payments.html`, T18) вместо дублирования логики сборки `AmericanoTeam` в самом `addTeam`. Результат — команда, созданная этой формой, физически неотличима от команды, собранной из обычной сайтовой парной регистрации (п.6 клиентского запроса: "дальше с ней можно работать так же").
6. **Существующие проверки сохраняются.** Игрок, который уже состоит в активной команде этого турнира (`isPlayerAlreadyOnActiveTeam`), не может быть добавлен повторно — ни как `player1`, ни как `player2` (текущая проверка в `addTeam`/LFPT-357, не ослаблять).
7. **Поля формы, не относящиеся к поиску/созданию игроков, не меняются.** `registrationSource`, `hasPaid`, `attended`, `adminComment` — как есть, применяются к создаваемой команде так же, как сейчас.

### Нефункциональные
- i18n: пользовательских строк на бэкенде нет (сообщения ошибок контроллера — существующий паттерн `flash`/редирект, не новые публичные строки; если добавляются новые тексты ошибок, видимые пользователю — i18n-ключ во все три `messages_{es,ru,en}`, `CODE_STYLE.md §6.4`).
- Безопасность: новая точка входа данных пользователя (поиск + данные нового игрока) — те же роли/авторизация, что и весь `TeamPlayoffViewController` (`tournamentAccessService.assertCanManageTournament`); телефон валидируется тем же паттерном, что и обычная регистрация, прежде чем попасть в БД.
- Производительность: поиск — по подстроке с `LIMIT`, как существующий прецедент (`TestTournamentController.searchPlayers`); не вводит N+1 или полный скан без лимита.

## Вне скоупа
- UI формы (поле поиска, автодополнение, переключатель "новый/существующий") — [#562].
- Любые изменения в обычном флоу регистрации пары через сайт (`DoubleTournamentRegistrationService`) — используется только как референс для формы данных, не меняется.
- Изменение способа поиска/создания гостевых игроков на тестовой странице `/test/tournaments` (`TestTournamentController`) — не трогается, это отдельный, уже существующий internal-инструмент.
- Team Americano (не Team Playoff) — ручного добавления команды по ID там сейчас нет вообще, в скоуп этой задачи не входит (клиентский запрос описывает конкретно существующую форму «Agregar equipo» Team Playoff).
- Применение/учёт лимита мест турнира (`cupoMax`) для команд, добавленных вручную координатором — текущий `addTeam` его не проверяет; это сознательный walk-in-сценарий администратора, не меняется в этой задаче.

## Изменения в системе

### API
- Новый `GET /tournaments/team-playoff/admin/{tournamentId}/players/search?query=...` — поиск активных игроков по имени/фамилии/телефону (опционально email), возвращает ограниченный список.
- `TeamPlayoffTeamRequest` (или новый DTO) — расширяется: вместо единственного обязательного `player1Id` и опционального `player2Id`/`player2Name`/`player2Phone` — по каждому из двух слотов независимо допускается либо `id` существующего игрока, либо данные для создания нового (`nombre`, `apellido`, `telefono`). Точная форма (вложенные объекты на слот vs. плоские поля с префиксом) — на усмотрение реализации, по аналогии со стилем существующих DTO проекта.
- `POST /tournaments/team-playoff/admin/{tournamentId}/teams/add` — то же URL, расширенное поведение (поиск-или-создание для обоих игроков, создание пары `TournamentRegistration` + вызов `addTeamFromRegistration`), сигнатура контроллера может измениться под новый DTO.

### БД
Нет новой миграции — используются существующие таблицы `player_padel_db`, `tournament_registrations_db`, `americano_teams_db`.

### UI
Нет (эта задача — backend-only; UI — [#562]).

## Критерии приёмки
- [ ] `GET .../players/search?query=` по имени находит активного игрока, по телефону — тоже; результат ограничен (не весь список игроков) и доступен только ролям, управляющим турниром.
- [ ] Создание команды с двумя существующими игроками (по найденным ID) — работает, команда видна среди участников турнира.
- [ ] Создание команды: игрок 1 существующий, игрок 2 — новый (имя/фамилия/телефон) — создаёт настоящий профиль `PlayerPadel` для игрока 2, а не текстовую заглушку.
- [ ] Создание команды: игрок 1 новый, игрок 2 существующий — симметрично предыдущему (сейчас `player1` обязан существовать — это ограничение снято).
- [ ] Создание команды: оба игрока новые — оба получают настоящие профили.
- [ ] Указание телефона, который уже принадлежит активному игроку, при создании "нового" игрока — не создаёт дубль, использует существующий профиль (проверяется прямым запросом к `player_padel_db` — количество строк с этим телефоном не увеличилось).
- [ ] Новый игрок, созданный через форму, удовлетворяет `hasValidContact()` (есть валидный телефон).
- [ ] После создания команды оба игрока (найденные или новые) имеют `TournamentRegistration` со статусом `CONFIRMED` на этот турнир.
- [ ] Команда, добавленная через обновлённый `addTeam`-флоу, появляется на странице `/admin/tournaments/{tournamentId}/payments` (виден `hasPaid`/`attended`, можно отмечать оплату так же, как для пары с сайта).
- [ ] Повторная попытка добавить игрока, который уже состоит в активной команде этого турнира — ошибка, как и сейчас (регрессия на существующую проверку `isPlayerAlreadyOnActiveTeam`).
- [ ] `./mvnw verify` зелёный.

## Edge cases
- Телефон нового игрока совпадает с телефоном игрока, который уже в активной команде **этого же турнира** — дедуп по телефону находит существующего игрока, дальше применяется обычная проверка `isPlayerAlreadyOnActiveTeam` → ошибка "уже зарегистрирован", а не тихое создание второй команды с тем же человеком.
- Пустой/слишком короткий поисковый запрос (1 символ) — не должен возвращать весь список активных игроков без разбора; разумный минимум длины запроса или просто `LIMIT`, как в существующем прецеденте.
- `player1` и `player2` — один и тот же человек (оба поля ссылаются на один ID, либо оба "новых" с одинаковым телефоном) — должно быть отклонено с понятной ошибкой, не создавать команду из одного игрока дважды.
- Два реплики в Docker Swarm — создание игрока по телефону и проверка дублей должны быть в одной транзакции (`@Transactional`, как и весь остальной `TeamPlayoffService`), чтобы не создать дубль при параллельном добавлении двух команд с одним и тем же новым телефоном почти одновременно.
- Существующий неактивный (`activo = false`) игрок с тем же телефоном — поиск/дедуп ориентируется на активных игроков (как и весь остальной поиск в проекте, `TestTournamentController.searchPlayers`); решение, что делать с деактивированным совпадением (реактивировать или создать нового) — на усмотрение реализации, задокументировать выбор в commit message (`GIT_WORKFLOW.md §3`).

## Открытые вопросы
Нет. Технические решения, не являющиеся бизнес-вопросом (аналогично `GIT_WORKFLOW.md §3`):
1. **Создание через пару `TournamentRegistration` + `addTeamFromRegistration`, а не напрямую `AmericanoTeam`.** Без этого команда физически не попадёт на страницу платежей (архитектурный факт, не предположение — `PaymentService.getPaymentManagementData` читает только `TournamentRegistration`), а именно это явно требует клиентский запрос (п.6). Переиспользование `addTeamFromRegistration` — не новая логика, а тот же путь, которым уже пользуется существующая кнопка «Agregar equipo» на странице платежей (`T18`, см. `payments.html`), поэтому не считается расширением скоупа.
2. **Email не запрашивается у пользователя при создании нового игрока**, генерируется автоматически — клиентский запрос прямо говорит "другие действительно обязательные поля, если они необходимы системе", и это ровно такой случай (поле нужно схеме `PlayerPadel`, но не нужно пользователю формы) — совпадает с уже принятым в проекте гостевым паттерном.
