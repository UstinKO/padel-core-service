# LFPT-0437: Feature автоматическое email-напоминание за 5 часов до начала парного турнира

## Статус
approved

## Источник
Клиентский запрос: [specs/requests/LFPT-0437-recordatorio-email-parejas.md](../requests/LFPT-0437-recordatorio-email-parejas.md). Issue: [#437](https://github.com/UstinKO/padel-core-service/issues/437).

Telegram-сообщение (для reply): 4666

## Контекст / зачем

Игроки, зарегистрированные на парный турнир, сейчас не получают заблаговременного email-напоминания о месте и времени начала — только письмо-подтверждение регистрации в момент записи. Автоматическое напоминание за несколько часов до старта снижает риск опозданий/неявок. Аналогичный механизм уже существует для Telegram (`TelegramReminderScheduler.sendTomorrowReminders()`, окно 3 часа до старта) — эта фича добавляет параллельный email-канал с окном 5 часов, только для парных турниров.

## Связь с MASTER.md

Затрагивает раздел "Уведомления игрокам" (добавляется новый тип email-уведомления) и опирается на инвариант "Статусы регистрации на турнир" (`CONFIRMED` = участвует в матчах) и модель модальности турнира (`Modalidad.DOBLES`/`INDIVIDUAL`, см. "Форматы турниров"). Новых инвариантов MASTER.md не меняет — правка `MASTER.md` не требуется.

## Анализ существующего кода

- **"Парный турнир"** технически — `Tournament.modalidad == Modalidad.DOBLES`. Это поле не привязано к одному `TournamentType`: `CANCHA_ABIERTA` может быть DOBLES или INDIVIDUAL, `AMERICANO_TEAMS` (Team Americano) **обязан** быть DOBLES (`TeamAmericanoService.java:611`), `AMERICANO` (индивидуальный) обязан быть INDIVIDUAL (`AmericanoService.java:78,266`). Парная регистрация (`DoubleTournamentRegistrationService`) также ключуется по модальности, а не по типу турнира (`tournamentDto.getModalidad() != Modalidad.DOBLES`, без проверки типа) — значит фича должна работать для любого `TournamentType` с `modalidad = DOBLES`, а не только для bracket-формата.
- **"Зарегистрированные игроки пары"** — при парной регистрации создаются **два** отдельных `TournamentRegistration` (по одному на каждого игрока пары, с взаимной ссылкой через поле `partner`), оба переходят в `CONFIRMED` (см. `DoubleTournamentRegistrationService.registerWithExistingPartner`/`confirmPartnerRegistration`). Это верно независимо от `TournamentType` — базовая регистрация на турнир всегда идёт через `TournamentRegistration` (проверено и для `AmericanoService.registerPlayerInternal`). Значит для рассылки достаточно взять все `TournamentRegistration` со `status = CONFIRMED` для турнира — каждая строка уже соответствует одному игроку с его контактными данными (`registration.getPlayer().getEmail()`), дедуплицировать пары не нужно.
- **Референс планировщика**: `TelegramReminderScheduler.sendTomorrowReminders()` — `@Scheduled(cron = "0 0/30 * * * *")`, окно `[now+2h45m, now+3h15m)`, кандидаты через `tournamentRepository.findByFechaInicioInAndActive(dates)`, дедуп — `Map<Long, LocalDate> sentReminders` **в памяти**. Для этой фичи защита от дублей должна быть персистентной (см. "Открытые вопросы" клиентского запроса — не отправлять повторно даже после редактирования турнира), в памяти недостаточно: перезапуск/передеплой приложения (`deploy.yml` на каждый мерж в `master`) сбросил бы `sentReminders`, и турнир, чьё окно ещё не закрылось на момент рестарта, получил бы письмо повторно.
- **Референс email-метода**: `EmailService.sendPartnerDataReminder(...)` — ближайший по смыслу существующий reminder-метод (паттерн `@Timed`/`@TrackErrors`/`@Async`, `EmailMetricsService.recordEmailAttempt/recordEmailSent/recordEmailRejected/recordEmailError`, проверка `emailMetricsService.isDailyLimitReached(dailyEmailLimit)` перед отправкой). Новый метод `sendPairTournamentReminderEmail` пишется по этому же паттерну.
- **i18n — намеренное исключение**: текст письма задан клиентом как фиксированный, на испанском, без вариантов перевода ("название клуба и адрес не переводятся, а берутся из данных турнира как есть"). Это соответствует уже принятому в проекте прецеденту — `TelegramReminderScheduler` тоже шлёт захардкоженный испанский текст без i18n-ключей (аудитория — игроки в Аргентине, канал не завязан на предпочитаемую локаль профиля). Новый email-шаблон `email/pair-tournament-reminder.html` пишется как статический Spanish-only HTML (без `th:text="#{...}"` для основного текста письма и меток) — это осознанное отступление от общего правила i18n в `CLAUDE.md`/`MASTER.md`, а не упущение.

## Требования

### Функциональные

1. Новый scheduled-метод (например, в новом `PairTournamentReminderScheduler` или как дополнительный `@Scheduled`-метод в существующем сервисе по аналогии с `TelegramReminderScheduler`) каждые 30 минут находит турниры с:
   - `modalidad == Modalidad.DOBLES`,
   - активные (`active`/аналог фильтра `findByFechaInicioInAndActive`),
   - начало (`fechaInicio` + `horaInicio`) попадает в окно `[now + 4ч45м, now + 5ч15м)`,
   - напоминание ещё не отправлено (см. п.3).
2. Для каждого найденного турнира — для всех `TournamentRegistration` со `status = CONFIRMED` отправить письмо `EmailService.sendPairTournamentReminderEmail(...)` на `registration.getPlayer().getEmail()`, с подстановками:
   - `{club}` — `Club.nombre` клуба турнира (`clubRepository.findById(tournament.getClubId())`), как есть, без перевода;
   - `{dirección}` — `Club.direccion`, как есть, без перевода;
   - `{hora}` — `tournament.getHoraInicio()`, формат `HH:mm`.
   Текст письма — ровно как в клиентском запросе (см. "Требования" запроса), без изменений формулировок.
3. После успешной отправки писем всем `CONFIRMED`-игрокам турнира — пометить турнир как "напоминание отправлено" **персистентно** (новое поле в БД, не in-memory), чтобы:
   - повторный прогон планировщика для того же турнира не отправлял письмо снова;
   - редактирование турнира (в т.ч. изменение даты/времени) **после** первой отправки не приводило к повторной отправке;
   - флаг переживал перезапуск приложения/деплой.
4. Если у турнира нет ни одной `CONFIRMED`-регистрации на момент попадания в окно — турнир всё равно помечается как "напоминание отправлено" (обработан), повторных попыток по нему быть не должно.
5. Ошибка отправки письма одному игроку не должна прерывать рассылку остальным игрокам того же турнира (по аналогии с try/catch на уровне турнира в `TelegramReminderScheduler.sendTomorrowReminders`, но здесь — try/catch на уровне отдельного письма, чтобы один невалидный email не заблокировал письма остальным игрокам пары/турнира).

### Нефункциональные

- i18n: новых пользовательских строк в `messages_{es,ru,en}.properties` не добавляется — см. "Анализ существующего кода" про намеренное исключение (текст письма фиксирован на испанском по требованию клиента, как и у `TelegramReminderScheduler`).
- Метрики: новый email-метод размечается `@Timed`/`@TrackErrors` с `tags = {"service=email", "type=pair_tournament_reminder"}` и `EmailMetricsService` вызовами (`recordEmailAttempt("PAIR_TOURNAMENT_REMINDER")` и т.д.) — по аналогии с остальными методами `EmailService`, попадает в существующие Prometheus-метрики `email_sent_total{type}`/`email_errors_total`/`email_rejected_total` и учитывается дневным лимитом `email_daily_limit` (300).
- Производительность: окно и частота (каждые 30 минут) соответствуют объёму данных проекта — не требует батчинга/асинхронной очереди сверх уже используемого `@Async` на email-методах.

## Вне скоупа

- Изменение/повторная отправка Telegram-напоминаний (`TelegramReminderScheduler`) — не трогаем.
- Настройка времени напоминания (5 часов) через админ-панель — жёстко задано кодом, как и 3-часовое окно у Telegram-напоминаний.
- Напоминания для одиночных (`INDIVIDUAL`) турниров — вне скоупа этой задачи (клиент явно просил только парные).
- UI/админ-индикация того, что напоминание уже отправлено — не запрошено клиентом, не делаем.

## Изменения в системе

### API
Новых HTTP-эндпоинтов нет — фича полностью фоновая (`@Scheduled`).

### БД
Новая Liquibase-миграция `v1.49-add-pair-reminder-sent-at-to-tournament.yaml`: колонка `pair_reminder_sent_at` (`TIMESTAMP`, nullable) в `tournaments_db`. `NULL` — напоминание ещё не отправлено (или не применимо); не-`NULL` — момент отправки (или обработки турнира без `CONFIRMED`-игроков, см. Требования п.4), после которого повторная отправка не выполняется никогда.

### UI
Нет — новый файл `src/main/resources/templates/email/pair-tournament-reminder.html` (email-шаблон, не веб-страница).

## Критерии приёмки

- [ ] Турнир с `modalidad = DOBLES`, старт которого через ~5 часов (в окне `[+4ч45м, +5ч15м)`) и есть хотя бы один `CONFIRMED`-игрок — каждый `CONFIRMED`-игрок получает письмо с текстом из клиентского запроса, где `{club}`/`{dirección}`/`{hora}` подставлены корректно (данные клуба и время — как в БД, без перевода).
- [ ] Турнир с `modalidad = INDIVIDUAL` в том же окне — письмо не отправляется никому.
- [ ] После отправки — `pair_reminder_sent_at` турнира становится не-`NULL`; повторный прогон планировщика (сразу после первого, турнир всё ещё в окне) не отправляет письма повторно.
- [ ] Редактирование турнира (включая изменение `fechaInicio`/`horaInicio`) после отправки — `pair_reminder_sent_at` не сбрасывается, повторной отправки не происходит.
- [ ] Флаг персистентен: перезапуск приложения (симулируется перечитыванием турнира из БД в новом прогоне планировщика) не приводит к повторной отправке уже обработанного турнира.
- [ ] Турнир с `modalidad = DOBLES` в окне, но без ни одной `CONFIRMED`-регистрации — турнир помечается обработанным (`pair_reminder_sent_at` проставлен), без писем и без ошибок в логе.
- [ ] Ошибка отправки одному игроку (например, невалидный email) не блокирует отправку остальным `CONFIRMED`-игрокам того же турнира.
- [ ] Метрики: успешная отправка увеличивает `email_sent_total{type="pair_tournament_reminder"}` (аналогично существующим типам писем).

## Edge cases

- Турнир без клуба или клуб без `direccion` — на практике `clubId`/`Club` для активного турнира всегда заполнены (создание турнира требует привязки к клубу); если данных всё же нет — не блокировать рассылку остальным, залогировать и пропустить письмо конкретному турниру/игроку (защитный `try/catch`, как в п.5 Требований), не бросать необработанное исключение в scheduled-методе.
- Турнир уже начался/прошло окно (`pair_reminder_sent_at IS NULL`, но старт уже в прошлом на момент первого прогона после деплоя, окно "проскочено") — не отправлять задним числом письмо про турнир, который уже идёт или прошёл; выборка кандидатов по точному временному окну (`[+4ч45м, +5ч15м)`) естественно это исключает, дополнительная проверка не нужна.
- Игрок без email (`PlayerPadel.email` пуст/null) — теоретически не должно происходить (email обязателен при регистрации аккаунта), но если встретится — пропустить письмо этому игроку с логом, не прерывая рассылку остальным (тот же защитный `try/catch`).
- Параллельные реплики (Docker Swarm, будущее масштабирование, см. `CLAUDE.md` "Переход на микросервисы") — гонка "оба инстанса видят `pair_reminder_sent_at IS NULL` одновременно и оба шлют письма" в скоуп этой задачи не входит (текущий деплой — один инстанс; `checkExpiredInvitations`/`sendTomorrowReminders` в проекте уже имеют этот же класс риска и явно не защищены от него) — не усложнять реализацию оптимистичной блокировкой/`SELECT ... FOR UPDATE` сверх существующего в проекте паттерна.
