# LFPT-1199: Feature многомодульный монолит, фаза 2 — выделить чтение публичных клубов в application

## Статус

approved

## Источник

[Issue #1199](https://github.com/UstinKO/padel-core-service/issues/1199), родитель [#1197](https://github.com/UstinKO/padel-core-service/issues/1197); утверждённая владельцем подготовка второй фазы. Техническая постановка без отдельного клиентского запроса.

## Контекст / зачем

Первый после движка небольшой срез — публичное чтение клубов. Последовательность отделяет проверку генерации, границу application, wire-контракт и независимую приёмку.

## Связь с MASTER.md

Бизнес-правила, роли и публичные данные сохраняются. Новых пользовательских строк, внутреннего HTTP и изменения БД нет.

## Требования

## Цель и конкретный срез
Выделить только чтение активных клубов для GET /api/public/clubs и GET /api/public/clubs/{id}. Сейчас PublicDiscoveryService вызывает ClubRepository и PublicClubMapper; PublicClubResponse — HTTP record из девяти полей. Каталог и главная остаются на прежнем пути.

## Что сделать
Создать padel-application с нейтральной read-моделью клуба, входным сценарием и выходным портом чтения. Перенести правила доступности и обращения к порту в сценарий; существующий контроллер остаётся web-адаптером в legacy bootstrap. Реализацию порта на текущем ClubRepository и MapStruct оставить в единственном корневом legacy src под bootstrap до #1051. DTO HTTP и JPA entity не пересекают границу application. Нейтральное отсутствие результата преобразуется web-адаптером в прежний ProblemDetail.

## Критерии приёмки
- [ ] Application не импортирует bootstrap/legacy, api-contract, persistence, JPA/JDBC, Spring Data, MVC, Jackson и web Security; разрешены согласованные service/transaction аннотации.
- [ ] Список: только активные клубы, прежний порядок nombre,id; пустая выборка — тот же JSON []. Карточка: действующий активный ID — прежние девять полей; неизвестный/неактивный — 404 CLUB_NOT_FOUND. Ошибочный тип ID и отказ БД сохраняют действующие HTTP/code/локализацию.
- [ ] Null-поля и canonicalUrl, Content-Type/Cache-Control, права профилей и вывод React не меняются; отрицательные/нулевые ID не получают придуманную новую бизнес-ошибку.
- [ ] Сохраняется readOnly-транзакционная граница и вызов через Spring proxy. Один bean сценария/адаптера; архпроверка запрещает обратные зависимости и возвращение entity/старого HTTP DTO через порт.
- [ ] Существующие PublicDiscoveryIntegrationTest и новые boundary/contract проверки пройдены; исходный HTTP DTO остаётся прежним до отдельной контрактной задачи.
- [ ] Полный verify/конечный jar/image и общий smoke/rollback подтверждены; модуль подключён в root/CI/docs согласованно.

## Границы
Нет записи клубов, прав клубных аккаунтов, переезда каталогов/проведения/регистрации, генерации API DTO, физической БД или выделения persistence. Действующий MVC клуба не переключать без анализа его потребителей.

## Изменения в системе

### API
Существующие GET /api/public/clubs и /api/public/clubs/{id}; контракт сохраняется. HTTP-контракт остаётся прежним; внутреннее чтение направляется через application.

### БД
Без миграций/переноса данных. PostgreSQL и Liquibase принадлежат поздней #1051.

### UI
Без изменения пользовательского интерфейса; потребители — React ClubPages/Catalogue/EventPage и API discovery.ts. Проверки в отдельной #1201.

## Edge cases

Пустой список, неизвестный/неактивный ID, нечисловой ID, nullable поля, порядок nombre/id, отказ БД, base URL с завершающим /, внешние OpenAPI $ref, неподдерживаемый тип генератора, старая вкладка клиента и возврат прежнего jar.
