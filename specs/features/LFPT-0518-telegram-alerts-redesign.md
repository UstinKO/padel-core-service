Telegram-сообщение (для reply): 4931

## Контекст / зачем

Механизм `logging/TelegramLogAppender.java` сейчас берёт любой `WARN`/`ERROR` лог из пакета `com.padle.core` (порог задан в `logback-spring.xml`, аппендер `TELEGRAM`) и форматирует его как `🔴 <имя класса>\n<текст сообщения>` — без структуры, без контекста (кто, где, с каким HTTP-статусом), без разделения по значимости. Пример из жалобы заказчика (`PlayerDashboardController.registerForTournament`, строка `log.error("Error registering for tournament", e)`) подтверждён в коде: один и тот же `catch (Exception e)` ловит и реальные баги, и ожидаемые бизнес-исключения (`TournamentRegistrationException`, например повторную регистрацию), не различая их.

Аналогично в один канал без разбора попадают: срабатывания `RateLimitFilter` (защита сработала штатно — это не баг) и `CustomAccessDeniedHandler` (попытка доступа к чужому ресурсу). Заказчик прямо просит разделить эти три природы алертов на уровни серьёзности.

Восстановление пароля (после [LFPT-0499](../done/LFPT-0499-password-reset-flow.md)) уже логирует причину отказа (not-found/used/expired) на уровне `warn` с замаскированным токеном, но без явного разделения по стадиям флоу (запрос → письмо → переход по ссылке → токен невалиден → пароль сменён) — заказчик отдельно просит ввести именно такую стадийность и подчёркивает высокий приоритет (забытый пароль = потерянный для сайта игрок).

## Связь с MASTER.md

Не затрагивает инварианты `specs/MASTER.md` — это внутренний канал диагностики (логирование → Telegram-бот для архитектора/владельца), не продуктовая/бизнес-логика и не часть флоу, видимого игрокам или организаторам.

## Требования

### Функциональные

1. **Три уровня серьёзности алерта**, определяющие значок и заголовок сообщения:
   - 🔴 `Application Error` — непредвиденное исключение (реальный баг).
   - 🟡 `Security Warning` — срабатывание защиты (`RateLimitFilter`, `CustomAccessDeniedHandler`).
   - 🟠 `User/Validation Error` — ожидаемое бизнес-исключение/ошибка пользовательского ввода (повторная регистрация, невалидный токен сброса пароля и т. п.).
2. **Структурированный формат** вместо `<имя класса> + текст`: заголовок (эмодзи + человекочитаемое название на русском) → `Event: <EVENT_CODE>` → предметные поля (`Tournament ID`, `User ID`, `Endpoint`, `HTTP`, `Error` и т. п. — конкретный набор зависит от события) → `Request ID: <id>` → `Time: <dd/MM/yyyy HH:mm, America/Argentina/Buenos_Aires>`.
3. **`Request ID`** — в проекте такого механизма пока нет (есть только неиспользуемый плейсхолдер `%X{requestId:-}` в Loki JSON-паттерне `logback-spring.xml`). Добавить фильтр, генерирующий короткий ID на входе HTTP-запроса, кладущий его в MDC (`requestId`) и очищающий после обработки запроса (`try/finally`, чтобы не утекало между запросами на переиспользуемых потоках Tomcat). Как побочный эффект — у Loki-логов всех запросов (не только мигрированных мест) наконец заполнится это поле.
4. **Применить структурированный формат + классификацию серьёзности** к следующим точкам (используемые в примерах заказчика + прямо упомянутые источники смешения):
   - `PlayerDashboardController#registerForTournament`, `catch` блок: `Event = TOURNAMENT_REGISTRATION`, поля `Tournament ID`, `User ID`, `Endpoint` (реальный метод+URI запроса), `HTTP` (код ответа, сейчас всегда `400`), `Error` (`e.getMessage()`). Серьёзность: `User/Validation Error`, если исключение — `TournamentRegistrationException`/`InvalidStateException`/`ResourceNotFoundException` (ожидаемые бизнес-исключения этого сервиса, см. `TournamentService`); иначе — `Application Error`.
   - Восстановление пароля (`PasswordResetService`/`PasswordResetController`) — 5 именованных стадий:
     - `PASSWORD_RESET_REQUEST` — запрошено письмо (включает случай email не найден в базе — остаётся `warn`, но теперь с этим кодом события).
     - `PASSWORD_RESET_EMAIL_SENT` — письмо отправлено.
     - `PASSWORD_RESET_LINK_OPEN` — пользователь открыл ссылку (`GET /recuperar-password?token=...`) с валидным токеном.
     - `PASSWORD_RESET_TOKEN_INVALID` — токен не найден / уже использован / просрочен (объединяет 3 существующие ветки). Поле `Token status`: `invalid` / `already_used` / `expired`. **Ни сам токен, ни ссылка, ни пароль не попадают в сообщение** — только эти 4 статуса.
     - `PASSWORD_RESET_SUCCESS` — пароль успешно сменён.
     Стадии `EMAIL_SENT`, `LINK_OPEN` (успех), `SUCCESS` — остаются на уровне `info` (как и сейчас), то есть **не создают алерт** в Telegram (порог аппендера `WARN` не меняется). Стадии `REQUEST` (случай email не найден) и `TOKEN_INVALID` — `warn`, серьёзность `User/Validation Error`.
   - `RateLimitFilter` (4 существующих `log.warn`): `Event = RATE_LIMIT_EXCEEDED` (обычное превышение лимита) или `Event = SUSPICIOUS_ACTIVITY_BLOCKED` (эскалация IP до `BLOCKED`), серьёзность `Security Warning`, поля `IP`, `Endpoint`/путь, `Limit type`.
   - `CustomAccessDeniedHandler` (`log.warn` на `SecurityException`): `Event = ACCESS_DENIED`, серьёзность `Security Warning`, поля `Endpoint`, `Error`.
5. **Остальные существующие `log.warn`/`log.error`**, не перечисленные в п.4 (например `RecaptchaService`, и другие ~30 мест по проекту) — продолжают попадать в Telegram в прежнем нестуктурированном формате (`🔴 <class> + текст`), без изменений. Полная миграция всех мест логирования — вне скоупа этой задачи (см. "Вне скоупа").

### Нефункциональные

- i18n: не применимо — это внутренний диагностический канал (Telegram для архитектора/владельца), не пользовательский UI; новых пользовательских строк нет.
- Безопасность: токен восстановления пароля, пароль и полный reset-link никогда не попадают в текст алерта — только статус токена (см. п.4). Это ужесточение по сравнению с текущим логированием замаскированного токена (`maskToken`) — для Telegram-алерта статус токена важнее самого (даже замаскированного) значения.
- Производительность: формирование структурированного сообщения — синхронная операция на пути запроса (строковая конкатенация, без I/O), доставка в Telegram — как и сейчас, через фоновую очередь (`TelegramAlertQueue`, `offer`, без блокировки запроса).

## Вне скоупа

- Полная миграция всех остальных `log.warn`/`log.error` по проекту (~30 файлов) на структурированный формат — технический долг, отдельные задачи по мере необходимости.
- Изменение порога фильтра аппендера `TELEGRAM` (сейчас `WARN`) — не меняем.
- `cancelRegistration`/`cancelDoubleRegistration` в том же `PlayerDashboardController` (похожий паттерн `catch (Exception e)`, но не упомянуты заказчиком явно) — не трогаем в этой задаче.
- Заполнение `userId`/`traceId` в MDC (плейсхолдеры `%X{userId:-}`/`%X{traceId:-}` в Loki JSON-паттерне) — только `requestId` заполняется в рамках этой задачи.
- Бизнес-логика восстановления пароля / регистрации на турнир — не меняется, только логирование вокруг неё.

## Изменения в системе

### API
Без изменений контракта REST/веб-эндпоинтов — меняется только внутреннее логирование вокруг существующих маршрутов.

### БД
Без миграций.

### UI
Без изменений шаблонов.

### Код (ориентир для реализации, не жёсткая спецификация классов)
- Новый пакет-уровня механизм в `logging/`: перечисление уровней серьёзности (эмодзи + заголовок) и небольшая утилита, которая по вызову из бизнес-кода формирует готовое многострочное сообщение (заголовок, `Event:`, поля в заданном порядке, `Request ID:`, `Time:`) и передаёт его в `log.warn`/`log.error` вместе с меткой "это структурированное сообщение" (например, через MDC-флаг), чтобы `TelegramLogAppender` мог отличить его от обычного лога и отправить как есть, не оборачивая в старый формат `🔴 <class>`.
- Новый `OncePerRequestFilter` (аналог `RateLimitFilter` по расположению в `security/`), генерирующий `requestId` на вход запроса, кладёт в MDC, снимает в `finally`. Регистрируется в `SecurityConfig` раньше `RateLimitFilter` (`addFilterBefore(requestIdFilter, RateLimitFilter.class)`), чтобы `requestId` был доступен уже на этапе rate-limit предупреждений.
- `TelegramLogAppender` — ветвление: структурированное сообщение (по MDC-флагу) уходит в очередь как есть (без `🔴 <b>%s</b>` обёртки); обычное сообщение — как сейчас, без изменений в поведении.
- Время — `America/Argentina/Buenos_Aires`, формат `dd/MM/yyyy HH:mm` (целевой рынок проекта — Аргентина, см. `CLAUDE.md`).

## Критерии приёмки

- [ ] Повторная регистрация на уже зарегистрированный турнир (`TournamentRegistrationException`, "Ya estás registrado...") → Telegram-алерт `🟠 User/Validation Error`, с полями `Event: TOURNAMENT_REGISTRATION`, `Tournament ID`, `User ID`, `Endpoint`, `HTTP`, `Error`, `Request ID`, `Time`.
- [ ] Непредвиденное исключение в том же эндпоинте (не входящее в известные бизнес-исключения) → Telegram-алерт `🔴 Application Error`, тот же набор полей.
- [ ] Превышение лимита в `RateLimitFilter` (любая из 4 веток) → Telegram-алерт `🟡 Security Warning`, `Event: RATE_LIMIT_EXCEEDED` или `SUSPICIOUS_ACTIVITY_BLOCKED`.
- [ ] `SecurityException` на чужом ресурсе (`CustomAccessDeniedHandler`) → Telegram-алерт `🟡 Security Warning`, `Event: ACCESS_DENIED`.
- [ ] Переход по ссылке восстановления пароля с несуществующим / уже использованным / просроченным токеном → Telegram-алерт `🟠 User/Validation Error`, `Event: PASSWORD_RESET_TOKEN_INVALID`, поле `Token status` = соответствующее значение; в тексте алерта нет ни самого токена, ни ссылки.
- [ ] Успешные стадии восстановления пароля (письмо отправлено, пароль сменён, открытие валидной ссылки) — логируются на `info`, НЕ создают Telegram-алерт.
- [ ] Запрос сброса пароля на незарегистрированный email → Telegram-алерт `🟠 User/Validation Error`, `Event: PASSWORD_RESET_REQUEST`.
- [ ] Место логирования, не входящее в п.4 требований (например `RecaptchaService.log.error`) — алерт в Telegram приходит в прежнем, нестуктурированном виде (регрессии нет).
- [ ] `Request ID` присутствует во всех структурированных алертах; для двух разных HTTP-запросов — разные значения; внутри одного запроса (если он логирует несколько раз) — одинаковое.
- [ ] MDC (`requestId` и флаг структурированного сообщения) не утекает между запросами — после завершения запроса (включая запрос, завершившийся исключением) следующий необработанный лог на том же потоке не содержит стартовых значений предыдущего запроса.
- [ ] Автотесты на классификацию серьёзности (бизнес- vs непредвиденное исключение) и на формирование структурированного сообщения.
- [ ] `./mvnw verify` проходит.

## Edge cases

- Исключение, брошенное внутри блока, где уже открыт MDC-контекст структурированного сообщения — MDC должен быть снят даже при вылете исключения (проверить через `try/finally`, не просто `try`).
- Длинное сообщение об ошибке (длинный `e.getMessage()`) — Telegram-сообщение не должно превышать разумный лимit; сохранить существующий паттерн обрезания (сейчас 400 символов для обычных сообщений), адаптировать лимит под более длинный структурированный формат (несколько полей), не дать одной строке "вытолкнуть" остальные поля за пределы читаемого сообщения.
- Два параллельных запроса (например, два игрока одновременно пытаются зарегистрироваться на один и тот же турнир) — у каждого свой `requestId` (MDC — thread-local, Tomcat обрабатывает каждый запрос в своём потоке).
- `RateLimitFilter` обрабатывает запрос раньше `UsernamePasswordAuthenticationFilter`, но позже `RequestIdFilter` (по порядку регистрации) — `requestId` должен быть доступен уже на этапе проверки rate limit, в том числе для запросов, не прошедших дальше по цепочке фильтров.
- Email, не найденный в БД при запросе сброса пароля — алерт создаётся (это ожидаемая ветка пользовательской ошибки), но не должен провоцировать срабатывание как security-инцидент — остаётся `User/Validation Error`, не `Security Warning` (отличие от повторяющихся попыток, которые уже отдельно ловит `RateLimitFilter` по REGISTER-лимиту).

## Открытые вопросы

Нет открытых бизнес-вопросов. Все решения в этой спеке — технические (точный набор классов/API, конкретный механизм передачи флага "структурированное сообщение" между вызовом и аппендером, формат времени/таймзона) и сделаны по аналогии с уже существующими в проекте паттернами (`RateLimitFilter`/`SecurityConfig` для нового фильтра, существующая бизнес-исключения `TournamentRegistrationException`/`InvalidStateException`/`ResourceNotFoundException` для классификации серьёзности, существующий `maskToken`/логирование из LFPT-0499 для стадий восстановления пароля). Набор мигрируемых точек (п.4 требований) — ровно то, что явно названо в клиентском запросе (регистрация на турнир, восстановление пароля, `RateLimitFilter`/подозрительная активность) плюс прямой аналог (`CustomAccessDeniedHandler` — тот же "попытки подозрительной авторизации", упомянутые заказчиком).
