# LFPT-0637: Вход через Google и почту для 1Padel.App и «Мои мероприятия»

## Статус
draft

## Источник
[specs/requests/LFPT-0637-vhod-google-pochta-mobile.md](../requests/LFPT-0637-vhod-google-pochta-mobile.md). Telegram-сообщение (для reply): 5245.

## Контекст / зачем
Заказчик хочет, чтобы игроки входили в мобильное приложение «1Padel.App» тем же аккаунтом сайта (Google или email/пароль) и видели список своих турниров («Мои мероприятия»). К запросу приложен внешний материал (архив, пересланный в Telegram от третьего лица), претендующий на «готовую реализацию» backend + мобильного приложения — он взят только как справочник желаемого контракта, не как применяемый патч (см. ограничение в клиентском запросе и прецедент PR #624/LFPT-0623).

## Связь с MASTER.md
`specs/MASTER.md` описывает вход через форму (сессия) для веба, JWT для API, Google OAuth2 только для игроков. Мобильный вход — расширение существующей модели (те же аккаунты `PlayerPadel`, тот же `JwtService`), не новая модель ролей. Если реализация подтвердится — `MASTER.md` нужно дополнить строкой о мобильном клиенте в разделе "Роли пользователей"/вход.

## Требования
Не формулируются до снятия гейта ниже — см. "Открытые вопросы". Предварительно, по присланному материалу и прецеденту #624, ожидаемый контур backend-части:
- Email/password вход мобильного клиента через существующий `AuthenticationManager`, только для активного `PlayerPadel`.
- Google-вход мобильного клиента — подтверждение через существующий серверный Google OAuth2 браузера (без изменения client id/secret/redirect URI), с коротким одноразовым связыванием мобильного запроса с подтверждённым браузерным логином.
- `GET`-эндпоинт своих регистраций игрока (из `principal`, без чужих данных) для раздела «Мои мероприятия» — только просмотр, без записи/отмены из приложения.

### Безопасность
Новая точка входа данных от пользователя (новые публичные/полу-публичные эндпоинты входа) — любые правки `SecurityConfig`/CSRF-исключений требуют отдельного внимания при ревью (Шаг 4 `develop-feature.md`), не автоматического копирования из вложения.

## Вне скоупа (предварительно)
Apple-вход, запись/отмена регистрации из приложения, публикация в App Store/Google Play (нативная сборка) — если не будет прямо подтверждено как часть этой задачи.

## Открытые вопросы

Задача гейтится по правилам `GIT_WORKFLOW.md` §1 ("для крупных задач с архитектурным выбором — сначала согласовать план") и `develop-feature.md` ("любой бизнес-вопрос уходит пользователю"). Не додумываю сам:

1. **Подтверждение источника.** Вложенный архив пришёл пересланным от третьего лица («Evgeny_754»), не напрямую от вас. Эта задача и приложенный материал — действительно от вас/по вашей инициативе? Если нет — задачу не делаем вообще.
2. **Что такое «1Padel.App» сегодня.** В репозитории и документации нет никакого существующего мобильного приложения — только планы на будущее (`docs/microservices-migration-plan.md`) и план перехода веба на React (`docs/frontend-react/`, пока не мобильный). Вложение описывает совершенно новый мобильный стек (React Native/Expo) с веб-экспортом на `/app/` того же домена. Это то, что нужно создать с нуля в этом же репозитории (новый язык/стек Node/React Native рядом с Java-монолитом), или речь о другом, отдельном проекте, которым я не управляю в этой сессии?
3. **Масштаб этого прогона.** Если мобильное приложение — часть этой задачи, это очень крупная доработка (новый стек, сборка, деплой статики, нативные сборки iOS/Android упомянуты в вложении). Делать её целиком одним автономным прогоном без ревью — то, что вы хотите, или сначала нужен только backend (вход + свои турниры), а мобильная часть — отдельная, более медленная задача с ручным контролем?
4. **Автодеплой для аутентификации.** Обычно конвейер сам вливает и деплоит в прод без ревью человека. Эта задача — изменения в аутентификации игроков (новые эндпоинты входа, исключения из CSRF, новая таблица БД). Подтверждаете, что такую задачу тоже можно довести до автодеплоя по обычным правилам, без отдельной ручной проверки перед проде?
5. **Раздел «Мои мероприятия».** Только просмотр своих турниров (как в прецеденте #624 — read-only), без записи/отмены через приложение — этого достаточно для этой задачи?

До ответа статус остаётся `draft`, реализация не начата.
