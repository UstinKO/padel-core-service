# LFPT-0772: Измерение рекламы Meta — атрибуция и оплата

## Статус
testing

## Источник
https://github.com/UstinKO/padel-core-service/issues/772. Прямое задание пользователя в Codex. Frontend: #773.
Уточнение пользователя: сумма платежа накопительная, при доплате организатор увеличивает существующую сумму.

## Контекст / зачем
Связать рекламный переход с сохранённой записью и фактическими поступлениями, чтобы оценивать стоимость оплаченного участника. Количество денежных событий не равно количеству участников.

## Связь с MASTER.md
Используются существующие статусы регистрации и ручные платежи. Цена мероприятия не заменяет полученную сумму; фиксируется только как ориентир полной оплаты участника на момент записи. Бизнес-статусы не меняются.

## Требования
- Маркетинговое согласие обязательно для атрибуции, браузерных событий и CAPI. Отказ/отзыв прекращает доставку.
- Первый/последний переход обновляются только при наличии UTM или реального fbclid. Прямой визит не стирает атрибуцию. Снимок источника связывается с регистрацией и её оплатами.
- CONFIRMED/PARTICIPATED → EventRegistration; WAITLIST/WAITLIST_INVITED → EventWaitlist; остальные активные ожидания партнёра → EventRegistrationPending. CANCELLED/SOLO_EXPIRED не создают успешную конверсию. Каждая категория для записи имеет постоянный идентификатор. Регистрация аккаунта не является регистрацией на мероприятие.
- Purchase — положительный прирост накопительной суммы в PAID. Высшая уже наблюдённая сумма не уменьшается при исправлении/возврате. Неизвестные/нулевые суммы и неподдерживаемые валюты не подменяются. Смена валюты существующего платежа не интерпретируется как новая оплата.
- Пара с двумя записями и гость-партнёр учитываются по отдельным платёжным строкам. Сумма банковского перевода распределяется по строкам, не дублируется целиком. Один Purchase — новое подтверждённое поступление по строке; paid_participants — отдельное число впервые достигших полной оплаты слотов. При несовпадающих валютах/неизвестной цене число полностью оплаченных не выдумывается.
- Исторические записи и суммы фиксируются миграцией как исходная база без событий. Новые приросты не отправляются без связанной маркетинговой атрибуции и согласия.
- События создаются транзакционно и сохраняются в БД. Фоновая доставка имеет аренду, блокировки, повторные попытки с прежними event_id/event_time и ограниченный срок. Запрос к Meta никогда не выполняется в транзакции оплаты.
- Перед недоставленным Purchase проверяются текущее согласие, статус и сумма платежа. Возвраты/снижения не дают новых Purchase; уже принятый Meta Purchase не отменяется этим API, чистая выручка/участники видны в локальном экспорте.
- Конфигурация по умолчанию выключена. Секрет только на сервере, payload и ошибки с токеном не логируются. Сопоставление по анонимному хешированному external_id и полученным от браузера участника fbp/fbc. IP/браузер организатора не используются. Ручная оплата: action_source=other.

## Изменения в системе
### API
Публичные CSRF-защищённые /api/marketing/* для контекста, конфигурации и браузерных событий; защищённый /admin/marketing/export.csv для отчёта.
### БД
Новая Liquibase-миграция: посетители с согласием, снимки атрибуции записей, прогресс накопительных оплат, впервые оплаченные слоты и очередь событий. Историческая база заполняется без доставки.
### UI
В отдельном frontend PR #773: Pixel, согласие, сбор UTM и выдача событий браузера.
