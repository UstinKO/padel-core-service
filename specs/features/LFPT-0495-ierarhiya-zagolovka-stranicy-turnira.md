# LFPT-0495: Feature иерархия заголовка страницы турнира — тип турнира главным заголовком

## Статус
approved

## Источник
Telegram-сообщение (для reply): 4862

Клиентский запрос: [specs/requests/LFPT-0495-ierarhiya-zagolovka-stranicy-turnira.md](../requests/LFPT-0495-ierarhiya-zagolovka-stranicy-turnira.md). Issue: [#495](https://github.com/UstinKO/padel-core-service/issues/495).

## Контекст / зачем
На публичной странице турнира (`/torneo/{id}`, `tournament-details.html`) главным крупным заголовком (`<h1>`) сейчас выводится `tournament.nombre` — поле, которое с LFPT-374 автогенерируется исключительно из пола и уровня (`Tournament.generateNombre()`, например «Mixto · TODOS»). Сам тип мероприятия (Cancha Abierta / Rey de Cancha / Americano / Americano Equipos / Clínica de Pádel) при этом — лишь одна из пяти вторичных плашек в общем ряду и визуально теряется среди пола, уровня, формата участия и статуса.

Это не соответствует карточкам турниров на главной странице (`static/js/home.js`, `createTournamentCard`): там уже сделано так, как просит заказчик — тип турнира в `<h3 class="tournament-title">`, пол/уровень — плашки в цветной шапке карточки, формат участия — подпись под заголовком. Заказчик прислал скриншот именно такой карточки как референс и попросил перенести эту иерархию на страницу самого турнира.

## Связь с MASTER.md
Фича не меняет ни одного инварианта `specs/MASTER.md` (роли, статусы регистрации, форматы турниров) — это чисто визуальная перегруппировка уже существующих полей турнира (`tipo`, `generoFormato`, `categoriaNivel`, `modalidad`, `estado`) на одной публичной странице. Раздел MASTER.md «Форматы турниров» (перечисление 4 форматов) используется как есть, без изменений.

## Требования

### Функциональные
1. В блоке `.tournament-title-section` на `tournament-details.html`: главный `<h1>` показывает переведённое название **типа турнира** (`tournament.tipo`), а не `tournament.nombre`.
2. Ниже заголовка — ряд вторичных плашек (`.tournament-badges`): пол (`generoFormato`), уровень (`categoriaNivel`), формат участия (`modalidad` → Individual/Parejas), статус турнира (`estado`). Прежняя отдельная плашка с типом турнира (`badge-type`) убирается — её содержимое теперь в `<h1>`, дублировать не нужно.
3. Перевод типа турнира в `<h1>` — через уже существующие ключи `enum.tipo.KING_OF_COURT` / `AMERICANO` / `AMERICANO_TEAMS` / `CANCHA_ABIERTA` / `PADEL_CLINIC` в `messages_{es,ru,en}.properties` (они уже заполнены для всех трёх локалей — see строки `enum.tipo.*` во всех трёх файлах; ровно этот же ключ раньше использовался для `badge-type`, новых строк заводить не нужно). Перевод определяется стандартным `AcceptHeaderLocaleResolver` проекта — отдельного переключателя не требуется.
4. Названия клубов и другие собственные названия в рамках этого изменения не переводятся — факт: в заголовке их нет, это требование удовлетворяется автоматически (клуб выводится отдельно, в `.info-card`, этот блок не трогается).
5. Правило применяется единообразно для всех 5 значений `TournamentType` — шаблон один на все типы (различие только в данных, ветвления по типу в этом блоке нет и не появляется).
6. **Побочный эффект, который нужно поправить в этом же PR:** JS-код шаринга турнира (`tournament-details.html`, инлайн-скрипт, формирует `href` для кнопок «Отправить по WhatsApp/Telegram») берёт текст турнира через `document.querySelector('h1').textContent` — расчёт на то, что `h1` = название турнира. После смены содержимого `h1` на тип турнира этот код начнёт подставлять в шаринг только тип («Cancha Abierta») без пола/уровня, что тоже не вполне информативно, но, что важнее, это неявная связка, которая случайно сломалась бы при любой будущей правке заголовка. Исправление: брать текст для шаринга из уже существующей на странице глобальной JS-переменной `tournament.nombre` (она же используется в `tournament-details.js` для текста календарного события, `text: tournament.nombre || ''`), а не парсить DOM `h1`. Сам `tournament.nombre` (пол · уровень) как текст не меняется и остаётся пригоден для шаринга.

### Нефункциональные
- i18n: новых пользовательских строк не добавляется — используются уже существующие ключи `enum.tipo.*` (все три локали заполнены). Проверить вручную, что фраза меняется при смене `Accept-Language`.
- Производительность/нагрузка: не затронуты (чисто шаблонная правка, без новых запросов).
- Безопасность: новых точек входа данных от пользователя нет.

## Вне скоупа
- `<title>`, `og:title`, `og:description`, meta-description и хлебная крошка (`breadcrumb-current`) на этой же странице по-прежнему используют `tournament.nombre` как есть (например, во вкладке браузера останется «Mixto · TODOS | 1-Padel») — заказчик просил изменить именно **главный заголовок на странице**, про `<title>`/SEO-метаданные и хлебную крошку речи не было. Трогать их в этой задаче не нужно — это отдельное решение с SEO-последствиями.
- Другие публичные страницы конкретных форматов (`/tournaments/king-of-court/{id}`, `/tournaments/americano/{id}`, `/tournaments/team-americano/{id}`, `/tournaments/team-playoff/{id}`) и админ-страницы (`admin/tournaments/details.html`, `admin/americano/*`) — у них своя разметка заголовка (используют тот же CSS-класс `badge-type`, но в другом HTML-контексте) и это другие экраны (live-табло/бэкофис, не «страница мероприятия» в смысле запроса заказчика). Не трогаются.
- Карточки турниров на `index.html`/`torneos.html` — уже в целевом состоянии, не трогаются (это референс, а не объект изменения).
- Поле `tournament.nombre` и логика его автогенерации (`Tournament.generateNombre()`, LFPT-374) не меняются — только то, что из него рендерится в заголовке этой страницы.

## Изменения в системе

### API
Нет изменений — это чисто фронтенд-правка существующего серверного рендеринга (Thymeleaf) и клиентского JS.

### БД
Нет изменений, миграция не нужна.

### UI
- `src/main/resources/templates/tournament-details.html`:
  - Блок `.tournament-title-section` (сейчас строки ~111-124): `<h1>` — переведённый тип турнира вместо `tournament.nombre`; из `.tournament-badges` убирается плашка `badge-type` (дублировала бы заголовок), остаются пол/уровень/формат участия/статус.
  - Инлайн-скрипт формирования ссылок шаринга (сейчас строка ~1118): источник текста — `tournament.nombre` (уже доступная JS-переменная) вместо `document.querySelector('h1').textContent`.
- `src/main/resources/static/css/tournament-details.css`: правило `.tournament-badges .badge-type` (строка ~1552) становится мёртвым после удаления соответствующего `<span>` из шаблона — убрать вместе с правкой шаблона, чтобы не копить неиспользуемый CSS.

## Критерии приёмки
- [ ] На `/torneo/{id}` главный `<h1>` показывает переведённое название типа турнира (а не пол/уровень) — проверено минимум для 2 разных `tipo` (например, `CANCHA_ABIERTA` и `KING_OF_COURT`).
- [ ] Под заголовком — вторичные плашки: пол, уровень, формат участия, статус; отдельной плашки с типом турнира больше нет (не задублирована с `<h1>`).
- [ ] Текст в `<h1>` меняется в соответствии с `Accept-Language` (es/ru/en) — проверено как минимум для 2 локалей на одном турнире.
- [ ] Клубные/собственные названия (`tournament.clubNombre`) по-прежнему выводятся как есть, не переведены (визуальная проверка блока «Club» — он не в составе изменённого блока, но критерий фиксирует, что правка его не задела).
- [ ] Кнопки «Отправить по WhatsApp» / «Отправить по Telegram» формируют ссылку с текстом на основе `tournament.nombre` (пол · уровень), а не с текстом нового `<h1>` — то есть шаринг не деградировал после смены содержимого заголовка.
- [ ] `./mvnw compile -DskipTests` проходит без ошибок.

## Edge cases
- Турнир без клуба/адреса — блок `.tournament-title-section` не зависит от этих полей, не затронут.
- Длинное/короткое название типа турнира на разных языках (например, "Clínica de Pádel" длиннее "Americano") — `<h1>` уже имеет `flex-wrap`/обычный блочный перенос в существующей вёрстке, дополнительных стилей под конкретную длину не требуется (визуально проверить, что не вылезает за карточку).
- `tournament.tipo` всегда non-null (обязательное поле при создании турнира, `TournamentType` enum без default/null-ветки) — отдельной обработки null не требуется, как и в уже существующем коде плашки `badge-type`, который на этом же выражении работал годами без NPE.

## Открытые вопросы
Нет открытых бизнес-вопросов. Технические решения (что делать с JS-шарингом, что не трогать `<title>`/breadcrumb/другие страницы) приняты самостоятельно и обоснованы в разделах «Изменения в системе» и «Вне скоупа» выше — они не меняют видимое заказчику поведение сверх того, что он попросил, и не требуют отдельного подтверждения.
