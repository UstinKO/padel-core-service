# LFPT-0472: Feature короткие ссылки для октябрьского календаря — редиректы /oct-tg, /oct-wa, /oct-ig с сохранением UTM-меток

## Статус
approved

## Источник
Клиентский запрос [specs/requests/LFPT-0472-oct-calendar-short-links.md](../requests/LFPT-0472-oct-calendar-short-links.md), issue [#472](https://github.com/UstinKO/padel-core-service/issues/472).

Telegram-сообщение (для reply): 4772

## Контекст / зачем

Маркетинг рассылает октябрьский календарь турниров по трём каналам (Telegram, WhatsApp, Instagram) и хочет короткие, легко произносимые/набираемые ссылки вместо длинного URL с UTM-параметрами. Каждый канал должен вести на один и тот же лендинг (главная страница `1-padel.com`), но с разной UTM-меткой источника — это нужно для разделения трафика по каналам в аналитике (см. также LFPT-0468 — Google Analytics уже подключён на сайте).

## Связь с MASTER.md

Фича не касается бизнес-логики продукта (роли, турниры, регистрации) — чисто техническая маршрутизация на публичном сайте. `MASTER.md` не затрагивается и не требует изменений.

## Требования

### Функциональные

- `GET /oct-tg` → HTTP-редирект на `https://1-padel.com/?utm_source=telegram&utm_medium=social&utm_campaign=calendar_october`
- `GET /oct-wa` → HTTP-редирект на `https://1-padel.com/?utm_source=whatsapp&utm_medium=message&utm_campaign=calendar_october`
- `GET /oct-ig` → HTTP-редирект на `https://1-padel.com/?utm_source=instagram&utm_medium=social&utm_campaign=calendar_october`
- Редирект — настоящий HTTP-редирект (`Location`-заголовок на полный целевой URL с query-string), не JS/meta-refresh — чтобы UTM-параметры были в адресной строке браузера сразу после перехода, до любой клиентской навигации.
- Доступ анонимный (без логина) — текущие три коротких пути не входят ни в один `permitAll()`-паттерн `SecurityConfig`, а дефолт — `.anyRequest().authenticated()`, поэтому без явного добавления в `permitAll()` анонимный переход по ссылке упёрся бы в `/login`.

### Нефункциональные

- Код статуса редиректа: **302 (Found / временный)**, не 301. Техническое решение (не оставлено на усмотрение, но обосновывается здесь, п.3 `GIT_WORKFLOW.md`): кампания привязана к конкретному месяцу (октябрь) и целевой URL/UTM-разметка могут измениться или ссылка может быть переиспользована под другую кампанию позже — постоянный 301 рискует быть закэширован браузерами/прокси навсегда, что осложнит будущую переразметку того же короткого пути. Spring MVC `"redirect:..."` отдаёт 302 по умолчанию — дополнительных действий не требуется.
- i18n: не применимо — редирект не рендерит пользовательский текст.
- Безопасность: нет новой точки входа данных от пользователя (нет параметров, нет записи в БД) — только статическая маршрутизация на предопределённые захардкоженные URL. CSRF/rate-limit не затрагиваются (простой `GET` без побочных эффектов).

## Вне скоупа

- Общий механизм управления короткими ссылками (админка, БД-таблица, произвольные алиасы) — не делаем, три ссылки захардкожены в коде. Если в будущем понадобится больше ссылок/самостоятельное управление ими без деплоя — отдельная задача.
- Изменения в `nginx`/Cloudflare — не требуются и не делаются: редирект реализован на уровне приложения (Spring MVC controller), что проходит через обычный git-flow и деплой `deploy.yml`. Серверные правки `nginx`/`CrowdSec` шли бы отдельным, явно согласованным процессом (`CLAUDE.md` § Серверный стек, `GIT_WORKFLOW.md` §7) — здесь это не нужно.
- Отслеживание кликов/статистика по переходам (кроме того, что увидит GA по UTM) — не делаем.

## Изменения в системе

### API

Новый `@Controller` (например `controller/view/MarketingRedirectController.java`), один обработчик на все три коротких пути, таблица соответствий short-path → target-URL как `Map<String, String>` (легко расширить на будущие кампании без копипасты метода):

| Method | URL | Ответ |
|---|---|---|
| GET | `/oct-tg` | 302 → `https://1-padel.com/?utm_source=telegram&utm_medium=social&utm_campaign=calendar_october` |
| GET | `/oct-wa` | 302 → `https://1-padel.com/?utm_source=whatsapp&utm_medium=message&utm_campaign=calendar_october` |
| GET | `/oct-ig` | 302 → `https://1-padel.com/?utm_source=instagram&utm_medium=social&utm_campaign=calendar_october` |

### БД

Не требуется.

### UI

Не требуется (чистый редирект, ни один шаблон не затронут). Задача — backend-only (`GIT_WORKFLOW.md` §1.4: только `src/main/java/**` + `SecurityConfig`).

### Конфигурация безопасности

`SecurityConfig.securityFilterChain` — добавить `/oct-tg`, `/oct-wa`, `/oct-ig` в список `permitAll()` рядом с остальными публичными путями.

## Критерии приёмки

- [ ] `GET /oct-tg` без авторизации возвращает `302` с заголовком `Location: https://1-padel.com/?utm_source=telegram&utm_medium=social&utm_campaign=calendar_october`
- [ ] `GET /oct-wa` без авторизации возвращает `302` с заголовком `Location: https://1-padel.com/?utm_source=whatsapp&utm_medium=message&utm_campaign=calendar_october`
- [ ] `GET /oct-ig` без авторизации возвращает `302` с заголовком `Location: https://1-padel.com/?utm_source=instagram&utm_medium=social&utm_campaign=calendar_october`
- [ ] Ни один из трёх путей не конфликтует с существующим маппингом (проверено `grep` по контроллерам — свободны)
- [ ] Существующие публичные и защищённые маршруты не затронуты (регрессия по соседним `permitAll()`-путям не ожидается — чисто аддитивное изменение)

## Edge cases

- Запрос с дополнительным query-string (`/oct-tg?foo=bar`) — не описан в запросе заказчика, лишние параметры из входящего запроса не нужно переносить на целевой URL (целевые UTM уже фиксированы и полны); `foo=bar` просто игнорируется.
- `POST`/другие методы на `/oct-tg` и т.п. — не описаны, не поддерживаются (только `GET`, как и сам сценарий клика по ссылке).
- Конкурентный доступ / несколько реплик (Docker Swarm) — не релевантно, обработчик stateless, без записи в БД.

Нет открытых вопросов, требующих решения заказчика — задача полностью технически однозначна (три фиксированных URL из запроса, стандартный HTTP-редирект).
