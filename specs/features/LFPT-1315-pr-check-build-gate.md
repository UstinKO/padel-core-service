# LFPT-1315: Fix итоговый check build — учитывать все обязательные проверки PR Check

## Статус

approved

## Источник

Техническая постановка по [GitHub issue #1315](https://github.com/UstinKO/padel-core-service/issues/1315). Основание — пункт П1 исследования LFPT-1220. [Разбор PR Check](../../docs/ci-cd-optimization-analysis.md#п1-build-ждёт-frontend-итоговый-check-не-учитывает-browser-marketing).

## Контекст / зачем

В `master` на `dc7f71cf` серверная сборка (`build`) и браузерные проверки (`browser-marketing`) ждут `frontend`, хотя каждый job делает собственный checkout и готовит собственное окружение. Затем эти два job выполняются параллельно. Автомерж смотрит на результат check-run `build` на текущем head PR, поэтому успешная серверная сборка допускает PR к повторной проверке, даже если `browser-marketing` ещё выполняется или завершился ошибкой. [PR Check](../../.github/workflows/pr-check.yml) · [Отбор кандидатов](../../.github/bin/pipeline-select.sh).

Цель — сделать `build` итогом всех обязательных проверок и сократить время ожидания за счёт одновременного запуска независимых jobs.

## Связь с MASTER.md

Задача касается только CI и допуска к автомержу. [MASTER.md](../MASTER.md) описывает бизнес-правила приложения.

## Требования

### Функциональные

1. **Распараллелить проверки.** Переименовать текущий job `build` в `backend`. Удалить `needs: frontend` у `backend` и `browser-marketing`. `frontend`, `backend` и `browser-marketing` доступны планировщику одновременно. Порядок фактического старта зависит от доступности раннеров.
2. **Перенести серверный job целиком.** В `backend` входят Maven `clean verify`, проверки артефактов модулей и OpenAPI, проверки автоматизации, проверка пакета выпуска, изолированный UI v2 с репетицией релиза и сценариями кругового турнира. Перенести вместе с ними настройки PostgreSQL, обработку ошибок, выгрузку `openapi-dto-probe` и `modular-pilot-qa`, а также остановку preview. `frontend` и `browser-marketing` выполняют свои текущие команды, используют свои окружения и публикуют свои отчёты.
3. **Добавить итоговый job `build`.** Идентификатор job и имя check-run в обычном PR Check — буквально `build`. Указать прямые зависимости `needs: [frontend, backend, browser-marketing]` и условие уровня job `if: ${{ always() }}`. Проверка успешна, только если каждый `needs.<job>.result` равен `success` и все три job подтвердили одну ревизию. При любом другом результате вывести имя каждого обязательного job и его итог, затем завершить шаг ненулевым кодом. Итоговый job только сводит результаты, без checkout, базы и сборки. [Семантика `needs`](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#needs-context) · [Обязательные проверки GitHub](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks#handling-skipped-but-required-checks).
4. **Подтвердить единую ревизию.** В обычном PR использовать стандартную ревизию события `pull_request`. При `workflow_call` использовать переданный `ref` для всех рабочих jobs. Предпочтительный для этой задачи вариант — сразу после checkout каждый job фиксирует `git rev-parse HEAD` и отдаёт его как job output. Итоговый `build` сравнивает три непустых SHA и завершает работу с ошибкой при расхождении. Это защищает от сдвига `refs/pull/N/merge` между checkout и смешения ревизий при перезапуске отдельных jobs.
5. **Поддержать оба входа.** Сохранить имя workflow `PR Check`, запуск по `pull_request` и `workflow_call` с обязательным строковым `ref`. Оркестратор вызывает тот же workflow с `refs/pull/N/merge` либо с SHA перестроенной ветки. Успех повторного `verify` требует прохождения всех обязательных jobs. Проверки актуальности head и `master` перед мержем продолжают выполняться в оркестраторе. [Вызов из оркестратора](../../.github/workflows/pipeline-merge.yml#L128-L167).

### Нефункциональные

- **Производительность.** Ориентир — около 1:45 экономии на обычном PR по замеру от 24 ноября. Сравнить интервал от старта первого обязательного job до окончания `build` на сопоставимых прогонах до и после изменения. Для исходного workflow использовать окончание последнего из трёх обязательных jobs. Отдельно зафиксировать ожидание раннера. Приложить ссылки на прогоны и объяснить заметное расхождение с оценкой. [Исходный замер](../../docs/ci-cd-optimization-analysis.md#pr-check--1410).
- **Диагностика.** Из журнала `build` должно быть видно, какие обязательные jobs завершились успешно и почему проверка заблокирована. При расхождении ревизий вывести SHA по jobs.
- **Среда.** Использовать существующие разрешения GitHub Actions и изолированные тестовые окружения. Проверки отказов воспроизвести в тестовом PR без меток автомержа или в отдельном временном workflow без вызова мержа и деплоя.

## Порядок реализации

1. Перенести текущий `build` в `backend` и убрать зависимости от `frontend` у `backend` и `browser-marketing`. Сохранить существующие команды, порядок шагов внутри каждого job и обработчики ошибок.
2. В трёх jobs сразу после checkout добавить получение фактического SHA и объявить его в job outputs. Для обычного PR сверить его с ревизией события. Для повторной проверки сверить, что все checkout используют входной `ref`.
3. Создать итоговый `build` с прямыми зависимостями на три job. Сначала проверить статусы, затем наличие и совпадение SHA. Напечатать сводку и завершить шаг с ошибкой при любом нарушении.
4. Проверить оба входа workflow и потребителей результата. В обычном PR проверить имя check-run через тот же запрос Checks API, что и в скрипте отбора. В повторном вызове проверить итог вызывающего job `verify`. Обновить описание автомержа после подтверждения поведения.

## Критерии приёмки

- [ ] В обычном PR `backend` и `browser-marketing` доступны к запуску до завершения `frontend`. Серверная сборка, браузерные проверки, репетиция выпуска и артефакты присутствуют в прогоне.
- [ ] При трёх `success` и одинаковых непустых SHA итоговый check-run называется `build`, получает `success` и доступен тому же запросу Checks API на текущем head PR, который использует `pipeline-select.sh`.
- [ ] Падение каждого из трёх обязательных jobs по отдельности даёт `failure` в `build`, даже когда два остальных завершились успешно. Особенно проверить случай, когда `backend` уже зелёный, а `browser-marketing` завершается ошибкой позже.
- [ ] `skipped` или `cancelled` у обязательного job даёт `failure`, если GitHub выполняет итоговый job. При отмене всего прогона check `build` не получает `success`. До завершения обязательных jobs `build` также не получает `success`.
- [ ] Три успешных job с разными SHA или с пустым SHA у одного завершаются ошибкой в `build`. При совпадении SHA проверяемая ревизия видна в журнале.
- [ ] При `workflow_call` проверены оба формата `ref` — `refs/pull/<N>/merge` и SHA. Подтвердить успех вызывающего `verify` при зелёных проверках и его неуспешный итог при ошибке обязательного job. Для этого достаточно безопасного тестового вызова того же reusable workflow.
- [ ] По ссылкам на сопоставимые прогоны видно устранение ожидания `frontend` на критическом пути. Фактическая длительность зафиксирована и сопоставлена с ориентиром 1:45.

### Порядок проверки

1. На успешном прогоне зафиксировать SHA, ссылки на run и артефакты, время старта каждого job и итог `build`. Сверить фактические имена check-runs на head PR запросом `gh api 'repos/UstinKO/padel-core-service/commits/<head-sha>/check-runs?per_page=100'`, подставив SHA из PR.
2. Проверить ошибку каждого обязательного job, неожиданный пропуск, отмену и несовпадение SHA на временном варианте workflow с теми же `needs` и той же логикой итогового шага. В примерах отказа достаточно коротких jobs, которые управляемо воспроизводят нужный статус. Для `cancelled` и `skipped` сверить фактические статусы GitHub Actions в журнале запуска.
3. Вызвать reusable workflow из временного вызывающего workflow с job `verify` и указанным `ref`. Зафиксировать результат вызывающего job на успешном и неуспешном прогоне. Проверки выполнять без `pipeline:ready` и без шагов мержа и деплоя.
4. Приложить к результатам ссылки на прогоны, итоговые статусы и сравнение длительности. Временные изменения для проверки отказов удалить из итогового дифа.

## Edge cases

- **Отмена всего запуска.** GitHub управляет завершением jobs и может остановить прогон до выполнения `build`. Для допуска к автомержу нужен именно `success`. [Отмена workflow](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-cancellation).
- **Новый push или повторный запуск.** Проверять результат на актуальном head PR. При повторе только упавших jobs SHA из предыдущей попытки допустим, если он совпадает со всеми остальными. При расхождении повторить полный прогон.
- **Старые зелёные checks на открытых PR.** Имя `build` сохраняется, поэтому старый результат не доказывает, что браузерные проверки учтены. Для проверки включения новой схемы на уже открытом PR нужен свежий прогон с обновлённым workflow и подтверждённым графом jobs.
