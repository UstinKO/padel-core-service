# LFPT-375: Клубные аккаунты — модель данных (Owner↔Club) и новая роль

## Статус
draft

## Источник
GitHub issue [#375](https://github.com/UstinKO/padel-core-service/issues/375) — прямая техническая постановка от архитектора/заказчика (клиентский запрос "доработка клубных аккаунтов и создания турниров", клуб Black Padel, пункты 3-4). Первая из трёх связанных задач: #375 (эта, модель данных) → #376 (изоляция доступа, зависит от #375) → #377 (пилот Black Padel, зависит от обоих).

Telegram-сообщение (для reply): 4320

## Контекст / зачем
Сейчас `Owner` не связан с `Club` никак — любой владелец/организатор глобален и видит все турниры всех клубов в админке. Клиент (клуб Black Padel) должен получить собственный аккаунт, ограниченный только своими турнирами. Эта задача — только фундамент (поле связи + новая роль), без изменения авторизации: сама изоляция доступа — предмет отдельной задачи #376, чтобы не смешивать миграцию схемы с изменением поведения безопасности в одном PR.

## Связь с MASTER.md
Таблица ролей в [specs/MASTER.md § Роли пользователей](../MASTER.md#роли-пользователей) перечисляет `ROLE_OWNER`/`ROLE_SUPER_ADMIN`/`ROLE_ORGANIZER` без клубного скоупа — эта фича добавляет техническую возможность (поле + enum-значение), но **не меняет поведение существующих ролей и не вводит ещё работающую клубную роль** (см. критерии приёмки issue: "поведение существующих аккаунтов не изменилось"). Поэтому `MASTER.md` в этом PR не обновляется — новая роль пока не задействована ни в одной проверке доступа. Обновление таблицы ролей в `MASTER.md` (описание, что `CLUB_ADMIN` видит только свой клуб) — задача #376, когда поведение реально появится.

## Требования

### Функциональные
- `Owner.clubId` — новое поле `Long`, nullable, без FK-констрейнта на `club_db` (см. "Технические решения" ниже).
- `OwnerRepository` — новый метод `findByClubId(Long clubId)` (и `List<Owner> findByClubIdAndIsActiveTrue(Long clubId)`, если понадобится в #376) — раз issue упоминает "клубо-скоуп-запросы" как то, чего сейчас нет; добавить хотя бы базовый `findByClubId`, не проектируя вперёд то, что реально понадобится только в #376 (YAGNI — не добавлять больше одного метода без конкретного потребителя).
- `OwnerRole` — новое значение `CLUB_ADMIN` (см. открытый вопрос №1 — точное решение о семантике роли блокирует реализацию).
- Существующие `Owner`-записи получают `club_id = NULL` при миграции, роль не меняется.

### Нефункциональные
- i18n: новых пользовательских строк нет — это чисто модельная задача, `CLUB_ADMIN` нигде не отображается в UI до #376.
- Безопасность: новых точек входа данных от пользователя нет (поле не выставляется ни через одну форму/API в этой задаче).
- Производительность: не применимо (одна nullable-колонка, без нагрузки).

## Технические решения (принято самостоятельно, см. GIT_WORKFLOW.md §3)
- **Без FK-констрейнта на `club_db.id`.** В проекте уже есть прецедент именно такой связи — `Tournament.clubId` (`Long`, не JPA-связь, без FK) — по словам issue, "единственная существующая связь турнира с клубом". Для консистентности стиля проекта и чтобы не создавать асимметрию (турнир→клуб без FK, а owner→клуб с FK) — тот же паттерн для `Owner.clubId`. Также снижает связанность на будущее разделение на микросервисы (Identity/Owner и Tournament-core в разных доменах по `docs/microservices-migration-plan.md`), где жёсткий FK между будущими отдельными БД всё равно не переживёт разделение.

## Вне скоупа
- Любая логика авторизации/изоляции по клубу — #376.
- UI для назначения `clubId`/`CLUB_ADMIN` (форма создания/редактирования owner) — #376 или #377, не эта задача.
- Обновление `MASTER.md` — до тех пор, пока роль не используется в реальной проверке доступа (см. "Связь с MASTER.md").
- Создание клубного аккаунта Black Padel — #377.

## Изменения в системе

### API
Нет изменений — ни один существующий endpoint не меняет контракт. `Owner.clubId` не выставляется через `POST/PUT /api/owners/**` в этой задаче (соответствующий DTO/маппер не трогаем, если только не потребуется для юнит-теста модели напрямую через репозиторий).

### БД
Новая Liquibase-миграция `v1.48-add-club-id-to-owner.yaml` (следующий номер после `v1.47-add-nivel-categories.yaml`), зарегистрированная в конце `changelog-master.yaml`:
- `ALTER TABLE owners_db ADD COLUMN club_id BIGINT NULL`.
- Без индекса в этой задаче — `findByClubId` в текущем виде не является горячим путём (нет ни одного вызывающего до #376); если #376 сделает его частым, индекс добавляется там, где он реально нужен, а не заранее.

### UI
Нет изменений.

## Критерии приёмки
- [ ] Миграция `v1.48-add-club-id-to-owner.yaml` добавляет nullable `owners_db.club_id`, зарегистрирована в `changelog-master.yaml`, применяется без ошибок на чистой БД и поверх текущих данных.
- [ ] `OwnerRole` содержит новое значение (имя — см. открытый вопрос №1) в дополнение к `SUPER_ADMIN`, `ORGANIZER`, `ADMIN`.
- [ ] `Owner.getClubId()`/`setClubId()` (через Lombok) читает/пишет колонку — покрыто тестом на уровне репозитория (`@DataJpaTest` или эквивалент по стилю проекта).
- [ ] Существующие `Owner`-записи после миграции имеют `club_id = NULL`, `role` не изменился.
- [ ] Логин и доступ к `/admin/**` для существующих `SUPER_ADMIN`/`ORGANIZER`/`ADMIN` аккаунтов работает как раньше (ручная проверка + существующие тесты `OwnerService`/`AuthController`, если есть, не должны сломаться).
- [ ] `./mvnw verify` проходит целиком (регрессия по всему проекту, не только по новому коду).

## Edge cases
- `clubId = NULL` для всех ролей, включая будущую клубную роль (пока не назначена никому в этой задаче) — не должно приводить к NPE ни в одном месте, где сейчас читается `Owner.getRole()` (новое поле нигде не читается в проверках этой задачи — риск в принципе отсутствует, но стоит явно прогнать существующие тесты `AmericanoService`/`OwnerService`, использующие `OwnerRole`, чтобы убедиться, что `.equals(OwnerRole.ORGANIZER)`-паттерн не превращается в exhaustive switch, который бы сломался на новом enum-значении).
- Повторное применение миграции (idempotency) — стандартный Liquibase changeset, `changeSetId` уникален, конфликтов с `v1.47` нет.

## Открытые вопросы

Issue #375 явно помечает эти два вопроса как **требующие согласования с пользователем**, не как техническую деталь на усмотрение реализующего:

1. **Новая роль или расширение существующей?** Issue рекомендует: отдельное новое значение `OwnerRole` (рабочее имя `CLUB_ADMIN`) поверх остающейся `ORGANIZER`, чтобы #376 мог авторизовать по явной роли, а не по одному только наличию `clubId`. Альтернатива из issue: любой `Owner` с непустым `clubId`, независимо от роли (в т.ч. существующий `ORGANIZER`), считается клубным. Нужно подтверждение, какой вариант закладывать в модель — само имя enum-значения и то, будет ли `clubId` без роли уже что-то значить, зависит от ответа.
2. **Что происходит с существующими `ORGANIZER`/`ADMIN` без `clubId`?** Issue рекомендует самый безопасный дефолт — они остаются глобальными (как сейчас), клубное ограничение будущего #376 применяется только там, где `clubId` явно проставлен (и/или роль — в зависимости от ответа на вопрос №1). Нужно подтверждение этого дефолта, поскольку он определяет семантику `clubId = NULL`, которую закладывает миграция этой задачи.

До ответа на оба вопроса статус остаётся `draft` — реализация (Developer) не начинается, чтобы не закладывать в схему семантику, которую потом придётся откатывать миграцией.
