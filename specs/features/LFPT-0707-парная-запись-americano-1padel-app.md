# LFPT-0707: Парная запись Americano в 1Padel.App

## Статус
approved

## Источник
Клиентский запрос [specs/requests/LFPT-0707-парная-запись-americano-1padel-app.md](../requests/LFPT-0707-парная-запись-americano-1padel-app.md) (Telegram, отправитель — customer, переслано от Evgeny_754, `telegram_launch_message_id: 5463`). Ссылка заказчика на подготовленный README/ТЗ: https://github.com/eugenegwork-coder/1padel-app/tree/main/updates/pair-registration — использован только как описание требований (сверено построчно при написании этой спеки); готовый патч/исходники из этого репозитория не применяются — реализация ведётся самостоятельно, в конвенциях `mobile-app/`, по образцу уже смерженной индивидуальной записи (LFPT-0660/PR #661).

Зависит от #706 (`feature/LFPT-0706`, уже в этой ветке): расширение `GET /players/tournaments/{id}/my-registration` полями `registrationId`/`status`/`waitlistPosition`/`registrationDate`/`isDoubleRegistration`.

## Контекст / зачем

Веб-клиент 1Padel.App (`mobile-app/`, Expo/React Native, сборка раздаётся на `/app/`) уже поддерживает индивидуальную запись внутри приложения (LFPT-0660) для `KING_OF_COURT`/`AMERICANO` (modality `INDIVIDUAL`)/`PADEL_CLINIC`/`CANCHA_ABIERTA`. Для парных мероприятий (`modality: DOBLES`) кнопка до сих пор ведёт на сайт (`openWebsite(selected.websiteUrl)`). Задача — замкнуть внутри приложения парную запись для Americano-форматов: классический `AMERICANO` с `modality: DOBLES` и `AMERICANO_TEAMS` (Team Americano/Team Playoff — один тип турнира, разные админ-экраны, см. `.claude/CLAUDE.md`).

Серверная часть почти полностью готова и переиспользуется без изменений: `POST /api/tournaments/double/{tournamentId}/register` (пара сразу — партнёр, существующий по ID или новые данные без email, LFPT-0687), `POST .../register-solo` (`SEARCH`/`ADD_LATER`), `POST .../add-partner`, `GET .../looking-for-partner`, `POST .../propose-pair/{targetRegistrationId}`, `GET /api/players/search?query=&tournamentId=`. Единственное серверное изменение — LFPT-0706 (уже в этой ветке).

## Связь с MASTER.md

Новых инвариантов не вводится. Используются существующие (раздел «Флоу парной регистрации», «Статусы регистрации на турнир»):
- Пара (с партнёром как с аккаунтом, так и без) сразу получает `CONFIRMED`/`WAITLIST` — без промежуточного статуса ожидания (LFPT-0687). Экран не ждёт email-подтверждения партнёра.
- Соло-регистрация "ищу пару"/"добавлю партнёра позже" (`SOLO_SEARCH`/`SOLO_ADD_LATER`) — свой дедлайн и правила перевода в резерв (старт минус 24 часа для `SOLO_ADD_LATER`), независимо от попадания в основной список/резерв.
- Обязательный контакт (`PlayerPadel.hasValidContact()`) и ограничение по уровню «±1 ступень» (`TournamentLevelPolicy`, не применяется к `TODOS`/`PRINCIPIANTES`/диапазонам/`SUMA_*`, но применяется к обычным категориям Americano) — клиент не дублирует проверки, только показывает серверный отказ (`needContact`/`needLevel`), как и индивидуальная запись (LFPT-0660).
- Контакты партнёра по сайту не публикуются даже своему игроку через `my-registration` (LFPT-0706) — экран показывает только имя/фамилию партнёра, не телефон/Telegram.

MASTER.md не меняется.

## Требования

### Функциональные

1. Новый предикат `isPairAmericanoEvent(event)` в `mobile-app/src/pairBooking.ts`: `event.modality === 'DOBLES' && (event.type === 'AMERICANO' || event.type === 'AMERICANO_TEAMS')`. На экране деталей (`PlayerScreen`) для таких событий с открытой регистрацией кнопка открывает `PairBookingScreen` внутри приложения вместо перехода на сайт. Остальные события (включая `DOBLES` для `CANCHA_ABIERTA`/`PADEL_CLINIC`, если такие создаются, и всё с закрытой регистрацией) — поведение не меняется.
2. Неавторизованный пользователь — тот же механизм отложенного намерения, что и у индивидуальной записи: существующий `bookingIntent.ts` переиспользуется (намерение — просто ID события, флоу записи определяется по актуальному `event.modality`/`type` после открытия, а не сохраняется отдельно для пары).
3. Экран при открытии выполняет свежую проверку (`pairBooking.load`): детали события (`GET /api/public/tournaments/{id}`), **своя** регистрация на это конкретное событие (`GET /players/tournaments/{id}/my-registration`, расширенный в LFPT-0706 — не список `/api/players/me/tournaments`, в котором нет данных о партнёре), статус контакта.
4. Если активной регистрации нет — выбор варианта (все три ведут к ровно одному POST при подтверждении):
   - **«Есть партнёр»**: поиск существующего игрока (`GET /api/players/search?query=&tournamentId=`, не короче 2 символов, явный выбор из списка; себя и уже выбранного — убрать из показа) **или** ввод нового партнёра (имя и фамилия обязательны, WhatsApp обязателен, Telegram — опционально, email не запрашивается и не передаётся). Подтверждение → `POST /api/tournaments/double/{id}/register` с `PartnerRegistrationDto` (`existingUserId`+`isExistingUser: true` либо `nombre`/`apellido`/`telefono`/`telegramUsername`).
   - **«Ищу партнёра на месте»**: без данных партнёра. Подтверждение → `POST .../register-solo {soloType: 'SEARCH', shareContacts}` (`shareContacts` — чекбокс, по умолчанию выключен — см. п. 7). После успеха экран показывает список `GET .../looking-for-partner` (кроме себя) с возможностью «предложить пару» → `POST .../propose-pair/{targetRegistrationId}` (это email-приглашение другому игроку, не мгновенное объединение — см. «Вне скоупа»).
   - **«Добавлю партнёра позже»**: без данных партнёра, явный текст о дедлайне (старт минус 24 часа, после — перевод соло-заявки в резерв). Подтверждение → `POST .../register-solo {soloType: 'ADD_LATER'}`.
5. Если активная регистрация уже существует без партнёра (`status` ∈ `{SOLO_SEARCH, SOLO_ADD_LATER}`) — экран предлагает тот же выбор «есть партнёр» (поиск/новый), подтверждение → `POST .../add-partner` (не `.../register`). Для `SOLO_SEARCH` дополнительно показывается список `.../looking-for-partner` с предложением пары, как в п. 4.
6. Если активная регистрация уже `CONFIRMED`/`WAITLIST` — показывается статус, позиция в листе ожидания (если есть) и имя партнёра (`partnerFirstName`/`partnerLastName` из `my-registration`, если `hasRegisteredPartner`); повторная отправка не предлагается. Кнопка «поделиться» (п. 9) — если `isDoubleRegistration` и партнёр уже есть.
7. Любая другая активная регистрация (`WAITLIST_INVITED`, `PENDING_PARTNER`, `PARTNER_INVITED`, `PAIR_REGISTERED`, `SOLO_EXPIRED`, легаси `CANCELLED`/`PARTICIPATED` на этом турнире и т.п. — состояния, которые в этот флоу не заводятся, но теоретически могут быть унаследованы от легаси-данных) — экран не пытается трактовать их как один из вариантов выше: нейтральное сообщение о текущем статусе и переход на сайт для управления записью.
8. Экран обзора перед подтверждением показывает: себя, партнёра (имя/фамилия выбранного/введённого — для вариантов «ищу»/«добавлю позже» явно указано «партнёра пока нет»), событие (тип, дата, клуб), стоимость за участника, актуальный дедлайн отмены (`cancellationDeadline`/дефолт старт-24ч — переиспользуется `cancellationDeadline()` из `individualBooking.ts`), финансовые условия отмены (переиспользуется та же формулировка, что у индивидуальной записи для Americano — штраф «−10 очков за опоздание» показывается и здесь, т.к. правило относится к формату `AMERICANO`/`KING_OF_COURT`, не к модальности). Запись не создаёт платежа.
9. После завершённой **парной** регистрации (есть оба участника, `CONFIRMED`/`WAITLIST`) — кнопка «Поделиться» формирует ссылку `{websiteBase}/app/?event={id}` и открывает системный выбор приложения через `Linking.openURL` с готовым текстом для WhatsApp (`https://wa.me/?text=...`) и Telegram (`https://t.me/share/url?url=...&text=...`); отдельные кнопки для каждого канала. Приложение не отправляет сообщения автоматически — только открывает системный диалог/приложение с предзаполненным текстом, отправка — действие пользователя.
10. Защита от повторной отправки, обрыва связи, смены условий и смены аккаунта — по той же модели, что и `individualBooking.ts` (переиспользуются примитивы `BookingError`, `bookingQuote`, `cancellationDeadline`, `parseBookingReceipt`): явное согласие чекбоксом перед подтверждением; не более одного `POST`/`PATCH` за подтверждение (`BUSY` блокирует повтор); обрыв связи переводит в `UNCERTAIN` и предлагает `reconcile` вместо повторной отправки; изменение цены/условий/мест/дедлайна между проверкой и подтверждением — `CHANGED`, требуется новая проверка и согласие; `401` на мутации не повторяет её автоматически (`REVIEW_REQUIRED`); смена аккаунта во время незавершённой проверки не может создать запись новому аккаунту данными старой сессии (`sessionVersion`).
11. `needContact`/`needLevel` — как в LFPT-0660: форма телефона/Telegram с сохранением через существующий `PATCH /api/players/me/contact`, либо сообщение и ссылка на профиль сайта.

### Нефункциональные

- **i18n**: новые строки — `mobile-app/src/pairCopy.ts` (ru/es/en), отдельный словарь по той же схеме, что `bookingCopy.ts`.
- **Безопасность**: identity только через Bearer access-токен (как и везде в `auth.ts`); поиск партнёра (`/api/players/search`) не раскрывает контакты других игроков в ответе (эндпоинт и так не отдаёт телефон/Telegram в `PlayerResponseDto`, см. текущую реализацию — только имя/фамилию/уровень); никакого автоматического повтора мутаций.
- **Производительность**: не применимо — объём запросов на пользователя не растёт относительно уже существующих экранов (переиспользуются те же паттерны, что у индивидуальной записи).

## Вне скоупа

- Принятие предложения о паре (`accept-pair` по токену из email) — только через сайт/email, как и сейчас; в приложении нет UI для входящих предложений.
- Отмена парной регистрации через приложение — остаётся на сайте (не входит, как и индивидуальная отмена изначально не входила в LFPT-0660).
- Отображение партнёра/статуса пары в списке «Мои мероприятия» (`MyEventsScreen`, `GET /api/players/me/tournaments`) — этот список-эндпоинт не отдаёт данные партнёра и не меняется в этой задаче; статус и партнёр видны при открытии `PairBookingScreen` для конкретного события.
- `CANCHA_ABIERTA`/`PADEL_CLINIC` в режиме `DOBLES` (если такие события когда-либо создаются) — вне скоупа; затронуты только `AMERICANO`/`AMERICANO_TEAMS`.
- Применение патча/исходников из `eugenegwork-coder/1padel-app` — см. «Источник»; README использован только как перечень требований.
- Изолированный тестовый режим `/?screen=pair-booking-test` — не создаётся в этой задаче (у индивидуальной записи он был явным пунктом ТЗ; здесь заказчик его не просил, а дублировать экран без необходимости — расширение скоупа).

## Edge cases

- Поиск партнёра возвращает самого пользователя или игрока, уже выбранного/уже зарегистрированного на этот турнир — такие кандидаты не показываются (сервер уже исключает текущего игрока по `excludeId`; дубли по уже выбранному — фильтр на клиенте).
- Новый партнёр без WhatsApp — отказ до отправки на сервер, запрос не уходит (сервер тоже не требует `telefono` строго, но ТЗ требует WhatsApp обязательным для нового партнёра — клиентская валидация).
- Мероприятие стало недоступно (`registrationOpen=false`, не `REGISTRO_ABIERTO`, либо уже началось) между списком и экраном записи — явный блок, без попытки `POST`, как и у индивидуальной записи.
- Ответ сервера неожиданной формы (`success` не булево, `status` не из известного множества, отрицательная позиция, HTML вместо JSON) — не трактуется как успех, уходит в `UNCERTAIN`, не создаёт ложного подтверждения.
- `propose-pair` на уже недоступную цель (у неё уже появился партнёр/она отменила регистрацию) — серверная ошибка показывается как есть, без повторной автоматической попытки.
- Два параллельных подтверждения на разные турниры одновременно — не блокируют друг друга (защита от повтора в `pairBooking.ts` привязана к конкретному `tournamentId`, как и в `individualBooking.ts`).

## Открытые вопросы

Нет открытых вопросов, требующих решения заказчика. README заказчика по ссылке в «Источнике» содержит подробное, уже согласованное описание требований — оно использовано для заполнения этой спеки. Технические решения, оставленные на усмотрение реализующего:
- Матчмейтинг-список («ищу партнёра») ограничен показом + предложением пары (`propose-pair`, email-приглашение) — приём входящих предложений внутри приложения не реализуется (см. «Вне скоупа»): это самостоятельная, более крупная задача (нужен UI для входящих приглашений, которого в проекте нет даже на сайте за пределами email-ссылки).
- Тестовый режим наподобие `/?screen=individual-booking-test` для пары не создаётся — заказчик не просил, площадка для ручной QA по-прежнему тестовое мероприятие на деплое.
