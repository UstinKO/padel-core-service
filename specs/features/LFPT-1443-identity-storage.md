# LFPT-1443: Feature многомодульный монолит, фаза 6 — выделить хранение идентичности и доступа

## Статус
approved

## Источник
[Issue #1443](https://github.com/UstinKO/padel-core-service/issues/1443). Техническая постановка по утверждённой фазе 6. Родитель [#1051](https://github.com/UstinKO/padel-core-service/issues/1051).

## Контекст / зачем
Отделить представление пользователя и владельца от методов PostgreSQL и JPA при проверках доступа.

## Связь с MASTER.md
[MASTER](../MASTER.md) определяет роли, границы клубного доступа, регистрацию, турнирные состояния и хранение истории вместе с подтверждённым изменением. Сценарии сохраняют текущие инварианты. Зависимости [#1442](https://github.com/UstinKO/padel-core-service/issues/1442).

## Требования

### Функциональные

- Разобрать связь Owner, PlayerPadel, UserDetails, сессий, JWT, контактов и токенов. Разделить работу на атомарные PR по реальному графу сущностей.
- Подготовить нейтральный principal и сценарии учётных записей, перенести подготовленное хранение. Сохранить данные сессии и ошибки входа/доступа.

### Нефункциональные
- Java release 17, JDK 21 в CI, одна транзакционная граница и один Boot JAR.
- Каждый PR проходит полный verify на отдельной PostgreSQL, артефактные и архитектурные guards, runtime/релевантный браузер и проверку совместимости предыдущего релиза.
- Сохраняются действующие права, i18n ES/RU/EN и внешние контракты. Новых пользовательских строк нет.

## Вне скоупа
Ручной релиз остаётся обычным. Физическая миграция PostgreSQL, Swarm и изменения бизнес-правил вне задачи.

## Изменения в системе

### API
Прежние MVC/HTTP/WS входы, поля, статусы и права.

### БД
Прежняя PostgreSQL и schema. Отдельная тестовая БД для интеграции.

### UI
Действующие клиенты используют прежние данные. Приёмочные сценарии запускаются через штатные входы.

### Документация
[План фазы 6](../../docs/modular-monolith/phase-6/README.md), документация фактических границ, затронутые endpoints и техническая карта при необходимости.

## Критерии приёмки

- [ ] Роли, клубные права, login, OAuth, session, JWT и связанные сценарии подтверждены на прежнем и текущем артефактах.
- [ ] Подготовленные JPA-части имеют одного владельца. Обратных импортов уровня web или bootstrap нет.

## Edge cases
Активные, выключенные и отсутствующие данные, пустой результат, прежние права, повтор запроса и rollback. Границы проверяются на актуальной схеме.

## Открытые вопросы
Бизнес-вопросов нет. Технические подзадачи выделяются по фактическим связям JPA и потребителям. Реальные пользовательские данные и production-сервер не используются для QA.
