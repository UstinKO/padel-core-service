# LFPT-1445: Feature многомодульный монолит, фаза 6 — выделить хранение турниров и историю проведения

## Статус
approved

## Источник
[Issue #1445](https://github.com/UstinKO/padel-core-service/issues/1445). Техническая постановка по утверждённой фазе 6. Родитель [#1051](https://github.com/UstinKO/padel-core-service/issues/1051).

## Контекст / зачем
Перенести связанное хранение турниров, команд, матчей, раундов и истории через подготовленные порты.

## Связь с MASTER.md
[MASTER](../MASTER.md) определяет роли, границы клубного доступа, регистрацию, турнирные состояния и хранение истории вместе с подтверждённым изменением. Сценарии сохраняют текущие инварианты. Зависимости [#1442](https://github.com/UstinKO/padel-core-service/issues/1442), [#1443](https://github.com/UstinKO/padel-core-service/issues/1443), [#1444](https://github.com/UstinKO/padel-core-service/issues/1444).

## Требования

### Функциональные

- Использовать JPA-группу турнира, заявок и оплат из [#1444](https://github.com/UstinKO/padel-core-service/issues/1444). Использовать принятые round-robin read/position/finish порты и определить недостающие операции для остальных форматов.
- Сохранить один persistence context, lock/version/key, snapshots/restore, flush и after-commit. Переносить связные группы отдельными PR.

### Нефункциональные
- Java release 17, JDK 21 в CI, одна транзакционная граница и один Boot JAR.
- Каждый PR проходит полный verify на отдельной PostgreSQL, артефактные и архитектурные guards, runtime/релевантный браузер и проверку совместимости предыдущего релиза.
- Сохраняются действующие права, i18n ES/RU/EN и внешние контракты. Новых пользовательских строк нет.

## Вне скоупа
Ручной релиз остаётся обычным. Физическая миграция PostgreSQL, Swarm и изменения бизнес-правил вне задачи.

## Изменения в системе

### API
Прежние MVC/HTTP/WS входы, поля, статусы и права.

### БД
Прежняя PostgreSQL и schema. Отдельная тестовая БД для интеграции.

### UI
Действующие клиенты используют прежние данные. Приёмочные сценарии запускаются через штатные входы.

### Документация
[План фазы 6](../../docs/modular-monolith/phase-6/README.md), документация фактических границ, затронутые endpoints и техническая карта при необходимости.

## Критерии приёмки

- [ ] Проверки W01–W18, остальные турнирные форматы, повтор и restore проходят.
- [ ] Позиции, счёт, статус и история откатываются вместе при отказе. Compose smoke, прежний JAR и схема совместимы.

## Edge cases
Активные, выключенные и отсутствующие данные, пустой результат, прежние права, повтор запроса и rollback. Границы проверяются на актуальной схеме.

## Открытые вопросы
Бизнес-вопросов нет. Технические подзадачи выделяются по фактическим связям JPA и потребителям. Реальные пользовательские данные и production-сервер не используются для QA.
