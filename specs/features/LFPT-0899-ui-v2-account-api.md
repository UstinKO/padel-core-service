# LFPT-0899: Feature backend API UI v2 — аккаунт, профиль и структурированные ошибки регистрации

## Статус
implemented — технический план подтверждён, реализация и проверки выполнены 2026-11-11.

## Источник
[GitHub issue #899](https://github.com/UstinKO/padel-core-service/issues/899), напрямую из issue. Разблокирует #908 и #912; #909 сохраняет другие открытые зависимости.

## Контекст / зачем
React нужны сессионный вход, регистрация, восстановление пароля и профиль с типизированными ответами. Сейчас JWT `/api/auth/login` предназначен для мобильных клиентов, веб-форма отвечает redirect/flash, а RateLimitFilter считает GET формы и обычную валидацию подозрительными регистрациями.

## Связь с MASTER.md
- Сохраняются два независимых типа пользователей, роли, JWT для мобильных клиентов и серверная сессия для веба.
- Контакт: действующий телефон +54 ИЛИ Telegram. Обязательность телефона из макета не переносится. Google-аккаунт не блокируется на входе из-за незаполненного контакта; требования к участию остаются серверными.
- Автоматическое подтверждение email сохраняется; новый блокирующий email-confirmation flow не вводится.
- Правила регистрации на мероприятия, очереди, отмены, оплаты и guest claim не меняются.

## Проверка существующего кода
- `AuthController` обслуживает `/api/auth/login`, `/refresh`, `/me` и выдаёт JWT. Его нельзя заменить веб-сессионным входом.
- `SecurityConfig` уже использует Spring form login `/login`, remember-me и отдельные success/failure handlers. ADR-0005 предусматривает JSON-ответ на том же endpoint по Accept.
- `PlayerPadelController` содержит web-регистрацию и `/players/api/registro`, проверяет CAPTCHA и делегирует `PlayerService`. Доступные проверки и защита должны переиспользоваться; второй независимый набор правил недопустим.
- `PasswordResetController` делегирует `PasswordResetService`; просроченный legacy GET уже перенаправляется на login, а не падает с отсутствующим шаблоном. Это поведение сохраняется.
- `CookieOverrideLocaleResolver`: `?lang=` устанавливает cookie `lang`, затем cookie имеет приоритет над Accept-Language. preferredLocale игрока — отдельная настройка писем.
- RateLimitFilter классифицирует путь без HTTP-метода и увеличивает suspiciousRegistrations до проверки результата; это причина ошибочных блокировок при посещении/исправлении формы.

## Требования

### API и безопасность
- `POST /login` остаётся form-urlencoded: username/password/remember-me, CSRF. Для Accept JSON — типизированный успех с сессией и безопасным destination; ошибка — 401 ProblemDetail. Для HTML — прежние redirect. Сессионная стратегия и remember-me остаются Spring Security.
- `POST /logout` с CSRF: JSON-ответ для XHR, прежний redirect для HTML; текущий `GET /api/auth/session` сохраняет контракт.
- `POST /api/players/registro`: анонимная JSON-регистрация, типизированный request/success, те же проверки полей/доменов/имён/контакта, CAPTCHA, honeypot и защита от абьюза. После создания — существующая семантика продолжения входа, без выдуманной JWT-сессии или автоматического слияния guest.
- `GET /api/public/config`: только публичные настройки CAPTCHA/siteKey, доступность Google, поддерживаемые языки и выбранная сервером локаль; без client-secret, внутренних адресов и токенов.
- `POST /api/password-reset/request`, `GET /api/password-reset/validate`, `POST /api/password-reset/confirm`: типизированные request/response, использование существующего сервиса, без раскрытия существования email. Проверка токена только читает; неизвестный/просроченный токен имеет стабильный ответ без 500.
- `GET/PUT /api/players/me`: собственный профиль PlayerPadel, существующие редактируемые поля и валидаторы, MapStruct. Owner с совпадающим числовым id не получает доступ к профилю игрока. Клиент не задаёт id/роль/active/emailConfirmed.
- `POST /api/players/me/password`: текущий пароль и подтверждённый новый пароль, без логирования секретов. Для Google-пользователя без известного пароля сохраняется путь восстановления. Новая политика глобального отзыва всех сессий не вводится.
- `401/403/422/429` для новых JSON-потоков не возвращают redirect или HTML. Валидация — ProblemDetail с устойчивым code и типизированным списком fieldErrors; текст локализован ES/RU/EN, неизвестное исключение не раскрывается.
- После сохранения профиля session/profile возвращают согласованные данные. Регистрация, reset и смена пароля не сохраняют пароли/CAPTCHA в сессии, URL, логах или ответах.

### Возврат и OAuth
- Сохранить event/безопасный same-origin destination через login, Google, completion и reset; запретить внешние URL, protocol-relative, обратные слэши, управляющие символы и повторно закодированные обходы.
- Переиспользовать TournamentLogin и текущие OAuth state/handlers. Мобильный OAuth и JWT-контракт не меняются.
- По умолчанию пользователи продолжают попадать на действующие публичные страницы, а не на защищённый SUPER_ADMIN preview. Production auth routes и SPA allowlist не переключаются.
- В отдельной локальной тестовой среде Google разрешён только с отдельным безопасным callback; при его отсутствии отключён и явно отмечен как непроверенный внешне. Demo login запрещён.

### Rate limiting
- Классифицировать запрос по методу и назначению: GET формы, session/config и обычный ответ валидации не увеличивают счётчик подозрительных регистраций.
- Сохранить действующие квоты, generic flood и защиту реальных попыток login/register/reset. Результат 422 сам по себе не превращает общий IP в BLOCKED.
- 429 JSON содержит фактические Retry-After/blockedUntil; тесты с управляемым временем покрывают оставшееся время bucket и блокировки. HTML-потоки сохраняют предусмотренное поведение.

## Изменения в системе
### API
Типизированные web account/profile/reset DTO, MapStruct и scoped ProblemDetail handler. Сессионный login — content negotiation существующего `/login`, не второй механизм. JWT-пути и legacy forms сохраняются.
### БД
Новых бизнес-полей заранее не планируется. Если код выявит необходимость миграции — отдельный новый Liquibase-файл в рамках согласованного scope, без изменения существующих миграций.
### UI
Не меняется в этой задаче; интерфейс реализуют #908 и #912.
### Документация
Обновить `docs/auth-flow.md`, endpoint docs, `docs/frontend-react/contract/api.md`, OpenAPI, `.agents/PROJECT.md`; уточнить связь ADR-0009 с существующей серверной cookie lang.

## Вне скоупа
Новые обязательные контакты, блокирующее подтверждение email, guest claim, правила записи/отмены/оплаты, изменение мобильного JWT, публичное переключение React, юридические формулировки.

## Критерии приёмки
- [ ] Legacy HTML-login/remember-me/logout и мобильный JWT/refresh проходят прежние тесты.
- [ ] JSON-login создаёт реальную серверную сессию, rotation/CSRF работают; JSON-ошибки не возвращают HTML/redirect.
- [ ] Анонимная регистрация сохраняет паритет защиты, типизированные fieldErrors и правило контакта ИЛИ.
- [ ] GET формы и несколько обычных ошибок валидации не блокируют двух пользователей за одним IP; flood по существующим лимитам даёт корректный 429 и время ожидания.
- [ ] Reset unknown/expired/reused token не даёт 500; ответы request не раскрывают существование email.
- [ ] Self-profile/password проверяют тип principal и принадлежность; чужой пользователь/Owner не может изменить профиль Player по совпадению id.
- [ ] Destination/event сохраняются без open redirect; OAuth-мобильный сценарий не меняется.
- [ ] Пароли/CAPTCHA/токены/полные формы не появляются в логах и ответах; ES/RU/EN и OpenAPI полны.
- [ ] Полный clean verify, docs-drift и проверки CI проходят с сохранёнными настройками Surefire и отдельной тестовой БД.

## Edge cases
Одинаковый email Owner/Player, завершение сессии между вкладками, неверный CSRF, дубликат контакта, CAPTCHA/domain/name error, несколько ошибок сразу, unknown/expired/reused reset token, неподдерживаемый principal, недоступная БД/почта, повторная отправка и поддельный destination. Мутации после неопределённого сетевого исхода автоматически не повторяются.

## Открытые вопросы
Бизнес-инварианты сохраняются. Технический план блока #899 → #908 → #912 подтверждён пользователем. Внешний Google callback нельзя объявлять проверенным без отдельного тестового provider/callback.

## Интеграция системных страниц
Для зависимой #912 добавлены реальные HTTP-статусы неизвестного preview-маршрута и системных страниц; legal preview получает canonical на старый публичный URL и noindex. Покрыто сквозным тестом сервера.

Внешний Google callback не проверялся; provider заменён в интеграционных тестах.
