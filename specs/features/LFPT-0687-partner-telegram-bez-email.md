# LFPT-0687: Контакт нового партнёра без email — Telegram вместо email, статус регистрации без авто-приглашения (backend)

## Статус
draft

## Источник
Клиентский запрос [specs/requests/LFPT-0687-partner-telegram-bez-email.md](../requests/LFPT-0687-partner-telegram-bez-email.md) (Telegram, `telegram_launch_message_id: 5407`, отправитель customer). GitHub issue [#687](https://github.com/UstinKO/padel-core-service/issues/687). Разбито на бэкенд/фронтенд (`GIT_WORKFLOW.md` §1.4) — эта спека покрывает бэкенд. Фронтенд — [#688](https://github.com/UstinKO/padel-core-service/issues/688).

## Контекст / зачем

Реальный процесс парной регистрации (по словам заказчика): игрок, который регистрирует пару, уже сам договорился с партнёром, а координатор турнира потом вручную связывается с партнёром по телефону (WhatsApp) или Telegram — email партнёру почти никогда не нужен. Текущий код не соответствует этому процессу в двух местах:

1. `TournamentRegistration` хранит «сырые» контактные поля ожидающего (пока не ставшего реальным `PlayerPadel`) партнёра — `partnerFirstName`/`partnerLastName`/`partnerPhone`/`partnerEmail`. Telegram-поля нет, поэтому `TournamentRegistrationMapper.getPartnerTelegram()` отдаёт Telegram координатору только когда партнёр уже стал подтверждённым `PlayerPadel` (`registration.getPartner() != null`) — до этого момента координатор видит телефон и email партнёра, но не Telegram, даже если тот был бы указан.
2. `DoubleTournamentRegistrationService.registerWithNewPartner` всегда ставит `RegistrationStatus.PARTNER_INVITED`, а письмо-приглашение с токеном подтверждения (`confirmPartnerRegistration`) отправляется только если указан email. Без email партнёр никогда не получает ссылку — регистрация навсегда «застревает» в статусе «Compañero Invitado» / «Партнёр приглашён», хотя приглашения не было и партнёр не может сам её подтвердить. Тот же паттерн — в `addPartnerToSoloRegistration` (ветка нового партнёра) и `replacePlayerInPair` (ветка создания приглашения).

## Связь с MASTER.md

Затрагивает [specs/MASTER.md § Флоу парной регистрации](../MASTER.md#флоу-парной-регистрации): сейчас флоу описан как «первый игрок регистрируется → партнёру уходит email-приглашение → партнёр подтверждает по ссылке → оба CONFIRMED». Эта спека вводит для партнёра **без email** альтернативную ветку того же флоу — подтверждение не по ссылке из письма, а действием координатора в админ-панели после того, как он вручную связался с партнёром (созданием `PlayerPadel` из тех же данных регистрации — тот же эффект, что сейчас даёт `confirmPartnerRegistration`, только без email-триггера). `MASTER.md` нужно обновить в этом же PR, отразив обе ветки.

Решение по открытым вопросам ниже определяет итоговое название нового статуса/состояния — после ответа заказчика обновить и `RegistrationStatus`-таблицу в `MASTER.md` (`specs/MASTER.md` § «Статусы регистрации на турнир»).

## Требования

### Функциональные

1. **Миграция**: новая колонка `partner_telegram` в `tournament_registrations_db` — `src/main/resources/db/changelog/versions/v1.56-add-partner-telegram.yaml`, зарегистрировать в `changelog-master.yaml`.
2. **`PartnerRegistrationDto`**: добавить опциональное поле Telegram-юзернейма партнёра (без обязательной валидации, как и `telefono` при `existingUserId`).
3. **Запись Telegram во всех ветках, где сейчас пишутся `partnerPhone`/`partnerEmail` нового партнёра**: `registerWithNewPartner`, `addPartnerToSoloRegistration` (ветка без существующего игрока), `replacePlayerInPair` (ветка создания приглашения) — писать `partnerTelegram` из `PartnerRegistrationDto`.
4. **Запись Telegram там, где партнёр уже существующий игрок**: `registerWithExistingPartner` и симметричная запись регистрации самого партнёра, а также ветка `addPartnerToSoloRegistration`/`replacePlayerInPair` для существующего игрока — заполнять `partnerTelegram` из `partner.getTelegramUsername()`, аналогично уже имеющимся там `partnerPhone`/`partnerEmail`.
5. **`TournamentRegistrationMapper.getPartnerTelegram()`**: убрать ветвление по `registration.getPartner() != null`, читать `registration.getPartnerTelegram()` напрямую (как уже сделано для `partnerPhone` — `@Mapping(target = "partnerPhone", source = "partnerPhone")`), т.к. поле теперь заполняется в обеих ветках (п.3–4).
6. **`confirmPartnerRegistration`**: при создании `PlayerPadel` из данных приглашения — заполнять `telegramUsername` из `registration.getPartnerTelegram()` (сейчас копируются только `nombre`/`apellido`/`telefono`/`email`).
7. **Статус/подтверждение без email-приглашения** — реализация этого пункта зависит от ответа на «Открытые вопросы» ниже; требования будут дописаны после снятия гейта.

### Нефункциональные

- **i18n**: пользовательских строк на бэкенде нет сверх текста статуса (п.7, зависит от ответа на открытый вопрос).
- **Безопасность**: новых публичных точек входа не добавляется — `partnerTelegram` передаётся через уже существующий авторизованный путь регистрации (`PartnerRegistrationDto`), как и `partnerPhone`/`partnerEmail`.
- **Обратная совместимость данных**: существующие записи `tournament_registrations_db` с заполненным `partner_email` не трогаем и не мигрируем — колонка `partner_email` остаётся в модели и в БД (историю не изменяем), фронтенд (#688) просто перестаёт показывать поле email в форме для новых регистраций.

## Вне скоупа

- Удаление колонки/поля `partner_email` из `TournamentRegistration`/`PartnerRegistrationDto` — поле остаётся на бэкенде (историческая совместимость, возможность указать email точечно, если когда-то понадобится), убирается только из UI формы (#688).
- Автоматическая отправка сообщений в WhatsApp/Telegram партнёру (явное ограничение клиентского запроса, п.2) — координатор связывается вручную, система только показывает контакты.
- Жёсткая серверная защита от дублей партнёра — отдельная тема, закрыта в #677/#679/#680.
- Любые изменения `TestTournamentController` (JDBC, не JPA, не использует `PartnerRegistrationDto`).

- [ ] Новый партнёр с указанным Telegram (без email) — после регистрации координатор видит его Telegram в админ-панели (таблица, где сейчас видна только отсутствующая колонка для неподтверждённого партнёра).

## Edge cases

- Партнёр указал и телефон, и Telegram — оба сохраняются и показываются координатору независимо.
- Партнёр без Telegram (`null`/пусто) — не падает, колонка `partner_telegram` остаётся `null`.
- Существующий партнёр, у которого в профиле *нет* Telegram (`telegramUsername == null`) — координатор видит только телефон, как и сейчас.
- Регистрация, созданная до этой миграции (старые записи без `partner_telegram`) — читается как `null`, не ломает существующий UI (колонка новая, nullable).

## Открытые вопросы

Статус спеки — `draft`, пока не получены ответы. Оба вопроса — бизнес-решения о процессе координатора, не технические детали (`GIT_WORKFLOW.md` §3 здесь неприменим — реализующий не может сам выбрать разумный вариант, т.к. разные варианты по-разному меняют видимый пользователям флоу и ответственность координатора):

1. **Как координатор завершает регистрацию партнёра, с которым связался вручную (без email-приглашения)?** Сейчас единственный технический способ перевести регистрацию из "Compañero Invitado" в `CONFIRMED`/`WAITLIST` — переход партнёра по ссылке с токеном из письма (`confirmPartnerRegistration`). Без email эта ссылка никому не доставляется — предлагается добавить в админ-панели (таблица «Invitación pendiente» на странице турнира) кнопку «Партнёр подтверждён», которая выполняет то же самое действие от имени координатора (создаёт `PlayerPadel` из указанных контактных данных, переводит пару в очередь по текущим правилам листа ожидания — как сейчас делает переход по ссылке). Подтвердить этот вариант или предложить другой процесс?
2. **Как называть статус/состояние этой регистрации до подтверждения координатором?** Сейчас в интерфейсе (админка, кабинет игрока) это "Compañero Invitado" ("Партнёр приглашён") — текст прямо говорит о приглашении, которого не было. Нужен новый текст (например, «Партнёр указан, ожидает подтверждения» / «На связи с координатором») — технически можно обойтись заменой текста существующего статуса `PARTNER_INVITED` без нового значения enum, если он во всех сценариях (включая редкий случай «email всё же указан, письмо отправлено») должен выглядеть одинаково; либо завести отдельное значение `RegistrationStatus`, если сценарии должны различаться визуально. Какой вариант предпочтителен?
