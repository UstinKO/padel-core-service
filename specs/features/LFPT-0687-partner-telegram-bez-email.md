# LFPT-0687: Контакт нового партнёра без email — Telegram вместо email, статус регистрации без авто-приглашения (backend)

## Статус
approved

## Источник
Клиентский запрос [specs/requests/LFPT-0687-partner-telegram-bez-email.md](../requests/LFPT-0687-partner-telegram-bez-email.md) (Telegram, `telegram_launch_message_id: 5407`, отправитель customer). GitHub issue [#687](https://github.com/UstinKO/padel-core-service/issues/687). Разбито на бэкенд/фронтенд (`GIT_WORKFLOW.md` §1.4) — эта спека покрывает бэкенд. Фронтенд — [#688](https://github.com/UstinKO/padel-core-service/issues/688).

## Контекст / зачем

Реальный процесс парной регистрации (по словам заказчика): игрок, который регистрирует пару, уже сам договорился с партнёром, а координатор турнира потом вручную связывается с партнёром по телефону (WhatsApp) или Telegram — email партнёру почти никогда не нужен. Текущий код не соответствует этому процессу в двух местах:

1. `TournamentRegistration` хранит «сырые» контактные поля ожидающего (пока не ставшего реальным `PlayerPadel`) партнёра — `partnerFirstName`/`partnerLastName`/`partnerPhone`/`partnerEmail`. Telegram-поля нет, поэтому `TournamentRegistrationMapper.getPartnerTelegram()` отдаёт Telegram координатору только когда партнёр уже стал подтверждённым `PlayerPadel` (`registration.getPartner() != null`) — до этого момента координатор видит телефон и email партнёра, но не Telegram, даже если тот был бы указан.
2. `DoubleTournamentRegistrationService.registerWithNewPartner` всегда ставит `RegistrationStatus.PARTNER_INVITED`, а письмо-приглашение с токеном подтверждения (`confirmPartnerRegistration`) отправляется только если указан email. Без email партнёр никогда не получает ссылку — регистрация навсегда «застревает» в статусе «Compañero Invitado» / «Партнёр приглашён», хотя приглашения не было и партнёр не может сам её подтвердить. Тот же паттерн — в `addPartnerToSoloRegistration` (ветка нового партнёра) и `replacePlayerInPair` (ветка создания приглашения).

**Ответ заказчика на оба открытых вопроса (см. ниже) показал, что проблема шире одного только email** — партнёр без аккаунта не должен ждать ни email, ни отдельного подтверждения в принципе: регистрирующий игрок уже договорился с ним заранее. Решение — создавать аккаунт партнёра сразу (требование 7).

## Связь с MASTER.md

Затрагивает [specs/MASTER.md § Флоу парной регистрации](../MASTER.md#флоу-парной-регистрации): флоу был описан как «первый игрок регистрируется → партнёру уходит email-приглашение → партнёр подтверждает по ссылке → оба CONFIRMED». По ответу заказчика (см. «Открытые вопросы») флоу меняется полностью, а не только для партнёра без email: регистрация завершается немедленно для партнёра с аккаунтом и без него одинаково — `MASTER.md` обновлён в этом же PR (новое описание флоу + `PARTNER_INVITED` помечен легаси-статусом в таблице «Статусы регистрации на турнир»).

## Требования

### Функциональные

1. **Миграция**: новая колонка `partner_telegram` в `tournament_registrations_db` — `src/main/resources/db/changelog/versions/v1.56-add-partner-telegram.yaml`, зарегистрировать в `changelog-master.yaml`.
2. **`PartnerRegistrationDto`**: добавить опциональное поле Telegram-юзернейма партнёра (без обязательной валидации, как и `telefono` при `existingUserId`).
3. **Запись Telegram во всех ветках, где сейчас пишутся `partnerPhone`/`partnerEmail` нового партнёра**: `registerWithNewPartner`, `addPartnerToSoloRegistration` (ветка без существующего игрока), `replacePlayerInPair` (ветка создания приглашения) — писать `partnerTelegram` из `PartnerRegistrationDto`.
4. **Запись Telegram там, где партнёр уже существующий игрок**: `registerWithExistingPartner` и симметричная запись регистрации самого партнёра, а также ветка `addPartnerToSoloRegistration`/`replacePlayerInPair` для существующего игрока — заполнять `partnerTelegram` из `partner.getTelegramUsername()`, аналогично уже имеющимся там `partnerPhone`/`partnerEmail`.
5. **`TournamentRegistrationMapper.getPartnerTelegram()`**: убрать ветвление по `registration.getPartner() != null`, читать `registration.getPartnerTelegram()` напрямую (как уже сделано для `partnerPhone` — `@Mapping(target = "partnerPhone", source = "partnerPhone")`), т.к. поле теперь заполняется в обеих ветках (п.3–4).
6. **`confirmPartnerRegistration`**: при создании `PlayerPadel` из данных приглашения — заполнять `telegramUsername` из `registration.getPartnerTelegram()` (сейчас копируются только `nombre`/`apellido`/`telefono`/`email`).
7. **Регистрация без ожидания подтверждения (ответ заказчика, см. «Открытые вопросы»)**: игрок, регистрирующий пару, уже сам договорился с партнёром заранее — ни email-приглашение, ни отдельное подтверждение (ни партнёром по ссылке, ни координатором кнопкой) не нужны. `registerForDoubleTournament` с партнёром без аккаунта (`registerWithNewPartner`), `addPartnerToSoloRegistration` (ветка нового партнёра) и `replacePlayerInPair` (ветка нового партнёра) создают аккаунт партнёра **сразу** и регистрируют пару тем же путём, что и для уже существующего партнёра — статус определяется только занятостью турнира (`CONFIRMED`/`WAITLIST`), без промежуточного состояния и без токена. Старый email-токен-флоу (`confirmPartnerRegistration`, `PartnerRegistrationController`) не удаляется — он остаётся легаси-путём для регистраций, созданных до этого изменения (их `PARTNER_INVITED`-статус и токен уже существуют в БД и должны продолжать работать).
8. **Чекбокс-подтверждение регистрирующего игрока** ("Я согласовал участие с партнёром", предложен заказчиком как возможное, но не обязательное дополнение) — технически это чисто UI-элемент без серверного принуждения (заказчик явно оставил это на усмотрение реализующего, "если нужно"); бэкенд не валидирует его отдельным полем — решение по UI (нужен ли он вообще) принимает фронтенд-задача #688.

### Нефункциональные

- **i18n**: пользовательских строк на бэкенде не добавляется — статус после регистрации (CONFIRMED/WAITLIST) уже имеет существующие i18n-ключи, отдельного текста не требуется (см. «Открытые вопросы», п.2).
- **Безопасность**: новых публичных точек входа не добавляется — `partnerTelegram` передаётся через уже существующий авторизованный путь регистрации (`PartnerRegistrationDto`), как и `partnerPhone`/`partnerEmail`.
- **Обратная совместимость данных**: существующие записи `tournament_registrations_db` с заполненным `partner_email` не трогаем и не мигрируем — колонка `partner_email` остаётся в модели и в БД (историю не изменяем), фронтенд (#688) просто перестаёт показывать поле email в форме для новых регистраций.

## Вне скоупа

- Удаление колонки/поля `partner_email` из `TournamentRegistration`/`PartnerRegistrationDto` — поле остаётся на бэкенде (историческая совместимость, возможность указать email точечно, если когда-то понадобится), убирается только из UI формы (#688).
- Автоматическая отправка сообщений в WhatsApp/Telegram партнёру (явное ограничение клиентского запроса, п.2) — координатор связывается вручную, система только показывает контакты.
- Жёсткая серверная защита от дублей партнёра — отдельная тема, закрыта в #677/#679/#680.
- Любые изменения `TestTournamentController` (JDBC, не JPA, не использует `PartnerRegistrationDto`).

## Изменения в системе

### API
Без изменений сигнатур существующих эндпоинтов (`POST /api/tournaments/double/{tournamentId}/register` и др.) — `PartnerRegistrationDto` получает новое опциональное поле (`telegramUsername`), контракт запроса/ответа не меняется (статус в ответе и раньше мог быть `CONFIRMED`/`WAITLIST`, теперь это так всегда, а не только для партнёра с аккаунтом). Новый admin-эндпоинт не нужен — заказчик отклонил идею кнопки «Партнёр подтверждён» (см. «Открытые вопросы»).

`tournament_registrations_db` — новая колонка `partner_telegram` (nullable, `varchar`, по аналогии с `partner_phone`/`partner_email`).

### UI

## Критерии приёмки

- [ ] Новый партнёр с указанным Telegram (без email) — после регистрации координатор видит его Telegram в админ-панели (таблица, где сейчас видна только отсутствующая колонка для неподтверждённого партнёра).
- [ ] Партнёр — существующий игрок с заполненным `telegramUsername` — Telegram виден координатору сразу (регрессия на уже работающий случай подтверждённого партнёра).
- [ ] `confirmPartnerRegistration` — созданный `PlayerPadel` получает `telegramUsername` из данных приглашения, если был указан (легаси-путь).
- [ ] Регистрация пары с новым партнёром (только телефон/Telegram, без email) через `POST /api/tournaments/double/{tournamentId}/register` завершается немедленно одним запросом — ответ содержит финальный статус `CONFIRMED` (если есть место) или `WAITLIST` (если турнир полон), без `PARTNER_INVITED` и без токена.
- [ ] То же для `addPartnerToSoloRegistration` (ветка нового партнёра) и `replacePlayerInPair` (ветка нового партнёра) — партнёр создаётся сразу, без ожидания.
- [ ] «Добавлю партнёра позже» (`SOLO_ADD_LATER`) с новым (безаккаунтным) партнёром: до дедлайна — пара сразу `CONFIRMED` (слот уже занят соло-регистрацией), после перевода в резерв — пара встаёт в конец очереди резерва (`WAITLIST`), как и для партнёра с существующим аккаунтом.
- [ ] Старый email-токен-флоу (`POST /api/tournaments/double/confirm`) продолжает работать для легаси-регистраций в статусе `PARTNER_INVITED` (не удалён, не меняет поведение для них).
- [ ] `python3 .github/bin/docs-drift.py` — 0 расхождений после обновления документации.
- [ ] `./mvnw verify` зелёный.

## Edge cases

- Партнёр указал и телефон, и Telegram — оба сохраняются и показываются координатору независимо.
- Партнёр без Telegram (`null`/пусто) — не падает, колонка `partner_telegram` остаётся `null`.
- Существующий партнёр, у которого в профиле *нет* Telegram (`telegramUsername == null`) — координатор видит только телефон, как и сейчас.
- Регистрация, созданная до этой миграции (старые записи без `partner_telegram`) — читается как `null`, не ломает существующий UI (колонка новая, nullable).

## Открытые вопросы (сняты — ответ заказчика, 2026-10-21)

1. **Кнопка «Партнёр подтверждён» — не нужна.** Игрок, регистрирующий пару, уже сам договорился с партнёром до регистрации и записывает уже согласованную пару. После указания партнёра регистрация завершается немедленно, без ожидания email или действия координатора — координатор может связаться с участниками вручную (WhatsApp/Telegram) позже, но это не условие участия. Опциональное дополнение (не обязательное технически, решение за фронтендом #688) — чекбокс/подпись у регистрирующего игрока «Я согласовал участие с партнёром».
2. **Статус** — «Пара сформирована» / «Зарегистрированы» подходят; «Партнёр приглашён» и «Ожидает подтверждения» — нет, т.к. приглашение не отправляется и отдельного подтверждения не ждём. Технически это означает: пара сразу получает обычный статус по занятости турнира (`CONFIRMED`/`WAITLIST`) — отдельное значение `RegistrationStatus` не требуется, `PARTNER_INVITED` остаётся только для уже существующих легаси-записей (см. требование 7).

**Отдельно подтверждено заказчиком:** сценарий «Добавлю партнёра позже» (`SOLO_ADD_LATER`) сохраняет текущий дедлайн и правила резерва без изменений — наличие партнёра (создан сразу, без ожидания) и попадание пары в основной список или резерв — разные вещи, лимит мест проверяется как раньше (`isPendingSoloAddLater`/`isReserveWithoutPartner` в `addPartnerToSoloRegistration`).
