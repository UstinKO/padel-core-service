# LFPT-1447: Feature многомодульный монолит, фаза 6 — независимо принять рабочий модуль хранения

## Статус
approved

## Источник
[Issue #1447](https://github.com/UstinKO/padel-core-service/issues/1447). Техническая постановка по утверждённой фазе 6. Родитель [#1051](https://github.com/UstinKO/padel-core-service/issues/1051).

## Контекст / зачем
Независимая приёмка фазы хранения завершает координацию #1051 после включения всех backend-частей.

## Связь с MASTER.md
[MASTER](../MASTER.md) определяет роли, границы клубного доступа, регистрацию, турнирные состояния и хранение истории вместе с подтверждённым изменением. Сценарии сохраняют текущие инварианты. Зависимости [#1446](https://github.com/UstinKO/padel-core-service/issues/1446).

## Требования

### Функциональные

- Повторить реальные HTTP/браузер/React/Expo/WS и соседний игровой пилот на принятом JAR. Сверить прежний JAR и данные при restart/rollback, включая все поля истории Liquibase.
- Зафиксировать проверки прав, регистраций и оплат, JPA-инвариантов и фактических мостов. Уточнить следующий перенос web/integrations.

### Нефункциональные
- Java release 17, JDK 21 в CI, одна транзакционная граница и один Boot JAR.
- Каждый PR проходит полный verify на отдельной PostgreSQL, артефактные и архитектурные guards, runtime/релевантный браузер и проверку совместимости предыдущего релиза.
- Сохраняются действующие права, i18n ES/RU/EN и внешние контракты. Новых пользовательских строк нет.

## Вне скоупа
Ручной релиз остаётся обычным. Физическая миграция PostgreSQL, Swarm и изменения бизнес-правил вне задачи.

## Изменения в системе

### API
Прежние MVC/HTTP/WS входы, поля, статусы и права.

### БД
Прежняя PostgreSQL и schema. Отдельная тестовая БД для интеграции.

### UI
Действующие клиенты используют прежние данные. Приёмочные сценарии запускаются через штатные входы.

### Документация
[План фазы 6](../../docs/modular-monolith/phase-6/README.md), документация фактических границ, затронутые endpoints и техническая карта при необходимости.

## Критерии приёмки

- [ ] Независимая приёмка проверяет новую и существующую PostgreSQL, полное сравнение данных и совместимый возврат без повторных миграций.
- [ ] Один JAR, один Liquibase, принятые клиентские контракты и архитектурные границы подтверждены.

## Edge cases
Активные, выключенные и отсутствующие данные, пустой результат, прежние права, повтор запроса и rollback. Границы проверяются на актуальной схеме.

## Открытые вопросы
Бизнес-вопросов нет. Технические подзадачи выделяются по фактическим связям JPA и потребителям. Реальные пользовательские данные и production-сервер не используются для QA.
