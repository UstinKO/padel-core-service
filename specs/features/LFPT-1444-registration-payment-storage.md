# LFPT-1444: Feature многомодульный монолит, фаза 6 — выделить хранение регистраций, оплат и журнала

## Статус
approved

## Источник
[Issue #1444](https://github.com/UstinKO/padel-core-service/issues/1444). Техническая постановка по утверждённой фазе 6. Родитель [#1051](https://github.com/UstinKO/padel-core-service/issues/1051).

## Контекст / зачем
Сгруппировать хранилище заявок, платежей и их транзакционного журнала по связанным сущностям и операциям.

## Связь с MASTER.md
[MASTER](../MASTER.md) определяет роли, границы клубного доступа, регистрацию, турнирные состояния и хранение истории вместе с подтверждённым изменением. Сценарии сохраняют текущие инварианты. Зависимости [#1442](https://github.com/UstinKO/padel-core-service/issues/1442), [#1443](https://github.com/UstinKO/padel-core-service/issues/1443).

## Требования

### Функциональные

- Инвентаризировать ссылки регистрация → турнир/pairs/участник, listener, журнал, outbox и локальные эффекты. Уточнить совместную группу с турнирным хранением перед первым PR, если граф этого требует.
- Перенести подготовленные адаптеры и нейтральные порты. Проверить запись последнего места, резерв, оплату, rollback и доставку после commit.

### Нефункциональные
- Java release 17, JDK 21 в CI, одна транзакционная граница и один Boot JAR.
- Каждый PR проходит полный verify на отдельной PostgreSQL, артефактные и архитектурные guards, runtime/релевантный браузер и проверку совместимости предыдущего релиза.
- Сохраняются действующие права, i18n ES/RU/EN и внешние контракты. Новых пользовательских строк нет.

## Вне скоупа
Ручной релиз остаётся обычным. Физическая миграция PostgreSQL, Swarm и изменения бизнес-правил вне задачи.

## Изменения в системе

### API
Прежние MVC/HTTP/WS входы, поля, статусы и права.

### БД
Прежняя PostgreSQL и schema. Отдельная тестовая БД для интеграции.

### UI
Действующие клиенты используют прежние данные. Приёмочные сценарии запускаются через штатные входы.

### Документация
[План фазы 6](../../docs/modular-monolith/phase-6/README.md), документация фактических границ, затронутые endpoints и техническая карта при необходимости.

## Критерии приёмки

- [ ] Резерв, вместимость, пары, оплата и связанная история совпадают с принятым поведением.
- [ ] Отказ откатывает связанные строки и journal/outbox, успех сохраняет прежнюю границу commit; режим сцен с двумя репликами остаётся в отдельной #1214.

## Edge cases
Активные, выключенные и отсутствующие данные, пустой результат, прежние права, повтор запроса и rollback. Границы проверяются на актуальной схеме.

## Открытые вопросы
Бизнес-вопросов нет. Технические подзадачи выделяются по фактическим связям JPA и потребителям. Реальные пользовательские данные и production-сервер не используются для QA.
