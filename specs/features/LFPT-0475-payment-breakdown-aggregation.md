# LFPT-0475: Feature агрегация суммы оплат по способу оплаты для страницы платежей турнира (бэкенд)

## Статус
approved

## Источник
`specs/requests/LFPT-0475-payment-method-breakdown.md` (клиентский запрос через Telegram, тема "AI Разработка"), issue [#475](https://github.com/UstinKO/padel-core-service/issues/475).

Telegram-сообщение (для reply): 4784

## Контекст / зачем
На странице `/admin/tournaments/{tournamentId}/payments` организатор видит только общую сумму по каждой валюте (например `ARS — $330 000`). После турнира ему нужно сразу видеть, сколько денег пришло каждым способом (наличные/банковский перевод/карта/крипто-площадка), чтобы сверить физические наличные и остатки на счетах без ручного пересчёта строк таблицы.

Эта задача — агрегация данных на бэкенде (DTO + сервисный метод + атрибут модели контроллера). Сама разметка блока в UI — зависимая задача [LFPT-0476](https://github.com/UstinKO/padel-core-service/issues/476), не входит сюда.

## Связь с MASTER.md
Раздел "Платежи" `specs/MASTER.md` — платежи фиксируются организатором вручную в админ-панели, без платёжного шлюза. Эта фича не меняет сам механизм фиксации оплаты (поле "Способ" уже существует и уже сохраняется), добавляет только агрегированное отображение уже введённых данных. Инварианты MASTER.md не меняются, обновление MASTER.md не требуется.

## Требования

### Функциональные
- Новый метод агрегации сумм платежей по валюте и способу оплаты, учитывающий **только** платежи со статусом `PaymentStatus.PAID` ("Оплачено") — остальной список критериев см. "Изменения в системе → API".
- **Поле/селектор площадки для крипты заводить не нужно.** Анализ существующего кода показал, что клиентское предположение «система хранит только общий способ "Крипто"» неверно: `PaymentMethod` (`model/enums/PaymentMethod.java`) уже содержит отдельные константы `BY_BIT` и `BINANCE` (наравне с `CASH`, `BANK_TRANSFER`, `TARJETA`, `TRANSFERENCIA`, `OTHER`), выпадающий список "Способ" в `payments.html` уже строится по `PaymentMethod.values()` (`admin.payments.col.method`, шаблон `payments.html:251-261`), а значения уже сохраняются через `POST /admin/tournaments/{id}/payments/save` → `PaymentService.savePaymentManagementData` → `payment.setPaymentMethod(dto.getPaymentMethod())`. Группировка по `paymentMethod` при агрегации автоматически разделит Bybit/Binance как отдельные способы — без миграции схемы и без нового поля на `Payment`.

### Нефункциональные
- i18n — не в этой задаче (новых пользовательских строк не добавляется, эта задача не содержит UI).
- Безопасность — новой точки входа данных от пользователя нет: метод читает уже загруженный на странице список платежей, доступ к странице уже защищён `tournamentAccessService.assertCanManageTournament(owner, tournamentId)` (не меняется).
- Производительность — агрегация выполняется над уже загруженным в память списком `List<PaymentManagementViewDto>` (обычно десятки записей на турнир), дополнительных запросов к БД не добавляется.

## Вне скоупа
- Разметка/вывод блока разбивки в `admin/tournaments/payments.html`, иконки, CSS, i18n-подписи заголовка блока — задача [LFPT-0476](https://github.com/UstinKO/padel-core-service/issues/476), отдельный PR, зависит от этой.
- Исправление существующего блока общей суммы по валюте (`#aggregates.sum(...)` в шаблоне, не фильтрует по `PAID`, не исключает партнёрские строки) — заказчик явно просил оставить общую сумму как есть; найденная проблема заведена отдельно как технический долг — issue [#477](https://github.com/UstinKO/padel-core-service/issues/477), не трогается в этой задаче.
- Обновление `.claude/CLAUDE.md` — вне `git diff` этого PR (`.claude/` в `.gitignore`), синхронизируется архитектором отдельно при необходимости.

## Изменения в системе

### API
Без изменений HTTP-контракта (нет новых/изменённых endpoint'ов). `GET /admin/tournaments/{tournamentId}/payments` — в модель Thymeleaf добавляется новый атрибут (например `paymentBreakdown`), пока не используемый ни одним шаблоном (используется зависимой задачей LFPT-0476).

Новый сервисный метод (точная сигнатура — на усмотрение реализующего, пример):
```java
List<CurrencyPaymentBreakdownDto> getPaymentMethodBreakdown(List<PaymentManagementViewDto> players)
```
Правила агрегации:
1. Берётся только `paymentStatus == PaymentStatus.PAID`.
2. **Виртуальные строки партнёра (`PaymentManagementViewDto.isPartnerRow() == true`) не исключаются и не требуют особой обработки.** Важное уточнение по итогам чтения кода `PaymentService.getPaymentManagementData`: при парной регистрации с партнёром-гостем (не зарегистрирован в БД) вторая строка ("partnerRow") — это не копия суммы основного игрока, а **отдельная запись `Payment`** (отличается от платежа основного игрока маркером `PARTNER_PAYMENT` в `notes`, см. `PaymentService.PARTNER_PAYMENT_MARKER`). Оба платежа независимы и оба должны учитываться в сумме — ровно как это уже (корректно) делает существующий блок общей суммы по валюте в шаблоне, который `partnerRow` не исключает. Счётчики `Total`/«Не оплатили» исключают `partnerRow` по другой причине — это подсчёт количества людей/мест, а не денег, дублировать эту логику для денежной агрегации не нужно.
3. Исключаются записи с `amount == null` или `amount.compareTo(BigDecimal.ZERO) <= 0`.
4. Группировка — по валюте (`currency == null` трактуется как `"ARS"`, как и в существующем блоке общей суммы), внутри каждой валюты — по `paymentMethod`. `paymentMethod == null` (оплата отмечена `PAID`, но способ не выбран) — не отбрасывается молча, попадает в отдельную псевдо-группу "способ не указан" (представление группы — на усмотрение реализующего, например `paymentMethod == null` в DTO).
5. Способ с нулевой итоговой суммой по валюте в результат не включается (нулевых групп после фильтрации по построению не возникает, но если возникнет — не включать).
6. Валюты, не имеющие ни одной подходящей записи, в результат не включаются.

### БД
Миграция Liquibase не требуется — ни новых таблиц, ни новых колонок.

### UI
Нет изменений в этой задаче.

## Критерии приёмки
- [ ] Новый метод в `PaymentService` возвращает агрегат сумм по валюте и способу оплаты, учитывая только `PaymentStatus.PAID`
- [ ] Партнёрская строка (`isPartnerRow() == true`) с собственным оплаченным платежом учитывается в сумме наравне с обычной строкой (не исключается, не задваивается — это независимый платёж)
- [ ] Записи с `amount == null` или `amount <= 0` исключены
- [ ] Группа «способ не указан» формируется для `paymentMethod == null` и не теряется
- [ ] Способ с нулевой суммой по конкретной валюте отсутствует в результате этой валюты
- [ ] Валюта без ни одной подходящей записи отсутствует в результате целиком
- [ ] `PaymentManagementController.paymentManagementPage` передаёт новый атрибут модели (проверяется тестом на уровне сервиса/контроллера)
- [ ] Unit/интеграционный тест покрывает минимум: 2 валюты, несколько способов оплаты в одной валюте, пару с независимыми платежами у главного игрока и у партнёра-гостя (`partnerRow`, оба суммируются), один платёж с `paymentMethod == null`, один неоплаченный платёж (`PENDING`) с ненулевой суммой — все граничные случаи из правил агрегации выше
- [ ] `./mvnw compile -DskipTests` и `./mvnw verify` проходят

## Edge cases
- Турнир без единого платежа — метод возвращает пустой список, без исключений.
- Все платежи одной валюты — результат содержит одну группу валюты.
- Платёж с `amount == 0` и статусом `PAID` (например, скидка 100%, как в примере на скриншоте заказчика) — не попадает в агрегацию (правило 3 выше); это осознанное решение: нулевая сумма не несёт информации о распределении денег по способам.
- Повторный вызов метода с тем же списком `players` — результат детерминирован (идемпотентность), порядок групп внутри списка не специфицируется спекой (на усмотрение реализующего, например — валюты и способы в порядке объявления `PaymentMethod`/первого появления валюты).
