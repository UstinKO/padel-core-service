# LFPT-0558: Feature создание турнира клубным аккаунтом — статус автоматически «Регистрация открыта» (бэкенд)

## Статус
approved

## Источник
Клиентский запрос [specs/requests/LFPT-0558-club-tournament-default-status.md](../requests/LFPT-0558-club-tournament-default-status.md), issue [#558](https://github.com/UstinKO/padel-core-service/issues/558).

Telegram-сообщение (для reply): 5055

## Контекст / зачем
При создании турнира через админ-панель организатор обязан выбрать статус из шести значений (`estado`, обязательный `<select>`). Для клубной учётной записи (`ROLE_CLUB_ADMIN`) это лишний шаг, который почти всегда должен приводить к одному и тому же результату — турнир сразу открыт для регистрации, — и вдобавок путает «Опубликован» и «Регистрация открыта». Цель — убрать эту путаницу и упростить создание стандартного турнира клубом: для клубного аккаунта статус при создании устанавливается автоматически.

## Связь с MASTER.md
Не меняет ни одного инварианта `MASTER.md`. Роль `ROLE_CLUB_ADMIN` и её возможности («видит и администрирует только турниры... своего клуба», `specs/MASTER.md` § Роли пользователей) уже описаны и не меняются. Статусы турнира и их значения (раздел «Статусы регистрации на турнир» в `MASTER.md` описывает статусы *регистрации игрока*, не статус самого турнира — это разные сущности: `TournamentRegistration.status` vs `Tournament.estado`/`TournamentStatus`) не меняются, меняется только то, какое из существующих значений выбирается автоматически для одной роли в одном сценарии (создание).

## Требования

### Функциональные
- При создании турнира (`POST /admin/tournaments`) владельцем с ролью `ROLE_CLUB_ADMIN` (`Owner.isClubAdmin() == true`) — итоговый статус созданного турнира всегда `TournamentStatus.REGISTRO_ABIERTO` ("Регистрация открыта"), **независимо** от значения, пришедшего из поля `estado` формы.
- Для остальных ролей, имеющих право создавать турниры (`SUPER_ADMIN`, `ORGANIZER` — не `ADMIN`, тому создание турниров запрещено существующей проверкой `owner.isAdminRole()`), поведение не меняется: сохраняется статус, выбранный в форме.
- Копирование турнира (`GET /admin/tournaments/{id}/copy`) рендерит ту же форму и ведёт к созданию через тот же `POST /admin/tournaments` — для клубного аккаунта результат копирования тоже получает `REGISTRO_ABIERTO`, без дополнительного кода (переиспользует ту же точку входа).
- Редактирование существующего турнира (`POST /admin/tournaments/{id}/edit`) не затрагивается этой задачей — статус там по-прежнему выбирается вручную и сохраняется как есть, для любой роли, включая клубный аккаунт («в дальнейшем статус можно менять обычной логикой управления турниром» — прямое требование клиентского запроса).
- Поле `infoDetallada` ("Дополнительная информация / Описание") не затрагивается.

### Нефункциональные
- i18n: новых пользовательских строк нет (значение статуса пишется программно, не через новый текст).
- Безопасность: новой точки входа данных от пользователя нет — наоборот, значение из формы для клубного аккаунта перестаёт влиять на итоговый статус (игнорируется так же, как уже игнорируется `clubId` из формы для той же роли, LFPT-376).

## Вне скоупа
- Скрытие/упрощение самого поля выбора статуса на форме создания для клубного аккаунта — отдельная зависимая frontend-задача [#559](https://github.com/UstinKO/padel-core-service/issues/559) (`GIT_WORKFLOW.md` §1.4: фронтенд и бэкенд — разные задачи). В рамках текущей (бэкенд) задачи поле `estado` на форме продолжает отображаться и быть обязательным для всех ролей — выбор клубного аккаунта просто перестаёт влиять на результат (симметрично существующему `clubId`, см. ниже).
- REST API `POST /api/tournaments` — не затронут: этот эндпоинт и так закрыт `@PreAuthorize("hasAnyRole('SUPER_ADMIN', 'ORGANIZER')")`, `CLUB_ADMIN` не может вызвать его в принципе.
- Любые изменения модели статусов, бизнес-правил листа ожидания или других инвариантов `MASTER.md`.

## Изменения в системе

### API
Без изменений сигнатур. Меняется только внутреннее поведение `AdminController.createTournament` (`POST /admin/tournaments`, form-эндпоинт, не JSON API).

### БД
Нет. Новой миграции не требуется — используется существующее значение `TournamentStatus.REGISTRO_ABIERTO`.

### UI
Шаблоны не меняются в этой задаче (форма `admin/tournaments/form.html` продолжает показывать и требовать выбор статуса для всех ролей — см. «Вне скоупа» и задачу #559).

### Код
`AdminController.createTournament` (`src/main/java/com/padle/core/padelcoreservice/controller/admin/AdminController.java`): рядом с уже существующим принудительным переопределением `clubId` для клубного аккаунта —

```java
if (owner.isClubAdmin()) {
    tournamentDto.setClubId(owner.getClubId());
    tournamentDto.setEstado(TournamentStatus.REGISTRO_ABIERTO);
}
```

— до вызова `tournamentService.createTournament(...)`, тем же приёмом и в том же месте, что и существующее правило LFPT-376 для `clubId` (комментарий в коде на `clubId`-строке явно объясняет этот приём: "не доверяем значению из формы"). Выбор именно контроллера, а не сервиса: `TournamentService.createTournament` используется также REST API-контроллером (`POST /api/tournaments`), который и так закрыт для `CLUB_ADMIN` на уровне `@PreAuthorize` — переопределение по роли логично держать там же, где уже есть аналогичное правило для той же роли и того же сценария (форма создания), а не размазывать по двум местам.

## Критерии приёмки
- [ ] Турнир, созданный клубным аккаунтом (`ROLE_CLUB_ADMIN`) через `/admin/tournaments/new` с явно выбранным в форме статусом, отличным от «Регистрация открыта» (например, «Черновик») — после создания имеет статус «Регистрация открыта» в БД и на странице деталей турнира.
- [ ] Турнир, созданный клубным аккаунтом без изменения статуса по умолчанию в форме — тоже «Регистрация открыта» (тривиально следует из предыдущего пункта, но проверяется отдельно, т.к. это основной пользовательский сценарий).
- [ ] Турнир, созданный `SUPER_ADMIN` или `ORGANIZER` с явно выбранным статусом (например, «Черновик») — сохраняет именно этот статус, не «Регистрация открыта» (регрессия не допускается).
- [ ] Копирование турнира (`/admin/tournaments/{id}/copy` → сохранение) клубным аккаунтом — новый турнир тоже «Регистрация открыта», независимо от статуса оригинала и выбора в форме копии.
- [ ] После создания клубным аккаунтом статус турнира можно свободно изменить через `/admin/tournaments/{id}/edit` (регресс отсутствует — поведение редактирования не изменилось ни для одной роли).
- [ ] Поле `infoDetallada` сохранённого турнира соответствует введённому в форме значению, без изменений логики.
- [ ] `./mvnw verify` — зелёный.

## Edge cases
- Клубный аккаунт отправляет форму без выбора статуса (или с некорректным значением, которое не биндится в `TournamentStatus`) — текущая валидация формы (`required` на `<select>`) уже не позволяет это сделать на уровне браузера; на уровне сервера переопределение происходит после биндинга, независимо от того, что пришло (даже если бы пришло пустое/невалидное значение и `estado` осталось `null`, переопределение всё равно явно выставляет `REGISTRO_ABIERTO` до вызова сервиса — конфликта с существующим фолбэком `TournamentService.createTournament` на `null` → `REGISTRO_ABIERTO` нет, значения совпадают).
- Конкурентный доступ (2 реплики) — не релевантно, создание турнира не имеет состояния гонки между репликами в этом сценарии (один HTTP-запрос, один владелец).
- Существующие турниры (уже созданные до этой задачи) — не затрагиваются, миграции данных нет, задача касается только пути создания новых турниров.

## Открытые вопросы
Нет — область применения (`ROLE_CLUB_ADMIN`, точка приложения, отсутствие изменений для других ролей и для редактирования) однозначно следует из клиентского запроса и существующего кода (`Owner.isClubAdmin()`, существующий аналогичный приём переопределения `clubId` в том же методе, REST API закрыт для `CLUB_ADMIN` на уровне `@PreAuthorize`).
