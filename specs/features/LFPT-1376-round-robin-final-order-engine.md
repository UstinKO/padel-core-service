# LFPT-1376: Feature многомодульный монолит, фаза 4 — отделить итоговые места дополнительных встреч

## Статус
approved

## Источник

[Issue #1376](https://github.com/UstinKO/padel-core-service/issues/1376), родитель [#1374](https://github.com/UstinKO/padel-core-service/issues/1374). Техническая постановка напрямую из поручения подготовить задачи следующей фазы после мержа PR #1372. Зависит от #1375.

## Контекст / зачем

Родитель #1374. Убрать JPA/DTO-зависимость последнего вычисления итоговых мест перед композицией результата в application.

## Связь с MASTER.md

[MASTER](../MASTER.md): круговой парный турнир, история проведения, роли и границы доменов. POINTS/SETS, личные встречи и общие места, дополнительные встречи без изменения круговой статистики, завершение/восстановление и права сохраняются. Изменения бизнес-инвариантов не требуются.

## Требования

### Функциональные

- До изменения расширить characterization RoundRobinRules.finalOrder: без дополнительных встреч, общие места SETS, финал/третье/прочие места, сдвиг оставшихся строк, pending и встреча без placementStart, стабильность входов; описать уже существующее поведение некорректных внутренних входов.
- Ввести чистый final-order engine в существующем engines. Вход — нейтральные records исходных строк/мест и назначений, результат — идентификатор исходной строки и итоговое место. Имена/DTO/entities/legacy enum в engine не передавать.
- Сохранить RoundRobinRules.finalOrder как MapStruct-адаптер с прежним Java API и RoundRobinStandingDto. Фильтрация completed/placement и интерпретация счёта соответствуют исходному коду; новых проверок/правил ничьей/конфликтов не добавлять.
- Перенести единственного владельца алгоритма; service/транзакции/начисление и SETS/POINTS прежние. Расширить artifact guard обязательными фактическими типами и отрицательными пробами; ArchUnit не ослаблять.

### Нефункциональные

Java release 17, типизированные records/порты, MapStruct на границах. Собственные синтетические данные и PostgreSQL; внешние реальные уведомления не отправляются. Каждый реализационный PR самостоятельно проходит полный verify с frontend и runtime smoke, не требует последующей задачи для восстановления. Зависимости фаз — Java в одном процессе; один boot jar.

## Вне скоупа

Перенос команд запуска/счёта/завершения и начисления, смена формул/HTTP/JSON/WS/HTML, generated ranking DTO, UI v2 switching, новые дизайн/переводы, persistence/web/integrations и физическая БД/Swarm. Проверки команды не означают её перенос; #1051 остаётся поздней задачей.

## Изменения в системе

### API

Новых endpoints нет. Сохраняются GET /tournaments/team-americano/api/{id}/ranking, public/admin MVC и ответы initialize/finish. Реальные прямые/непрямые потребители уточняет #1375; API DTO остаются в legacy на этой фазе.

### БД

Схема/Liquibase и физическое размещение сохраняются. Только собственная тестовая БД; сохраняются propagation/isolation/readOnly/flush, история и after-commit. GET не приобретает записи.

### UI

Действующие страницы/контракты сохраняются. Проверка через браузер не включает новый UI; RU/ES/EN и desktop/mobile по исходной матрице.

## Критерии приёмки

- [ ] Один и тот же characterization-набор проходит на исходной и выделенной реализации с прежними ожиданиями; engine unit-тесты работают без Spring/БД.
- [ ] finalRanking сохраняет номера/имена/места и порядок, а круговая статистика/таблица и исходные объекты не меняются.
- [ ] В engines только нейтральные типы/JDK, в bootstrap только адаптация; копии формулы нет, Java 17/artifact/ArchUnit guard проходят.
- [ ] Полный verify и реальный браузер дополнительных встреч/исправления/завершения/истории для POINTS/SETS проходят; baseline API совпал.
- [ ] Прежний jar и возврат на собственной БД сохраняют обе таблицы/матчи/строки команд и схему/Liquibase; документация и безопасный отчёт обновлены.

## Edge cases

Пустой/неинициализированный/несуществующий турнир, null scoringMode и fallback config, гостевой партнёр/уровень/сторона, частичный круг, равенства/общие места, pending и дополнительные встречи без места, исправление/restore. Чтение из write-транзакции видит её изменения; не вводятся новый isolation/lock/REQUIRES_NEW и новый commit. Отсутствие повторной ручной/физической приёмки отмечается явно. Некорректные legacy-входы не превращаются в новые бизнес-правила.

Бизнес-вопросов нет. Технические решения сохраняют существующее поведение и согласованную архитектуру.
