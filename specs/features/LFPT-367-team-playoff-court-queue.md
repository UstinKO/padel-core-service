# LFPT-367: очередь пар без назначения корта (Team Playoff, квалификация)

## Статус
approved

## Источник
GitHub issue [#367](https://github.com/UstinKO/padel-core-service/issues/367) — прямая техническая постановка от архитектора по итогам клиентского фидбека (Telegram, тема "AI Разработка"), без промежуточного файла-запроса в `specs/requests/`.

## Контекст / зачем

Квалификация Team Playoff (`TeamPlayoffService`) — court-driven: координатор вручную создаёт матч через `createQualificationMatch(tournamentId, team1Id, team2Id, courtNumber)`, сразу указывая свободный корт. Когда все корты заняты, а несколько команд уже закончили предыдущие матчи и ждут следующий, координатору приходится держать в голове очередь: кто освободился раньше и кто должен играть следующим. На 12 командах это ещё терпимо, на 16+ — уже неудобно (та же логика раньше велась вручную в Excel, см. issue).

Нужна возможность зафиксировать пару заранее, до появления свободного корта, и упорядочить такие пары по времени ожидания — чтобы координатору оставалось только назначить корт первому матчу очереди одним действием, когда корт освобождается.

## Связь с MASTER.md

Фича — техническая надстройка над существующим форматом "Team Americano / Team Playoff" ([specs/MASTER.md § Форматы турниров](../MASTER.md#форматы-турниров)), инвариантов мастер-спеки не меняет. Спортивная логика подбора соперников (победитель/победитель и проигравший/проигравший в квалификации, посев и анти-реванш в плей-офф) не затрагивается — очередь влияет только на порядок выхода уже сформированных пар на корты.

## Требования

### Функциональные

1. **Постановка пары в очередь.** Координатор может создать квалификационный матч между двумя доступными командами **без** указания корта. Матч сохраняется со статусом "в очереди" (`QUEUED`), `courtNumber = null`. С этого момента обе команды считаются занятыми (не показываются в списке доступных для новой пары, как и для обычного `IN_PROGRESS`-матча).
2. **Порядок очереди.** Пары в очереди упорядочены по времени постановки в очередь (`createdAt` матча) — раньше поставленная пара выше (дольше ждёт → выше приоритет), что соответствует ТЗ ("если одна пара ждёт уже 15 минут, а другая освободилась только что, первой должна идти та, которая ждёт дольше" — время постановки в очередь практически совпадает с моментом, когда обе команды освободились и координатор их свёл).
3. **Назначение корта.** Координатор может назначить любой свободный корт любому матчу очереди одним действием (не обязательно только первому — ручная корректировка всегда разрешена, см. `GIT_WORKFLOW.md`/`CODE_REVIEW.md` про координатора как последнюю инстанцию). После назначения матч переходит в `IN_PROGRESS`, `courtNumber` и `startedAt` заполняются, матч выходит из очереди.
4. **Изменение пары в очереди.** Координатор может заменить любую из двух команд в ещё не начатом матче очереди — переиспользуется существующий механизм `changeMatchTeam` (T11), уже поддерживающий любой незавершённый матч; предупреждение о повторной встрече показывается как обычно, но не блокирует.
5. **Удаление из очереди.** Координатор может убрать матч из очереди целиком (обе команды возвращаются в пул доступных).
6. **Публичная страница.** Команда, чей матч поставлен в очередь, видит на публичной странице турнира отдельный статус ("в очереди") вместо "ожидает", с указанием соперника и позиции в очереди (1-я / N-я).
7. **Административная панель.** Отдельный блок "Матчи в очереди" со списком (соперники, время ожидания в минутах), с действиями на каждой строке: назначить корт (выбор из свободных кортов), изменить пару, убрать из очереди.
8. Существующая форма создания матча (`Nuevo partido`) получает вторую кнопку — поставить в очередь (без выбора корта), рядом с уже существующей "создать матч на корте".

### Нефункциональные

- i18n: новые пользовательские строки (статус "в очереди", позиция в очереди, время ожидания, кнопки "Назначить корт"/"Убрать из очереди", подсказки) — в `messages_es/ru/en.properties`.
- Realtime: изменения очереди транслируются через уже существующий канал `/topic/team-playoff/{tournamentId}` (`WebSocketService`) — оба потребителя (admin/public) уже подписаны на любое обновление и перерисовывают/перезагружают страницу, отдельного нового клиентского кода для подписки не требуется.
- Не требует новой Liquibase-миграции: `americano_matches_db.status` — `VARCHAR(20)` без CHECK-constraint, `court_number` уже `NULL`-able, `created_at` уже проставляется автоматически (`@CreationTimestamp`) и используется как момент постановки в очередь.

## Вне скоупа

- Плей-офф: там корты для всей стадии выделяются сразу при посеве матчей (`courts(pairs.size())`), свободных кортов в процессе стадии не появляется — очередь для плей-офф не нужна и не реализуется.
- Автоматическое назначение корта первому в очереди при освобождении корта (например, при сохранении результата) — координатор нажимает действие сам; полностью автоматический перевод не запрошен и добавляет риск (что если корт нужен для другого приоритетного матча).
- Изменение спортивного алгоритма подбора соперников (кто с кем играет) — не меняется, очередь только про порядок выхода на корты уже сформированных пар.

## Изменения в системе

### API (`/tournaments/team-playoff`, тот же `TeamPlayoffViewController`)

| Method | URL | Описание |
|--------|-----|----------|
| POST | `/api/{tournamentId}/qual-matches/queue` | Body `{team1Id, team2Id}` — поставить пару в очередь без корта |
| POST | `/api/matches/{matchId}/assign-court` | Body `{courtNumber}` — назначить корт матчу из очереди, перевести в `IN_PROGRESS` |
| POST | `/api/matches/{matchId}/queue/remove` | Убрать матч из очереди (только пока `QUEUED`) |
| GET | `/api/{tournamentId}/court-board` | Существующий endpoint — ответ дополняется полем `queue`: список матчей в очереди (упорядочен), каждый с `queuePosition` и `waitingMinutes` |

Существующие `/api/matches/{matchId}/team` (изменить пару) и `/api/{tournamentId}/ranking` переиспользуются без изменений сигнатуры — только расширяется состав данных, которые они возвращают (см. DTO ниже).

### БД

Без новой миграции — используются существующие колонки `americano_matches_db.status` (новое значение enum `QUEUED`, хранится как строка), `court_number` (остаётся `NULL` пока матч в очереди), `created_at` (момент постановки в очередь).

### UI

- `src/main/resources/templates/admin/americano/tournament-playoff.html` — новый блок "Matches en cola" между "Nuevo partido" и раундами квалификации; вторая кнопка в форме "Nuevo partido" — "Agregar a la cola".
- `src/main/resources/templates/tournaments/team-playoff/view.html` — новый кейс `QUEUED` в статусной колонке таблицы рейтинга (позиция в очереди + соперник).

## Критерии приёмки

- [ ] Координатор ставит пару команд в очередь без указания корта → матч создаётся со статусом "в очереди", `courtNumber = null`, обе команды пропадают из списка доступных для новой пары (`GET /api/{tournamentId}/court-board` → `availableTeams`/`teamGroups`).
- [ ] Попытка поставить в очередь команду, уже занятую (в матче `IN_PROGRESS` или уже в очереди) → 400/ошибка с понятным сообщением, как для обычного `createQualificationMatch`.
- [ ] Два матча поставлены в очередь один за другим (с задержкой) → `GET /api/{tournamentId}/court-board` возвращает `queue` с более ранним матчем первым (`queuePosition = 1`) и корректным `waitingMinutes` у обоих (первый ≥ второго).
- [ ] Координатор назначает свободный корт матчу из очереди (`POST /api/matches/{matchId}/assign-court`) → матч переходит в `IN_PROGRESS`, `courtNumber` заполнен, `startedAt` проставлен, матч пропадает из `queue`, корт в `court-board.courts` отмечен занятым этим матчем.
- [ ] Попытка назначить уже занятый корт матчу из очереди → ошибка "La cancha N está ocupada", матч остаётся в очереди.
- [ ] Попытка назначить корт матчу, который не в очереди (уже `IN_PROGRESS`/`COMPLETED`) → ошибка, ничего не меняется.
- [ ] Координатор меняет одну из команд матча в очереди (`POST /api/matches/{matchId}/team`) → матч остаётся в очереди с новой командой, старая команда возвращается в пул доступных, новая — занята.
- [ ] Координатор убирает матч из очереди (`POST /api/matches/{matchId}/queue/remove`) → матч удаляется, обе его команды снова доступны для новой пары.
- [ ] Публичная страница турнира (`GET /tournaments/team-playoff/{tournamentId}`) для команды, чей матч в очереди: `tournamentStatus = "QUEUED"`, `queuePosition` и `queueOpponentName` заполнены корректно (1-я/N-я позиция).
- [ ] Существующие сценарии не сломаны: `createQualificationMatch` (матч сразу с кортом) по-прежнему работает и не считается "в очереди"; команды с завершёнными 2 квалификационными матчами по-прежнему не предлагаются как доступные.

## Edge cases

- Пустая очередь → `court-board.queue` — пустой список, блок "Matches en cola" в админке показывает соответствующее сообщение, ничего не падает.
- Команда, стоящая в очереди, случайно выбрана координатором для новой пары через обычную форму — заблокировано на уровне валидации (`isActive()` учитывает `QUEUED` как занятость), как и для `IN_PROGRESS`.
- Все корты заняты весь турнир, в очереди накопилось много пар — очередь ничем не ограничена по длине, сортировка стабильна по `createdAt`.
- Обе команды матча из очереди уже отыграли лимит в 2 квалификационных матча к моменту, когда координатор пытается назначить корт (например, ошибочно поставил в очередь до завершения последнего разрешённого) — не проверяется повторно при `assignCourtToQueuedMatch` (лимит проверяется только при постановке в очередь/создании матча, как и в существующем `createQualificationMatch`, который тоже не перепроверяет лимит на более поздних шагах типа `changeMatchCourt`).

## Открытые вопросы

Нет открытых вопросов, требующих решения заказчика — постановка задачи (issue #367) уже содержит достаточно конкретики по бизнес-правилам (порядок очереди по времени ожидания, действия координатора, что видят игроки). Технические решения (переиспользование `createdAt` вместо новой колонки, scope только на квалификацию, отсутствие автоматического назначения корта) сделаны самостоятельно и обоснованы выше в "Вне скоупа"/"Требования".
