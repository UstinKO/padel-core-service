## Контекст / зачем

Монолит сложно сопровождать. Нужно подготовить обоснованный переход к проверяемым границам модулей и доменной модели, а не механически разложить пакеты. Подготовительный результат — документы, решения и последовательный бэклог; реализация приложения отдельными задачами.

## Связь с MASTER.md

Сохраняются все роли/клубные права, форматы, регистрация/резерв, отмены, оплаты, история и дополнительные очки. Изменения бизнес-инвариантов не планируются. По прямому решению владельца раздел «Границы доменов» MASTER уточнён: ближайшая цель — многомодульный монолит, без внутреннего HTTP; исторический микросервисный план остаётся справочным материалом. Бизнес-правила сохранены.

## Требования

### Функциональные

- Подготовить `docs/modular-monolith/`: анализ текущего состояния, целевую схему, ADR, план и вопросы/риски.
- Предложить число модулей без ограничения пятью, размещение домена/портов/bootstrap, порядок compile-зависимостей и адаптеров.
- Описать генерацию OpenAPI JSON → API DTO, совместимость с текущим стеком и принятое направление вместо прежнего Java → OpenAPI. Generated Java не коммитится и не обязана быть record; узкое исключение внесено в CODE_STYLE.
- Разрешить Spring service/transaction в application, сохраняя ACID и запрет зависимостей на адаптеры.
- Отложить persistence/Liquibase и инфраструктурный переезд БД; пилот сохраняет действующие пути/подключение.
- Исходная e2e-задача #1048 фиксирует поведение до переноса; #1045 повторяет матрицу после. Обе включают скрипты/Playwright и отдельный ручной проход.
- Инвентаризировать зависимости, транзакции, пути сборки/доставки и ресурсы; отделить факты от предложений и неизвестных.
- Разложить реализацию на небольшие задачи с результатом, зависимостями, проверками и откатом. После согласования завести реальные issues, проверить дубли и связать зависимости.
- Сделать сохранение работоспособности всего приложения критерием каждой задачи; зависимость от следующего PR для восстановления работы запрещена.

- Сохранять Java release 17; не совмещать перенос с upgrade стека или бизнес-рефакторингом.
- Не включать секреты, приватные адреса и runtime-состояние в документы/issue.

## Edge cases

- Нельзя перенести entity без цикла: сначала меньшая задача на границу; приложение продолжает использовать старый путь.
- Генератор не совместим с Jackson 3/Jakarta/MapStruct: зафиксировать результат проверки и альтернативы; не добавлять несовместимую зависимость.
- Переезд Liquibase меняет путь: сохранить идентичность; не сбрасывать checksum и не пересоздавать существующие базы.
- Две реализации записи/доставки не должны одновременно выполнять побочные эффекты.
- Конкурентные записи и несколько реплик: сохранить действующие транзакции/блокировки; новых гарантий Swarm эта задача не вводит.
- Параллельные React/Swarm-задачи меняют пути/контракты: обновить зависимости перед началом конкретного переноса.
