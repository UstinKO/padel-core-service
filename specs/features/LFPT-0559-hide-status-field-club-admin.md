# LFPT-0559: Feature форма создания турнира — скрыть выбор статуса для клубного аккаунта (фронтенд)

Telegram-сообщение (для reply): 5068

## Контекст / зачем

LFPT-0558 сделал так, что выбор статуса в форме создания турнира клубным аккаунтом (`ROLE_CLUB_ADMIN`) больше ни на что не влияет — `AdminController.createTournament` принудительно переопределяет `estado` на `REGISTRO_ABIERTO`. Но само поле `estado` (обязательный `<select>` с шестью значениями) по-прежнему отображается на форме — это создаёт визуальную путаницу: клуб вынужден выбирать значение, которое будет проигнорировано. Задача — скрыть поле там, где оно бессмысленно (создание, копирование), и оставить его там, где оно по-прежнему работает (редактирование).

## Связь с MASTER.md

Не меняет инвариантов. Роль `ROLE_CLUB_ADMIN` и её ограниченная видимость/управление своим клубом уже описаны (`specs/MASTER.md` § Роли пользователей) и не меняются — это чисто визуальное упрощение формы, бизнес-поведение (какой статус получает турнир) уже зафиксировано в LFPT-0558 и этой задачей не меняется.

## Требования

### Функциональные
- На форме **создания** турнира (`GET /admin/tournaments/new`, шаблон `admin/tournaments/form.html`) — для владельца с `Owner.isClubAdmin() == true` поле «Estado del Torneo» (`estado`) не рендерится вообще (не просто визуально скрыто, а не выводится в DOM — `th:if`/`th:unless`, не `display:none`).
- На форме **копирования** (`GET /admin/tournaments/{id}/copy`, тот же шаблон, тот же признак "создание" — `tournament.id == null`) — для клубного аккаунта поле тоже не рендерится.
- На форме **редактирования** существующего турнира (`GET /admin/tournaments/{id}/edit`) — поле статуса остаётся видимым и редактируемым для клубного аккаунта без изменений (прямое требование issue — «в дальнейшем статус можно менять обычной логикой управления турниром»).
- Для `SUPER_ADMIN`/`ORGANIZER` поле видно на всех трёх формах (создание/копирование/редактирование) без изменений — обе роли могут создавать турниры (`!owner.isAdminRole()`), `ADMIN`-роли создание турниров запрещено существующей проверкой и до рендера формы не доходит.
- Когда поле скрыто и форма отправлена (без значения `estado` в теле запроса) — поведение не меняется относительно уже задеплоенного LFPT-0558: `AdminController.createTournament` переопределяет `tournamentDto.setEstado(REGISTRO_ABIERTO)` для клубного аккаунта **до** использования значения, независимо от того, пришло оно из формы или нет. В `TournamentDto` на поле `estado` нет bean-validation аннотаций (`@NotNull`/`@NotBlank` и т.п.) — отсутствие параметра `estado` в form-POST не вызывает ошибку валидации (`bindingResult.hasErrors()`), сервисный фолбэк `TournamentService.createTournament` (`estado == null → REGISTRO_ABIERTO`, строки 683-684) в любом случае совпадает по значению с принудительным переопределением контроллера.
- Повторный рендер формы создания после ошибки валидации (ветка `bindingResult.hasErrors()` в `createTournament`) должен скрывать поле так же, как и первичный `GET /admin/tournaments/new` — иначе при ошибке в другом поле клубный аккаунт на мгновение увидит статус-селект, которого не было на первом рендере.

### Нефункциональные
- i18n: новых пользовательских строк нет — существующие ключи (`admin.tournaments.form.field.status`, `enum.estado.*`) не меняются, просто условно не рендерятся.
- Безопасность: новой точки входа данных от пользователя нет. Наоборот — физическое отсутствие поля в DOM для клубного аккаунта исключает даже теоретическую отправку произвольного `estado` через модифицированный HTML-запрос с каким-либо практическим эффектом (бэкенд и так его игнорирует после LFPT-0558, это чисто defense-in-depth на уровне "нечего посылать").

## Вне скоупа
- Любые изменения `AdminController`/`TournamentService`/бизнес-логики статуса — всё уже сделано в LFPT-0558. Эта задача — только шаблон + минимальная передача флага роли в модель.
- REST API `POST /api/tournaments` — не рендерит эту форму, не затронут.
- Форма `admin/tournaments/{tournamentId}/payments` и другие формы турнира, не связанные с `estado`, — не затронуты.

## Изменения в системе

### API
Без изменений сигнатур контроллеров. Добавляется только новый model-атрибут `isClubAdmin` (boolean) на точках, которые рендерят форму **создания/копирования**:
- `AdminController.newTournamentForm` (`GET /admin/tournaments/new`)
- `AdminController.createTournament`, ветка `bindingResult.hasErrors()` (повторный рендер формы создания)
- `AdminTournamentCopyController.copyTournament` (`GET /admin/tournaments/{id}/copy`)

На форме **редактирования** (`AdminController.showEditForm`, `AdminController.updateTournament` ветка ошибок) атрибут не добавляется — там он не нужен: условие в шаблоне уже завязано на `tournament.id == null` (true только для создания/копирования, false для редактирования), поэтому даже без атрибута `isClubAdmin` на странице редактирования поле не скрывается (SpringEL `and` — короткое замыкание, правая часть `isClubAdmin == true` не вычисляется, когда `tournament.id == null` ложно).

### БД
Нет изменений.

### UI
`src/main/resources/templates/admin/tournaments/form.html` — секция «Estado y Fechas Límite», блок поля `estado`:
- Обёртка `form-group` получает `th:if="${tournament.id != null or isClubAdmin != true}"` (эквивалент «не (создание И клубный аккаунт)»).
- Атрибут `required` на `<select>` переводится в `th:if`-зависимый рендеринг того же выражения (поле либо полностью в DOM с `required`, либо отсутствует — отдельного «видимо, но необязательно» состояния не нужно).

## Критерии приёмки
- [ ] `GET /admin/tournaments/new` под клубным аккаунтом (`ROLE_CLUB_ADMIN`) — в HTML-ответе нет `id="estado"` (поле отсутствует в DOM).
- [ ] `GET /admin/tournaments/{id}/copy` под клубным аккаунтом — в HTML-ответе нет `id="estado"`.
- [ ] `GET /admin/tournaments/{id}/edit` под клубным аккаунтом — `id="estado"` присутствует, `<select>` содержит все значения `TournamentStatus`, действующий статус турнира выбран (`selected`), сохранение формы с изменённым статусом работает как раньше (регресс отсутствует).
- [ ] `GET /admin/tournaments/new` и `GET /admin/tournaments/{id}/copy` под `SUPER_ADMIN` и под `ORGANIZER` — поле `estado` присутствует и обязательно, поведение не изменилось (регресс отсутствует).
- [ ] `GET /admin/tournaments/{id}/edit` под `SUPER_ADMIN`/`ORGANIZER` — поле присутствует, без изменений.
- [ ] Отправка формы создания клубным аккаунтом (без поля `estado` в DOM, соответственно и в теле POST-запроса) — турнир создаётся успешно со статусом «Регистрация открыта», без ошибки валидации формы.
- [ ] `./mvnw verify` — зелёный.

## Edge cases
- Клубный аккаунт модифицирует HTML/отправляет POST-запрос с произвольным `estado` напрямую (минуя UI) — не релевантно этой фронтенд-задаче: бэкенд уже (LFPT-0558) игнорирует любое значение `estado` из формы для `ROLE_CLUB_ADMIN` и принудительно подставляет `REGISTRO_ABIERTO` до вызова сервиса. Эта задача только убирает лишний визуальный элемент, не является единственным рубежом защиты.
- Повторный рендер формы создания/копирования после ошибки валидации другого поля (например, пустая `fechaInicio`) — должен сохранять то же скрытие `estado` для клубного аккаунта (см. требование выше, учтено явной передачей `isClubAdmin` в ветке `bindingResult.hasErrors()`).
- Пользователь без роли (`isAdminRole() == true`, т.е. `ADMIN`) — уже отфильтровывается существующей проверкой `owner.isAdminRole()` в начале методов `newTournamentForm`/`createTournament`/`copyTournament` (редирект до рендера формы) — этот сценарий не затронут и не тестируется в рамках этой задачи.
