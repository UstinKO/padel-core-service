# LFPT-0900: Feature backend отмена участия — мягкий статус, инициатор и причина без удаления истории

## Статус

approved — реализация технического плана подтверждена пользователем 2026-11-11.

## Источник

Напрямую из [issue #900](https://github.com/UstinKO/padel-core-service/issues/900). Продолжение блока UI v2 после #903/#911. Связанные задачи: #759 → #760 → #902 → #910; booking #909 дополнительно зависит от #901. Здесь реализуется только #900, без обещания готовности зависимых экранов.

## Контекст / зачем

Описание issue частично устарело: #792 уже заменил физическое удаление регистрации мягкой отменой, сохранил платежи/атрибуцию, блокировку турнира и отправку писем после commit. #673 уже исправил выбор письма для пары в резерве. Повторять эти реализации не требуется.

Оставшийся пробел: у регистрации есть только cancellationDate/cancellationReason, без структурированного инициатора и устойчивого кода. При повторной записи используется тот же регистрационный ряд, его поля отмены очищаются. Поэтому текущий ряд не может быть единственным источником истории для будущего кабинета #902/#910. Нужен сохраняемый факт каждого завершённого перехода в отмену, включая повторные циклы записи.

## Связь с MASTER.md

Используются правила сохранения места оставшегося участника пары, отсутствия продвижения резерва при выходе одного участника, освобождения места при отмене всей заявки и сохранения платежей/истории. Допуски, сроки отмены и денежные условия PairTermsService/PairCancellationPolicy сохраняются. Подтверждение участия и новая модель приоритетов резерва не вводятся.

MASTER дополнить описанием устойчивой истории отмен и источника безопасной причины. Правило допуска к отмене и правила оплаты не менять. В MASTER остаётся устаревшее описание временного WAITLIST_INVITED; его полный пересмотр относится к #759, не выполняется попутно.

## Требования

### Функциональные

1. Сохранить CANCELLED/is_active=false, ID регистраций, платежи и маркетинговые связи. Не заменять существующее переиспользование регистрационного ряда созданием дублей или изменением его уникальности.
2. Ввести структурированный контекст отмены: тип инициатора PLAYER/OWNER/SYSTEM/UNKNOWN, внутренний идентификатор при наличии, область PARTICIPANT/PAIR, время события, устойчивый reasonCode. Тип инициатора и код выводятся из проверенного пути выполнения; их нельзя подставить из пользовательского тела запроса или определить разбором свободного текста.
3. Добавить неизменяемую историю отмен: событие операции и затронутые регистрационные ряды/участники, исходные статусы и необходимые идентификаторы пары. Полная отмена пары — одна операция с двумя затронутыми рядами; выход одного — другая операция. При отсутствии UUID у старой пары использовать действующий resolver состава, без объединения чужих заявок по одному игроку.
4. Повторный запрос к уже отменённому состоянию возвращает фактический результат и не создаёт новое событие/письмо/продвижение. Повторная отмена после новой успешной регистрации создаёт новое событие и не меняет прежнее. Конкурирующие отмены сериализуются существующей блокировкой турнира; отказ проверки прав/срока/токена ничего не записывает.
5. Переиспользовать общий сервис перехода/фиксации факта отмены из существующих входов: самостоятельная индивидуальная/solo-отмена, выход из пары, полная отмена пары и PairTerms confirmation, удаление организатором, Americano, отмена по ссылке резерва, замена игрока, массовая отмена при деактивации. Разные правила допуска этих входов сохраняются; объединение записи факта не унифицирует их полномочия.
6. Проверять права до обработки повторов. Старый токен или запрос с версией не может отменить заново активированную заявку. Для player cancel/cancel-double добавляется необязательный If-Registration-Version; текущая cancellationVersion доступна в DTO своей регистрации. Старый запрос без версии остаётся совместимым: отличить его задержавшийся повтор от нового пользовательского действия после повторной записи технически невозможно; это ограничение явно указывается в отчёте. Повтор полной отмены по PairTerms возвращает уже сохранённое состояние только после проверки принадлежности, без нового расчёта/создания финансового обязательства. Подтверждённые условия и данные pair_cancellations_db не переписываются.
7. Причины разделить машинным кодом: выход участника, отмена всей заявки участником, удаление организатором, системная деактивация, замена участника, неизвестная историческая отмена. Для отмены через ссылку резерва фиксировать выход участника и канал операции, не объявлять предъявителя токена подтверждённым владельцем профиля. Точный набор enum и DTO фиксируется при реализации и описывается в контракте.
8. Свободный текст хранить отдельно от кода. Разрешённый комментарий организатора — обычный текст с ограничением длины, без HTML и автоматического перевода; подписи причин локализуются ES/RU/EN. Ошибка БД, исключение или внутренний служебный reason не становятся пользовательской причиной.
9. Дать типизированную безопасную проекцию для будущего кабинета #902: время/код/область отмены и допустимый комментарий. Обычный игрок читает только собственную историю; OWNER/CLUB_ADMIN — только события управляемого турнира, SUPER_ADMIN — по действующим полномочиям. В публичные event/live DTO, поиск партнёра и ответы постороннему игроку комментарий/аудит не включаются. Внутренний actorId не входит в пользовательскую проекцию.
10. Изменение регистрации, запись события, изменение оставшегося участника и существующее продвижение резерва — одна транзакция. Письма после commit; rollback не оставляет событий и не отправляет письма. Новая долговременная очередь доставки не добавляется.
11. Если остаётся второй участник, его место и допустимое время заявки сохраняются. При отмене всей заявки продвижение запускается один раз, а не по одному разу на ряд. Полный редизайн подсчёта мест/queued_at/готовности пары не входит в #900.

### Нефункциональные

- Java release 17, типизированные record DTO, MapStruct для проекций, доменные операции в сервисах. Без Map<String,Object> в новых контрактах.
- Существующие маршруты, HTTP-методы и обязательные поля ответов legacy/mobile сохраняются. Не менять source mobile-app и собранный /app ради нового read-contract.
- Историю читать пакетно с индексами по регистрации/участнику и времени, без запроса на каждую строку. Не раскрывать другие заявки/контакты через связь пары.
- Новые причины/ошибки ES/RU/EN. Логи не содержат свободных комментариев, токенов, полных контактов или снимков приватного запроса.

## Вне скоупа

Новая очередь резерва #759, participation_status и письма подтверждения #760, guest claim #901, кабинет и его новые REST-маршруты #902, React #909/#910, изменение сроков/цен/возвратов, удаление WAITLIST_INVITED, OAuth, production-переключение, деплой, новая outbox-доставка. Физическое удаление синтетических данных тестового инструмента не подменять пользовательской отменой.

## Изменения в системе

### API

Обновляются делегаты существующих player/admin/Americano/reserve/PairTerms путей отмены. Внутренний типизированный результат сообщает changed/no-op и фактическое состояние; текущие внешние success/message и PairTerms ответы сохраняются. Новый публичный endpoint истории не добавляется: кабинетный REST-контракт остаётся #902. Безопасное чтение предоставляется общим сервисом с проверкой принадлежности для последующего подключения.

### БД

Новая Liquibase-миграция после текущей версии для структурированного события отмены и его участников; ранее применённые миграции не менять. История не удаляется и не переписывается при реактивации строки регистрации. Индексы и уникальность защищают одно событие одного перехода, допуская следующий цикл регистрации/отмены.

Backfill только для сохранившихся CANCELLED-строк: LEGACY_UNKNOWN/UNKNOWN, известное время отмены при наличии. Не определять инициатора по cancellationReason, не делать старый служебный текст публичным, не подставлять время миграции вместо неизвестного времени события. Удалённые прежде строки и стёртые при старой реактивации факты достоверно восстановить невозможно; это ограничение явно документируется. Новые таблицы не должны создавать каскадное удаление платежей/атрибуции или неожиданные права на удаление профиля.

### UI

Новая вёрстка не добавляется. Существующие формы/мобильные операции сохраняют контракт; любые необходимые изменения видимых элементов оформляются отдельной frontend-задачей. Для технической регрессии существующие self/pair/reserve пути проверяются браузером.

## Критерии приёмки

- [ ] Индивидуальная, solo и парная отмены сохраняют регистрационные ID, платежи, источник и другие мероприятия игрока; новая регистрация не стирает предыдущее событие отмены.
- [ ] Инициатор/область/код соответствуют фактическому пути player/owner/system/token; передача чужого actor/reasonCode в запросе не даёт подменить аудит.
- [ ] Выход главного и второго участника одинаково сохраняет место оставшегося; отмена всей пары меняет оба ряда и освобождает одно место.
- [ ] Повтор и два конкурентных запроса создают один переход, одно событие и не дублируют письмо/продвижение. Новый цикл записи создаёт отдельное событие.
- [ ] Старый токен после реактивации/замены состава не отменяет новую заявку; PairTerms retry не создаёт повторную денежную запись.
- [ ] Принудительная ошибка БД/rollback откатывает состояние и историю, писем нет; успешные уведомления используют существующий after-commit механизм.
- [ ] Посторонний игрок/другой клуб не видит историю и комментарии; авторизованный участник получает только разрешённую проекцию без internal actor/контактов/исключений.
- [ ] Старые CANCELLED-строки мигрируют без выдуманного инициатора/времени; существующие legacy/mobile ответы и денежные условия не меняются.
- [ ] Unit/integration/authorization/concurrency и миграционные тесты проходят; полный ./mvnw verify выполняется на отдельной PostgreSQL, docs-drift и необходимые проверки конвейера без ошибок.
- [ ] Реальный браузер подтверждает сохранность существующей индивидуальной/парной/резервной отмены; GET-ссылки не выполняют отмену.
- [ ] Один итоговый backend-коммит и PR с Closes #900; новые бизнес-правила и производственный деплой не добавлены.

## Edge cases

Повторная отмена после успешной записи, реактивация того же регистрационного ID, старая пара без booking UUID, выход любого участника, неполная основа/резерв, параллельные self/pair/admin-запросы, изменение оплаты/условий между preview и POST, истёкший/пересланный токен, rollback, активное проведение Americano, деактивация игрока с несколькими турнирами, старые CANCELLED без даты, служебный reason и вредоносный свободный текст, удалённый профиль инициатора, конкурирующая регистрация при освобождении места.

## Проверка реализации

- `./mvnw verify`: 923 теста, 0 ошибок, 1 пропуск; отдельная PostgreSQL, без использования пользовательской БД.
- Миграционный тест проверяет старые отмены с известной и неизвестной датой, отсутствие выдуманного инициатора и сохранность истории при удалении синтетической регистрации.
- Интеграционные тесты покрывают права, повторные циклы, конкурентную отмену, откат транзакции, версию регистрации, повтор PairTerms и сохранение места партнёра.
- Playwright проверил действующие формы индивидуальной и парной отмены, выход одного участника, повтор PairTerms, ссылку резерва без побочного действия GET, действие организатора и приватность комментария. Дополнительно проверены строки истории в тестовой БД; письма перехвачены локальным SMTP-приёмником. Собственный экземпляр остановлен, синтетические данные удалены.
- `docs-drift.py`, `check-agent-migration.py`, 48 тестов конвейера и `git diff --check` прошли.
- Ограничение совместимости: старый запрос без `If-Registration-Version` после новой записи нельзя отличить от нового действия. Новые клиенты используют текущую `cancellationVersion`; старая история, уже удалённая или затёртая до миграции, не восстанавливается.

### Уточнение CI

Первый PR Check остановился при установке дополнительных шрифтов через apt: runner не разрешал имя azure.archive.ubuntu.com. Нужные Chromium библиотеки уже были установлены. В задании frontend используется `playwright install chromium` без повторной установки системных пакетов; обязательные браузерные тесты и проверка зависимостей самим Playwright сохранены.

Повторный CI подтвердил успешные frontend и build, но browser-marketing остановился при загрузке системных библиотек: runner не разрешал ни Azure-зеркало, ни официальный archive.ubuntu.com. Задание browser-marketing использует официальный контейнер `mcr.microsoft.com/playwright:v1.64.1-noble` с уже установленными Chromium/WebKit и системными библиотеками. npm-пакет закреплён на той же версии. Тестовый PostgreSQL доступен по имени сервиса postgres; локальный запуск по умолчанию сохраняет localhost. Maven запускается через wrapper проекта, поскольку образ не обязан содержать Maven. Обращений к apt и ослабления браузерных проверок нет.
