# LFPT-0679: Feature расширить поиск партнёра (телефон/Telegram) и добавить подсказки при ручном вводе (backend)

## Статус
approved

## Источник
Клиентский запрос [specs/requests/LFPT-0679-poisk-partnera-podskazki.md](requests/LFPT-0679-poisk-partnera-podskazki.md) (Telegram, `telegram_launch_message_id: 5384`, отправитель customer). GitHub issue [#679](https://github.com/UstinKO/padel-core-service/issues/679). Разбито на бэкенд/фронтенд (`GIT_WORKFLOW.md` §1.4) — эта спека покрывает бэкенд. Фронтенд — [#680](https://github.com/UstinKO/padel-core-service/issues/680), спека [LFPT-0680-poisk-partnera-frontend.md](LFPT-0680-poisk-partnera-frontend.md).

## Контекст / зачем

`GET /api/players/search?query=...&tournamentId=...` (`PlayerContactController.searchPartners` → `PlayerService.searchPartnerCandidates` → `PlayerRepository.searchPartnerCandidates`) — единственный поиск партнёра в модалке парной регистрации (`tournament-details.html`). Сейчас ищет только по `nombre`/`apellido`/`email`. `PlayerPadel` уже хранит `telefono` и `telegramUsername` (оба поля существуют, миграция не нужна), но поиск по ним не ведётся — заказчик жалуется, что пользователи не находят уже зарегистрированного партнёра по телефону/Telegram и создают дублирующийся профиль вручную (та же проблема количественно оценена в #677 «Аудит дублей игроков»).

## Связь с MASTER.md

Не меняет инварианты. Опирается на §«Флоу парной регистрации» — результат поиска используется ровно так же, как сейчас (`existingUserId` в `PartnerRegistrationDto`), только находит больше реальных совпадений.

## Требования

### Функциональные

1. **Поиск по телефону.** `PlayerRepository.searchPartnerCandidates` — добавить ветку `OR`, сопоставляющую `p.telefono` с цифровой частью `query` без учёта `+`, пробелов, тире и скобок (`REPLACE` в JPQL, по аналогии с тем, что `PlayerDuplicatesAuditService` уже делает в Java для аудита — здесь делаем в SQL, чтобы не терять `LIMIT`/пагинацию). Ветка активируется только если `query` после удаления всех нецифровых символов содержит **не менее 4 цифр** — короче нельзя считать значимым фрагментом телефона (избегаем «ошибочного сопоставления разных номеров» из клиентского запроса и не даём короткому цифровому фрагменту схлопнуться в «найти всех с любым телефоном»). Параметр считается в `PlayerService.searchPartnerCandidates` и передаётся в репозиторий как `phoneDigits` (`null`, если условие не выполнено — тогда ветка в `WHERE` не матчит).
2. **Поиск по Telegram.** Ещё одна ветка `OR`: `p.telegramUsername` без учёта регистра и без учёта лидирующего `@` (`REPLACE(..., '@', '')`, `LOWER(...)`) сравнивается с `query` в том же виде. Активна всегда (как и поиск по имени/фамилии/email), без доп. условий на длину — Telegram username может быть коротким.
3. **Имя/фамилия/email — без изменений** (уже работают, условие в задаче не просит их трогать).
4. **Остальная логика метода не меняется**: исключение самого игрока (`excludeId`) и уже активно зарегистрированных на этот турнир (`tournamentId`) — как сейчас; лимит результатов — как сейчас (`PageRequest.of(0, 15)`).
5. **Rate limiting** — не вводить новый механизм. `/api/players/search` уже подпадает под `RateLimitFilter.LimitType.API` (60 запросов/мин на IP, см. `RateLimitFilter.classifyPath`) — этого достаточно для защиты от массового перебора контактных данных через этот эндпоинт (переиспользование существующего паттерна, `CODE_REVIEW.md` §2); отдельный Bucket4j-бакет не создаётся.

### Нефункциональные

- **Нормализация телефона** — эвристика, не полноценный парсер (как и в #677): убрать `+`, пробелы, `-`, `(`, `)` из обеих сторон сравнения через `REPLACE`, сравнивать как substring (`LIKE '%...%'`), не по точному совпадению длины. Ограничение (не 100% надёжно отличает похожие, но разные, короткие номера) — задокументировать в `docs/endpoints/`.
- **Производительность**: запрос остаётся одним JPQL-запросом с `LIMIT` (через `Pageable`), без доп. запросов к БД и без полной загрузки таблицы игроков в память — дополнительные `OR`-ветки не меняют этот профиль.
- **i18n**: пользовательских строк на бэкенде нет (ответ — тот же `PlayerResponseDto`, как сейчас).
- **Безопасность**: доступ как сейчас — `GET /api/players/search` только для аутентифицированных (`Authentication` обязателен, принцип текущего кода: `PlayerContactController.searchPartners` берёт `authentication.getPrincipal()`). Новых полей ответа не добавляется, значит новых данных не раскрывается сверх того, что эндпоинт уже отдаёт (полный `telefono`/`email` в `PlayerResponseDto` — существующее поведение, не предмет этой задачи).

## Вне скоупа

- Жёсткая серверная защита от создания дублей при самом создании партнёра (явное ограничение клиентского запроса — отдельная будущая задача, продолжение #677).
- Новое поле `telegramUsername` в `PlayerPadel` — уже существует (`CLAUDE.md`, `PlayerContactController.updateContact`), миграция не нужна.
- Изменение структуры `PlayerResponseDto` (какие поля отдаёт поиск) — фронтенд (#680) сам решает, что показывать в UI; бэкенд не вводит отдельный «урезанный» DTO для этого эндпоинта (не запрошено, не считается расширением скоупа без явной причины).
- Любые изменения `TestTournamentController.searchPlayers`/`searchActivePlayers` (LFPT-0561) — отдельный, не связанный с этой формой инструмент.
- Новый отдельный rate-limit бакет для этого эндпоинта — переиспользуется существующий `API`-лимит (см. «Функциональные» п.5).
- Любые изменения режимов «Ищу партнёра» (`SEARCH`)/«Добавлю партнёра позже» (`ADD_LATER`) — не затронуты, они не используют этот поиск.

## Критерии приёмки

- [ ] Поиск по телефону: игрок с `telefono = "+5491122334455"` находится по запросу `"01122334455"` (разный формат, те же цифры) и по запросу `"91122334455"`.
- [ ] Поиск по телефону: запрос из 3 и менее цифр не возвращает список "всех, у кого есть телефон" — ветка телефона не активируется (сравнить с результатом до изменения, где такого фильтра телефона не было вовсе — теперь он не включается слишком рано).
- [ ] Поиск по Telegram: игрок с `telegramUsername = "@Ivan_Petrov"` находится по запросу `"ivan_petrov"` (без `@`, другой регистр) и по запросу `"@Ivan_Petrov"`.
- [ ] Поиск по имени/фамилии/email — не регрессировал (существующие сценарии работают как раньше).
- [ ] Результат не включает самого текущего игрока и игроков, уже активно зарегистрированных на указанный турнир (регрессия на существующую логику `excludeId`/`tournamentId`).
- [ ] Результат ограничен 15 записями (как сейчас).
- [ ] `python3 .github/bin/docs-drift.py` — 0 расхождений после обновления документации.
- [ ] `./mvnw verify` зелёный.

## Edge cases

- Запрос состоит только из цифр, совпадающих с частью номера **другого** турнира/игрока лишь частично (например, запрос `"1122"` и в базе есть номера `...1122...` у двух разных людей, не являющихся дублями друг друга) — оба находятся, это ожидаемо (как и в обычном `LIKE`-поиске по имени — находим кандидатов, окончательное решение о выборе — за пользователем).
- Игрок без телефона (`telefono = null`) — не падает и не совпадает с телефонным запросом (NULL не матчит `LIKE`).
- Игрок без Telegram (`telegramUsername = null`) — аналогично, не совпадает и не вызывает ошибку.
- Запрос с `@` где-то в середине строки (не только в начале) — `REPLACE` убирает все `@` из запроса и из сохранённого username перед сравнением, т.к. в Telegram username `@` возможен только в начале, этого достаточно.
- Два реплики в Docker Swarm — эндпоинт read-only, конкурентности не требует.

## Открытые вопросы

Нет. Технические решения, не требующие бизнес-согласования (`GIT_WORKFLOW.md` §3):
1. **Минимальная длина 4 цифры для срабатывания телефонной ветки** — выбрана как разумный компромисс между «найти частичный номер» и «не схлопнуться в полный список»; точное число не было задано клиентским запросом, он прямо оставляет это на техническую реализацию («избегать ошибочного сопоставления»).
2. **Существующий API rate-limit (60/мин) достаточен**, отдельный механизм не вводится — следует явному принципу проекта «не изобретать параллельный механизм» (`CODE_REVIEW.md` §2); если это окажется недостаточно на практике — отдельная будущая задача.
