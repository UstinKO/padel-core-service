## Контекст / зачем

Заказчик проверил LFPT-0688 на iPhone (реальное устройство, мобильный Safari) и подтвердил, что сама регистрация пары и поле Telegram вместо email работают верно. Но нашёл два недочёта в той же модалке парной регистрации («Tengo compañero» / `WITH_PARTNER`, `tournament-details.html`), не замеченных на Шаге 3 LFPT-0688 (там мобильная QA шла через headless Chromium с эмуляцией вьюпорта, без реальной клавиатуры iOS и без реального движка WebKit):

1. Подсказки «Возможно, ваш партнёр уже зарегистрирован» (LFPT-0680/LFPT-0688) при ручном вводе имени/фамилии/телефона не показываются на мобильном — хотя верхний поиск (`partnerSearch`/`partnerSearchResults`) работает.
2. Модалка слишком узкая на iPhone — по бокам пустые поля, заголовок «Registrar pareja para…» сжимается, название турнира не видно.

## Связь с MASTER.md

Не затрагивает бизнес-инварианты — чисто вёрстка/позиционирование существующей (LFPT-0680/LFPT-0688) функциональности на мобильных экранах. Не меняет флоу парной регистрации.

## Анализ (проведён в этом прогоне, т.к. вопрос изначально был сформулирован как "разберитесь и проверьте")

### Причина №2 — ширина модалки (воспроизведено и подтверждено визуально, Playwright/Chromium, iPhone 13 — 390×664)

`tournament-details.css` — общий файл для `tournament-details.html`, `admin/tournaments/details.html`, `players/dashboard.html` — содержит **два независимых, несогласованных набора правил** `.modal`/`.modal-dialog`/`.modal-content`/`.modal-header`/`.modal-body`/`.modal-footer`/`.form-group`/`.form-control` (строка ~536 и строка ~1377). Второй набор — не копипаст-дубликат первого (значения разные: более плоский дизайн, другие отступы/радиусы), похоже, добавлен позже для другого места той же страницы (сразу после `.btn-icon.move-to-main:hover` — иконок действий в админке) и использует те же общие имена классов — специфичность у всех этих селекторов одинаковая в обоих блоках, поэтому для любого модального окна на этих трёх страницах **на экране реально действует второй (более поздний) набор**, а не первый.

Для `.modal-content`/`.modal-body`/`.modal-footer`/`.form-group`/`.form-control` это не баг сам по себе — так выглядит уже сейчас весь сайт, трогать не нужно (слишком большой блэст-радиус, не то, о чём просил заказчик). Но для `.modal-dialog` второй блок (`width: 90%; margin: 1.75rem auto;`, без media query — действует на любом экране) **перекрывает уже существующее мобильное правило** `@media (max-width: 768px) { .modal-dialog { width: 100%; ... } }` (строка ~1090) — то же самое "побеждает тот, кто позже в файле, при равной специфичности", независимо от того, что мобильное правило логически более specific по назначению. Отсюда и узкая модалка на телефоне: вместо задуманных «почти во весь экран» получается 90% с пустыми полями по бокам.

**Фикс:** убрано только дублирующее правило `.modal-dialog` во втором блоке (3 строки). Остальные селекторы второго блока не тронуты — иначе поменялся бы вид всех модалок сайта, это не входит в скоуп задачи.

Отдельно, после того как модалка стала шире, заголовок всё ещё переносился уродливо («Regis/trar/parej/a/para», название турнира обрезалось многоточием). Причина — независимая: `#partnerModalLabel` (`h5.modal-title`) — flex-контейнер; `#modalTournamentName` внутри media-правила `@media (max-width: 480px)` был `white-space: nowrap; max-width: 200px` — при вёрстке строки это нераздельный flex-элемент, который забирал почти всю ширину строки под название турнира (даже обрезанное многоточием), оставляя статичному лейблу «Registrar pareja para» считанные пиксели — тот с `word-break: break-word` ломался посимвольно. **Фикс:** `#partnerModalLabel` — `flex-wrap: wrap` (лейбл — своей строкой, не сжимается, `white-space: nowrap` через новый класс `.modal-partner-title-text`), `#modalTournamentName` — `width: 100%` на отдельной строке, многоточие убрано (`white-space: normal`, `overflow: visible`) — название турнира показывается полностью, оборачиваясь по словам, а не обрезается (прямое требование клиентского запроса — "название турнира почти не видно"). Применено в обоих шаблонах, использующих эту же модалку (`tournament-details.html`, `players/dashboard.html`) — там те же id/структура и тот же баг.

Подтверждено скриншотами до/после на эмулированном iPhone 13 (390×664): модалка — 350px из 390px (ранее 315px), заголовок на одной строке, название турнира читается целиком на 2-3 строках вместо обрезанной одной.

### Причина №1 — подсказки ручного ввода не видны (правдоподобная причина найдена и исправлена; **не подтверждена на реальном устройстве** — см. "Что не удалось проверить")

В облачной песочнице нет реального iPhone и нет движка WebKit (`PLAYWRIGHT_BROWSERS_PATH` содержит только Chromium, `webkit.launch()` недоступен — не баг, а ограничение окружения, подтверждённое уже в `specs/done/telegram-remote-pipeline-stage0-validation.md`). Воспроизвести баг "как есть" через headless Chromium с эмуляцией вьюпорта iPhone не удалось — `positionManualDropdown()` отработал корректно во всех опробованных сценариях (ввод в поле, переключение между полями, скролл формы).

Правдоподобная причина, которую headless Chromium принципиально не может воспроизвести: `positionManualDropdown()`/`positionDropdown()` считают доступное место через `window.innerHeight`. На iOS Safari внутри модалки с `position: fixed` (вся модалка — `.modal { position: fixed; ... }`) `window.innerHeight` **не уменьшается**, когда появляется экранная клавиатура — известная особенность WebKit (для этого и существует `window.visualViewport`, который как раз отражает реально видимую область). Поля ручного ввода (`partnerFirstName`/`partnerLastName`/`partnerPhone`) расположены ниже в форме, чем основной поиск (`partnerSearch`), — при расчёте по устаревшему (завышенному) `window.innerHeight` подсказки у нижних полей с большей вероятностью позиционируются в зоне, которую реально перекрывает клавиатура (то есть технически отрендерены, но не видны пользователю), тогда как у верхнего поля в большинстве случаев попадают в видимую область даже с неточным расчётом — это объясняет, почему заказчик видит разницу именно между "верхний поиск работает" и "ручной ввод — нет".

**Фикс:** `window.innerHeight` в обеих функциях позиционирования (`positionDropdown()` — верхний поиск, `positionManualDropdown()` — подсказки ручного ввода) заменён на `window.visualViewport.height` (с фоллбэком на `window.innerHeight`, если `visualViewport` недоступен). Добавлен слушатель `visualViewport.resize` (и `window.resize` как фоллбэк), пересчитывающий позицию видимой в данный момент подсказки — раньше пересчёт был только по скроллу модалки, но не по открытию/закрытию клавиатуры. Переключение между полями уже работало корректно (`manualActiveInput` обновляется на `input`/`focus`) — не трогали.

Фикс целенаправленно применён только к `tournament-details.js` (где воспроизведена задача и где единственная реализация подсказок ручного ввода — `dashboard.html` этой функциональности не имеет, см. LFPT-0688 "Вне скоупа"). `dashboard.js` содержит аналогичный паттерн для своего `partnerSearchResults`, но трогать его — расширение скоупа за пределы того, что сообщил заказчик (другая страница, не упомянута в запросе).

## Требования

### Функциональные

1. `tournament-details.css`: убрать дублирующее правило `.modal-dialog { width: 90%; margin: 1.75rem auto; }` (строка ~1395, блок "Modal styles" без media query) — мобильное `@media (max-width: 768px) { .modal-dialog { width: 100%; ...} }` должно реально применяться.
2. `tournament-details.css`, `@media (max-width: 480px)`: `#partnerModalLabel` — `flex-wrap: wrap`, лейбл (новый класс `.modal-partner-title-text`, применить в обоих шаблонах) — `white-space: nowrap`; `#modalTournamentName` — своя строка на всю ширину, без обрезки многоточием (`white-space: normal`, полный текст виден). Убрать дублирующий/конфликтующий `max-width: 150px` для `#modalTournamentName` в `@media (max-width: 360px)` — после правки родительского правила он не нужен.
3. `tournament-details.js`: `positionDropdown()` и `positionManualDropdown()` — использовать `window.visualViewport.height` вместо `window.innerHeight` (с фоллбэком), чтобы учитывать реально видимую область при открытой клавиатуре iOS. Добавить слушатель `visualViewport.resize`/`window.resize`, пересчитывающий позицию открытой в данный момент подсказки (аналогично уже существующему слушателю скролла `.modal-body`).

### Нефункциональные

- i18n: новых пользовательских строк нет (только CSS/JS-правки) — обновлять `messages_{es,ru,en}` не требуется.
- Безопасность: не затронута — изменения чисто клиентские (позиционирование/вёрстка), нового пользовательского ввода не добавляют.
- Совместимость: `window.visualViewport` поддерживается во всех актуальных мобильных браузерах (Safari iOS 13+, Chrome Android); фоллбэк на `window.innerHeight` сохраняет прежнее поведение там, где API недоступен.

## Вне скоупа

- Остальные селекторы второго (позднего) CSS-блока (`.modal-content`, `.modal-header`, `.modal-body`, `.modal-footer`, `.form-group`, `.form-control`) — уже активны на сайте для всех модалок всех трёх страниц; правка изменила бы внешний вид всех модалок, заказчик об этом не просил.
- `dashboard.js`/`players/dashboard.html`: перенос подсказок ручного ввода туда — не было в скоупе LFPT-0688 и не упомянуто в этом запросе; исправление `window.innerHeight` → `visualViewport` в `dashboard.js` для его собственного `partnerSearchResults` — тоже не запрошено (другая страница).
- Регистрация пары и поле Telegram вместо email (LFPT-0687/LFPT-0688) — заказчик явно подтвердил, что работает, не трогаем.

## Критерии приёмки

- [ ] На мобильном вьюпорте (390×664, Playwright/Chromium с эмуляцией iPhone) модалка парной регистрации занимает ≥85% ширины экрана (было ~80%/315px из 390px, после фикса — 350px/390px), без горизонтальной прокрутки.
- [ ] Заголовок «Registrar pareja para» не переносится посимвольно; название турнира показывается целиком (без обрезки многоточием), оборачиваясь по словам на несколько строк при необходимости.
- [ ] Desktop-вьюпорт (1280×900): модалка по-прежнему ограничена `max-width: 500px`, без визуальной регрессии (проверено).
- [ ] Верхний поиск партнёра (`partnerSearch`/`partnerSearchResults`) — без регрессии: ввод → результаты → позиционирование рядом с полем → выбор без дубля (проверено, см. "Что проверено").
- [ ] Ввод в поля ручного ввода (имя/фамилия/телефон) при наличии совпадения в базе — подсказка рендерится, позиционируется у активного поля, следует за переключением между полями (проверено headless Chromium — работало и до, и после фикса; целевой сценарий "не видна на мобильном" в облачной песочнице технически невозможно подтвердить/опровергнуть на реальном устройстве — см. ниже).
- [ ] Клик по подсказке — выбирает партнёра (`selectPartner`), не создаёт дубль (регрессия на LFPT-0680, не допущена).
- [ ] `python3 .github/bin/docs-drift.py` — 0 расхождений (документация не затронута — чисто UI/CSS/JS).

## Edge cases

- Модалка открыта без активного поля ручного ввода (`manualActiveInput == null`) — `positionManualDropdown()` не падает (ранний `return`, без изменений).
- `window.visualViewport` недоступен (очень старый браузер) — используется прежний `window.innerHeight`, поведение не хуже, чем было.
- Очень длинное название турнира (проверено — 83 символа) — переносится на несколько строк, не обрезается, модалка не растягивается по горизонтали.
- Очень маленький экран (`@media max-width: 360px`) — убранный `max-width: 150px` не оставляет название турнира без ограничения ширины, т.к. правило из `@media (max-width: 480px)` (`#modalTournamentName { width: 100%; max-width: 100% }`) продолжает действовать и на экранах ≤360px (media-запросы не эксклюзивны, оба применяются).

## Что проверено (в этом прогоне, облачная песочница, Playwright headless Chromium с эмуляцией устройств — нет claude-in-chrome и нет реального iPhone/WebKit)

- До/после — скриншоты модалки на эмуляции iPhone 13 (390×664): ширина модалки, перенос заголовка, видимость полного названия турнира.
- Desktop (1280×900) — модалка не регрессировала (max-width 500px, по центру).
- Подсказки ручного ввода: ввод в `partnerFirstName`, результат находится и рендерится, позиционируется сразу под полем; переключение на `partnerLastName` — подсказка корректно пересчитывает позицию под новым активным полем (подтверждено прямым сопоставлением `getBoundingClientRect()` поля и `style.top` блока подсказок); скролл `.modal-body` — подсказка остаётся прикреплённой к полю.
- Симуляция несовпадения `window.innerHeight`/`window.visualViewport.height` (искусственно уменьшенный `visualViewport.height` + событие `resize`) — подтверждает, что слушатель репозиционирует открытую подсказку по новому значению; не доказывает и не может доказать, что это даёт видимый результат именно на реальном iOS Safari (для этого нужен реальный девайс).

## Что не удалось проверить

- **Причина №1 (подсказки не видны при ручном вводе) не воспроизведена и не может быть окончательно подтверждена в этой среде** — нет доступа к реальному iPhone и нет WebKit-движка в облачной песочнице (только Chromium, `webkit.launch()` недоступен). Фикс (`window.visualViewport` вместо `window.innerHeight`, слушатель `resize`) — наиболее вероятная причина по анализу кода (задокументированная особенность WebKit, см. выше), устраняет единственное структурное отличие между "рабочим" верхним поиском и "нерабочими" подсказками ручного ввода, но требует подтверждения заказчиком на реальном устройстве после деплоя.
