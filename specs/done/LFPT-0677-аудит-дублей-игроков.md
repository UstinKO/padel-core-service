# LFPT-0677: Аудит дублей игроков в базе — admin-эндпоинт с отчётом

## Статус
done

## Источник
`specs/requests/LFPT-0677-аудит-дублей-игроков.md` (клиентский запрос через Telegram, `[telegram_launch_message_id: 5366]`, отправитель отмечен как customer) → issue [#677](https://github.com/UstinKO/padel-core-service/issues/677).

## Контекст / зачем

Заказчик подозревает, что регистрация партнёра на парные турниры создаёт дублирующиеся записи `PlayerPadel` для одного и того же реального человека вместо того, чтобы связать его с уже существующим аккаунтом. Код подтверждает механизм: `DoubleTournamentRegistrationService.confirmPartnerRegistration()` (строки 411-491) при подтверждении партнёра по токену **всегда** создаёт новую запись `PlayerPadel` с `nivelJugador = SIN_ESPECIFICAR` — единственная защита от дублей там — `playerRepository.existsByTelefono(...)`, которая блокирует регистрацию только при точном строковом совпадении телефона, но не ищет и не связывает с уже существующим игроком по имени/email/Telegram. При этом партнёрская запись получает собственную `TournamentRegistration` со `isDoubleRegistration = true` и `mainPlayerId` = id игрока-инициатора — то есть `mainPlayerId != player.id` для такой строки. Это даёт надёжный и однозначный технический признак "эта запись `TournamentRegistration` создана для партнёра через флоу приглашения", не требующий новых полей/миграций.

На этом этапе задача — только посчитать масштаб проблемы и зафиксировать типичные сценарии, ничего не меняя в данных и не трогая логику регистрации (это сознательно отдельная будущая задача).

## Связь с MASTER.md

Инварианты регистрации (уникальность по email/телефону, `hasValidContact()`) не меняются. Новый read-only эндпоинт не затрагивает ни один инвариант `specs/MASTER.md` — чисто диагностическая надстройка поверх существующих данных.

## Требования

### Функциональные

Новый эндпоинт `GET /api/admin/players/duplicates-audit`, доступный только `ROLE_SUPER_ADMIN` (это чувствительные персональные данные всех игроков сразу одним ответом — строже, чем обычный `hasAnyRole('SUPER_ADMIN', 'ORGANIZER')` других admin-эндпоинтов, см. `AdminMetricsController`). Выполняет единоразовый расчёт (без кэша, без пагинации — см. "Вне скоупа") по текущему состоянию `player_padel_db` и `tournament_registrations_db` и возвращает JSON-отчёт:

1. **Сводка** (`summary`): `totalRecords` (всего записей в `player_padel_db`), `duplicateGroupsCount` (число групп дублей — объединение exact + probable, без пересечений, см. ниже), `uniquePlayersEstimate` (`totalRecords` минус лишние записи в группах дублей), `recordsPerPlayerDistribution` — карта `{"2": N2, "3": N3, "4+": N4plus}` — сколько игроков имеют ровно 2, ровно 3 и 4-и-более записей (считается по объединённым группам дублей, см. алгоритм).
2. **Точные дубли** (`exactDuplicates: DuplicateGroupDto[]`) — группы из 2+ записей, совпавших по одному из двух критериев:
   - нормализованный телефон (нормализация — см. "Нефункциональные"), оба телефона непустые;
   - `telegramUsername` без учёта регистра, оба значения непустые.
   У каждой группы — `matchType` (`PHONE` / `TELEGRAM`), `matchKey` (нормализованное значение, по которому совпали) и `members` — список `PlayerSummaryDto`.
3. **Вероятные дубли** (`probableDuplicates: DuplicateGroupDto[]`) — группы из 2+ записей с совпадающим нормализованным именем+фамилией (`matchType = NAME`), **за исключением** пар игроков, которые уже целиком покрыты какой-либо группой из `exactDuplicates` (чтобы одна и та же пара не попадала в обе категории одновременно).
4. **Дубли, заведённые через флоу подтверждения партнёра** (`partnerFlowSuspects: PlayerSummaryDto[]`) — записи `PlayerPadel`, для которых существует хотя бы одна `TournamentRegistration` с `isDoubleRegistration = true` и `mainPlayerId != player.id` (т.е. запись создана как партнёрская сторона приглашения, не как инициатор). Независимый от п.2-3 список — элемент может одновременно входить и в `exactDuplicates`/`probableDuplicates`, и в `partnerFlowSuspects`.
5. **Разбивка по вероятному источнику записи** (`sourceBreakdown: Map<String, Long>`) — по всем записям `player_padel_db`, непересекающиеся категории в таком порядке приоритета:
   - `ADMIN_GUEST` — `PlayerPadel.isGuestAccount()` (email оканчивается на `@1padel.guest`);
   - `OAUTH2` — `oauth2User = true`;
   - `PARTNER_INVITE` — попадает в `partnerFlowSuspects` (п.4) и не подошёл под два предыдущих пункта;
   - `SELF_REGISTERED` — все остальные.
   Это эвристика по существующим полям, не точный источник — явно задокументировать в коде и в `docs/endpoints/`, что `SELF_REGISTERED` — категория "все, что не распознано как другое", а не подтверждённая самостоятельная регистрация.

### Нефункциональные

- **Нормализация телефона** — только для сравнения внутри эндпоинта, не меняет данные в БД: убрать все символы кроме цифр, взять последние 10 цифр (стандартная длина аргентинского номера без кода страны/городского кода — `+54 9 11 2233-4455` и `011 2233-4455` после нормализации совпадут на последних 10 цифрах). Эвристика, не полноценный парсер (libphonenumber не добавляется — новая зависимость ради одного read-only отчёта не оправдана, YAGNI); ограничение явно указать в `docs/endpoints/`.
- **Нормализация имени** — `trim()`, схлопнуть повторные пробелы, lowercase, сравнение `nombre + " " + apellido`. Без транслитерации/снятия диакритики (испанские имена в домене обычно без диакритики за пределами `ñ`/ударений, которые для аргентинского рынка — редкость; усложнение не оправдано для первого отчёта).
- **Производительность**: один проход `playerRepository.findAll()` (сотни-тысячи строк на текущем масштабе проекта — не оправдывает пагинацию/курсор) + один batched-запрос по `tournament_registrations_db` для п.4 (не N+1 на каждого игрока). Если список игроков вырастет на порядки — отдельная задача на пагинацию/кэш, не в скоупе этой.
- **i18n**: эндпоинт — JSON API для одного технического пользователя (суперадмина), не рендерит UI-строки — новых i18n-ключей не требуется.
- **Безопасность**: `@PreAuthorize("hasRole('SUPER_ADMIN')")`; ответ содержит email/телефон/Telegram всех игроков с совпадениями — тот же уровень чувствительности, что уже отдаёт `/admin/export` (Excel) и `/admin/players/{id}` тому же `SUPER_ADMIN`, не новый прецедент раскрытия PII.
- Маппинг `PlayerPadel → PlayerSummaryDto` — через MapStruct-маппер (`mapper/`), не вручную в сервисе/контроллере (`CODE_REVIEW.md` §5).

## Вне скоупа

- Автоматическое объединение, пометка "дубликат" или удаление каких-либо записей — явное ограничение заказчика на этом этапе.
- Изменение `DoubleTournamentRegistrationService.confirmPartnerRegistration()` или любой другой логики регистрации — отдельная будущая задача, которую этот отчёт должен обосновать.
- UI/admin-страница для просмотра отчёта в браузере с таблицами/фильтрами — по запросу это нужно только суперадмину ("Кто это увидит/использует: только я"); JSON-ответа существующего `@PreAuthorize`-защищённого REST API достаточно (открывается прямо в браузере или через `curl`/Postman с JWT). Фронтенд-задача не заводится.
- Пагинация/курсор/кэширование результата — не нужны на текущем масштабе данных (см. "Нефункциональные").
- Полноценный парсинг телефонных номеров (libphonenumber) — эвристика "последние 10 цифр" признана достаточной для первого отчёта.
- Запуск отчёта по расписанию / cron — разовый ручной вызов, не повторяющаяся задача.

## Изменения в системе

### API

Новый: `GET /api/admin/players/duplicates-audit` — `AdminPlayerAuditController` (новый, `/api/admin/players`), `@PreAuthorize("hasRole('SUPER_ADMIN')")`. Делегирует в новый `PlayerDuplicatesAuditService`. Ответ — `DuplicatesAuditReportDto` (новый record-DTO, см. "Функциональные").

Новый repository-метод в `TournamentRegistrationRepository`: выборка id игроков, чья собственная регистрация создана через флоу приглашения партнёра (`isDoubleRegistration = true AND mainPlayerId <> player.id`) — батчем, не по одному игроку.

### БД

Без изменений. Никаких новых таблиц/колонок/миграций — эндпоинт только читает существующие `player_padel_db` и `tournament_registrations_db`.

## Критерии приёмки

- [ ] `GET /api/admin/players/duplicates-audit` возвращает 200 для пользователя с ролью `SUPER_ADMIN`.
- [ ] Для пользователя без роли `SUPER_ADMIN` (включая `ORGANIZER`/`OWNER` без `SUPER_ADMIN`) и для анонимного запроса — 403/401.
- [ ] Ответ содержит `summary.totalRecords`, равный реальному количеству строк в `player_padel_db` на момент вызова.
- [ ] Два игрока с одинаковым телефоном в разном формате (например `+5491122334455` и `01122334455`), оба активные обычные (не guest) записи — попадают в `exactDuplicates` с `matchType = PHONE`.
- [ ] Два игрока с одинаковым `telegramUsername` в разном регистре — попадают в `exactDuplicates` с `matchType = TELEGRAM`.
- [ ] Два игрока с одинаковыми именем и фамилией (с учётом регистра/пробелов), но разными или отсутствующими телефоном/email/Telegram — попадают в `probableDuplicates` с `matchType = NAME`, и не дублируются в `exactDuplicates`, если они не совпали ни по телефону, ни по Telegram.
- [ ] Игрок, запись которого создана через `confirmPartnerRegistration` (есть `TournamentRegistration` с `isDoubleRegistration = true` и `mainPlayerId`, не равным id этого игрока) — присутствует в `partnerFlowSuspects`.
- [ ] Игрок с email на `@1padel.guest` — учтён в `sourceBreakdown.ADMIN_GUEST`, не в `SELF_REGISTERED`.
- [ ] Игрок с `oauth2User = true` — учтён в `sourceBreakdown.OAUTH2`.
- [ ] `recordsPerPlayerDistribution` корректно считает группы на 2/3/4+ записей на заранее подготовленном тестовом наборе (минимум одна группа каждого размера).
- [ ] Вызов эндпоинта не создаёт, не изменяет и не удаляет ни одной строки в `player_padel_db`/`tournament_registrations_db` (проверяется сравнением снимков таблиц до/после теста).
- [ ] `python3 .github/bin/docs-drift.py` — 0 расхождений после обновления документации.

## Edge cases

- Игрок без телефона и без Telegram (`hasValidContact() == false` — теоретически не должно встречаться у активных аккаунтов, но могло остаться у старых/гостевых) — не участвует в `exactDuplicates` по телефону/Telegram (нет значения для сравнения), может попасть только в `probableDuplicates` по имени или быть один в своей группе (тогда группа не формируется — группы меньше 2 элементов не включаются в отчёт).
- Группа из 3+ записей с одинаковым телефоном — один элемент `DuplicateGroupDto` с `members.size() == 3`, учитывается в `recordsPerPlayerDistribution["3"]`, не как отдельные пары.
- Один и тот же игрок одновременно входит в группу по телефону и в отдельную группу по имени с другим составом участников (A совпал с B по телефону, A совпал с C по имени, B и C не совпадают друг с другом) — допустимо, что одна запись встречается в нескольких группах `exactDuplicates`/`probableDuplicates`; `duplicateGroupsCount`/`uniquePlayersEstimate` считаются по объединению всех записей, попавших в любую группу (connected components по всем совпадениям), а не по сумме размеров групп, иначе A будет учтён дважды.
- Пустая база (0 игроков) или база без единого дубля — отчёт возвращается с нулевыми счётчиками и пустыми списками, не ошибкой.
