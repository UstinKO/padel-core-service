# LFPT-0555: Форма создания турнира — поле «Максимум пар» для парных форматов

## Статус
done

## Источник
Telegram-сообщение (для reply): 5050
Клиентский запрос через Telegram (сообщение 5050, отправитель customer, переслано от Evgeny_754) → issue [#555](https://github.com/UstinKO/padel-core-service/issues/555). Прямой технический вход без промежуточного `specs/requests/` — запрос сразу содержал чёткую, непротиворечивую формулировку; после анализа кода уточнено только техническое решение (см. ниже), бизнес-требование не менялось.

## Контекст / зачем
На форме создания/редактирования турнира (`admin/tournaments/form.html`) поле вместимости (`cupoMax`) всегда подписано «Максимум игроков», независимо от формата. Для парных форматов (Americano Parejas / `AMERICANO_TEAMS`, где `modalidad` всегда `DOBLES`) это вводит организатора в заблуждение: он мыслит количеством пар/команд, а не отдельных игроков.

## Связь с MASTER.md
Затрагивает раздел «Статусы регистрации на турнир» косвенно — через лимит `cupoMax`, который определяет момент перехода `CONFIRMED → WAITLIST`. Сама бизнес-логика этого перехода не меняется, только то, в каких единицах организатор вводит число на форме. MASTER.md не обновляется — инвариант не меняется.

## Техническая проверка (определяет решение, сделана до реализации)

Проверено по коду: для турниров с `modalidad == DOBLES` (включая принудительно `AMERICANO_TEAMS`, и свободно выбираемый `DOBLES` для `CANCHA_ABIERTA`/`PADEL_CLINIC`) `cupoMax` **уже хранится и используется как количество ПАР**, без какого-либо умножения/деления на 2, во всех местах, где реально ограничивается регистрация:

- `TournamentService.mapToDtoWithDetails()` (и аналогичные методы ~L915-946, L1225-1227) — `confirmedSpots = registrationRepository.countConfirmedPairs(...)`, сравнивается с `tournament.getCupoMax()` напрямую.
- `TournamentService` (реактивация отменённой регистрации, ~L291-302) — `confirmedPairsCount` сравнивается с `cupoMax` напрямую.
- `DoubleTournamentRegistrationService` (3 места: `registerPair`, `confirmPartner`, `addPartner`) — `confirmedPairs (+ soloRegs) >= cupoMax`.
- Публичная `tournament-details.html` и `admin/tournaments/list.html` — показывают `tournament.cupoMax` для DOBLES как есть, с подписью «cupos»/«parejas», без деления.
- Закрытая, принятая спека `specs/done/LFPT-374-tarjeta-torneo-autotitulo-cupos.md` явно документирует: «для DOBLES считаются уникальные подтверждённые пары» в сравнении с `cupoMax` — то есть это осознанное, протестированное поведение, не случайность.

**Вывод:** клиентский запрос предполагал, что внутренне нужно будет умножать введённое число пар на 2 перед сохранением («16 пар → 32 игрока»). Это предположение о реализации неверно и прямо противоречит критерию приёмки №4 того же запроса («17-я пара не должна попадать в основной список») — если умножить на 2, реальный лимит регистрации станет 32 парами, а не 16. Соответственно, умножение на 2 **не делается**: `cupoMax` сохраняется как есть, меняется только подпись поля на форме. Это техническое решение (не бизнес-вопрос) — наблюдаемый результат для организатора (единицы измерения на форме, корректный лимит регистрации) совпадает с тем, что просил заказчик; расходится только предположение о внутреннем механизме, которое заказчик не мог знать не видя кода.

Отдельно, в процессе проверки обнаружен не связанный с этой задачей баг отображения в `admin/tournaments/details.html` (делит `cupoMax` на 2 при показе лимита пар, в отличие от остальных страниц) — заведён отдельным issue [#556](https://github.com/UstinKO/padel-core-service/issues/556), не в скоупе этой фичи.

## Требования

### Функциональные
- На форме `admin/tournaments/form.html` подпись поля `cupoMax` переключается в зависимости от текущего значения `modalidad`:
  - `modalidad == DOBLES` → «Максимум пар» (новый ключ `admin.tournaments.form.field.capacity_pairs`).
  - `modalidad == INDIVIDUAL` → «Максимум игроков» (существующий ключ `admin.tournaments.form.field.capacity`, без изменений).
- Переключение подписи работает:
  - при смене типа турнира (`tipo`), который форсирует `modalidad` (`AMERICANO_TEAMS` → DOBLES, `AMERICANO`/`KING_OF_COURT` → INDIVIDUAL) — существующая функция `onTipoChange()`;
  - при прямой смене `modalidad` пользователем (доступно для `CANCHA_ABIERTA`/`PADEL_CLINIC`, где модальность не форсируется);
  - при начальной загрузке формы редактирования (`GET /admin/tournaments/{id}/edit`), когда `modalidad` уже сохранена в БД.
- Значение, вводимое организатором, сохраняется в `cupoMax` без каких-либо преобразований — число пар как есть.

### Нефункциональные
- i18n: один новый ключ `admin.tournaments.form.field.capacity_pairs` в `messages.properties`, `messages_es.properties`, `messages_ru.properties`, `messages_en.properties` — рядом с существующим `admin.tournaments.form.field.capacity` (ровно тем блоком, который реально используется `form.html`, без расширения дублирующихся мёртвых блоков того же ключа в этих файлах — это отдельная, не связанная проблема).
- Переключение подписи — на клиенте (JS), без лишнего запроса на сервер; оба варианта текста рендерятся сервером (Thymeleaf, с учётом локали) в `data-*`-атрибуты, JS только выбирает между ними — никаких хардкод-строк на испанском/русском в JS не добавляется (в отличие от уже существующего `tipoHint.textContent` в том же файле, который не трогаем — не в скоупе).
- Безопасность: новой точки входа данных нет, валидация `cupoMax` (`@Min(2) @Max(64)`) не меняется.

## Вне скоупа
- Любые изменения `cupoMax`/валидации/бизнес-логики лимита регистрации — лимит и сейчас корректно работает в единицах пар для DOBLES, трогать не нужно.
- Исправление деления `cupoMax / 2` на `admin/tournaments/details.html` — issue [#556](https://github.com/UstinKO/padel-core-service/issues/556), отдельная задача.
- Исправление хардкод-испанских строк в `onTipoChange()` (`tipoHint.textContent`) — существующий, не связанный с этой задачей тех-долг (покрывается отдельными задачами #533/#534 по смешению языков в админке).
- Очистка дублирующихся/мёртвых блоков ключа `admin.tournaments.form.field.capacity` в properties-файлах — предсуществующая проблема, не трогаем.
- Миграция/пересчёт `cupoMax` для уже существующих турниров — семантика не меняется, только подпись.

## Критерии приёмки
- [ ] При выборе `AMERICANO_TEAMS` на форме создания турнира подпись поля вместимости меняется на «Максимум пар» (ru), «Máximo de Parejas» (es), «Maximum Pairs» (en).
- [ ] При выборе `CANCHA_ABIERTA` или `PADEL_CLINIC` с ручным выбором модальности `Dobles` подпись также меняется на «Максимум пар»; при возврате к `Individual` — обратно на «Максимум игроков».
- [ ] При выборе `AMERICANO` (индивидуальный) или `KING_OF_COURT` подпись — «Максимум игроков», без изменений.
- [ ] На форме редактирования (`GET /admin/tournaments/{id}/edit`) существующего турнира с `modalidad == DOBLES` подпись при загрузке страницы сразу «Максимум пар» (без необходимости трогать select).
- [ ] Введённое число пар (например, 16) сохраняется в `cupoMax` как есть, без умножения.
- [ ] Для турнира с `cupoMax = 16` и `modalidad = DOBLES`: 16 пар регистрируются и подтверждаются, 17-я пара уходит в `WAITLIST`, не в основной список (поведение не изменилось — проверка регрессии).
- [ ] Для индивидуальных форматов лимит и поведение регистрации не изменились.
- [ ] `./mvnw compile -DskipTests` — зелёный.
- [ ] Ручная/browser-проверка формы создания турнира (Playwright) для обоих случаев (парный и индивидуальный формат), включая переключение `tipo`/`modalidad` без перезагрузки страницы.

## Edge cases
- Пользователь переключает `tipo` туда-обратно несколько раз до сабмита — подпись должна каждый раз корректно переключаться, финальное состояние соответствует последнему выбору.
- Форма редактирования турнира, у которого `modalidad == DOBLES`, но `tipo` — не `AMERICANO_TEAMS` (например, старый bracket-турнир с ручным выбором `Dobles` для другого типа, если такие существуют) — подпись всё равно должна быть «Максимум пар», так как переключение зависит от `modalidad`, не от `tipo`.
- JS отключён в браузере — подпись останется той, что отрендерил Thymeleaf при начальной загрузке (соответствует текущему `modalidad` в форме при редактировании; при создании — дефолтному состоянию формы, как и сейчас). Деградация не хуже текущего поведения.

## Открытые вопросы
Нет — расхождение между буквальным предложением заказчика (умножение на 2) и фактическим устройством `cupoMax` — техническая деталь реализации, не бизнес-вопрос; разрешено самостоятельно (см. «Техническая проверка» выше), наблюдаемый результат соответствует тому, что просил заказчик.
