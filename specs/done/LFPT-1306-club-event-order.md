# LFPT-1306: Порядок мероприятий клубного кабинета

## Статус
done

## Источник
Постановка задачи №6 в чате 23.11.2026; [issue #1306](https://github.com/UstinKO/padel-core-service/issues/1306). Спецификация составлена напрямую по запросу.

## Контекст
Общий список сортируется только по дате, клубная ветка `findByOwnerId` не сортируется. Требуется единый порядок полного списка по дате и времени проведения, независимо от порядка создания или ответа БД.

## Связь с MASTER
Действующие роли и принадлежность событий сохраняются: CLUB_ADMIN видит только свои события, главный администратор — все. Фильтры не расширяют область доступа. Бизнес-инварианты MASTER не меняются.

## Требования и реализация
- Общая чистая функция сортировки для `getAllTournaments` и `getTournamentsForOwner`.
- Существующая группировка главного кабинета сохраняется: сегодняшний день и последующие даты перед предыдущими днями. Уже начавшееся сегодня мероприятие остаётся в сегодняшней группе; статус не заменяет дату как критерий порядка.
- Сегодняшние/будущие события: дата ASC, время ASC, ID ASC. Предыдущие дни: дата DESC, время DESC, ID ASC. При одинаковом старте ID обеспечивает стабильность.
- Сравниваются локальные поля fechaInicio/horaInicio, как они показаны на странице мероприятия; день границы определяется в действующей зоне сайта America/Argentina/Buenos_Aires, а не зоне браузера/процесса.
- Пустая дата ставится в конец, пустое время — после известных времён в своём дне. Валидные существующие данные не изменяются.
- Сортируется весь доступный список до фильтрации/рендеринга; текущий список без пагинации. Никакой сортировки отдельного фрагмента браузером.
- Создание/редактирование влияет на следующий GET; отдельного сохранённого порядка или кеша нет.
- Отменённые/завершённые/неактивные события остаются доступными по существующим правам и фильтрам.

## Изменения системы
Новых API, параметров, миграций, UI-строк и переводов нет. Действующие мобильные карточки и настольная таблица используют один серверный список. Существующий календарь сортирует события отдельно, его поведение сохраняется.

## Вне объёма
Виджет последних созданных турниров, правила регистрации/оплат, создание координаторов, пагинация, редизайн и изменение прав доступа. Рабочие события не используются для изменяющих проверок.

## Критерии приёмки
- [x] Единый ближайший порядок, включая несколько времён одного дня и одинаковый старт.
- [x] Прошедшие и статусы сохраняются; пустые данные и список обрабатываются безопасно.
- [x] После создания/изменения даты и времени следующий GET показывает новое место.
- [x] Комбинированные фильтры, сброс и обновление не нарушают порядок.
- [x] Два организатора одной площадки: клуб не получает чужие события, главный видит все.
- [x] Отдельная PostgreSQL, полный verify и реальные настольный/мобильный браузеры.

Проверки: [отчёт приёмки](../../docs/acceptance/LFPT-1306-order-2026-11-23.md). Слияние и выпуск выполняются отдельным поручением.

## Открытые вопросы
Нет: группировка уже начавшихся и прошлых событий взята из существующей реализации главного кабинета.
