# LFPT-0580: Протокол конвейера для автомержа — бэк и фронт в одном прогоне, маркеры задачи, доведение PR до зелёного

## Статус
done

## Источник
[GitHub issue #580](https://github.com/UstinKO/padel-core-service/issues/580). Прямая постановка архитектора, клиентского запроса нет. Этап 2 дорожной карты «Автономный конвейер: от Telegram до прода» (локальная `docs/pipeline-autonomy.md`). Зависит от #579 (оркестратор автомержа).

## Контекст / зачем
Оркестратор (#579) вливает только PR с меткой `pipeline:ready` и учитывает `Depends-On`, движок задач (#581) отслеживает задачу по маркеру `Pipeline-Task`. Сейчас роутина ничего из этого не ставит, PR ждут ревью, а задачу «бэк + фронт» роутина часто доводит только до бэк-PR, фронт лишь заводит. Нужно, чтобы роутина реализовывала оба слоя, сама доводила PR до зелёного pr-check и отдавала их оркестратору по протоколу.

## Связь с MASTER.md
Не затрагивает бизнес-логику продукта. Меняет процесс: `.claude/commands/develop-feature.md`, `.claude/GIT_WORKFLOW.md` §1.4.

## Требования

### Функциональные
1. Раздел «Протокол автономного конвейера» в `develop-feature.md`: номер задачи `Pipeline-Task` (`telegram_launch_message_id` или `manual-<RUN>`), маркеры `Pipeline-Task: <N>` (issue и PR) и `Depends-On: #<бэк-PR>` (фронт-PR), метки `pipeline`, `pipeline:ready`, `pipeline:needs-input`, `pipeline:failed`, критерий «сессия закончила работу».
2. Задача на два слоя — две issue и два PR, но обе реализуются в одном прогоне; фронт-ветка от бэк-ветки.
3. Шаг 5.1: `gh pr checks --watch`, починка красного (≤ 2 попыток) или `pipeline:failed`; зелёный → `pipeline:ready` последним действием по PR.
4. Гейт на открытых вопросах в `cloud`: ветка со спекой запушена, `pipeline:needs-input` + комментарий `🤖 pipeline-questions`, `🤖 pipeline-release`.
5. Продолжение по `[продолжение задачи #N]` — поиск задачи по `Pipeline-Task: N`, снятие `pipeline:needs-input`.
6. Починка PR с `pipeline:conflict` — обновить ветку, зелёный pr-check, снять `pipeline:conflict`, поставить `pipeline:ready`.
7. Итог в Telegram: «PR открыт, проверки зелёные — вольётся и задеплоится автоматически»; фраза «ревью и мерж — за пользователем» из PR убрана.
8. `GIT_WORKFLOW.md` §1.4 — обе задачи слоя в одном прогоне, `Depends-On`.

### Нефункциональные
- Маркеры и первая строка `🤖 pipeline-questions` — фиксированное написание (их парсят оркестратор и движок).

## Критерии приёмки
- [ ] Задача «бэк + фронт» даёт два PR за один прогон; у фронт-PR — `Depends-On: #<бэк-PR>`.
- [ ] У всех issue и PR задачи — `Pipeline-Task` и метка `pipeline`.
- [ ] `pipeline:ready` ставится только после зелёного pr-check; красный роутина чинит сама или ставит `pipeline:failed`.
- [ ] Открытые вопросы → `pipeline:needs-input` + `🤖 pipeline-questions`.
- [ ] Правила согласованы с `GIT_WORKFLOW.md` §1.4, §8, §10.

## Edge cases
- pr-check долго в очереди GitHub — `--watch` ждёт; сессия роутины не ограничена 10 минутами.
- Бэк-PR красный после 2 попыток — фронт не начинается, задача `pipeline:failed`.
- Фронт-PR конфликтует после мержа бэка — оркестратор ставит `pipeline:conflict`, движок перезапускает роутину на починку (п. 6).
