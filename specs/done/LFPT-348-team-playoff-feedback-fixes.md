# LFPT-348: Team Playoff — разделение раундов квалификации, приоритет посева 1/4, стабильная нумерация команд

## Статус
done — PR #349, деплой подтверждён успешным (run https://github.com/UstinKO/padel-core-service/actions/runs/32487970134, commit 67baa19)

## Источник
GitHub issue [#348](https://github.com/UstinKO/padel-core-service/issues/348) — заведён конвейером напрямую по фидбеку заказчика (Telegram, роль `architect`, 3 сообщения с 3 скриншотами теста парного турнира на 8 команд). Прямого клиентского файла `specs/requests/` нет — вход соответствует варианту 3 из `.claude/commands/develop-feature.md` (issue с готовой технической постановкой).

## Контекст / зачем
Организатор провёл первый реальный турнир Team Playoff (8 команд) вручную и обнаружил три нюанса, мешающих проведению:
1. Список квалификационных матчей не разделён визуально на 1-й и 2-й тур — координатору сложно понять, какие матчи к какому туру относятся; корты в списке идут не по порядку.
2. Правило формирования пар четвертьфинала после квалификации в коде расставляет приоритеты в обратном порядке относительно того, что нужно организатору: система сейчас в первую очередь бережёт посев (сильный/слабый), а анти-реванш — по остаточному принципу. Организатору нужно наоборот: сначала не допустить повтора, потом сохранить группу по результату (2-0/1-1/0-2), и только затем сортировать по силе.
3. Номер команды, под которым она отображается на странице оплат при регистрации, не сохраняется — при добавлении пары в турнир (кнопка "Agregar equipo") ей присваивается новый порядковый номер по факту нажатия кнопки, а не по факту регистрации, из-за чего команда №5 при регистрации может стать, например, командой №2 в ходе турнира.

## Связь с MASTER.md
Не затрагивает инварианты `specs/MASTER.md` — Team Playoff уже упомянут как под-режим Team Americano (таблица форматов турниров), сама механика плей-офф-стадии в MASTER.md не описана на уровне бизнес-правил (только в коде/комментариях `TeamPlayoffService`, `PlayoffMatchingEngine`). Изменения ниже — фиксы существующей реализации, не новый инвариант.

## Требования

### Функциональные

#### 1. Визуальное разделение раундов квалификации + сортировка по корту

Сейчас вся квалификация Team Playoff технически хранится как **один** `AmericanoRound` (см. `TeamPlayoffService.getOrCreateQualificationRound` — единый контейнер-раунд для всей фазы, матчи добавляются в него по одному по мере готовности координатора: `createQualificationMatch` → `nextMatchNumber(round.getId())`). Каждая команда играет ровно 2 квалификационных матча; `TeamPlayoffService.computeQualMatchOrdinals(tournamentId)` уже вычисляет для каждого матча пару `[ordinal команды1, ordinal команды2]` — является ли это 1-м или 2-м квалификационным матчем для каждой из двух команд этого матча (используется сейчас только для подписи "1-й"/"2-й матч" в карточке ввода счёта, см. `TeamPlayoffViewController.applyQualMatchOrdinals`).

Нужно на основе этих же ordinal'ов разбить единый список матчей на 2 логические волны при построении модели для шаблона:
- **Волна ("Раунд") N** = все матчи, где `max(team1MatchOrdinal, team2MatchOrdinal) == N` (обоснование распределения "пограничного" матча — см. Edge cases).
- Внутри каждой волны матчи сортируются по `courtNumber` по возрастанию.
- Каждая волна рендерится как отдельная запись в существующем UI-паттерне "round-tabs" (тот же, что уже используется для раундов Americano/плей-офф в этих же шаблонах) — т.е. `qualRounds` в модели контроллера превращается из списка с одним элементом в список из 1 или 2 элементов (2-й элемент появляется, как только координатор создал хотя бы один матч 2-й волны).
- Подпись вкладки/раунда — не хардкод `'R' + roundNumber`, а локализованный `#{americano.round.prefix}` (уже существующий ключ, значения `Round`/`Ronda`/`Раунд` во всех трёх `messages_*.properties` — переиспользуется, новый ключ не нужен) + номер.

Затронуть:
- `TeamPlayoffViewController.viewPublic` и `TeamPlayoffViewController.viewAdmin` (оба сейчас строят `qualRounds` через одинаковый `buildRoundDtos` + `applyQualMatchOrdinals` — добавить общий приватный метод разбивки на волны и сортировки по корту, вызвать из обоих методов).
- `admin/americano/tournament-playoff.html` (строки ~451-481: `th:text="'R' + ${r.roundNumber}"` → локализованный вариант).
- `tournaments/team-playoff/view.html` (строки ~200-222: то же самое).

Доска кортов (`GET /api/{tournamentId}/court-board`, live-обновления `team-playoff-realtime.js`) эту логику не использует (там нет группировки по раундам вообще, только по кортам) — не трогать.

#### 2. Приоритет анти-реванш при посеве 1/4 финала из квалификации

`TeamPlayoffService.seedPlayoffPairs(tournamentId, seeded)` — единая точка входа, которая строит пары через `PlayoffMatchingEngine.match(candidates, priorOpponents)` (по умолчанию `PriorityOrder.SEED_FIRST` = `[посев, разведение групп, анти-реванш]`) для:
- четвертьфинала при чётном числе команд, вызывается из `createPlayoffRound` (используется `initPlayoff` для 8/16 команд);
- play-in (1/8 финала) при 9-15 командах, вызывается из `initPlayoffWithPlayIn`.

Оба случая — ровно тот сценарий, который описал организатор: пары формируются сразу по итогам 2 квалификационных матчей, `Candidate.winStreak` = `AmericanoTeam.matchesWon` (0/1/2), что при ровно 2 сыгранных матчах эквивалентно группам 0-2/1-1/2-0.

Добавить в `PlayoffMatchingEngine.PriorityOrder` новое значение `REMATCH_FIRST` = `[анти-реванш, разведение групп, посев]` (переставляет тот же `rawCost = [seedingDeviation, streakViolations, rematchViolations]` в порядок `{rawCost[2], rawCost[1], rawCost[0]}`, по аналогии с уже существующим `STRENGTH_FIRST`). Изменить единственный вызов в `seedPlayoffPairs` на `matchingEngine.match(candidates, buildPriorOpponentsMap(tournamentId), PlayoffMatchingEngine.PriorityOrder.REMATCH_FIRST)`.

**Не трогать** `seedNextPlayoffStage` (полуфинал и далее, `PriorityOrder.STRENGTH_FIRST`) — фидбек организатора специально про формирование пар "сразу после квалификации"; для более поздних стадий (там уже нет группы 2-0/1-1/0-2, играет роль текущая серия побед в плей-офф) действующий порядок приоритетов уже ставит анти-реванш выше чистого посева и не является предметом фидбека.

Прямой посев старших команд по формуле "1 место против 8, 2 против 7..." для случая 9-15 команд (`initPlayoffWithPlayIn`, массив `crossing`, команды `direct` штук) через движок не идёт вообще (жёсткая формула по месту в рейтинге, не через `matchesWon`-группы) — вне скоупа этого фикса, фидбек её не касается.

#### 3. Стабильная сквозная нумерация команд

`AmericanoTeam.teamNumber` должен совпадать с `TournamentRegistration.position`, под которым пара показана на странице `/admin/tournaments/{id}/payments` (колонка "Posición" — общий порядковый номер пары, назначаемый `TournamentService.reorderPairPositions`/`confirmedCount+1` в общем флоу регистрации турнира, никак не связанный с Team Playoff).

Изменить `TeamPlayoffService.buildTeamFromPair` (единственное место, где создаётся `AmericanoTeam` из `TournamentRegistration`, вызывается из `addTeamFromRegistration` — обработчик кнопки "Agregar equipo" на странице оплат, и из `importFromRegistrations` — массовый импорт всех пар разом):
- Если у `mainReg.getPosition()` есть значение и оно ещё не занято другой командой этого турнира — использовать его как `teamNumber`.
- Иначе (позиция `null`, либо уже занята другой командой — см. Edge cases) — прежнее поведение: `findMaxTeamNumber(tournamentId).orElse(0) + 1`.

`TeamPlayoffService.addTeam` (общая ручная форма добавления команды в админке Team Playoff, без привязки к `TournamentRegistration` — `POST /tournaments/team-playoff/admin/{id}/teams/add`) не меняется: там нет исходной позиции регистрации, откуда её брать.

Поскольку `teamNumber` — единственное поле, через которое во всех перечисленных организатором местах строится подпись команды (`AmericanoTeam.getDisplayName()`/`AmericanoTeamDto.teamNumber`, используется в шаблонах `admin/americano/tournament-playoff.html` и `tournaments/team-playoff/view.html`, а также во всех DTO плей-офф стадий, доски кортов и рекомендаций пар), сам факт корректного присвоения на этапе создания автоматически распространяется на все перечисленные экраны — отдельных правок в каждом из них не требуется.

### Нефункциональные
- i18n: новых строк не требуется — `americano.round.prefix` уже переведён на все 3 языка.
- Безопасность: новых точек входа данных от пользователя нет, изменения — во внутренней логике существующих обработчиков.
- Производительность: разбивка на волны/сортировка по корту — O(n log n) от числа квалификационных матчей на странице турнира (десятки), не создаёт новых запросов к БД сверх уже выполняемых.

## Вне скоупа
- Изменение приоритетов движка для полуфинала/финала (`STRENGTH_FIRST`) — фидбек не касается этих стадий.
- Изменение формулы прямого посева (`crossing` — 1 против 8, 2 против 7...) для 9-15 команд.
- Редизайн UI раундов (переход с вкладок на постоянно видимые блоки) — используется существующий паттерн вкладок "round-tabs", уже принятый в проекте для похожих списков раундов.
- Пересчёт/миграция уже назначенных `teamNumber` для уже проведённых или идущих турниров — фикс касается только новых вызовов `addTeamFromRegistration`/`importFromRegistrations` после деплоя.
- Изменение самого расчёта `TournamentRegistration.position` (флоу регистрации турнира вне Team Playoff не трогаем).

## Изменения в системе

### API
Существующие endpoint'ы, меняется только внутреннее поведение — новых нет:
- `GET /tournaments/team-playoff/{tournamentId}` и `GET /tournaments/team-playoff/admin/{tournamentId}` — `qualRounds` в модели теперь может содержать до 2 элементов (волны) вместо 1, каждый со своим отсортированным по корту подсписком матчей.
- `POST /tournaments/team-playoff/api/{tournamentId}/qual-matches` (создание квал.матча из доски кортов) и `POST /admin/tournaments/{tournamentId}/payments/add-team` — без изменений сигнатуры, `teamNumber` результата может отличаться от текущего поведения (см. п.3).

### БД
Миграция не нужна — колонка `team_number` (`v1.26-create-americano-teams.yaml`) уже существует, меняется только логика присвоения значения в коде.

### UI
- `src/main/resources/templates/admin/americano/tournament-playoff.html` — блок вкладок квалификации (~строки 451-481).
- `src/main/resources/templates/tournaments/team-playoff/view.html` — блок вкладок квалификации (~строки 194-222).

## Критерии приёмки
- [ ] На турнире с чётным числом команд (например, 8), после того как все команды сыграли оба квалификационных матча — на `/tournaments/team-playoff/admin/{id}` и на `/tournaments/team-playoff/{id}` отображаются 2 отдельных раздела ("Раунд 1"/"Раунд 2" на ru, "Ronda 1"/"Ronda 2" на es, "Round 1"/"Round 2" на en), в каждом ровно N/2 матчей.
- [ ] Матчи внутри каждого раздела отсортированы по возрастанию номера корта.
- [ ] Пока не создан ни один матч 2-й волны — отображается только раздел "Раунд 1" (аналогично текущему поведению, когда нет матчей вообще).
- [ ] Юнит-тест на `PlayoffMatchingEngine`/`TeamPlayoffService`, воспроизводящий пример из фидбека (8 команд: 2×2-0, 4×1-1, 2×0-2, без предыдущих встреч между кандидатами на пару) — движок формирует пары строго 2-0 vs 0-2 и 1-1 vs 1-1, внутри группы сильный против слабого.
- [ ] Юнит-тест на случай, когда стандартная пара внутри группы 1-1 уже встречалась в квалификации — движок сдвигает пару внутри той же группы результатов (а не жертвует группировкой ради посева), повтора нет.
- [ ] Для 9-15 команд (play-in), когда анти-реванш физически невозможен для какой-то пары — поведение как раньше: лучший доступный вариант, `log.warn` не теряется.
- [ ] Команда, добавленная через "Agregar equipo" на странице оплат, получает `teamNumber`, равный отображаемой на этой же странице "Posición" пары на момент добавления.
- [ ] Этот номер не меняется и совпадает во всех точках отображения команды: доска кортов, оба раздела квалификации, итоговая таблица (`getQualRanking`), предложения пар (`suggestSecondRoundPairings`), матчи 1/8, 1/4, полуфинала, финала.
- [ ] Сценарий из скриншотов организатора: команды добавлены в порядке, отличном от порядка регистрации (например, команда с Posición 5 добавлена в турнир раньше команды с Posición 2) — итоговый `teamNumber` всё равно соответствует Posición, а не порядку добавления.
- [ ] `TeamPlayoffEndToEndTest` и остальные существующие тесты `AmericanoTeamRepository`/`TeamPlayoffService`/`PlayoffMatchingEngine` продолжают проходить.

## Edge cases
- Матч, где `team1MatchOrdinal != team2MatchOrdinal` (нечётное число команд, "дополнительная" команда играет свой 1-й матч против команды, для которой это уже 2-й, ТЗ §20-23 в существующих комментариях кода) — относится к волне `max(team1MatchOrdinal, team2MatchOrdinal)` (т.е. отображается в "Раунд 2" — на момент этого матча волна 2 уже фактически идёт для соперника).
- `addTeamFromRegistration` вызван для регистрации без `position` (`null`, например статус не `CONFIRMED`) — используется прежнее поведение (следующий свободный номер по счётчику); такая регистрация и так отклоняется более ранней проверкой статуса в этом методе, случай маловероятен, но не должен приводить к исключению.
- Вычисленный из `position` номер уже занят другой командой этого турнира (смешение ручного `addTeam` и `addTeamFromRegistration`/`importFromRegistrations` в одном турнире) — не бросать исключение и не затирать существующую команду; использовать следующий свободный номер (`findMaxTeamNumber + 1`) и залогировать `warn` с указанием конфликтующего номера.
- `importFromRegistrations` (массовый импорт всех пар разом) — тот же принцип: `teamNumber` каждой импортируемой пары берётся из её `position`, а не из порядка перебора реестра регистраций.
- Один корт встречается дважды в одной волне быть не должно (в квалификации на конкретном корте одновременно может идти только 1 матч — уже гарантируется `validateCourtFree`/доской кортов), сортировка по корту в рамках волны детерминирована без дополнительной обработки дублей.

## Открытые вопросы
Нет — все три пункта фидбека формализуются как технические фиксы существующей логики без новых бизнес-решений; технические решения по неоднозначным местам (граница волны для "пограничного" матча нечётного случая, конфликт номеров при смешении путей создания команды) приняты выше и зафиксированы в Edge cases.
