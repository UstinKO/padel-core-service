# LFPT-1440: Feature многомодульный монолит, фаза 6 — перевести внутренние запросы к клубам на порты

## Статус
done

## Источник
[Issue #1440](https://github.com/UstinKO/padel-core-service/issues/1440). Техническая постановка по утверждённой фазе 6. Родитель [#1051](https://github.com/UstinKO/padel-core-service/issues/1051).

## Контекст / зачем
Закрыть прикладное чтение клубов в регистрации, каталоге, профиле, расписании напоминаний и уведомлениях перед сменой владельца JPA.

## Связь с MASTER.md
[MASTER](../MASTER.md) определяет роли, границы клубного доступа, регистрацию, турнирные состояния и хранение истории вместе с подтверждённым изменением. Сценарии сохраняют текущие инварианты. Зависимости [#1439](https://github.com/UstinKO/padel-core-service/issues/1439).

## Требования

### Функциональные

- Перевести обнаруженные неадминистративные запросы по ID, пакетам ID и статусу активности на типизированные application-порты, сохранив правила отсутствующего или выключенного клуба.
- Сохранить пакетные выборки, порядок, количество запросов и текущие транзакции. Сверить актуальный граф с ранее подготовленным инвентарём.

### Нефункциональные
- Java release 17, JDK 21 в CI, одна транзакционная граница и один Boot JAR.
- Каждый PR проходит полный verify на отдельной PostgreSQL, артефактные и архитектурные guards, runtime/релевантный браузер и проверку совместимости предыдущего релиза.
- Сохраняются действующие права, i18n ES/RU/EN и внешние контракты. Новых пользовательских строк нет.

## Вне скоупа
Ручной релиз остаётся обычным. Физическая миграция PostgreSQL, Swarm и изменения бизнес-правил вне задачи.

## Изменения в системе

### API
Прежние MVC/HTTP/WS входы, поля, статусы и права.

### БД
Прежняя PostgreSQL и schema. Отдельная тестовая БД для интеграции.

### UI
Действующие клиенты используют прежние данные. Приёмочные сценарии запускаются через штатные входы.

### Документация
[План фазы 6](../../docs/modular-monolith/phase-6/README.md), документация фактических границ, затронутые endpoints и техническая карта при необходимости.

## Критерии приёмки

- [x] Внутренние потребители вне отдельных административных операций обращаются к сценариям или конкретным портам. Снаружи не возвращаются entity, Sort или Pageable.
- [x] Проверки регистрации, каталога и уведомлений сохраняют прежние результаты для активного, выключенного и отсутствующего клуба, запросы остаются пакетными.
- [x] Проверенный JAR самостоятельно собирается и запускается с прежней схемой.

[Реализация и результаты проверок](../../docs/modular-monolith/phase-6/internal-club-reads.md).

## Edge cases
Активные, выключенные и отсутствующие данные, пустой результат, прежние права, повтор запроса и rollback. Границы проверяются на актуальной схеме.

## Открытые вопросы
Бизнес-вопросов нет. Технические подзадачи выделяются по фактическим связям JPA и потребителям. Реальные пользовательские данные и production-сервер не используются для QA.
