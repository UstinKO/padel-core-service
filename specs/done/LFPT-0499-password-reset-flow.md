## Контекст / зачем

Пользователи сообщают, что ссылка/кнопка из письма восстановления пароля «не работает» — переход по ней не открывает форму нового пароля, пароль нельзя сменить, войти в аккаунт невозможно.

Анализ кода подтверждает конкретную причину: `PasswordResetController#mostrarFormularioNuevoPassword` (`GET /recuperar-password?token=...`) при невалидном, просроченном или уже использованном токене возвращает `view "error"`. Шаблона `templates/error.html` на корневом уровне **не существует** (есть только `templates/error/{403,rate-limit,tournament-not-found}.html` — Thymeleaf-резолвер имени вида `"error"` ищет файл `templates/error.html`, которого нет) → `TemplateInputException` → 500 вместо понятного сообщения. Для пользователя (и для любого email-клиента/антивирусного сканера ссылок, который делает `GET` по ссылке раньше) это выглядит как «ссылка не работает».

Этот же баг уже был описан отдельно и раньше в issue [#425](https://github.com/UstinKO/padel-core-service/issues/425) (бэкенд-редирект на `/login?error=reset_expired`, ещё не реализован) и в issue [#428](https://github.com/UstinKO/padel-core-service/issues/428) (фронтенд-сообщение на странице входа для `?error=reset_expired`, зависит от #425, тоже не реализован). Эта спека реализует бэкенд-часть (закрывает #425) и расширяет её по просьбе заказчика: улучшенное логирование причин отказа и сквозная проверка всего сценария восстановления пароля (генерация токена → письмо → переход по ссылке → смена пароля → старый пароль не работает → новый работает → токен нельзя переиспользовать → просроченный токен не крэшит).

Фронтенд-часть (понятное сообщение именно на странице `/login` для `reset_expired`, кнопка «запросить новое письмо») — отдельная задача **#428**, зависящая от этой (по конвенции проекта `GIT_WORKFLOW.md` §1.4 — frontend и backend не смешиваются в одном PR). После этого PR #428 технически не блокирован (бэкенд уже отдаёт `?error=reset_expired`).

## Требования

### Функциональные

1. `GET /recuperar-password?token=...` с невалидным, просроченным или уже использованным токеном — редирект `302` на `/login?error=reset_expired` вместо попытки отрендерить несуществующий view `"error"`.
2. `GET /recuperar-password?token=...` с валидным токеном — поведение без изменений: `redirect:/?token=...` (главная страница, JS `password-reset.js` подхватывает токен и показывает модалку нового пароля).
3. Логирование в `PasswordResetService`/`PasswordResetController` — указывать конкретную причину отказа при проверке токена:
   - токен не найден в БД;
   - токен уже использован (`used = true`);
   - токен просрочен (`expiryDate` в прошлом).
   Во всех случаях — на уровне `warn`, с email/playerId (если известен) для диагностики, **без вывода полного значения токена в открытом виде** (это секрет для одноразового сброса пароля) — маскировать (например, первые 8 символов + `...`).
4. `requestPasswordReset` — залогировать фактический `resetUrl`, который попадёт в письмо (на уровне `info`, без сокращения — сам URL не секрет, секрет — токен в нём; это осознанное отличие от п.3: нужно для диагностики жалоб вида «ссылка ведёт не туда», а токен внутри URL и так уже логируется один раз здесь по необходимости — обрезать нет смысла, т.к. URL и так уходит пользователю в письме).

### Нефункциональные

- i18n: новых пользовательских строк не добавляется (сообщение на `/login` для `reset_expired` — отдельная задача #428, не в этом PR).
- Безопасность: токен восстановления пароля — одноразовый секрет; не логировать его в открытом виде целиком (см. п.3 выше). Поведение при неверном/просроченном токене не должно раскрывать существование/несуществование email (уже так — `requestPasswordReset` всегда возвращает `true`, не трогаем).

## Вне скоупа

- Сообщение на странице `/login` для `?error=reset_expired` (кнопка «запросить новую ссылку») — issue #428, отдельный PR.
- Проверка фактического значения `APP_BASE_URL` на продакшен-сервере (нет доступа к прод-окружению из облачной песочницы, где выполняется этот прогон) — отмечается как ограничение в отчёте тестировщика, не блокирует этот PR.
- Реальный клик по ссылке из настоящего письма в Gmail/другом почтовом клиенте (нет доступа к реальному почтовому ящику в облачной песочнице) — вместо этого: прямой `curl`/Playwright по точному URL, который формирует `PasswordResetService`, что эквивалентно для серверной части флоу (сервер не различает «клиент кликнул в Gmail» и «клиент открыл URL напрямую» — это один и тот же `GET`-запрos).
- Изменение `TOKEN_EXPIRATION_HOURS` (24 часа) или механизма генерации токена (`UUID.randomUUID()`) — не запрошено, не трогаем.
- `cleanExpiredTokens()` — существующий метод, не вызывается по расписанию ни из одного шедулера (проверить отдельно, не в скоупе этой фичи — если окажется мёртвым кодом, это отдельная находка для `gh issue create`, не фикс здесь).

## Критерии приёмки

- [ ] Невалидный/несуществующий токен на `GET /recuperar-password?token=...` → `302 /login?error=reset_expired`, без исключения в логах приложения.
- [ ] Просроченный токен (expiryDate в прошлом) → тот же результат.
- [ ] Уже использованный токен (`used=true`) → тот же результат.
- [ ] Валидный, неиспользованный, непросроченный токен → `redirect:/?token=<token>` (поведение не изменилось).
- [ ] При каждом из трёх случаев отказа (not-found/used/expired) в логе есть `warn`-запись, явно называющая причину, без полного токена в открытом виде.
- [ ] `requestPasswordReset` логирует собранный `resetUrl` на уровне `info`.
- [ ] Полный цикл (интеграционный тест + ручная проверка в cloud-окружении): `requestPasswordReset(email)` создаёт токен в БД → `GET /recuperar-password?token=...` с этим токеном редиректит на главную с токеном → `POST /recuperar-password/confirmar` с новым паролем возвращает `success=true` → старый пароль не проходит `PasswordEncoder.matches(...)` → новый пароль проходит → повторный `POST /recuperar-password/confirmar` с тем же токеном возвращает `success=false` (токен уже `used`).
- [ ] Автотесты на все перечисленные ветки в `src/test/java/.../controller/player/PasswordResetControllerTest.java` и/или `service/PasswordResetServiceTest.java`.
- [ ] `./mvnw verify` проходит.

## Edge cases

- Токен отсутствует в query (`GET /recuperar-password` без `?token=`) — уже обрабатывается глобально (`GlobalExceptionHandler#handleMissingParam` → `redirect:/`), не меняем.
- Два параллельных запроса сброса пароля для одного игрока — `requestPasswordReset` удаляет старые токены (`tokenRepository.deleteByPlayer`) перед созданием нового, так что при повторном запросе первое письмо станет невалидным (ожидаемое поведение, не новое для этой задачи — сохраняется как есть).
- Email, который прогружает все ссылки письма сканером безопасности (Outlook Safe Links и т.п.) сразу при доставке: `GET /recuperar-password` — операция без побочных эффектов на токен (не помечает `used`), только читает; статус токена не меняется, пользователь всё ещё сможет пройти по ссылке позже. Явный тест на этот edge case не нужен — это свойство уже существующего кода (`validateToken` — read-only), фиксируем в отчёте тестировщика как проверенное наблюдение, а не меняем код.
