## Требования

### Функциональные

#### Проблема и результат
PlayoffMatchingEngine подтверждён владельцем как пилот. Существующие 8 unit-тестов и TeamPlayoffEndToEndTest не являются полной браузерной приёмкой; preview seed не содержит готового полного набора пилота. Нужны исходные проверки и воспроизводимые синтетические данные до изменения сборки. Родитель #1041; не включает перенос алгоритма.

#### Что сделать
- На актуальном master зафиксировать SHA/артефакт; повторно проверить потребителей движка, engine/service tests и известные дефекты.
- Переиспользовать PlayoffMatchingEngineTest и TeamPlayoffEndToEndTest: 8–16 команд, play-in, early seeding/TBD/backfill, полуфинал и финал, NO_SHOW, история/восстановление; добавлять только отсутствующие проверки поведения.
- Проверить порядок входных кандидатов/пар при равной стоимости, три PriorityOrder, warning/allConstraintsSatisfied, пустой/нечётный вход. В production service используются REMATCH_FIRST и STRENGTH_FIRST; SEED_FIRST допускает unit-only проверку.
- Подготовить resettable пилотные fixtures в существующем изолированном контуре: 8, 9 и 16 команд, воспроизводимые квалификационные результаты, своё/чужое управление клубом, завершённый и незавершённый турнир. Расширять только guard-защищенный preview/test-механизм; без новых публичных endpoints и Liquibase.
- Не менять контракт существующего PreviewController.Fixtures без нужды; отдельные pilot-данные должны очищаться только в своей тестовой среде. Публикуемые инструкции не содержат fixture-паролей.
- Выполнить unit/integration/full verify на отдельной БД, сохранить исходный отчёт. Ошибки текущего приложения не скрывать рефакторингом; отдельные defect issues.

#### Критерии приёмки
- [x] 8 engine unit-тестов и действующие Team Playoff integration проходят; пробелы покрытия явно перечислены.
- [x] Исходный полный verify выполнен на отдельном PostgreSQL с текущим master, SHA/команды/результаты записаны.
- [x] Fixtures 8/9/16 и роли доступны последующей браузерной задаче, повторная подготовка/очистка воспроизводимы.
- [x] Проверки history/conductVersion, stale expectedTeam, транзакционного отказа/блокировок по фактическим гарантиям определены; нет выдуманной гарантии конкурентной записи.
- [x] Код поведения алгоритма, схемы и текущие пути БД не менялись.
- [x] Фактические проверки/данные описаны в docs/modular-monolith/phase-1/ и pilot-and-e2e.md.

#### Зависимости
Подготовлено в #1041; основные решения владельцем приняты. Можно начать с актуального master, не ожидая остальных этапов миграции.


### Нефункциональные




Каждый PR самостоятельно оставляет приложение работоспособным: корневая полная сборка/verify, отдельный PostgreSQL для integration, smoke итогового jar/образа, действующие MVC/API/React/Expo, rollback. Реальные пользовательские БД/уведомления не используются. Java release 17, бизнес-правила и JSON/WS не меняются. Один слой и отдельный PR; без pipeline:ready, автомержа и деплоя в рамках подготовки. Документация — docs/modular-monolith/, спека с настоящим LFPT-номером.

Пилот сохраняет пути db/changelog, схему/данные/подключение. Временный root legacy src имеет одного владельца и один путь компиляции.

## Вне скоупа

Выделение persistence, физический перенос БД/Swarm, новые бизнес-правила, внутренний HTTP/микросервисы, полный рефакторинг TeamPlayoffService (#509), остальные движки и API codegen.

## Изменения в системе

### API

Публичные endpoints без изменений; допускается только guard-защищённая test/preview-подготовка fixtures без новой публичной точки входа.

### БД

Нет Liquibase и production-изменений данных. Синтетические fixtures только в своей тестовой среде.

### UI

Внешний UI без изменений; browser/API smoke необходим по границе задачи.

### Документация

docs/modular-monolith/phase-1/ и актуальные карта/команды/пути по затронутой области; docs/Home.md, docs/architecture.md и .agents/PROJECT.md при реализации сборочных изменений. Фактическое состояние не подменяется будущими семью модулями.

## Зависимости

Согласованные решения #1041; можно начинать с актуального master, подготовительный родитель не обязан быть закрыт.

## Edge cases

Равная стоимость/порядок перечисления, три приоритета, пустой/нечётный вход, play-in/TBD/backfill, no-show, stale pair/version, чужой клуб, rollback/history/after-commit. Для сборки: CWD тестов, один main/repackage/bean, frontend один раз, модульные отчёты, явный runtime jar, отсутствие shadow-класса. Применимость — по матрице и конкретному изменению; недостижимый из UI вход не получает выдуманную кнопку.

## Открытые вопросы

Неразрешённых бизнес-вопросов нет. Точные fixtures/ожидаемые результаты и дефекты фиксируются исходными #1047/#1048; технический выбор внутри согласованной границы выполняется по анализу, без изменения поведения.
