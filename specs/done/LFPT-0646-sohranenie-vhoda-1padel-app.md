# LFPT-0646: Feature сохранение входа в 1Padel.App после перезапуска — персистентный refresh-токен для веб-клиента (Google и почта)

## Статус
done

## Источник
`specs/requests/LFPT-0646-sohranenie-vhoda-1padel-app.md`

## Контекст / зачем

Веб-клиент 1Padel.App (`/app/`, LFPT-0637/LFPT-0638) теряет сессию при закрытии и повторном открытии вкладки/PWA: `mobile-app/src/AuthContext.tsx` держит refresh-токен на вебе только в памяти текущей вкладки (`store.get`/`store.set` — no-op для `Platform.OS === 'web'`, комментарий в коде: «Браузерные токены только в памяти текущей вкладки»). На native (iOS/Android через Expo) токен уже персистентен — `expo-secure-store`. Пользователь ожидает, что вход сохранится, как в обычном мобильном приложении.

## Связь с MASTER.md

Не затрагивает `specs/MASTER.md` — чисто клиентская (мобильный веб-клиент) задача, бизнес-инварианты регистрации/турниров не меняются. Серверная аутентификация (`/api/auth/**`, stateless JWT, `docs/auth-flow.md`) не меняется.

## Требования

### Функциональные

- Refresh-токен веб-клиента персистится между закрытием и открытием вкладки/PWA — одинаково для входа по почте (`client.login`) и через Google (`client.adopt` после редиректа с токенами во fragment, LFPT-0637).
- При старте приложения (`AuthProvider` → `retryRestore` → `client.restore()`) сохранённый токен подхватывается и обменивается на новый access-токен — пользователь не видит экран входа, если refresh ещё не истёк (7 дней, `JwtService`).
- Логаут (`client.logout`) физически удаляет сохранённый токен — следующее открытие приложения требует новый вход.
- Хранение остаётся за тем же гейтом `secureAuthContext`, что и сам вход (только HTTPS или `localhost`/`127.0.0.1`) — на незащищённом origin ничего не сохраняется, как и сейчас нельзя войти.
- Native-поведение (SecureStore) не меняется.
- Логика выбора/использования хранилища (web vs native, доступно/недоступно) выносится в отдельный тестируемый модуль без JSX и без прямой зависимости от React — `mobile-app/src/sessionStore.ts` (в `AuthContext.tsx` сейчас эта логика встроена прямо в JSX-файл, который невозможно юнит-тестировать текущим раннером `node --test`, см. "Edge cases").

### Нефункциональные

- i18n: новых пользовательских строк нет.
- Безопасность: хранение refresh-токена в `localStorage` веб-версии расширяет поверхность атаки при XSS (токен, которого раньше не было после закрытия вкладки, теперь доступен JS на странице в течение до 7 дней) — осознанный трейд-офф по прямому запросу заказчика («сохранять вход»), смягчённый существующими мерами: HTTPS обязателен (`secureAuthContext`), CSP уже включён для `/app/` (LFPT-0638), хранится только refresh-токен (не access-токен), срок жизни refresh не меняется (7 дней, решение не этой задачи). Access-токен как и раньше не персистится — только в памяти.
- Деградация: если `localStorage` бросает исключение (приватный режим Safari, заблокированное хранилище и т.п.) — `get`/`set` не должны ронять вход/выход, сессия просто не переживает закрытие (как сейчас).

## Вне скоупа

- Серверная ревокация refresh-токена при логауте — сервер stateless (`docs/auth-flow.md` §5, «Stateless — сессия не создаётся»), «удаление сессии» на логауте — чисто клиентская операция (удаление токена из хранилища). Полноценная ревокация потребовала бы таблицы/блэклиста токенов на сервере — не запрошено и не нужно для этой задачи.
- Контент внешнего репозитория `github.com/eugenegwork-coder/1padel-app` — не читается и не применяется (вне доступа сессии к GitHub; политика LFPT-0637/LFPT-0638 — сторонние материалы не используются как патч без возможности ревью).
- Любые изменения `/api/auth/**` или `JwtService` — не требуются, срок жизни refresh-токена не меняется.
- "Запомнить меня" как отдельный переключатель в UI — не запрошено; сохранение всегда включено (как и раньше на native).

## Изменения в системе

### API
Нет изменений.

### БД
Нет изменений.

### UI (клиент)

- `mobile-app/src/sessionStore.ts` (новый файл) — `createWebSessionStore(storage, key)` и `createNativeSessionStore(secureStore, key, keychainAccessible?)`, обе возвращают `Store` (`{ get, set }`), совместимый с типом, уже используемым в `auth.ts`.
- `mobile-app/src/AuthContext.tsx` — `store` собирается через `createWebSessionStore`/`createNativeSessionStore` вместо встроенной логики; на вебе передаётся `window.localStorage`, только если `secureAuthContext` истинен и `window` определён, иначе `null` (хранение недоступно).
- Документация: `docs/auth-flow.md` — короткая заметка в разделе про `client=app`/мобильный JWT-флоу о персистентности refresh-токена на вебе через `localStorage` (сейчас там только upоминание native `expo-secure-store` подразумевается неявно — явно этого не описано, добавить строку).

## Критерии приёмки

- [ ] `createWebSessionStore` с рабочим `localStorage`: `set('r1')` → `get()` возвращает `'r1'` у **нового** экземпляра стора с тем же объектом хранилища (симуляция перезапуска приложения — состояние только в хранилище, не в памяти).
- [ ] `createWebSessionStore` с `storage = null` (гейт `secureAuthContext` не прошёл): `get()` всегда `null`, `set()` не бросает исключение.
- [ ] `createWebSessionStore` с хранилищем, у которого `getItem`/`setItem` бросают исключение (приватный режим браузера): `get()` возвращает `null` без исключения, `set()` резолвится без исключения.
- [ ] `createWebSessionStore`: `set(null)` вызывает `storage.removeItem(key)` (логаут физически удаляет токен).
- [ ] `createNativeSessionStore`: `set('r1')` вызывает `secureStore.setItemAsync(key, 'r1', { keychainAccessible })`, `get()` вызывает `secureStore.getItemAsync(key)`, `set(null)` вызывает `secureStore.deleteItemAsync(key)` — native-поведение не изменилось относительно текущего кода.
- [ ] Реальный веб-браузер (Playwright против собранного `/app/`, см. "Edge cases" про бэкенд): вход по почте → перезагрузка страницы → пользователь остаётся на экране «Мои мероприятия» без повторного ввода пароля.
- [ ] То же для входа через Google (можно проверить через `client.adopt` эквивалент — ручная симуляция fragment-токенов в адресной строке, т.к. реальный Google OAuth недоступен в автоматической проверке).
- [ ] Логаут на вебе → `localStorage.getItem('onepadel.refresh.v1')` возвращает `null` → перезагрузка страницы показывает экран входа.
- [ ] `pnpm --dir mobile-app test`, `pnpm --dir mobile-app typecheck`, `pnpm --dir mobile-app build:site` — все зелёные.

## Edge cases

- `localStorage` недоступен/бросает исключение (приватный режим Safari на iPhone — основная целевая платформа клиента) — покрыто отдельным критерием приёмки выше.
- Origin не HTTPS и не `localhost`/`127.0.0.1` — хранение не включается (как и вход в целом недоступен при `!secureAuthContext`, без изменений в этой задаче).
- Истёкший refresh-токен в хранилище (прошло 7+ дней) — уже обрабатывается существующей логикой `auth.ts` (`refresh()` → `SESSION_EXPIRED` → `clear()` → `onExpired()`), не требует изменений.
- Два параллельных входа на разных вкладках одного браузера (общий `localStorage`) — вне скоупа; существующий код не синхронизирует состояние между вкладками ни сейчас, ни после этой задачи (как и раньше, каждая вкладка живёт своим `session` в памяти, расходится только при логауте/рефреше в одной из них — не хуже текущего поведения на native с несколькими устройствами).
- Юнит-тесты `sessionStore.ts` гоняются как обычный `.ts`-модуль без JSX через `node --test` (Node 22 поддерживает нативный strip типов для `.ts`); `AuthContext.tsx` (JSX) таким способом не тестируется — это существующее ограничение раннера проекта, не regress от этой задачи. Браузерная E2E-проверка (Playwright) выполняется тестировщиком отдельно, с подъёмом бэкенда (`SPRING_PROFILES_ACTIVE=cloud`) и сборкой `/app/`.
