# LFPT-1187: Клубный аккаунт — свои мероприятия на назначенных площадках

Статус: approved. Источник: согласованный план пользователя 18.11.2026; issue #1187.

## Правила
- SUPER_ADMIN видит и управляет всеми мероприятиями всех клубов. ADMIN/ORGANIZER сохраняют действующие полномочия.
- CLUB_ADMIN видит и управляет только мероприятиями с ownerId своего аккаунта. Совпадение clubId не даёт доступ к чужому мероприятию.
- Создание и перенос своего мероприятия возможны только в назначенный активный клуб. Несколько клубов поддерживаются одним аккаунтом.
- Только SUPER_ADMIN назначает клубы существующему CLUB_ADMIN. Передача роли, создание аккаунта и смена пароля не входят в задачу.
- Существующий club_id переносится в набор назначений; авторство и сами мероприятия не меняются. Снятие площадки закрывает создание/перенос на неё, но не отбирает у создателя ранее созданный турнир.
- Все производные ресурсы (матчи, корты, результаты, история, регистрации, оплаты) используют единую проверку ownerId. Копирование чужого турнира из админки запрещено.
- Список игроков, их административная история, статистика и недавние события клубного кабинета ограничены своими мероприятиями. Общедоступные карточки игроков/турниров не меняются.
- Уровни игроков и данные клубов CLUB_ADMIN не редактирует.

## Реализация
Аддитивная таблица owner_club_access_db с переносом прежней связи, без изменения старых миграций. Права назначения перечитываются из БД, чтобы открытая сессия не сохраняла отозванные площадки. Серверные обработчики /admin/club-accounts доступны только SUPER_ADMIN; их шаблоны — зависимая задача #1188.

## Приёмка
1. Два аккаунта на одной площадке: свой турнир доступен, чужой закрыт по ID на всех форматах и сопутствующих страницах.
2. Две назначенные площадки: создание и выбор сохраняются; неназначенная/неактивная площадка отклонена, в том числе при подмене формы.
3. SUPER_ADMIN сохраняет доступ ко всем и меняет список назначений; прочие роли не могут назначать клубы.
4. Список, сводка и игроки исключают чужие мероприятия той же площадки.
5. Миграция сохраняет одиночную привязку, существующие результаты/оплаты/авторство не меняются.
6. Полный mvnw verify на отдельной PostgreSQL, проверки документации/relay; затем совместная browser-проверка с #1188.
