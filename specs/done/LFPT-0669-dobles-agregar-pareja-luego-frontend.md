# LFPT-0669: Feature отображение резерва «ожидает партнёра» / «пара сформирована» и страницы подтверждения из email

## Статус
done

## Источник
Клиентский запрос заказчика (Telegram): [specs/requests/LFPT-0668-dobles-agregar-pareja-luego.md](requests/LFPT-0668-dobles-agregar-pareja-luego.md). Issue: #669. Зависит от бэкенд-спеки [LFPT-0668](LFPT-0668-dobles-agregar-pareja-luego.md) (issue #668, PR #670, `pipeline:ready`).

## Контекст / зачем

Бэкенд LFPT-0668 переводит просроченные `SOLO_ADD_LATER`-заявки в `WAITLIST` (резерв) вместо тупикового `SOLO_EXPIRED`. В существующей таблице «Lista de Espera» админ-панели (`admin/tournaments/details.html`) все `WAITLIST`-записи выглядят одинаково — нет способа отличить заявку, которая ещё ждёт партнёра, от полностью сформированной пары, ожидающей свободного места. Заказчик явно просит различать эти два состояния.

**Важное уточнение по факту реализации бэкенда** (на момент написания этой спеки): чтобы self-service-ссылки из писем (`/reserva/accion/confirmar`, `/reserva/accion/cancelar`) не вели на 500/404 в проде в промежутке между деплоем бэкенда и деплоем фронта, бэкенд уже включает минимальные рабочие шаблоны (`reserve-cancel-confirm.html`, переиспользование существующего `waitlist-confirmation.html` для confirmar/результата) — см. PR #670, раздел "UI" спеки LFPT-0668 там слегка расходится с фактом по этой причине (явная, обоснованная техническая правка в процессе реализации). Эта фронт-задача **не создаёт их с нуля** — только проверяет, что они достаточно соответствуют общему стилю сайта (они уже построены на основе существующего `waitlist-confirmation.html`), и при необходимости делает точечные визуальные правки. Основной объём этой задачи — пункт 1 ниже.

## Связь с MASTER.md

Не меняет инварианты `specs/MASTER.md` — чисто отображение существующих (после LFPT-0668) состояний `WAITLIST` в уже существующей админ-таблице.

## Требования

### Функциональные

1. **Различение в таблице «Lista de Espera»** (`admin/tournaments/details.html`, секция "Таблица 4"): для каждой `WAITLIST`-записи парного турнира показывать явный бейдж:
   - «Резерв — ожидает партнёра» (янтарный), если `reg.partnerRegistered == false` (DTO уже отдаёт это поле — `registration.getPartner() != null`, готово на бэкенде, ничего нового считать не нужно);
   - «Резерв — пара сформирована» (зелёный), если `reg.partnerRegistered == true`.
   - Для `INDIVIDUAL`-турниров (у которых `partner` не применяется концептуально) бейдж не показывать — определять по `tournament.modalidad == DOBLES`.
2. Полноценные готовые пары (сценарий «пара сформирована») не должны визуально выглядеть как единственная строка на двух игроков — таблица уже рисует по строке на каждого игрока пары (как и везде в проекте), это не меняем; бейдж просто уточняет статус каждой строки.
3. Не ломать существующую кнопку "Перевести в основной состав" (`move-to-main`) — она должна оставаться доступной независимо от бейджа (у администратора есть право вручную перевести в основной состав в любой момент, это не меняется этой фичей).
4. i18n — два новых ключа (`admin.tournaments.details.waitlist.pending_partner`, `admin.tournaments.details.waitlist.pair_complete`) в `messages_{es,ru,en}.properties`.

### Нефункциональные
- Чисто визуальное изменение, без новых запросов к серверу (данные уже приходят в существующем DTO).

## Вне скоупа
- Создание self-service-страниц `/reserva/accion/**` с нуля — уже сделано в бэкенд-PR #670 (см. "Контекст" выше).
- Любая логика качалификации/генерации сетки матчей — она и сейчас берёт только `CONFIRMED`-регистрации, `WAITLIST` (в любом из двух состояний) туда не попадает ни до, ни после LFPT-0668 — требование заказчика "незавершённые пары не должны попадать в квалификацию" уже выполняется статус-моделью, без изменений.

## Критерии приёмки
- [ ] Турнир DOBLES, резервная заявка без партнёра (`WAITLIST`, `partnerRegistered=false`) — в таблице "Lista de Espera" виден бейдж «ожидает партнёра».
- [ ] После добавления партнёра та же заявка (если осталась в `WAITLIST`, т.е. сценарий Б/В из LFPT-0668) — бейдж меняется на «пара сформирована» для обеих строк пары.
- [ ] Турнир INDIVIDUAL — бейджи не показываются (не применимо).
- [ ] Кнопка "Перевести в основной состав" работает как раньше для обоих состояний.
- [ ] Новые строки — во всех трёх `messages_{es,ru,en}.properties`; страница под `Accept-Language: ru` показывает русский текст бейджа.
- [ ] `python3 .github/bin/docs-drift.py` — 0 расхождений (чисто визуальное изменение, но свериться).
- [ ] `./mvnw verify` — зелёный.

## Edge cases
- Турнир без ни одной `WAITLIST`-записи — таблица целиком скрыта, как и сейчас (`tournament.waitlistCount > 0`), ничего не меняется.
- Запись `WAITLIST` без `partnerId`, но `isDoubleRegistration == true` (теоретически не должно происходить после LFPT-0668 — isDoubleRegistration ставится в true только при наличии партнёра) — на всякий случай бейдж ориентируется строго на `partnerRegistered`, а не на `isDoubleRegistration`.
