# LFPT-1465: Feature многомодульный монолит, фаза 6 — перенести хранение токенов восстановления пароля

## Статус
done

## Источник
[Задача #1465](https://github.com/UstinKO/padel-core-service/issues/1465), срез [#1443](https://github.com/UstinKO/padel-core-service/issues/1443). Предшественник PR #1458.

## Контекст / зачем
Выделить самостоятельное хранилище восстановления учётных записей игроков в padel-persistence. Связь с аккаунтом представляется playerId, физический ключ и таблица сохраняются.

## Связь с MASTER.md
[MASTER](../MASTER.md) определяет роли, доступ к клубам, вход, регистрацию и контакты. Срез сохраняет их действующие правила.

## Требования

### Функциональные
- Перенести PasswordResetToken, единственный репозиторий и адаптер в persistence. Выдача, проверка, отзыв при удалении/объединении профиля и очистка обращаются к порту application.
- Сохранить 24 часа, проверки активного негостевого профиля, ответ на неизвестный email, блокировку строки токена и общую транзакцию смены пароля.

### Нефункциональные
- Java 17, один Boot JAR и общая транзакционная инфраструктура.
- Проверить целевой сценарий на прежнем и новом JAR с той же схемой PostgreSQL.
- Сохранить строки ES/RU/EN, HTTP-контракты, версии библиотек и пути миграций.

## Вне скоупа
Физическая миграция PostgreSQL планируется отдельно. Соседние продуктовые сценарии остаются в соответствующих задачах.

## Изменения в системе

### API и UI
Прежние MVC/API и действующие шаблоны и клиенты. Выдача и подтверждение восстановления используют прежние маршруты.

### БД
Действующая схема. Проверка на отдельной PostgreSQL с данными прежней сборки.

### Документация
[План фазы 6](../../docs/modular-monolith/phase-6/README.md), [вход и учётные записи](../../docs/auth-flow.md), [разбиение идентичности](../../docs/modular-monolith/phase-6/identity-storage.md).

## Критерии приёмки
- [x] Выданный предыдущим JAR токен принимается новым. Смена пароля и отметка used записываются вместе, повтор отклоняется. При отказе после записи пароля обе записи откатываются.
- [x] PostgreSQL, схема и история Liquibase сохраняются. Работают прежние MVC и API.

## Edge cases
Существующие MVC и REST-входы восстановления сохраняют поля, статусы и редиректы. Выдача, отзыв и очистка используют ID игрока. Проверяются использованный, истёкший и неизвестный токен, выключенный и гостевой игрок, повтор и rollback после ошибки записи.

## Открытые вопросы
Бизнес-вопросов нет. Точный граф и тесты уточняются по актуальному master перед реализацией.
