## Контекст / зачем
`Nivel` — плоский enum с уровнями/категориями турнира, вперемешку мужские (`C*`), женские (`D*`) и микс (`SUMA_*`) значения, с пробелами в шкале (не все смежные пары присутствуют, женская шкала короче мужской). Форма создания/редактирования турнира показывает **все** значения `Nivel.values()` без фильтрации по `generoFormato` — организатор технически может выбрать `D9` для турнира с `generoFormato = MASCULINO`. Нужно дополнить шкалы до полных зеркальных наборов и отфильтровать список в форме по выбранному полу.

## Связь с MASTER.md
Не затрагивает инварианты `specs/MASTER.md` — форматы турниров, статусы регистрации и роли не меняются. `MASTER.md` не редактируется.

## Анализ (что реально происходит в коде)

- `Tournament.categoriaNivel` — поле типа `Nivel` (`@Enumerated(EnumType.STRING)`, колонка `categoria_nivel VARCHAR(50)`), не строка "на глаз" — расширение enum технически безопасно для JPA-маппинга.
- **Критично, не упомянуто в issue:** на колонку `tournaments_db.categoria_nivel` в БД наложен `CHECK`-constraint `tournaments_db_categoria_nivel_check`, явно перечисляющий допустимые значения (см. `v1.43-add-nivel-d9.yaml`, `v1.45-add-nivel-suma16.yaml` — каждое прошлое расширение `Nivel` сопровождалось миграцией, обновляющей этот constraint). Без новой миграции INSERT/UPDATE турнира с любым новым значением `Nivel` упадёт на уровне БД с `CheckViolationException`, несмотря на то что Java-enum его пропустит. Формулировка issue "чисто аддитивное изменение… безопасно для отдельного деплоя" верна только в части существующих данных — миграция всё равно обязательна для новых значений. Учтено в разделе "БД" ниже.
- `AdminController.getNiveles()` (4 места: `GET /admin/tournaments/new`, `POST /admin/tournaments` при ошибке валидации, `GET /admin/tournaments/{id}/edit`, `POST /admin/tournaments/{id}/edit` при ошибке валидации) и `AdminTournamentCopyController.copyTournament` (`GET /admin/tournaments/{id}/copy`) — все передают в шаблон `Nivel.values()` без фильтрации.
- `admin/tournaments/form.html` рендерит `<select id="categoriaNivel">` через `th:each="nivel : ${niveles}"`, без клиентского JS, связанного с `generoFormato`. У `generoFormato`-селекта уже есть прецедент клиентского `onchange`-обработчика на этой же странице (`onTipoChange(this)` для поля `tipo`, показывающего/скрывающего `modalidadGroup`) — расширяем тем же паттерном.
- `Nivel.getDisplay()` возвращает `name()` (не `orden` — судя по всему, существующая особенность/недоработка, `orden` нигде не читается кроме конструктора) — вне scope этой задачи, не трогаем.
- `Nivel.PLAYER_LEVELS`/`isPlayerLevel()` — отдельный, не связанный с турнирами список "уровень игрока" (`players/perfil.html`, `admin/players/details.html`, `registro.html`). Формы игрока используют **захардкоженный** `<option>`-список в `registro.html` (`C9,C8,C7,C6,C5,D9,D7,D8,D6,C4`), не читают `Nivel.values()`/`isPlayerLevel()` динамически — issue касается только уровней **турнира**, расширение шкалы игрока (`D5`, `D4` как персональный уровень) не запрошено и не делается (см. "Вне скоупа").
- `SIN_ESPECIFICAR` — служебный sentinel для `PlayerPadel.nivelJugador`, **никогда не входил** в CHECK-constraint `categoria_nivel` ни в одной из прошлых миграций → фактически никогда не мог быть валидным значением турнира на уровне БД, хотя `getNiveles()` его в форму по факту отдаёт (существующий, не задокументированный в issue баг — не тестируется, не выбирается ни в одном реальном сценарии). Новая gender-based фильтрация естественным образом исключает его из выбора и на форме (у него нет `generoAplicable`) — не отдельная фича, а побочный эффект схемы фильтрации.

## Требования

### Функциональные

1. **Дополнить `Nivel`** до зеркальных мужской/женской шкал + расширенного mixto:
   - Мужские одиночные (уже полные): `C9, C8, C7, C6, C5, C4`.
   - Мужские смежные пары (добавить недостающие): `C9_C8 ("C9/C8")`, `C8_C7 ("C8/C7")`, `C7_C6` (уже есть), `C6_C5 ("C6/C5")`, `C5_C4 ("C5/C4")`.
   - Женские одиночные (добавить `D5`, `D4`): `D9, D8, D7, D6, D5, D4`.
   - Женские смежные пары: `D9_D8 ("D9/D8")` (новое), `D7_D8` — уже существует с display `"D7/D8"`, **переиспользуется** как пара D7/D8 (не создаётся дублирующий `D8_D7` — та же семантическая пара категорий; сохраняет обратную совместимость с уже созданными турнирами на этом значении), `D7_D6 ("D7/D6")` (новое), `D6_D5 ("D6/D5")` (новое), `D5_D4 ("D5/D4")` (новое).
   - Mixto: добавить `SUMA_10 ("10+")`, `SUMA_11 ("11+")`, `SUMA_12 ("12+")` — вместе с уже существующими `SUMA_13..SUMA_16` шкала `Suma 10–16` полная.
   - `PRINCIPIANTES`, `TODOS`, `SIN_ESPECIFICAR` — существующие значения не удаляются и не переименовываются.
2. **Привязка к полу для фильтрации.** У каждого значения `Nivel` — новый атрибут "применимый `generoFormato`" (`GenderFormat` или отсутствие для служебных/устаревших значений): все `C*` (индивидуальные и пары) → `MASCULINO`, все `D*` → `FEMENINO`, все `SUMA_*` → `MIXTO`, `PRINCIPIANTES`/`TODOS`/`SIN_ESPECIFICAR` → без привязки.
3. **Список уровней для создания нового турнира** (`GET /admin/tournaments/new`, ре-рендер `POST /admin/tournaments` при ошибке валидации, `GET /admin/tournaments/{id}/copy`) — исключает `PRINCIPIANTES`, `TODOS` (и, как естественное следствие пункта 2, `SIN_ESPECIFICAR`, у которого никогда не было валидного generoFormato для турнира).
4. **Список уровней для редактирования существующего турнира** (`GET /admin/tournaments/{id}/edit`, ре-рендер `POST /admin/tournaments/{id}/edit` при ошибке валидации) — тот же список, что в п.3, **плюс** текущее значение `categoriaNivel` турнира, даже если оно устаревшее/не привязано к полу (`PRINCIPIANTES`/`TODOS`) — иначе `<select>` откроется без выбранной опции, и не тронутое пользователем поле молча обнулится при сохранении формы.
5. **Клиентская фильтрация по полу.** На `admin/tournaments/form.html`: при выборе `generoFormato` список `categoriaNivel` показывает только значения с совпадающим `generoAplicable`, плюс любые значения без `generoAplicable`, которые уже присутствуют в списке (см. п.4 — устаревшее значение редактируемого турнира остаётся видимым независимо от выбранного пола). Если `generoFormato` ещё не выбран (пустое значение при создании) — список не фильтруется, показываются все переданные бэкендом значения. Если ранее выбранный уровень перестаёт быть видимым после смены пола — сбросить `categoriaNivel` в пустое значение (как в существующем `onTipoChange`, применяется и при `DOMContentLoaded` для уже заполненной формы редактирования).

### Нефункциональные
- i18n: не требуется — отображение уровня в форме (`nivel.display`) уже выводит `name()` enum без локализации (существующее поведение, не меняется), новых пользовательских строк текст-меток не добавляется.
- Безопасность: новая точка входа данных отсутствует — `categoriaNivel` как и раньше валидируется через `@Enumerated(EnumType.STRING)` + новый CHECK-constraint на уровне БД; попытка отправить значение, не входящее в constraint (в обход UI), как и раньше приведёт к ошибке на уровне БД, поведение эквивалентно текущему.

## Вне скоупа
- Расширение шкалы **персонального** уровня игрока (`registro.html`, `players/perfil.html`, `admin/players/details.html`, `PLAYER_LEVELS`/`isPlayerLevel()`) — issue касается только уровней/категорий турнира. `D5`/`D4` не добавляются как выбираемый персональный уровень игрока.
- Переименование/чистка уже существующего `D7_D8` под конвенцию "больший номер первым" (как у мужской `C7_C6`) — сохраняется как есть ради обратной совместимости с данными, новая пара `D9_D8` использует единообразную конвенцию мужской шкалы, но сам `D7_D8` не трогается.
- Починка `Nivel.getDisplay()` (возвращает `name()`, не человекочитаемый `orden`) — существующее поведение, не входит в issue.
- Фильтрация уровней в любых других формах/страницах, кроме `admin/tournaments/form.html` (создание/редактирование/копирование турнира) — issue называет только эту форму.
- Скрытие `SIN_ESPECIFICAR` — отдельная задача/фикс, не заводится и не документируется отдельно; здесь это только описанный побочный эффект схемы фильтрации по полу (п.3 "Требований").

## Изменения в системе

### API
Нет изменений в REST/JSON API. Затронута только server-rendered форма `admin/tournaments/form.html` (server POST `/admin/tournaments`, `/admin/tournaments/{id}/edit` не меняют контракт — по-прежнему принимают `categoriaNivel` как имя enum-значения).

### БД
Новая Liquibase-миграция `v1.47-add-nivel-categories.yaml`: `DROP CONSTRAINT IF EXISTS tournaments_db_categoria_nivel_check` + `ADD CONSTRAINT ... CHECK (categoria_nivel IN (...))` с полным обновлённым списком допустимых значений (все текущие + новые из п.1 "Требований", без `SIN_ESPECIFICAR` — не входил и раньше). Регистрируется в `changelog-master.yaml` следующим по номеру. Формат — как в `v1.43-add-nivel-d9.yaml`/`v1.45-add-nivel-suma16.yaml` (rollback — восстановление предыдущего списка).

### UI
- `src/main/java/.../model/enums/Nivel.java` — новые значения, поле `generoAplicable` (`GenderFormat`, nullable), метод(ы) для получения списка "для формы турнира" (с учётом текущего значения) и геттер `generoAplicable` для шаблона.
- `src/main/java/.../controller/admin/AdminController.java` — `getNiveles()` → принимает текущее значение уровня (`null` для create/new).
- `src/main/java/.../controller/admin/AdminTournamentCopyController.java` — аналогичная замена `Nivel.values()`.
- `src/main/resources/templates/admin/tournaments/form.html` — `data`-атрибут с `generoAplicable` на каждый `<option>` уровня, JS-обработчик `onGeneroChange()` (по аналогии с существующим `onTipoChange`), вызов при `change` `generoFormato` и при `DOMContentLoaded`.

## Критерии приёмки
- [ ] `Nivel` содержит все значения по мужской шкале `C9-C4` (одиночные + все смежные пары `C9/C8, C8/C7, C7/C6, C6/C5, C5/C4`).
- [ ] `Nivel` содержит все значения по женской шкале `D9-D4` (одиночные, включая новые `D5`, `D4`) + все смежные пары `D9/D8, D8/D7 (=D7_D8), D7/D6, D6/D5, D5/D4`.
- [ ] `Nivel` содержит полный mixto-диапазон `Suma 10-16`.
- [ ] `GET /admin/tournaments/new` — список `categoriaNivel` НЕ содержит `PRINCIPIANTES`, `TODOS`, `SIN_ESPECIFICAR`.
- [ ] На форме создания турнира: выбор `generoFormato = Masculino` в браузере оставляет в `categoriaNivel` только `C*`-значения; `Femenino` — только `D*`; `Mixto` — только `SUMA_*`.
- [ ] На форме создания турнира: смена `generoFormato` после того, как уже был выбран `categoriaNivel`, который стал недоступен под новый пол — `categoriaNivel` сбрасывается в пустое значение (не остаётся невидимо выбранным старым значением).
- [ ] `GET /admin/tournaments/{id}/edit` для существующего турнира с `categoriaNivel = PRINCIPIANTES` (или `TODOS`) — форма открывается с этим значением корректно выбранным в `<select>` (не пустым), сохранение формы без изменения уровня сохраняет то же значение.
- [ ] `GET /admin/tournaments/{id}/edit` для турнира с обычным (не устаревшим) значением, например `C7` — фильтрация по полу применяется сразу при загрузке страницы (список уже отфильтрован под текущий `generoFormato` турнира).
- [ ] Создание турнира с новым значением уровня (например, `C9_C8` или `SUMA_10`) через форму реально сохраняется в БД без ошибки (CHECK-constraint обновлён).
- [ ] Тест на persist нового значения `Nivel` через `TournamentRepository` (регрессия на CHECK-constraint, по аналогии с историей `v1.43`/`v1.45`).
- [ ] Тест на список уровней для create (без legacy) и edit (с текущим legacy-значением, если оно легаси) — юнит-тест на новый метод `Nivel`.
- [ ] `./mvnw verify` — зелёный.

## Edge cases
- Турнир уже существует с `categoriaNivel = D7_D8` (легаси-обозначение пары) — не трогается, продолжает отображаться как есть; новая пара `D9_D8` — самостоятельное отдельное значение, не подменяет и не мигрирует `D7_D8`.
- Форма редактирования турнира с легаси-значением (`PRINCIPIANTES`/`TODOS`) и админ меняет `generoFormato` на другой пол — легаси-значение, добавленное в список только как "текущее", должно остаться видимым в `<select>` даже после смены пола (не привязано ни к какому конкретному `generoAplicable`, JS не должен его скрывать, но должно быть и не единственной опцией — остальные варианты фильтруются по новому полу как обычно).
- Ошибка валидации формы (`bindingResult.hasErrors()`) при создании/редактировании — список уровней в модели пересчитывается так же, как при GET (не теряется, не возвращает нефильтрованный `Nivel.values()`).
- `SIN_ESPECIFICAR` как текущее значение турнира на практике невозможен (не входил в CHECK-constraint ни в одной прошлой миграции) — если гипотетически такая запись всё же существует в БД в обход constraint, `forTournamentForm` включает и её по тому же правилу "текущее значение всегда в списке", защитное поведение не требует отдельного теста.
