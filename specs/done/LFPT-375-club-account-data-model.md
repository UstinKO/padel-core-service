## Контекст / зачем
Проект переходит на модель клубных аккаунтов: у клуба Black Padel (и последующих клубов) должен появиться собственный админ-аккаунт, который управляет только своими турнирами, не видя чужие. Сейчас `Owner` никак не привязан к `Club` — все владельцы аккаунтов полностью глобальны, а `OwnerRole` не различает "клубного администратора" среди прочих ролей. Это первый шаг (чистая модель данных, без изменения поведения авторизации) — логика изоляции доступа реализуется отдельно в #376.

## Связь с MASTER.md
Добавляет новую роль в таблицу "Роли пользователей" `specs/MASTER.md` — `ROLE_CLUB_ADMIN` (клубный администратор, управляет только турнирами своего клуба). Существующие роли (`ROLE_OWNER`/`ROLE_SUPER_ADMIN`/`ROLE_ORGANIZER`) и их описание не меняются. Само ограничение видимости (что именно клубный админ видит/не видит) — предмет #376, здесь только заводится роль и связь данных; `MASTER.md` обновляется в этом PR, чтобы отразить факт существования новой роли (без описания ещё не реализованного поведения изоляции).

## Требования

### Функциональные
- `Owner` получает новое поле `clubId` (nullable `Long`), ссылку на `Club.id` — без `@ManyToOne`/FK-constraint на уровне БД (проект уже хранит `Tournament.clubId` как сырой `Long`, см. `CLAUDE.md` — следуем тому же, устоявшемуся в проекте паттерну, не вводим новый).
- `OwnerRole` получает новое значение `CLUB_ADMIN` — четвёртая роль, добавляется в конец enum (после `ADMIN`), существующие значения не переупорядочиваются (порядок enum влияет на `ORDINAL`, если где-то используется — в проекте маппинг через `EnumType.STRING` (`Owner.java:45`), поэтому порядок безопасен, но не переставляем на всякий случай).
- `OwnerRepository` получает `findByClubId(Long clubId)` — список клубных аккаунтов конкретного клуба (задел под #376/#377, само использование — не в этой спеке).
- Никакой другой код (`SecurityConfig`, контроллеры, проверки владения) не меняется — роль `CLUB_ADMIN` не даёт и не отнимает никаких прав в этом PR, это будет сделано в #376.

### Нефункциональные
- i18n: не требуется — новая роль пока нигде не отображается в UI (ни в форме создания владельца, если она есть, ни в списках) в рамках этой спеки.
- Безопасность: новых точек входа пользовательских данных нет — чисто модель + миграция.
- Обратная совместимость: миграция аддитивная (новая nullable-колонка + новое enum-значение), не переносит данные существующих строк, ничего не может сломать в проде до момента, пока кто-то не назначит `CLUB_ADMIN` роль реальному аккаунту.

## Вне скоупа
- Любая проверка авторизации/фильтрация по `clubId` — это #376.
- UI для назначения `clubId`/роли `CLUB_ADMIN` конкретному `Owner` (форма создания владельца, если такая есть, или ручной SQL) — не создаётся в этой спеке; назначение аккаунта Black Padel — предмет #377, может делаться напрямую в БД/существующими средствами.
- `Club` → `Owner` обратная связь (`@OneToMany` на стороне `Club`) — не нужна для #376 (там паттерн запроса "по `clubId`", не по объектному графу от клуба), не добавляем ради симметрии, которой никто не просил (YAGNI).

## Критерии приёмки
- [ ] `OwnerRole` содержит 4 значения: `SUPER_ADMIN, ORGANIZER, ADMIN, CLUB_ADMIN` (в этом порядке, `CLUB_ADMIN` — новое, последнее)
- [ ] `Owner` имеет поле `clubId` (тип `Long`, `nullable`, колонка `club_id`), геттер/сеттер через Lombok, без FK/`@ManyToOne`
- [ ] Миграция `v1.48-add-club-id-to-owner.yaml` существует, зарегистрирована в `changelog-master.yaml`, применяется на чистой БД (`./mvnw verify` поднимает контекст и накатывает Liquibase без ошибок)
- [ ] После миграции у всех существующих строк `owners_db` значение `club_id IS NULL` (backfill не выполняется)
- [ ] `OwnerRepository.findByClubId(Long clubId)` существует и возвращает корректный список (тест с 2 `Owner` разных клубов + 1 без клуба — запрос по конкретному `clubId` возвращает только его владельца)
- [ ] Логин существующим `Owner`-аккаунтом (`ORGANIZER`/`ADMIN`/`SUPER_ADMIN`, `club_id = NULL`) и доступ к `/admin` работают как раньше — не изменилось (ручная/интеграционная проверка, не только чтение кода)
- [ ] Создание `Owner` с ролью `CLUB_ADMIN` и произвольным `clubId` через `OwnerRepository.save(...)` — сохраняется и читается корректно (round-trip тест)
- [ ] `specs/MASTER.md`, раздел "Роли пользователей" — добавлена строка `ROLE_CLUB_ADMIN` с пометкой, что изоляция доступа реализуется в #376 (чтобы не описывать ещё не существующее поведение как готовое)

## Edge cases
- `Owner` с ролью `CLUB_ADMIN`, но `clubId = NULL` (некорректно созданный/переходный аккаунт) — модель это не запрещает (валидация на уровне модели данных не требуется по этой спеке, поле nullable); поведение такого аккаунта в авторизации — вопрос #376, здесь достаточно, что модель не падает.
- `Owner` с ролью, отличной от `CLUB_ADMIN` (например `ORGANIZER`), но с непустым `clubId` — тоже валидное с точки зрения модели данных состояние (не запрещаем на уровне БД/модели); согласно решению открытого вопроса №1 ниже, семантика "кто считается клубным" в #376 будет определяться ролью, а не наличием `clubId`, так что это поле здесь — просто данные, не флаг поведения.
- Существующие Liquibase-миграции с похожим паттерном (`v1.24-add-contact-fields-to-player.yaml`) в прошлом делали backfill + `NOT NULL` для добавленной роли-колонки — здесь сознательно **не** делаем backfill, потому что цель другая (новая колонка опциональна для всех текущих строк, а не обязательное поле, которое раньше не существовало).

## Открытые вопросы

Оба вопроса были явно поставлены в issue #375 с рекомендацией архитектора; архитектор подтвердил обе рекомендации сообщением в Telegram (`telegram_launch_message_id: 4323`) до старта этого конвейера — решения зафиксированы ниже, статус спеки `approved`.

1. **Новая роль или расширение существующей?** Решено: **отдельная роль `CLUB_ADMIN`**, поверх (в дополнение к) существующих ролей `OwnerRole` — не переиспользуем "любой `Owner` с непустым `clubId`" как признак клубности. Авторизация в #376 будет завязана на явную роль `CLUB_ADMIN`, а не на факт наличия `clubId`.
2. **Что происходит с существующими `ORGANIZER`/`ADMIN` без `clubId`?** Решено: они остаются полностью глобальными, как сейчас — самый безопасный дефолт, не меняющий текущее поведение. Клубное ограничение (#376) применяется только к аккаунтам с ролью `CLUB_ADMIN`.
