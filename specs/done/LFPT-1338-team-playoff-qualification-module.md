## Источник

[Issue #1338](https://github.com/UstinKO/padel-core-service/issues/1338), родитель #1041, предшественник #1332 / PR #1335. Техническая постановка напрямую из поручения продолжить переход после мержа; промежуточный клиентский запрос не нужен.

## Контекст / зачем

QualificationPairing и PlayoffFormat уже отделены от хранения и используют только JDK. Перенос их вместе с исходными тестами продолжает выделение вычислений Team Playoff в существующий engines, сохраняя алгоритм и самостоятельную работоспособность приложения.

## Связь с MASTER.md

Сохраняются формат Team Playoff, квалификация, посев, права и история проведения. Таблица 8–16 команд и обмен при нечётных группах остаются такими, как в исходном коде и принятых #247/#249/#251/#550. Бизнес-инварианты MASTER не меняются.

## Требования

### Функциональные

- Переместить QualificationPairing, PlayoffFormat и два одноимённых Test из корневого src в padel-tournament-engines. Все четыре файла сохраняются байтово, включая package, package-private доступ, record Pairing, порядок обхода/обмена, fallback и константы таблицы.
- TeamPlayoffService, EarlyPlayoffSeeding, сервисные тесты, сохранение/права/транзакции/история остаются в bootstrap. Новые bean, Spring-конфигурация и Maven-модули не создаются.
- Artifact guard требует шесть вычислительных классов и десять обязательных вложенных типов в одной библиотеке. Новый QualificationPairing.Pairing не объявляется публичным. Основные и любые вложенные shadow-классы в bootstrap запрещены; Java 17, без Spring/JPA.
- Сохранить адресный DevTools restart.include для библиотеки engines; доступ к package-private классам из bootstrap проверить на настоящем запуске и перезапуске, без расширения видимости Java API.

### Нефункциональные

Корневой clean verify с frontend выполняется на отдельной PostgreSQL. Итоговый jar проверяется в своём preview, включая прежний jar/возврат на той же синтетической БД. Производительность, Random, внешние контракты и пользовательские строки не меняются; новых переводов и миграций нет.

## Вне скоупа

Переписывание алгоритмов, оптимизация тестов #1324/#1325, перенос EarlyPlayoffSeeding, RoundRobinRules/Standings, массовый рефакторинг TeamPlayoffService, новые application/persistence/web/integrations-модули, физическая БД и Swarm. #1051 сохраняет поздний порядок.

## Изменения в системе

### API

HTTP/JSON/WS и Java API сохраняются, включая package-private доступ через уже существующий временный мост общего package/classloader.

### БД

Без изменений схемы, Liquibase и пользовательских данных. Только синтетические fixtures своего контура.

### UI

Production UI не меняется. Действующие экраны квалификации/плей-офф и история проверяются реальным браузером.

### Документация

.agents/PROJECT.md, docs/architecture.md, навигация/план модульного монолита и отдельный отчёт переноса с безопасной сводкой. Остаток вычислительных и application-срезов явно отделяется от выполненного.

## Критерии приёмки

- [x] Четыре файла совпадают с исходным master; 6 QualificationPairing и 11 PlayoffFormat тестов автономно исполняются в engines.
- [x] ArchUnit и положительные/отрицательные artifact-проверки подтверждают единственного владельца всех выделенных типов и Java 17 без framework.
- [x] Полный clean verify с frontend и отдельной PostgreSQL проходит; сервисные сценарии 8–16 команд и раннего плей-офф сохранены.
- [x] Конечный jar проходит существующие полный и расширенный браузерные сценарии Team Playoff, UI/историю, общий smoke и репетицию выпуска/отката.
- [x] Прежний jar и возврат сохраняют snapshots игровых данных, схему и checksums Liquibase.
- [x] Настоящий запуск с DevTools и перезапуск подтверждают package-private вызовы из bootstrap без IllegalAccessError.
- [x] Документация, автоматика, новые ссылки, приватность и локальное ревью пройдены; доказательства привязаны к jar, ограничения перечислены.

## Edge cases

8 и 16 команд; таблица для всех 8–16 и отказ для 7/17; квалификация 10/14 с нечётными группами, чётные группы, по одной команде, хвост только с одной стороны, пропуск небезопасной пары во избежание рематча. Сохранённый package разделён между библиотекой и bootstrap: одинаковый classloader обязателен, существующий DevTools-мост сохраняется. Старый jar должен читать те же данные после нового.

## Открытые вопросы

Нет. Изменение исключительно техническое, исходное поведение и согласованная архитектура сохраняются.
