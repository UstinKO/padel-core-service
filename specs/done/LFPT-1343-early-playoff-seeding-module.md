## Источник

[Issue #1343](https://github.com/UstinKO/padel-core-service/issues/1343), родитель #1041, предшественник #1338 / PR #1341. Техническая постановка напрямую из поручения продолжить переход после мержа; промежуточный клиентский запрос не нужен.

## Контекст / зачем

EarlyPlayoffSeeding уже содержит чистый расчёт ранних пар и зависит только от JDK, PlayoffMatchingEngine и PlayoffFormat. Последние два класса находятся в engines. Отдельный unit-набор сначала фиксирует существующее поведение в bootstrap, затем переезжает с неизменённым production-классом.

## Связь с MASTER.md

Сохраняются формат Team Playoff, квалификация, ранние подтверждённые пары, прямой проход, права и история. Бизнес-инварианты MASTER и реализованные #1152/#1153 не меняются; источником вычислительного поведения остаётся исходный код.

## Требования

### Функциональные

- До переноса добавить автономные тесты существующей реализации: допустимый счёт, projectedByes/исключение прямого прохода, fixed-пары, анти-рематч, устойчивые пары, раннюю остановку, manualBye, полный ручной перебор, сценарии ниже/выше лимита и неизменность входов.
- Выполнить этот набор в bootstrap на исходном production-классе. Затем переместить оба файла в padel-tournament-engines; production-файл и тест сохраняются байтово относительно проверенной до переноса версии.
- Не менять package-private доступ, четыре record, private Search, порядок обхода/кеш, SCENARIO_LIMIT=4096 и семантику exhaustive/limited/manualBye.
- TeamPlayoffService, TeamPlayoffReadService, PlayoffPairExchange и сервисные тесты остаются в bootstrap. Транзакции, история, права, HTTP/JSON/WS, новые bean и Maven-зависимости не меняются.
- Artifact guard требует семь вычислительных классов и пятнадцать обязательных вложенных типов, включая private Search. Запрет shadow, Spring/JPA и bytecode новее Java 17 сохраняется; ArchUnit не ослабляется.
- Существующий DevTools restart.include проверяется с прямыми package-private вызовами расчёта/перебора после старта и настоящего перезапуска, плюс отрицательный контроль без include в частной копии ресурсов.

### Нефункциональные

Корневой clean verify с frontend — на отдельной PostgreSQL. Итоговый jar — в собственном preview с полным/расширенным браузерным пилотом, общим smoke и репетицией выпуска/отката. Новых строк, переводов, миграций и внешних интеграций нет.

## Вне скоупа

Оптимизация перебора/кеша, изменение лимита и бизнес-правил, массовый рефакторинг сервисов, RoundRobinRules/Standings, новые application/persistence/web/integrations-модули, физическая БД и Swarm. #1051 остаётся поздним этапом.

## Изменения в системе

### API

Java API/видимость и внешние HTTP/JSON/WS сохраняются. Прежний общий package и DevTools-мост продолжают действовать.

### БД

Без изменений схемы/Liquibase и пользовательских данных. Только синтетические fixtures своего контура.

### UI

Production UI не меняется; существующие ранние стадии и история проверяются реальным браузером.

### Документация

.agents/PROJECT.md, docs/architecture.md, навигация/план модульного монолита, отдельный отчёт и безопасная сводка с хешами.

## Критерии приёмки

- [x] Тот же unit-файл проходит до переноса в bootstrap и затем автономно в engines; production-файл совпадает с исходным master байтово.
- [x] Проверки границ/jar проходят, включая отсутствие любого из пяти новых вложенных типов и shadow-копии.
- [x] Полный clean verify с frontend и отдельной PostgreSQL проходит; прежние сервисные сценарии ранних стадий и 8–16 команд сохранены.
- [x] Итоговый jar проходит полный/расширенный браузерный пилот, общий smoke и репетицию выпуска/отката.
- [x] Прежний jar и возврат сохраняют игровые snapshots, схему и журнал Liquibase.
- [x] DevTools restart подтверждает доступ к расчёту из bootstrap; без include получен ожидаемый IllegalAccessError.
- [x] Документация, автоматика, ссылки, приватность и локальное ревью пройдены; доказательства привязаны к исходникам/jar, ограничения отражены.

## Edge cases

6:0–6:5 в обе стороны; отрицательные, ничья и превышение лимита; 8–16 команд и границы прямого прохода; полное равенство показателей; уже назначенная немиррорная пара; прежний соперник; пустой eligible; отсутствие оставшихся встреч; ручная пара с возможным прямым проходом; 12³ и 12⁴ исходов относительно исходного лимита 4096. На остановке по лимиту устойчивые рекомендации не выдаются. Входные коллекции не меняются. Семантика флагов проверяется по исходной реализации, новое бизнес-правило из тестов не выводится.

## Открытые вопросы

Нет. Изменение техническое и сохраняет принятое поведение.
