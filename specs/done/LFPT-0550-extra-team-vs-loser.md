# LFPT-0550: Feature рекомендация соперника дополнительной команде в квалификации Team Playoff при нечётном числе команд — играть с проигравшим, не с победителем

Telegram-сообщение (для reply): 5016

## Контекст / зачем

Формат Team Playoff (`TeamPlayoffService`, `TournamentType.AMERICANO_TEAMS` с двумя квалификационными раундами и плей-офф) — при нечётном числе команд (9, 11, 13, 15, 17...) одна команда ("дополнительная", `extraTeam`) не попадает в пары 1-го тура и ждёт своего первого матча.

Сейчас, как только завершается первый матч какой-либо пары, система рекомендует координатору поставить дополнительную команду против **победителя** этого матча. Заказчик (архитектор проекта) хочет изменить это на **проигравшего**: для проигравшего это будет уже 2-й квалификационный матч, для дополнительной команды — 1-й. Мотивация: проигравший первого матча с большей вероятностью попадёт в раннюю стадию плей-офф (1/16, 1/8 и т.д.) и выигрывает от того, что получит свой 2-й квалификационный матч раньше; победитель же (с больше шансами пройти в плей-офф напрямую) не должен терять скорость из-за ожидания партнёра для дополнительной команды.

Не затрагивает отдельный формат Round Robin / Team Americano (`TeamAmericanoService`, "Todos contra todos") — там фиксированные пары играют каждая с каждой, механики "дополнительной команды" там нет.

## Связь с MASTER.md

Не меняет инвариантов `specs/MASTER.md` (там Team Playoff описан на уровне формата, без детализации алгоритма парования квалификации). Технический алгоритм рекомендаций живёт только в `TeamPlayoffService`/`QualificationPairing` и соответствующих комментариях-ТЗ в коде.

## Требования

### Функциональные

- В `TeamPlayoffService.suggestSecondRoundOpponent(tournamentId, teamId)`: когда дополнительная команда (`extraTeam`) есть и присутствует ровно одна, предложение подставить её как соперника должно выдаваться для команды, которая **проиграла** свой первый квалификационный матч (а не выиграла), при условии что сама команда `teamId` ожидает 2-го матча (как и сейчас).
- Для победителя первого завершившегося матча (в той же ситуации — дополнительная команда есть) `suggestSecondRoundOpponent` должен вести себя так, как если бы дополнительной команды не было: обычная логика "победитель к победителю" через `QualificationPairing.pairSecondRound` (с учётом текущих `winners`/`losers`-пулов).
- В `TeamPlayoffService.suggestSecondRoundPairings(tournamentId)`: приоритетная пара "дополнительная команда + команда, ожидающая 2-го матча" должна строиться на основе **первого проигравшего** среди команд в `waiting` (`teamsAwaitingSecondQualMatch`), а не первого победителя. Остальной механизм метода (приоритет команд без единого матча, `used`-исключение, порядок `QualificationPairing` для оставшихся) не меняется.
- Обновить javadoc/комментарии у обоих методов и у `AmericanoMatchSuggestionDto.priority` (сейчас: "матч победитель — дополнительная команда") — заменить на описание нового правила ("проигравший — дополнительная команда").

### Нефункциональные

- i18n: новых пользовательских строк нет (поведение чисто алгоритмическое, UI не меняется).
- Безопасность: новых точек входа данных от пользователя нет.

## Вне скоупа

- Формат Round Robin / Team Americano (`TeamAmericanoService`) — не затрагивается, в задаче явно указано "не относится".
- Логика 2-го тура квалификации при чётном остатке команд (`QualificationPairing`, победитель-к-победителю/проигравший-к-проигравшему) — не меняется, только момент подстановки дополнительной команды.
- UI/шаблоны координатора (`tournament-playoff.html`) — рендерят то, что вернул сервис; изменений верстки не требуется.

## Изменения в системе

### API
Без изменений сигнатур. Поведенчески меняется результат (кого рекомендует) двух существующих методов `TeamPlayoffService.suggestSecondRoundOpponent` и `suggestSecondRoundPairings`, используемых эндпоинтами админки Team Playoff (через контроллер `TeamPlayoffViewController` / админ-страницу квалификации).

### БД
Нет изменений схемы.

### UI
Нет изменений шаблонов — координатор видит ту же форму предложения пары, но с другой рекомендованной командой.

## Критерии приёмки

- [ ] При нечётном числе команд, после завершения первого матча какой-либо пары, `suggestSecondRoundOpponent(tournamentId, loserTeamId)` возвращает дополнительную команду как рекомендованного соперника.
- [ ] `suggestSecondRoundOpponent(tournamentId, winnerTeamId)` в той же ситуации **не** возвращает дополнительную команду — рекомендация идёт по обычному правилу "победитель к победителю" (или пусто, если партнёра пока нет).
- [ ] `suggestSecondRoundPairings(tournamentId)` в списке предложений ставит в пару с дополнительной командой именно первого (по порядку в `waiting`) проигравшего, а не победителя; `priority = true` на этой паре сохраняется.
- [ ] Поведение при чётном числе команд (без `extraTeam`) не изменилось.
- [ ] Структурные гарантии квалификации сохранены: сквозной прогон (9, 11 и 13 команд) — каждая команда играет ровно 2 квалификационных матча, без зацикливания.
- [ ] Новый/дополненный unit-тест на `TeamPlayoffService` (или отдельный модульный тест на пару методов, по аналогии с `QualificationPairingTest`) явно проверяет: проигравший первого матча получает дополнительную команду, победитель — нет.

## Edge cases

- Дополнительных команд 0 (чётное число участников) — поведение не меняется, веткa с `extraTeam` не активируется (как и раньше).
- Дополнительных команд ≥2 (несколько команд ещё не начали ни одного матча) — правило подстановки `extraTeam` не применяется вовсе, как и в текущей реализации (`extraTeam()` возвращает `Optional.empty()`, если "нетронутых" команд больше одной) — не меняется этой задачей.
- Первый завершившийся матч оказался ничьёй невозможен в этом формате (Americano-пара всегда имеет победителя/проигравшего по очкам) — `wonFirstQualMatch` основан на существующей бизнес-логике определения победителя, не пересматривается.
- Несколько матчей 1-го тура завершаются почти одновременно — `suggestSecondRoundPairings` вызывается заново на актуальном состоянии БД при каждом запросе координатора, порядок проигравших берётся из `teamsAwaitingSecondQualMatch` (как и раньше для победителей) — поведение по порядку выбора первого элемента списка идентично прежнему, меняется только фильтр (проигравший вместо победителя).
