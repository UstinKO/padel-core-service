# LFPT-0607: Fix доверенные IP rate limit — только из конфигурации окружения, без значений по умолчанию в коде

## Статус
done

## Источник
[Issue #607](https://github.com/UstinKO/padel-core-service/issues/607), найдено при аудите документации (#602).

## Контекст / зачем
`RateLimitFilter.whitelistedIpsProperty` (`src/main/java/com/padle/core/padelcoreservice/security/RateLimitFilter.java:66`) объявлен как `@Value("${app.security.whitelisted-ips:194.124.210.113,152.171.139.176,167.235.34.217}")` — три реальных IP прода захардкожены как default-значение прямо в публичном исходнике. Это утечка инфраструктурной информации (какие IP имеют безлимитный доступ к API, минуя rate limiting) в публичный репозиторий. Нужно убрать дефолт из кода и держать список только в переменной окружения прод-сервера.

## Связь с MASTER.md
Не затрагивает бизнес-логику продукта — чисто инфраструктурная/security правка. `specs/MASTER.md` не меняется.

## Требования

### Функциональные
- `app.security.whitelisted-ips` без значения по умолчанию в коде — если переменная окружения `APP_SECURITY_WHITELISTED_IPS` не задана, список доверенных IP пуст (rate limiting применяется ко всем IP как к обычным).
- `docker-compose.yml` (сервис `padel-app`) явно пробрасывает `APP_SECURITY_WHITELISTED_IPS` из окружения хоста — для согласованности с остальными переменными в этом файле (сам серверный docker-compose.yml не в репозитории, см. комментарий архитектора в issue, но локальный/репозиторный файл должен быть согласован с остальными секциями `environment`).

### Нефункциональные
- Безопасность: устраняется утечка реальных IP прод-инфраструктуры в публичный Git-репозиторий.
- i18n: не применимо, строк пользовательского интерфейса нет.
- На проде поведение не меняется — переменная `APP_SECURITY_WHITELISTED_IPS` уже задана в окружении прод-сервера заранее (подтверждено комментарием архитектора в issue от 2026-10-16), значения совпадают с текущим хардкодом.

## Вне скоупа
- Сама установка/проверка переменной на сервере — уже сделана отдельно (см. комментарий в issue), в этот PR не входит.
- Любые изменения `nginx`/`CrowdSec` whitelist — вне скоупа, их синхронизация с `app.security.whitelisted-ips` остаётся ручной (как и раньше, см. комментарий в `RateLimitFilter`).

### Конфигурация
- `RateLimitFilter.java`: `@Value("${app.security.whitelisted-ips:}")` — пустая строка по умолчанию вместо списка IP.
- `docker-compose.yml`, сервис `padel-app`, секция `environment`, блок "Приложение": добавить `APP_SECURITY_WHITELISTED_IPS: ${APP_SECURITY_WHITELISTED_IPS:-}`.

## Критерии приёмки
- [ ] В `RateLimitFilter.java` нет конкретных IP-адресов — `@Value` без хардкод-дефолта.
- [ ] Без заданной переменной окружения `whitelistedIps` — пустой `Set` (не падает с исключением при `@PostConstruct`, пустая строка корректно парсится в пустой список благодаря существующему `.filter(ip -> !ip.isEmpty())`).
- [ ] С заданной переменной окружения (`APP_SECURITY_WHITELISTED_IPS=1.2.3.4,5.6.7.8`) — `whitelistedIps` содержит ровно эти IP, поведение фильтра (полный пропуск rate limiting для них) не изменилось относительно текущей реализации.
- [ ] `docker-compose.yml` пробрасывает `APP_SECURITY_WHITELISTED_IPS` в контейнер `padel-app`.
- [ ] `grep -rn "194.124.210.113\|152.171.139.176\|167.235.34.217"` по `src/` и `docker-compose.yml` — ничего не находит.

## Edge cases
- Переменная задана, но с пустой строкой (`APP_SECURITY_WHITELISTED_IPS=`) — тот же эффект, что и без переменной: пустой список (уже покрыто существующим `.filter(ip -> !ip.isEmpty())`).
- Переменная с лишними пробелами вокруг запятых (`" 1.2.3.4 , 5.6.7.8 "`) — уже обрабатывается существующим `.map(String::trim)`.
- Прод: поведение не меняется в момент деплоя, так как переменная уже задана в окружении сервера со старыми значениями (см. источник).
