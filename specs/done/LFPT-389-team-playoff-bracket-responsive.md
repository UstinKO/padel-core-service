## Контекст / зачем

Единственная в проекте визуальная древовидная турнирная сетка (`.bracket`/`.bracket-col`, публичная страница `GET /tournaments/team-playoff/{tournamentId}`) верстается server-side flexbox-колонками фиксированной ширины (250px) с `overflow-x:auto`. При достаточном числе команд (от 1/8 финала и выше) сетка становится шире экрана: на десктопе — горизонтальный скролл, на мобильном — то же самое, но менее удобно (объект интереса — этапы 1/16 → финал видны целиком только через долгую прокрутку). Клиент прислал скриншот именно этой проблемы (широкая сетка, часть корт-карточек обрезана по правому краю экрана).

Дополнительно клиент хочет кнопку «Скачать сетку» — готовое PNG-изображение всей сетки целиком (с шапкой турнира и логотипом), которое можно сразу постить в Instagram/Stories/WhatsApp, не собирая скриншоты вручную.

Это чисто фронтенд-доработка одной страницы — не меняет бизнес-логику построения сетки (`TeamPlayoffService`) и не требует нового backend-DTO (все нужные для шапки экспорта поля — `nombre`, `clubNombre`, `fechaInicio`, `generoFormato`, `categoriaNivel` — уже приходят в `${tournament}`, часть просто ещё не отрисована на странице).

## Связь с MASTER.md
Не затрагивает ни один инвариант `MASTER.md` (форматы турниров, статусы регистрации, роли) — Team Playoff как формат и структура его сетки (§ "Форматы турниров") не меняются, только отображение уже существующих данных. Обновлений `MASTER.md` не требуется.

## Требования

### Функциональные

**Скоуп: только `templates/tournaments/team-playoff/view.html`, блок `th:if="${playoffStarted}"` (`.bracket`).** Ни один другой bracket-подобный экран (`admin/americano/tournament-playoff.html` — вертикальный список для организатора, не грид; `admin/tournaments/matches.html` — отдельный grid-of-cards для формата `BracketService`, публично нигде не рендерится) не трогаем — см. "Вне скоупа".

1. **Десктоп-автомасштабирование** (ширина viewport ≥ 769px, тот же брейкпоинт, что уже используется в файле для таблицы рейтинга):
   - При открытии страницы и при `resize`/повороте экрана вычисляется `fitScale = min(1, доступная_ширина_контейнера / естественная_ширина_сетки)`.
   - У масштаба снизу есть **порог читаемости** (`MIN_DESKTOP_SCALE`, ориентировочно 0.75 — ниже уже не сжимаем самый мелкий текст карточки, `.team-sub` 12px, ощутимо ниже ~9px): если `fitScale < MIN_DESKTOP_SCALE`, применяется `MIN_DESKTOP_SCALE`, а не дальнейшее сжатие, и остаётся возможность прокрутки/pan вправо для той части сетки, что не поместилась.
   - `fitScale` никогда не применяется выше 1 (сетку не увеличиваем сверх исходного размера автоматически).
   - Если пользователь вручную поменял масштаб кнопками — очередной `resize` не должен молча сбрасывать его в fit-масштаб (см. Edge cases).
2. **Мобильный режим** (viewport ≤ 768px):
   - При открытии сетка вписывается в экран целиком («показать всю сетку») — здесь **порога читаемости нет**: масштаб может быть меньше `MIN_DESKTOP_SCALE`, это ожидаемо (пользователь дальше сам приближает нужный матч).
   - Поддерживается pinch (двумя пальцами) для увеличения/уменьшения масштаба относительно точки между пальцами и pan (перемещение одним пальцем) в обе стороны (X и Y).
   - Нативный жест масштабирования страницы браузером (double-tap zoom, browser pinch) на блоке сетки должен быть отключен (`touch-action`), чтобы не конфликтовать с собственной обработкой жестов.
3. **Кнопки управления масштабом** — над `.bracket`, видны и на десктопе, и на мобильном/планшете: `−` (шаг уменьшения), `100%` (сброс к истинному масштабу 1:1, не к fit-масштабу), `+` (шаг увеличения), и отдельная кнопка **«Вместить в экран»** (пересчитывает и применяет текущий `fitScale`, как при первом открытии). Ручной масштаб через кнопки может выходить за пределы `MIN_DESKTOP_SCALE` в обе стороны (нижнюю/верхнюю абсолютную границу — например [0.25, 2.0] — выбирает разработчик, лишь бы не ломался layout).
4. **Кнопка «Скачать сетку»** — рядом с кнопками масштаба:
   - Генерирует PNG (через `SnapDOM`, CDN `https://cdn.jsdelivr.net/npm/@zumer/snapdom/dist/snapdom.min.js` — см. рекомендацию в комментарии к issue #389, тот же паттерн подключения через CDN, что уже используется для `sockjs-client`/`stompjs` в этом же файле) со **всей сеткой целиком**, в естественном (не текущем экранном) масштабе и без обрезки текущим scroll/pan/viewport.
   - На изображении, помимо самой сетки (все стадии, все карточки матчей с результатами как есть), должна быть шапка с: названием турнира (`tournament.nombre`), категорией (`tournament.categoriaNivel`) и форматом пола (`tournament.generoFormato`) — как в существующем `.tournament-banner`, плюс дата (`tournament.fechaInicio`) и клуб (`tournament.clubNombre`) — оба поля уже есть в `${tournament}`, но пока нигде на этой странице не выводятся, и логотипом 1Padel (`/images/1.svg`).
   - Скачивание — обычный файловый download (`<a download>`), имя файла — по турниру (например `bracket-team-playoff-{tournamentId}.png`).
   - Логика раундов/матчей (`TeamPlayoffService`, `playoffRounds`) не меняется — это чисто фронтенд-надстройка над уже существующей разметкой.
5. **i18n**: новые пользовательские строки — минимум подпись кнопки «Скачать сетку» (`team_playoff.bracket.download`) и «Вместить в экран» (`team_playoff.bracket.fit_screen`) — во все три файла (`messages_es/ru/en.properties`). Кнопки `−`/`100%`/`+` — символьные, без текста (как в клиентском ТЗ), но по возможности с `aria-label`/`title` через те же ключи i18n (`team_playoff.bracket.zoom_out`/`zoom_in`/`zoom_reset`) — на усмотрение разработчика, не блокирующий критерий.

### Нефункциональные
- Никаких новых серверных endpoint'ов, DTO или Liquibase-миграций — фича полностью клиентская (JS/CSS/минимальная правка Thymeleaf-разметки одного файла).
- Новых точек входа пользовательских данных нет (нет новой формы/параметра) — секция "Безопасность" неприменима сверх уже существующей защиты страницы.
- Realtime: существующий механизм (`team-playoff-realtime.js` → событие `team-playoff-update` → `window.location.reload()` через 1.5с) должен продолжать работать без ошибок в консоли после добавления нового JS-модуля.
- Новый статический JS-файл — `static/js/bracket-zoom-export.js`, по аналогии с уже существующим `team-playoff-realtime.js` (тот же паттерн: отдельный файл, подключается только в этом шаблоне).

## Вне скоупа
- Формат «Одиночный/парный bracket» (`BracketService`/`Match`) — публично нигде не рендерится, отдельная задача, если понадобится.
- Админ-страница `admin/americano/tournament-playoff.html` — вертикальный список для организатора, не бракет-грид; масштабирование/экспорт туда не переносим.
- Изменение самой логики построения сетки/раундов (`TeamPlayoffService`) — явное требование клиента "не менять".
- Полноценная бесконечная свобода зума (например произвольный zoom-to-cursor колесом мыши на десктопе) — не запрошено, только кнопки.
- Кэширование/предгенерация PNG на сервере — экспорт полностью на клиенте, по требованию.

## Критерии приёмки
- [ ] Десктоп (≥1280px), сетка на 16+ команд (5 стадий: 1/16→1/8→1/4→1/2→финал): при первой загрузке страницы вся сетка видна без горизонтального скролла (масштаб автоматически уменьшен, но не ниже порога читаемости); если даже минимальный читаемый масштаб не позволяет вместить — сетка остаётся частично прокручиваемой/pan-able.
- [ ] Десктоп, маленькая сетка (например только финал, 1 стадия): сетка не увеличивается автоматически выше 100%.
- [ ] Мобильная эмуляция (≤480px): при первой загрузке видна вся сетка целиком (даже мельче порога читаемости, свойственного десктопу); pinch двумя синтетическими touch-точками меняет масштаб; одно touch-перемещение двигает сетку (pan) по X и Y.
- [ ] Кнопки `−`/`100%`/`+`/«Вместить в экран» видны и кликабельны на десктопе и в мобильной эмуляции; каждая клик-операция видимо меняет применённый масштаб (проверяется через computed `transform`/CSS-переменную состояния).
- [ ] После клика «Скачать сетку» браузер инициирует скачивание PNG-файла; в файле присутствуют: название турнира, категория, дата, клуб, логотип 1Padel и **все** стадии/матчи сетки целиком (не только видимая на экране в момент клика часть).
- [ ] Изменение масштаба/зума никак не меняет данные `playoffRounds`/расположение матчей — `TeamPlayoffService` не тронут, существующие юнит/интеграционные тесты по Team Playoff (если есть) по-прежнему проходят.
- [ ] После срабатывания realtime-обновления (WebSocket → reload) страница остаётся рабочей, в консоли браузера нет новых JS-ошибок, связанных с добавленным кодом.
- [ ] Новые пользовательские строки присутствуют во всех трёх файлах локализации (`es`/`ru`/`en`).

## Edge cases
- **Resize после ручного зума**: если пользователь явно менял масштаб кнопками, последующий `resize`/поворот экрана не должен молча откатывать его к fit-масштабу — только "Вместить в экран" делает это осознанно. Разумно скорректировать позицию pan, чтобы сетка не улетала за пределы видимой области, не трогая сам выбранный масштаб.
- **playoffStarted = false**: секция плей-офф (и вся новая UI сверху неё) не рендерится вообще — как и сейчас (`th:if="${playoffStarted}"`), новых условий не добавляем.
- **Очень узкий экран (<320px)**: минимальный масштаб на мобильном не ограничен снизу явным порогом — сетка просто становится очень мелкой, это ожидаемо (клиент подтверждает pinch как способ приблизить).
- **iOS Safari**: учитывать нативное поведение double-tap-to-zoom и pull-to-refresh, конфликтующие с pan/pinch на этой секции — ограничить через `touch-action`/`preventDefault` только в пределах блока сетки, не на всей странице.
- **Данные турнира без части полей** (например `clubNombre`/`fechaInicio` не заполнены у старого турнира) — шапка экспорта не должна падать/показывать `null`, только пропускать отсутствующее поле.
- **Конкурентный доступ / несколько реплик**: неприменимо — фича не трогает сервер, состояние не хранится (это read-only отображение уже переданных в шаблон данных).
- **Существующие турниры**: применяется сразу, без бэкфилла/миграции.

## Открытые вопросы
Нет открытых бизнес-вопросов — задача полностью технически специфицирована клиентом и уточнена в issue #389 (включая рекомендацию библиотеки для экспорта). Технические решения ниже приняты архитектором самостоятельно (см. GIT_WORKFLOW.md §3):
- **SnapDOM, а не html2canvas** — по рекомендации из комментария к issue #389; современнее, быстрее, без явных недостатков для этой задачи.
- **Ручные touch-обработчики pinch/pan вместо подключения ещё одной библиотеки** (Hammer.js/panzoom) — единственная нужная функциональность узкая (pinch relative to midpoint + одно-пальцевый pan), не требует полноценной жестовой библиотеки; меньше зависимостей соответствует KISS/YAGNI.
- **Единый JS-модуль масштаба/pan** (`bracket-zoom-export.js`) управляет и кнопками, и touch-жестами через общее применение transform — не два параллельных механизма.
