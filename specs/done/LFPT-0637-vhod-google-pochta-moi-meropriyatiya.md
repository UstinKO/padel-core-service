## Контекст / зачем

Заказчик готовит отдельный клиент «1Padel.App» (вне этого репозитория) и хочет, чтобы он ходил в реальный бэкенд padel-core-service: логинился по email/паролю или через Google и показывал игроку список его турниров. Эта задача — только серверная часть; сам клиент (размещение готового веб-билда на `/app/`) — отдельная, следующая задача (см. «Вне скоупа»), потому что исходники клиента физически недоступны конвейеру (пришли только как описание в тексте Telegram-сообщения, не как файл, см. запрос).

Важно: `backend.patch`/исходники мобильного приложения из присланного заказчиком архива **не используются** ни частично, ни как референс кода — только как словесное описание желаемого контракта API. Вся реализация ниже написана заново по образцу уже существующего кода проекта.

## Связь с MASTER.md

Затрагивает [«Статусы регистрации на турнир»](../MASTER.md#статусы-регистрации-на-турнир) только на чтение (новый API не меняет инварианты статусов, только отдаёт их). Роли и форматы турниров (`specs/MASTER.md` § «Роли пользователей», «Форматы турниров») не меняются.

## Требования

### Функциональные

1. **Вход по email/паролю для клиента.** Уже реализован (`POST /api/auth/login`, `docs/endpoints/auth.md`) и ничего не меняет — используется как есть. Фиксируем это явно, чтобы Developer не реализовывал второй раз.
2. **Вход через Google для клиента.** Существующий веб-флоу Google OAuth2 (`/oauth2/authorization/google` → `CustomOAuth2UserService` → `OAuth2AuthenticationSuccessHandler`) должен уметь завершаться возвратом в клиентское приложение (`/app/`) с токенами вместо редиректа на `/players/dashboard`, **когда и только когда** вход был инициирован из `/app/`. Признак «вход из приложения» передаётся явным параметром на самом же эндпоинте инициации (`GET /oauth2/authorization/google?client=app`), а не через пользовательский `redirect_uri`/произвольный URL — так результирующий редирект-таргет всегда фиксирован (`/app/`), без риска open redirect.
   - Токены (access + refresh, как из `/api/auth/login`) передаются клиенту через fragment URL (`/app/#accessToken=...&refreshToken=...&expiresIn=...`), а не через query-параметр — fragment не уходит на сервер и не попадает в access-логи/`Referer`.
   - Обычный (не `?client=app`) вход через Google на сайте не меняется — редирект на `/players/dashboard`/`/admin` как сейчас.
3. **«Мои мероприятия» (read-only).** Новый эндпоинт для игрока (JWT или сессия — тот же `Authentication`, что и везде в `/api/**`), отдающий:
   - предстоящие турниры, на которые игрок зарегистрирован (турнир в статусе `PUBLICADO`/`REGISTRO_ABIERTO`), со статусом регистрации и позицией в листе ожидания;
   - историю — турниры в статусе `CERRADO`/`FINALIZADO`/`CANCELADO`, на которые игрок был зарегистрирован.
   - Источник данных — тот же запрос, что уже используется дашбордом игрока (`TournamentRegistrationRepository.findActiveRegistrationsByPlayerId`, см. `TournamentService.getHistoricalAndActiveTournamentsByPlayer`) — то же разбиение по `TournamentStatus`, без новой бизнес-логики статусов.
   - Запись/отмена регистрации через этот API — не нужны (есть `POST /players/tournaments/{id}/register|cancel|cancel-double`, ими же продолжает пользоваться сайт; не в скоупе этой задачи).

### Нефункциональные

- **Безопасность**: новая точка входа — только для аутентифицированного игрока (`PlayerPadel`); при принципале-`Owner` — 403 (как в `PlayerDashboardController.extractPlayerFromPrincipal`, но без скрытого `null` — см. Edge cases). Признак `?client=app` не позволяет подменить итоговый редирект (хардкод `/app/`, никакого request-controlled URL) — исключает open redirect. Токены никогда не логируются (fragment, не query/path).
- **i18n**: эндпоинт — чистый JSON для внешнего клиента (не Thymeleaf), без пользовательских строк на странице — тексты ошибок, как и в `AuthController`/остальном `/api/**`, на испанском (единственном языке пользовательских сообщений API в проекте сейчас).
- **Производительность**: не отличается от уже существующего `getHistoricalAndActiveTournamentsByPlayer` — один запрос регистраций игрока, без постраничной разбивки (у игрока разумное число турниров).
- **БД**: миграция не нужна — ни новой таблицы, ни новых колонок (вопреки тому, что мог подразумевать присланный архив — его описание не используется, см. «Контекст»).

## Вне скоупа

- Само клиентское приложение (React Native/Expo исходники, сборка, публикация в App Store/Google Play) — не в этом репозитории и не в этой задаче.
- Размещение готового веб-билда клиента на `/app/` по HTTPS — отдельная, следующая задача; заблокирована до тех пор, пока заказчик не передаст сам билд/исходники через канал, который конвейер реально может прочитать (ветка/PR в этом репозитории, или прямая ссылка на скачивание — не текстовое описание в Telegram). См. отдельную issue.
- Запись на турнир и отмена регистрации через API клиента — остаются только через сайт.
- Любые изменения пароля/учётных данных существующих аккаунтов.
- Авторизация админов (`Owner`) через этот клиент — не требуется, только игроки.

## Изменения в системе

### API

- `GET /oauth2/authorization/google?client=app` — существующий Spring Security эндпоинт, новый необязательный параметр `client=app`, меняющий только пост-логин редирект (см. выше). Без параметра — поведение не меняется.
- `GET /api/players/me/tournaments` — новый, аутентифицированный (`ROLE_PLAYER`), отдаёт `{ "upcoming": [...], "historical": [...] }`.

### БД

Миграция не нужна.

### UI

Нет изменений в Thymeleaf-шаблонах — задача целиком серверная.

## Критерии приёмки

- [ ] `POST /api/auth/login` работает без изменений (регрессионная проверка) — игрок логинится и получает `accessToken`/`refreshToken`.
- [ ] `GET /oauth2/authorization/google` (без `client=app`) после успешного входа через Google редиректит на `/players/dashboard` (или `/admin` для админа) — как сейчас.
- [ ] `GET /oauth2/authorization/google?client=app` после успешного входа через Google редиректит на `/app/#accessToken=...&refreshToken=...&expiresIn=...` (без обращения к `/players/dashboard`), сессия/remember-me по-прежнему выставляются (для единообразия с обычным веб-входом).
- [ ] `GET /api/players/me/tournaments` для аутентифицированного игрока с предстоящей регистрацией (`REGISTRO_ABIERTO`) возвращает её в `upcoming` с верным `status`/`waitlistPosition`.
- [ ] Регистрация на турнир в статусе `FINALIZADO`/`CERRADO`/`CANCELADO` попадает в `historical`, а не в `upcoming`.
- [ ] Игрок без регистраций получает `{ "upcoming": [], "historical": [] }`, а не ошибку.
- [ ] Запрос `GET /api/players/me/tournaments` от `Owner` (админ/организатор) — `403`, не 500 и не пустой список чужого игрока.
- [ ] Неаутентифицированный запрос — `401`/редирект на форму логина (как остальной `/api/**` сейчас).
- [ ] `./mvnw compile -DskipTests` и `./mvnw verify` — зелёные.
- [ ] `docs/auth-flow.md` (§6 Google OAuth2) и `docs/endpoints/auth.md` обновлены под новый параметр `client=app`; `.agents/PROJECT.md` REST API таблица — новая строка `GET /api/players/me/tournaments`.
- [ ] `python3 .github/bin/docs-drift.py` — 0 расхождений.

## Edge cases

- `client=app` без успешного логина (пользователь отменил согласие в Google) — текущий `failureUrl("/login?error=oauth2")` не меняется (ошибка всё равно обрабатывается на сайте, не в приложении — приемлемо для первой версии, сложные сценарии ошибок на стороне клиента — вне скоупа).
- Игрок, зарегистрированный и затем отменивший регистрацию (`CANCELLED`) — не должен попадать ни в `upcoming`, ни в `historical` (как и в существующем дашборде — `findActiveRegistrationsByPlayerId` уже исключает отменённые).
- Парная регистрация (игрок — `partnerId` в чужой записи, не `playerId`) — учитывается только по записям, где сам игрок — `playerId` (как и в текущем дашборде), партнёрская сторона не дублируется.
- Два одновременных запроса `GET /api/players/me/tournaments` (несколько реплик за Docker Swarm) — read-only, без побочных эффектов, конкурентность не требует отдельной обработки.
