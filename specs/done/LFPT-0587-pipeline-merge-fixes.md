# LFPT-0587: Оркестратор автомержа — verify пропускался, PR с только что поставленной меткой не находился

## Статус
done

## Источник
[GitHub issue #587](https://github.com/UstinKO/padel-core-service/issues/587). Найдено при живой проверке LFPT-0579 (PR #583) на PR #584.

## Контекст / зачем
После мержа #583 оркестратор не смог влить первый настоящий PR: job `verify` всегда пропускался (его предок `deploy-result` на обычных событиях `skipped`, а GitHub по умолчанию пропускает потомков пропущенной джобы), `merge` воспринимал это как упавшую проверку и ставил ложный `pipeline:conflict`. Отдельно прогон по событию `labeled` не видел PR с только что поставленной меткой — фильтр `gh pr list --label` отдаёт данные с задержкой индекса.

## Связь с MASTER.md
Не затрагивает.

## Требования

### Функциональные
1. `verify` и `merge` — явное условие `!cancelled() && needs.select.result == 'success'` плюс прежние.
2. Кандидаты — все открытые PR в `master`, фильтр меток `pipeline` и `pipeline:ready` (и исключение `pipeline:conflict` / `pipeline:deploy-failed`) в `jq`.
3. `«${title}»` вместо `«$title»` (граница имени переменной перед многобайтовым символом).

## Вне скоупа
Остальная логика LFPT-0579 без изменений.

## Изменения в системе
`.github/workflows/pipeline-merge.yml`, `.github/bin/pipeline-select.sh`.

## Критерии приёмки
- [ ] PR с `pipeline` + `pipeline:ready` и зелёным `build` проходит `verify` и вливается (проверка — PR #584 после мержа фикса).
- [ ] Прогон по событию `labeled` находит PR, на который только что поставили метку.

## Edge cases
- Упавший `deploy-result` (сбой деплоя): `select` всё равно идёт (`!cancelled()`), но halt-issue остановит выбор.
