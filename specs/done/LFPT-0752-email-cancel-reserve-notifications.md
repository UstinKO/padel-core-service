# LFPT-0752: Email-уведомления при отмене регистрации и переводе в резерв

## Статус
done

## Источник
GitHub issue [#752](https://github.com/UstinKO/padel-core-service/issues/752) — технический вход от архитектора (Telegram, роль `architect`), напрямую, без `specs/requests/`.

Telegram-сообщение (для reply): 5669

## Контекст / зачем

Статус регистрации игрока на турнир может измениться по многим причинам: сам игрок отменил участие, администратор/организатор перевёл его в резерв или отменил регистрацию, система автоматически подтвердила его из листа ожидания. Сегодня игрок узнаёт об изменении своего статуса только если сам зайдёт на сайт — часть этих переходов (самостоятельная отмена, отмена администратором, перевод в резерв администратором) вообще не отправляет никакого письма. Это путает игроков: человек может не знать, что он больше не в основном составе, или что его отмена действительно прошла.

## Связь с MASTER.md

Затрагивает раздел [specs/MASTER.md § Статусы регистрации на турнир](../MASTER.md#статусы-регистрации-на-турнир) — сама машина состояний не меняется, фича добавляет уведомления к уже существующим переходам `* → CANCELLED` и `CONFIRMED → WAITLIST` (и, как улучшение, `WAITLIST → CONFIRMED` там, где сегодня уведомления нет). Новых статусов, новых инвариантов не вводится — `MASTER.md` не меняется.

## Требования

### Функциональные

**Сценарий 1 — отмена регистрации (статус → `CANCELLED`).** Отправить письмо участнику с подтверждением отмены: название/тип турнира, дата, время, клуб, причина отмены (если она есть в `TournamentRegistration.cancellationReason`). Затрагиваемые точки изменения статуса (все существующие методы, которые реально переводят активную регистрацию в `CANCELLED`):

1. `TournamentService.cancelRegistration()` — самостоятельная отмена игроком (одиночная регистрация либо свой ряд парной, опция `self` в `cancel-double`).
2. `TournamentService.cancelPairRegistration()` — самостоятельная отмена всей пары игроком (опция `full` в `cancel-double`). Письмо уходит **обоим** игрокам пары — читать данные (email, имя, локаль) обоих до удаления их регистрационных записей (метод физически удаляет строки, не просто помечает `CANCELLED`).
3. `AmericanoService.cancelRegistration()` — администратор/организатор отменяет регистрацию игрока в Americano-турнире. Письмо с причиной отмены, если она передана (`reason` уже есть как параметр формы в `AmericanoViewController`).
4. `DoubleTournamentRegistrationService.cancelReserveByToken()` — самостоятельная отмена резервной заявки без партнёра по self-service email-ссылке (`/reserva/accion/cancelar`, LFPT-0668).

**Сценарий 2 — перевод из основного состава в резерв (`CONFIRMED → WAITLIST` уже состоявшейся регистрации).** Единственная точка в коде, которая переводит уже `CONFIRMED`-регистрацию обратно в `WAITLIST` — `TournamentService.moveToWaitlist()` (админ-действие `/admin/tournaments/{id}/move-to-waitlist/{playerId}`). Письмо должно отличаться по смыслу от письма о первичной постановке в лист ожидания при регистрации (`sendWaitlistNotificationEmail`/`waitlist-notification.html` — используется при самой регистрации, когда мест не было, это другое бизнес-событие): явно сказать, что регистрация **не отменена**, а переведена в резерв, и что при освобождении места придёт отдельное уведомление.

Сегодня `moveToWaitlist()` уже вызывает `sendWaitlistNotification(...)` (переиспользует `waitlist-notification.html`/"Has sido agregado a la lista de espera") — текст предполагает первичную постановку в очередь, а не перевод из основного состава, и не говорит явно "это не отмена". Заменить этот вызов на новое, отдельное письмо.

**Сценарий 3 (желательно) — перевод из резерва в основной состав.** Автоматический перевод (когда освобождается место — `autoConfirmFromWaitlist`/`confirmDoublesPairsFromWaitlist`/`confirmFromWaitlist`) уже отправляет письмо (`sendWaitlistAutoConfirmEmail`, `vacancy-invitation.html`) — не трогаем. Единственная точка без уведомления — ручной перевод администратором: `TournamentService.moveToMain()` (`/admin/tournaments/{id}/move-to-main/{playerId}`). Добавить вызов того же существующего письма (`sendWaitlistAutoConfirmEmail`) — оно уже корректно по смыслу ("вы подтверждены") для обоих случаев, не нужен новый шаблон.

**Идемпотентность (п.2 ТЗ).** Все перечисленные методы уже проверяют текущий статус перед переходом и бросают исключение на no-op повтор (`cancelRegistration` — `!isActive` → exception; `cancelPairRegistration` — фильтрует только активные записи; `AmericanoService.cancelRegistration` — `!isActive` → exception; `cancelReserveByToken` — явный `if (reg.isCancelled()) return;` без побочных эффектов; `moveToWaitlist`/`moveToMain` — требуют текущий статус `CONFIRMED`/`WAITLIST` соответственно). Письмо добавляется строго после прохождения этих проверок и реального `save()` — повторный вызов на уже изменённый статус не создаёт новое письмо, т.к. не доходит до точки отправки.

**Пары / команда (п.4 ТЗ).** Только `cancelPairRegistration` реально затрагивает двух игроков одной операцией — туда письмо шлётся обоим. Остальные точки (`cancelRegistration`, `moveToWaitlist`, `moveToMain`, Americano, резерв-без-партнёра) всегда меняют статус ровно одной регистрационной записи (одного игрока) — письмо уходит только ему, что уже соответствует правилу "если изменение касается только одного игрока — письмо только ему". Americano не поддерживает парную регистрацию вообще (`cancelRegistration` явно отбрасывает `isDoubleRegistration`).

**Локализация (п.5 ТЗ).** Оба новых письма — через `Context(locale)` с `player.getLocale()`, как все существующие письма; новые i18n-ключи во все три `messages_{es,ru,en}.properties`. Собственные имена (клуб, игрок) не переводятся — передаются как переменные шаблона, как и везде.

### Нефункциональные

- i18n: новые ключи `email.registration_cancelled.*` и `email.moved_to_reserve.*` в `messages_es/ru/en.properties`.
- Письма — через существующий `EmailService` (async, `@Timed`/`@TrackErrors`, `EmailMetricsService`, дневной лимит) — новый код повторяет конвенцию существующих методов (`sendWaitlistNotificationEmail`, `sendPartnerReserveEmail` и т.д.), не вводит параллельный механизм отправки.
- Безопасность: новых точек входа пользовательских данных не добавляется — причина отмены уже существующее поле/параметр (`cancellationReason`, `reason`), просто прокидывается в письмо, не выводится как raw HTML (Thymeleaf `th:text`, не `th:utext`, кроме как в существующих местах, где `th:utext` уже используется для статичного текста шаблона, не для пользовательского ввода).

## Вне скоупа

- **Team Americano / Team Playoff** (`AmericanoTeam` и связанные сущности) — другая модель участников, не основана на `TournamentRegistration.status`; резерв для Team Playoff уже реализован отдельной фичей (LFPT-0729/0730) со своей логикой. Не затрагивается этой задачей.
- **Каскадная отмена при удалении/деактивации аккаунта игрока** (`TournamentService.cancelAllRegistrationsForPlayer()`, вызывается из `TestTournamentController` при удалении тестового игрока и потенциально при реальном удалении аккаунта) — технически тоже перевод в `CANCELLED`, но это побочный эффект удаления самого аккаунта, не обычный жизненный цикл регистрации на турнир. Письмо не отправляется (разумный выбор реализующего — рассылать уведомления об отмене турниров человеку, чей аккаунт в этот момент удаляют, контрпродуктивно и не упомянуто в задаче).
- **Легаси-flow `PARTNER_INVITED`** (приглашение партнёра по email до LFPT-0687) — не имеет в коде отдельного действия "отклонить приглашение", соответствующего вызова `.cancel()` для этого статуса не существует; ничего менять не требуется.
- Админ-UI для ввода причины отмены там, где его сегодня нет (например, `/admin/tournaments/{id}/move-to-waitlist/{playerId}` — без формы причины) — не добавляется; письмо показывает причину только если она уже доступна через существующий параметр/поле.
- Новая Liquibase-миграция — не требуется, используются существующие поля `cancellationReason`/`reason`.

## Критерии приёмки

- [ ] Самостоятельная отмена одиночной регистрации (`POST /players/tournaments/{id}/cancel`) → письмо с подтверждением отмены (название турнира, дата, время, клуб); без причины — поле причины в письме не показывается.
- [ ] Отмена своей регистрации в паре, партнёр остаётся (`cancel-double`, `option=self`) → письмо только отменяющему игроку, партнёр не получает письма (его статус не менялся).
- [ ] Отмена всей пары (`cancel-double`, `option=full`) → письмо отмены получают **оба** игрока пары, с данными турнира.
- [ ] Отмена резервной заявки без партнёра по email-ссылке (`GET/POST /reserva/accion/cancelar`) → письмо с подтверждением отмены этому игроку; повторный переход по той же ссылке (уже отменено) — письмо не отправляется повторно.
- [ ] Админ/организатор отменяет регистрацию игрока в Americano через `/tournaments/americano/{id}/cancel` с указанной причиной → письмо игроку содержит эту причину; без причины — поле не показывается.
- [ ] Админ переводит игрока CONFIRMED → WAITLIST (`POST /admin/tournaments/{id}/move-to-waitlist/{playerId}`) → письмо отличается от письма о первичной постановке в лист ожидания, явно говорит "не отменено, в резерве".
- [ ] Админ переводит игрока WAITLIST → CONFIRMED (`POST /admin/tournaments/{id}/move-to-main/{playerId}`) → письмо о подтверждении участия (переиспользуется существующее `vacancy-invitation.html`).
- [ ] Письма локализуются по `player.getLocale()` — проверить ES/RU/EN текст хотя бы одного нового письма.
- [ ] `python3 .github/bin/docs-drift.py` — 0 расхождений после обновления `.agents/PROJECT.md`.

## Edge cases

- Причина отмены отсутствует (`null`/пустая строка) — блок "причина" в письме не рендерится (не пустая строка вида "Причина: ").
- У игрока не указан email (в проекте обязателен при регистрации — `PlayerPadel.email` not null) — отправка идёт как обычно, доп. проверки не нужны (как и во всех существующих письмах).
- `cancelPairRegistration` удаляет записи — данные для письма (email/имя/локаль обоих игроков, объект `Tournament`) нужно прочитать **до** `registrationRepository.delete(reg)`, иначе из уже удалённой/отсоединённой сущности их не получить в рамках той же транзакции безопасно.
- Дневной лимит писем (`EmailMetricsService.isDailyLimitReached`) — новые письма подчиняются общему лимиту, как и все существующие (`emailMetricsService.recordEmailRejected(...)` при достижении).
