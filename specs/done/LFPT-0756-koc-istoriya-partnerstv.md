# LFPT-0756: Feature алгоритм формирования пар в «Короле корта» — учёт истории партнёрств для разнообразия команд

## Статус
done

## Источник
Клиентский запрос [specs/requests/LFPT-0756-koc-istoriya-partnerstv.md](requests/LFPT-0756-koc-istoriya-partnerstv.md) (Telegram-сообщение 5712, issue [#756](https://github.com/UstinKO/padel-core-service/issues/756)).

## Контекст / зачем

В формате «Король корта» (`KingOfCourtService.createNextRound`) после перемещения игроков между кортами (победители выше, проигравшие ниже — не меняется) на каждом корте из четырёх игроков формируются две команды. Сейчас это делает `createTeamsAvoidingPreviousPartners`: метод избегает повторения партнёра только из **непосредственно предыдущего** раунда (бинарный фильтр — валидный вариант либо есть, либо откат к случайному), и не учитывает историю партнёрств за весь турнир. Из-за этого одни и те же пары могут повторяться чаще, чем необходимо, особенно на первом/последнем корте, где состав между раундами меняется слабее. Нужно учитывать полную историю партнёрств турнира и выбирать из 3 возможных комбинаций команд по приоритетам, а не бинарным фильтром.

## Связь с MASTER.md

Не затрагивает `specs/MASTER.md` — чисто внутренний алгоритм формирования команд King of Court, не меняет статусы регистрации, роли, инварианты регистрации или другие форматы турниров. Новых инвариантов в MASTER.md не вносится.

## Требования

### Функциональные

1. **История партнёрств за весь турнир.** Для каждой неориентированной пары игроков хранить (в оперативной памяти на момент расчёта следующего раунда, без новой таблицы БД — см. «Изменения в системе»): количество совместных матчей и номер раунда последнего совместного матча. Источник — фактически сыгранные корты (`KingOfCourtCourt.getResult() != null`) всех раундов турнира (`KingOfCourtRound` → `KingOfCourtCourt.getTeams()`), включая калибровочные раунды. Корты без результата (несыгранные, ещё не введённые) не учитываются.
2. **Выбор команд на корте.** Для четвёрки игроков, назначенной на корт в новом раунде, сгенерировать все 3 варианта разбиения на две команды (как и сейчас — `generatePossibleTeams`/аналог) и выбрать один по приоритетам, сравнивая **весь набор из 3 вариантов**, а не фильтруя бинарно:
   - **Приоритет 1** — минимум количества пар в варианте, чьё последнее совместное появление (`lastRoundNumber` в истории) равно номеру раунда, который только что завершился (т.е. повтор партнёрства из раунда, сразу предшествующего новому).
   - **Приоритет 2** — при равенстве приоритета 1 — минимум суммы количества совместных матчей (`timesPlayedTogether`) по обеим парам варианта за весь турнир.
   - **Приоритет 3** — при равенстве приоритетов 1 и 2 — минимум «давности»: для каждого варианта взять максимум `lastRoundNumber` среди его двух пар (пара без истории — `0`), выбрать вариант с наименьшим таким значением (чем меньше номер раунда последней встречи — тем давнее; «никогда не играли» всегда не хуже, чем «играли», независимо от номера раунда, так как сравнивается не абсолютное время, а номер раунда — `0` всегда ≤ любого сыгранного раунда).
   - **Приоритет 4** — при полном равенстве 1–3 по всем вариантам — случайный выбор среди них.
3. **Первый раунд и калибровочные раунды не выделяются отдельным кодом.** Первый раунд турнира (`createFirstRound`/`createTeamsForCourt`) формирует команды тем же алгоритмом, но с пустой историей — все 3 варианта равны по приоритетам 1–3, поэтому выбор эквивалентен текущему случайному (поведение первого раунда не меняется, код не дублируется — DRY). Калибровочные раунды используют тот же путь кода, что и обычные (`nextRound`/`createNextRound`); специальной логики формирования команд для калибровки нет и не добавляется — только начисление бонусных очков калибровочных раундов (`updatePlayerStats`), которое не меняется.
4. **Неизбежные повторения не блокируют турнир.** Поскольку выбор всегда делается из 3 сгенерированных вариантов без отбрасывания «невалидных» (в отличие от текущей реализации, где при отсутствии валидного варианта код проверяет пустой список и идёт в `else`), а просто ранжируется по приоритетам, турнир продолжает создавать раунды даже когда все 3 варианта содержат повторения — выбирается наименее плохой по приоритетам 1–3.
5. **Устойчивость к исправлению результата и откату.** `updateMatchResult` меняет только счёт/результат (кто победил), не состав команд (`CourtTeam.player1`/`player2` на корте не трогается этим методом) — история партнёрств и до, и после правки одинакова, искажений нет. `rollbackLastRound` удаляет сущность раунда целиком (каскадно удаляются корты/команды/результат) — при пересчёте истории для следующего `nextRound` этот раунд физически не попадёт в выборку (история строится по `KingOfCourtRound` турнира на момент расчёта), повторного учёта или потери данных не возникает.

### Нефункциональные

- Производительность: история строится один раз за вызов `nextRound` проходом по всем раундам/кортам турнира (не на каждый корт отдельно) — O(раунды × корты), для реальных масштабов турнира (≤ 24 игрока, ≤ 6 кортов, десятки раундов) пренебрежимо дешево.
- Тестируемость: алгоритм выбора команд и построения истории выносится в отдельный класс без зависимости от JPA/Spring (по аналогии с `AmericanoScheduleEngine`/`AmericanoScheduleValidator` — чистые функции над `Long`-идентификаторами игроков, не над `PlayerPadel`), чтобы покрыть unit-тестами без Spring-контекста.
- i18n: новых пользовательских строк нет (чисто серверная логика, не выходит на UI/API DTO).
- Безопасность: новой точки входа пользовательских данных нет — вход алгоритма (составы кортов, результаты матчей) уже проходит через существующие ADMIN-эндпоинты `KingOfCourtApiController`.

## Вне скоупа

- Алгоритм перемещения игроков между кортами (`calculateCourtAssignments`) — не меняется.
- Начисление очков, бонусов калибровки/обычных раундов, расчёт рейтинга, определение победителя турнира — не меняется.
- Другие форматы турниров (Americano, Team Americano, bracket) — не затрагиваются.
- Хранение истории партнёрств в БД (новая таблица/колонка) — не требуется, история пересчитывается из уже существующих данных (`KingOfCourtMatchResult`/`CourtTeam`) на каждый вызов `nextRound`.
- UI/API — без изменений (ни новых эндпоинтов, ни DTO).

## Изменения в системе

Нет новых/изменённых эндпоинтов — существующий `POST /api/king-of-court/tournaments/{kingId}/next-round` (и form-эндпоинт `/admin/tournaments/king-of-court/{kingId}/next-round`) продолжают работать с тем же контрактом, меняется только внутренняя логика формирования команд.

### UI
Не затрагивается.

### Документация

## Критерии приёмки

- [ ] Новый класс (чистые функции над `Long` id игроков, без Spring/JPA) строит историю партнёрств по списку сыгранных раундов: пара → (количество совместных матчей, номер раунда последней встречи); пары без общих матчей в истории отсутствуют
- [ ] Из 4 игроков корта генерируются все 3 варианта команд, и выбор учитывает приоритеты 1→2→3→4 строго в этом порядке (сравнение на уровне компаратора, не последовательная фильтрация с ранним отбрасыванием)
- [ ] Сценарий из примера клиента: A+B и E+F — партнёрство только что завершённого раунда; A+E — 3 раунда назад; B+F, A+F, B+E — никогда → выбирается ровно вариант A+F vs B+E
- [ ] Сценарий «все варианты содержат повтор завершённого раунда» (court, где любые 2 из 3 комбинаций содержат пары завершённого раунда) → выбирается вариант с наименьшим количеством таких повторов, создание раунда не прерывается ошибкой
- [ ] Сценарий «один и тот же счёт по приоритетам 1 и 2, но разная давность» (пример из запроса: A+B 2 раунда назад vs C+D никогда, против A+C 6 раундов назад vs B+D никогда) → выбирается вариант с более давним партнёрством (A+C/B+D)
- [ ] Первый раунд турнира (`createFirstRound`) формирует команды тем же методом с пустой историей — поведение (случайный выбор одной из 3 комбинаций) не изменилось
- [ ] Калибровочные раунды используют общий путь кода `nextRound`/`createNextRound`; их результаты попадают в историю для последующих раундов; начисление бонусных очков калибровки не изменилось (`updatePlayerStats` не тронут)
- [ ] `updateMatchResult` (исправление результата без изменения состава команд) не меняет количество учтённых партнёрств в истории — до и после исправления история идентична
- [ ] `rollbackLastRound` (откат раунда) исключает партнёрства откатанного раунда из истории при расчёте следующего `nextRound`
- [ ] Алгоритм перемещения между кортами (`calculateCourtAssignments`) не изменён — существующее поведение (победители выше/не выше 1-го, проигравшие ниже/не ниже последнего) идентично до и после правки
- [ ] Автоматические симуляции турниров на 8/12/16/20/24 игроках (2/3/4/5/6 кортов), не менее 20 раундов каждая: ни разу не нарушены инварианты «на корте ровно 4 уникальных игрока», «раунд успешно создаётся даже при неизбежных повторениях»
- [ ] `./mvnw verify` зелёный, включая новые unit-тесты алгоритма
- [ ] Другие форматы турниров (Americano/Team Americano/bracket) и расчёт очков/рейтинга King of Court — без регрессий (ручная/тестовая проверка, что существующие тесты и ручной прогон турнира по очкам не изменились)

## Edge cases

- Турнир только начался (1 сыгранный раунд) — история содержит только пары первого раунда, остальные варианты оцениваются как «никогда не играли» (приоритеты 2–3 не блокируют выбор).
- Все 3 комбинации четвёрки уже встречались (многократные повторы на протяжении турнира) — алгоритм обязан вернуть один из вариантов (наименее плохой), не бросать исключение и не возвращать пустой результат.
- Четвёрка, где 3 из 4 игроков — новые для турнира (например, после замены/опоздания — вне скоупа данной задачи, но алгоритм не должен падать на пустой истории для части пар): пары без записи в истории считаются как `timesPlayedTogether=0`, `lastRoundNumber=0`.
- Корт с `null` результатом (раунд создан, но матч ещё не сыграли на момент расчёта — не должно происходить в штатном потоке, так как `nextRound` проверяет `allResultsEntered` перед вызовом, но метод построения истории не должен включать такие корты, если когда-либо вызовется раньше).
- Конкурентный доступ: расчёт следующего раунда — не чаще одного раза за раунд, под тем же `@Transactional`, что и раньше; новый код не добавляет дополнительных точек состояния гонки по сравнению с текущей реализацией.

## Открытые вопросы

Нет открытых вопросов — запрос заказчика содержит исчерпывающую техническую постановку (приоритеты, примеры, таблица тест-сценариев), однозначно реализуемую существующими структурами данных без дополнительных бизнес-решений.
