# LFPT-0303: Ограничение самостоятельной регистрации на турнир по уровню игрока

## Статус

Telegram-сообщение (для reply): 5223

## Контекст / зачем

Игрок указывает уровень (`PlayerPadel.nivelJugador`) в профиле, но при самостоятельной регистрации на категорийный турнир (`Tournament.categoriaNivel`) сейчас никакой проверки нет — игрок любого уровня может зарегистрироваться на турнир любой категории. Заказчик хочет ограничить разницу между уровнем игрока и категорией турнира одной ступенью (своя категория либо соседняя — сильнее или слабее), чтобы не допускать явно неравных турниров, но не мешать игре в своей и соседних категориях.

## Связь с MASTER.md

Не меняет инвариантов `specs/MASTER.md` — там уже зафиксировано, что `PlayerPadel.hasValidContact()` обязателен для регистрации; это правило добавляет ещё одно условие регистрации (уровень), не заменяя существующие. `MASTER.md` стоит дополнить короткой строкой об этом правиле в том же PR (раздел "Форматы турниров"/рядом с инвариантом контактов) — не меняет существующий текст, только добавляет новый абзац.

## Требования

### Функциональные

1. **Правило ±1 ступень.** Игрок с уровнем `L` может самостоятельно зарегистрироваться на турнир с категорией `C`, если `|ordinal(L) − ordinal(C)| ≤ 1` и `L`/`C` относятся к одному `GenderFormat` (мужской/женский). Направление ordinal соответствует порядку объявления `Nivel` (`C9 < C8 < ... < C4`, `D9 < D8 < ... < D4`) — подтверждено примерами заказчика.
2. **Область действия правила.** Правило применяется **только** когда `Nivel.isPlayerLevel(tournament.getCategoriaNivel())` истинно — т.е. категория турнира одна из 10 "простых" уровней: `C9, C8, C7, C6, C5, C4, D9, D8, D7, D6`. Для любой другой категории (`null`, `TODOS`, `PRINCIPIANTES`, диапазоны `C9_C8`/`C7_C6`/`D7_D8`/др., `SUMA_10..16`, `D5`/`D4` — последние два не входят в `PLAYER_LEVELS`, см. #373/#206) — проверка **не выполняется**, регистрация не ограничивается этой фичей. Это технически обоснованное решение (не додумывание бизнес-правила): заказчик явно вывел `SUMA_*` и "другие специальные категории" из скоупа, а диапазоны/`PRINCIPIANTES` структурно — то же самое множество "непростых" категорий, что и раньше потребовало отдельной логики (см. исходный анализ в issue #303).
3. **Открытые форматы.** Независимо от `categoriaNivel`, правило не применяется, если `tournament.getTipo()` — `CANCHA_ABIERTA` или `PADEL_CLINIC` (заказчик явно назвал оба).
4. **Уровень не указан.** Если применимо правило (п.1-3 требуют проверки) и `player.getNivelJugador()` — `null` или `SIN_ESPECIFICAR` — регистрация блокируется с отдельным, отличимым от "уровень далёк", результатом (для фронтенд-попапа "Указать уровень", отдельная зависимая задача). Текст ошибки — `tournament.register.level_required`.
5. **Уровень слишком далёк.** Если `|diff| > 1` либо разный `GenderFormat` — регистрация блокируется с сообщением `tournament.register.level_mismatch`, параметризованным: текущий уровень игрока, категория турнира, список допустимых категорий (тот же уровень ± 1 ступень, отфильтрованный по `Nivel.isPlayerLevel`).
6. **Точки входа (самостоятельная регистрация).**
   - `TournamentService.registerPlayer()` — одиночная регистрация, все форматы турнира.
   - `DoubleTournamentRegistrationService.registerForDoubleTournament()` — проверяется `mainPlayer`; если партнёр — уже существующий аккаунт (`existingPartner.isPresent()`, ветка `registerWithExistingPartner`), проверяется и его уровень (оба становятся `CONFIRMED`/`WAITLIST` сразу, это тоже момент их самостоятельного согласия на регистрацию).
   - `DoubleTournamentRegistrationService.registerSoloForDoubleTournament()` — проверяется регистрирующийся игрок.
   - `DoubleTournamentRegistrationService.addPartnerToSoloRegistration()` — если партнёр — существующий аккаунт, проверяется его уровень (симметрично п. выше).
7. **Администратор/координатор — без ограничения.** Единственный существующий механизм ручного добавления реального игрока в турнир — `TestTournamentController` (`/test/tournaments/...`), работает напрямую через JDBC, не вызывает `TournamentService.registerPlayer()`/`DoubleTournamentRegistrationService` — новое правило туда не попадает технически, без дополнительного кода. Отдельного admin-override флага не требуется.

### Нефункциональные

- i18n: 2 новых ключа (`tournament.register.level_required`, `tournament.register.level_mismatch`) — во все три `messages_{es,ru,en}.properties`. Сообщение резолвится через `MessageSource`/`LocaleContextHolder` (как в `PlayerService`), не хардкод.
- Безопасность: новая точка входа данных не добавляется (используются уже существующие `nivelJugador`/`categoriaNivel`); важно, что проверка — на backend (п. "Проверка на backend" заказчика), прямой вызов API без фронтенда тоже должен быть заблокирован.
- Производительность: без доп. запросов к БД — все нужные поля уже загружены в существующих методах (`player`, `tournament`/`tournamentDto`, `existingPartner`).

## Вне скоупа

- `SUMA_*` (сумма уровней пары) и диапазонные категории (`C9_C8`, `D7_D8` и т.п.) — отдельная логика, не в этой задаче (заказчик явно вывел из скоупа).
- Фронтенд: попап "уровень не указан" с кнопкой "Указать уровень" и возврат к регистрации после сохранения уровня — отдельная зависимая задача (frontend), заводится после мержа и деплоя этой.
- `replacePlayerInPair` (замена партнёра в уже зарегистрированной паре) и flow нового (безаккаунтного) партнёра через `confirmPartnerRegistration`/`registerWithNewPartner` — новый партнёр создаётся с `nivelJugador = SIN_ESPECIFICAR` в момент подтверждения по токену (без браузерной AJAX-сессии, часто без предварительного логина) — технически невозможно применить проверку "сначала укажите уровень" на этом шаге без полного редизайна flow подтверждения партнёра. Остаётся как есть (как и раньше — не новый долг, просто не расширяем на этот flow в текущей задаче).
- Админ-панель / `TestTournamentController` — не затрагиваются.

## Изменения в системе

### API

Без изменений контрактов эндпоинтов — только новое возможное тело ошибки (400) для существующих:
- `POST /players/tournaments/{tournamentId}/register`
- `POST /api/tournaments/double/{tournamentId}/register`
- `POST /api/tournaments/double/{tournamentId}/register-solo`
- `POST /api/tournaments/double/{tournamentId}/add-partner`

Для `/players/tournaments/{tournamentId}/register` (единственный эндпоинт, где уже есть прецедент `needContact: true` для похожего случая) — JSON-ответ при "уровень не указан" дополнительно содержит `"needLevel": true`, по аналогии с существующим `needContact`. Остальные три эндпоинта такого прецедента не имели — им `needLevel: true` добавляется тем же способом, для единообразия (фронтенд-задача использует этот флаг).

### БД

Нет новой миграции — используются существующие поля `PlayerPadel.nivelJugador` и `Tournament.categoriaNivel`.

### UI

Нет изменений в этой (backend) задаче.

## Критерии приёмки

- [ ] Игрок уровня `L` не может зарегистрироваться (одиночно) на турнир категории `C`, где `C` — "простой" уровень (`isPlayerLevel`) того же пола и `|ordinal(L)-ordinal(C)| > 1` — `TournamentService.registerPlayer()` бросает исключение с сообщением вида «Ваш текущий уровень — C8. Регистрация на турнир C6 недоступна. Вы можете участвовать в турнирах категорий C9, C8 и C7.» (параметризовано текущим уровнем/категорией/списком допустимых).
- [ ] Тот же игрок успешно регистрируется на турнир своей категории и на категорию ±1 ступень (включая крайние случаи `C9`→только `C9`/`C8`, `C4`→только `C5`/`C4`).
- [ ] Турнир с `categoriaNivel` = `null`, `TODOS`, `PRINCIPIANTES`, любой диапазон (`C9_C8` и т.п.) или `SUMA_10..16` — любой игрок (включая `SIN_ESPECIFICAR`) регистрируется без ограничения по уровню.
- [ ] Турнир типа `CANCHA_ABIERTA` или `PADEL_CLINIC` с `categoriaNivel`, который в остальных случаях ограничивал бы (например `C7`) — регистрация не ограничивается.
- [ ] Игрок с `nivelJugador == SIN_ESPECIFICAR` (или `null`) не может зарегистрироваться на турнир с "простой" категорией — отдельное сообщение/флаг `needLevel`/`tournament.register.level_required`, отличимое от «уровень далёк».
- [ ] Кросс-гендерное сравнение: игрок мужской шкалы не регистрируется на турнир женской шкалы даже при близких ordinal (защищает от хрупкости `.ordinal()`, см. предупреждение в issue #303).
- [ ] Парная регистрация: `registerForDoubleTournament` с существующим партнёром вне допустимого диапазона — блокируется (с тем же сообщением) независимо от того, кто — основной игрок или партнёр — не проходит проверку.
- [ ] Парная регистрация с партнёром **без аккаунта** (имя/email/телефон через форму) — не блокируется этой проверкой на этапе `registerForDoubleTournament`/`registerWithNewPartner` (уровень партнёра неизвестен до создания аккаунта).
- [ ] `registerSoloForDoubleTournament` и `addPartnerToSoloRegistration` (с существующим партнёром) — аналогичные проверки.
- [ ] Прямой вызов API (без фронтенда, напрямую `curl`/тест) получает ту же ошибку — проверка не обходится через UI.
- [ ] `TestTournamentController` (`/test/tournaments/register-real-players`, `register-pair`, `register-guest-pair`) — не затронут, продолжает работать как раньше вне зависимости от уровня.
- [ ] Юнит-тесты на все ветки выше (как минимум: `TournamentLevelPolicyTest` для чистой логики + тесты на уровне сервисов для интеграции), `./mvnw verify` зелёный.
- [ ] `docs/domain-overview.md` (раздел "Эндпоинты Registrations") и `.agents/PROJECT.md` обновлены (упоминание нового правила там, где описана регистрация), `specs/MASTER.md` дополнен, `python3 .github/bin/docs-drift.py` — 0 расхождений.

## Edge cases

- `tournament.getCategoriaNivel() == null` — не ограничивается (большинство существующих турниров без заданной категории).
- Крайние значения шкалы: `C9` (нет "слабее" соседа) и `C4` (нет "сильнее" соседа), аналогично `D9`/`D6` (поскольку `D5`/`D4` не входят в `PLAYER_LEVELS` — не являются допустимым уровнем игрока на сегодня) — список допустимых категорий в сообщении корректно включает только 2 значения, а не 3.
- `player.getNivelJugador() == null` (теоретически не должно случаться, см. issue #82 — поле `NOT NULL` в БД с `DEFAULT SIN_ESPECIFICAR`) — обрабатывается наравне с `SIN_ESPECIFICAR`, защитный код, не ожидаемый в проде путь.
- Конкурентный доступ (2 реплики) — проверка синхронная, в рамках той же транзакции, что и остальная логика регистрации; не вносит новых гонок сверх уже существующих в `registerPlayer`/`registerForDoubleTournament`.
