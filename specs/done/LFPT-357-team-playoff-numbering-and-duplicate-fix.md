# LFPT-357: Team Playoff — корректная нумерация команд + защита от дубля пары в двух командах

## Статус
done — PR #358, деплой подтверждён успешным (run https://github.com/UstinKO/padel-core-service/actions/runs/32646447993, commit d0ec89d)

## Источник
GitHub issue [#357](https://github.com/UstinKO/padel-core-service/issues/357) — заведён конвейером напрямую по фидбеку заказчика (Telegram, роль `architect`, скриншот страницы `/admin/tournaments/80/payments`). Прямого клиентского файла `specs/requests/` нет — вход соответствует варианту 3 из `.claude/commands/develop-feature.md` (issue с готовой технической постановкой).

## Контекст / зачем
Организатор по ходу реального проведения Team Playoff турнира заметил два симптома:
1. Номера команд идут не по порядку — предположительно из-за исправлений при регистрации (отмена + повторная регистрация пары).
2. Одна и та же команда задублировалась дважды в ходе турнира — предположительно тоже из-за отмены и повторной регистрации.

Оба симптома — следствие двух самостоятельных, независимо чинимых технических дефектов, найденных при чтении кода `TeamPlayoffService`/`PaymentService` (см. ниже), а не новых бизнес-правил.

## Связь с MASTER.md
Не затрагивает инварианты `specs/MASTER.md` — Team Playoff уже упомянут как под-режим Team Americano, механика плей-офф-стадии описана только в коде/спеках (`specs/done/LFPT-348-*.md`). Изменения ниже — исправление существующей логики, введённой в LFPT-348 (#348) и ранее.

## Требования

### Функциональные

#### 1. Нумерация команд должна совпадать с тем, что реально показано на странице оплат

**Причина расхождения.** `TeamPlayoffService.resolveTeamNumberFromRegistration` (введён в LFPT-348) берёт `TournamentRegistration.position` напрямую из БД. Но `PaymentService.getPaymentManagementData` (метод, который формирует "Posición" на `/admin/tournaments/{id}/payments`) **не показывает** координатору сырое `position` — поверх него уже выполняется отдельная нормализация (существовавшая до LFPT-348, судя по комментарию в коде "устраняет дубли из-за тестовых данных или race conditions"): регистрации группируются по паре (`pairGroupId` = `mainPlayerId`, либо собственный id игрока, если он сам главный), и каждой новой группе присваивается следующий по порядку номер — 1, 2, 3... без пропусков и дублей, независимо от того, что реально хранится в `position`. Этот пересчитанный номер **не сохраняется обратно** в БД. Из-за этого `resolveTeamNumberFromRegistration` может присвоить `teamNumber`, отличный от Posición, которую координатор реально видел на экране — именно то расхождение, которое LFPT-348 (п.3, критерий приёмки "команда... получает teamNumber, равный отображаемой на этой же странице Posición") должен был устранить, но не устраняет, если сырое `position` содержит дубли/пропуски (ровно сценарий "были ошибки и исправления при регистрации").

**Фикс.** Вынести логику нормализации позиций (сейчас — приватный блок кода в `PaymentService.getPaymentManagementData`, строки ~289-298) в переиспользуемый метод, дающий `Map<Long pairGroupId, Integer displayedPosition>` по списку регистраций турнира, отсортированных так же, как сейчас (`findByTournamentIdOrderByPositionAscWaitlistPositionAsc`), отфильтрованных по `status IN (CONFIRMED, PARTNER_INVITED)` — то есть **тем же способом и с теми же входными данными**, что и `PaymentService` использует для отображения. Разместить как небольшой stateless-хелпер (например, статический метод в новом маленьком классе `service/PairGroupPositions` или аналогичном месте по вашему усмотрению — главное, не дублировать логику в двух местах), используемый и `PaymentService.getPaymentManagementData`, и `TeamPlayoffService.resolveTeamNumberFromRegistration`.

`resolveTeamNumberFromRegistration` вызывает этот метод и берёт значение по ключу `mainReg.getMainPlayerId() != null ? mainReg.getMainPlayerId() : mainReg.getPlayer().getId()` (тот же способ вычисления `pairGroupId`, что и в `PaymentService`). Если значение отсутствует (регистрация не входит в отфильтрованный список — см. Edge cases) или уже занято другой командой этого турнира (`existsByTournamentIdAndTeamNumber`) — прежнее поведение без изменений: `findMaxTeamNumber(tournamentId).orElse(0) + 1` с `log.warn`.

#### 2. Пара не должна одновременно оказаться в двух активных командах турнира

**Причина пробела.** И `TeamPlayoffService.addTeamFromRegistration`, и `importFromRegistrations` проверяют дубль только по `player1Id` (`teamRepository.existsByTournamentIdAndPlayer1Id(tournamentId, mainPlayerId)`). Если между двумя попытками регистрации одной и той же физической пары "главный" игрок (`mainPlayerId`) поменялся местами с партнёром (отмена регистрации → повторная регистрация, инициированная другим игроком той же пары) — старая команда (если её не удалили вручную) остаётся в турнире с одним player1/player2, а новая создаётся с игроками, переставленными местами по ролям player1/player2. Проверка `existsByTournamentIdAndPlayer1Id` не видит конфликт, потому что оба раза сравнивается только "текущий" `player1Id`, а не "занят ли этот игрок вообще, в любой роли, в любой активной команде турнира".

**Фикс.** Добавить в `AmericanoTeamRepository` метод `existsByTournamentIdAndPlayer2Id(Long tournamentId, Long player2Id)` (симметричный уже существующему `existsByTournamentIdAndPlayer1Id`; `findByTournamentIdAndPlayer2Id` уже есть в репозитории — переиспользуется тот же индекс/запрос). В `TeamPlayoffService` — приватный хелпер `isPlayerAlreadyOnActiveTeam(Long tournamentId, Long playerId)` = `existsByTournamentIdAndPlayer1Id(...) || existsByTournamentIdAndPlayer2Id(...)`, `false` если `playerId == null`.

Применить хелпер вместо/в дополнение к прежней проверке `existsByTournamentIdAndPlayer1Id`:
- `addTeam` (ручное добавление, `POST /tournaments/team-playoff/admin/{id}/teams/add`): проверить и `player1Id`, и, если указан, `player2Id` — при конфликте бросить `InvalidStateException` с указанием, какой из двух игроков уже занят.
- `addTeamFromRegistration` (кнопка "Agregar equipo" на странице оплат): проверить `mainPlayerId` (как раньше, но через новый хелпер) **и** id партнёра, если он определился (`partnerReg.getPlayer().getId()`, если партнёр зарегистрирован в БД; `mainReg.getPartner()`, если это существующий игрок, привязанный к регистрации иначе — та же логика, что уже использует `buildTeamFromPair` для определения `player2`). При конфликте — `InvalidStateException` (страница оплат уже оборачивает создание команды в try/catch с выводом `errorMessage`, см. `PaymentManagementController.saveAndAddTeam`).
- `importFromRegistrations` (массовый импорт): та же проверка для `mainPlayerId` и партнёра — при конфликте `continue` (пропустить пару, как и раньше для уже существующих по `player1Id`), плюс `log.warn` с указанием, какая пара и какой игрок конфликтуют (массовый импорт не имеет отдельного канала фидбека пользователю за пределами счётчика `imported`).

### Нефункциональные
- i18n: новых пользовательских строк не требуется — оба фикса меняют только внутреннюю логику существующих обработчиков, тексты ошибок уже локализованы шаблоном (общий `errorMessage`/`error` flash-атрибут).
- Безопасность: новых точек входа данных от пользователя нет.
- Производительность: нормализация позиций — та же O(n log n)-операция, что и сейчас в `PaymentService`, просто вызывается из одного места; проверка по `player2Id` — один дополнительный индексированный запрос на попытку создания команды, не влияет на массовые операции чтения.

## Вне скоупа
- **Исправление уже существующих в проде данных** (турнир из скриншота — `/admin/tournaments/80/payments`): фикс касается только новых вызовов `addTeamFromRegistration`/`importFromRegistrations`/`addTeam` после деплоя, как и было явно оговорено в LFPT-348. Уже задублированная команда и уже расставленные не по порядку номера команд в существующих турнирах фиксом не устраняются — это ручная правка координатором через уже существующую кнопку "Eliminar equipo" (если у дублирующей команды ещё нет сыгранных матчей) или отдельное обращение к разработчику, если матчи уже есть (см. Edge cases — `removeTeam` не разрешает удаление команды с матчами, это существующее, вне скоупа этой спеки поведение).
- Возможность принудительно удалить команду, у которой уже есть назначенные матчи ("рестарт турнира", предположение заказчика в исходном сообщении) — самостоятельная фича с отдельными компромиссами (что делать с уже сыгранными результатами соперников, счётом раунда и т.д.), не техническая мелочь; не входит в эту спеку.
- Пересчёт/пересборка уже присвоенных `teamNumber` для турниров, где команды уже добавлены с расхождением.
- Любые изменения самого расчёта `TournamentRegistration.position` (флоу регистрации турнира вне Team Playoff) — не трогаем, как и в LFPT-348.

## Изменения в системе

### API
Существующие endpoints, меняется только внутреннее поведение — новых нет:
- `POST /admin/tournaments/{tournamentId}/payments/add-team` (через `addTeamFromRegistration`) — `teamNumber` результата теперь совпадает с реально отображённой Posición; при конфликте партнёра по новой проверке возвращает `errorMessage` вместо создания дублирующей команды.
- `POST /tournaments/team-playoff/admin/{tournamentId}/teams/add` (`addTeam`) — дополнительная проверка `player2Id`.
- `POST /tournaments/team-playoff/admin/{tournamentId}/import-registrations` (`importFromRegistrations`) — пары с конфликтующим партнёром пропускаются (как и уже пропускаются пары с занятым `player1Id`).

### БД
Миграция не нужна — используются существующие колонки `player1_id`/`player2_id`/`team_number` (`v1.26-create-americano-teams.yaml`), меняется только логика в коде и добавляется один derived-query метод в существующий репозиторий.

### UI
Не затрагивается — оба фикса меняют только серверную логику, существующие шаблоны и flash-сообщения об ошибках уже на месте.

## Критерии приёмки
- [ ] Пара с `TournamentRegistration.position = 5`, добавленная в турнир кнопкой "Agregar equipo" **раньше**, чем пара с `position = 2` (порядок нажатия отличается от порядка регистрации, как в исходном фидбеке LFPT-348) — при этом сырое `position` в БД содержит пропуск или дубль у других регистраций турнира (например, из-за отменённой и повторно созданной регистрации) — получившийся `teamNumber` всё равно равен нормализованному номеру, который координатор видит в колонке "Posición" на `/admin/tournaments/{id}/payments` в момент добавления, а не сырому `position`.
- [ ] Юнит-тест, воспроизводящий: 3 подтверждённые пары, у одной из которых `position` задублирован с другой (симулирует "отмена + повторная регистрация") — нормализованные позиции 1/2/3 без дублей и пропусков, и `teamNumber`, присвоенный через `addTeamFromRegistration`, совпадает с нормализованным, а не сырым значением.
- [ ] Регистрация без подходящего статуса (не входит в `CONFIRMED`/`PARTNER_INVITED`, например `PAIR_REGISTERED`) — нормализованная позиция для неё не определена, `resolveTeamNumberFromRegistration` откатывается к прежнему поведению (`findMaxTeamNumber + 1`), без исключения.
- [ ] Игрок A зарегистрирован в паре с B, пара добавлена в турнир как команда (A=player1, B=player2). Регистрация отменена и A, и B, но команда физически не удалена (`removeTeam` не вызывался). Позже создаётся новая регистрация той же пары, где теперь B — главный игрок (B=player1, A=player2). Попытка добавить эту пару через "Agregar equipo" — `InvalidStateException` ("уже зарегистрирован"/аналог существующего текста), команда не создаётся; в турнире по-прежнему ровно одна команда с этой парой.
- [ ] Тот же сценарий (роли поменялись местами) для `importFromRegistrations` — конфликтующая пара пропускается (не создаёт вторую команду), счётчик `imported` её не учитывает, в логе `WARN`.
- [ ] Обычный сценарий без конфликта (игрок не участвует ни в одной существующей команде турнира ни как player1, ни как player2) — команда создаётся как раньше, поведение не регрессирует.
- [ ] `addTeam` (ручное добавление в админке Team Playoff): попытка добавить команду, где `player2Id` уже играет в другой активной команде этого турнира (а `player1Id` — новый игрок) — тоже отклоняется с понятной ошибкой (раньше этот случай не проверялся вовсе).
- [ ] Существующие тесты `TeamPlayoffService`/`AmericanoTeamRepository`/`TeamPlayoffEndToEndTest`/`PaymentService` продолжают проходить.

## Edge cases
- Регистрация без корректного статуса для отображения на странице оплат (`getPaymentManagementData` фильтрует `CONFIRMED`/`PARTNER_INVITED`, а `addTeamFromRegistration` дополнительно допускает `PAIR_REGISTERED`) — для такой регистрации нормализованная карта позиций не содержит её `pairGroupId` → откат на `findMaxTeamNumber + 1` (как и было для `position == null` в LFPT-348).
- Смешение ручного `addTeam` (без привязки к регистрации) и `addTeamFromRegistration`/`importFromRegistrations` в одном турнире — если вычисленный нормализованный номер уже занят другой командой (например, ранее создана вручную с этим же числом), поведение как в LFPT-348: `findMaxTeamNumber + 1` + `log.warn`, без исключения.
- Партнёр не зарегистрирован в БД (`partnerReg == null`, `mainReg.getPartner() == null`, есть только `partnerFirstName`/`partnerPhone`) — проверка на конфликт применяется только к `player1`(`mainPlayerId`), т.к. второй "игрок" не имеет `PlayerPadel`-записи и физически не может уже быть в другой команде.
- Оба игрока пары одновременно конфликтуют (оба уже в разных существующих командах, не обязательно друг с другом) — при первом найденном конфликте (main или partner) операция отклоняется целиком, отдельная команда не создаётся частично.

## Открытые вопросы
Нет — оба пункта фидбека формализуются как технические фиксы существующей логики (нормализация уже применяется на экране оплат, просто не переиспользуется при создании команды; проверка дубля уже существует, просто не покрывает `player2`) без новых бизнес-решений. Восстановление данных в уже пострадавшем турнире и возможность форс-удаления команды с матчами — вынесены во "Вне скоупа" как отдельные вопросы для последующего обсуждения с заказчиком.
