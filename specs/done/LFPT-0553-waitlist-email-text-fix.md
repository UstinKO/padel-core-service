# LFPT-0553: Fix текст письма о зачислении в лист ожидания не соответствует реальной логике — убрать упоминание 5-минутного подтверждения

## Статус
done

## Источник
[Issue #553](https://github.com/UstinKO/padel-core-service/issues/553) — клиентский запрос [`specs/requests/LFPT-0553-waitlist-email-text-check.md`](requests/LFPT-0553-waitlist-email-text-check.md) (Telegram, тема "AI Разработка", `[отправитель: customer]`).

Telegram-сообщение (для reply): 5045

## Контекст / зачем

Заказчик попросил проверить, соответствует ли фактической логике текст письма, которое получает игрок при попадании в лист ожидания (`email.waitlist.explanation`, шаблон `waitlist-notification.html`). Текст обещает: приглашение по email при освобождении места + 5 минут на подтверждение, иначе место уходит следующему.

Проверка кода показала, что это описание устарело. Логика листа ожидания была переработана в [#89](https://github.com/UstinKO/padel-core-service/issues/89) (смержено 2026-06-10, `feature/LFPT-0048`, за 4 месяца до текущей задачи): вместо приглашения с дедлайном система **автоматически** переводит первого игрока из `WAITLIST` в `CONFIRMED` и отправляет письмо-уведомление по факту, без необходимости что-либо подтверждать.

Детали проверки (отвечая на пункты клиентского запроса):

1. **Что происходит при освобождении места** — `TournamentService.processWaitlistForTournament(tournamentId)` вызывается из всех мест, где регистрация покидает `CONFIRMED` (отмена игроком, перевод организатором и т.д., см. вызовы на строках 451, 1037, 1079, 1103, 1281, 1321).
2. **Перемещается ли первый из листа ожидания в основной список автоматически, без доп. действий** — да. `processWaitlistForTournament` → `autoConfirmFromWaitlist(registration, tournament)` (строка 502) ставит `registration.setStatus(RegistrationStatus.CONFIRMED)` напрямую, никакого промежуточного состояния и никакого действия от игрока не требуется.
3. **Письмо — уведомление или приглашение с подтверждением** — простое уведомление постфактум: `sendWaitlistAutoConfirmEmail` (строка 516) → `EmailService.sendWaitlistAutoConfirmEmail(...)`, шаблон `vacancy-invitation.html`. Метод принимает только `tournamentUrl` — ни `confirmationUrl`, ни `deadline` в сигнатуре нет.
4. **Есть ли кнопка «Подтвердить участие»** — нет. В `vacancy-invitation.html` единственная кнопка — `email.vacancy.btn` = "🏆 Ver el torneo" (ссылка на страницу турнира). Кнопка подтверждения была убрана ещё в #89.
5. **Есть ли реальный таймер 5 минут** — для новых регистраций нет. Поле `invitationExpiresAt` и статус `RegistrationStatus.WAITLIST_INVITED` в коде формально существуют (`TournamentService.checkExpiredInvitations()`, `@Scheduled(cron = "0 */10 * * * *")`, строка 1564; `TournamentService.confirmFromWaitlist(token)`, строка ~1414), но ни один текущий code path не создаёт новых записей со статусом `WAITLIST_INVITED` — единственный путь из `WAITLIST` теперь сразу в `CONFIRMED` через `autoConfirmFromWaitlist`. Это подтверждённый мёртвый код, оставленный намеренно только "для дообработки существующих `WAITLIST_INVITED` записей в БД" (см. тело #89) — на момент этой проверки таких записей в проде, видимо, уже не осталось (переход случился 4 месяца назад).
6. **Что если участник не подтвердил за 5 минут** — неприменимо к текущим регистрациям: подтверждать нечего, статус `WAITLIST_INVITED` для новых регистраций не возникает. Cron `checkExpiredInvitations` продолжает молча отрабатывать каждые 10 минут, но находит (и находил всё это время) только устаревшие записи, если они ещё остались.
7. **Статусы на практике** — `WAITLIST` → `CONFIRMED` напрямую. Стадии "приглашён" для новых переходов нет.
8. **Соответствует ли текст письма фактической логике** — нет, не соответствует, во всех трёх локалях. Несоответствие — ровно в одном i18n-ключе:
   - `src/main/resources/i18n/messages_es.properties:691` — `email.waitlist.explanation`
   - `src/main/resources/i18n/messages_ru.properties:688` — `email.waitlist.explanation`
   - `src/main/resources/i18n/messages_en.properties:688` — `email.waitlist.explanation`

   Используется в `waitlist-notification.html:162` (`th:text="#{email.waitlist.explanation}"`). Хардкод-фолбэк в самом HTML на этой же строке ("Si algún jugador confirmado cancela, se liberará un lugar.") уже был поправлен при правке #89 вручную в шаблоне, но реальный рендеринг всегда берёт значение из `messages_{es,ru,en}.properties` (ключ там есть и резолвится), а не фолбэк — то есть именно properties-файлы и есть источник бага, во всех локалях, не только в ru.

Отдельно для сравнения: соседний ключ `email.vacancy.text` (письмо о самом зачислении, `vacancy-invitation.html`) уже написан корректно ("Has sido confirmado automáticamente...") — эталон тона/формулировки для правки ниже.

По указанию заказчика в клиентском запросе ("если логика автоматическая без подтверждения — текст письма нужно будет изменить, а не просто увеличивать время") — это прямая, заранее одобренная инструкция по итогам проверки, открытых бизнес-вопросов нет.

## Связь с MASTER.md

`specs/MASTER.md § Статусы регистрации на турнир` и `.claude/CLAUDE.md § Registration Status Flow` тоже описывают устаревшую механику ("следующий WAITLIST-игрок автоматически получает WAITLIST_INVITED и email с дедлайном... теряет место после 2 неотвеченных приглашений") — это тот же разрыв между документацией/текстом и кодом, обнаруженный после #89, просто в документации для разработчиков, а не в пользовательском письме. Эта задача **не** затрагивает `MASTER.md`/`CLAUDE.md` — только пользовательский текст письма, по прямому скоупу issue; расхождение в документации для разработчиков — см. "Вне скоупа".

## Требования

### Функциональные

- Переписать `email.waitlist.explanation` в `messages_es.properties`, `messages_ru.properties`, `messages_en.properties` так, чтобы текст описывал реальное поведение: при освобождении места игрок автоматически переводится в основной состав, письмо приходит уведомлением по факту, никаких действий от игрока не требуется и не предполагается никакой таймер.
- Не менять ключ/параметры (`email.waitlist.explanation` остаётся без плейсхолдеров, как сейчас) — меняется только текст значения.
- Не трогать `email.waitlist.how_it_works` (заголовок блока "Как это работает?") — он нейтральный, не требует правки.

### Нефункциональные

- i18n: правка затрагивает все три существующих файла локализации (es/ru/en) — новых ключей не добавляется, значит обновление остальных JS-эквивалентов не требуется (ключ не используется на фронтенде, только в email-шаблоне).
- Безопасность: новых точек входа данных от пользователя нет.

## Вне скоупа

- Удаление мёртвого кода (`checkExpiredInvitations`, `RegistrationStatus.WAITLIST_INVITED`, `confirmFromWaitlist`, `invitationExpiresAt`) — отдельная tech-debt задача, не затрагивается этим фиксом (issue прямо выносит это за скоуп).
- Обновление `specs/MASTER.md` и `.claude/CLAUDE.md`, которые тоже описывают старую механику приглашения с дедлайном — отдельная документационная задача (см. "Связь с MASTER.md" выше); не входит в критерии приёмки этой задачи.
- Текст `vacancy-invitation.html`/`email.vacancy.*` — уже корректен, не меняется.

## Критерии приёмки

- [ ] `email.waitlist.explanation` в `messages_es.properties`, `messages_ru.properties`, `messages_en.properties` не содержит упоминания "5 минут"/"5 minutos"/"5 minutes" и не предполагает никакого действия со стороны игрока (нет слов "подтвердить"/"confirmar"/"confirm").
- [ ] Новый текст описывает: автоматический перевод в основной состав + письмо-уведомление по факту, без таймера.
- [ ] Письмо `waitlist-notification.html`, отрендеренное под `Accept-Language: ru`, `es`, `en`, показывает новый текст (ручная/browser-проверка — см. `.claude/GIT_WORKFLOW.md` §4).
- [ ] `./mvnw verify` проходит без новых падений (логика не менялась — тест на отсутствие регрессии).
- [ ] Логика (`TournamentService`, статусы, cron `checkExpiredInvitations`) не изменена — diff ограничен i18n-файлами (и, если нужно, самим email-шаблоном — не ожидается).
