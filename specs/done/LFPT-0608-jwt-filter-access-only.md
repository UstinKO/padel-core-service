# LFPT-0608: Fix JWT-фильтр — принимать для доступа только access-токены

## Контекст / зачем

`JwtAuthenticationFilter` аутентифицирует запрос по заголовку `Authorization: Bearer <token>`, если `JwtService.validateToken(token, userDetails)` возвращает `true`. `validateToken` проверяет только совпадение `username` (claim `sub`) и срок действия (`exp`) — но не claim `tokenType`. Refresh-токен (claim `tokenType = refresh`, TTL 7 дней, выдаётся только для обмена на новую пару в `POST /api/auth/refresh`) подписан тем же секретом и имеет тот же `sub`, поэтому проходит `validateToken` точно так же, как access-токен (TTL 24ч, предназначен для аутентификации запросов).

Итог: клиент, которому достался (украден, утёк) refresh-токен, может использовать его как полноценный access-токен для любого API-запроса в течение 7 дней вместо 24 часов — токен с более узким предназначением (только обмен) даёт тот же доступ, что и токен с широким предназначением (любой запрос). Это расширяет окно действия скомпрометированного токена в 7 раз и нарушает принцип разделения access/refresh, ради которого в токен вообще кладётся claim `tokenType`.

## Требования

### Функциональные
- `JwtAuthenticationFilter.doFilterInternal` аутентифицирует запрос из `Bearer`-токена **только** если `tokenType = access`. Если токен валиден (подпись, срок, пользователь), но `tokenType = refresh` — `SecurityContext` не устанавливается (как если бы токен был невалиден), запрос идёт дальше по цепочке фильтров анонимным — далее `AuthorizationFilter` отклоняет его как обычно для защищённых эндпоинтов (401/403 от Spring Security, тот же путь, что и сейчас для просроченного/невалидного токена).
- `POST /api/auth/refresh` не меняется: эндпоинт и сейчас сам явно проверяет `jwtService.isRefreshToken(refreshToken)` перед `validateToken` (`AuthController.refreshToken`) — обмен refresh-токена продолжает работать, т.к. не идёт через `JwtAuthenticationFilter`-ветку с новой проверкой.
- `JwtService.validateToken(token, userDetails)` — сигнатура и поведение не меняются (используется и для access, и для refresh токена в `AuthController.refreshToken`); новая проверка типа токена — отдельно, только в `JwtAuthenticationFilter`, через уже существующий `jwtService.isRefreshToken(token)`.

### Нефункциональные
- Безопасность: закрывает возможность использовать refresh-токен как access-токен для аутентификации произвольных запросов (новая точка входа данных не добавляется — источник риска уже существующий, этой фичей сужается).
- i18n: не требуется — ответ 401/403 формируется стандартным механизмом Spring Security (`AuthenticationEntryPoint`/`AccessDeniedHandler`), как и сейчас для прочих случаев отказа в этом фильтре; новых пользовательских строк нет.

## Вне скоупа
- Ротация/чёрный список refresh-токенов (`docs/auth-flow.md` отдельно отмечает это как возможную будущую доработку) — не часть этой задачи.
- Изменение TTL access/refresh токенов.
- Любые изменения в `/api/auth/login`, `/api/auth/refresh`, `/api/auth/me` кроме не требующихся (эндпоинты не трогаем).

Эндпоинты не добавляются и не меняются. Меняется поведение middleware (`JwtAuthenticationFilter`): запросы с refresh-токеном в `Authorization` к любому защищённому эндпоинту получают 401 вместо прежней успешной аутентификации.

### БД
Нет изменений, миграция не требуется.

### UI
Не затрагивается (чисто backend/API слой).

## Критерии приёмки
- [x] Запрос к защищённому эндпоинту (например `GET /api/auth/me`) с `Authorization: Bearer <refresh-токен>` возвращает 401 (SecurityContext не устанавливается, принципал не резолвится).
- [x] Запрос с `Authorization: Bearer <access-токен>` к тому же эндпоинту продолжает аутентифицироваться и возвращать 200, как раньше.
- [x] `POST /api/auth/refresh` с валидным refresh-токеном продолжает работать как раньше (возвращает новую пару access+refresh).
- [x] Юнит-тесты на `JwtAuthenticationFilter`: access-токен → `SecurityContext` установлен; refresh-токен → `SecurityContext` не установлен (пустой/анонимный); невалидный/просроченный токен — поведение не изменилось.

## Edge cases
- Истёкший access-токен — поведение не меняется (как и сейчас, не аутентифицируется).
- Токен без claim `tokenType` вовсе (гипотетически, не генерируется текущим кодом) — `isRefreshToken()` вернёт `false` (`"refresh".equals(null) == false`), то есть такой токен пройдёт как access; это не хуже текущего поведения и не regresses ничего, т.к. все токены, выпускаемые `JwtService.generateToken`/`generateRefreshToken`, всегда содержат `tokenType`.
- Запрос без заголовка `Authorization` или без `Bearer ` — не меняется, фильтр пропускает как раньше.
