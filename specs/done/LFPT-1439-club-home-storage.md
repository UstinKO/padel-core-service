## Источник
[Issue #1439](https://github.com/UstinKO/padel-core-service/issues/1439). Техническая постановка по утверждённой фазе 6. Родитель [#1051](https://github.com/UstinKO/padel-core-service/issues/1051).

## Контекст / зачем
Подготовить первый проверяемый срез #1051. Публичная главная сейчас напрямую использует ClubRepository для totalClubs, хотя список и карточка уже читаются через PublicClubQuery.

## Связь с MASTER.md
[MASTER](../MASTER.md) определяет роли, границы клубного доступа, регистрацию, турнирные состояния и хранение истории вместе с подтверждённым изменением. Сценарии сохраняют текущие инварианты. Исходная фаза принята через PR #1413.

## Требования

### Функциональные

- Зафиксировать текущие потребители Club/ClubRepository и связанный граф (ORM, запросы и границы транзакций). Сверить базовый JAR, схему и историю Liquibase с текущим master.
- Перенести чтение totalClubs через существующий PublicClubQuery и ClubReadPort. Прежний countByIsActiveTrue вызывается адаптером одним count без загрузки списка.
- Зафиксировать утверждённый порядок фазы, пул задач, критерии упаковки и сверки истории.

### Нефункциональные
- Java release 17, JDK 21 в CI, одна транзакционная граница и один Boot JAR.
- Каждый PR проходит полный verify на отдельной PostgreSQL, артефактные и архитектурные guards, runtime/релевантный браузер и проверку совместимости предыдущего релиза.
- Сохраняются действующие права, i18n ES/RU/EN и внешние контракты. Новых пользовательских строк нет.

## Вне скоупа
Ручной релиз остаётся обычным. Физическая миграция PostgreSQL, Swarm и изменения бизнес-правил вне задачи.

## Изменения в системе

### API
GET /api/public/home возвращает прежний totalClubs и остальные поля. Публичный список и карточка остаются в прежнем application-срезе.

### БД
Прежняя PostgreSQL и schema. Отдельная тестовая БД для интеграции.

### UI
Действующие клиенты используют прежние данные. Приёмочные сценарии запускаются через штатные входы.

### Документация
[План фазы 6](../../docs/modular-monolith/phase-6/README.md), документация фактических границ, затронутые endpoints и техническая карта при необходимости.

## Критерии приёмки

- [x] /api/public/home сохраняет поле totalClubs и считает только активные клубы. Пустой набор даёт 0, неактивный клуб не прибавляется.
- [x] PublicDiscoveryService не зависит от ClubRepository. Прежний COUNT вызывается в read-only через существующий адаптер.
- [x] Полная сборка на PostgreSQL, guards, проверки клиента, предыдущий JAR и история Liquibase сверены. Граф потребителей клубов и последующие задачи задокументированы.

## Edge cases
Ноль активных клубов, приращение от активного клуба и отсутствие приращения от выключенного. COUNT не подменяется загрузкой строк. Транзакция порта read-only. PostgreSQL использует существующие migrations и историю.

## Открытые вопросы
Бизнес-вопросов нет. Технические подзадачи выделяются по фактическим связям JPA и потребителям. Реальные пользовательские данные и production-сервер не используются для QA.
