# LFPT-0590: Оркестратор автомержа — триггер метки из master и перестройка фронт-ветки после мержа бэка

## Статус
done

## Источник
[GitHub issue #590](https://github.com/UstinKO/padel-core-service/issues/590). Продолжение LFPT-0579 / LFPT-0587, найдено при живой проверке; кейс конфликта стека поднят пользователем 2026-10-16 (в тот же день конфликтовал #575).

## Контекст / зачем
1. Событие `labeled` не запускало оркестратор на PR #584: для `pull_request` GitHub берёт workflow из коммитов PR, а ветка #584 создана до появления `pipeline-merge.yml`.
2. Протокол #580 создаёт фронт-ветку от бэк-ветки. Бэк вливается squash-ом; во фронт-ветке остаются исходные бэк-коммиты, и обычный мерж фронта конфликтует, когда фронт правит те же строки (`messages_*.properties`). Подтверждено моделью: 3-way мерж — конфликт, `rebase --onto` — чисто.

## Связь с MASTER.md
Не затрагивает.

## Требования

### Функциональные
1. Триггер метки — `pull_request_target: labeled`; `select` всегда берёт скрипт из default branch (полный клон, `fetch-depth: 0`).
2. Перестройка стека в `pipeline-select.sh`: у кандидата `Depends-On: #M`, #M влит (и задеплоен, если менял код), последний коммит #M — предок head PR → в отдельном worktree `git rebase --onto origin/master <head #M>`, `push --force-with-lease` в ветку PR, комментарий в PR; verify — на новом head.
3. Rebase не прошёл → `rebase --abort`, ветка не тронута, `pipeline:conflict` + комментарий.
4. PR, head которого закоммичен `github-actions[bot]` (перестроен оркестратором), не требует check `build` — его заменяет verify.
5. Выход `verify_ref`: `refs/pull/N/merge` либо новый head после перестройки.
6. Документация: `GIT_WORKFLOW.md` §10 — две ступени конфликтов и `pull_request_target`; `develop-feature.md` — роутина не трогает фронт-ветку после `pipeline:ready`.

### Нефункциональные
- `pull_request_target` не исполняет код PR с правами на запись: `select` — скрипт из master, `verify` — сборка без секретов, права только на чтение.

## Вне скоупа
Автопочинка настоящих конфликтов роутиной — движок задач #581.

## Изменения в системе
`.github/workflows/pipeline-merge.yml`, `.github/bin/pipeline-select.sh`, `.claude/GIT_WORKFLOW.md`, `.claude/commands/develop-feature.md`.

## Критерии приёмки
- [ ] `pipeline:ready` на PR из ветки, созданной до появления оркестратора, запускает оркестратор.
- [ ] Фронт-PR, правящий те же строки, что влитый бэк-PR, после перестройки вливается автоматически.
- [ ] Настоящий конфликт при перестройке → `pipeline:conflict` + комментарий, ветка не изменена.

## Edge cases
- Фронт-ветка создана не от бэк-ветки (head #M не в истории) — перестройки нет, обычная проверка mergeable.
- Перестройка прошла, но verify упал → `pipeline:conflict`; ветка уже перестроена — роутина чинит её как обычный PR.
- master сдвинулся между перестройкой и мержем → мержа нет, следующий прогон: head от бота — без требования `build`, повторная перестройка не нужна (head #M уже не в истории), проверка mergeable + verify.
