# LFPT-1279: Feature многомодульный монолит — выделить движок подбора пар King of Court

## Статус
done
implemented

## Источник

[Issue #1279](https://github.com/UstinKO/padel-core-service/issues/1279). Техническая постановка напрямую из согласованного с владельцем плана: #1201 → KingOfCourtPairingEngine → отдельный последующий перенос Americano. Переход разрешён после мержа PR #1240. Родитель — #1041.

## Контекст / зачем

После пилота PlayoffMatchingEngine и клубного среза библиотека engines расширяется ещё одним уже чистым вычислением. KingOfCourtPairingEngine использует только JDK, вызывается статически из KingOfCourtService и имеет 13 исходных unit-тестов. Новый модуль и новая сервисная граница для него не нужны.

## Связь с MASTER.md

Сохраняются проведение King of Court, история, дополнительные очки, права, HTTP/WS и действующие транзакции. Бизнес-инварианты MASTER не меняются.

## Требования

### Функциональные

- Перенести KingOfCourtPairingEngine и KingOfCourtPairingEngineTest из корневого src в padel-tournament-engines без изменения содержимого файлов; сохранить package, вложенные record, сигнатуры, приоритеты, порядок и Random.
- В bootstrap оставить KingOfCourtService и KingOfCourtServiceNextRoundTest. Вызовы и транзакционные границы не менять; для статической утилиты не создавать Spring bean.
- Удалить shadow-исходники. ArchUnit разрешает только JDK и реальные классы engines; весь legacy service-пакет не разрешается.
- Проверять конечный boot jar: одна библиотека engines; оба движка и их вложенные классы принадлежат ей; в BOOT-INF/classes дубликатов нет; library не перепакована; bytecode Java 17, без Spring/JPA.
- Проверить отрицательные случаи контроля границ и артефакта, включая отсутствие второго движка и дубликат вложенного класса.

### Нефункциональные

После PR приложение работает самостоятельно. Полный verify с frontend — на отдельной PostgreSQL; итоговый jar проверяется в собственном preview. Новых строк, переводов, миграций и сетевых интеграций нет. Разрешение пользователя на ветку, проверки и PR уже дано; ручной мерж и production-деплой остаются отдельными действиями.

## Вне скоупа

Изменение алгоритма, полный рефакторинг KingOfCourtService, Americano, новые application/persistence/web/integrations модули, физическая БД и Swarm.

## Изменения в системе

### API

Существующие King of Court HTTP/WS и публичное Java API сохраняются.

### БД

Без изменений схемы, Liquibase и данных пользователей. Только синтетические fixtures своего preview.

### UI

Шаблоны и JavaScript не меняются. Реальный браузер проверяет существующие экраны проведения.

### Документация

Техническая карта .agents/PROJECT.md, docs/architecture.md, навигация и план docs/modular-monolith/, отдельный отчёт переноса с артефактом, проверками и ограничениями.

## Критерии приёмки

- [x] Два перенесённых файла байтово совпадают с master; все 13 unit-тестов исполняются в engines без Spring/БД.
- [x] Bootstrap-проверка nextRound и полный verify проходят; сервисы, транзакции и алгоритм не изменены.
- [x] Границы и артефакт отклоняют потерянный движок, shadow основного/вложенного класса, запрещённую зависимость и неверный bytecode.
- [x] На итоговом jar реальные API и браузер проходят инициализацию, счёт и следующий раунд King of Court; история партнёрств учитывается.
- [x] Общий legacy/API/React/Expo/session/CSRF/JWT smoke и репетиция выпуска/отката сохраняют контрольные данные; прежний артефакт работоспособен на той же синтетической схеме.
- [x] Документация, автоматизация, docs-drift, privacy/diff и локальное ревью пройдены; результаты и ограничения явно зафиксированы.

## Edge cases

Четвёрка не из четырёх игроков; три возможных разбиения; приоритет последнего раунда, суммарных повторов и давности; равенство и Random; история с обратным порядком ID и несколькими раундами. Всё сохраняется по исходным тестам без добавления новых правил. Для сборки — вложенные record и единственный владелец класса; для runtime — CSRF, права и возврат старого jar без SQL-отката.

## Открытые вопросы

Нет. Граница и последовательность согласованы владельцем; технические проверки уточняются по существующим сценариям без изменения поведения.
