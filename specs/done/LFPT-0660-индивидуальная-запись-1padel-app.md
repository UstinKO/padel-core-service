## Контекст / зачем

Веб-клиент 1Padel.App (`mobile-app/`, Expo/React Native, сборка раздаётся на `/app/`) сейчас только показывает расписание (`PlayerScreen`) и «Мои мероприятия» (`MyEventsScreen`, LFPT-0637/LFPT-0638, read-only) — сама запись на турнир требует перехода на сайт (`openWebsite(selected.websiteUrl)`). Для четырёх индивидуальных форматов — King of Court, Americano (модальность `INDIVIDUAL`), Padel Clinic («Тренировка + игра») и Cancha Abierta — запись устроена просто (`POST /players/tournaments/{id}/register`, без выбора партнёра), поэтому её можно перенести внутрь приложения без изменений на сервере. Парная регистрация (double-регистрация с партнёром/приглашением) существенно сложнее и не входит в эту задачу — для `DOBLES`-мероприятий кнопка по-прежнему ведёт на сайт.

## Связь с MASTER.md

Новых инвариантов не вводится. Используются существующие:
- Обязательный контакт для регистрации (`PlayerPadel.hasValidContact()`, раздел «Роли пользователей») — клиент получает `needContact` тем же способом, что и сайт (сервер отвечает `400` с флагом `needContact: true`), и даёт форму сохранения через существующий `PATCH /api/players/me/contact`.
- Ограничение по уровню «±1 ступень» (`TournamentLevelPolicy`, LFPT-0303) — клиент не дублирует проверку, только показывает серверный отказ (`needLevel: true`) со ссылкой на профиль сайта (у клиента нет безопасного отдельного API для изменения уровня — известная граница первого инкремента, явно вне скоупа).
- Статусы регистрации `CONFIRMED`/`WAITLIST` (раздел «Статусы регистрации на турнир») — для индивидуальных форматов `TournamentService.registerPlayer()` возвращает только эти два статуса (проверено по коду: `PAIR_REGISTERED`/`PARTNER_INVITED`/`WAITLIST_INVITED` возникают только в парном флоу `DoubleTournamentRegistrationService`, который этот экран не вызывает).

MASTER.md не меняется.

## Требования

### Функциональные

1. На экране деталей мероприятия (`PlayerScreen`) для событий `isIndividualEvent(event)` (модальность `INDIVIDUAL` и тип в `KING_OF_COURT | AMERICANO | PADEL_CLINIC | CANCHA_ABIERTA`) кнопка записи ведёт не на сайт, а открывает `IndividualBookingScreen` внутри приложения. Для всех остальных событий (включая все `DOBLES`, `AMERICANO_TEAMS`) — поведение не меняется (переход на сайт).
2. Если пользователь не вошёл в аккаунт — сначала открывается существующий `LoginScreen`; выбранное мероприятие сохраняется как намерение (`bookingIntent.ts`, `sessionStorage`, TTL 30 минут, переживает уход на Google OAuth2 и возврат на `/app/#accessToken=...`) и открывается автоматически после успешного входа.
3. Экран записи при открытии выполняет свежую проверку (`individualBooking.reconcile`): деталей мероприятия (`GET /api/public/tournaments/{id}`), собственных регистраций (`GET /api/players/me/tournaments`) и статуса контакта (`GET /api/players/me/contact-status`) — не использует закэшированные со списка данные.
4. Если у игрока уже есть активная регистрация на это мероприятие (`CONFIRMED`/`WAITLIST`) — показывается её статус и позиция в листе ожидания (если есть), повторная запись не предлагается.
5. Если контакта нет (`needContact`) — форма телефона (`+54...`) или Telegram-юзернейма, сохранение через `PATCH /api/players/me/contact`; после сохранения экран перечитывает статус контакта автоматически, но запись не создаёт.
6. Если турнир требует уровень, которого у игрока нет (`needLevel`, разбор `PlayerLevelRequiredException` на сервере) — сообщение и ссылка на профиль сайта (`https://1-padel.com/perfil`).
7. Условия участия в карточке — по формату: финансовые условия отмены (24 часа / полная оплата при поздней отмене / возврат при найденной замене) одинаковы для King of Court/Americano/Padel Clinic; у Cancha Abierta — своя формулировка без финансовых санкций. Штраф «−10 очков за опоздание» показывается только для King of Court и Americano (после LFPT-0651/PR #652 Padel Clinic и Cancha Abierta его не показывают и на сайте — тексты в `bookingCopy.ts` соответствуют текущим ключам `regConfirm.*` в `static/js/i18n/messages-ru.js` и логике `showRegistrationConfirmModal()` в `tournament-details.js`/`dashboard.js`).
8. Запись требует явного согласия (чекбокс «проверил мероприятие, стоимость и условия») перед тем, как кнопка подтверждения становится активной.
9. Подтверждение вызывает ровно один `POST /players/tournaments/{tournamentId}/register` (Bearer-сессия, без ID игрока в теле/URL, `credentials: 'omit'`). Результат (`CONFIRMED`/`WAITLIST` + позиция) — только из ответа сервера, никаких предположений на клиенте.
10. Если между открытием экрана и подтверждением изменились цена/валюта/дедлайн отмены/описание/клуб/уровень/наличие мест (переход в лист ожидания) — подтверждение сбрасывается (`CHANGED`), требуется повторная проверка и новое согласие.
11. Двойное нажатие на кнопку подтверждения не создаёт второй запрос (`BUSY` блокирует повтор, пока первый не завершился).
12. Обрыв связи/таймаут при `POST` не повторяется автоматически. Экран переходит в состояние «не удалось подтвердить» (`UNCERTAIN`) и предлагает сверить статус через повторный `reconcile` (не новый `POST`) — если запись обнаружится, показывается её реальный статус; если нет — явное предупреждение не отправлять новую заявку, пока не точно известно, что первая не обрабатывается.
13. `401` на мутации (истёкшая сессия, обновлённая после `refresh`) не повторяет `POST`/`PATCH` автоматически — требуется новая явная проверка и подтверждение пользователя (`REVIEW_REQUIRED`). `403` не трактуется как «игрок — организатор» и не навязывает иной UI, кроме сообщения об ошибке.
14. Смена аккаунта (логаут/повторный вход другим пользователем) во время незавершённой проверки не может завершить запись от имени нового аккаунта данными старой сессии (версионирование через `sessionVersion()`).
15. Изолированный тестовый режим компонента `/?screen=individual-booking-test` (query-параметр, не связан с обычной навигацией) — отдельная модель с вымышленными данными in-memory, не выполняет никаких запросов на сервер. Решение (техническое, не бизнес-вопрос): оставить как есть — он недостижим обычной навигацией (как и уже существующий `/?screen=login`), полезен для ручной/визуальной проверки сценариев без тестового турнира и явно маркирован в UI как тестовый режим.

### Нефункциональные

- **i18n**: новые строки — в `mobile-app/src/bookingCopy.ts` (ru/es/en), отдельный словарь от основного `copy.ts`, по той же схеме, что уже принята в `mobile-app/` (не затрагивает Spring `messages_{ru,es,en}.properties` — это независимый клиент).
- **Безопасность**: ID игрока никогда не передаётся клиентом — identity только через Bearer access-токен; cookies сайта не отправляются (`credentials: 'omit'`, как и у всех остальных запросов `auth.ts`); никакого автоматического повтора мутаций.
- **Производительность**: не применимо — объём запросов на пользователя не растёт (те же эндпоинты, что уже используют сайт/дашборд).

## Вне скоупа

- Парная (`DOBLES`) регистрация и отмена участия через приложение — остаются на сайте.
- Отмена регистрации через приложение (нет в патче, нет в запросе).
- Отдельный безопасный JSON API для изменения уровня игрока — используется существующий профиль сайта.
- Атомарная серверная фиксация цены/idempotency key для `POST /register` — известное ограничение существующего API, не меняется в этой задаче (риск смягчается preflight-проверкой на клиенте, а не устраняется).
- Любые доработки выявленных ранее пяти «расхождений регистрации» сверх того, что уже покрыто LFPT-0651/PR #652 — при сверке (см. «Критерии приёмки») новых расхождений в текстах условий для этих четырёх форматов не найдено; если найдутся — это предмет отдельной задачи, не блокирует эту.

## Edge cases

- Пустой/некорректный телефон и Telegram одновременно при сохранении контакта — отказ до отправки на сервер (валидация на клиенте, как в патче), запрос не уходит.
- Мероприятие стало недоступно (`registrationOpen=false`, статус не `REGISTRO_ABIERTO`, либо уже началось) между списком и экраном записи — явный блок, без попытки `POST`.
- Ответ сервера с неожиданной формой (`success` не булево, `status` не `CONFIRMED`/`WAITLIST`, отрицательная позиция в листе ожидания, HTML вместо JSON) — не трактуется как успех, уходит в `UNCERTAIN`/`UNAVAILABLE`, не создаёт ложного подтверждения на экране.
- Повторные попытки `reconcile` после `UNCERTAIN`, если запись так и не появилась — предупреждение, что первый запрос мог ещё обрабатываться, без разрешения повторной отправки.
- Параллельная регистрация на другое мероприятие в то же время, когда первое ещё «неопределённое» (`UNCERTAIN`) — не блокируется (неопределённость привязана к конкретному `tournamentId`).
- Docker Swarm / несколько реплик — не релевантно: клиент работает через обычный HTTP API, сервер уже асимметрично обрабатывает конкурентный доступ на уровне `TournamentService.registerPlayer()` (вне скоупа этой задачи).
