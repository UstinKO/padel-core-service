# Создание, продолжение и завершение PR

Общий протокол обычной сессии и `develop-feature`. Выполняется до новой issue/ветки/реализации и повторно перед push/созданием PR. Источник задачи — issue `LFPT-XXXX`; один действующий PR на одну issue. Backend/frontend имеют разные issues и разные PR. Правила полномочий, проверок и публикации — в [GIT_WORKFLOW.md](GIT_WORKFLOW.md); раздел бэклога — [ISSUE_ORGANIZATION.md](ISSUE_ORGANIZATION.md).

## Полная инвентаризация

Читай PR **всех авторов**, включая draft, все base-ветки и все страницы. Поиск по последним 100 заголовкам или только своим PR не является полной проверкой. Сначала получи открытые PR через список REST, затем найди связанные закрытые/влитые PR и issues. Поиск помогает найти кандидатов, но задержка индекса не доказывает отсутствие работы.

Пример чтения из корня без изменения GitHub:

```sh
gh api --paginate 'repos/UstinKO/padel-core-service/pulls?state=open&per_page=100' \
  --jq '.[] | {number,title,head:.head.ref,base:.base.ref,draft,body}'
```

Для исторического списка используй `state=closed` с пагинацией; для конкретной найденной связи перечитай `GET /repos/{repo}/pulls/{number}`, issue и список файлов PR. Не ограничивайся одним способом поиска. При неполной выдаче или ошибке GitHub создание второй попытки не разрешается.

Ищи одну задачу по совокупности: `Closes/Fixes/Resolves`, номеру LFPT в заголовке/ветке, `Pipeline-Task`, исходному запросу, спецификации, зависимостям и diff. `LFPT-909` и `LFPT-0909` — один номер; похожие слова в названии — ещё не дубль. Упоминание номера в отчёте аудита, ссылке или Depends-On чужого PR не делает этот PR владельцем issue: проверяй закрывающую связь и уникальный объём. Issue и PR имеют общее пространство числовых номеров: вид объекта проверяй API, а не по одному номеру.

## Решение до начала работы

| Состояние | Действие |
|---|---|
| Для issue уже есть открытый PR | Продолжить этот PR при поручении на доработку, конфликт или CI. Если это повтор исходного запроса, вернуть его ссылку. Второй PR не создавать |
| Есть активный другой исполнитель/claim | Не писать параллельно в его ветку. Уточнение доставить владельцу существующей работы; возраст claim сам по себе не доказывает остановку |
| PR закрыт без мержа | Прочитать причину и проверить текущий master. Закрытие не означает ни выполненную задачу, ни разрешение начать заново; восстановление/продолжение требует основания |
| Issue закрыта как выполненная либо найден влитый PR | Проверить реализованный объём и текущий код. Доработка сверх него — новая связанная issue; повтор реализации не запускать |
| Старый PR не merged, но изменения включены составным/другим PR | Сопоставить файлы/требования/тесты с canonical PR и master. Записать связь и остаток; не реализовывать заново только из-за состояния старого PR |
| Работа частично включена, остался уникальный объём | Сохранить ветку и описать остаток. Согласованно продолжить canonical PR либо отдельную задачу только на остаток; не выдавать его за полный дубль |
| Ничего не найдено и выдача полная | Обычный старт с issue, Milestone и одной веткой |

Правила claim/release для Telegram — [develop-feature, шаг 0.1](workflows/develop-feature.md). Перед перехватом просроченной заявки дополнительно перечитай PR, удалённую ветку, новые коммиты и доступное состояние исполнителя. После публикации claim перечитай заявки: выигрывает самый ранний активный run по created_at, при равенстве — по id комментария. Такой протокол уменьшает гонки, но не заменяет атомарную программную блокировку.

## Повторная проверка перед публикацией

1. Перечитай список PR и состояние конкретной issue непосредственно перед записью. Если параллельно появился PR, не создавай второй и не пушь поверх чужого head.
2. Для собственного существующего PR проверь repository/head, issue, слой и ожидаемый SHA. Обновляй его ветку. Повтор команды после сетевой ошибки начинается с чтения результата предыдущей попытки: PR мог уже создаться.
3. Если операция требует создания PR, убедись в отсутствии PR для **точной head-ветки и base** и для этой issue на других ветках. Отсутствие одного head не разрешает дубль на другом head. После `create` перечитай номер/URL и сохрани их для продолжений.
4. Проверь заголовок, `Closes #<issue>`, source issue, один подходящий Milestone и метки типа/слоя/формата. Существующие метки и маркеры сохраняй; техническая классификация не ставит `pipeline:ready`.
5. `Depends-On: #N` указывает на **PR**, не issue. Проверь `GET .../pulls/N`, слой, его `Closes` и head. Draft на родительскую feature-ветку допустим как явно описанный стек в обычной сессии; перед передачей автомержу base должен быть `master`, зависимости — действительными PR. Порядок проверок/деплоя сохраняется.
6. Финальный diff сверяй с фактической base и с master: файлы родительского стека не объявляй новым объёмом дочерней задачи. При уже влитой зависимости проверь, что остался только уникальный объём; историю опубликованной ветки меняй только в пределах действующих полномочий.
7. `pipeline`, `Pipeline-Task` и `pipeline:*` принадлежат явно запущенному автономному конвейеру. Отсутствующие метки не восстанавливай предположением по автору PR; обычная сессия сохраняет ручной мерж.

## Составной мерж и очистка

Предпочтительный процесс — одна issue/один слой/один PR. Если при согласованной интеграции PR содержит работу других открытых PR, до мержа перечисли исходные issue/PR и проверь уникальные изменения. Закрывающие ссылки ставятся только для полностью выполненных критериев. Частичное включение не закрывает исходную задачу.

После подтверждённого включения выбери и запиши canonical PR/commit. У полностью покрытого старого PR укажи причину и ссылку на замену, закрой его без повторного мержа, сохрани ветку. Исходную issue закрой как completed только при подтверждённом выполнении её объёма; это не duplicate issue. При сомнении оставь открытым с конкретным остатком. Не удаляй ветки, worktree, комментарии и уникальные коммиты ради уменьшения счётчика.

Историческое несходство SHA/patch-id не доказывает уникальность: squash и перенос файлов меняют их. Для доказательства используй diff конкретных PR, совпадение blobs, состав интеграционного коммита, требования и тесты. Успешный reverse-apply целого патча — сильное дополнительное свидетельство; неуспех может быть вызван последующими изменениями и сам по себе ничего не закрывает. Старый CI не заменяет проверки остатка после интеграции.

## Служебная архивация

PR от `deploy.yml` вида `docs/archive-specs-<sha>` — служебное исключение из ключа LFPT: его идентичность — deployed revision и набор архивируемых путей. Наличие такого PR не доказывает повтор продуктовой реализации. Перед ручной архивацией читай открытые archive-PR и оба расположения файла. Продолжи существующий PR; если файл уже в done, сверь содержимое. Не создавай вторую архивацию после таймаута без чтения GitHub. Невлитую корректную архивацию не закрывай как дубль только из-за возраста.

## Программные ограничения

Этот документ — инструкции агенту, а не серверный запрет. На срезе аудита 18.11.2026 `engine.py` ищет задачи по поисковому индексу, а `pipeline-select.sh` отбирает только готовые PR в master; общего атомарного реестра issue → canonical PR и проверки уникальности перед созданием у них нет. Детерминированный preflight, защита параллельных запусков, повтор после сбоя API и тесты гейтов требуют отдельной реализации. Не обещай, что изменение Markdown уже технически исключило появление дублей.
