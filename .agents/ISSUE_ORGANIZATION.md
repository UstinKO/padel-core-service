# Организация GitHub-задач по Milestones

Правило для `UstinKO/padel-core-service`: каждая новая рабочая issue получает **один открытый Milestone по цели задачи**. Применяется в обычной сессии, `new-feature`, `develop-feature` и при декомпозиции. Метки типа, слоя и формата дополняют Milestone, а не заменяют его.

Живой каталог — [Milestones](https://github.com/UstinKO/padel-core-service/milestones), навигация — [закреплённый индекс #1055](https://github.com/UstinKO/padel-core-service/issues/1055). Числовые номера и текущие названия разделов читать из GitHub, не переносить из примеров или прошлой сессии.

## Выбор раздела

До создания issue прочитай её цель, границы и зависимости, проверь дубли и актуальные открытые Milestones с описаниями. Все страницы списка должны быть прочитаны. Каталог ниже помогает выбрать направление; это не исчерпывающий список и не замена живому состоянию GitHub.

| Цель задачи | Направление |
|---|---|
| React-переход, его API, административный пилот, приёмка и переключение | UI v2 — переход на новый интерфейс |
| Подготовка и переход Compose → Swarm, оркестрация и эксплуатационные гарантии | Docker Swarm — анализ и переход |
| Границы семи модулей, reactor, пилот движка, выделение persistence | Многомодульный монолит — архитектура и пилот |
| Исправление смешения языков ES/RU/EN и проверки локализации | Локализация — ES, RU и EN |
| Изолированный рейтинг Elo, его данные, расчёт и приёмка | Рейтинг Elo — изолированный пилот |
| Просмотр сохранённых итогов/истории, комплекты и публикация результатов | Результаты турниров — просмотр и публикация |
| Общий рефакторинг, типизация, CODE_STYLE, инструкции и инструменты разработки | Техдолг — качество и сопровождение кода |
| Ошибка действующего приложения без более точного тематического направления | Баги — исправление и стабилизация |
| Отдельное продуктовое улучшение действующих турниров, админки или маркетинга | Развитие продукта — турниры, админка и маркетинг |

Более точное направление важнее общего типа работы. Например, баг локализации получает Milestone локализации **и** `bug`; баг UI v2 — Milestone UI v2 **и** `bug`. Общий фильтр `label:bug` продолжает находить их все. Слово «турнир», наличие frontend-кода или метки `tech-debt` сами по себе не определяют Milestone.

Пограничные случаи:

- Улучшение старого списка мероприятий не становится UI v2 только потому, что это интерфейс. Явная часть React-перехода относится к UI v2, самостоятельное legacy-улучшение — к продуктовому направлению.
- Общий рефакторинг `TeamPlayoffService` относится к техдолгу; перенос `PlayoffMatchingEngine` в Maven-модуль — к многомодульности.
- Выделение persistence относится к многомодульности, даже если окно совпадает со Swarm. Переключение инфраструктуры PostgreSQL/томов при переходе оркестрации — к Swarm. Разные результаты при необходимости оформляются отдельными связанными задачами.
- Backend/frontend-пара одной фичи обычно имеет один Milestone, но отдельные issues, метки слоя и PR с прежними зависимостями.
- Если существующая issue уже имеет подходящий открытый Milestone, сохрани его. Не перераспределяй соседние задачи при создании новой. При нескольких подходящих направлениях выбери по основному результату и родительской инициативе; кратко поясни выбор в описании/отчёте. Бизнес-неопределённость не разрешается выбором Milestone.

## Когда нужен новый Milestone

Если **ни один открытый раздел не соответствует цели**, создай новый. Не отправляй независимое направление в общий продуктовый или технический раздел ради заполнения поля.

Перед созданием проверь также закрытые Milestones и смысловые дубли: одинаковая цель может называться иначе. Завершённый исторический этап не переоткрывай автоматически. Для нового самостоятельного этапа задай отличимое название и укажи связь с историей в описании.

Новый раздел получает русское название направления/результата и короткое описание: что входит и какова граница с соседними разделами. Срок `due_on` задавай только при порученном сроке, не придумывай дату релиза. Отдельный раздел допустим и для одной задачи, если это самостоятельное направление; раздел на каждый файл/мелкую правку не нужен.

Поручение создать или декомпозировать рабочую задачу включает выбор Milestone, а при отсутствии подходящего — создание раздела и добавление его в навигацию. Дополнительного подтверждения на эту классификацию не требуется. Правило не разрешает создавать новые issues по обычному вопросу или совету, когда создание задачи не поручено; фактические разрешения среды сохраняются.

## Создание и проверка

Предпочитай доступные GitHub-инструменты. Если они не умеют читать/создавать Milestones, используй `gh api` в рамках доступных прав. Пример чтения всех страниц:

```bash
gh api --paginate --slurp 'repos/UstinKO/padel-core-service/milestones?state=open&per_page=100'
```

Для проверки исторических разделов запроси `state=all`. Создание — `POST /repos/UstinKO/padel-core-service/milestones` с `title`, `description`, `state: open`; обновление issue — `PATCH /repos/UstinKO/padel-core-service/issues/{number}` с `milestone`. Передавай данные структурированным аргументом инструмента либо JSON-файлом через `gh api --input`; токены и локальные настройки не выводи.

Назначай Milestone сразу при создании: поле `milestone` инструмента/REST принимает актуальный **`number` Milestone**, не его `id`/`node_id`; `gh issue create --milestone` использует название. Если создание и назначение раздельные, после получения номера issue сразу заверши назначение, не создавая вторую issue. Сохраняй правила LFPT-заголовка и меток из [GIT_WORKFLOW.md](GIT_WORKFLOW.md).

Для последующих правок передавай только изменяемое поле, например `milestone`. Метки добавляй аддитивно, не заменяй полный набор ради категории; `Pipeline-Task`, `Depends-On`, `Closes`, `pipeline` и `pipeline:*` сохраняются. Классификация не запускает работу и не даёт права ставить `pipeline:ready`.

После записи перечитай issue: правильный открытый Milestone назначен, прежние метки/зависимости/текст не потеряны. Для нового раздела проверь отсутствие смыслового дубля перед самой записью; если другой процесс уже создал подходящий, используй его. При ошибке/недоступности GitHub не выдумывай номер и не объявляй классификацию завершённой: сохрани известный номер созданной issue, сообщи о недостающем назначении, безопасно повтори только незавершённый шаг.

## Навигация и исключения

- При создании нового Milestone добавь ссылку и назначение в таблицу разделов [индекса #1055](https://github.com/UstinKO/padel-core-service/issues/1055). Перед редактированием прочитай актуальное тело; меняй только относящийся к разделу блок. Исторические счётчики/список среза не выдавай за текущее состояние.
- Новая issue в существующем разделе автоматически видна по живой ссылке Milestone. Переписывать исторический полный список и счётчики индекса при каждом создании не требуется.
- Исключение — постоянный служебный индекс с `backlog:index`: он остаётся без Milestone, чтобы не считаться работой одного направления. Не используй эту метку для обычной задачи без подходящего раздела.
- Контроль новых неклассифицированных задач: `is:issue is:open no:milestone -label:backlog:index`. В итоговом отчёте создания укажи issue и назначенный Milestone; для нового раздела также его ссылку.
