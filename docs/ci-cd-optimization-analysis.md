# Ускорение CI, тестов и деплоя

Анализ узких мест PR Check, Java-тестов и production-деплоя: найденные проблемы, варианты оптимизации и оценка выигрыша по каждому пункту. Документ дополняет [аудит времени тестирования, CI и деплоя](ci-cd-performance-audit.md) свежими замерами многомодульного master и новыми находками. Код, workflow и production в ходе анализа не менялись.

## Итог

| Контур | Сейчас | После быстрых пунктов | После всех пунктов |
|---|---:|---:|---:|
| PR Check (до завершения всех обязательных проверок) | **15:36** | **~6:45** (П1–П3) | **~5:55–6:05** |
| Деплой (job `deploy`) | **4:40** | **~3:35–3:55** (Д1, Д4, Д5) | **~1:50–2:40** (Д2 или Д3, Д7, Д8) |
| PR → прод при ручном мерже (PR Check + деплой) | **~20:15** | **~10:20–10:40** | **~7:45–8:45** |
| PR → прод через автоконвейер (PR Check + повторная проверка + деплой) | **~35:50** | **~17:05–17:25** | **~7:45–8:45** (с А1) |

- **PR Check сокращается на 9:30–9:40 (−61…62%).** Основной выигрыш даёт структура workflow, а не ускорение тестов: параллельные jobs, отдельный job для UI v2 и отказ от `sleep 60` (П1–П3) экономят **8:50** почти без изменения кода.
- **После перестройки самым длинным становится job пилота с репетицией релиза** (~6:25). Ускорение Java-тестов и проверки пакета перестаёт сокращать общее время, пока не ускорен этот job (П10, П4б). Тесты всё равно стоит ускорить: это запас на рост и более быстрый локальный `./mvnw verify`.
- **Деплой сокращается на 2:00–2:50 (−43…61%).** В каждый выпуск упаковывается и передаётся весь Docker-образ (~210 МБ), хотя меняется около 4 МБ. На сервере больше половины активации (55 с из 1:33) занимает старт Spring.
- **Оценочное окно недоступности во время деплоя — около минуты** (Д10). Оценка основана на хронологии замены контейнера и запуска Spring. Фактическое влияние на пользовательские запросы ещё нужно сверить с логами прокси.

## Проблемы и варианты: PR Check

### П1. Независимые jobs выполняются последовательно

**Проблема.** `build` ждёт `frontend` (`needs: frontend`), а `browser-marketing` ждёт `build`. Данными они не обмениваются: у каждого свой checkout, у `browser-marketing` своя PostgreSQL. [Workflow](../.github/workflows/pr-check.yml)

**Вариант.**
- Убрать `needs`, текущий `build` переименовать (например, в `backend`).
- Добавить итоговый job `build` с `needs` на все обязательные jobs и `if: always()`. Он должен падать, если хоть один из них не `success`, включая `skipped` и `cancelled`.
- Имя `build` сохранить обязательно: [pipeline-select.sh](../.github/bin/pipeline-select.sh) ищет check-run `build` на head-коммите.

**Экономия:** **−3:45** (1:47 + 2:03 минус ~0:05 на итоговый job). PR Check 15:36 → ~11:50.
**Трудоёмкость:** малая, правится только workflow.

### П2. Проверка UI v2 выполняется в одном job с Maven

**Проблема.** Шаг UI v2 (6:29) начинается только после `mvn clean verify` (3:43) и проверки пакета (0:53), хотя ему нужен только JAR, а результаты тестов не нужны.

**Вариант.**
- Отдельный job: checkout, Java с кэшем Maven, `./mvnw -B package -Dmaven.test.skip=true` (~0:35 по замеру деплоя), затем шаги preview.
- Сервис PostgreSQL этому job не нужен: у preview своя БД в Compose.

**Экономия:** **−4:05**. Критическим становится job UI v2 (~1:05 подготовки + 6:29 ≈ 7:35) вместо `build` (11:40). PR Check ~11:50 → ~7:45.
**Трудоёмкость:** средняя. Проверить, что оба job собирают один SHA и что загрузка артефактов `modular-pilot-qa` и остановка окружения переехали вместе с шагом.

### П3. Фиксированная пауза `sleep 60`

**Проблема.** Между `check.py` и `playoff-pilot.py` стоит `sleep 60` из-за лимита AUTH в 10 входов в минуту. Лимит задан в коде: `Bandwidth.classic(10, Refill.intervally(10, Duration.ofMinutes(1)))` в [RateLimitFilter.java](../src/main/java/com/padle/core/padelcoreservice/security/RateLimitFilter.java).

**Варианты.**
- Вынести лимит в настройку и поднять его в профиле закрытого контура `preview`.
- Запускать наборы в разных окружениях (П4): у каждого будет свой счётчик.

**Экономия:** **−1:00**. PR Check ~7:45 → ~6:45.
**Трудоёмкость:** малая. Убедиться, что ни один набор не проверяет сам лимит входов.

### П4. Проверка контура и пилот выполняются в одном окружении

**Проблема.** `check.py` (0:18) и пилот с репетицией идут последовательно. Кроме того, `playoff-pilot.py` повторно запускает общий браузерный smoke `ui-preview.browser.mjs`, который уже прошёл в `check.py`: строка «Браузер: внешний барьер, роли…» встречается в логе дважды.

**Вариант.**
- Вынести `check.py` в отдельный job со своим окружением.
- Пилот и репетицию релиза **не разделять**: [playoff-pilot.py](../automation/ui-preview/playoff-pilot.py) снимает состояние турниров пилота до репетиции и сверяет его после отката.
- Повторный общий smoke в пилоте убрать, если он не нужен для проверки артефакта.

**Экономия:** **−0:20** (0:18 + ~0:05 на повтор). PR Check ~6:45 → ~6:25.
**Трудоёмкость:** малая или средняя.

### П4б. Репетиция релиза в каждом PR (решение за командой)

**Проблема.** Репетиция выпуска и отката занимает 2:19 в каждом PR, хотя релизная автоматика меняется редко.

**Вариант.** Запускать репетицию только при изменениях, влияющих на выпуск (`automation/releases/**`, `automation/ui-preview/**`, Dockerfile, `pom.xml` и т. п.), и всегда — при повторной проверке перед автомержем. Это компромисс между скоростью и полнотой проверки.

**Экономия:** в PR без таких изменений **−1:55…−2:05** сверх остальных пунктов: PR Check ~4:00 вместо ~5:55–6:05, если сделаны также П5 и Т1–Т4.
**Трудоёмкость:** средняя.

### П5. Проверка пакета релиза повторяет медленную упаковку деплоя

**Проблема.** Шаг «Check immutable release package» (0:53) выполняет те же `docker save` и gzip уровня 9, что и деплой (см. Д1).

**Вариант.** Исправляется вместе с Д1 или Д2: это тот же код в [production.py](../automation/releases/production.py).

**Экономия:** **−0:35…−0:45** у job `backend`. После П2 на общее время не влияет, потому что `backend` уже не самый длинный, но даёт запас.
**Трудоёмкость:** сверх Д1/Д2 — нулевая.

### П6. Устаревшие прогоны не отменяются

**Проблема.** В workflow нет `concurrency`, и после нового push старый прогон доходит до конца. Среди последних 60 прогонов таких случаев 8: старый прогон работал ещё 3–17 мин, суммарно около 1,5 ч раннеров.

**Вариант.** Отменять только прогоны `pull_request`, не трогая `workflow_call` из [pipeline-merge.yml](../.github/workflows/pipeline-merge.yml):

```yaml
concurrency:
  group: pr-check-${{ github.event_name == 'pull_request' && github.event.pull_request.number || github.run_id }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
```

**Экономия:** на время одного прогона не влияет. Освобождает раннеры и убирает очередь, когда открыто несколько PR.
**Трудоёмкость:** малая.

### П7. PR только с документацией запускают полный PR Check

**Проблема.** В `deploy.yml` пути `docs/**`, `specs/**`, `.agents/**`, `AGENTS.md` исключены, а PR Check для таких PR выполняется целиком.

**Вариант.**
- Отдельный job `changes` (через `git diff --name-only` или `dorny/paths-filter`) и условия на тяжёлых jobs. Итоговый `build` из П1 считает пропуск успехом только в этом случае.
- `paths-ignore` на уровне workflow не подходит: обязательный check `build` останется в ожидании, и автомерж не сработает.

**Экономия:** для PR только с документацией — 15:36 → ~0:30.
**Трудоёмкость:** малая или средняя.

### П8. `browser-marketing` пересобирает проект ради одного теста

**Проблема.** `./mvnw -Dtest=RegistrationSourceBrowserTest test` собирает оба модуля, ставит Node и pnpm и собирает фронтенд. Из 1:04 шага сам тест занимает около 0:33. Ещё 0:40–0:54 уходит на загрузку образа Playwright и PostgreSQL.

**Вариант.** Добавить `-Dskip.frontend=true`, если тесту не нужны React-ресурсы (проверить).

**Экономия:** ~0:10–0:15 времени раннера. После П1 job не на критическом пути, поэтому общее время не меняется.
**Трудоёмкость:** малая.

### П9. Node, pnpm и Chromium устанавливаются заново

**Проблема.**
- `frontend-maven-plugin` ставит Node в `target/frontend-toolchain`, а `clean` этот каталог удаляет.
- Хранилище pnpm в `build` и `deploy` не кэшируется: в логе деплоя «reused 0, downloaded 281».
- Chromium устанавливается заново и в `frontend`, и в `build`.

**Вариант.** Вынести `installDirectory` из `target/` и кэшировать его, добавить кэш хранилища pnpm и `~/.cache/ms-playwright`.

**Экономия:** ~0:05–0:10 на каждый job, где это есть.
**Трудоёмкость:** малая, приоритет низкий.

### П10. Перезапуски приложения в репетиции релиза

**Проблема.** После П1–П4 самым длинным становится job пилота с репетицией (~6:25). Каждый сценарий сбоя запускает приложение минимум дважды: кандидата и восстановленный предыдущий выпуск. В preview приложение готово примерно через 16 с после старта. Сценарий chunk занимает 1:12, readiness — 0:26; разбивки внутри сценариев в логе нет.

**Вариант.** Запускать распакованный JAR (`java -Djarmode=tools extract`) вместо вложенного fat JAR: по замеру старт быстрее на **25%** без дополнительных артефактов (см. «Замер: время старта приложения и CDS»). CDS-архив даёт ещё −13 п.п., но в репетиции не окупается: варианты выпуска разные, и для каждого нужен свой тренировочный запуск, который длится примерно как обычный старт.

Для окружений CI можно добавить `-XX:TieredStopAtLevel=1` (только JIT C1): по замеру это ещё −21% старта (Д9). Совместный эффект с распакованным JAR не замерен, поэтому в оценку ниже не включён.

**Экономия:** **−0:20…−0:30** (~4 с на старт при 16 с × 5–7 стартов). PR Check ~6:25 → ~5:55–6:05.
**Трудоёмкость:** средняя. Проверка выпуска сейчас извлекает исходный JAR из образа и сверяет его SHA-256 (`image_jar`, `artifact.verify`): её нужно перевести на распакованный вид или хранить исходный JAR рядом.

## Проблемы и варианты: Java-тесты

Т1–Т4 вместе сокращают Surefire на **0:45–1:20**. Влияние на общее время зависит от момента внедрения:
- **до перестройки CI** (П1–П4) это прямая экономия **−0:45…−1:20** PR Check;
- **после перестройки** `backend` (~5:20) уже короче job пилота, поэтому общее время не меняется, но появляется запас.

Локально эффект больше: на Windows `LokiLoggingConfigurationTest` идёт около 100 с (по аудиту).

### Т1. `LokiLoggingConfigurationTest` — 39,6 с

**Проблема.** 28 сценариев, каждый запускает отдельную JVM через `ProcessBuilder`. В тесте есть фиксированные паузы `Thread.sleep(500)`. [Тест](../src/test/java/com/padle/core/padelcoreservice/logging/LokiLoggingConfigurationTest.java)

**Варианты.**
- Два потока только для этого класса, с временными каталогами в `target`. По аудиту это дало −41…58% на Windows; на Linux и в полном `verify` не проверено.
- Заменить паузы после подтверждённой доставки ожиданием события: до −5 с.
- Наблюдение 500 мс при выключенном Loki сохранить.

**Экономия:** **−0:15…−0:25**.
**Трудоёмкость:** средняя.

### Т2. `PlayoffPilotFixtureIntegrationTest` — 27,4 с

**Проблема.** Семь из восьми сценариев вызывают `seed()` напрямую, восьмой — через контроллер. В локальном прогоне с TRACE на подготовку пяти турниров через `seed()` ушло **98,6 из 135,0 с измеренных фаз (73%)**. Весь класс занял **202,8 с**, включая старт Spring. Часть сценариев работает только с одним турниром, например `qualified-8`. [Тест](../src/test/java/com/padle/core/padelcoreservice/preview/PlayoffPilotFixtureIntegrationTest.java)

**Вариант.** Минимальный набор данных для сценариев с одним турниром. Полный набор оставить только для проверок повторяемости, полного сброса и сохранности.

**Экономия:** **−0:08…−0:14**.
**Трудоёмкость:** средняя.

### Т3. `AmericanoScheduleEngineTest` — 16,3 с

**Проблема.** `fullCycleConfigurations…` генерирует по 100 расписаний для пяти конфигураций (8/12/16/20/24 игрока). Затем `reportedConfigurations…` (20, 24) и `smallerCourtConfigurations…` (8, 12, 16) генерируют те же конфигурации повторно, так что каждая считается дважды. [Тест](../src/test/java/com/padle/core/padelcoreservice/service/americano/AmericanoScheduleEngineTest.java)

**Вариант.** Генерировать 100 расписаний один раз на конфигурацию и проверять на них все критерии с прежними порогами. Генерация — чистая работа CPU, поэтому конфигурации можно считать параллельно на 4 vCPU.

**Экономия:** **−0:08** за счёт удаления повтора, до **−0:12** с параллелизмом.
**Трудоёмкость:** малая.

### Т4. Лишние Spring-контексты

**Проблема.** 71 класс с `@SpringBootTest` даёт около 31 уникальной конфигурации контекста, 27 из них используются одним классом. Многие различия косметические:
- `recaptcha.secret-key=test` вместо `test-secret-key`;
- `spring.mail.username=test@example.invalid` вместо `test@example.com`;
- наличие `@AutoConfigureMockMvc` при тех же свойствах: 31 класс без него, 10 с ним.

## Проблемы и варианты: деплой

### Д1. Сжатие пакета gzip уровня 9

**Проблема.** `tarfile.open(archive, 'w:gz')` в [production.py](../automation/releases/production.py) по умолчанию сжимает на уровне 9. `docker save` вместе со сжатием примерно 380 МБ занимает 0:53.

**Вариант.** `compresslevel=1`. Передаваемый объём немного вырастет: JAR и так сжат, сжатие слоёв JRE станет чуть хуже.

**Экономия:** **−0:30…−0:40** (упаковка ~0:10–0:15, передача +0:05…0:10). Тот же выигрыш получает П5 в PR Check.
**Трудоёмкость:** малая.

### Д2. В каждый выпуск передаётся весь образ

**Проблема.** В пакете лежит `docker image save` целиком: базовый JRE (115,5 МБ, одинаковый всегда) и JAR (99 МБ). На сервере пакет распаковывается в Python и загружается через `docker image load`.

**Вариант.**
- Передавать JAR и манифест, а образ собирать на сервере от того же закреплённого digest по Dockerfile из пакета.
- Проверка SHA-256 JAR уже есть (`artifact.verify`). Откат не меняется: прежние образы остаются на сервере.
- Модель доверия меняется: проверяемым артефактом становится JAR вместе с digest базового образа, а не готовый образ.

**Экономия:** **−1:25…−1:40**:
- упаковка −0:55…−1:00;
- передача ~210 → ~99 МБ, −0:25…−0:30;
- активация: распаковка и `docker load` сейчас занимают 0:15 (Д6), сборка образа на сервере от закэшированного базового — оценочно 0:05–0:10, то есть −0:05…−0:10.

Д2 заменяет Д1.
**Трудоёмкость:** средняя.

### Д7. Старт приложения

**Вариант.** Распакованный JAR в образе выпуска. В локальном замере время старта сократилось с 69,2 до 52,1 с (**−25%**). ### Д9. Долгий старт Spring (52,6 с) — профиль JFR

Профиль записан локально 19.11.2026 в тех же условиях, что и замер старта: 2 ядра, профиль `prod`, fat JAR. Под JFR старт занял 55 с, как на сервере.

Куда уходит процессорное время основного потока (доли пересекаются: один стек может попасть в несколько строк):

| Что | Доля |
|---|---:|
| Загрузка классов из вложенного JAR | ~40% |
| Разбор JPQL-запросов парсером ANTLR (111 `@Query` в 20 репозиториях) | ~22% |
| Hibernate | ~20% |
| Прокси CGLIB, ByteBuddy, AOP | ~17% |
| Разбор конфигурационных классов и сканирование | ~16% |
| Liquibase: разбор changelog и контрольные суммы | ~11% |
| Tomcat | ~7% |

- **JIT-компилятор C2 расходует почти столько же процессора, сколько основной поток.** На двух ядрах он отнимает у старта заметную долю.
- **Сборка мусора не узкое место:** 1,6 с пауз за весь старт.
- **Liquibase при каждом старте обращается к своим серверам** `config.liquibase.com` и `config-endpoint.liquibase.com` (аналитика и удалённая конфигурация). Это около 1,5 с сетевых ожиданий и передача сведений о запуске третьей стороне.

Проверенные настройки, без изменения кода (по 2 запуска; 4 контрольных запуска текущего варианта: 56,7–65,2 с, среднее 60,3 с):

| Настройка | Среднее | Эффект |
|---|---:|---:|
| `spring.data.jpa.repositories.bootstrap-mode=lazy` | 51,6 с | **−14%** |
| `-XX:TieredStopAtLevel=1` (только C1) | 47,6 с | **−21%** |
| `bootstrap-mode=deferred` + `spring.task.execution.mode=force` | 60,3 с | нет: оба ядра и так заняты |
| `liquibase.analytics.enabled=false` | 56,1 с | в пределах разброса, ожидаемо ~1,5 с |

Без `spring.task.execution.mode=force` режим `deferred` вообще не запускается: в проекте нет автоконфигурируемого `applicationTaskExecutor`.

**Варианты.**
- **Распакованный JAR (Д7)** бьёт по самой большой доле — загрузке классов.
- **Режим `lazy` для репозиториев: −14%.** Цена: ошибка в JPQL проявится при первом обращении к репозиторию, а не при старте, и первые запросы к каждому репозиторию медленнее. Проверку можно сохранить в CI, оставив тестам обычный режим. Решение за командой.
- **Только C1 — для окружений CI** (preview, репетиция, браузерные тесты), где приложение живёт минуты: −21% старта. Для production не подходит: C2 нужен для пиковой производительности.
- **Отключить обращения Liquibase к его серверам** (`liquibase.analytics.enabled=false`): около −1,5 с и никаких данных третьей стороне.

**Экономия на сервере:** `lazy` — **−0:05…−0:08**, аналитика Liquibase — ~−0:01…−0:02. Совместный эффект с распакованным JAR не замерен (обе меры уменьшают загрузку классов), поэтому в итоговое время не включён.
**Трудоёмкость:** малая (настройки), но `lazy` требует решения.

### Д10. Оценочное окно недоступности во время деплоя (~1 мин)

**Наблюдение.** `docker compose up -d --no-deps padel-app` пересоздаёт единственный контейнер. В исследованном деплое старый контейнер остановился до создания нового (21:44:09), Spring отметил старт в 21:45:06, а smoke завершился в 21:45:16. По хронологии контейнеров оценочное окно недоступности составляет около минуты. Момент, с которого сайт снова отвечал пользователям, нужно подтвердить по логам прокси. При откате возможна аналогичная пауза.

**Вариант.** Сине-зелёное переключение: новый контейнер стартует рядом со старым на другом порту, после smoke прокси переключается на него, старый останавливается. Сначала стоит проверить сам простой по логам прокси или `docker events` за окно деплоя.

**Цель:** сократить подтверждённый период недоступности для пользователей. Время выполнения деплоя измерять отдельно.
**Трудоёмкость:** большая: меняется схема запуска на сервере и откат.

## Проблемы и варианты: автоконвейер

Последние 40 запусков `pipeline-merge` не содержат долгих прогонов: сейчас PR вливают вручную. Пункты ниже имеют смысл, когда используется автомерж.

### А1. Повторная проверка перед мержем повторяет весь PR Check

**Проблема.** Job `verify` в `pipeline-merge` заново запускает PR Check целиком на `refs/pull/N/merge`, даже если master не сдвинулся с момента зелёного PR Check на том же merge-коммите.

**Вариант.** Пропускать `verify`, если база последнего успешного PR Check совпадает с текущим master, а head PR не менялся.

**Экономия:** весь PR Check на каждый такой мерж: **−15:36** сейчас, **−5:55…−6:05** после П1–П10.
**Трудоёмкость:** средняя.

### А2. Деплой пересобирает то, что собрала повторная проверка

**Проблема.** После `verify` деплой заново собирает Maven и пакет.

**Вариант.** Передавать пакет из `verify` в деплой. Сложность в том, что `build.py` требует совпадения ревизии с `HEAD`, а SHA squash-коммита отличается от SHA merge-ref. Нужна идентификация по дереву или перевыпуск манифеста.

**Экономия:** **−0:40…−1:40** (после Д2 — около −0:45).
**Трудоёмкость:** средняя или большая.

## Замер: время старта приложения и CDS

Проведён 19.11.2026 локально (Docker Desktop, 4 ядра), чтобы проверить оценки П10 и Д7.

- JAR собран с `origin/master` `315df3f5` в контейнере `maven:3.9.9-eclipse-temurin-21` командой `package -Dmaven.test.skip=true`.

- **Старт упирается в процессор.** JVM использует 1,9 из 2 ядер (107,5 с CPU за 56 с старта), с CDS процессорного времени на 35% меньше (69,6 с). На 4 ядрах на этой машине старт почти не ускорился (53,5 с), вероятно из-за общей нагрузки хоста.

CDS дал ещё **18% относительно распакованного запуска**, или **9,4 с**. В общую оценку его не включаем из-за дополнительного размера пакета и стоимости тренировочного запуска.
