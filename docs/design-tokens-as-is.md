# Дизайн-токены "as-is" — padel-core-service

> **Назначение:** зафиксировать реальную (а не задуманную) палитру/типографику/отступы приложения перед переносом фронтенда на React. Это не новый дизайн — это аудит существующего CSS, приведённый к одному документу.
> **Методология:** канонический источник — `:root` в `src/main/resources/static/css/style.css` (единственный файл с полноценной системой токенов). Остальные 13 CSS-файлов (12.3k строк суммарно) проверены на соответствие/отклонение от него через grep по хексам и raw-значениям.
> **Как использовать:** этот документ — прямой вход для конфига дизайн-системы в React (Tailwind theme / CSS custom properties — один в один, без интерпретации). Также — сопроводительный материал к скриншотам/Figma-фреймам из `html.to.design`, чтобы при переносе не тащить старый "бардак" дальше как будто он и есть дизайн.

## 2. Где реальность расходится с каноном

### 2.1. `admin.css` — параллельная копия той же палитры под другими именами

`admin.css` объявляет собственный `:root` с 12 переменными (`--admin-primary`, `--admin-secondary`, …) вместо переиспользования `--color-*`. Использует свои `--admin-*` 170 раз, `--color-*` — **ни разу**. Значения почти везде идентичны каноническим:

| `--admin-*` (admin.css) | Значение | Совпадает с |
|---|---|---|
| `--admin-primary` | `#FF6B35` | `--color-primary` (точное совпадение) |
| `--admin-secondary` | `#7B2CBF` | `--color-secondary` (точное совпадение) |
| `--admin-success` | `#10b981` | `--color-success` (точное совпадение) |
| `--admin-danger` | `#ef4444` | `--color-error` (точное совпадение, другое имя) |
| `--admin-warning` | `#f59e0b` | `--color-warning` (точное совпадение) |
| `--admin-info` | `#3b82f6` | `--color-info` (точное совпадение) |

**Вывод:** это не два разных дизайна, это один и тот же дизайн, случайно продублированный под вторым набором имён. При переносе в React — один набор токенов на всё приложение, `--admin-*` не переносится вообще.

### 2.2. "Почти-дубликаты" — тот же цвет, чуть другое число

`#E54B2B`/`#e55a2b` (задумывался как `--color-primary-dark`) и `#FF8C5A`/`#ff8255` (задумывался как `--color-primary-light`) встречаются как **раздельные, чуть отличающиеся хексы** в 5+ файлах (`admin-forms.css:143`, `admin.css:348`, `admin_details_style_fix.css:63`, `americano.css:584,647`, `cookie-consent.css:96`, `admin.css:24,30,300,307` — включая внутри `linear-gradient()`). Похоже на то, что кто-то на глаз подбирал "чуть темнее/светлее оранжевый" вместо того, чтобы взять готовую переменную — итог: три разных оттенка "primary-dark" сосуществуют в приложении одновременно, визуально почти неотличимые, но не идентичные.

### 2.3. Совсем посторонние цвета (не часть палитры вообще)

Топ по частоте среди цветов, которых нет в каноне: `#6366f1` (индиго), `#dc3545`/`#28a745` (Bootstrap-дефолты — красный/зелёный, встречаются в `admin.css`, `dashboard.css`, `payment-management.css`, `style.css`, `tournament-details.css`), `#ffd700` (золотой), `#2563eb`, `#d97706`. Похоже на копипаст из Bootstrap-примеров или сторонних сниппетов на разных этапах разработки, без сверки с уже существующей палитрой.

### 2.4. Border-radius — та же картина: 5-шаговая шкала существует, но игнорируется

В каноне 5 значений (6/8/16/24px + full). По факту в CSS встречается **14 разных сырых значений** (`4px, 6px, 8px, 10px, 12px, 16px, 20px, 24px, 30px, 40px, 100px, 0.5rem, 1rem, 2rem` — с разным числом употреблений, топ — `8px` 43 раза и `12px` 30 раз, которых в шкале вообще нет).

### 2.5. Файлы с нулевым использованием токенов (write вообще не смотрели на style.css)

`americano.css`, `cookie-consent.css`, `payment-management.css`, `admin_details_style_fix.css` — **0** обращений к `var(--color-*)` или `var(--admin-*)`, только сырые значения. Это самые "молодые" по всей видимости фичи (Americano, Cookie-consent, Payment management) — писались отдельно от исходной системы `style.css`, без импорта переменных.

## 3. Рекомендация для React-переноса

1. **Один источник токенов**, не два — `--admin-*` из `admin.css` не переносится, все ссылки на него меняются на канонический `--color-*`/`--admin-danger`→`--color-error` и т.д. (таблица в §2.1 — прямой маппинг).
2. **Схлопнуть "почти-дубликаты"** (§2.2) в единственный канонический hex — при рендере в Figma через `html.to.design` эти отличия всё равно будут видны на скриншотах как еле заметная рассинхронизация оттенка; в React их не должно быть вообще.
3. **Посторонние цвета (§2.3)** — решить по каждому: либо это осознанный семантический цвет для конкретной фичи (тогда — завести как новый именованный токен, не разово), либо случайность (тогда — заменить на ближайший канонический).
4. **Border-radius** — свести 14 сырых значений к существующей 5-шаговой шкале (§2.4); почти наверняка `8px`→`--border-radius-md`, `12px`/`16px`→`--border-radius-lg`, `20px`/`24px`→`--border-radius-xl` покрывают большинство случаев без визуальной потери.
5. Прямое переиспользование в React: этот документ ложится 1:1 либо в `tailwind.config.js` (`theme.colors`, `theme.spacing`, `theme.borderRadius`, `theme.boxShadow`), либо в общий файл CSS custom properties, если решите не использовать Tailwind — в обоих случаях выбор технологии React-стилизации не блокирует использование этого документа.

## 4. Что дальше

Токены зафиксированы — можно параллельно:
- прогонять реальные страницы через `html.to.design` (Figma-плагин) для захвата разметки "as-is";
- при чистке фреймов в Figma сверяться с этим документом, чтобы явно видеть, где скриншот показывает "дрейф" (§2.2-2.4) — тогда в React-версии сознательно берётся канонический токен, а не то, что оказалось на конкретном скриншоте.
