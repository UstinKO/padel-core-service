# Какие серверы нужны первому клубу

**Предложение для заказчика от 27 ноября 2026 года.** Для пилота берём три ВМ у независимых провайдеров, суммарно **8 vCPU и около 16 GiB оперативной памяти по классу тарифов**. Самую большую машину отдаём двум JVM и Redis. В смету входят сбор метрик и логов, интеграции и пилот gRPC. Это стартовая конфигурация для испытания одного клуба. Производственный пик и время ответа пяти выделенных сервисов предстоит измерить. [Утверждённая карта сервисов](architecture-map.md)

## Что арендуем

| Площадка | ВМ и SSD | Что на ней работает | Аренда, USD/мес. |
|---|---|---|---:|
| A | 2 vCPU, класс 4 GiB, действующий диск 291 GiB | Управление турнирами и интеграции | 20,00 по текущей аренде |
| B | 4 vCore, 8 GB, 75 GB NVMe | Аккаунты, расчёт Elo и возможный Redis | от 8,50 |
| C | 2 vCPU, 4 GiB, 80 GiB SSD | Prometheus, Loki, Grafana и оповещение | 24,00 |
| **Три площадки** | **8 виртуальных CPU** | **На каждой также два шлюза, журнал SQLite и узел PostgreSQL** | **от 52,50** |

A подходит по цене, если её провайдер независим от B и C. Для B пример — OVHcloud VPS-2, для C — DigitalOcean Basic Regular. OVHcloud указывает десятичные единицы: 8 GB ≈ 7,45 GiB и 75 GB ≈ 69,85 GiB. Нижняя цена зависит от региона, срока, налогов и доступности. При B за $16 три ВМ стоят $60. Остаток до серверного потолка $70 составляет $10–17,50. [Тариф OVHcloud](https://us.ovhcloud.com/vps/os/vps-linux/) · [Тариф DigitalOcean](https://www.digitalocean.com/pricing/droplets)

**Полный плановый счёт — $68,25–75,75 в месяц** при аренде $52,50–60, внешнем входе $8,75, копиях $2 и резерве на трафик и прочие расходы $5. В примере внешние HTTPS-проверки следят за публичным чтением на трёх площадках. Шлюз проверяет приём событий и бизнес-запись отдельно. Девять платных внешних HTTPS-проверок вместо трёх добавили бы $16,50. Тарифы SMTP и других внешних API, платные наблюдения сверх этих строк, оборудование клуба и работа дежурного требуют отдельной оценки. Если $70 — предел всех ежемесячных расходов с указанными резервами, на B остаётся не более $10,25. При закупке сверить регионы, доступность из Аргентины, счёт за исходящий трафик и итог с налогами. [Состав сметы](README.md#бюджет-за-месяц) · [Цена проверок Route 53](https://aws.amazon.com/route53/pricing/)

**В клубе** предлагаем два имеющихся устройства с независимыми SSD и питанием, каждое с 4 логическими CPU, 8 GiB RAM и **20 GiB свободного места**. Одинаковый класс позволяет проверить замену судейского устройства после безопасной передачи полномочий и восстановления двух копий. На активном работают локальные №1 и №2, интерфейс и движок Java 25. Для движка отдельно закладываем 0,25–1 vCPU и 384–640 MiB, на втором штатно работает №2. Нужны исправная LAN, резерв питания для сети и проверенный исходящий канал от 10 Мбит/с для догрузки. Судья подтверждает счёт по двум долговечным записям даже без интернета.

## Сколько выделить каждому сервису

В каждой паре **первое значение — резерв для планирования, второе — бюджет пика одного экземпляра на стенде**. RAM охватывает процесс целиком, включая память JVM вне heap, TLS и сетевые буферы. CPU в долях vCPU. Процессы могут кратковременно делить свободный CPU, сумму всех пиков CPU одновременно ВМ не гарантирует. Окончательные ограничения контейнеров выставляются после замеров при совместной нагрузке.

| Сервис | Облачные экземпляры | CPU, резерв / пик | RAM, MiB, резерв / пик | Что входит |
|---|---|---:|---:|---|
| №1. API Gateway и оркестратор · Go | 2 на каждой ВМ, всего 6 | 0,10 / 0,35 | 96 / 160 | HTTP, JWT, WebSocket, TLS, маршрутизация и потоки gRPC |
| №2. Протокол и табло · Go | 1 на каждой ВМ, всего 3 | 0,20 / 0,55 | 192 / 320 | Один писатель SQLite, WAL, квитанции, снимки, архив и догоняющая доставка |
| №3. Аккаунты · Java 25 | 1 на B | 0,30 / 1,00 | 512 / 768 | Spring Security, веб-сессии, Google OAuth и проверка регистрации |
| №4. Управление турнирами · Java 25 | 1 на A | 0,45 / 1,20 | 768 / 1 024 | Заявки, оплаты, чеки, подготовка пакета и фоновые интеграции |
| №5. Результаты и Elo · Kotlin/JVM 25 | 1 на B | 0,25 / 1,00 | 512 / 768 | Один активный импорт, проверка архива, расчёт и публикация среза |

**При потере двух провайдеров** оставшаяся ВМ принимает журнал и обслуживает зрителей по последнему доступному снимку. Проведение остаётся в клубе. Для нового официального Elo требуются три совпадающих квитанции за архив. Облачная заявка или оплата может ждать восстановления строгой записи PostgreSQL. Такой режим не требует запускать все пять сервисов на одной оставшейся ВМ. [Границы доступности](README.md#что-означает-гарантия)

## База, мониторинг и запас на машине

| Компонент | Где и сколько | CPU, резерв / пик | RAM, MiB, резерв / пик |
|---|---|---:|---:|
| ОС, Docker/Swarm, Nginx/TLS, сборщик логов и метрик узла | По одному комплекту на A/B/C | 0,20 / 0,40 | 512 / 704 |
| PostgreSQL 15 | 1 на каждой ВМ, общий primary и два standby | 0,35 / 0,95 | 448 / 640 |
| Управление ролью БД и локальный DB proxy | Бюджет на каждом узле под кандидат Patroni/etcd и proxy | 0,10 / 0,30 | 128 / 256 |
| Архивация WAL и резервное копирование | Бюджет на каждом узле, тяжёлые копии по очереди | 0,05 / 0,25 | 64 / 128 |
| Redis для веб-сессий и общих квот | 1 на B в этом варианте пилота | 0,10 / 0,30 | 96 / 192 |
| Prometheus | 1 на C | 0,15 / 0,45 | 192 / 384 |
| Loki | 1 на C | 0,15 / 0,50 | 192 / 384 |
| Grafana и доставка оповещений | 1 комплект на C | 0,10 / 0,30 | 128 / 256 |

| Узел | Суммарный резерв CPU | RAM, резерв / сумма пиков, MiB | Свободно при сумме пиков относительно указанной ёмкости |
|---|---:|---:|---:|
| A | 1,55 из 2 | 2 304 / 3 392 | 519 MiB из фактически видимых 3 911 |
| B | 1,75 из 4 | 2 656 / 4 096 | около 3 533 MiB из 8 GB до системных вычетов |
| C | 1,50 из 2 | 2 048 / 3 392 | 704 MiB из 4 GiB до системных вычетов |

На каждом узле общая часть вместе с двумя №1 и одним №2 составляет 1,10 vCPU и 1 536 / 2 368 MiB. Суммы выше относятся к целевой системе. У A самый узкий запас: при сумме пиков до порога в 512 MiB остаются лишь 7 MiB сверху. **В теневом периоде старая JVM добавляет около 734 MiB уже в спокойном состоянии**: 3 392 + 734 > 3 911, ещё до учёта второй БД, runner и соседней автоматизации. Для одновременного прогона держать копию площадки A на отдельной временной ВМ у того же провайдера. При ставке $20 за полный месяц наложения серверы обойдутся в $72,50–80, длительность и тарификацию короткого окна подтвердить отдельно. Для постоянного использования нынешней A сначала инвентаризировать соседние процессы и доказать запас на пике. Если они остаются и запас не проходит, запросить цену A класса 8 GiB.

Redis учтён один раз. У прикладного набора сессий предлагаем начальный предел 64 MiB, у процесса до 192 MiB с накладными расходами. При потере B облачные сессии могут потребовать повторного входа, защищённые операции ждут проверки, клуб продолжает ввод. Spring Session JDBC убирает строку Redis, но переносит записи, очистку TTL и часть задержки в облачный PostgreSQL. Решение принимаем после сравнения. Пулы БД для испытания: №3 до 8 соединений, №4 до 12, №5 до 4; сумма 24 на штатные экземпляры. При повторном запуске, миграции и восстановлении отдельно проверить служебные подключения, WAL, блокировки и общий бюджет. [Сравнение хранилищ сессий](pilot-checks.md#проверки-после-ревью)

## Из чего получены цифры

В эксплуатационном срезе **19 ноября 2026 года** у монолита были 2 vCPU и 3 911 MiB RAM. Контейнер приложения занимал 734,1 MiB при максимальном heap 512 MiB. PostgreSQL занимал 62,8 MiB, Prometheus 73,45 MiB, Loki 65,37 MiB, Grafana 56,52 MiB. База содержала около 20 MB, том Prometheus — 2,2 GiB, логи приложения — 2,1 GiB. Отправка в Loki у приложения была выключена. Локальный расчёт 25 600 матчей занял 10,44 мс по медиане на ARM64 без SQL и загрузки архива. Это основания для первого прогона. Пиковое потребление пяти независимых сервисов ещё не измерено. [Инвентаризация ВМ](../swarm/README.md#реестр-подтверждённых-фактов) · [Условия замера Elo](service-boundaries.md#сколько-стоит-один-пересчёт)

**Исходный профиль для испытания** — один клуб, до 8 одновременно играющих кортов, 300 зрителей с WebSocket, 2 принятых изменения счёта в секунду суммарно, до 5 входов и 5 заявок/оплат в секунду в коротком пике, одновременно один пересчёт Elo. Это предложенная нагрузка, которую заказчик сверяет с расписанием и аудиторией. Веб, iOS и Android делят эти 300 подключений и один API. Перед допуском берём больший из этого профиля и наблюдаемого пика клиента.

## Метрики, интеграции и связь

- **Метрики и логи.** Сохраняем Micrometer/Actuator, метрики Go и хостов, Prometheus, Grafana, Loki и оповещения. Опрос каждой реплики раз в 10 с и хранение метрик 30 дней соответствуют настройкам приложения. Для примера, 10 000 активных рядов на весь стенд дают 1 000 отсчётов/с. При 1–2 байтах на отсчёт блоки за 30 дней займут около 2,4–4,8 GiB плюс WAL, индексы и временное место. На C выделяем 10 GiB для Prometheus и 8 GiB для Loki при пробном объёме до 0,2 GiB сохранённых логов/сутки за 30 дней. Под нагрузкой включаем реальную доставку в Loki, измеряем заполнение буфера и возраст последней метрики. При потере C внешний монитор продолжает проверять публичный вход и оповещать дежурного, на живых узлах сохраняются локальные логи с ограниченной очередью. Историю мониторинга восстанавливаем из внешней копии, интервал пропуска сбора измеряем отдельно. [Настройки опроса](../../prometheus.yml) · [Хранение в Compose](../../docker-compose.yml) · [Оценка места Prometheus](https://prometheus.io/docs/prometheus/latest/storage/)
- **Интеграции.** В бюджете №3 зарезервировать 0,10 vCPU и 64 MiB из указанного объёма под Google OAuth и регистрацию с reCAPTCHA. В №4 — 0,15 vCPU и 128 MiB под Brevo SMTP, Telegram, напоминания, файлы чеков и Meta CAPI. GA4 и Meta Pixel работают в браузере, серверные события и обращения за контекстом входят в нагрузку №4. Резервы входят в таблицу сервисов. Начать с двух одновременных внешних отправок и двух файлов до 5 MiB на процесс, проверить таймауты провайдеров, повторы и заполнение outbox. Тяжёлая отправка выполняется после бизнес-транзакции. У бота один активный читатель. Размер вложений и возраст очереди нужны также для расчёта диска и WAL. Для испытаний использовать тестовые адресаты и режимы интеграций. [Чеки](../endpoints/payment-receipts.md) · [Каналы Meta](../endpoints/meta-marketing.md) · [Метрики почты](../architecture.md#кастомные-email)
- **gRPC.** Клуб поддерживает три независимых двунаправленных потока HTTP/2 с mTLS, по одному к каждой площадке. Предложенное ограничение полезных данных в полёте — 1 MiB на поток. Дополнительную память на TLS, сериализацию и буферы учитываем внутри №1 и №2. При двух событиях по 2 KiB в секунду три копии требуют около 0,10 Мбит/с до заголовков и повторов. После 6 часов без связи накопится около 84 MiB полезных данных для каждой площадки. При общем ограничении догрузки 5 Мбит/с передача трёх копий займёт теоретически от 7 минут плюс новые события и накладные расходы. Сравнить с пакетным HTTPS при одинаковом окне и проверить время ответа судье. Полный архив и готовый срез передаются по HTTPS. [Испытание транспорта](data-and-contracts.md#оценка-потокового-grpc-для-турнирного-дня) · [Управление потоком gRPC](https://grpc.io/docs/guides/flow-control/)
- **Канал зрителей.** Для прогона задаём периодическую сверку версии раз в 15 с и полный снимок 24 KiB. Если после каждого сигнала все подписчики корта читают снимок, равномерная аудитория создаст около 95 GET/с с учётом периодической сверки. На финале со всеми зрителями на одном корте и двумя изменениями в секунду — до 620 GET/с. При передаче полного снимка на каждый запрос это до 19 и 122 Мбит/с полезных данных соответственно. Условное чтение неизменившейся версии сокращает расход. При десяти четырёхчасовых турнирах в месяц 19 Мбит/с в течение игры дали бы около 342 GB исходящего трафика без архивов и WAL. Проверить **200 Мбит/с полезной исходящей полосы на каждой облачной ВМ** как ориентир стенда с запасом на TLS, WAL и догрузку, включая путь к зрителям в Аргентине. Подставить фактические размер снимка, частоту и одновременные подписки перед заказом тарифа.

## Диски и критерии приёмки

Бюджет каждой чистой ВМ в GiB: ОС, образы и предыдущий выпуск — 12, PostgreSQL с WAL — 10, SQLite с архивами и очередью — 6, локальные логи и буферы — 3, временная копия и восстановление — 5. Всего **36 GiB** на площадку. На B добавляем 1 GiB для Redis, на C — 10 GiB Prometheus, 8 GiB Loki и 1 GiB Grafana и оповещений. Получаем **A 36, B 37, C 55 GiB** занятого места. Для сохранения 20% свободного места на чистых узлах нужны соответственно 45, 47 и 69 GiB usable SSD с округлением вверх. На A из 291 GiB в исходном срезе было занято 165 GiB. Сверить доступное место после размещения образов, копий и журналов. Внешние защищённые архивы и резервные копии считают отдельно по сроку хранения. Даже 1 000 чеков по 5 MiB — ещё около 4,9 GiB полезных файлов до WAL, реплик и копий. При росте увеличить объём хранения до заполнения и согласовать сроки. [Сохранение данных и восстановление](../swarm/data-recovery.md)

| Когда проверяем | Что измеряем | Условие для решения о железе |
|---|---|---|
| Обычная игра, пик входов и финал на одной уцелевшей площадке | Полный путь от нажатия до экрана, p95/p99, ошибки, одновременные WS, исходящий трафик, CPU/steal и время синхронной записи SSD | Счёт ≤200/400 мс, следующий раунд ≤300/600 мс, чтение ≤250/500 мс и результат не хуже текущей версии на тех же условиях. Проверить отказы A+B, A+C, B+C по отдельности. На дисках клуба измерить p99 фиксации при двух записях и фоновом чтении. Для локального табло проверить p95/p99 ≤500 мс/1 с. |
| Запущены Elo, мониторинг, резервное копирование и догрузка одновременно | Постоянный RSS и пик при старте каждой JVM, MemAvailable, CPU, I/O, очередь WAL, HTTP и SQL пулы, отставание каждого outbox и gRPC-канала | Ориентиры пилота: CPU ≤80% за устойчивую пиковую нагрузку, доступно ≥512 MiB RAM на каждом узле, свободно ≥20% диска, без OOM и устойчивого роста очередей при здоровых получателях. При потере внешнего API судейская запись сохраняет тот же p95/p99. |
| Отключение сети клуба, диска или провайдера, возврат primary | Хеши двух клубных копий, три квитанции за архив, восстановление оплат и всех строк Elo, внешний сигнал мониторинга и восстановление сбора | Ноль потерянных и задвоенных принятых результатов. Одна облачная площадка читает свой снимок и принимает события. Оплата при строгой записи ждёт зависимостей. После восстановления результат и рейтинг совпадают с эталоном. |

Для решения о закупке заказчик подтверждает число одновременных клубов, кортов и зрителей, длительность отключения, объём чеков и срок хранения. Команда прикладывает реальные пики, стоимость региона и результат каждого прогона. При упоре в прикладную память на A сначала пересчитать класс RAM, при росте WAL и логов — диски, при задержке массового чтения — канал и размер снимка. Официальное переключение проходит после проверки скорости и сохранности. [Протокол команды](pilot-checks.md) · [Лист заказчика](customer-agreement.md)
