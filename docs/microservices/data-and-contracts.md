# Пять сервисов пилота, их данные и связь

**Владелец согласовал пять сервисов, их языки и работу без RabbitMQ и Kafka.** Шлюз и турнирный протокол используют Go, аккаунты и управление турнирами — Java 25, результаты и рейтинг Elo — Kotlin/JVM на Java 25. У каждого сервиса свой выпуск. Экземпляры в клубе, реплики в Swarm и библиотека расчёта раундов в это число входят как части соответствующих сервисов. Ниже — предлагаемый стек и решения для проверки на стенде. Действующая система остаётся источником официальных результатов до приёмки. ## Почему Kotlin подходит сервису результатов

**Целевая платформа JVM — Java 25.** Для аккаунтов и управления турнирами выбираем Java 25. Для результатов выбран Kotlin/JVM с целевой версией байткода 25. Для клубного пакета движков также предусматривается совместимая среда Java 25. В действующем монолите Maven пока задаёт Java 17, CI и Docker используют 21. При выделении сервиса согласовать в его сборке JDK 25, Java `--release 25`, Kotlin `jvmTarget=25` и JVM 25 в образе. Компилятор Kotlin поддерживает эту цель начиная с 2.3.0. Версию плагина и библиотек Kotlin закрепить согласованно с версией Spring Boot в Maven. [Текущая сборка](../../pom.xml) · [CI](../../.github/workflows/pr-check.yml) · [Контейнер](../../Dockerfile) · [Поддержка Java 25 в Kotlin](https://kotlinlang.org/docs/whatsnew23.html#kotlin-jvm-support-for-java-25)

| Кандидат | Что означает выбор Kotlin |
|---|---|
| **№ 3. Аккаунты и вход** | Spring Security поддерживает Kotlin. Основная работа при выделении — сохранить поведение действующих сессий, OAuth, восстановления доступа и токенов. Уже написанные Java-обработчики можно перенести на новую платформу без смены языка. |
| **№ 4. Управление турнирами** | Здесь больше всего существующего кода заявок и связанных транзакций. Перевод на Kotlin одновременно с выделением процесса расширил бы объём проверки очереди, оплат и прав. Для пилота берём существующую реализацию на Java. |
| **№ 5. Результаты и рейтинг** | Приём архива, обработку повторов и публикацию предстоит написать. В Kotlin обязательные поля и типы вариантов результата позволяют явно представить принятие, повтор и конфликт архива. Эту работу можно проверить на завершённых турнирах независимо от интерфейса судьи. |

В № 5 Kotlin отвечает за новый код обработчика. Для существующего Java-расчёта выделяем вызываемый из Kotlin интерфейс и типы входа и результата в одной JVM. Сейчас класс расчёта имеет пакетную видимость. До переключения сравниваем **все строки и порядок Elo** с прежней реализацией на тех же архивах, включая исправление задним числом и повтор доставки. Для пилота достаточно Spring Boot, JDBC и ограниченного числа фоновых заданий. Выбор Kotlin не закладывает ускорения расчёта или дополнительных серверов. ## Что общее в PostgreSQL

Для пилота — **один кластер PostgreSQL, одна логическая база, три схемы**. На A, B и C размещаем по экземпляру с отдельным диском. В штатном режиме у кластера один пишущий primary и две потоковые реплики. Каждому из сервисов № 3–5 выдаём свою прикладную роль, отдельный пул соединений и миграции своей схемы. Роль миграции отделена от прикладной. Права и `search_path` ограничивают доступ к чужим таблицам. № 1 и № 2 не получают учётных данных PostgreSQL. Размещаем пилот на трёх предусмотренных сметой ВМ. Достаточность памяти, IOPS и скорости репликации предстоит измерить. [Схемы и привилегии PostgreSQL](https://www.postgresql.org/docs/15/ddl-schemas.html) · [Бюджет трёх площадок](README.md#бюджет-за-месяц)

В целевой схеме сервис читает чужие данные через API владельца или свою локальную копию разрешённых полей, обновляемую событиями. Для перехода существующие связанные таблицы и объединение гостя с аккаунтом сохраняют одного транзакционного владельца до сверки старых ID, связей и истории Elo. Миграция идёт по одной операции, с единственным писателем. Событие о создании аккаунта связывается со спортивным профилем по стабильному ID. Повторная доставка не создаёт второго игрока. Во время перехода обязательные проверки контакта и уровня при записи продолжают работать. [Правила продукта](../../specs/MASTER.md) · [Переход данных профиля](service-boundaries.md)

**Предложение по долговечности облачных операций.** Для подтверждения долговечных изменений аккаунта, заявки, оплаты и официальной версии рейтинга на стенде выбрать фиксацию WAL на primary и обеих репликах (`synchronous_commit=on`, два обязательных standby). Успешный ответ ждёт более медленную площадку. При недоступности одной из трёх новая такая операция может остаться без подтверждения. Потеря ответа означает, что клиент сверяет статус по ID, прежде чем повторять команду. Повышение standby требует кворума управления 2 из 3 и изоляции прежнего писателя. После смены primary сохраняется требование двух других долговечных копий. Длительность межпровайдерской записи и доступность облачной регистрации проверяем отдельно от судейского пути. Если это ухудшает действующие p95/p99, конфигурация не проходит приёмку. [Подтверждение записи PostgreSQL](https://www.postgresql.org/docs/15/warm-standby.html#SYNCHRONOUS-REPLICATION)

## Какие вызовы синхронные, какие фоновые

**Пользовательские команды и чтение используют HTTPS/JSON и OpenAPI, табло получает сигналы по WebSocket.** Для фоновой доставки событий из клуба в A/B/C согласован пилот gRPC/Protobuf поверх HTTP/2. Пакетный HTTPS/JSON служит базой сравнения и вариантом возврата. Короткое задание на импорт, загрузка полного архива и публикация целого среза обслуживаются по HTTPS. Внутренние вызовы проходят по маршрутам оркестратора с взаимной аутентификацией и ограничением времени ожидания. Запущенная в фоне операция продвигается отправителем из устойчивой очереди независимо от того, открыт ли клиент у пользователя.

| Сценарий | Кто кому и по какому каналу передаёт данные | Чего ждёт инициатор |
|---|---|---|
| Вход, заявка или оплата | Клиент → № 1 → № 3 для входа или № 4 для заявки и оплаты. Синхронный HTTPS/JSON. Известный действующий access-токен шлюз проверяет локально. Для cookie-сессии сохраняются серверная проверка, CSRF и OAuth callback. | Результата входа либо фиксации бизнес-транзакции. После таймаута изменяющей команды состояние проверяется по ID. |
| Ввод счёта и следующий раунд | Судья → клубный № 1. Шлюз синхронно вызывает Java-движок по HTTP/JSON на loopback, затем экземпляры № 2 в клубе. Между устройствами — HTTPS/JSON по LAN. | После записи события на двух независимых дисках и фиксации квитанции на первом устройстве возвращается принятая версия. Облачная сеть, Elo и брокер в это время не нужны. |
| Доставка протокола в облако | № 1 возобновляет задания локального № 2. В пилоте события идут по отдельному двунаправленному gRPC-потоку к каждой из A/B/C. Для контрольного прогона используется пакетный HTTPS POST. Полный финальный архив передаётся по HTTPS с проверкой длины и хеша. | Отправитель отмечает доставку конкретной площадке после её долговечной квитанции. Задержка площадки не задерживает судью и две другие доставки. |
| Импорт финала | После трёх квитанций за одинаковый полный архив № 1 передаёт № 5 его ID, версию, хеш и ссылку служебным HTTPS POST. № 5 читает неизменяемый архив у № 2 по HTTPS частями и сверяет полную длину и хеш. Это одиночная передача по известной версии, как и доставка готового среза. Для постановки самого задания достаточно короткого запроса и ID. | Для нового задания № 5 возвращает `202 Accepted` с ID после устойчивой записи в `rating`. Затем фоновый обработчик выполняет импорт и расчёт. Готовность видна по опубликованной версии. [Семантика HTTP 202](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3) |
| Публикация Elo | № 5 одной транзакцией фиксирует обработку архива, новую версию и задания на распространение. Через маршруты № 1 фоновые HTTPS-вызовы доставляют подписанный срез каждому облачному № 2. | Каждая площадка переключает чтение только после проверки и фиксации целого среза. До этого зрители видят предыдущую полную версию. |
| Чтение табло и рейтинга | Зритель → № 1 → местный № 2. Синхронный HTTPS GET возвращает срез с версией. WebSocket сообщает о новой версии табло. При открытом соединении клиент периодически сверяет версию с №2 через №1 по HTTPS. При отставании или переподключении получает целый актуальный снимок. Интервал сверки подбираем по задержке обновления и трафику на пилоте. | Отрисовки уже готовой версии. Закрытые представления проходят проверку аудитории и используют `private, no-store`. |
| Создание аккаунта и привязка профиля | После создания аккаунта № 3 пишет событие и в фоне доставляет его через № 1 в № 4 по HTTPS. | № 4 фиксирует связь по стабильному ID один раз. Операции, которым нужен готовый профиль, проверяют состояние привязки. |

**Устойчивость фоновой доставки.** Владелец записывает изменение и задание на отправку в одной транзакции своей SQLite или PostgreSQL (outbox). Фоновый отправитель забирает задания ограниченными порциями. Успех отмечается после долговечного ответа адресата, при перезапуске незаконченные задания снова доступны. Получатель в одной транзакции фиксирует ID входящего события (inbox) и результат или задание. Таким образом, доставка идёт **как минимум один раз**, а повтор той же операции не начисляет очки дважды. Для одного турнира проверяются версия и хеш. Пропуск версии ждёт догрузки, расхождение хеша блокирует публикацию. Временные ошибки повторяются с нарастающей паузой. Ключ операции сохраняется между попытками, а ID трассировки служит для диагностики.

### Оценка потокового gRPC для турнирного дня

**Решение владельца — включить двунаправленный gRPC в пилот фоновой репликации событий из клуба в A, B и C.** Во время игры образуется последовательность изменений одного турнира, а после обрыва нужно доставить накопившиеся события. Один поток HTTP/2 на доступную площадку позволяет передавать несколько событий до прихода первой квитанции и получать подтверждения по мере записи. Библиотеки Go поддерживают такую модель, дополнительная ВМ не нужна. Появляется второй контракт (`.proto`), который надо версионировать, проверять на совместимость и пропускать через внутренний шлюз с mTLS и HTTP/2. Открытый поток закреплён за выбранным экземпляром до переподключения. [Модель RPC](https://grpc.io/docs/what-is-grpc/core-concepts/) · [Рекомендации по производительности](https://grpc.io/docs/guides/performance/) · [Пропуск gRPC через Nginx](https://nginx.org/en/docs/http/ngx_http_grpc_module.html)

| Аргумент | Что получаем на нашем маршруте |
|---|---|
| Система запускает задания сама | Сразу после двух локальных записей судья может продолжать матч. Прогресс обеспечивают устойчивое задание и отдельный отправитель. Асинхронный клиент gRPC может одновременно обслуживать доступные площадки. При перезапуске задания восстанавливаются из БД. |
| Поток ускорит обмен | Потенциальный выигрыш максимален при накопившейся очереди. Для иллюстрации возьмём 96 событий и RTT 50 мс до одной площадки. При отправке строго по одному с ожиданием каждой квитанции сетевые ожидания составят 4,8 с. Шестью группами по 16 с ожиданием после каждой группы — 0,3 с. Это расчёт для прогретого соединения без учёта передачи байтов и записи на диск. Пакетный HTTPS может получить ту же экономию RTT. На редких одиночных событиях выгода от потока может оказаться малой. |
| Фон не повлияет на скорость приложения | Отправка убрана из времени ожидания ответа судье, но фон потребляет CPU, читает локальный диск и занимает исходящий канал клуба. Например, отправка архива 5 MiB на три площадки через общий канал 10 Мбит/с занимает как минимум 12,6 с без накладных расходов. Обычный ввод счёта в этот момент должен укладываться в прежние p95/p99. Время работы формулы Elo и фиксации PostgreSQL измеряется отдельно от сетевой доставки. |

**Как восстановить поток.** № 1 управляет отправкой из outbox сервиса № 2. На каждую площадку ведётся независимая позиция по турниру и полномочию писателя. Получатель проверяет ID, номер и хеш, сохраняет событие и обновляет позицию в одной транзакции. Он отвечает квитанцией с последним непрерывно записанным номером и его хешем после устойчивого commit. Вызов записи в gRPC может завершиться уже при передаче сообщения библиотеке. Только прикладная квитанция разрешает отправителю отметить доставку. После обрыва или перезапуска отправитель сверяет позицию с получателем и повторяет неподтверждённый хвост. Дубль не изменяет счёт, пропуск запрашивается заново, конфликт хешей останавливает применение этой истории. Номер последнего события и квитанция за целиком проверенный финальный архив учитываются раздельно. Официальная публикация по-прежнему ждёт три квитанции за один и тот же полный архив. [Управление потоком](https://grpc.io/docs/guides/flow-control/) · [Повторы RPC](https://grpc.io/docs/guides/retry/)

Protobuf служит конвертом для доставки. Внутри передаются исходные подписанные байты события или ссылка на неизменяемый архив с хешем. Проверяем хеш этих байтов. Повторная сериализация структуры в Go или Kotlin может дать другое представление. [Сериализация Protobuf](https://protobuf.dev/programming-guides/serialization-not-canonical/)

**Как сохранить отзывчивость.** Отдельно для каждой площадки ограничиваем число неподтверждённых событий, объём в памяти и скорость отправки. При замедлении адресата остаток хранит outbox на диске. Ввод судьи получает приоритет доступа к локальному журналу, а загрузка больших архивов уступает текущим событиям. Для каждого подключения задаются окно ожидания прогресса и переподключение с растущей паузой и случайной задержкой. Зависание B не должно занять ресурсы отправки в A и C. Фоновый Kotlin-обработчик Elo использует собственные лимиты CPU и пула БД. [Ограничение времени RPC](https://grpc.io/docs/guides/deadlines/)

**Сравнение на трёх ВМ.** Вариант A — пакетный HTTPS/JSON с повторным использованием соединения. Вариант B — gRPC/Protobuf с двунаправленным потоком и ограниченным окном. Использовать одинаковые подписанные события, область подтверждения на диске, окно, лимиты CPU и сети, условия TCP/TLS и политику сжатия. Прогнать редкий живой ввод, догоняющую очередь, медленную площадку и обрыв после commit до доставки квитанции. На одних и тех же устройствах проверить время от нажатия до принятого счёта (p95/p99), отставание каждой площадки, время до трёх квитанций, байты, CPU, память и дисковое ожидание. Повторить при отказе каждой пары провайдеров и сравнить все результаты Elo. Потоковый gRPC стоит выбрать для рабочего маршрута, если он воспроизводимо сокращает догоняющую доставку либо расход ресурсов, сохраняет скорость судьи в пределах целей **и не хуже действующего приложения**, а каждый подтверждённый счёт восстанавливается ровно один раз. При сопоставимых результатах рабочим вариантом остаётся пакетный HTTPS. Перед сменой транспорта отправитель сверяет непрерывную позицию площадки и возобновляет доставку с теми же ID и хешами. Сравнительных измерений на клубном оборудовании и у трёх провайдеров пока нет. [Цели и эталон скорости](gateway-and-services.md#как-проверить-скорость)

## Где допустим кеш

- **Gateway** может потерять кеш маршрутов и открытых ключей. Для работы клуба после перезапуска нужны предварительно сохранённые пакет доверия и полномочие судьи с ограниченным сроком. Неизвестный ключ требует проверки до допуска защищённой команды.
- **Redis** нужен только тем облачным маршрутам, которые используют веб-сессии или общие квоты. При его потере может понадобиться повторный вход, а запросы, требующие проверки сессии или квоты, ждут восстановления либо возвращают временную ошибку. Счёт, архив и официальный Elo в Redis не записываются. Это использование согласуется с отдельным планом для Swarm на одной ВМ. [План Swarm](../swarm/README.md) · [Задача об общих сессиях](https://github.com/UstinKO/padel-core-service/issues/1210)
- **Табло и рейтинг** можно держать в памяти для быстрых повторных GET. Источник после очистки памяти — локальная долговечная версия № 2. Ключ кеша включает объект, версию и аудиторию. Для публичных данных новая версия меняет ключ. Восстановившаяся площадка принимает только целую проверенную версию новее своей. Удаление кеша не меняет счёт, оплату или место игрока.

## Что проверить до переключения

1. Перезапустить обе реплики Gateway между записью и ответом. Повторить тот же ID. Проверить одно событие, один результат и возобновление доставки. Погасить по очереди каждое клубное устройство после подтверждения и восстановить протокол из оставшегося. Для новых подтверждений снова нужны два независимых диска. WAL-файл SQLite привязан к локальной площадке. Образ онлайн-копии снимать согласованным способом. [Режим WAL SQLite](https://sqlite.org/wal.html) · [Долговечность SQLite](https://sqlite.org/pragma.html#pragma_synchronous)
2. По очереди отключить PostgreSQL, Redis, Identity и обработчик Elo. На заранее подготовленных устройствах продолжить матч без внешней сети. Проверить локальное табло, следующую сетку и прежние p95/p99. Отдельно измерить вход, оплату и запись в состав с тремя синхронными копиями при обычной сети, задержке и потере площадки. [Критерии скорости](gateway-and-services.md#как-проверить-скорость)
3. Изолировать две облачные площадки после квитанций 3/3. С третьей восстановить архив и контрольный Elo, затем повторить для двух других пар. Переиграть дубль и позднее исправление, сверить все строки и версию. Отдельно поднять PostgreSQL из базовой резервной копии и непрерывного архива WAL вне трёх ВМ, проверить аккаунты, оплаты и связи профилей. Версионные защищённые копии архивов и ключи проверки должны быть доступны при восстановлении. [Восстановление PostgreSQL](https://www.postgresql.org/docs/15/continuous-archiving.html)
