# Пять сервисов пилота, их данные и связь

**Состав согласован владельцем.** API Gateway с оркестратором, турнирный протокол и табло, аккаунты и вход, управление турнирами, результаты и рейтинг Elo. Это пять независимо выпускаемых сервисов. Экземпляры в клубе, реплики в Swarm и библиотека расчёта раундов в это число входят как части соответствующих сервисов. Ниже — предлагаемый стек и решения для проверки на стенде. Действующая система остаётся источником официальных результатов до приёмки. [Условия сохранности и смета](README.md) · [Анализ нагрузки](service-boundaries.md)

## По каждому сервису

| № | Сервис и стек | Собственное хранилище и кеш | Как он взаимодействует с остальными |
|---|---|---|---|
| 1 | **API Gateway и оркестратор.** Go, стандартный HTTP-сервер, HTTPS/JSON и OpenAPI. Два экземпляра на каждой облачной ВМ, локальный экземпляр в клубе. | **Своей БД нет.** В памяти держит маршруты и кеш открытых ключей. Для холодного запуска в клубе доверенные ключи и подписанный пакет доступны на диске. Устойчивый статус команды и незавершённая доставка находятся у владельца операции. | Ведёт запрос к одному владельцу, проверяет подпись и общие права. Для входа вызывает № 3, для заявки — № 4. Судейскую команду сверяет с локальным движком и передаёт № 2. После рестарта узнаёт исход по тому же ID. |
| 2 | **Турнирный протокол и табло.** Go, SQLite, HTTPS/JSON, WebSocket для сигнала обновления. Один процесс имеет право записи в локальный журнал устройства или площадки. | **Своя SQLite на каждом диске**, в режиме WAL и `synchronous=FULL`. Хранит события, версии, хеши, квитанции, задания доставки и последний подтверждённый снимок табло. У каждой облачной площадки есть и восстанавливаемая копия опубликованного рейтинга для чтения. | № 1 координирует запись в клубе. Связь между площадками передаёт подписанные события и квитанции по HTTPS. № 2 выдаёт № 5 проверяемый полный архив и получает от него готовую версию рейтинга. После пропуска WebSocket-сигнала клиент повторно читает снимок через № 1. |
| 3 | **Аккаунты и вход (Identity).** Java 17, Spring Boot, Spring Security, OAuth2, JWT с асимметричной подписью. | **PostgreSQL, схема `identity`.** Учётные записи, способы входа, хеши паролей, привязки и состояние отзыва учётных данных. Закрытый ключ подписи передаётся только экземплярам Identity через хранилище секретов. Для общих веб-сессий предлагаем использовать Redis, уже предусмотренный планом Swarm. | Через № 1 обслуживает создание аккаунта, вход, восстановление и обновление токена. Публикует набор открытых ключей JWKS. Gateway проверяет действующий access-токен с известным ключом локально. Доступ к конкретному турниру и заявке проверяет № 4. |
| 4 | **Управление турнирами.** Существующее приложение на Java 17, Spring Boot, Spring Data JPA/JDBC и Liquibase. Включает подготовку судейского пакета. Библиотека Java с правилами раундов также поставляется в клубный пакет и вызывается через loopback. | **PostgreSQL, схема `tournament`.** Клубы, спортивные профили и их стабильные ID, права на конкретный турнир, состав, очередь, оплаты и квитанции об оплате. Одна локальная транзакция на связанные изменения заявки и оплаты. | Принимает команды через № 1. До старта передаёт подписанный пакет проведения клубному контуру. Изменение действующего протокола проходит через авторизованного писателя № 2. Подписчики изменений состава или профиля получают события после фиксации транзакции. |
| 5 | **Результаты и рейтинг Elo.** Java 17, существующая формула Elo, Spring Boot/JDBC, Liquibase. Фоновый обработчик со своим лимитом CPU и пулом подключений. | **PostgreSQL, схема `rating`.** Входящие задания, обработанные версии архивов, привязки идентификаторов для воспроизведения, версии формулы, строк рейтинга и публикаций. Исходные архивы сохраняет № 2. Официальную версию выбирает № 5. | Принимает внутреннее задание после трёх квитанций за один архив, получает его у № 2, проверяет и пересчитывает в фоне. Отправляет подписанную версию среза облачным экземплярам № 2. Открытие рейтинга через № 1 читает готовые данные своей площадки. |

## Что общее в PostgreSQL

Для пилота — **один кластер PostgreSQL, одна логическая база, три схемы**. На A, B и C размещаем по экземпляру с отдельным диском. В штатном режиме у кластера один пишущий primary и две потоковые реплики. Каждому из сервисов № 3–5 выдаём свою прикладную роль, отдельный пул соединений и миграции своей схемы. Роль миграции отделена от прикладной. Права и `search_path` ограничивают доступ к чужим таблицам. № 1 и № 2 не получают учётных данных PostgreSQL. Размещаем пилот на трёх предусмотренных сметой ВМ. Достаточность памяти, IOPS и скорости репликации предстоит измерить. [Схемы и привилегии PostgreSQL](https://www.postgresql.org/docs/15/ddl-schemas.html) · [Бюджет трёх площадок](README.md#бюджет-за-месяц)

В целевой схеме сервис читает чужие данные через API владельца или свою локальную копию разрешённых полей, обновляемую событиями. Для перехода существующие связанные таблицы и объединение гостя с аккаунтом сохраняют одного транзакционного владельца до сверки старых ID, связей и истории Elo. Миграция идёт по одной операции, с единственным писателем. Событие о создании аккаунта связывается со спортивным профилем по стабильному ID. Повторная доставка не создаёт второго игрока. Во время перехода обязательные проверки контакта и уровня при записи продолжают работать. [Правила продукта](../../specs/MASTER.md) · [Переход данных профиля](service-boundaries.md)

**Предложение по долговечности облачных операций.** Для подтверждения долговечных изменений аккаунта, заявки, оплаты и официальной версии рейтинга на стенде выбрать фиксацию WAL на primary и обеих репликах (`synchronous_commit=on`, два обязательных standby). Успешный ответ ждёт более медленную площадку. При недоступности одной из трёх новая такая операция может остаться без подтверждения. Потеря ответа означает, что клиент сверяет статус по ID, прежде чем повторять команду. Повышение standby требует кворума управления 2 из 3 и изоляции прежнего писателя. После смены primary сохраняется требование двух других долговечных копий. Длительность межпровайдерской записи и доступность облачной регистрации проверяем отдельно от судейского пути. Если это ухудшает действующие p95/p99, конфигурация не проходит приёмку. [Подтверждение записи PostgreSQL](https://www.postgresql.org/docs/15/warm-standby.html#SYNCHRONOUS-REPLICATION)

## Какие вызовы синхронные, какие фоновые

| Сценарий | Путь и момент завершения |
|---|---|
| **Запись счёта** | Судейский клиент → № 1 в клубе → локальный движок → № 2 на первом и втором устройствах. После устойчивой записи события на обоих устройствах и фиксации квитанции на первом судья видит принятую версию. Облачный PostgreSQL, Redis, интернет и Elo здесь не вызываются. Один авторизованный писатель ведёт турнир. Вторая копия получает тот же номер и хеш. |
| **Вход и запись на турнир** | Клиент → № 1 → № 3 для входа. При записи с access-токеном путь — клиент → № 1 → № 4 → его транзакция в `tournament`. Повторный вход на каждый запрос не нужен. При браузерной cookie-сессии сохраняются серверная проверка сессии, CSRF и OAuth callback. |
| **Финал и публикация Elo** | № 2 сохраняет финал и задания по каждой площадке. № 1 возобновляет доставку в фоне. После квитанций A, B и C за одинаковый архив № 1 вызывает внутренний HTTPS-приёмник № 5. Ответ о приёме приходит только после записи задания в `rating`. № 5 строит версию отдельно, одной транзакцией фиксирует применённый архив, указатель версии и задание публикации. Каждая площадка № 2 проверяет подписанный срез и целиком переключает свою локальную версию. |
| **Чтение табло и рейтинга** | Зритель → № 1 → локальное представление № 2. WebSocket сообщает об изменении, GET возвращает снимок с номером версии. Сбой № 5 оставляет доступной последнюю полную публикацию на площадке. Облачная копия для общего рейтинга содержит только разрешённые поля. Для закрытых представлений сохраняются проверка аудитории и `private, no-store`. При невозможности подтвердить доступ выдача личных данных закрывается. |

Для команд и событий используем версионированный HTTPS/JSON и взаимную аутентификацию внутренних сервисов. Внутренний вызов идёт по маршрутам оркестратора, с ограничением времени ожидания. Идентификатор для трассировки отделён от устойчивого ключа операции. На изменениях передаются ID операции, ID объекта и ожидаемая версия. Владелец проверяет ключ и хеш содержимого. Повтор той же операции возвращает прежний исход, иное содержимое с тем же ключом отклоняется.

Фоновая доставка допускает повторы. Владелец записывает изменение и задание на отправку в одной транзакции своей SQLite или PostgreSQL (outbox). Получатель атомарно сохраняет ID входящего события и результат либо задание на обработку (inbox). Повторы идут с увеличивающейся паузой. Для архива ключ включает турнир и версию, хеш проверяется отдельно. Конфликт или пропуск задерживает публикацию. При потере ответа или перезапуске шлюза незавершённая работа находится у владельца по ID. Отдельный брокер для этого пилота не требуется.

## Где допустим кеш

- **Gateway** может потерять кеш маршрутов и открытых ключей. Для работы клуба после перезапуска нужны предварительно сохранённые пакет доверия и полномочие судьи с ограниченным сроком. Неизвестный ключ требует проверки до допуска защищённой команды.
- **Redis** нужен только тем облачным маршрутам, которые используют веб-сессии или общие квоты. При его потере может понадобиться повторный вход, а запросы, требующие проверки сессии или квоты, ждут восстановления либо возвращают временную ошибку. Счёт, архив и официальный Elo в Redis не записываются. Это использование согласуется с отдельным планом для Swarm на одной ВМ. [План Swarm](../swarm/README.md) · [Задача об общих сессиях](https://github.com/UstinKO/padel-core-service/issues/1210)
- **Табло и рейтинг** можно держать в памяти для быстрых повторных GET. Источник после очистки памяти — локальная долговечная версия № 2. Ключ кеша включает объект, версию и аудиторию. Для публичных данных новая версия меняет ключ. Восстановившаяся площадка принимает только целую проверенную версию новее своей. Удаление кеша не меняет счёт, оплату или место игрока.

## Что проверить до переключения

1. Перезапустить обе реплики Gateway между записью и ответом. Повторить тот же ID. Проверить одно событие, один результат и возобновление доставки. Погасить по очереди каждое клубное устройство после подтверждения и восстановить протокол из оставшегося. Для новых подтверждений снова нужны два независимых диска. WAL-файл SQLite привязан к локальной площадке. Образ онлайн-копии снимать согласованным способом. [Режим WAL SQLite](https://sqlite.org/wal.html) · [Долговечность SQLite](https://sqlite.org/pragma.html#pragma_synchronous)
2. По очереди отключить PostgreSQL, Redis, Identity и обработчик Elo. На заранее подготовленных устройствах продолжить матч без внешней сети. Проверить локальное табло, следующую сетку и прежние p95/p99. Отдельно измерить вход, оплату и запись в состав с тремя синхронными копиями при обычной сети, задержке и потере площадки. [Критерии скорости](gateway-and-services.md#как-проверить-скорость)
3. Изолировать две облачные площадки после квитанций 3/3. С третьей восстановить архив и контрольный Elo, затем повторить для двух других пар. Переиграть дубль и позднее исправление, сверить все строки и версию. Отдельно поднять PostgreSQL из базовой резервной копии и непрерывного архива WAL вне трёх ВМ, проверить аккаунты, оплаты и связи профилей. Версионные защищённые копии архивов и ключи проверки должны быть доступны при восстановлении. [Восстановление PostgreSQL](https://www.postgresql.org/docs/15/continuous-archiving.html)
