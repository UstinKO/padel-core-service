# Объём передачи пользовательского интерфейса 1-Padel

Уточнено 26 октября 2026 по шести комментариям Сергея, переданным пользователем. Этот документ задаёт текущий объём и порядок работы; он заменяет прежнее предложение сначала подключить пилот к API и только потом продолжать макеты.

## Результат и ответственность

Передаём полный интерактивный интерфейс пользовательской части на React + TypeScript в утверждённом стиле Play Concept. Это страницы, их состояния, адаптация для телефона и компьютера, модальные окна, меню, баннеры, формы и переходы. Не набор отдельных картинок.

Наша работа: дизайн, компоненты, демонстрационные данные и ответы, состояния операций, документация и исходники. При интеграции исполнитель подключает авторизацию, регистрацию и остальные операции к действующему API, обеспечивает права, серверные правила и инфраструктуру тестирования. Работа над макетами продолжается независимо от подключения API.

Административные экраны из полной инвентаризации остаются отдельным этапом. Наличие в инвентаризации 40 позиций не означает, что все они входят в текущую пользовательскую поставку. Создание нового приложения с нуля не входит в этот этап; общие компоненты дизайна и правила учитывают существующее Expo-приложение.

## Какие разделы покрыть

| Группа | Экраны и сценарии |
|---|---|
| Начало | Главная для гостя и вошедшего игрока, каталог, фильтры, выбор уровня, мобильное меню |
| Аккаунт | Вход, регистрация без подтверждения email, восстановление и новый пароль; состояния входящих ссылок и сохранение выбранного мероприятия |
| Мероприятие | Общая страница каждого формата, правила, организатор, FAQ, основной состав, резерв, поделиться, переход к проведению |
| Участие | Запись, согласие с условиями, подтверждение, резерв, приглашение на освободившееся место, отмена; различия индивидуальной и парной заявки |
| Парные сценарии | Выбор/поиск партнёра, приглашение и его принятие, ожидание ответа, отказ или истёкшее приглашение; соответствие существующей серверной модели |
| Кабинет | Мои мероприятия, история, статусы участия и оплаты, профиль и редактирование доступных игроку данных |
| Проведение для игрока | King of Court, индивидуальный Americano, постоянные пары и плей-офф: корты, расписание, полный рейтинг, история и завершение |
| Остальная публичная часть | Клубы и страница клуба, рейтинг, место лиги в навигации, информация о приложении, правила и юридические страницы |
| Системные экраны | Нет доступа, страница не найдена, истёкшая ссылка/сессия, ограничение запросов, отсутствие сети, недоступность сервиса, «В разработке» |

Лига и общий рейтинг, которые ещё не готовы на сервере, получают согласованные демонстрационные состояния или явный экран «В разработке». Не изображать вымышленные показатели как настоящие. Юридические тексты брать из согласованных материалов; недостающие тексты помечать для заполнения.

## Матрица состояний

Для каждой применимой страницы задаются роль, состояние данных и состояние операции. Не нужны отдельные компоненты для каждой комбинации: компоненты общие, примеры состояния переключаются на странице проверки.

| Область | Обязательные варианты |
|---|---|
| Пользователь | Гость; вошедший игрок; участник; игрок в резерве; ожидающий подтверждения; сессия истекла |
| Каталог | Загрузка; мероприятия доступны; нет мероприятий; фильтры ничего не нашли; ошибка загрузки |
| Мероприятие | Есть места; заполнено; запись закрыта; ещё не запущено; идёт; завершено; отменено; отсутствует |
| Запись | Проверка полей и условий; отправка; успех; резерв; место уже занято другим игроком; отказ; результат запроса неизвестен |
| Резерв | Позиция в очереди; предложено место; срок принятия; место подтверждено; предложение истекло; выход из очереди |
| Парная запись | Партнёр выбран/не выбран; приглашение отправлено; принято/отклонено/просрочено; категория не подходит; пара подтверждена |
| Кабинет | Пустой; есть будущие записи; резерв; история; отмена запрошена/выполнена/не выполнена; статус оплаты по серверным данным |
| Проведение | Сетка ещё не создана; текущий раунд; ожидание результатов; обновление; нет новых данных; завершённый турнир; ошибка получения данных |
| Обратная связь | Успех; предупреждение; ошибка поля; ошибка операции; повтор; недоступное действие с понятной причиной |

## Недоступная функция и ошибка — разные сценарии

- **В разработке:** функция намеренно не подключена. Короткое объяснение и переход к доступному разделу. Не обещать дату, если она не согласована, и не делать запрос к заведомо отсутствующему API.
- **Не удалось загрузить:** существующий сервис не ответил или вернул ошибку. Сохраняем навигацию и введённые данные, показываем повтор загрузки. Последние известные данные, если они есть, отмечаем как не обновлённые.
- **Сессия истекла / нет доступа:** отдельное объяснение и корректный переход. После входа возвращаем к исходному мероприятию.
- **Запрос записи мог выполниться:** не показываем ложный успех или отказ. Сообщаем, что проверяем статус. При интеграции сначала запрашивается состояние заявки, затем решается, можно ли повторять операцию.

Дизайн не исключает HTTP 500 на сервере. Он обеспечивает предусмотренное отображение ошибки; Исполнитель подключает соответствующие ответы API. Ошибка отдельного блока не должна скрывать весь интерфейс. Для непредвиденного сбоя остаётся резервный экран приложения.

Для проверки готовим именованные сценарии и типизированные демонстрационные ответы: успешный, пустой, загрузка, ошибка, ограниченный доступ, конфликт записи и недоступная функция. Это примеры для интерфейса, не новые обязательные маршруты или схемы API. Страница `/#/review` должна позволять открыть нужный вариант напрямую без ручного изменения кода.

## Общие элементы и мобильное поведение

Переиспользуем шапку, нижнюю навигацию, карточки, кнопки, поля, фильтры, списки игроков, статусы, таблицы, окна и уведомления. Разные форматы используют общую визуальную систему, сохраняя свои правила и действия.

Проверяем длинные имена и фамилии, малые экраны, клавиатуру телефона, прокрутку окон, доступность основной кнопки, фокус клавиатуры, закрытие окна и возвращение к прежнему месту. Основной состав и резерв доступны последовательно. Вводная страница события и проведение турнира остаются отдельными страницами.

Русская версия используется для согласования; пользовательские тексты, числа и даты подготавливаются к испанской локализации. Переключение языка сохраняется между страницами. Производственные тексты не должны включать внутренние технические пояснения разработчику.

## Порядок работы

1. Уточнить карту именно пользовательских экранов и добавить переключаемые примеры состояний к уже готовому пути выбора и записи.
2. Довести аккаунт, входящие ссылки, личный кабинет, профиль, резерв и парные сценарии.
3. Подготовить просмотр проведения всех форматов: корты, раунды, рейтинг и история. Алгоритмы генерации и подсчёта остаются серверными.
4. Закрыть остальные публичные разделы, меню, баннеры, модальные окна и системные состояния. Для будущих функций — отдельные понятные заглушки.
5. Проверить пользовательскую часть целиком на телефоне и компьютере; собрать исходники, демонстрационные сценарии, ассеты и инструкции в архив.

Интеграция может параллельно подключать готовые экраны. Это не блокирует остальные макеты и не превращает каждую итерацию в обязательный этап серверной интеграции.

## Ассеты и состав передачи

Отдельно собрать логотипы, пиктограммы, фотографии, иллюстрации и прочий медиа-контент. Для каждого указать файл, назначение, место использования, исходный источник/лицензию и доступные варианты. Карта ассетов — `ASSETS.md`; текущие места файлов и ещё не выполненные части отмечены явно.

Финальный ZIP: исходники React/TypeScript, зависимости и lock-файл, общие стили, ассеты, демонстрационные данные и ответы, обзор всех состояний, инструкция запуска и инструкция интеграции. Служебный выбор сценариев не выдаётся за функции настоящего аккаунта.

## Закрытый контур и завершение

Новый функционал проверяется в отдельном окружении с доступом для одного-двух согласованных IP. Ограничение обеспечивает сервер или хостинг; скрытая ссылка и проверка IP в JavaScript не являются ограничением доступа. Конкретные IP и настройку выполняют в закрытом контуре при развёртывании.

Существующий публичный дизайн-концепт не является таким закрытым контуром. Реальные пользовательские данные в демонстрационную публикацию не добавляются.

Старая версия сайта остаётся рабочей до завершения тестирования всего перенесённого функционала. Переключение выполняется отдельно после проверки, с возможностью возврата. Этот документ не означает, что закрытый контур уже настроен или все перечисленные макеты уже готовы.
