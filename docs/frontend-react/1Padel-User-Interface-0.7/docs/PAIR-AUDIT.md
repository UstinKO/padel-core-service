# Парная регистрация: сверка поведения

Проверено 26.10.2026 по локальному `padel-pair-integration/` и более раннему `padel-core-service/`. Первый каталог — снимок без Git-истории; второй заканчивается коммитом `85d0f03` от 18.10.2026. Production и актуальная серверная ветка не проверялись. Эти пути относятся к исходной рабочей папке, а не к содержимому ZIP интерфейса.

## Три режима

| Режим | Запрос | Результат и ограничения |
|---|---|---|
| У меня есть партнёр | `POST /api/tournaments/double/{id}/register` | Существующий игрок выбирается по ID; для нового указываются имя, фамилия и контакт. Обоим создаётся готовая пара сразу: `CONFIRMED` или `WAITLIST`. Отдельного согласия по email для уже договорившейся пары этот путь не требует |
| Добавлю партнёра позже | `POST …/{id}/register-solo` с `soloType: ADD_LATER` | До срока — `SOLO_ADD_LATER`; срок = начало −24 часа. После срока — `WAITLIST` без партнёра. Это ещё не готовая пара |
| Ищу партнёра | `POST …/{id}/register-solo` с `soloType: SEARCH` | `SOLO_SEARCH`. Контакты скрыты по умолчанию; `shareContacts` включает их показ в списке поиска |

Источник: `src/main/java/com/padle/core/padelcoreservice/service/DoubleTournamentRegistrationService.java`, методы `registerForDoubleTournament` (строка 89), `registerWithExistingPartner` (251), `registerWithNewPartner` (342), `registerSoloForDoubleTournament` (730). DTO: `PartnerRegistrationDto.java`, `SoloDoubleRegistrationDto.java`.

Вместимость парного турнира на сервере измеряется парами. В проверенной реализации одиночная заявка учитывается как занятый слот: `confirmedPairs + activeSoloRegistrations`. Если сумма достигла вместимости, сервер отклоняет новые одиночные заявки, даже «Ищу партнёра». Готовую пару при этом можно поставить в резерв. Это ограничение текущего backend, а не новое требование продукта. По решению владельца UI теперь разрешает все три режима в резерве. В отдельной серверной задаче потребуется изменить register-solo и завершение пары, чтобы одиночные заявки полного турнира оставались WAITLIST и не занимали слот до формирования пары.

## Поиск, дубли и категории

Входящий API поиска — `GET /api/players/search?query=…&tournamentId=…`. Клиент поддерживает имя, фамилию, WhatsApp, Telegram; поиск от двух символов. При ручном вводе подсказки показываются у активного поля. Найденного существующего игрока нужно выбрать по ID, а не создавать повторно.

В `mobile-app/src/pairBooking.ts` реализованы проверки: нельзя выбрать себя, нельзя использовать свои контакты, выбранный игрок заново проверяется поиском перед записью, совпавший телефон/Telegram требует выбора существующего игрока, после смены аккаунта операция отменяется. Для нового партнёра этот клиент требует имя, фамилию и WhatsApp; Telegram необязателен. Backend DTO при этом не объявляет телефон обязательным — это расхождение нужно согласовать, а не считать серверной гарантией.

Категории проверяются `service/TournamentLevelPolicy.java`: для простой категории (например, C7) допускается отклонение на одну ступень и та же шкала. Для диапазонов, сумм и других составных категорий эта проверка не применяется. Тренировки и Cancha abierta исключены. В текущем интерфейсе пример C7 допускает C6–C8; окончательное решение остаётся серверу. У нового гостевого партнёра сервер пока сохраняет уровень `SIN_ESPECIFICAR`, поэтому интерфейс не может обещать автоматическую проверку его категории.

## Добавить партнёра к существующей заявке

`POST …/{id}/add-partner` разрешён для `SOLO_ADD_LATER` либо `WAITLIST`, если ещё нет партнёра и `isDoubleRegistration=false`. Для `SOLO_SEARCH` этот метод не предусмотрен: там используется предложение пары.

При завершении `SOLO_ADD_LATER` пара подтверждается в уже занятом слоте. Если заявка без партнёра уже в резерве, готовая пара становится в конец очереди; затем сервер обрабатывает очередь и может подтвердить её при доступном месте. Нельзя автоматически повышать её перед готовыми ожидающими парами.

Источник: `DoubleTournamentRegistrationService.java`, `addPartnerToSoloRegistration`, строки 841–973. Срок добавления партнёра и срок бесплатной отмены — разные понятия; нельзя выводить первый из второго, особенно при новых правилах отмены за 3 часа.

## Предложение пары и принятие

Публичный `GET …/{id}/looking-for-partner` возвращает только активные `SOLO_SEARCH`, с полным именем и уровнем. Телефон и Telegram возвращаются только при `shareContacts=true`. Источник: `TournamentRegistrationRepository.java:284–288`, сервис `getLookingForPartnerPlayers:977`.

Отправить предложение могут `SOLO_SEARCH` и `SOLO_ADD_LATER`. Получатель также должен оставаться в одном из этих двух состояний; нельзя предложить пару себе или игроку другого турнира. `POST …/{id}/propose-pair/{targetRegistrationId}` сохраняет токен у получателя и отправляет письмо. Токен живёт 48 часов. Новое входящее предложение перезаписывает прежний токен у этого получателя.

Отправка не переводит регистрацию в `CONFIRMED`. На интерфейсе показываем «Предложение отправлено / ждём ответ», сохраняя одиночный статус заявки. Автоматического принятия при взаимных предложениях нет.

Письмо ведёт на `GET /double-registration/accept-pair?token=…`; открытие показывает страницу, а принятие выполняется отдельным `POST /api/tournaments/double/accept-pair?token=…`. Сервер проверяет срок токена и доступность обоих игроков, затем связывает их и ставит обоим `CONFIRMED`. Повторный/старый токен не должен создавать новую пару.

Источник: `DoubleTournamentRegistrationService.java:1002–1125`, `PartnerRegistrationController.java:34`, `DoubleTournamentRegistrationController.java:206–245`. В снимке не найден API отклонения, список входящих/исходящих предложений или просмотр данных предложения по токену. Страницы `declined` и полноценный список предложений нельзя подключить только существующими операциями. Кнопка «Отклонить» в React-примере меняет локальное состояние; серверную операцию требуется добавить или согласовать её замену.

## Регистрация аккаунта и Google

`dto/RegistroRequestDto.java`: обязательны имя и фамилия по 3–100 символов, email до 150, пароль 8–100, подтверждение пароля, уровень. Валидатор `PhoneOrTelegramValidator.java` требует хотя бы телефон или Telegram. В серверной HTML-форме есть обязательное согласие с условиями. CAPTCHA проверяется в контроллере при её включении; серверные ограничения домена/email и антибот-проверки сохраняются.

Форма `POST /players/registro` после успеха создаёт серверную сессию и отправляет на `/?welcome=true`. JSON-метод контроллера фактически расположен по `POST /players/api/registro` и возвращает 201 с профилем, без аналогичного автоматического входа. В security allowlist есть похожий, но другой `/api/players/registro`: маршрут и доступность API регистрации нужно сверить перед интеграцией.

Google: `/oauth2/authorization/google` возвращает обычный веб на `/players/dashboard`. Параметр `?client=app` выставляет флаг в сессии; callback возвращает Expo web на `/app/#accessToken=…&refreshToken=…&expiresIn=…`, клиент убирает фрагмент из адреса. Новый сайт не должен перезаписывать этот маршрут приложения. Возврат к выбранному событию нужно согласовать отдельным безопасным механизмом, не произвольным внешним redirect URL.

Источники: `PlayerPadelController.java:35,54,183`, `security/oauth2/OAuth2AppLoginOriginFilter.java`, `OAuth2AuthenticationSuccessHandler.java:65–83`, `mobile-app/src/AuthContext.tsx`.

## Что сделано в React-примере

- `PairRegistration.tsx`: три режима, выбор существующего игрока, ручной ввод, подсказки по четырём полям, отдельное согласие на показ контактов, состояние полного турнира и истёкшего срока добавления партнёра.
- `domain/pairs.ts`: вымышленные кандидаты, поиск, проверки телефона, Telegram, дублей, выбора себя, занятости и простой категории. `validatePairSelection(value, {user, eventLevel, full})` возвращает текст ошибки либо `null`.
- `/partners/:id`: управление одиночной заявкой, добавление партнёра позже, просмотр кандидатов, подтверждение отправки предложения, ожидание ответа. После добавления видно состояние готовой пары.
- `/partner-invitation?state=pending|accepted|declined|expired|incompatible`: явное принятие или отказ и отдельные исходы. Query управляет только демонстрацией, а не реальной авторизацией по токену.

Корневой компонент записи выполняет submit через свой сервис. UI не отправляет реальные запросы, письма или сообщения. Для production необходимы свежая серверная проверка перед изменением, сверка результата после сетевой неопределённости, запрет повторного submit и обработка смены аккаунта.

## Вопросы к подключению backend

1. Уточнить актуальность ограничений слотов для одиночных заявок и сохраняемого места до дедлайна; не смешать их с вместимостью, рассчитанной только по подтверждённым парам.
2. Исправить или согласовать путь JSON-регистрации и последующий вход. Не подменять серверную регистрацию локальным профилем.
3. Выбрать контракт просмотра входящего предложения, отклонения и статуса отправки. Одного токена в URL недостаточно, чтобы достоверно показать имена и событие до принятия.
4. Проверить конкурентные предложения, актуальность обоих игроков и токенов, права/состояние турнира при accept. В снимке один токен на получателя; интерфейс не должен обещать независимый inbox множества действующих предложений.
5. Согласовать обязательность контактов нового партнёра и проверку его категории; существующий guest-path пока допускает неизвестный уровень.
6. Убедиться, что конфиденциальность контактов соответствует тексту согласия: endpoint поиска партнёра доступен публично и при разрешении отдаёт контакты. Не писать «видны только авторизованным ищущим», если сервер это не ограничивает.
7. Добавить или согласовать операцию изменения `shareContacts` после создания заявки. На `/partners/:id` переключатель видимости контактов сейчас меняет только локальный `allowContact`. В проверенном backend `shareContacts` сохраняется при `register-solo` (`DoubleTournamentRegistrationService.java:780`), а отдельного endpoint для последующего изменения в `DoubleTournamentRegistrationController.java` нет. При интеграции переключатель должен сохранять серверное согласие; при ошибке нельзя показывать контакты скрытыми, пока сервер продолжает их возвращать.
