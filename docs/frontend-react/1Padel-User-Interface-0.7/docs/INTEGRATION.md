## Что передаём сейчас

React 19, TypeScript, Vite, React Router и локальные стили. Маршруты демонстрации используют hash routing: `/#/home`, `/#/events` и далее. Полный перечень — в [SCREEN-MAP.md](SCREEN-MAP.md).

Они не создают реальные аккаунты, заявки, платежи или письма. Данные демосессии сохраняются в браузере; это не механизм production-авторизации.

Области для подключения сервера уже разделены:

- `src/data/events.ts` — демонстрационные события и участники;
- `src/domain/types.ts` — упрощённые типы пилота, пока не официальный API-контракт;

Перед заменой локальной реализации нужно согласовать реальные ответы сервера и состояния интерфейса. Сервер определяет наличие места, статус заявки, позицию резерва, стоимость, сроки отмены, права доступа и результат операции. Клиент только отображает ответ и отправляет намерение пользователя.

## Общий сервер для сайта и приложения

Приложение уже существует. Новый проект мобильного приложения с нуля для этого редизайна не требуется. Сайт и приложение должны использовать одни и те же записи игроков, турниры, платежные статусы и серверные правила.

В проверенной реализации доступны следующие операции; перед подключением нужно сверить актуальные схемы ответов, права и коды ошибок:

| Область | Найденные маршруты | Источник |
|---|---|---|
| Расписание и событие | `GET /api/public/tournaments`, `GET /api/public/tournaments/{id}` | `mobile-app/src/schedule.ts` |
| Мобильная авторизация | `POST /api/auth/login`, `POST /api/auth/refresh`, `GET /api/auth/me` | `mobile-app/src/auth.ts` |
| Мои мероприятия | `GET /api/players/me/tournaments` | `mobile-app/src/auth.ts` |
| Контакты игрока | `GET /api/players/me/contact-status`, `PATCH /api/players/me/contact` | `mobile-app/src/auth.ts` |
| Индивидуальная запись и отмена | `POST /players/tournaments/{id}/register`, `POST /players/tournaments/{id}/cancel` | `mobile-app/src/auth.ts` |
| Своя заявка | `GET /players/tournaments/{id}/my-registration` | `mobile-app/src/auth.ts` |

| Предложение пары | `POST /api/tournaments/double/{id}/propose-pair/{targetId}` | `mobile-app/src/auth.ts` |

Маршруты записи вне `/api/` приведены намеренно: именно их использует проверенный клиент. Не переименовывать их в новом интерфейсе без серверной поддержки. Входящий DTO серверного расписания содержит `modality`, `capacityUnit`, `startsAt`, `timeZone`, `registrationOpen`, `cancellationDeadline`; упрощённая модель демо этих гарантий пока не даёт.

При подключении нужны состояния загрузки, пустого результата, ошибки, истёкшей сессии, изменившихся условий и неопределённого результата записи. После обрыва связи нельзя автоматически повторять запись или отмену: запрос мог выполниться. Сначала повторно запросить состояние заявки. Блокировка повторного нажатия в интерфейсе не заменяет серверную идемпотентность.

## Авторизация сайта и приложения — разные способы доступа к одному аккаунту

Действующий веб использует серверную сессию Spring Security, `JSESSIONID`, remember-me и CSRF-cookie `XSRF-TOKEN`. В старом ADR-0005 для нового React-веба предложено сохранить эту схему на том же домене: передавать `X-XSRF-TOKEN` при изменяющих запросах. Это совместимо с постепенной заменой Thymeleaf-страниц.

Существующий Expo-клиент использует Bearer access/refresh tokens. В проверенном снимке refresh хранится в SecureStore на телефоне, а в браузерной версии Expo — в localStorage на HTTPS/localhost; access находится в памяти. Этот способ нельзя автоматически переносить в новый веб только потому, что оба клиента написаны на React.

Перед интеграцией нужно выбрать и зафиксировать способ авторизации нового веба с учётом действующей конфигурации. Предложение для сайта — сохранить общую серверную сессию. Предложенный старым ADR `GET /api/auth/session` нельзя считать уже реализованным без проверки.

Google OAuth в проверенном Expo web работает через `/oauth2/authorization/google?client=app` с возвратом на `/app/`. В native-версии этот путь ещё не подключён. Регистрация аккаунта приложения ведёт на действующий `/players/registro`. Формы входа, регистрации и восстановления в пилоте показывают дизайн; реальные операции, Google, письма и обработку токенов нужно подключить отдельно.

## Не перезаписать существующее `/app/`

Старый план React-миграции предлагал разместить новый сайт в `/app/`. Сейчас этот адрес уже используется Expo web: `mobile-app/scripts/build-site.mjs` собирает приложение в `src/main/resources/static/app` с базовым путём `/app`.

Новый сайт сначала размещать на отдельном тестовом адресе или отдельном пути, согласованном для интеграции. Не копировать его сборку поверх `static/app` и не менять OAuth callback приложения ради пилота. Адреса production, стратегия маршрутов и место сборки определяются при интеграции. Hash routing демо не является требованием для публичного сайта; для production нужны реальные ссылки на события и корректные SEO/OG-данные.

## Правила форматов нельзя объединять по названию

Индивидуальный Americano, King of Court и парный турнир имеют разную логику. Новая визуальная система общая; алгоритмы турниров остаются существующими серверными.

- Индивидуальный Americano: партнёры меняются, расписание раундов формируется заранее. Полный формат на 20 игроков — 19 раундов при достаточном числе кортов; фактический режим и количество раундов определяет серверная конфигурация.
- King of Court: переходы между кортами, калибровка и бонусы зависят от настроек организатора. Счёт матча и бонусы нужно показывать раздельно.
- Парный Americano / Team Playoff: постоянные пары, два квалификационных матча и затем плей-офф. Лимит подтверждён в `TeamPlayoffService.java`, `validateTeamAvailableForQualification`. Формулировка «новый партнёр каждый раунд» сюда не подходит.
- В серверном контракте `DOBLES` использует вместимость в парах (`capacityUnit: PAIRS`). Демонстрационный пересчёт мест по двум игрокам не заменяет эту модель.
- Условия отмены, опоздания и оплаты выводятся из актуального правила конкретного события. Нельзя переносить старые «24 часа / −10 очков» на все форматы. Парные правила, обсуждавшиеся позднее, отличаются; перед подключением сверить их действующую версию, а не брать текст демо за источник истины.

## Приложение: согласовать основу сейчас, обновлять экраны поэтапно

Сейчас закрепить общие названия, состояния заявки, серверные контракты, цвета, типографику, отступы и компоненты дизайна. После согласования основного веб-сценария обновлять соответствующие экраны существующего Expo-приложения. Совместно использовать типы данных, чистые функции, API-контракты и дизайн-токены там, где это оправдано.

React DOM и React Native имеют разные элементы интерфейса и стили. Вёрстка сайта не переносится автоматически в native, поэтому сайт и приложение могут иметь собственные UI-компоненты при одинаковой логике и внешнем характере.

Push-уведомления — отдельный этап: разрешения, регистрация устройств, отправка с сервера, переход в нужное событие, настройка предпочтений и тестирование доставки. В проверенном приложении не найдены готовые push-механизм, service worker или web manifest. Наличие Expo-кода и браузерной ссылки не означает готовность к App Store/Google Play или установке PWA. Публикацию и native-вход проверять отдельно.

## Как подключать и выпускать

1. Продолжать все пользовательские макеты на демонстрационных данных: страницы, состояния ролей, меню, баннеры, модальные окна, ошибки и будущие функции. Не ждать подключения API для завершения дизайна.
2. Перед интеграцией сверить текущую ветку сервера, актуальные API и роли; подключить отдельный адаптер вместо mock-сервисов. Для разработки использовать отдельное окружение и тестовые записи.
3. Разместить новую версию в закрытом контуре с доступом для одного-двух согласованных IP. Доступ ограничивает сервер/хостинг, не скрытая ссылка и не клиентский код. Публичный дизайн-концепт не считается этим контуром. Проверить возврат к событию после входа, резерв, отмену, парные сценарии и ссылки из писем.
4. Проверить всю пользовательскую часть на телефонах и компьютере, клавиатуру, длинные фамилии, прокрутку модальных окон, состояния ошибок, загрузку и сетевые сбои. Административные экраны проверяются отдельно, когда будут перенесены.
5. Переключать действующий сайт только после завершения проверки всего переносимого функционала. Сохранить действующие URL, OAuth, ссылки в письмах, Telegram и QR; серверные редиректы направлять на соответствующий новый экран без потери идентификаторов и токенов.
6. Перед выпуском сохранить предыдущую сборку и конфигурацию маршрутизации. Предусмотреть возврат на старые страницы без отката пользовательских регистраций. Не совмещать редизайн с необратимой сменой структуры данных.
7. Старую реализацию сохранять рабочей до завершения тестирования всего переносимого функционала. Её удаление не входит в текущую задачу и не происходит автоматически после публикации макетов.

## Revised reserve contract (owner decision, 2026-10-27)

- Full pair tournaments accept all three modes. Ready pair → WAITLIST ready queue; ADD_LATER and SEARCH → incomplete WAITLIST, no reserved main slot. Retain partnerMode and contact-sharing consent. SEARCH entries must remain discoverable and able to send/accept proposals.
- Ready pairs have priority over incomplete entries even if the incomplete entry was created earlier. Once a pair is completed, use its readyAt timestamp to append it after existing ready pairs. Promotion must skip incomplete pairs; move both paired registrations atomically and never exceed capacity. Re-check this on manual partner addition and proposal acceptance; the existing acceptance path unconditionally confirms and needs adjustment.
- Current audited backend: DoubleTournamentRegistrationService rejects register-solo when confirmedPairs + activeSoloRegistrations reaches capacity. This is a required backend change, not something the frontend alone fixes.
- Current TournamentService.processWaitlistForTournament → autoConfirmFromWaitlist already confirms and saves the registration before sending sendWaitlistAutoConfirmEmail. EmailService renders email/vacancy-invitation. This supports the owner's automatic-promotion model; do not reintroduce a temporary seat offer.
- Separate roster status from the player's response: CONFIRMED + participationStatus=PENDING after promotion. The participant already counts toward capacity and appears in the main roster. Confirm participation only records acknowledgement; it must not allocate another place. Decline cancels the allocated registration (both players for a pair) and immediately runs the ready-queue promotion transaction for the next eligible participant/pair.
- No response deadline or automatic removal for silence. Organizers can see pending responses and contact players. The existing WAITLIST_INVITED expiry scheduler is a different legacy flow; never apply it to these CONFIRMED/PENDING registrations.
- Delivery: email to registered address whether or not the app is installed; push additionally if a device subscription is available and permission granted; persistent notification in My entries. Send after promotion commits, retry failures without duplicate promotions. This demo does not send notifications.
- Suggested notification: “You have been moved to the main roster for [event, date, time, club]. Please confirm that you will attend, or decline so the next participant can play.” Email buttons open the relevant confirmation/decline page, not a state-changing GET. App push opens the same registration. Website must work without installing the app.
- Bind links/tokens to the intended registration and user; after login return to the notification. Display actual server state on repeated, stale or forwarded links; no imaginary allocation when the entry is absent. Explicit POST for confirm/decline with idempotency and transactional capacity checks. A token security expiry, if required, must not cancel an allocated place: allow the authenticated player to respond from My entries instead.
- Browser demo models only the current user's registration. It shows confirmation and decline outcomes; delivery and promotion of other users must be verified in Sergey's staging integration. Do not treat the demo as a full multi-user queue engine.

## Проведение турнира: рейтинг и история игрока (27.10.2026)

- King of Court: явно подписать бонусные очки на каждом корте. Личные очки = очки своей пары за каждый матч + бонусы за корт. Калибровка в демо — первые 3 раунда без бонусов; в интеграции число раундов и таблицу бонусов брать из настроек турнира.
- В рейтинге под итогом отдельно «Матчи» и «Бонусы». Нажатие имени открывает модальное окно со всеми завершёнными матчами игрока, партнёром, соперниками, кортом, счётом с его стороны, бонусом и личным итогом. Не включать будущие/несохранённые результаты. Обновлять модальное окно после исправлений результатов.
- Парный рейтинг: компактная таблица и раскрываемая подробная статистика всех пар. Сохранены match1GamesWon/Lost, match2GamesWon/Lost, setsWon/Lost, gamesWon/Lost, setDifference, gameDifference, matchesPlayed. Референс: templates/tournaments/team-playoff/view.html и model/americano/AmericanoTeam.java. В текущем формате один сет на матч; реальный ответ API является источником статистики, не вычислять сеты из побед для иных форматов.
- Подробные показатели на странице рейтинга относятся к квалификации; окно пары включает все её завершённые матчи, в том числе плей-офф. Чемпион определяется финалом, квалификационный рейтинг не становится итоговым рейтингом плей-офф.
- После запуска турнира на мобильной вводной странице постоянная нижняя кнопка «Распределение, сетка и рейтинг» заменяет цену/регистрационный CTA. Статус участия остаётся над кнопкой. До запуска сохраняется обычный сценарий записи. Доступность определяется статусом API, query state — только для демонстрации.
- Демонстрационные данные и алгоритмы оставлены в domain/live.ts. Новые функции playerMatches/pairStats служат только для согласованного примера UI; не заменяют существующую серверную систему расчёта.


## Вид участника при проведении
В демо предусмотрены `?view=player` (Даниил Медведев) и `?view=public`; переключение не меняет аккаунт и записи. Карточка «Ваш матч» находится перед правилами на телефоне, а соответствующий корт выделен зелёным фоном и рамкой. В реальном приложении выделение определяется идентификатором авторизованного игрока в распределении API; демопереключатель и фиксированный игрок должны быть удалены. Гость или игрок вне состава не получает чужой матч как свой.
