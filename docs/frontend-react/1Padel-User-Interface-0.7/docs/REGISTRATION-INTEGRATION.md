## Регистрация: найденная причина блокировок

`security/RateLimitFilter.java`, `classifyPath`:

- Учитывает URL, но не HTTP-метод. GET формы `/players/registro`, POST, восстановление пароля и `/double-registration/**` входят в общий REGISTER-счётчик одного IP.
- Каждый такой запрос добавляет +1. `markRegistrationFailed` добавляет +2. Порог блокировки — 5. Cache истекает через 15 минут после записи.
- Дополнительно REGISTER ограничен тремя запросами в минуту.
- `controller/PlayerPadelController.java`, POST `/registro`: обычные ошибки валидации, несовпадение паролей, дубликаты контактов и неудачная CAPTCHA повышают этот счётчик.
- При валидационной ошибке выбирается только первое сообщение; затем redirect на пустую форму. BindingResult и заполненные значения не переносятся.

Воспроизводимый по коду сценарий: открытие формы = 1; ошибочная отправка = 2 + 2 = 4; GET после redirect = 5. Следующий запрос уже BLOCKED. Поэтому даже одна обычная ошибка способна запустить блокировку при следующем действии. На общей Wi-Fi сети обращения разных людей суммируются. Это объяснение возможной причины, а не доказанный диагноз каждого обращения пользователя: сопоставить с событиями сервера и временем жалоб.

Отдельный дефект: BLOCKED для `/players/api/registro` попадает в браузерный redirect, поскольку проверка API использует только префикс `/api/`. API-клиент может получить HTML вместо ожидаемого JSON. `Retry-After` сейчас фиксированный (900/60), а не фактически оставшееся время.

## Фактические ограничения и различия нового дизайна

Источник: `dto/RegistroRequestDto.java`, `validation/DomainValidator.java`, `validation/BotPatternValidator.java`, `service/PlayerService.java`.

| Поле | Доступная серверная реализация |
| --- | --- |
| Имя, фамилия | Обязательны; 3–100 символов; Unicode-буквы, пробел, точка, дефис, ASCII-апостроф. Дополнительно NoBotPattern. |
| Email | Обязателен; валидный формат; максимум 150; проверки подозрительных и одноразовых адресов; уникальность. |
| Телефон | До 20 символов; необязательный +, цифры, пробелы, дефисы; тело 8–20 символов; уникальность. |
| Telegram | Необязательный @; 5–32 символа username; первая латинская буква, далее буквы/цифры/подчёркивание; уникальность без учёта регистра. |
| Контакт | В старом DTO достаточно телефона ИЛИ Telegram. По новому согласованному требованию телефон обязателен, Telegram необязателен. Это изменение нужно согласованно применить на сервере. |
| Пароль | 8–100 символов. Обязательных цифр, заглавных букв или спецсимволов нет. Повтор должен совпадать точно. |
| Уровень | Обязательный enum Nivel. «Не знаю» в прототипе — UX-состояние: согласовать значение API, не отправлять произвольную строку. |
| Почта после регистрации | `PlayerService` сразу отмечает подтверждённой; письмо с кодом не требуется. |

NoBotPattern может ошибаться на настоящих именах. Ограничение минимум три символа исключает короткие реальные фамилии (Li, Ng). Не просить человека выдумывать данные: предусмотреть ручное разрешение ситуации и пересмотреть правило с разработчиком. Аналогично эвристика неизвестного почтового домена не доказывает мошенничество.

Bean Validation выполняется до trim в контроллере: нормализацию имени, email и контактов следует перенести до проверки. Пароль не обрезать и не менять молча. Телефон нормализовать единообразно перед проверкой уникальности; подтвердить миграцию существующих значений. Проверить реальные ограничения хэшера паролей, включая длину в байтах: DTO сам по себе этого не доказывает.

## Что реализовано в прототипе

- Подсказки до отправки и ошибки после выхода из поля; ошибка обновляется во время исправления.
- Проверки длины/символов имени, email, телефона, Telegram; длина пароля и совпадение повтора.
- Отправка с ошибками не выполняется; фокус и прокрутка к первому полю; список ссылок на ошибочные поля.
- Значения не сбрасываются при исправлении. Пароли остаются только в памяти формы, не сохраняются в storage.
- Отдельные демонстрации существующего email/телефона, ошибочного срабатывания проверки фамилии, CAPTCHA и ожидания с таймером.
- Нет настоящей регистрации, CAPTCHA или серверного rate limit. Сценарии показывают интерфейс для интеграции. Кнопка завершения демопоказа ожидания — только инструмент просмотра макета, её нельзя переносить в рабочую блокировку.
- Юридические страницы помечены как требующие проверки; спорные юридические положения не заменены вымышленными реквизитами.

## Серверные вопросы для отдельной задачи через Telegram-бота

1. Отделить просмотр формы от попытки регистрации. Не начислять abuse-баллы за GET, валидацию обычных полей, несовпадение паролей и корректно обработанные дубликаты. Сохранить отдельную защиту от автоматизации, ограничения на POST/логин и CAPTCHA. Не просто увеличить порог или отключить защиту.
2. Разделить регистрацию аккаунта, восстановление доступа и запись в парный турнир; учесть пользователей за одним IP. Добавить безопасную диагностику: requestId, тип ошибки, HTTP-метод, путь, фактический срок. Не логировать пароли/CAPTCHA/токены/полные формы.
3. Вернуть все ошибки в структурированном ответе. Например 422 `VALIDATION_ERROR` + `fieldErrors:{nombre,apellido,email,telefono,telegramUsername,password,confirmPassword,nivelJugador}`. Для HTML сохранить безопасные значения полей и вывести BindingResult. Не переносить пароль через flash/session.
4. Дубликаты контактов и ошибки проверки — понятные коды с действиями: войти, восстановить доступ, проверить контакт. Защитить endpoint от массового перебора аккаунтов; не добавлять публичный поиск email/телефонов.
5. CAPTCHA: отдельная ошибка с повторной проверкой без очистки остальных полей. Ошибка стороннего сервиса не должна выглядеть как неверное имя.
6. API 429 должен возвращать JSON и реальный Retry-After/blockedUntil; не редиректить JSON-запросы. Таймер UI не заменяет серверную проверку. После истечения — новая попытка, не автоматическая регистрация.
7. На время сетевой отправки блокировать повторный submit. При потере сети сохранить поля в памяти и дать повторить; не объявлять профиль созданным без успешного ответа.
8. Проверить: GET без штрафа; обычная ошибка без 15-минутной блокировки; повторное исправление; два пользователя одного IP; настоящий флуд блокируется; редирект после ошибки не увеличивает abuse; API никогда не возвращает HTML; смена языка; Google → заполнение контактов → исходный турнир.
