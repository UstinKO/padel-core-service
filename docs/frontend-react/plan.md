# План перехода на React — по фазам

> **Статус:** v1, черновик на согласование (2026-09-28). Решения, на которых стоит план, — в [ADR](adr/README.md); чек-листы экранов — в [контракте](contract/README.md).
> **Ресурсы:** один разработчик + Claude Code и SDD-конвейер `/develop-feature`. Дедлайнов нет, турниры — каждую неделю.
> **Оценки** — S / M / L / XL (как в `docs/microservices-migration-plan.md`), не в днях. Риск — отдельно.

## Принципы (кратко)

- Одна фаза даёт ценность сама по себе и может стать последней — сайт при этом полностью рабочий.
- Экран = одна фиче-спека `LFPT-XXX` = один PR = один деплой (ADR-0007).
- Сначала API экрана (DTO, эндпоинты, тесты), потом React-экран (ADR-0004).
- Откат экрана — убрать маршрут из `app.spa.routes`; legacy-версия живёт на `/legacy/...` до Фазы 6 (ADR-0003, ADR-0007).
- Live-экраны переключаются только между турнирами.
- Баги из [findings.md](contract/findings.md) — отдельными issue, не внутри переезда.

## Карта фаз

| Фаза | Что | Экраны | Объём | Риск |
|---|---|---|---|---|

| **1** | Пилот: клубы в админке | A-13, A-14, A-15 | M | низкий |
| **2** | Админка: CRUD, турниры, игроки, платежи | A-01…A-06, A-16…A-19 | XL | средний |
| **3** | Live-форматы: пульты и публичные табло | A-07…A-12, L-01…L-06 | XL | **высокий** |
| **4** | Игрок: кабинет, профиль, вход, регистрация | U-01, U-02, P-02, P-03, P-10, P-11, F-d | L | средний |

## Пре-0. Срочное, не ждёт React (S)

Отдельные issue, можно делать прямо сейчас:

1. **F-00** — закрыть `/test/telegram/**` (сейчас анонимный доступ к рассылке напоминаний игрокам).
2. **F-12** — положить `og-image`, `favicon`, `apple-touch-icon`; `og:image` — абсолютным URL. Превью ссылок начнут работать и на текущих страницах.
3. **F-05** — заполнить ссылки в футерах писем (или убрать их).
4. **F-01, F-02** — маршруты, отвечающие ошибкой (рейтинг Team Americano, просроченный токен сброса).

## Фаза 0. Фундамент (L)

Цель: вся инфраструктура на месте, в проде ничего не поменялось для пользователей, кроме того, что экраны ошибок могут рендериться SPA.

**Сборка и раздача** (ADR-0002, 0003)
- [ ] `frontend/`: Vite + React + TS, ESLint/Prettier, Vitest, Playwright, `size-limit`, README.
- [ ] `frontend-maven-plugin` в `pom.xml`: `npm ci`, `npm run build`, копирование в `target/classes/static/app/`; флаг `-Dskip.frontend` для быстрой сборки бэкенда.
- [ ] `Dockerfile`: builder копирует `frontend/`; кэш npm.
- [ ] `pr-check.yml`: сборка фронта, линт, тесты; кэш `~/.npm`.
- [ ] `deploy.yml`: health-check проверяет, что `/app/index.html` отдаётся.
- [ ] `SpaRoutesConfig` + `app.spa.routes` (пустой список) + `/app/**` с правильными `Cache-Control`.
- [ ] `app.frontend-url` в конфиге; письма/Telegram/OAuth строят ссылки на страницы от него.
- [ ] Облачная среда конвейера собирает фронт (проверить Node) — иначе `/develop-feature` не сможет делать экраны.

**API-основа** (ADR-0004, 0005, 0011)
- [ ] `springdoc-openapi`, Swagger UI только для SUPER_ADMIN; генерация TS-типов + проверка расхождений в CI.
- [ ] `401` JSON для `/api/**` (F-08); `RateLimitFilter` — `429` для `/api/**` (F-10).
- [ ] `@RestControllerAdvice` с `ProblemDetail` + каталог кодов ошибок.
- [ ] `GET /api/auth/session`, `GET /api/public/config`, `GET /api/admin/reference-data`.
- [ ] Решить F-09 (роль `OWNER`) — привести права к существующим ролям.

**Каркас SPA** (ADR-0006, 0009, 0010, 0012)
- [ ] HTTP-клиент: CSRF, `Accept-Language`, обработка `401/403/429/ProblemDetail`.
- [ ] Сессия и гарды роутов; редирект на текущую Thymeleaf-страницу `/login?redirect=`.
- [ ] i18n-инфраструктура (react-i18next, три языка, проверка полноты в CI).
- [ ] Файл токенов с as-is значениями; `<AdminLayout>`, `<PublicLayout>`; тосты; модалка; `<NivelSelect>`.
- [ ] STOMP-клиент и хук подписки (пока без потребителей).
- [ ] Экраны `NotFound`, `Forbidden`, `RateLimited`, `ServerError`.

**Процесс**
- [ ] Правила фронта в `.agents/CODE_REVIEW.md`; обновить `.agents/roles/developer.md`, `tester.md`; шаблон фиче-спеки — раздел «экран из contract/screens.md».
- [ ] Обновить `.agents/PROJECT.md` (стек, команды, где фронт) и исправить F-11.

**Готово, когда:** прод работает как раньше; `mvn package` даёт jar с `/app/`; скрытый служебный маршрут (например `/admin/_spa-health` для SUPER_ADMIN) рендерит SPA в `<AdminLayout>` с данными из `/api/auth/session`; CI проверяет типы API и словари.

**Откат:** убрать плагин из `pom.xml` — бэкенд не зависит от фронта.

## Фаза 1. Пилот — клубы (M)

Экраны A-13, A-14, A-15. Выбраны потому что: простой CRUD, только админы, нет SEO и realtime, API почти есть (`/api/clubs`), но требует правки прав для `CLUB_ADMIN` ([api.md §3](contract/api.md#3-расхождения-в-правах-доступа-проверить-до-перевода-экрана)) — то есть пилот проверит весь путь: права → DTO → OpenAPI → типы → экран → тесты → деплой → откат.

**Готово, когда:** клубы в проде на React ≥ 2 недель без регрессий; хотя бы один из трёх экранов сделан конвейером `/develop-feature` от спеки до PR; откат через `app.spa.routes` проверен на стейдже/локально; по итогам пилота обновлены правила в `CODE_REVIEW.md` и, если нужно, ADR.

## Фаза 2. Админка (XL)

Порядок: A-18 telegram-pipeline (разминка) → A-16/A-17 игроки → A-01 панель → A-02 список турниров → A-03 форма турнира (заодно #384 — даты в ISO) → A-06 платежи → A-05 сетка → **A-04 детали турнира** (самый большой экран, 1 856 строк; вход во все пульты) → A-19 экспорт (только ссылка).

**Готово, когда:** вся админка, кроме пультов форматов, на React; JSON-эндпоинты под `/admin/**` перенесены под `/api/admin/**`.

## Фаза 3. Live-форматы (XL, высокий риск)

Порядок по готовности API и риску:
1. **King of Court** A-07 + L-01 — API и WebSocket уже есть, не хватает `reset`/`start`.
2. **Americano** A-08, A-09 + L-02, L-03 — API почти весь есть; предпросмотр перестаёт быть «ответом на POST».
3. **Team Americano** A-10, A-11 + L-04 — перенос `/tournaments/team-americano/api/**` под `/api/`; попутно закрываются #334, #329.
4. **Team Playoff** A-12 + L-06 — **последним**: самый сложный и самый используемый прямо сейчас пульт (очередь матчей, swap, две колонки квалификации, WebSocket, экспорт сетки).

Правила фазы:
- админские страницы форматов закрываются ролями (#391) сразу при переводе;
- публичные табло требуют публичного read-only API ([api.md §2.2](contract/api.md#22-публичное-чтение-фаза-35));
- черновики счёта не теряются при обрыве сети (сейчас `localStorage` по matchId);
- переключение — между турнирами; на первом турнире организатор знает про `/legacy/...`;
- по каждому формату — Playwright-сценарий «провести мини-турнир от инициализации до финиша».

**Готово, когда:** каждый формат прошёл ≥ 2 реальных турнира на React без отката.

## Фаза 4. Игрок (L)

U-01 дашборд → U-02 профиль → P-11 принять пару → сброс пароля (F-d, новый роут вместо модалки на лендинге) → P-02 **вход** (JSON-логин, ADR-0005) → P-03 **регистрация** (починить F-07, reCAPTCHA/honeypot/rate limit на JSON-пути) → P-10 (если F-06 решён «оставить»).

Входящие ссылки из писем ([cross-cutting.md §5](contract/cross-cutting.md#5-входящие-ссылки-которые-нельзя-сломать)) — проверить каждую вручную после перевода.

**Готово, когда:** весь путь игрока «регистрация → подтверждение email → вход (форма и Google) → запись на турнир (соло/пара/ищу пару) → отмена» проходит Playwright-сценарием на React.

## Фаза 5. Публичные SEO-страницы (L)

Перед стартом — вернуться к ADR-0008 (открытые вопросы). P-09 legal → P-06/P-07 клубы → P-08 рейтинг → P-04 список турниров → **P-05 карточка турнира** (серверная подстановка OG) → P-01 лендинг (с учётом решения `DESIGN.md` §10 о продающем лендинге).

**Готово, когда:** превью ссылки на конкретный турнир в WhatsApp/Telegram показывает его название/формат/картинку; Lighthouse мобильный ≥ 90 по Performance/SEO для P-05.

## Фаза 7 (вне плана). Вынос фронта в отдельный сервис

Когда появится причина (отдельный цикл релизов, CDN, отдельная команда). Шаги — в [ADR-0003 «Путь выноса»](adr/0003-serve-spa-from-spring-boot.md#путь-выноса-в-отдельный-сервис-когда-понадобится). Код фронта и API не меняются.

## Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Регрессия на live-пульте во время турнира | средняя | Переключение между турнирами; `/legacy/...`; Playwright-сценарий турнира; Team Playoff последним |
| Потеря поля/действия при переносе | средняя | `screens.md` как чек-лист приёмки в каждой спеке; Tester сверяет по нему |
| Превью ссылок на турниры станут одинаковыми | высокая, если не думать | Публичные страницы — последними, ADR-0008 |
| Права: CLUB_ADMIN/ORGANIZER теряют доступ после перехода на REST | высокая | [api.md §3](contract/api.md#3-расхождения-в-правах-доступа-проверить-до-перевода-экрана); права view-контроллера — эталон |
| Разъезд API и фронта | средняя | Генерация типов + проверка в CI (ADR-0004) |
| Бандл тяжёлый для мобильного интернета | средняя | `size-limit` в CI, ленивые разделы |
| Переходный период затягивается на годы | средняя | Каждая фаза самоценна; можно остановиться после Фазы 3 (главная выгода — пульты) и оставить публичную часть на Thymeleaf (запасной вариант ADR-0008) |
| Конвейер `/develop-feature` не умеет фронт | средняя | Фаза 0: Node в облачной среде, правила в `CODE_REVIEW.md`, пилот Фазы 1 — через конвейер |
| Сборка в Docker/CI замедлится | низкая | Кэш npm, флаг пропуска фронта для бэкенд-итераций |

## Как отслеживать прогресс

- Сводная таблица [screens.md](contract/screens.md) — колонка «Фаза» → `✅ React, PR #…` по мере перевода.
- GitHub: milestone `React migration`, метка `frontend-react` на issue экранов.
- В конце каждой фазы — короткая запись в этот файл: что сделано, что пошло не так, что меняем в плане.
