# Первичный прогон UI v2 от 18 ноября 2026

Историческая запись первого прохода. Последующая реализация и повторная приёмка текущего оформления описываются отдельно; нижеследующие замечания относятся к исходному коммиту c473b92.

Статус общей приёмки — **есть препятствия для выпуска**. Запись, кабинет, отмена и история работают в проверенной сборке. В переходах между экранами воспроизведены три разрыва. Требуется также совместить изменения с актуальной основной веткой и повторить затронутые проверки. Приложение и production-конфигурация в рамках этой ревизии не изменялись.

## Уточнение владельца: актуальный дизайн и кабинет с рейтингом

После функционального прогона владелец уточнил обязательный критерий: новые изменения должны дополнять текущий сайт и переработанный кабинет с рейтингом, сохраняя действующее оформление. Прежняя зелёная версия UI v2 сама по себе больше не является основанием для визуальной приёмки или замены кабинета. Ранее подтверждённые сценарии записи подтверждают только поведение в проверенной сборке.

Сверка кода с origin/master на 3c16455 показала:

- В актуальном players/dashboard.html подключён fragments/elo-preview.html. Карточка игрока содержит Elo, место в категории и общем списке, достижения, историю турниров и график изменения рейтинга. Показ зависит от доступности рейтинга для игрока.
- В актуальном elo-preview.css у кабинета есть отдельное оформление: тёплый оранжевый заголовок, фиолетовые акценты и светлый фон. В проверенном frontend/src/styles/tokens.css остаётся самостоятельная зелёная палитра и шрифт Manrope.
- PlayerEventsPage.tsx проверенной React-сборки отображает мероприятия и действия с регистрацией. Он не переносит перечисленные блоки рейтингового кабинета. Его функциональный проход не подтверждает равноценность замены действующего кабинета.

Это сверка кода. Визуальное сравнение с действующим авторизованным кабинетом, включая различия между участником рейтингового пилота и обычным игроком, ещё не проведено. Если последние согласованные изменения находятся в другой незавершённой ветке, их также нужно включить в эталон до подготовки кандидата.

Дополнительные обязательные условия выпуска:

1. Зафиксировать актуальные экраны сайта и кабинета как эталон: цвета, шрифты, шапка, карточки, мобильная компоновка и рейтинговые блоки.
2. Сохранить действующий кабинет с рейтингом до подтверждения полной функциональной и визуальной совместимости его замены. Новые действия с регистрацией должны дополнять его.
3. Проверить сохранность рейтинга, достижений, графика, истории и прав доступа в актуальной интегрированной сборке, а также сценарий игрока без рейтингового пилота.
4. Оценивать #1189, #1190 и #1192 с учётом этой границы. Переход на действующую страницу сам по себе не означает, что её следует заменить зелёной React-версией. Решение о целевом экране принимается после сверки; существующие замечания не являются поручением переключить кабинет.
5. Повторную приёмку владельца проводить на согласованном оформлении. Переключение production-маршрутов требует отдельного решения.

| Вход и возврат | POST /login, destination, карточка /preview/torneo/{id} | Вход возвращает обычного игрока в ту же карточку |
| React-форма входа из шапки | /preview/login, POST /login, GET /api/auth/session | Данные приняты, сессия PLAYER создана; без destination открывается прежний кабинет — #1192 |
| Профиль | GET/PUT /api/players/me, /preview/perfil | Сохранение фамилии синтетического игрока подтверждено HTTP 200 и refresh; затем исходная фамилия восстановлена |
| Индивидуальная запись | POST /players/tournaments/{id}/register, чтение my-registration | Создана заявка в резерве заполненного мероприятия, интерфейс показывает серверную позицию |
| Кабинет после записи | GET /api/players/me/events, /preview/players/dashboard | Заявка видна в предстоящих, сохраняется после refresh |
| Выход из турнира | POST /api/players/me/events/{registrationId}/withdraw | Подтверждение в диалоге, HTTP 204, заявка переходит в историю |
| Повторная запись | Те же карточка, API и кабинет | Предстоящая заявка создана повторно, предыдущая отмена остаётся в истории |
| Отмена готовой пары | POST /api/tournaments/double/{id}/pair-cancellation | Пара снята, следующая готовая пара из резерва переведена в основу |
| Ответ после продвижения | POST /api/players/me/participation/{id} | Игрок подтверждает участие в кабинете, статус сохранён |
| Чужое подтверждение | Тот же API из сессии постороннего игрока | HTTP 404, чужой ответ недоступен |
| Поиск партнёра | register-solo, looking-for-partner, кабинет | Одиночная заявка доступна, её можно отменить из кабинета |
| Видимость контактов | PUT /api/players/me/events/{id}/contact-visibility | Включение сохраняется после refresh, после выключения публичный список скрывает телефон |
| Статус оплаты | Синтетический платёж PAID, API кабинета | Оплата показана своему игроку, другому игроку этот статус не показан |
| Live Team Playoff | Реальный публичный snapshot и STOMP/WebSocket | Новая версия результата получена, переподключение после перезапуска собственного шлюза прошло, refresh сохраняет состояние |
| Выход из аккаунта | POST /logout, затем переход на вход | Интерфейс показывает завершение сессии и форму повторного входа |

Для проверки оплаты тестовый платёж подготовлен непосредственно в выделенной базе. Действие кассира в админке в этот сценарий не входит. Для проверки live результат сохранён через действующий API управления собственным синтетическим турниром.

Сценарии новых форм из #909 ранее прошли на том же коммите — готовая пара с существующим игроком и гостем, добавление партнёра позже, предложение пары, отказ с сохранением обеих заявок, принятие с итогом WAITLIST, восстановление записи после потери ответа. Владелец подтвердил проход записи и обоих ответов на физическом iPhone в этом чате. Эта проверка покрывает указанную часть #909.

## Браузер, языки и доступность

В Chromium пройдены ES/RU/EN на ширинах 320, 390 и 1440 px. В форме поиска партнёра отсутствует горизонтальное переполнение, поля имеют подписи. Клавиша Tab переводит фокус из поиска на найденного игрока. Проверено предпочтение reduced motion.

Диалог выхода из индивидуального турнира проверен на ширине 390 px. Он помещается в экран, фокус после открытия находится внутри диалога. Отдельно пройдены мобильные сценарии общего браузерного набора.

Это проверка DOM, клавиатуры и размеров. Озвучивание VoiceOver и полный аудит экранным диктором ещё требуется. Проверка физического iPhone для кабинета, диалога отмены и истории подготовлена отдельно. Реальный Android в этой среде недоступен.

## Репетиция выпуска и отката

automation/releases/rehearse.py завершилась успешно на исходном коммите c473b92. Подтверждены два синтетических выпуска, загрузка прежнего lazy chunk из открытой вкладки, ручной rollback, автоматическое восстановление после отсутствующего chunk и недоступного readiness, восстановление незавершённого переключения по журналу. В конце восстановлен исходный снимок стенда.

Безопасный локальный отчёт — target/release-rehearsal/report.json. Технические свидетельства живого прогона и responsive находятся в target/ui-v2-acceptance/. Доступы и токены хранятся только в игнорируемом runtime.

В промежуточном results.json сохранены два таймаута сценарного скрипта. Проверки оплаты и адаптивности после исправления ожиданий и разделения браузерных контекстов выполнены отдельно: итоговые свидетельства — payment.json и responsive.json. Проверка клиентских страниц отражена в navigation.json; вход и фактический переход — в login.json. Общий результат приёмки определяется данным отчётом, а не одной промежуточной попыткой.

## Замечания

1. [#1189](https://github.com/UstinKO/padel-core-service/issues/1189). Обычный игрок открывает отдельную карточку, затем переходит через меню в каталог. Клиентский переход работает, refresh или прямой вход в /preview/torneos получает 403. Аналогично главная, клубы и юридические страницы. Необходимо согласовать доступные игроку страницы закрытой приёмки и согласовать поведение меню и HTTP-маршрутов.
2. [#1190](https://github.com/UstinKO/padel-core-service/issues/1190). Название мероприятия в новом кабинете использует /torneo/{id} и открывает прежнюю страницу. Для закрытой версии требуется переход в /preview/torneo/{id} с сохранением языка.
3. [#1192](https://github.com/UstinKO/padel-core-service/issues/1192). Вход через шапку нового интерфейса успешен, однако без destination по умолчанию открывается /players/dashboard прежнего интерфейса. Требуется согласовать возврат в закрытый кабинет, сохранив правила обычных production-адресов.
4. Совместимость с master. Текущая основная ветка содержит последующие изменения. Для принятия выпуска потребуется актуальная интегрированная сборка, разрешение найденных конфликтов и повторная проверка изменённых сценариев.
5. Остаток ручной приёмки. Физический iPhone для кабинета и истории, VoiceOver и реальный Android остаются явно непроверенными. Проход владельца по #909 учитывается только для записи и ответа на предложение. Создание нового аккаунта и восстановление пароля в React-формах покрыты моделируемыми E2E, но их полный живой проход в этом прогоне не подтверждён; общий путь ограничен правилами #1189.

## Порядок продолжения

Сначала согласовать эталон текущего сайта и кабинета с рейтингом и состав недостающих функций проверенной версии. С учётом этого пересмотреть решения #1189, #1190 и #1192, внести необходимые изменения отдельными задачами, совместить ветки с актуальным master и повторить затронутые сценарии. Затем завершить ручную проверку устройств и зафиксировать решение владельца о каждом выпускаемом маршруте. Общая задача #913 остаётся открытой.

Для владельца в локальном закрытом контуре подготовлена отдельная запись «Preview 5». На странице входа со ссылкой на кабинет нужно войти синтетическим игроком из локального файла доступа, открыть мероприятие «Preview 5», нажать «Выйти из турнира» → «Подтвердить», затем «История». Ожидается «Запись отменена», сохраняющаяся после обновления. Доступ с частной сети проверен: без внешнего пароля возвращается 401, с доступом открываются вход и кабинет. Пароли в отчёт не включены. После уточнения дизайна этот дополнительный проход необязателен: он не является визуальным акцептом и не разрешает заменить действующий кабинет. Для окончательной приёмки нужна обновлённая сборка по критериям выше.
