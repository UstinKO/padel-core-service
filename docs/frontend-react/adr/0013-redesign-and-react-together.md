# ADR-0013. Новый дизайн и React — одним ходом: экран переводится один раз, сразу в новом стиле, через демо и акцепт заказчика

- **Статус:** Принято (2026-10-26, решение пользователя)
- **Дата:** 2026-10-26
- **Заменяет:** [ADR-0012](0012-design-tokens.md) целиком; [ADR-0007](0007-incremental-migration.md) п. 2 (порядок) и п. 7 (визуальный стиль «как есть»); [ADR-0003](0003-serve-spa-from-spring-boot.md) п. 2 (префикс статики `/app/`)
- **Связано:** [0001](0001-react-spa.md), [0008](0008-seo-public-pages.md), [план](../plan.md), `.agents/DESIGN.md`

## Контекст

ADR-0012 предлагал переносить экраны на React в текущем виде, а новый дизайн накатывать потом заменой значений токенов. Отказ от варианта «сразу в новом дизайне» держался на том, что палитра не выбрана.

2026-10-26 заказчик прислал [сетку страниц нового UI](../design-grid.md) — кликабельные демо основных страниц, King of Court и Americano. Дизайн будет согласован до начала переезда. Перенос «как есть» с последующей перерисовкой означает, что каждый экран делается дважды. Пользователь это отверг: «переводить старые страницы на React, а потом их править — пустая трата ресурсов».

Кроме того, `/app/` с LFPT-0637/0643 занят веб-сборкой клиента 1Padel.App (Expo) — префикс статики из ADR-0003 недоступен.

## Решение

1. **Каждый экран переводится один раз — сразу на React и сразу в новом дизайне.** Никаких React-копий старого вида и никакого редизайна Thymeleaf-шаблонов. Thymeleaf-страницы до своего перевода не трогаются визуально (только баги).
2. **Этапы:**
   1. **Варианты дизайна** — статичные кликабельные макеты (HTML) по [сетке заказчика](../design-grid.md), 2–3 направления → заказчик выбирает и правит направление. Сетка задаёт только расположение и состав контента — во всех направлениях оно идентично сетке; визуальный стиль демо заказчика не берётся (он плоский и несовременный), стиль — тот, что будет согласован. Итог фиксируется в `.agents/DESIGN.md` (токены и компоненты размораживаются).
   2. **Демо на React** — несколько кликабельных **закрытых** страниц, уже на настоящем стеке (ADR-0006) и в утверждённом дизайне. Это первые реальные экраны, а не одноразовый прототип: после акцепта они дорабатываются до боевых.
   3. **Акцепт дизайна заказчиком** по демо → старт плавного перехода.
   4. **Переход экран за экраном:** сделать экран → проверить → согласовать с заказчиком (демо на закрытом адресе) → переключить боевой URL на новую версию → старую отключить.
3. **Закрытый демо-контур.** Новые экраны до переключения живут под служебным префиксом `/preview/<исходный путь>`, доступным только `SUPER_ADMIN` (и, при необходимости, отдельному демо-аккаунту заказчика). Боевой URL в это время по-прежнему отдаёт Thymeleaf. Данные — из реального API; где API экрана ещё нет — фикстуры на стороне фронта с явной пометкой «демо-данные».
4. **Переключение** — как в ADR-0003/0007: путь добавляется в `app.spa.routes`, боевой URL начинает отдавать React. Старая страница уходит на `/legacy/...` на срок из ADR-0007 п. 4, затем удаляется. URL страниц для пользователей не меняются (ссылки из писем, Telegram, QR).
5. **Порядок экранов** определяет не риск-порядок старого плана, а приоритет заказчика и состав согласованной [сетки](../design-grid.md). Ограничения остаются: live-пульты переключаются только между турнирами; публичные индексируемые страницы переключаются только после серверной подстановки meta/OG (ADR-0008) — эта часть фундамента нужна до первого публичного экрана.
6. **Токены** — CSS-переменные с именами и **значениями из утверждённого `.agents/DESIGN.md`** (не as-is). Светлая и тёмная тема — с первого экрана, если их утвердит дизайн. Структурные пункты `DESIGN.md` §3 (единый layout, одна иконочная система) реализуются только в React.
7. **Префикс статики SPA — `/web/`** (`vite base: '/web/'`) вместо `/app/`, занятого 1Padel.App.
8. **Конечное состояние:** на Thymeleaf остаются только письма (`templates/email/*`). Весь веб-UI, включая админку и пульты, — React. `test/tournaments` — по ADR-0007 (не переносится, удаляется когда станет не нужен).

## Отвергнутые альтернативы

| Вариант | Почему нет |
|---|---|
| React «как есть», редизайн потом (ADR-0012) | Каждый экран делается дважды |
| Сначала редизайн Thymeleaf, потом React | То же самое: двойная работа |
| Демо-прототип на отдельном стеке (Figma/HTML) до акцепта, потом код с нуля | Допустимо только для выбора направления (этап 2.1). Демо для акцепта — уже на React, чтобы демо-код стал боевым |
| Big bang: весь новый UI в ветке, переключение разом | Те же причины, что в ADR-0007 |

## Последствия

- Фундамент (Фаза 0 плана) нужен **до** демо: сборка фронта в jar, раздача `/web/`, `/preview/**` под `SUPER_ADMIN`, каркас SPA, токены из `DESIGN.md`.
- Переходный период — два визуальных стиля на одном сайте (новые экраны в новом, старые в старом). Принимаем; шапку/футер новых экранов делать так, чтобы переход между старой и новой страницей не терял навигацию.
- Перевод экрана — уже не «перенос как есть»: в спеке экрана к чек-листу `contract/screens.md` (что нельзя потерять) добавляется макет экрана из согласованного дизайна. Поведение и бизнес-логика по-прежнему не меняются в рамках перевода; новые фичи — отдельными спеками.
- Каждое переключение — после согласования заказчиком: в процесс экрана добавляется шаг «демо на `/preview/...` → акцепт».
- Палитра 1Padel.App (`mobile-app/src/theme.ts`) и веб должны прийти к одному бренду — учитывать при выборе направления дизайна.
