# ADR-0005. Аутентификация SPA — серверная сессия + CSRF-cookie, same-origin; JWT только для мобильных

- **Статус:** Предложено
- **Дата:** 2026-09-28
- **Связано:** [0003](0003-serve-spa-from-spring-boot.md), [cross-cutting.md §1–2](../contract/cross-cutting.md#1-вход-сессия-роли), `docs/auth-flow.md`

## Контекст

В системе уже три способа войти: form login (сессия `JSESSIONID`), Google OAuth2 (тоже сессия + принудительный remember-me, #297), JWT (`/api/auth/login`, access 24ч / refresh 7д, `JwtAuthenticationFilter`). Remember-me общий для формы и Google. CSRF — cookie `XSRF-TOKEN`, читаемая JS, без маскирования (сделано специально под `csrf.js`, см. комментарий в `SecurityConfig`). CSRF отключается для запросов с `Authorization`.

Во время переезда старые и новые страницы работают **одновременно** под одним доменом — пользователь не должен логиниться отдельно для «новой» части.

## Решение

1. **SPA использует ту же серверную сессию**, что и Thymeleaf-страницы: `JSESSIONID` + remember-me, `SameSite=Lax`, `HttpOnly`. Никаких токенов в `localStorage`/`sessionStorage`.
2. **CSRF — как сейчас:** HTTP-клиент SPA читает `XSRF-TOKEN` и ставит `X-XSRF-TOKEN` на `POST/PUT/PATCH/DELETE` (включая `/login` и `/logout`). Серверную конфигурацию CSRF не трогаем.
3. **Вход:** тот же `POST /login` (`username`, `password`, `remember-me`, form-urlencoded). Success/failure-хендлеры отвечают JSON-ом, если запрос пришёл с `Accept: application/json` (`200` + данные сессии / `401 {code: BAD_CREDENTIALS | NOT_CONFIRMED}`), иначе — редиректы, как сейчас. Так старая страница входа и новая форма работают на одном эндпоинте. Rate limit на `POST /login` для JSON — `429`, не редирект (F-10).
4. **Google:** без изменений — полная навигация на `/oauth2/authorization/google`, после успеха редирект на `app.frontend-url` + `/players/dashboard`.
5. **`GET /api/auth/session`** — единый источник «кто я» для SPA (один формат для игрока и админа, [api.md §4.2](../contract/api.md#42-что-изменить-на-бэкенде-фаза-0)).
6. **`/api/**` без аутентификации → `401` JSON** (сейчас `302 /login`, F-08); `403` — JSON (уже так). Клиент на `401` уводит на `/login?redirect=…`.
7. **JWT остаётся для мобильных клиентов** и API-интеграций. Веб его не использует.
8. **Пока экран входа не переведён (до Фазы 4)**, React-экраны используют текущую Thymeleaf-страницу `/login`: сессия общая, после входа пользователь попадает на нужный экран.

## Отвергнутые альтернативы

| Вариант | Почему нет |
|---|---|
| **JWT в `localStorage` для SPA** | Токен доступен любому XSS; нужна своя логика refresh; две параллельные модели входа (Thymeleaf-страницы остаются на сессии весь переходный период); remember-me и Google OAuth пришлось бы переделывать |
| **JWT в HttpOnly-cookie** | По безопасности эквивалентно сессии, но это новый механизм (ротация, отзыв, CSRF всё равно нужен) без выигрыша при одном домене |
| **Отдельный JSON-эндпоинт входа `/api/auth/session-login`** | Второй путь входа с отдельными rate-limit/audit/remember-me — больше мест для расхождений. Content negotiation на существующем `/login` дешевле |
| **Spring Session (Redis/JDBC)** | Нужен только при нескольких инстансах; решено оставаться на одном (2026-09-06). Решение не блокирует его подключение позже |

## Последствия

- Сессия in-memory в Tomcat: рестарт при деплое разлогинивает тех, у кого нет remember-me (как и сейчас).
- Вынос фронта в отдельный сервис **на том же домене** ничего не меняет в аутентификации (ADR-0003). На **другой** домен — только через новый ADR.
- Тестам (Vitest/Playwright) нужен помощник логина через `POST /login` с CSRF.
