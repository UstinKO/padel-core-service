# Выпуск UI v2 и восстановление

Механизм доставляет backend, React index и граф ресурсов одним неизменяемым образом. Он используется штатным `deploy.yml` и закрытым [preview-контуром](ui-v2-preview.md). Управляемый production-выпуск принимает пустой список маршрутов либо единственный согласованный маршрут `/players/dashboard`. Публичная главная сохраняет Thymeleaf. Профиль `preview` по-прежнему требует пустого списка, доступ к его экранам определяется ролями.

## Артефакт

После `./mvnw verify` команда `python3 automation/releases/build.py --revision "$(git rev-parse HEAD)"` создаёт:

- `target/release-manifest.json`: Git SHA, SHA-256 jar, хеши всех React/Expo-файлов, пустой список переопределений SPA routes со стороны упаковки. Принятый маршрут кабинета задан в production-конфигурации приложения и проверяется при запуске. Vite manifest включает статические и динамические imports; отсутствие любого узла отклоняет артефакт. Expo сравнивается с существующей сборкой в исходниках.
- `target/release-<revision>.tar.gz`: только `image.tar` и манифест с уникальным тегом загружаемого образа. Runtime закреплён digest; метки образа связывают revision и SHA-256 jar. Каждая сборка получает уникальный tag, поэтому повторная сборка той же ревизии не переназначает ссылку сохранённого образа.
- `target/release-runner.pyz`: автономный runner Python 3.9+ без сторонних зависимостей. Включает только разрешённые модули выпуска и существующий конфигуратор Meta; код QA и секреты не упаковываются.

CI передаёт эти файлы в выделенный каталог доставки. На сервере образ после загрузки ищется по тегу, затем проверяется по меткам и фактическому jar. Снимок выпуска фиксирует локальный ID образа. Выпуск проходит без пересборки и без подстановки новых зависимостей. Пакеты репетиции с синтетическими module probes отклоняются.

## Состояние и границы

Runner использует существующие `docker-compose.yml`, `.env`, Compose project и сервис `padel-app`. Перед первым переключением сохраняет работающий образ и фактическое окружение контейнера как baseline. Read-only инвентаризация показала, что серверный Dockerfile отличается от Dockerfile репозитория; выпуск не заменяет его и не предполагает одинаковую сборку. Runtime сохраняет прежние UID/GID 100:101 и TZ Europe/Moscow, чтобы продолжать писать существующие логи без изменения владельцев файлов.

Внутри `releases/<случайный id>/` находятся снимки jar, разрешённой Compose-конфигурации, env/secrets и их контрольные суммы. Эти файлы приватные, не входят в репозиторий, CI artifacts или публичный манифест. Каталоги состояния закрыты; файл Docker secret доступен контейнеру только внутри такого каталога. Логи runner показывают тип ошибки без конфигурации, токенов и аргументов подключения.

`release-state/` содержит current/previous, lock и журнал pending. Блокировка отклоняет параллельное переключение. Журнал и указатели записываются через fsync/atomic replace. Candidate проверяется до изменения контейнера, после запуска проверяются:

- readiness с ограниченным ожиданием и `X-Release-Revision`;
- SHA-256 реальных HTTP-ответов всех React-ресурсов и Expo index;
- immutable для hashed assets, перепроверка index, 404 для отсутствующего JS;
- прежняя публичная главная и действующая конфигурация Meta в штатном выпуске.

Успешная версия публикуется после smoke. Ошибка восстанавливает предыдущие образ, Compose/env и метаданные и повторяет smoke. Ошибка восстановления сохраняет pending и возвращает ненулевой код. После принудительного завершения процесса нужен `recover`; журнал позволяет закончить восстановление, но не заменяет запуск этой команды оператором.

Перезапускается только приложение с `--no-deps --no-build --pull never`; БД и зависимые контейнеры не пересоздаются. Zero-downtime не обещается. **Миграции и пользовательские данные не откатываются:** выпуск должен сохранять совместимость схемы с предыдущей версией. При первом запуске без предыдущего снимка успешный rollback не заявляется.

`/web/assets/**` сначала обслуживается из jar, затем из readonly-каталога сохранённых chunks. Коллизия одного имени с другими байтами отклоняется. Старые chunks не удаляются автоматически: это сохраняет отложенные imports в открытых вкладках. Sourcemaps не архивируются, поскольку не нужны runtime и могут измениться без изменения JS. За объёмом каталога ресурсов нужно следить отдельно.

После подтверждённого выпуска сохраняются current, previous и исходный baseline. Очистка касается только собственных завершённых снимков; Docker image удаляется без force и не удаляется при использовании другими контейнерами. Общий prune не выполняется.

## Ручное восстановление

Выполняется уполномоченным оператором в существующей среде; обычная реализация задачи не включает боевой запуск этих команд.

```sh
# Закончить восстановление незавершённого переключения.
python3 /opt/padel-app/temp/release-runner.pyz recover --root /opt/padel-app

# Вернуть предыдущий подтверждённый выпуск.
python3 /opt/padel-app/temp/release-runner.pyz rollback --root /opt/padel-app

# Для автоматического отката обязательно проверить ожидаемую текущую ревизию.
python3 /opt/padel-app/temp/release-runner.pyz rollback \
  --root /opt/padel-app --revision <полный-Git-SHA>
```

До повторного выпуска проверить `current_version.txt`, readiness и результат команды. Не редактировать вручную снимки/указатели и не запускать `docker compose build/up` в обход механизма. Если восстановление не подтверждено, сохранить pending и диагностировать причину; повторный `recover` использует прежний снимок. Источник для восстановления должен оставаться доступным на диске и в Docker.

Workflow автоматически откатывает candidate при неуспешном smoke/readiness. Если после принятого выпуска падает очистка Cloudflare, отдельный шаг откатывает только ожидаемую текущую ревизию; он не затрагивает более новый выпуск. Ошибка очистки старых локальных артефактов не объявляет проверенное приложение неработающим.

## Проверка в изолированном контуре

`automation/releases/rehearse.py` использует тот же transaction/adapter/runtime-образ, настоящий backend, синтетическую PostgreSQL и Chromium. Две QA-версии отличаются невидимым module probe; их ревизии синтетические, исходный Git SHA указан отдельно в `target/release-rehearsal/report.json`. Проверяются переключение A → B, ещё не загруженный lazy chunk A после B, ручной rollback, реальные HTTP 404/503 и восстановление журнала после замены контейнера. В конце восстанавливается baseline.

Проверка `automation/ui-preview/check.py` отдельно подтверждает роли guest/PLAYER/SUPER_ADMIN, refresh/deep link, данные, cache headers, Expo и прежнюю публичную главную. CI выполняет её перед репетицией. Это проверка выделенного локального контура; фактический production deploy и пользовательская приёмка оформляются отдельно.
