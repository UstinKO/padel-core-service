# План переноса фронтенда — padel-core-service

> ⚠️ **Заменён** каталогом [frontend-react/](frontend-react/README.md) (2026-09-28). Этот план исходил из микросервисов и gateway; 2026-09-06 решено остаться на монолите. Документ оставлен как история — актуальные решения в `frontend-react/adr/`.

> **Статус:** черновик v1 (2026-07-22) — зафиксирован подход к захвату as-is дизайна и области исключений. Детальные фазы переноса — по мере заведения задач (по аналогии с [планом перехода на микросервисы](microservices-migration-plan.md)).
> **Куда переезжаем:** текущий server-rendered Thymeleaf UI → отдельный React-фронтенд, обращающийся к бэкенду через gateway (Traefik, см. Фазу 0 бэкенд-плана) и далее по цепочке к сервисам/монолиту в зависимости от того, что уже вынесено на момент переноса конкретного экрана.
> **Подход:** дизайн as-is, не редизайн — стили сейчас несогласованы (см. [дизайн-токены as-is](design-tokens-as-is.md)), но исправление этого — побочный эффект переноса, не отдельная дизайнерская задача.
> **Связанные документы:** [дизайн-токены as-is](design-tokens-as-is.md), [архетипы экранов](screen-archetypes.md), [план перехода на микросервисы](microservices-migration-plan.md).

## 1. Сделано на сегодня

1. **Дизайн-токены as-is** — свёл цвета/типографику/отступы/радиусы/тени из 14 CSS-файлов в один канонический документ, с явным маппингом дублей (`admin.css` → `style.css`) и списком "дрейфа" (посторонние цвета, рассинхронизированные радиусы). Готов к прямому переносу в Tailwind-конфиг или CSS-переменные React-проекта.
2. **Архетипы экранов** — все 56 Thymeleaf-шаблонов сгруппированы в 13 layout-архетипов, чтобы захватывать в Figma по одному репрезентативному экрану на архетип, а не все 56 по отдельности.
3. **Инструмент захвата выбран:** Figma + плагин `html.to.design` — конвертирует живые страницы в редактируемые Figma-фреймы без ручной перерисовки.

## 2. Область переноса и три исключения

Из 56 шаблонов **не все становятся React-экранами**. Ниже — явные решения по трём категориям, которые не проходят по общему процессу "Figma-фрейм → React-компонент":

### 2.1. Email-шаблоны (11 файлов, `templates/email/*`) — НЕ переносятся

`bienvenida`, `confirmacion`, `tournament-confirmation`, `new-partner-invitation`, `looking-for-partner-notification`, `pair-proposal`, `partner-data-reminder`, `vacancy-invitation`, `waitlist-notification`, `no-spots-left`, `admin-solo-registration`, `recuperar-password`.

**Решение:** остаются server-side Thymeleaf HTML вне зависимости от того, куда переезжает остальной фронтенд — email-клиенты (Gmail, Outlook и т.д.) не рендерят React/SPA, письма физически должны быть статическим HTML с инлайновыми стилями. По [плану перехода на микросервисы](microservices-migration-plan.md) эти шаблоны переезжают вместе с `EmailService` в `notification-service` (Фаза 4), но остаются на Thymeleaf и там — это ортогонально фронтенд-переносу.

**Единственная точка пересечения с фронтенд-работой:** сверить цвета/шрифты email-шаблонов с `design-tokens-as-is.md`, чтобы бренд не разъехался ещё больше между вебом и письмами — небольшая отдельная задача, не блокирует остальной перенос.

### 2.2. Layout-фрагменты (6 файлов, `templates/fragments/*`) — НЕ отдельные экраны, становятся shared-компонентами

`public-header.html`, `public-footer.html`, `admin-header.html`, `admin-footer.html`, `king-of-court-modals.html`, `nivel-options.html`.

**Решение:** это не экраны для мокапа, а переиспользуемые куски разметки — в React превращаются в компоненты дизайн-системы, которые собираются один раз в начале переноса, а не мокапятся отдельно по архетипам:
- `public-header.html` + `public-footer.html` → `<PublicLayout>` (обёртка для всех публичных экранов из §1-2 архетипов)
- `admin-header.html` + `admin-footer.html` → `<AdminLayout>` (обёртка для всех admin-экранов из §4-5 архетипов)
- `king-of-court-modals.html` → переиспользуемые модальные компоненты (`<ResultModal>` и т.п.), общие для live-контроля KoC
- `nivel-options.html` → переиспользуемый `<NivelSelect>` (выпадающий список уровней игры), используется в нескольких формах

Эти компоненты — фактически первое, что стоит собрать в React-проекте (до переноса самих экранов), т.к. каждый экран из архетипов на них опирается.

### 2.3. `test/tournaments.html` (1 файл, 3158 строк) — НЕ переносится

Внутренний dev-инструмент для организатора (регистрация тестовых игроков, создание пар, debug-эндпоинты) — работает напрямую через JDBC (`DataSource`), в обход JPA, согласно `.agents/PROJECT.md`. По аналогии с решением из i18n-плана ("не переводим — dev-инструмент, только для организатора") — **не переносится в React**, остаётся Thymeleaf-страницей, доступной так же, как сейчас.

**Открытый момент:** если после переноса основного UI на React понадобится держать этот инструмент — он либо продолжает жить как отдельная Thymeleaf-страница поверх бэкенда (не мешает остальному стеку, т.к. полностью изолирован по функциональности), либо не переносится вообще и на каком-то этапе удаляется, если перестанет быть нужен для тестирования. Решается по факту, не блокирует перенос остального.

## 3. Что дальше (детализируется по мере заведения задач)

Следующие шаги, но без разбивки на подробные фазы до момента, когда работа реально начнётся:

- Собрать shared-компоненты (§2.2) в React-проекте на основе токенов из `design-tokens-as-is.md`.
- Прогнать репрезентативные экраны каждого архетипа (§ таблицы в `screen-archetypes.md`) через `html.to.design`.
- Определиться с порядком переноса самих экранов — вероятно, имеет смысл синхронизировать с бэкенд-фазами (например, публичные read-only экраны переносить одними из первых, т.к. не требуют доработки auth-контракта; admin live-контроль KoC/Americano — позже, когда стабилизируется WebSocket/событийная модель из Фазы 0 и 6-7 бэкенд-плана).
