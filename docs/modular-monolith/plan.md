Статус: семь модулей и PlayoffMatchingEngine приняты; первая фаза подробно декомпозирована и поставлена в GitHub. Остальные этапы предварительные, LFPT-1041. Задачи первой фазы созданы; задачи следующих фаз дополняются по результатам пилота; каждая получает отдельную спецификацию, backend/frontend-метку и PR. S/M/L — относительный объём и неопределённость, не сроки.

## Условия приёмки каждой реализационной задачи

**Требование владельца: после каждой задачи приложение целиком продолжает работать.** Выполнение всех зависимых задач в будущем не заменяет этот критерий сейчас.

1. Ветка относительно актуального master собирает всё приложение: `./mvnw verify` из корня с отдельным PostgreSQL. Проверяется конечный исполняемый jar, а не только `-pl` нового модуля. При смене структуры пути проверок адаптируются в том же PR.
2. Итоговый артефакт запускается в изолированном контуре. Smoke охватывает health/readiness, legacy MVC, API, React shell/ресурсы и `/app/`; проверяются отсутствие конфликтующих beans, entity scan и ровно один старт Liquibase. Один успешный `/health` не доказывает работу сценариев.
3. Регрессия сохраняет публичное чтение, session/CSRF и JWT, права клуба, индивидуальную/парную регистрацию и резерв, ручную оплату, генерацию/счёт турнира и историю. Общий набор автоматизируется в #1047/#1048; затронутые сценарием операции проверяются углублённо, включая отказ и rollback транзакции. Внешние интеграции подменяются безопасными адаптерами; реальные письма/платежи не отправляются.
4. Контракты запросов, ответов, HTTP-статусов, redirect, WS destination/payload и ES/RU/EN сохраняются. Изменение внешнего поведения не входит в перенос. Проверяются React, Expo и действующий Thymeleaf в пределах их существующих сценариев; UI — реальным браузером.
5. Для переноса ресурсов БД: запуск на новой тестовой БД и на подготовленной тестовой схеме предыдущего выпуска. Повторный запуск не исполняет старые changeset заново; существующие данные сохраняются. Пользовательские БД не используются и не пересоздаются.
6. Для сборочных изменений: Docker image, включение frontend/static/templates/email, release archive, preview и отчёты CI работают с новыми путями. Прогон без frontend не заменяет проверку production-сборки.
7. Архитектурные проверки не допускают новых циклов/запрещённых импортов. Оставшийся legacy-мост перечислен адресно с зависимой задачей удаления. Документация и карта путей актуальны.
8. `docs-drift`, проверки агентской автоматики и `git diff --check` проходят. Ограничения ручных проверок перечислены. Локальное ревью проверяет атомарность, after-commit и AOP.
9. Описан и проверен возврат на предыдущий артефакт в тестовом контуре. Для задач без изменения схемы это не требует SQL-отката. Несовместимую миграцию нужно вынести из текущей задачи.

PR не готов к слиянию, если любой обязательный сценарий требует следующего PR для восстановления. Подзадачу, не проходящую эти условия самостоятельно, пересобрать в меньший совместимый срез.
