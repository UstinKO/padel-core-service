# ADR-0004: Spring в application и приоритет транзакций

Статус: **Принято** владельцем 13.11.2026. Источник: LFPT-1041, пункт 3 согласования.

## Контекст

Первый черновик предлагал application без Spring и внешние транзакционные декораторы. Владелец выбрал практичный подход: транзакционность и ACID в приоритете, при необходимости архитектуру можно уточнить позднее.

## Решение

Разрешить Spring `@Service`, constructor DI и `@Transactional` в сценариях application. Доменные типы и engines остаются чистыми Java-типами. Application не импортирует JPA, JDBC, Spring Data, Servlet, HTTP-клиенты или реализации адаптеров.

Сценарий записи задаёт транзакционную границу. Persistence-адаптеры участвуют в ней; границу нельзя дробить переносом. Сохранять isolation/propagation/readOnly/rollback, блокировки, flush и after-commit. Проверять реальный proxy-вызов: self-invocation в стандартном режиме не включает отдельную транзакционную обработку ([Spring](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)).

ACID не выводится из наличия аннотации. Обязательны тесты rollback при отказе между записями и конкурентного доступа по гарантиям конкретного сценария. Внешняя доставка не входит в ACID БД; сохраняется текущий outbox/after-commit без выдуманной гарантии exactly-once.

## Альтернативы и последствия

Строгие внешние декораторы уменьшают Spring-зависимость, но увеличивают объём переноса и риск изменения транзакций. Изолированная транзакция на каждый repository ломает атомарный сценарий. Выбранный подход сохраняет знакомую модель проекта; удаление Spring из application не является задачей миграции.
