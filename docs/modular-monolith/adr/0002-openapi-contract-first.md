# ADR-0002: API DTO из OpenAPI JSON

Статус: **Принято** владельцем 13.11.2026 в обсуждении LFPT-1041. Выбор инструмента/версий требует технической пробы, принятие направления не доказывает совместимость генератора.

## Контекст

Владелец подтвердил OpenAPI JSON → Java API DTO. Генерация JSON Schema из Java была бы другим процессом. OpenAPI — описание HTTP API с операциями и схемами; отдельная JSON Schema сама по себе не описывает весь HTTP-контракт ([спецификация OAS 3.1](https://spec.openapis.org/oas/v3.1.0.html)). Конкретную версию OAS ещё предстоит выбрать.

[Прежний frontend ADR-0004](../../frontend-react/adr/0004-api-only-boundary-openapi.md) предлагал Java → springdoc → OpenAPI → TS. В репозитории уже есть частичные OpenAPI JSON и рукописные Java/TS-модели. Нельзя поддерживать два независимых источника истины для одного endpoint.

## Решение

1. Для перенесённого HTTP-контракта источник — версионируемый OpenAPI JSON в contract-модуле. Существующие JSON сначала сверяются с endpoint-тестами и затем перемещаются либо подключаются единственным `$ref`/сборочным источником; копии не редактируются независимо.
2. Из этого источника генерируются только API-модели Java. Генерация клиентов/серверных интерфейсов и TypeScript — отдельные явно описанные шаги; бизнес-модель, JPA и формы MVC генератору не принадлежат.
3. Версия генератора, шаблоны, параметры и версия OAS фиксируются после пробной проверки. [OpenAPI Generator](https://openapi-generator.tech/docs/generators/java/) — кандидат, а не уже выбранное совместимое решение. Не добавлять старый Jackson ради генератора.
4. Maven `generate-sources` воспроизводимо создаёт Java в `target/generated-sources`; ручные исправления запрещены. Java-результат не коммитим; в Git храним входной контракт, настройки и версию инструмента. TS-артефакты сверять с отдельными правилами frontend ADR.
5. Подключать endpoint по одному через MapStruct. Сохранять wire-контракт и старые Java-модели для ещё не перенесённых сценариев. Обратная генерация schema из generated Java не становится источником.

## Проверка кандидата до выбора

На представительных существующих моделях проверить: Java release 17; Jakarta validation без javax; Jackson 3 и допустимые общие annotations; MapStruct; исключение CODE_STYLE для generated-классов; деньги BigDecimal; ISO/часовые пояса; readOnly/writeOnly; enum; отсутствующее поле против null; collections; oneOf/allOf/$ref; ProblemDetail и fieldErrors. Generated API DTO разрешены обычными классами; это согласованное узкое исключение. Рукописные DTO/результаты следуют record-правилу; generated Java не редактируется вручную. Совместимость не считается доказанной наличием флага в документации.

Критерий пробы: две чистые генерации дают один результат; модели компилируются в текущем стеке без нового HTTP-клиента, Spring Data и JPA; JSON-примеры и endpoint-контракты совпадают до/после. Contract может зависеть от согласованных validation/serialization annotations, но не от MVC/Spring Data или внутренних доменных enum.

## Альтернативы и последствия

Сохранение code-first уменьшает начальную работу, но расходится с предполагаемым направлением запроса. Рукописные DTO без генерации оставляют ручную синхронизацию. Отдельная JSON Schema подходит для схем данных, но требует дополнительного HTTP-описания. Массовая генерация всех существующих DTO слишком рискованна: они обслуживают также формы и внутренние вызовы.

Принятое решение уточняет направление генерации frontend ADR-0004 для нового конвейера; остальные его принципы HTTP/WS, безопасности и разделения frontend сохраняются. Изменение React/Expo-клиента оформляется отдельной задачей, backend остаётся обратно совместимым.
