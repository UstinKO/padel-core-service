# Матрица проверок первой фазы

Задачи: #1047 — backend/данные, #1048 — исходный browser/API/ручной прогон, #1049/#1050 — собственные проверки изменений, #1045 — финальный повтор и откат. Точные исходные пары/стадии сохранены в [JSON-эталоне #1048](browser-expectations.json); автоматический результат и отдельный статус ручной проверки — в [browser baseline](browser-baseline.md).

## Данные

- F8: 8 активных пар, воспроизводимые квалификационные результаты/история, все команды имеют два сыгранных квалификационных матча.
- F9: 9 активных пар; проверка выбора прямых слотов и play-in с продвижением в конкретный QF-слот по действующему правилу.
- F16: 16 активных пар; полный путь play-in/1⁄8 → QF → SF → final, пары/составы по исходному эталону.
- FEARLY: ранняя сетка с TBD и незавершённой квалификацией; после завершения заполняются только ожидающие слоты, существующие пары сохраняются.
- FNOSHOW: команда помечена NO_SHOW; не участвует в активной квалификации/посеве по текущим правилам.
- FUNIT: фиксированные входы трёх приоритетов, равной стоимости, неизбежного реванша, пустого/нечётного списка.
- Роли: управляющий своим событием, CLUB_ADMIN другого клуба, аноним; отдельные синтетические сессии для stale/repeated действий. Проверять сервер, а не только кнопки.

Для данных хранить логические ключи команд, порядок входов, квалификационные результаты и ожидаемые пары; database ID может отличаться между чистыми инстансами. Не сравнивать случайно назначенные ID или timestamps как бизнес-результат. Seed/reset ограничен собственной guard-защищённой тестовой БД. Отдельный защищённый pilot seed #1047 подготавливает F8/F9/F16, исходный состав и завершённый турнир; составы/команды и API — в [backend-отчёте](backend-baseline.md). FEARLY/FNOSHOW создаются действиями отдельной браузерной приёмки.

## Отчёт и контроль продолжения

По каждому TC фиксировать применимость/данные, SHA/артефакт, ожидаемое/фактическое, команды или точные нажатия, результат, ссылку на безопасные доказательства/дефект/повтор. Три набора результатов: baseline, после переноса, после отката. Недостижимые через UI случаи помечаются unit-only, а не «пройдены вручную».

#1047 и #1048 должны дополнить fixtures и точные ожидаемые результаты, не ослабляя критерии под текущую реализацию. Бизнес-несоответствие MASTER — отдельный issue. После #1049/#1050 их рабочие smoke выполняются до готовности каждого PR. #1045 завершает независимую приёмку и решение о расширении миграции.
