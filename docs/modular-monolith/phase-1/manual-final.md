# Ручная приёмка итогового пилота #1045

Статус всех пунктов ниже — **NOT_RUN**. Данные подготовлены автоматически; нажатия и технические запросы ещё должен выполнить человек.

## Открыть стенд

Оператор из отдельного preview-checkout выполняет:

```sh
python3 automation/ui-preview/playoff-pilot.py manual --reset
```

Это один начальный сброс пяти пилотных мероприятий, подготовка отдельных данных M04/M05/M06 и запуск видимого Chromium
с уже выполненным входом управляющего. Окно открывается на настоящем управлении турниром M01 и прокручивается к старту плей-офф.
Подтверждения `confirm` **оставлены человеку**: ручной launcher не принимает и не отклоняет их автоматически.
Ссылки с текущими портом и ID: `target/modular-pilot/manual-plan.md`; технические ID/маршруты: `manual-plan.json` рядом.
Старые ссылки из #1048 относятся к другому стенду.

Если окно закрыто, запустить `resume-manual`: данных это не сбрасывает. В терминале работающего launcher можно открыть новую вкладку:
`M02 manager adminPath`, `M07 foreign adminPath`, `M07 anonymous publicPath`, `M08 admin reactPath`, `M08 manager historyPath`.
Роли используют разные browser contexts; две вкладки одной роли разделяют сессию. `/preview/**` открывать ролью admin.
Нет необходимости выходить из сессии управляющего, искать пароль или начинать с общей карточки `/admin/tournaments/{id}`.

После подготовки файл `runtime/pilot-manual-session.json` блокирует команды пилота и `check.py` до явного `end-manual`.
Закрытие окна не снимает блокировку. Она локальная: прямой HTTP reset, `preview.py reset`, release rehearsal и другие процессы
не блокируются этим файлом; оператор их не запускает во время ручного прохода.
`end-manual` только снимает блокировку и не записывает PASS. Ошибка подготовки тоже оставляет её: сначала проверить состояние,
затем явно завершить сессию перед новым `manual --reset`.

## M04: актуальная ранняя сетка после #1152

**M04A, восемь пар.** Открыть M04A: первые шесть пар завершили квалификацию, для 7–8 подготовлен последний матч на корте 4.

Теперь стартовать плей-офф: четыре QF, восемь различных команд, пустых слотов нет. Это заменяет старый ранний TBD-сценарий восьми пар;
не пытаться выполнить недоступную кнопку из исторической инструкции.

**M04B, девять пар.** В M04B осталось квалификационное 9–1 на корте 1. В предложениях раннего плей-офф есть безопасная пара 6–8.
Выбрать ей корт 2 и подтвердить. Записать пару/ID, ввести 6:3 слева. Квалификация ещё не закончена.
В последнем квалификационном матче сначала попробовать 5:4: сервер должен отказать, ранний результат остаться прежним.
Затем сохранить 5:6. Проверить завершение квалификации, сохранение ранней пары/счёта и попадание победителя в связанный QF-слот.
Матчи очереди назначать на свободный корт через выбор корта и кнопку назначения, затем вводить результаты.

**M04C, шестнадцать пар.** Осталось квалификационное 16–1. Первую безопасную раннюю пару подтвердить на корте 2,
вторую — без корта, в очередь. Записать обе пары/ID, первую сыграть 6:3 слева, последнее квалификационное завершить 5:6.
Ранние пары/результат сохраняются, очередь достраивается без повторного матча. Завершить 1/8 через назначение очереди.
Перед QF остановиться: оператор прочитает фактические четыре пары и предложит победителей первых двух QF без прежней очной встречи;
так проверяется достижимое предложение раннего SF, а не выдуманная кнопка. Человек вводит эти два результата,
подтверждает предложенный SF на корте 2, затем завершает два оставшихся QF. ID/пара/корт раннего SF сохраняются,
появляется ровно один дополнительный SF. Сохранить screenshot до/после; закончить сетку до одного чемпиона.

Каждый M04A/B/C записывается отдельно; ранний SF — отдельный подпункт. Подготовка оператором не считается ручным выполнением результата/подтверждения.

## M06: устаревший запрос, состав и повтор ключа

Использовать отдельный M06: плей-офф уже создан, результаты ещё не введены. Открыть управление в двух вкладках.
Во вкладке A сохранить значение `metadata.conductVersion` из `/api/public/events/{id}/live`.
Во вкладке B сохранить один результат. Экран A может сам обновиться по WS: это нормально.
Отправить из A POST `/tournaments/team-playoff/admin/{id}/regenerate-playoff` с **сохранённой старой**
`expectedConductVersion`, CSRF и form-urlencoded. В Network начальный POST: 302, `X-Conduct-Stale: true`;
затем redirect. Итоговый fetch 200 после redirect не заменяет чтение исходного POST. Версия, пары и результаты не изменились.

Технические подпункты выполнять человеком в DevTools своего M06; оператор подставляет текущие ID из `manual-plan.json`/court-board.
Токены, cookies и полный HAR в журнал не копировать.

1. Сохранить до запроса версию и сетку. На незавершённый матч отправить JSON POST
   `/tournaments/team-playoff/api/playoff-matches/{matchId}/result?expectedTeam1=-1&expectedTeam2=-2`,
   тело `{"team1Games":6,"team2Games":3}`, действующий `X-XSRF-TOKEN` из своей cookie.
   Ожидается 200, success=false с сообщением об изменившемся состоянии; версия и сетка прежние.
2. Для настоящих team1Id/team2Id этого матча отправить результат с новым `Idempotency-Key`, затем повторить **тот же** запрос с тем же ключом.
   Первый: success=true; повтор: 200/success=false и `X-Conduct-Replayed: true`. Версия после повтора не выросла, результат один.
3. Отдельно повторить один ключ из двух независимых клиентов управляющего: одно принятое действие и один отказ.
   Это отдельный ручной подпункт; автоматический concurrent PASS не переносится сюда.

Для этих запросов оператор даёт точные команды под текущий матч перед выполнением; секреты остаются в браузере.
Обычный проход двух вкладок не закрывает stale-pair/replay/concurrent подпункты.

## M08: два зрителя, WS и история

Открыть M08 anonymous/publicPath и M08 admin/reactPath; управляющий остаётся в третьей вкладке.
В Network у зрителей включить запись, открыть WebSocket → Messages. Подписки:
legacy `/topic/team-playoff/{id}` и React `/topic/public/live/{id}`.
Перед новым результатом открыть историю M08 manager/historyPath, сохранить ссылку версии **до** результата.
Человек вводит новый результат управляющим; оба зрителя обновляются без refresh. В Network проверить полученные STOMP-сообщения;
публичное сообщение — invalidation, актуальные данные загружаются snapshot-запросом.
В сохранённой версии истории нажать восстановление и подтвердить: последний результат исчезает,
предыдущие результаты и связи остаются; сверить обе страницы и повторное чтение.
Screenshot экрана не подменяет отдельного чтения WS в Network.

## M09: сохранение, restart/rollback и общий smoke

Повторно войти и открыть завершённый M01: итог и все результаты сохранены. Открыть главную, `/web/`, `/app/`.
Отдельно пройти синтетическую регистрацию/резерв/участие на общем seed-контуре под руководством оператора;
эти данные после автоматизации могут нуждаться в отдельной подготовке, пять пилотных событий не сбрасывать.
Оператор согласует момент и перезапускает только свой app, затем штатно переключает старый reactor, итоговый jar,
rollback и возвращает итоговый. После **каждого** шага человек открывает M01 и сверяет итог.
Автоматическое сравнение семи snapshots/схемы уже есть; ручной результат записывается только после наблюдения человеком.
JWT-проверка из контейнера и участие имеют собственные автоматические доказательства; если технический ручной HTTP-проход
не выполнен, его оставить NOT_RUN отдельно, не приписывать обычному открытию `/app/`.
