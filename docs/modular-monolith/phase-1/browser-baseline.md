## Проверенный артефакт

Дата: 13.11.2026. Исходный master после мержа #1047: `a99793a786a5c3f711ab367c1e30ec032e13872d`. SHA-256 jar: `aeef762a9c1cd027d45cd1250048f3edceb3937cc404ae890aa46e072f39ca30`. Собран полный jar с React; использован отдельный локальный preview с собственной PostgreSQL и Mailpit. Java исходников/production UI/HTTP/WS/схемы в этой задаче не меняются. Новый код — только скрипты проверок и документация.

`playoff-pilot.py` проверяет локальный Docker, runtime marker и environment=preview, затем сверяет SHA-256 `/app/app.jar` с локальным jar **до reset**. Набор — пять сценариев #1047; reset удаляет только их турниры. Общие шесть preview-мероприятий в конце сравниваются с исходным статусом. Синтетические роли и аккаунты сохраняются. Файл для браузера создаётся с правами 0600 и удаляется также при ошибке; публикация паролей/токенов, cookies и полного network trace не выполняется.

Гарантия TC17 относится к одному actor и одному валидному ключу. Произвольные конкурентные действия с разными ключами, повтор без ключа и optional expectedTeam не объявляются идемпотентными. HTTP 200/302 отдельно не считается доказательством успешной записи: скрипт читает success, версии и сохранённый snapshot.

Для legacy WS браузер загружает только два уже используемых клиентских CDN-скрипта SockJS/Stomp; остальные внешние запросы заблокированы тестовым контекстом. Реальный transport `/ws` не подменяется, браузерные backend-ответы не мокируются. React использует свой собранный клиент. Скрипты legacy CDN — внешняя зависимость исходного приложения; при их недоступности тест не заявляет успешный WS.

JWT проверяется настоящим HTTP внутри **своего** preview app-контейнера: login 200, `/api/auth/me` и `/api/players/me/events` с Bearer без session cookie 200, без авторизации `/api/auth/me` 401. Gateway предназначенно удаляет Authorization после Basic Auth; он не перенастраивался ради JWT. Токен существует только в памяти скрипта и stdin curl, не в argv/отчёте.

## Команды и доказательства

После настройки своей отдельной тестовой БД и запуска preview по runbook:

```sh
./mvnw verify
PLAYWRIGHT_MODULE_PATH="$PWD/frontend/node_modules/@playwright/test/index.mjs" \
  ./mvnw -Dskip.frontend=true -Dparticipation.browser=true -Dtest=ParticipationBrowserTest test
python3 automation/ui-preview/playoff-pilot.py run
python3 automation/ui-preview/playoff-pilot.py smoke --rehearse
```

`run` пересоздаёт только pilot fixtures, выполняет общий smoke и матрицу, сравнивает с принятым JSON. `smoke` выполняет общий browser/JWT проход без сброса; `--rehearse` запускает существующую репетицию и сверяет сохранённые турниры. `prepare --reset` готовит отдельный ручной набор без автоматического турнирного прогона. Не запускать run/reset во время ручной проверки.

`run --record` сохраняет только `target/modular-pilot/expectations-candidate.json`; принятый JSON не изменяется. Обновлять его вручную после разбора расхождений и решения по конкретному изменению, затем повторять обычный `run`. Зафиксирован успешный повтор со сравнением после первого recording-прогона. В последующих #1049/#1050/#1045 использовать тот же эталон; адаптация пути runtime jar при reactor — часть #1049.

Матрица не является нагрузочным тестом. Во время подготовки слишком быстрые повторные прогоны достигали существующих лимитов. Финальный скрипт закрывает неиспользуемые живые страницы между API-операциями, выполняет общий smoke перед матрицей и выдерживает 150 мс между обычными сохраняющими запросами. Конкурентная проверка остаётся одновременной. Лимиты приложения не отключены и мутирующие запросы автоматически не повторяются.

Результаты: полный verify — **981 тест, 0 ошибок, 2 штатных пропуска**; optional `ParticipationBrowserTest` отдельно включён и прошёл, без пропуска: реальная email-ссылка, вход с возвратом, делегирование гостя, кабинет, подтверждение/отказ, продвижение резерва, ES/RU/EN. Marketing-browser остаётся штатно выключенным в общем verify; он не заявляется выполненным. Перед итоговым коммитом прошли 91 Python-тест (8 + 48 + 5 + 8 + 22), docs-drift/agent-migration — 0 расхождений, diff — без ошибок. `pnpm --dir frontend check` успешен, включая 44 теста; отдельный frontend e2e — 52 теста. Этот frontend-набор с собственными fixtures не подменяет описанный выше реальный preview-прогон.

Безопасные локальные файлы: `target/modular-pilot/{report,actual,fixture,jwt-smoke,rollback}.json`, пять screenshots, `target/release-rehearsal/report.json`. В Git сохраняются принятый JSON, этот отчёт и выбранные screenshots; runtime-файлы, доступы, cookies, исходные логи и traces не публикуются. ## Известный дефект и дальнейшее решение

[LFPT-1067](https://github.com/UstinKO/padel-core-service/issues/1067), milestone «Баги — исправление и стабилизация»: №9 после победы в play-in и поражения в QF ошибочно сохраняет ADVANCED вместо ELIMINATED. Наблюдается до модульного переноса; правильные счёт, победители и связи не исправляют ошибку статуса. Вероятная причина — выбор последнего матча по порядку создания roundId вместо хода стадий; подтверждение/исправление — отдельный backend PR. Это исходный дефект, а не принятое правило; исправление потребует осознанного обновления эталона.

Автоматизация подготовлена для повторов C/D и #1045. Владелец принял ручные 8/9 пар и автоматизированную матрицу как достаточную исходную приёмку #1048. После успешного CI и мержа PR #1070 допускается #1049. Полное ручное покрытие остаётся обязательным в #1045; невыполненные здесь пункты сохранены в журнале и в её постановке.
