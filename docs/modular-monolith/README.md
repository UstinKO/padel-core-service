# Многомодульный монолит: анализ и план перехода

Задача подготовки: [LFPT-1041](https://github.com/UstinKO/padel-core-service/issues/1041), решения от 13.11.2026. Семь модулей и пилот PlayoffMatchingEngine приняты владельцем. Фактическое состояние после клубного среза, #1279, #1332 и #1338: parent и четыре дочерних Maven-модуля; PlayoffMatchingEngine, KingOfCourtPairingEngine, AmericanoScheduleEngine, AmericanoScheduleValidator, QualificationPairing и PlayoffFormat с unit-тестами находятся в engines, чтение публичных клубов — в application, клубный API DTO генерируется в api-contract, приложение собирает bootstrap. [Реализация переноса и проверки](phase-1/engine-extraction.md). Остальные три модуля ещё не выделены; #1045 принята владельцем 20.11 с ограничениями. [Первый application-срез](phase-2/application-club-read.md).

Цель — облегчить сопровождение через Maven-модули и гексагональные границы; количество не ограничено пятью. Сохраняются один процесс приложения, один выпускаемый Spring Boot jar и существующая PostgreSQL. Разделение на технические модули дополняется доменными пакетами внутри них.

**Обязательное требование владельца:** каждая завершённая задача оставляет приложение целиком работоспособным. Нельзя планировать промежуточный merge с обещанием восстановить сборку, запуск, API или пользовательский сценарий следующей задачей. Обязательные условия каждого этапа описаны в [плане](plan.md#условия-приёмки-каждой-реализационной-задачи).

Исходное предложение: API DTO из OpenAPI JSON, турнирные движки, БД и миграции, сервисный слой, контроллеры и эндпоинты. Главная поправка — сервисный модуль владеет портами хранения; модуль БД зависит от этих портов, а не наоборот. API DTO не становятся общей доменной моделью.

Связанные направления: [исторический микросервисный план](../microservices-migration-plan.md), [React ADR](../frontend-react/adr/README.md), [анализ Swarm #1040](https://github.com/UstinKO/padel-core-service/issues/1040). По решению владельца текущая цель — многомодульный монолит; микросервисный план остаётся материалом возможного будущего, внутренние HTTP-вызовы не создаются. Переход на модули не требует предварительного включения Swarm.

Документы обновляются с каждой принятой реализационной задачей: состояние этапа, фактические зависимости, результаты проверок и оставшиеся временные мосты. Предложенный граф нельзя описывать как уже реализованный. Spring в application и исключение record для generated-классов приняты; выделение хранения отложено. Сформирован пул первой фазы; отдельная поздняя задача хранения — #1051. Исходная автоматизация и принятые ручные 8/9 пар — #1048. [Итоговая автоматизация и откат #1045](phase-1/final-report.md) прошли; [ручной сеанс 18.11](phase-1/manual-final.md) содержит PARTIAL и ограничения. [Повтор после исправлений 20.11](phase-1/followup-2026-11-20.md) отделяет технические проверки от решения владельца: 20.11 приёмка принята с ограничениями без нового ручного повтора; первая фаза завершена.
