# Клубная граница хранения и счётчик главной

[LFPT-1439](https://github.com/UstinKO/padel-core-service/issues/1439), первый срез [фазы 6](README.md). Исходный master `b1ddcca60693fec2310243bd0b03ff2736127eed`. Контрольный исходник предыдущего релиза `4773fcb9fee6a106c5028f70e38632a55b314e90`. Разница между ними — архивация спецификаций. Схема на обоих срезах v1.93.

## Изменение

`GET /api/public/home` формирует `totalClubs` через `PublicClubQuery.countActive() → ClubReadPort.countActive() → LegacyClubReadAdapter`. Адаптер вызывает прежний `ClubRepository.countByIsActiveTrue()`. JPA и Spring Data остаются внутри адаптера. Внешняя и прикладная границы читают в общей read-only транзакции. Запрос всего списка клубов для подсчёта не выполняется.

Счётчики игроков и турниров и сортировка ближайших турниров сохраняют свои запросы. Публичный список и карточка клуба продолжают использовать прежние операции порта. Liquibase и физическая схема на этом шаге сохраняют прежнее владение.

## Граф для переноса Club

`Club` хранится в `club_db`. В entity нет JPA associations к другим сущностям. Ссылки на клуб в проводимых сценариях используют ID. `ClubRepository` использует JPA для чтения одной entity, поиска по имени/городу, активности, порядка, создания, обновления и удаления. HTTP-контракт не получает эту entity.

| Потребитель на исходном master | Запросы и обязанности | Владелец следующей задачи |
|---|---|---|
| `PublicDiscoveryService` | Прямой count для публичной главной. Список и карточка уже делегируют application | #1439 |
| `LegacyClubReadAdapter` и `ClubReadModelMapper` | Активные список/ID и преобразование в `PublicClub`. После #1439 также COUNT | #1442, перемещение одного адаптера с repository/entity |
| `PlayerEventsService` | Пакетное обогащение событий именами клуба через `findAllById` | #1440 |
| `DoubleTournamentRegistrationService`, `AmericanoService` | Имя клуба по ID в прикладном сценарии | #1440 |
| `IndividualTournamentReminderScheduler`, `PairTournamentReminderScheduler`, `TelegramReminderScheduler`, `SoloRegistrationSchedulerService` | Чтение клуба по ID для напоминаний | #1440 |
| `TournamentNotificationService`, `PlayerTelegramNotifications` | Чтение клуба по ID для уведомлений | #1440 |
| `ClubService` | Списки, DTO по ID и пакетам, имя/город/поиск, активность, создание/изменение/удаление. Один сервис используется административными и другими потребителями | #1441 владеет этим фасадом. При необходимости #1440 выводит только операции его внутренних потребителей |
| `ClubAccountService` | Список доступных активных клубов, проверка выбора, сверка существующих ID. Работа с аккаунтом и проверками роли остаётся в своей границе | #1441 |

Клубный HTTP-маппинг принадлежит web-границе. Текущий `ClubReadModelMapper` подготавливает нейтральное чтение внутри JPA-адаптера. У внутренних чтений по ID сохранится прежнее поведение для неактивных клубов. Публичный порт фильтрует активность, поэтому #1440 нужен сценарий с исходным условием активности.

Шаги #1440 и #1441 должны сохранить пакетность, количество вызовов, проверки существования/доступа и границы commit. После них #1442 переносит единственный `Club`, репозиторий, адаптеры и маппинг. Критерий перед перемещением — сверка потребителей после фактического мержа обеих задач, включая изменения соседних PR.
