# Административные операции с клубами

[#1441](https://github.com/UstinKO/padel-core-service/issues/1441) завершает подготовку клубной границы к [переносу в #1442](https://github.com/UstinKO/padel-core-service/issues/1442). Исходный master `2df34ee242f91f312737fe54556a7caace38fbbd` включает внутренние чтения из PR #1450.

- `ClubService` сохраняет фасад для прежних MVC и REST-входов. `ClubAdminReadPort` и `ClubAdminWritePort` передают профиль клуба и редактируемые поля. `ClubDtoMapper` собирает прежний DTO. `LegacyClubAdminAdapter` выполняет существующие запросы, сортировку и поиск, а `ClubMapper` преобразует данные JPA.
- При создании автор берётся из действующего аккаунта. Правка сохраняет ID, автора, дату создания и активность и может очистить необязательные поля. Деактивация и переключение сохраняют прежние входы и правила. Физическое удаление проверяет наличие любых связанных турниров через `ClubTournamentUsage`; прежний запрос принадлежит `TournamentRepository`.
- `ClubAccountService` читает активные площадки по имени, проверяет создание в активном назначенном клубе и одним запросом подтверждает существование всех ID при назначении. Назначать можно и выключенный клуб, а пустой набор снимает назначения. Прежняя одиночная привязка сохраняет минимальный ID выбранного набора. Сохранение аккаунта относится к границе идентичности.
- Транзакции принадлежат существующим фасадам. Адаптер обновляет управляемую сущность в той же транзакции, где прочитан профиль для проверок. Проверки доступа, дубликатов и связанных турниров сохраняют порядок.

`ClubRepository` используют два адаптера, `LegacyClubReadAdapter` и `LegacyClubAdminAdapter`. В #1442 они переходят вместе с единственными entity и репозиторием клуба, JPA-мапперами и неизменённым деревом Liquibase. Прежний HTTP-маппинг и проверка турниров остаются у своих потребителей.
