## Какой перенос открывает дорогу следующим модулям

`padel-persistence` меняет зависимости Java. Для выделения web и integrations сначала принимаем работающий модуль хранения на текущей БД. Если понадобится физический перенос PostgreSQL, переключение подключения пройдёт отдельно на принятой сборке приложения.

Целевые зависимости остаются `bootstrap → persistence → application → engines`. Boot JAR один, DataSource и EntityManagerFactory одни, Liquibase запускается одним владельцем. Web получает application-сценарии, storage entities и Spring Data остаются за портами. Контракты MVC/API, роли и транзакции сохраняются. Окно физической миграции больше не должно быть блокирующей зависимостью Maven-выделения. Порядок утверждён и закреплён в #1051 и [ADR-0007](../adr/0007-persistence-first.md). [Целевые модули](../target-architecture.md) · [#1051](https://github.com/UstinKO/padel-core-service/issues/1051)

Клубный срез выбран потому, что у `Club` нет исходящих JPA-ссылок на другие сущности, `ClubRepository` по типам использует одну entity, а `ClubReadPort` и `PublicClubQuery` уже приняты. При этом прежний repository обслуживает `ClubService`, `ClubAccountService`, счётчик главной, регистрацию и задачи уведомлений. Подготовка пункта 1 охватывает эти обращения. Новый модуль в пункте 2 начинает с действующего адаптера и миграций, имеющих постоянное место. Копии таблиц, репозиториев или маппинга для перехода не требуются.

Каждый PR оставляет один работоспособный JAR. Сохраняются classpath `db/changelog/**`, порядок include, identity `id/author/filename` и checksum существующих changeset. В JAR ровно один набор миграций. Уже применённые миграции не выполняются повторно на существующей схеме. Архитектурные проверки фиксируют прогресс по каждой перенесённой группе, а полный запрет прямого доступа контроллеров к persistence применяется при закрытии #1051. Для каждой записи сохраняются блокировки, транзакционные границы и время отправки уведомления.

## Если нужен физический перенос PostgreSQL до остальных модулей

Это отдельное переключение инфраструктуры. Сначала подобрать цель: новый volume/узел или поддерживаемый вариант Swarm. Проверить в закрытом контуре фактическую версию и расширения PostgreSQL, размер данных, роли и права, диск и доступность проверенной резервной копии. Согласовать окно записи и допустимые потери/простой по замерам. [#1040](https://github.com/UstinKO/padel-core-service/issues/1040) · [#1209](https://github.com/UstinKO/padel-core-service/issues/1209) · [#1218](https://github.com/UstinKO/padel-core-service/issues/1218)

1. Восстановить резервную копию в отдельном контуре. Сверить строки, последовательности, роли, constraints, индексы, функции, extensions и `DATABASECHANGELOG`. Проверить запуск принятого JAR на целевой БД и измерить восстановление. Репетиция #1209 на синтетических данных даёт методику и фиксирует прежние проблемы восстановления. Открытые этапы Swarm не считаются принятыми.
2. На согласованном переключении закрыть записи, остановить все источники записи, получить финальную согласованную копию либо использовать подтверждённый механизм догонки. Запустить целевую БД и проверить тот же принятый JAR, который работал до переключения. Включить запись после сверки и проверить рабочий write-сценарий.
3. До открытия записей возврат возможен на прежнюю актуальную БД. После записи на новой БД прежний volume или dump могут отставать. Возврат подключения требует переноса этих записей или отдельно принятого решения. Приложение при необходимости откатывается на текущей БД при совместимой схеме. [Репетиция и runbook восстановления](../../swarm/data-recovery.md)

Раздельные проверки артефакта и подключения позволяют установить причину ошибки и сохранить независимые точки отката даже при одном календарном окне. В кодовом плане физический переезд PostgreSQL не является предпосылкой ни для #1051, ни для worktree с исходниками. Если выбран физический перенос в Swarm, production-допуск учитывает этапы #1214, #1217, #1218 и принятую топологию.

## Выпуск модуля на текущем PostgreSQL

Порядок с ранним выделением хранения утверждён владельцем 27.11.2026. Для Maven-переноса достаточно штатного выпуска JAR. Действующий production runner применяет образ сервиса приложения с `--no-deps`. Служба PostgreSQL, том, параметры доступа и схема используются прежние. Возможная пауза связана с перезапуском приложения и его readiness.

На master `b1ddcca60693fec2310243bd0b03ff2736127eed` в changelog уже 99 файлов. В локальной пробе Liquibase 5.0.4 с загрузчиком Spring Boot прочитал их сначала из `BOOT-INF/classes`, затем из вложенной библиотеки. Для всех 109 changeset совпали порядок, `id/author/filepath` и вычисленная контрольная сумма. Проба не использовала подключение к БД и не заменяет проверку конечной сборки.

Перед выпуском конечный JAR проверяется на отдельной PostgreSQL с историей предыдущего релиза. Проверяем один набор changelog, ноль повторных миграций, совпадение `ID/AUTHOR/FILENAME/MD5SUM` в `DATABASECHANGELOG`, повторный запуск и возврат прежнего JAR. Версия Liquibase и classpath-пути сохраняются для этого шага. При расхождении исправляется артефакт до выкладки. История боевой БД и её контрольные суммы сохраняются.

## Что идёт после хранения

Шаблоны, статика и HTTP/WS переходят в `padel-web` в своих рабочих срезах. Email, Telegram и внешние API переходят в `padel-integrations` за согласованными портами. Java сценариев переходит в application или остаётся рядом с владельцем существующей границы до её выделения. Bootstrap в конце содержит только main, wiring, профили запуска и сборку. Тогда корневой `src` удаляется: миграции уже принадлежат persistence. Сборщики React/Expo и release переключаются вместе с ресурсами конечного владельца.

Следующие клубные задачи — внутреннее чтение #1440 и административные операции #1441. После них #1442 подключает JPA-реализацию и переносит Liquibase.
