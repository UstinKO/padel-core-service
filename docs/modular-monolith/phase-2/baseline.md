# Независимый baseline клубного среза

Приёмка LFPT-1201 сравнивает приложение после обоих backend-переносов с принятым артефактом до application и generated DTO. Результаты #1199/#1200 используются как контекст, новый PASS получается отдельным прогоном на одной синтетической БД.

| Артефакт | Revision | SHA-256 jar |
|---|---|---|
| До обоих переносов | `8a9ee29e2e29aa60970ad3201455e42da187533e` | `5126f460d3771e22fc7fd7f22922476d5d17138f99d272bf7977f4ff7efd700c` |
| Принятый master после #1234/#1238 | `ad4da10cc2d75a2ade343b570c402d92a64d0eb8` | `a4787cd5468e92efa1e12f70128c05d86d2949f9b73000e14f8392a7c3bd0b8f` |

Предыдущий jar сохранён как отдельный проверенный артефакт первой фазы; его ручной preview и данные не запускаются и не изменяются. Он применяется только в новом собственном preview этой приёмки, с его синтетическими данными и конфигурацией. Источник итогового jar — master с уже включёнными #1199/#1200; production Java/UI, миграции и настройки в приёмочном PR не меняются.

## Набор данных и сравнение

Существующий fixture-сервис создаёт пять самостоятельных турниров пилота в новом preview. Дополнительно приёмочный наблюдатель добавляет три клуба: активный с публичными значениями/экранируемым текстом, активный с шестью nullable полями и неактивный. Контакты имеют отдельный синтетический маркер для проверки отсутствия в публичном ответе и DOM. `nombre` остаётся NOT NULL по действующей БД; искусственное изменение ограничения ради nullable name не выполняется.

Для RU/ES/EN фиксируются реальные ответы двух GET: список, полная и nullable-карточка, неактивный, неизвестный, нулевой, отрицательный и нечисловой ID. Отдельно все клубы временно скрываются только в собственном preview для реального пустого списка; прежние флаги восстанавливаются в finally. UI-моки ответов не используются.

Сравниваются весь JSON, порядок массива, HTTP-статус, Content-Type и Cache-Control. Список дополнительно сопоставляется с SQL-порядком nombre/id. У каждого Club ровно девять полей, nullable-ключи присутствуют, canonicalUrl сохраняет прежнюю строку. Ошибки 404/400 проверяются по локализованному ProblemDetail. Отказ хранения 503 и безопасный код ошибки покрываются повторным PublicClubApplicationIntegrationTest в полном verify; физический отказ БД в этом baseline не моделируется.

Полные ответы остаются в `target/club-acceptance/http-baseline-private.json`. В Git включаются только безопасная [сводка приёмки](acceptance.md) и хеши артефактов. Динамические request IDs, время и session/cookies не объявляются частью golden JSON. У пяти live snapshots исключается только metadata.generatedAt; версии проведения, ID, счёт, пары и связи сравниваются целиком.

## Воспроизведение

На отдельной рабочей копии подготовить собственный preview, собрать/проверить конечный jar и запустить его. Использовать сохранённый baseline jar с указанным выше SHA-256, не копировать частный runtime другой рабочей копии.

```sh
python3 automation/ui-preview/preview.py init --port 18204
python3 automation/ui-preview/preview.py build
python3 automation/ui-preview/preview.py up
python3 automation/ui-preview/club-acceptance.py \
  --baseline-jar /путь/к/прежнему.jar \
  --baseline-revision 8a9ee29e2e29aa60970ad3201455e42da187533e
```

Общий smoke запускается отдельно командой `python3 automation/ui-preview/playoff-pilot.py smoke --rehearse`; режим smoke сохраняет пять контрольных турниров и использует отдельные fixtures участия.

Наблюдатель проверяет локальный preview, UUID-маркер БД и отсутствие ручной блокировки. Его вход браузеру с временными доступами создаётся mode 0600 в игнорируемом runtime и удаляется в finally; публичный отчёт не содержит доступов. Синтетические клубы удаляются после проверки; прежний текущий выпуск восстанавливается при ошибке. Паузы и Retry-After сохраняют продуктовый rate limit.
