# Короткое приглашение с сайта

`/telegram/join` — основной общий адрес для чата после выпуска #1459/#1460. Гость проходит действующий обычный/Google-вход с destination `/telegram/join`, игрок видит своё имя и добровольное согласие. Одна нативная форма CSRF+POST получает 303 прямо в персональный Start бота. После Start связь завершена; вторая кнопка, callback и возврат на сайт не требуются. Уже подключённый игрок видит готовый результат без формы.

Тексты ES/RU/EN, оранжевый стиль и доступная клавиатура сохранены. JS только блокирует два submit и сбрасывает кнопку на pageshow; без JS форма работает. В общей странице нет персонального токена; GET/языковые переходы не меняют связь. Referrer-Policy same-origin позволяет нативный POST с корректным Origin и скрывает Referer от внешних сайтов. Ошибки и недоступность не запускают повтор сами.

В редакторе рассылок новая общая ссылка приходит из `/api/admin/telegram/site-invitation`. Проверяется HTTPS, точный путь без query/fragment/credentials; есть fallback ручного копирования. Копирование не заполняет текст кампании, не выбирает игроков и ничего не отправляет.

`PlayerTelegramJoinBrowserTest` запускает настоящий Spring/QA PostgreSQL и Playwright; внешний Telegram подменён, Start доставляется тестовому poller. Старый браузерный сценарий сохраняется. Настройки Cloudflare и независимый пилот чеков не меняются.

Проверка 27.11.2026: девять групп нового браузерного сценария прошли, включая ES/RU/EN (1440/390/320), один POST при двух активациях, отказ CSRF, другую роль, копирование/ручной fallback и недоступную функцию. После имитации личного Start настоящим poller все три профиля получили CONNECTED без callback; реальных сообщений игрокам не отправляли. Прежний браузерный сценарий и 17 DOM-проверок кабинета прошли. Полный verify совместной ветки на отдельной PostgreSQL: 1763 теста, 0 падений/ошибок, 13 пропусков (включаемые отдельно браузерные проверки). Артефакты: `target/telegram-join-qa/` и `target/telegram-onboarding-qa/`.

# Интерфейс Telegram: проверка

## Общий вход из бота

Переключение ES/RU/EN сохраняет UUID текущего подключения и его статус. Во время сохранения контекста или подтверждения языковые переходы временно недоступны; вход использует канонический destination без лишних параметров.

[Порядок выпуска и отката](telegram-onboarding-rollout.md). Публикация общей ссылки — после отдельного выпуска и живой приёмки, не во время подготовки PR.

Интерфейс #1429 поверх сервера #1428: `/telegram/connect` без аналитики. Fragment-секрет сохраняется в серверной сессии; публичный UUID request разделяет вкладки, вход и Google возвращают к своему запросу без раскрытия секрета. Игрок видит профиль и согласие, явно продолжает и завершает привязку в исходном Telegram. Повторное открытие показывает актуальный READY/PENDING/CONNECTED. Невалидная ссылка и потеря сессии объясняются без внутренних кодов; неизвестный ответ не повторяет POST, доступна ручная проверка статуса.

Общая ссылка бота доступна для копирования в редакторе при включённом флаге общего входа. Она не содержит персональный токен; при отказе буфера обмена ссылка выделяется для ручного копирования. Выбор адресатов и текст рассылки сохраняются пустыми, ничего не отправляется автоматически.

`PlayerTelegramOnboardingBrowserTest` и `tests/browser/telegram-onboarding.browser.mjs` проверяют настоящий Chromium, RU/ES/EN и 320/390/1440: личная ссылка → вход → профиль → одно подтверждение → PENDING после reload → подменённый Telegram callback → CONNECTED. Проверяются также Google destination, потерянный ответ после настоящего POST без повтора, истечение сессии, смена fragment в открытой вкладке и общий URL в админке с отказом clipboard. Внешние сервисы подменены, БД и игроки синтетические. Это проверка интерфейса и серверного контракта, без реальных сообщений, физического Telegram-клиента или живого Google-провайдера. Доказательства сохраняются в `target/telegram-onboarding-qa/` и артефакте существующего browser CI.

## Компактный блок на странице оплат

`fragments/player-telegram :: admin` использует native `details/summary` без начального `open`. Заголовок, действие «Развернуть/Свернуть» и четыре счётчика доступны постоянно; пояснение, действия и список скрываются вместе. Обновление списка не заменяет контейнер и не меняет раскрытие. Live-область результата находится снаружи `details`, поэтому видима при сворачивании во время запроса.

`player-telegram.js` хранит только boolean раскрытия в `localStorage` по ключу `telegram-admin-expanded:<ownerId>:<tournamentId>`. ID текущего Owner рендерится сервером; контакты и данные сеанса не сохраняются. При недоступном хранилище работает обычное переключение без запоминания. Форма оплат остаётся отдельной и не пересоздаётся. Переключение не отправляет API-запросов; прежние кнопки действий и ограничения SUPER_ADMIN сохранены.

Браузерный прогон выдерживает полное минутное окно перед каждой ролью: другие сценарии используют тот же IP и общий лимит API. Лимиты приложения не меняются; при чтении страницы проверяется HTTP 200 сводки, чтобы отказ API не выглядел как ошибка счётчика. Бюджет дочернего процесса учитывает эти паузы.

Автоматическая проверка `PlayerTelegramBrowserTest.paymentDisclosurePreservesDraftsAcrossRolesAndRequests` и `tests/browser/telegram-disclosure.browser.mjs`: реальный Spring/Thymeleaf и 20 учебных участников, четыре административные роли, RU/ES/EN, 1440/390/320 px, клавиатура, черновик формы, reload/возврат, другой аккаунт/турнир, завершение и ошибка запроса в закрытом блоке. Мутирующие Telegram-запросы в этом браузерном сценарии перехвачены; отправка оплаты и внешние сообщения запрещены. Дополнительные DOM-проверки включены в `tests/player-telegram-ui.test.cjs`.

Проверено 26.11.2026: 17 DOM-тестов, 15 составных проверок в настоящем Chrome с сервером и отдельной PostgreSQL, включая все четыре роли и три локали; полный Maven verify на актуальной основной ветке — 1745 тестов, 0 ошибок/провалов, 11 дополнительных сценариев пропущено. Новый браузерный сценарий выполнен отдельным запуском с `browser.qa=true`. Документация и миграция инструкций — без расхождений; relay — 48 тестов успешно. Проверялись размеры браузера, физические телефоны не использовались. Рабочие данные не менялись.

## История первоначального интерфейса

Описанные ниже ограничения относятся к прежним этапам; результаты новой проверки компактного блока приведены выше.

### Изолированный браузерный прогон

`PlayerTelegramBrowserTest` запускает настоящий Spring HTTP-сервер на loopback, отдельную QA-базу и `tests/browser/player-telegram.browser.mjs`. Запуск только при `-Dbrowser.qa=true`; в обычном verify тест пропущен. Внешние Telegram API, почта и уведомления подменены, scheduling и автоматические рассылки отключены. Production-доступы и токен не нужны.

Прогон проверяет ES/RU/EN по языку браузера, фактическую регистрацию в основу и резерв, окно на 1440/390/320, запись WhatsApp через настоящий API/CSRF, повторную запись без предложения и чтение выбора в новом контексте браузера (для RU также WebKit). Админка проверяется с ручной locale. Ссылка Telegram создаётся явным кликом, внешний чат не открывается; Java проверяет сохранённую locale и статусы регистраций в БД. Отдельный подключённый профиль не получает повторное предложение. Отчёт и снимки — `target/telegram-browser-qa/`, включены в существующий CI browser job. Это дополнение не заменяет живое подключение в Telegram.

Задача #1295, серверная зависимость #1294. Расширены действующие Thymeleaf-профиль и административная страница состава/оплат. Рейтинг, React-пилот и мобильный клиент не переключаются.

Проверено локально:
- Три параметризованных прогона реального Thymeleaf: ES/RU/EN, персональная ссылка и скрытие блока при выключенном флаге.
- Четыре JS DOM-теста: явное создание ссылки с CSRF и защита двойного клика; отключение и обновление статуса; безопасный вывод имён и проблем отправки; отсутствие автоматического повтора после неопределённой мутации.
- Команда после установки frontend-зависимостей: NODE_PATH=frontend/node_modules node --test tests/player-telegram-ui.test.cjs.
- docs-drift и git diff --check успешны. Backend unit-проверки описаны в player-telegram-validation.md.

Не проверено: настоящий браузер 320/390/1440 и полный путь с сервером/БД. Среда запрещает локальные сетевые соединения; браузер дополнительно запретил file-превью. Ограничение не обходилось. CSS содержит перенос кнопок и строк для малого экрана, но чтение CSS не считается браузерной приёмкой. Полный Maven verify блокируется PostgreSQL-соединением; требуется CI и доступный отдельный стенд. Черновик не означает готовность к выпуску.
# Предложение после записи и способ связи

В `/players/dashboard` и карточке турнира подключён фрагмент `registration`. `PlayerTelegramRegistration.mount` вызывается только из веток успешной регистрации (индивидуальной, готовой пары, резерва и одиночной заявки). Он читает серверный статус, пропускает подключённых, WhatsApp и недоступного бота, затем добавляет предложение в действующее окно результата. Правила и результат сохраняются. Поздний ответ не добавляет предложение в заменённое или закрытое окно; устаревший таймер результата не закрывает новое окно. При показе предложения автозакрытие приостанавливается.

WhatsApp записывается через CSRF-защищённый PUT, без playerId. Подтверждение показывается только после ответа сервера; выбор меняется в профиле. Старый link удаляется из интерфейса после WhatsApp. В админке отображаются предпочтение и необходимость ручной связи. Автоматических WA-сообщений нет. Все тексты, включая ошибки и сообщения сохранения, берутся из ES/RU/EN bundle текущего сайта; отдельной клиентской локали и локального источника предпочтений нет.

Проверено после дополнения: 10 JS DOM-тестов; 6 реальных Thymeleaf-прогонов профиля/предложения по ES/RU/EN и feature flag; 9 тестов существующего locale resolver. Полный локальный Maven verify останавливается на недоступной PostgreSQL (запрет сокетов); relay — 48 тестов, 6 ошибок запрета socket bind. Браузерная проверка с backend и реальный Telegram не выполнены. Нужен повторный CI на опубликованном head и изолированный проход перед выпуском.

## Ограниченный первый запуск

`eligible` в статусе управляет видимостью профиля и предложения после записи. Изначально профильный блок скрыт; ошибка чтения не раскрывает предложение другим аккаунтам. Админский блок рендерится через серверный `PlayerTelegramAccess.allowsEvent`. Пилот по умолчанию ограничен одним player ID и одним event ID; остальные пользователи продолжают пользоваться сайтом без новых предложений Telegram. Отдельный browser-проход проверяет разрешённый и посторонний аккаунты, API-отказ и отсутствие блока в другом мероприятии. Внешний Telegram в CI подменяется.
