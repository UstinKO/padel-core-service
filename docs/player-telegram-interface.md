# Интерфейс Telegram: проверка

## Изолированный браузерный прогон

`PlayerTelegramBrowserTest` запускает настоящий Spring HTTP-сервер на loopback, отдельную QA-базу и `tests/browser/player-telegram.browser.mjs`. Запуск только при `-Dbrowser.qa=true`; в обычном verify тест пропущен. Внешние Telegram API, почта и уведомления подменены, scheduling и автоматические рассылки отключены. Production-доступы и токен не нужны.

Прогон проверяет ES/RU/EN по языку браузера, фактическую регистрацию в основу и резерв, окно на 1440/390/320, запись WhatsApp через настоящий API/CSRF, повторную запись без предложения и чтение выбора в новом контексте браузера (для RU также WebKit). Админка проверяется с ручной locale. Ссылка Telegram создаётся явным кликом, внешний чат не открывается; Java проверяет сохранённую locale и статусы регистраций в БД. Отдельный подключённый профиль не получает повторное предложение. Отчёт и снимки — `target/telegram-browser-qa/`, включены в существующий CI browser job. Это дополнение не заменяет живое подключение в Telegram.

Задача #1295, серверная зависимость #1294. Расширены действующие Thymeleaf-профиль и административная страница состава/оплат. Рейтинг, React-пилот и мобильный клиент не переключаются.

Проверено локально:
- Три параметризованных прогона реального Thymeleaf: ES/RU/EN, персональная ссылка и скрытие блока при выключенном флаге.
- Четыре JS DOM-теста: явное создание ссылки с CSRF и защита двойного клика; отключение и обновление статуса; безопасный вывод имён и проблем отправки; отсутствие автоматического повтора после неопределённой мутации.
- Команда после установки frontend-зависимостей: NODE_PATH=frontend/node_modules node --test tests/player-telegram-ui.test.cjs.
- docs-drift и git diff --check успешны. Backend unit-проверки описаны в player-telegram-validation.md.

Не проверено: настоящий браузер 320/390/1440 и полный путь с сервером/БД. Среда запрещает локальные сетевые соединения; браузер дополнительно запретил file-превью. Ограничение не обходилось. CSS содержит перенос кнопок и строк для малого экрана, но чтение CSS не считается браузерной приёмкой. Полный Maven verify блокируется PostgreSQL-соединением; требуется CI и доступный отдельный стенд. Черновик не означает готовность к выпуску.
# Предложение после записи и способ связи

В `/players/dashboard` и карточке турнира подключён фрагмент `registration`. `PlayerTelegramRegistration.mount` вызывается только из веток успешной регистрации (индивидуальной, готовой пары, резерва и одиночной заявки). Он читает серверный статус, пропускает подключённых, WhatsApp и недоступного бота, затем добавляет предложение в действующее окно результата. Правила и результат сохраняются. Поздний ответ не добавляет предложение в заменённое или закрытое окно; устаревший таймер результата не закрывает новое окно. При показе предложения автозакрытие приостанавливается.

WhatsApp записывается через CSRF-защищённый PUT, без playerId. Подтверждение показывается только после ответа сервера; выбор меняется в профиле. Старый link удаляется из интерфейса после WhatsApp. В админке отображаются предпочтение и необходимость ручной связи. Автоматических WA-сообщений нет. Все тексты, включая ошибки и сообщения сохранения, берутся из ES/RU/EN bundle текущего сайта; отдельной клиентской локали и локального источника предпочтений нет.

Проверено после дополнения: 10 JS DOM-тестов; 6 реальных Thymeleaf-прогонов профиля/предложения по ES/RU/EN и feature flag; 9 тестов существующего locale resolver. Полный локальный Maven verify останавливается на недоступной PostgreSQL (запрет сокетов); relay — 48 тестов, 6 ошибок запрета socket bind. Браузерная проверка с backend и реальный Telegram не выполнены. Нужен повторный CI на опубликованном head и изолированный проход перед выпуском.
