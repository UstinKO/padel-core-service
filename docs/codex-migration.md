# Работа с Codex и перенос автономного конвейера

Локальные правила и исполняемый адаптер подготовлены в LFPT-0761. Боевой Telegram relay
этими изменениями не переключается. Его текущие настройки и исходники нужно отдельно сверить
с сервером перед активацией, как требует журнал `pipeline-engine-lessons.md`.

Сверка 2026-10-30: служба relay активна; серверные `relay.py`, `engine.py` и `test_relay.py`
совпали с локальными исходниками прежней версии, `test_engine.py` на сервере отсутствует.
В стандартном PATH сервера не найдены `codex`, `gh`, `java` и `node`. Перед выкаткой сравнение
нужно повторить: состояние сервера может измениться. Локальный Codex CLI авторизован через ChatGPT;
короткий запуск в режиме только чтения завершился успешно. Это не проверка серверного воркера.

Подготовка 2026-10-30: на сервере отдельно собран Docker-образ Codex-воркера; внутри него успешно
прошли 46 тестов relay. Тестовая PostgreSQL запущена с отдельным томом и закрытым паролем,
проверены статус healthy, лимит 512 МБ и привязка к `127.0.0.1:55432`. Старая служба остаётся active.
Авторизация Codex и сквозной пилот на сервере пока не подтверждены; новый relay не включён.
Последующая диагностика: вход через device code не сохранился; запрос авторизации завершился
сетевой ошибкой и затем ответом `503 Service Unavailable`. Стандартные seccomp/AppArmor настройки
Docker блокируют namespaces и mount, необходимые песочнице Codex. Подготовлены отдельные профили
`automation/codex-worker/apparmor.profile` и `seccomp.profile.json`: в одноразовом контейнере без сети
и capabilities с `no-new-privileges` песочница Codex запустилась, запись за пределы рабочей области
отклонена. Это тест изоляции, не подтверждение готовности полного Telegram-конвейера.

## Файлы и команды

| Было | Теперь |
|---|---|
| `.claude/CLAUDE.md` | `AGENTS.md` — обязательная точка входа; `.agents/PROJECT.md` — технический справочник |
| `.claude/CODE_STYLE.md`, `CODE_REVIEW.md`, `GIT_WORKFLOW.md`, `DESIGN.md` | Те же документы в `.agents/` |
| `.claude/agents/` | `.agents/roles/` — инструкции ролей, без привязки к инструментам Claude |
| `/develop-feature` | `$develop-feature`, навык `.agents/skills/develop-feature/SKILL.md` |
| Старые команды конкретного Team Playoff | `.agents/archive/`, исторические постановки |
| Подготовка новой фичи | `$new-feature`, навык подготовки спецификации без реализации |
| Anthropic routine `/fire` | Отдельный процесс `codex exec` с чистым checkout |
| Игнорируемая локальная копия `scripts/telegram-relay/` | Версионируемый код `automation/telegram-relay/`; серверную копию сверить отдельно |

Codex автоматически читает корневой `AGENTS.md`; навыки проекта находятся в `.agents/skills/`.
Подробные инструкции загружаются по ссылкам из точки входа, а не целиком при каждой задаче.
После переноса начни новую сессию Codex, чтобы обновился список навыков. В текущей сессии
инструкции навыка можно прочитать по его пути.

Старые `.claude/worktrees/` и `.claude/settings.local.json` сохранены локально и исключены из Git.
Перемещение зарегистрированных Git worktree требует отдельного `git worktree move`, а не `mv`.
Разрешения прежнего `settings.json` не являются разрешениями Codex; резервная копия приватна.

## Сохранённый протокол

Telegram → relay → SQLite-очередь → Codex → GitHub → pipeline-merge → deploy → archive-specs.
GitHub остаётся источником состояния: `Pipeline-Task`, `Depends-On`, `Closes`, `pipeline:*`,
`🤖 pipeline-questions` и `🤖 pipeline-reply`. Выход CLI с кодом 0 означает только завершение
процесса: задача готова после подтверждённого мержа и успешного деплоя всех её слоёв.

Очередь сохраняет прежние карточки, связи и статусы. При первом запуске новый код добавляет
nullable-колонки `execution_id` и `launch_key` в SQLite без удаления записей. Ключ запуска сохраняется
до создания процесса, поэтому рестарт relay восстанавливает то же исполнение. Провал запуска или выполнения CLI
отображается как сбой, включая случай, когда агент не успел создать issue. Старые задачи без
`execution_id` продолжают отслеживаться по GitHub.

## Выделенный CLI-воркер

Для каждой одноразовой копии `codex exec` получает `--add-dir` только для её `.git`: без этого
песочница блокирует создание ветки и коммита. Другие Git-каталоги остаются вне этой выдачи прав.

Контейнер relay дополнительно проверяет systemd-таймер `padel-codex-monitor.timer`. После двух
последовательных сбоев или пяти перезапусков за пять минут он отправляет одно аварийное уведомление
в тот же канал, что старая служба; при восстановлении монитор готов сообщить о новом сбое. Адресат
и токен находятся только в `/etc/padel-codex/monitor.env`, состояние — в отдельной приватной папке.

Для размещения на существующем сервере подготовлены `automation/codex-worker/Dockerfile` и
`compose.yml`: отдельный образ, отдельный том PostgreSQL и тома состояния/авторизации, ограничения
памяти 2 ГБ для воркера и 512 МБ для тестовой БД, одна CPU для воркера. База публикуется только на
`127.0.0.1:55432`. Воркер использует host network для доступа к существующему локальному выключателю
конвейера; это изоляция файлов и процессов контейнером, а не изоляция сетевого доступа от сервера.
Профиль `relay` по умолчанию выключен, чтобы подготовка базы или образа не запустила второй polling.
Запуск и авторизацию проверяют до переключения старой службы.

Это выбранная реализация адаптера, а не обещание доступного hosted API для Codex.
Он запускает установленный CLI с ранее выполненной авторизацией. Доступность и лимиты аккаунта
нужно проверить на самом воркере. GitHub Actions с OpenAI API — отдельный возможный способ
исполнения, который эта миграция не включает и не оплачивает.

Требования к выделенной машине или контейнеру:

- Отдельный пользователь `padel-codex`, Python 3.9+, Git, `gh`, Codex CLI, Java 21,
  Node/pnpm и Playwright/Chromium для UI-проверок.
- `codex login` и `codex login status` от имени пользователя службы. Секреты авторизации остаются
  в его домашней директории, не в Git. Не копировать пользовательские токены в сообщения или промпты.
- `gh` с правами на push, issue, PR и чтение Actions. Для `git clone/push` настроить
  `gh auth setup-git`; read-only PAT движка (`GITHUB_TOKEN_RO`) этого не заменяет.
- Отдельный PostgreSQL с БД, имя которой заканчивается `_codex_test`. Пример конфигурации в
  `automation/telegram-relay/.env.example` использует порт 55432. Воркер не создаёт и не удаляет БД.
- `MAX_PARALLEL=1`: все checkout этого экземпляра используют одну тестовую БД. Для параллельной
  работы нужны изолированные воркеры с отдельными базами и портами.
- Защищённый доступ к существующему API выключателя конвейера с `X-Internal-Secret`.
  Не открывать внутренний endpoint для всего интернета ради воркера.
- Сеть для Codex, GitHub и загрузки зависимостей. CLI работает с sandbox `workspace-write`;
  доступ к сети включён явно. Ограничения и политики самого хоста не обходятся. Если обязательная
  операция заблокирована политикой воркера, исправить его настройку и повторить пилот;
  автоматически отключать sandbox запрещено.

Новый код не использует `ROUTINE_ID`, `ROUTINE_TOKEN` или Anthropic API. Переменные Telegram
и shared secret не передаются дочернему процессу. Задача хранится в приватной spool-папке и
передаётся CLI через stdin, без текста и временных ссылок в аргументах процесса.
У каждой задачи свой checkout и закрытые журналы; директории имеют права 0700.
Оператор задаёт срок хранения и очищает только завершённые задания после диагностики:
в них могут находиться персональные данные и временные ссылки.
Рабочие процессы сериализуются файловой блокировкой. Закрытая карточка не освобождает тестовую БД,
пока предыдущий процесс ещё жив; истечение deadline само по себе тоже не освобождает слот.

## Активация после проверки

1. Влить правила и код в `master`: воркер клонирует именно эту ветку и откажется работать без `AGENTS.md`.
2. Скачать серверные `relay.py`, `engine.py`, тесты и unit-файлы, сравнить с локальной исходной копией.
   Перенести отсутствующие исправления. Не заменять работающую серверную версию вслепую.
3. Подготовить выделенную среду и авторизацию выше. Скопировать `.env.example` в приватный
   `/etc/padel-codex/relay.env`, заполнить значения; права 0600, владелец пользователь службы.
4. Проверить `python3 -m unittest discover -s automation/telegram-relay -p 'test_*.py'`.
   Выполнить отдельный пилот CLI в этой среде: чтение правил, тесты с тестовой БД, браузер,
   GitHub issue/ветка/PR и проверки. Для пилота не ставить `pipeline:ready`, пока не проверен весь путь.
5. Согласовать конкретное переключение службы. Остановить старый polling перед запуском нового:
   два процесса с одним Telegram bot token одновременно читать `getUpdates` не должны.
6. Сделать резервную копию `state.json` и `engine.db` при остановленном старом relay, перенести
   их в `/var/lib/padel-codex/`, сохранить владельца и права. Не запускать задачи со статусом `running`
   заново, пока не проверены их GitHub-следы и старые сессии.
7. Установить `automation/telegram-relay/padel-codex-relay.service`, проверить окружение службы,
   включить новый relay и наблюдать журнал, карточку, ответ на вопросы, PR, автомерж и деплой.

Откат: остановить новый relay, сохранить его состояние и восстановить бэкап старого relay и SQLite.
Старый движок без поддержки CLI не должен повторно запускать незавершённые Codex-задачи:
сначала сверить их ветки, PR и работающие процессы. Не запускать оба polling одновременно.

## Проверки и официальные источники

Локальные проверки не запускают Codex, не расходуют модельный лимит и не отправляют сообщения:

```bash
python3 .github/bin/check-agent-migration.py
python3 .github/bin/docs-drift.py
python3 -m unittest discover -s automation/telegram-relay -p 'test_*.py'
```

Основание формата: [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md),
[навыки](https://learn.chatgpt.com/docs/build-skills),
[неинтерактивный Codex CLI](https://learn.chatgpt.com/docs/non-interactive-mode).
Флаги также сверены с установленным `codex exec --help`. Успешный живой пилот и состояние сервера
не подтверждаются этими unit-тестами и должны быть проверены при активации.
