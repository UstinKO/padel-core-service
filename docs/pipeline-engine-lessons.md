# Движок задач конвейера: разобранные баги, гипотезы и грабли

Журнал инцидентов движка задач (`scripts/telegram-relay/engine.py`, `relay.py`), роутины (`.claude/commands/develop-feature.md`) и оркестратора автомержа (`.github/workflows/pipeline-merge.yml`) за 2026-10-19 — 2026-10-23. Как всё устроено — в [pipeline-autonomy](pipeline-autonomy). Здесь собрано, что ломалось, какие гипотезы подтвердились, а какие нет, и чего не делать, чтобы не наступать на те же грабли.

**Читать перед** правкой движка, релея, оркестратора или `develop-feature.md`, а также перед разбором жалобы вида «задача висит», «ответа нет», «отчёт не пришёл».

## 1. Как разбирать «задача висит / ответа нет»

Порядок. Каждый следующий шаг дороже предыдущего.

1. **GitHub — следы задачи.** Движок видит только их.
   - `gh api -X GET search/issues -f q='repo:UstinKO/padel-core-service is:issue "Pipeline-Task: <N>"'` и то же с `is:pull-request`. Без `is:` поиск отвечает 422.
   - Таймлайн PR: `gh api repos/UstinKO/padel-core-service/issues/<PR>/timeline`. Видно, кто и когда ставил и снимал метки, когда был мерж.
   - Деплой и оркестратор: `gh run list --workflow deploy.yml`, `gh run list --workflow pipeline-merge.yml --json event,createdAt,conclusion`.
2. **Состояние движка на сервере.** SSH на прод, адрес в приватном `.claude/SECURITY.md`. Чтение без согласования, изменения — только с явного «да» пользователя.
   - `journalctl -u telegram-relay --since ... | grep -E "INFO Задача #<N>|WARNING|ERROR"`. Переходы статусов пишутся как `Задача #N: running → stalled`.
   - `engine.db`: на сервере нет `sqlite3`, читать через `python3 -c "import sqlite3; ..."`. Полезные поля таблицы `tasks`:
     - `status`;
     - `snapshot_key` — что движок видит в GitHub;
     - `fired_key` — что было при запуске сессии;
     - `notified` — что уже отправлено в чат: `done`, `stalled`, `q:<id>`, `reply:<id>`, `nudge:ready`;
     - `progress_at`, `fired_at` — время последнего движения и запуска сессии;
     - `session_url` — URL **последней** запущенной сессии.
3. **Что сделала сессия роутины** — `RemoteTrigger get_run_log <session_id>`, где `session_id` — `cse_…` из карточки. Это единственный способ увидеть итоговое сообщение сессии и её рассуждения. Сразу отвечает на вопросы вида «почему не поставила метку» или «почему не ответила» (#5252, #5304).
4. **Не верить хронологии чата.** Карточка задачи редактируется на месте. Карточка, отправленная ночью, утром уже показывает «✅ влито на прод», а отдельное итоговое сообщение приходит только одно, в момент `done`. Отсюда жалобы вида «отчёт только по одной задаче» (20.10).

## 2. Правила работы с движком

- **Движок вне git.** `scripts/telegram-relay/` в `.gitignore`. Источник истины — копия на сервере в `/opt/padel-app/telegram-relay/`. На сервере бывают правки, которых нет локально (LFPT-0626 поправили только там).
  - Перед правкой скачать серверные `engine.py` и `relay.py` и сравнить с локальными.
  - Перед выкаткой ещё раз сравнить серверную версию со скачанной. Её мог поменять кто-то другой.
- **Выкатка.** Только с явного согласия пользователя, на каждую выкатку отдельно.
  1. `python3 -m py_compile`, `python3 -m unittest test_engine` — все тесты зелёные.
  2. Бэкап `engine.py.bak-<дата>-<задача>`.
  3. `scp`, затем `systemctl restart telegram-relay`.
  4. 1–2 минуты смотреть `journalctl`.
- **Запросы к GitHub проверять на живом API** (`gh api ...`) до выкатки. `FakeGH` в тестах принимает любой запрос, поэтому ошибку 422 тесты не поймали (§3.4).
- **Тест на баг должен падать без исправления.** Проверить это, временно откатив правку в копии файла.
- **`Snapshot.key()` — общий ключ для «было ли движение».** От него зависят `progress_at` (stall, nudge) и сравнение с `fired_key` (оценка сессии-починки). Добавил поле в ключ — проверь оба места. После выкатки ключ меняется у всех задач один раз, и застрявшие задачи «оживают» (§3.10).
- **Закрыть задачу вручную** (статус `answered` или `cancelled`) так, чтобы обновилась и карточка в чате. Перед этим сделать бэкап `engine.db`.
  ```bash
  cd /opt/padel-app/telegram-relay && set -a && . ./.env && set +a && python3 - <<'EOF'
  import relay, engine as eng
  cfg = relay.Config()
  e = eng.Engine(eng.EngineConfig(repo=cfg.github_repo, db_path=cfg.engine_db), eng.Store(cfg.engine_db),
                 eng.Telegram(send=lambda t, reply_markup=None, reply_to=None: relay.send_telegram_message(cfg, t, reply_markup, reply_to),
                              edit=lambda m, t, reply_markup=None: relay.edit_telegram_message(cfg, m, t, reply_markup)),
                 None, fire=lambda t: ("error", "manual", None), is_paused=lambda: False)
  e.store.update(<N>, status=eng.ANSWERED, note="закрыто вручную <дата>"); e.render(<N>)
  EOF
  ```
  Закрытую задачу можно продолжить реплаем на её карточку. Кнопка «🔁 Перезапустить» работает только для `failed`/`stalled`/`conflict`.

## 3. Инциденты

### 3.1. Прогон без своей issue/PR молча завершился — задача «в работе» 2,5 ч (#5252, 19.10)
- **Симптом.** Заказчик спросил «что сейчас происходит?». Задача висела «в работе», через 3 ч показала «нет движения».
- **Причина.** Сессия ответила за 85 с, но только в своём окне. Своей issue/PR у такого прогона нет, и движку нечего отслеживать.
- **Исправление (LFPT-0641).** Протокол `🤖 pipeline-reply <N>`: комментарий в любой связанной issue, первая строка — маркер. Движок пересылает текст в чат и закрывает задачу статусом `answered` («💬 ответ дан»). Уже доставленные ответы движок отмечает в `notified` как `reply:<comment_id>`.
- **Урок.** У любого прогона должен быть след в GitHub. Иначе для движка его нет.

### 3.2. Новые вопросы под той же меткой не доходили до чата (LFPT-0641)
- **Причина.** Ключ снимка учитывал метку `pipeline:needs-input`, но не id комментариев `🤖 pipeline-questions`. Повторная блокировка при той же метке для движка не была движением.
- **Исправление.** id вопросов включены в ключ. Повторно блокироваться нужно **новым** комментарием `pipeline-questions`.
- Там же исправлено: сводка очереди показывала служебные строки пачки (`[…]`, `--- Сообщение N ---`) вместо текста задачи.

### 3.3. PR без `Pipeline-Task` — задача «в работе», хотя влита и задеплоена (#5280, 19.10)
- **Причина.** Роутина написала маркер в issue #646, но не в PR #648. Движок видел закрытую issue без PR и держал `RUNNING`.
- **Исправление.** `GitHub.prs_closing()`: для issue задачи, которую не закрывает ни один PR с маркером, движок ищет PR с `Closes #<issue>`.
- **Урок.** Не полагаться на то, что роутина выполнит все пункты чек-листа. Движок должен восстанавливать связи по тем данным, которые есть в GitHub.

### 3.4. Поиск `pipeline-reply` получал 422 (регрессия LFPT-0641, 19.10)
- **Причина.** В `find_replies` не было `is:issue` / `is:pull-request`. Поиск issues в GitHub API без этих квалификаторов отвечает 422. В коде рядом, в `search_task`, это уже было написано в комментарии.
- **Исправление.** Общий `GitHub._search()` делает по запросу на каждый тип.
- **Урок.** См. §2: проверять запросы на живом API.

### 3.5. PR зелёный, а `pipeline:ready` нет — 3 ч «в работе», потом «нет движения» (#5289, #5317, 20.10)
- **Причина.** Сессия открыла PR, pr-check прошёл за ~2 минуты, но метку сессия не поставила и завершилась. Почему, не выяснено: логи этих сессий не смотрели (§5).
- **Исправление.** Если все issue задачи покрыты открытыми PR, проверки зелёные, а метки нет 30 минут (`nudge_minutes`), движок **один раз** сам продолжает задачу: «проверь Шаг 4 и поставь `pipeline:ready`». Отметка `nudge:ready` в `notified`. Сработало на #5317: через 30 минут после выкатки PR влит без участия человека.
- **Урок.** На каждое ожидание следа от роутины нужен таймаут и автоматическое действие, а не только «нет движения» через 3 ч.

### 3.6. Продолжение после ответа не оставило нового ответа (#5304, 20.10) — **не исправлено**
- **Ход событий.** Первая сессия ответила (`pipeline-reply`), задача получила статус `answered`. Заказчик ответил реплаем «сейчас есть что-то в работе?», запустилось продолжение. Вторая сессия **сознательно** не стала писать дубль ответа: «движок уже закрыл задачу». После продолжения задача снова `running`, старый ответ уже доставлен и повторно не засчитывается. Через 3 ч задача ушла в «нет движения».
- **Причина.** В `develop-feature.md` не сказано, что **каждый** прогон, включая продолжение, оставляет **новый** `pipeline-reply`, даже если ответ не изменился.
- **Что сделать.** Дописать это правило в «Прогон без своей issue/PR». Дубль в GitHub безвреден: движок различает ответы по id комментария. Задача в §5.

### 3.7. Двойное нажатие «Отправить» — «⚠️ Буфер был пуст» (#5325, 20.10)
- **Причина.** Релей однопоточный: проход движка, затем опрос Telegram, затем обработка обновлений. Пока идёт проход движка или медленная обработка предыдущего обновления (запуск роутины при отправке задачи), нажатие ждёт в очереди. Telegram спустя ~10–15 с считает его устаревшим (`query is too old`), у кнопки крутится индикатор, человек жмёт ещё раз. Второе нажатие застаёт буфер уже пустым.
- **Исправление.** Повторное «Отправить» в течение 3 минут после отправки (`RECENT_SUBMIT_SECONDS`) отвечает «Уже отправлено ✅». В журнал пишется `WARNING`, если проход движка или обработка обновления дольше 8 с (`SLOW_STEP_SECONDS`).
- **Что показал журнал.** С 21.10 по 23.10 проход движка длился до 23 с, обработка обновления — до 17,7 с, 3 нажатия опоздали. Симптом закрыт, причина осталась (§5).

### 3.8. Оркестратор не просыпался после деплоя (#5384, 21.10)
- **Симптом.** Бэк #681 задеплоен в 11:59 UTC, фронт #682 с `Depends-On` ждал до 13:07.
- **Причина.** Деплой запускает сам оркестратор: `gh workflow run deploy.yml` от `GITHUB_TOKEN`. У прогонов, запущенных этим токеном, GitHub **не порождает** событие `workflow_run`. По истории ни один деплой ни разу не разбудил оркестратор. Страховочный `schedule` каждые 15 минут GitHub почти не исполняет: 21.10 с 08:00 до 13:45 UTC был один прогон из ~22.
- **Следствие.** Job `deploy-result` (метка `pipeline:deploy-failed` + `pipeline:halt`) висел на том же событии и **не запускался ни разу**. Упавший деплой не остановил бы автомерж.
- **Исправление (LFPT-0685, PR #686).**
  - Job `pipeline-next` в `deploy.yml` запускает `pipeline-merge.yml` с `deploy_run_id`. `workflow_dispatch` от `GITHUB_TOKEN` разрешён.
  - `deploy-result` дожидается окончания прогона деплоя и смотрит его итог.
  - В триггер `pull_request_target` добавлен `unlabeled`: раньше снятие `pipeline:conflict` оркестратор не будило.
  - **Проверено после мержа:** 7 из 7 деплоев PR разбудили оркестратор за несколько секунд.
- **Урок.** Цепочки «workflow → событие → другой workflow» с `GITHUB_TOKEN` не работают, кроме `workflow_dispatch` и `repository_dispatch`. `schedule` — не страховка.

### 3.9. «🟠 Автопочинка не помогла», хотя она помогла (#5384, 21.10) — регрессия от §3.5
- **Причина.** Для nudge в ключ снимка добавили статус pr-check. Сессия-починка запушила фикс, статус сменился на pending, и ключ изменился. Движок решил: «сессия закончила, а `pipeline:conflict` осталась». Метку сессия сняла через минуту.
- **Исправление.** При сравнении с `fired_key` статус pr-check не учитывается (`_without_checks`).
- **Урок.** См. §2 про `Snapshot.key()`.

### 3.10. «Конфликт», которого не было (#5384, 21.10) — **не исправлено**
- Сборка на свежем master упала на нестабильном тесте из бэк-PR. Оркестратор ставит `pipeline:conflict` на **любую** упавшую проверку на свежем master, и заказчик видит «конфликт при вливании». Предложение: отдельная метка или хотя бы другой текст (§5).

### 3.11. Ответ найден через 1,5 ч — ложное «нет движения» (#5445, 22.10) — **не исправлено**
- **Ход событий.** Сессия оставила `pipeline-reply` в issue #700 через 2 минуты после запуска (15:26 UTC). Движок нашёл его через поиск только в 16:54 UTC. К этому времени задача без следов уже 60 минут как ушла в «нет движения» (порог из §3.12), а заказчик успел спросить «Что за задача?».
- **Вероятная причина.** Задержка индекса поиска GitHub по тексту комментариев. Не доказано, но других объяснений не нашлось: сейчас тот же запрос находит #700 сразу.
- **Что сделать.** Искать ответы не поиском, а через `GET /repos/{repo}/issues/comments?since=<fired_at>&sort=created`. Индекса там нет, и это один запрос на все задачи без следов (§5).

### 3.12. Пороги ожидания задач без следов и сводка (20.10)
- Задача без issue/PR и без ответа получает «нет движения» через 60 минут (`traceless_stall_minutes`), а не через 3 ч. С задержкой поиска из §3.11 это дало ложную тревогу. До исправления §3.11 порог не опускать.
- Сводка очереди не показывает задачи без движения дольше 24 ч (`summary_stalled_hours`). Раньше #5252 висела в каждой сводке.

## 5. Открытые задачи

1. **`develop-feature.md`:** каждый прогон без своей issue/PR, включая продолжение, оставляет **новый** `pipeline-reply` (§3.6).
2. **Движок:** `find_replies` через `issues/comments?since=` вместо поиска (§3.11).
3. **Релей:** вынести опрос GitHub и запуск роутины из основного цикла, например в фоновый поток, чтобы нажатия обрабатывались сразу (§3.7).
4. **Оркестратор:** не называть упавшую проверку на свежем master конфликтом (§3.10).
5. **Движок:** реплай-вопрос о статусе («есть что-то в работе?») запускает целую сессию. Можно отвечать сводкой, но есть риск принять настоящее уточнение за вопрос о статусе.
6. Когда сессия снова оборвётся до `pipeline:ready` (nudge сработает), посмотреть её `get_run_log` и закрыть вопрос о причине (§3.5, §4).

## 6. Константы движка и релея (на 2026-10-23)

| Константа | Значение | Где |

| `max_parallel` | 2 | `EngineConfig` |

| `stall_hours` | 3 ч без движения → «нет движения» | `EngineConfig` |
| `nudge_minutes` | 30 мин: зелёный PR без `pipeline:ready` → одно автопродолжение | `EngineConfig` |
| `traceless_stall_minutes` | 60 мин без issue/PR и ответа → «нет движения» | `EngineConfig` |

| Автопочинка `pipeline:conflict` | одна (`repair_count`) | `Engine._apply` |
