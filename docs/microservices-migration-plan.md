# План перехода на микросервисную архитектуру — padel-core-service

> **Статус:** v2, обновлён по итогам ревью (2026-07-22) — зафиксирован выбор технологий для Фазы 0, переставлен порядок выноса сервисов (Identity — сразу после Payments, не в конце)
> **Контекст:** MVP пройден, продукт работает и приносит доход. Следующий этап — подготовка архитектуры к: (1) горизонтальному масштабированию монолита в Docker Swarm (несколько реплик/сервис для роста нагрузки), (2) мобильным приложениям (iOS/Android), (3) новым продуктам/рынкам на той же платформе.
> **Ресурсы:** один разработчик + Claude Code. Жёстких дедлайнов нет.
> **Инфраструктура:** один физический сервер (VPS), Docker Swarm вместо голого Compose — реплики нужны для увеличения пропускной способности на этой же ноде, не для отказоустойчивости между серверами. Managed K8s и мультиузловой кластер — не сейчас.

---

## 0. Как читать этот план

Из-за соло-разработки план построен вокруг **strangler fig** (постепенное выдавливание функциональности из монолита), а не переписывания с нуля. Каждая фаза:

- даёт самостоятельную ценность даже если следующая фаза не начнётся никогда;
- откатываема без даунтайма дольше стандартного деплоя;
- не требует одновременного знания "всей будущей архитектуры" — фазы можно останавливать и возобновлять с недельными/месячными паузами (нет команды, которая простаивает).

Оценки объёма даны в **S / M / L / XL** (не в днях — темп у соло-разработчика с ассистентом сильно скачет), плюс отдельно отмечен риск.

## 2. Принцип декомпозиции и карта связей между доменами

### 2.1. По какому принципу режем на сервисы

Границы сервисов проводятся по **доменам** (bounded context из DDD), а не по техническим слоям (не "отдельно все контроллеры", не "отдельно вся работа с БД"). Практический тест на "это отдельный сервис или нет" — три вопроса:

1. **У домена своя предметная лексика и свой жизненный цикл?** (Оплата живёт и меняется независимо от логики турнира; правила турнира по King of Court меняются независимо от правил Americano.) Если да — кандидат на отдельный сервис.
2. **Домен может владеть своими таблицами, не заставляя другие домены делать прямой SQL/JPA-join в них?** Если сейчас это не так (см. карту связей ниже) — до выноса нужен рефакторинг на API/событие, а не сохранение "общей БД под капотом".
3. **Кто клиент этого домена — только текущий продукт (падел-турниры) или он переиспользуется другими продуктами/каналами (мобильное приложение, будущий второй продукт)?** Это разделяет сервисы на два слоя:

| Слой | Сервисы | Свойство |
|---|---|---|
| **Платформенные** (переиспользуются всеми продуктами) | Identity, Payments, Notifications | Не знают о конкретных турнирных форматах. Новый продукт подключается к ним через API, не дублирует пользователей/платежи/уведомления заново. |
| **Продуктовые** (специфичны для падел-турниров) | Tournament-core, Bracket, King of Court, Americano-family, Ranking, Clubs | Знают о доменной специфике текущего продукта. Новый продукт (другой вид турниров, другой рынок) получает свой набор продуктовых сервисов, но переиспользует платформенные. |

Это прямое обоснование того, зачем резать по доменам, а не по-другому: когда появится второй реальный продукт, он не должен требовать переделки логина, платежей или email/Telegram-уведомлений — он просто становится ещё одним потребителем уже существующих платформенных сервисов и получает свой набор продуктовых.

**Следствие для порядка выноса:** платформенные сервисы имеет смысл выносить раньше продуктовых там, где это не противоречит риск-профилю — каждый продуктовый сервис, вынесенный после платформенного, сразу интегрируется с финальным контрактом (auth, платежи, уведомления), а не переделывается дважды. Это и есть причина, по которой Identity в этой версии плана передвинут на Фазу 3 (сразу после Payments) — см. обоснование в Фазе 3 ниже.

### 2.2. Карта связей между доменами (входные данные для порядка выделения сервисов)

| Домен | Размер | Связанность |
|---|---|---|
| **Payments** | Мал (808 LOC) | Читает/пишет `TournamentRegistration` напрямую, но никто из форматов не лезет в Payment. Нет внешнего шлюза — интеграцию всё равно предстоит писать с нуля. **Наименьший риск + есть бизнес-ценность (реальный шлюз).** |
| **Notifications (Email/Telegram)** | Средний (1356 LOC) | Уже изолирован (единая точка входа `EmailService`), уже асинхронный (`@Async`, 12 методов). `TelegramBotPoller` — единственное исключение, лезет в `PlayerRepository` напрямую. |
| **Bracket** | Мал (714 LOC) | Единственный формат без JPA-связей на `Player`/`Tournament` (хранит голые `Long` id) — самый "отвязанный" по дизайну. Хорошая тренировочная площадка перед Americano/KoC. |
| **King of Court** | Большой (1912 LOC) | Единственный домен с real-time (WebSocket). Явные `notify*`-методы — уже похоже на публикацию доменных событий. |
| **Americano + Team Americano + Team Playoff** | Самый большой (5720 LOC суммарно) | Общие модели (`AmericanoRound`, `AmericanoTeam`) между тремя сервисами, плюс `TournamentService` напрямую чистит `AmericanoPlayerRepository` при удалении турнира. Выделять последним, когда паттерны обкатаны. |
| **Players/Identity** | Средний (1666 LOC) | `PlayerRepository` дергается напрямую из 9 классов вне `PlayerService` (KingOfCourtService, TeamPlayoffService, DoubleTournamentRegistrationService, TelegramBotPoller, TournamentService, security/OAuth2). Технически самый рискованный домен для выделения — нужен клиент-адаптер до реального разреза (см. Фазу 1). Платформенный сервис (§2.1) и приоритет бизнеса: нужен мобильным приложениям, будущим продуктам, и расширяемой модели ролей (сейчас `OwnerRole`: `SUPER_ADMIN`/`ORGANIZER` — планируется более гранулярная модель для admin-панели). **Выносится сразу после Payments (Фаза 3), а не последним из доменов.** |
| **Tournament + Registration "core"** | 2264 LOC | Настоящий агрегат, от которого зависят все форматы. Скорее всего останется как отдельный сервис-оркестратор дольше всех остальных, либо станет "shared kernel". |
| **Clubs** | Мал (646 LOC) | Слабо связан, но `AmericanoService` напрямую читает `ClubRepository` в обход `ClubService` — незначительный фикс перед разрезом. |
| **Ranking** | Мал (446 LOC) | Единственный потребитель — `MatchService` (Bracket). KoC/Americano ведут свою статистику отдельно — "рейтинг" как концепция сегодня фрагментирован, стоит решить до или во время выделения Bracket. |

## 3. Мины под 2 реплики (нужно закрыть ДО Swarm-масштабирования, независимо от микросервисов)

Требование "2 реплики на бэкенд-сервис + LB/умный gateway" всё равно всплывёт в каждом извлечённом сервисе — дешевле закрыть эти проблемы один раз, на монолите, пока он один процесс с одной кодовой базой.

### 3.1. WebSocket / King of Court real-time (KРИТИЧНО)
`enableSimpleBroker` держит подписки в памяти конкретного инстанса. При нескольких репликах клиент, подключённый к инстансу A, не получит broadcast, инициированный запросом, обработанным инстансом B (а с LB round-robin это будет происходить постоянно).
**Фикс (решено):** RabbitMQ + `enableStompBrokerRelay` вместо `enableSimpleBroker`. RabbitMQ выбран вместо Redis pub/sub, т.к. это встроенная в Spring фича (не нужен кастомный `MessageBroker`) и тот же брокер станет шиной межсервисных событий начиная с Фазы 2 (Payments) — не нужно поднимать второй message broker позже.

### 3.2. Rate limiting (КРИТИЧНО для security-модели)
Guava-кэш в `RateLimitFilter` — у каждой реплики свой независимый счётчик. С несколькими репликами лимит `5r/s` фактически умножается на число реплик, при этом CrowdSec/Nginx рассчитаны на текущие пороги.
**Фикс (решено):** Redis + `bucket4j-redis` (Lettuce-based `ProxyManager`) — минимальные изменения в `RateLimitFilter`, тот же Redis, что и для сессий (3.3).

### 3.3. HTTP-сессии (form login для admin/player web UI)
Без общего хранилища сессий пользователь будет "разлогинен" при каждом запросе, попавшем на другую реплику.
**Фикс (решено):** `spring-session-data-redis` — общее хранилище сессий в Redis. Одновременно с переходом стоит явно задать TTL/жизненный цикл сессии (`server.servlet.session.timeout` + `spring.session.timeout`, отдельно от TTL rate-limit-бакетов) — сейчас это управляется дефолтами Tomcat неявно, при переезде в Redis это нужно решить осознанно (например: сессия игрока — дольше, admin-сессия — короче, из соображений безопасности).
Redis — один инстанс, без Sentinel (осознанно избыточно на этом масштабе): при падении Redis деградация в том, что все разлогинятся и на короткое время ослабнет rate limiting — принятый риск для соло-проекта на одной ноде.

### 3.4. Дублирование cron-задач
`TournamentService.checkExpiredInvitations()`, `SoloRegistrationSchedulerService` (2 джобы), `TelegramReminderScheduler` (3 джобы), `TelegramBotPoller.poll()` (каждые 5 сек!) — если обе реплики их выполняют, будут дублироваться email/Telegram-уведомления и гонки при обработке waitlist.
**Фикс:** `ShedLock` (`net.javacrumbs.shedlock`) поверх Postgres (лёгкий, не требует нового инфраструктурного компонента) — распределённая блокировка на каждый `@Scheduled`-метод. Дешевле и быстрее, чем сразу выносить это в отдельный "scheduler-service".

### 3.5. Health-checks и graceful shutdown
Текущий деплой перезапускает единственный контейнер и ждёт лог "Started...". Swarm rolling update по 2 репликам требует нормального `/actuator/health/readiness` + `/liveness` (`management.endpoint.health.probes.enabled=true`) и `server.shutdown=graceful`, чтобы не рвать соединения при обновлении.

**Вывод фазы:** ставим Redis (сессии + rate-limit + STOMP relay кандидат) и ShedLock как инфраструктурные зависимости до включения второй реплики. Без этого "просто добавить реплику" тихо сломает live-обновления KoC, security rate-limit и уведомления.

## 4. Фазы

### Фаза 0 — Горизонтальное масштабирование монолита (без единого микросервиса)
**Цель:** тот же монолит, но безопасно работающий в N репликах за gateway.
**Объём:** M–L. **Риск:** средний (затрагивает security и real-time — тестировать вручную на проде через canary-реплику).

1. Поднять Redis (Swarm-сервис, реплика 1 — сам по себе stateful, шардирование не нужно на этом масштабе).
2. `spring-session-data-redis` для HTTP-сессий.
3. `bucket4j-redis` для `RateLimitFilter`.
4. STOMP relay (RabbitMQ) вместо `enableSimpleBroker`.
5. `ShedLock` на все `@Scheduled`-методы.
6. `/actuator/health/readiness`+`liveness`, `graceful shutdown`.
7. Выбор и настройка gateway: **Traefik** (нативная интеграция с Docker Swarm через labels, авто-обнаружение сервисов, встроенный LB) — предпочтительнее, чем городить это поверх текущего голого Nginx. Nginx на хосте остаётся как внешний край (Cloudflare→Nginx уже отлажен, трогать не нужно), а Traefik встаёт между Nginx и Swarm-сервисами как internal service mesh/gateway. Это же решение станет фундаментом для роутинга к будущим отдельным сервисам (Фаза 2+) — конфигурируется один раз.
8. Docker Swarm stack-файл (`docker-stack.yml`) на основе текущего `docker-compose.yml`, `deploy.replicas: 2` для `padel-app`, `update_config` (rolling, `order: start-first`).
9. CI/CD: обновить `.github/workflows/deploy.yml` под `docker stack deploy` вместо `docker compose up -d --no-deps`.

**Проверка готовности фазы:** убить одну из двух реплик под нагрузкой (ручной live-тест на проде в тихие часы) — сессии, KoC realtime-обновления и rate-limit не должны деградировать.

### Фаза 1 — Contract-first API и версионирование (готовим почву под мобильные приложения)
**Цель:** REST API, пригодный для внешнего мобильного клиента, отделённый от Thymeleaf-конкретики.
**Объём:** M. **Риск:** низкий.

1. Ввести префикс `/api/v1/...` для всех существующих `/api/*` эндпоинтов (текущие — оставить как deprecated-алиасы на переходный период, снять после релиза мобильного приложения).
2. OpenAPI-спецификация (`springdoc-openapi`) — сгенерировать из текущих контроллеров, вручную доописать то, что MapStruct/DTO не покрывают. Это даёт: (a) живую документацию взамен вручную поддерживаемых таблиц в PROJECT.md/docs, (b) контракт для мобильной команды/будущих продуктов.
3. Явно развести "public read API" (турниры, клубы, ranking — не требует авторизации) от "authenticated API" — сейчас это смешано по пакетам, а не по политике доступа.
4. Refresh-токены уже есть (`JwtService` выпускает access 24h + refresh 7d) — проверить, что flow пригоден для мобильного клиента (в проводе через Bearer, не через cookie).
5. Push-уведомления как отдельный контракт (ещё не сервис) — зарезервировать событие "нужно уведомить пользователя" в `TournamentNotificationService`, чтобы потом просто добавить APNs/FCM-канал рядом с email/Telegram.
6. **Анти-коррупшн слой для Identity (подготовка к Фазе 3, делается здесь, пока риск нулевой):** ввести интерфейс `PlayerDirectory` (или похожий), который сегодня внутри реализован через прямой `PlayerRepository`, и заменить им все 9 прямых обращений вне `PlayerService` (`KingOfCourtService.java:34`, `TeamPlayoffService.java:41`, `DoubleTournamentRegistrationService.java:42`, `TelegramBotPoller.java:31`, `TournamentService.java:61`, security/OAuth2-классы). Это чисто внутренний рефакторинг — ничего не режется по сети, поведение не меняется, только точка входа становится одна. Смысл: когда в Фазе 3 `PlayerDirectory` реально станет HTTP/gRPC-клиентом к `identity-service`, единственное, что меняется — реализация интерфейса, а не 9 разбросанных мест по коду. Это самый дешёвый момент для этой работы — риск почти нулевой, а Фаза 3 становится в разы safer.

**Не нужно** строить нативный gateway/BFF для мобильного прямо сейчас — Traefik + `/api/v1` достаточно, пока не появится реальная mobile-специфичная логика агрегации.

### Фаза 2 — Первый вынос: Payments Service
**Почему первым:** наименьшая связанность (см. §2.2), совпадает с реальным бизнес-приоритетом (настоящий платёжный шлюз MercadoPago/Stripe вместо ручной фиксации), и заставляет один раз построить паттерн "событие из монолита → отдельный сервис → событие обратно" на самом низкорисковом домене — этот паттерн затем используется в Фазе 3 (Identity) и во всех следующих.
**Объём:** L. **Риск:** средний (деньги — тестировать тщательно, держать fallback на ручную фиксацию платежей первое время).

1. Новый сервис `payment-service` (Spring Boot, своя БД `payments_db` — первый шаг к разделению данных).
2. Контракт: REST + событие через RabbitMQ (уже поднят в Фазе 0) — `TournamentRegistration` эмитит `RegistrationCreated`/`RegistrationCancelled`, `payment-service` — `PaymentConfirmed`/`PaymentFailed`, монолит слушает и обновляет статус регистрации.
3. Миграция данных `payments_db` из общего Postgres в БД нового сервиса (dump/restore, не онлайн-миграция — объём небольшой).
4. Интеграция реального шлюза (MercadoPago — основной в Аргентине) только внутри нового сервиса, не размазывать по монолиту.
5. `PaymentManagementController` в монолите превращается в тонкий прокси/BFF-вызов к `payment-service` (или временно — фичатогл на два бэкенда, старый ручной flow остаётся для админов ещё один релиз).

### Фаза 3 — Identity Service (Players + Owners + Auth)
**Почему сразу после Payments, а не в конце (изменено по твоему решению):** по принципу §2.1 это платформенный сервис — переиспользуется мобильными приложениями, будущими продуктами, и именно здесь будет жить расширяемая модель ролей (сейчас `OwnerRole` — плоский enum `SUPER_ADMIN`/`ORGANIZER`, для admin-панели планируется более гранулярная модель прав). Технически это самый рискованный домен (`PlayerRepository` дёргался из 9 мест напрямую), но этот риск уже снят в Фазе 1 анти-коррупшн слоем (`PlayerDirectory`) — реальный вынос теперь сводится к замене одной реализации интерфейса на HTTP-клиент, а не к поиску и правке 9 разбросанных мест "на горячую". Ранний вынос также означает, что все последующие сервисы (Notifications, Bracket, KoC, Americano, Core) с самого начала интегрируются против финального auth-контракта, а не переделываются дважды.
**Объём:** XL. **Риск:** средний-высокий (ниже, чем было бы без Фазы 1) — тестировать особенно тщательно login/refresh-token/OAuth2 flow и роли admin-панели, т.к. это меняет модель безопасности всей системы.

1. Убедиться, что анти-коррупшн слой из Фазы 1 (`PlayerDirectory`) действительно закрывает все 9 точек — если появились новые прямые обращения к `PlayerRepository` за время работы над Фазами 1-2, добавить и их сюда до выноса.
2. Новый сервис `identity-service`: `PlayerPadel`, `Owner`, весь `security/`+`security/oauth2/` пакет, `JwtService`, `CompositeUserDetailsService`.
3. **Редизайн модели ролей/прав** как часть этой фазы, не после: заменить плоский `OwnerRole` enum на модель ролей+прав (например, отдельная таблица permissions или хотя бы набор более гранулярных ролей помимо `SUPER_ADMIN`/`ORGANIZER`), раз известно, что admin-панель будет расширяться по ролям — дешевле спроектировать это сразу в новом сервисе, чем сначала выносить как есть, а потом переделывать модель прав во второй раз.
4. **Это меняет модель аутентификации всей системы** — остальные сервисы перестают сами валидировать пароли, а либо (a) доверяют JWT, подписанному `identity-service`, проверяя подпись локально (текущая модель JWT это уже почти поддерживает — просто нужно вынести issuer), либо (b) идут через gateway, который сам валидирует токен и прокидывает `X-User-Id`/`X-Role` вглубь (Traefik ForwardAuth middleware — хорошо сочетается с уже выбранным Traefik из Фазы 0).
5. Рекомендация: **вариант (b), ForwardAuth на Traefik** — меньше дублирования JWT-валидации в каждом будущем сервисе, и это прямая подготовка к мобильным SDK, которым тоже нужен единый auth-эндпоинт.
6. Google OAuth2 flow остаётся полностью внутри `identity-service`.
7. `PlayerDirectory`-клиенты в монолите (из Фазы 1) переключаются на реальный HTTP-вызов к `identity-service` — к этому моменту это должно быть небольшое изменение в одном месте (реализация интерфейса), не поиск по всему коду.

**Открытый вопрос к тебе:** нужна ли расширенная модель ролей для admin-панели раньше, чем дойдёт очередь до этой фазы? Если да — можно спроектировать и внедрить её в монолите уже сейчас, отдельной небольшой фичей (не архитектурная работа, обычная доработка `Owner`/`OwnerRole`), не дожидаясь выноса Identity как сервиса — тогда Фаза 3 просто унаследует уже готовую модель вместо того, чтобы проектировать её с нуля.

Заодно решает проблему дублирования cron-джоб (3.4) окончательно — переносим `TelegramReminderScheduler`, `TelegramBotPoller`, cron-часть `SoloRegistrationSchedulerService` (уведомления) в этот сервис как единственный владелец расписания уведомлений.
**Объём:** M. **Риск:** низкий (email/Telegram — не критичный путь, легко откатить).

### Фаза 9 — Готовность к новым продуктам (multi-tenancy)
**Открывается, а не решается сейчас:** конкретная форма зависит от того, что такое "новый продукт" в вашем понимании — (a) ещё один вид турниров/спорта на той же платформе, (b) отдельный бренд/рынок с тем же движком, (c) B2B-инструмент для клубов. Три этих варианта требуют разного уровня multi-tenancy (от "просто новый `TournamentType`" до полноценного tenant_id во всех таблицах). ## 5. Стратегия данных

- **Каждый новый сервис — своя БД** с самого начала выноса (не shared database между новыми сервисами) — иначе получаем "distributed monolith" вместо микросервисов.
- Для консистентности между сервисами (например, `payment-service` подтвердил оплату → `tournament-core` должен перевести регистрацию в `CONFIRMED`) — паттерн **outbox** в БД-источнике + консьюмер на другой стороне через RabbitMQ, а не двухфазные транзакции.
- Старый монолитный Postgres постепенно "худеет" — таблицы физически переносятся в БД нового сервиса при каждой фазе выноса (dump конкретных таблиц, не всей схемы).
- Liquibase-changelog каждого нового сервиса стартует с нуля (`v1.0-...`) от снапшота вынесенных таблиц, а не наследует общий `changelog-master.yaml`.

## 7. Тестирование (нельзя откладывать до "после микросервисов")

Сегодня в репозитории **один** тестовый файл (`PadelCoreServiceApplicationTests.java`, 27 строк), который глотает исключения при старте и содержит bare `assert` (не работает без `-ea`). Это некритично для монолита с одним автором, но выделение сервисов **без** контрактных тестов между ними — гарантированный источник тихих регрессий, которые некому будет ловить руками при соло-разработке.

Минимум перед началом Фазы 2 (первый вынос):
- Unit-тесты на сервис, который выносится, **до** выноса (быстрее ловить баги, пока код ещё в монолите и легко дебажится).
- Contract-тесты на события в RabbitMQ (Spring Cloud Contract или просто фиксированные JSON-схемы + Pact) — чтобы монолит и новый сервис не разъехались по формату события независимо друг от друга.
- Testcontainers для Postgres/RabbitMQ в CI (`pr-check.yml` уже поднимает Postgres service container — расширить на новые зависимости по мере фаз).

## 8. Наблюдаемость для распределённой системы

Текущий стек (Prometheus + Grafana + Loki, кастомные `@Timed`/`@Counted`/`@TrackErrors`) переживёт разрез без изменений в подходе, но с Фазы 2 добавляется **distributed tracing** — без него отладка "почему регистрация зависла между tournament-core и payment-service" превращается в ручной grep по логам трёх сервисов. Рекомендация: OpenTelemetry SDK + Grafana Tempo (укладывается в уже используемый Grafana/Loki стек без смены вендора). Добавлять начиная с Фазы 2, не откладывать до конца.

## 9. Открытые вопросы (требуют решения по ходу, не блокируют старт)

1. **Ranking:** оставить фрагментированным по форматам (как сейчас) или унифицировать через `ranking-service`, слушающий события `MatchCompleted`/`AmericanoMatchCompleted`/`KoCMatchCompleted` от всех форматов? Решить не позже Фазы 5 (Bracket), т.к. `MatchService` → `RankingService` вызов нужно либо оставить прямым (если Ranking едет вместе с Bracket), либо превратить в событие.
2. **Clubs:** остаются с `tournament-core` (Фаза 8) или выносятся отдельно раньше — актуально, если новые продукты (Фаза 9) подразумевают клубы как самостоятельную B2B-сущность (личный кабинет клуба, аналитика по клубу) независимо от турниров.
3. **Платёжный провайдер:** MercadoPago — единственный, или нужна абстракция под несколько провайдеров сразу (актуально, если "новые рынки" за пределами Аргентины)? Влияет на дизайн `payment-service` в Фазе 2.
4. **Мобильный push:** APNs/FCM как часть `notification-service` (Фаза 4) или отдельный сервис — решить, когда появится первый спринт с реальной мобильной разработкой.
5. **Роли admin-панели:** расширять модель ролей/прав уже сейчас в монолите (быстрее, но потом переносить в Identity) или спроектировать её сразу как часть Фазы 3 (Identity) — см. открытый вопрос в описании Фазы 3.
