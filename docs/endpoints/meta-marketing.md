# Измерение рекламы Meta

## Назначение и границы

Интеграция выключена по умолчанию. Бизнес-портфолио E.Padel.Torneos, рекламный аккаунт `1147420211310878`, dataset/Pixel `930260823500064` («1-Padel | Eventos web»). Наличие этих настроек не доказывает, что Meta получила событие.

`marketing/` — отдельный модуль аналитики. `MarketingEntityListener` делегирует наблюдение сохранённых JPA-регистраций/платежей в `MarketingJournal`; журнал использует JDBC в текущей JPA-транзакции. Он не вызывает сеть и не меняет бизнес-статусы. Откат записи откатывает и события. Нативные SQL-операции тестового инструмента не получают атрибуцию браузера администратора.

## Конфигурация

Параметры `app.analytics.meta.*` в `application.yml` читаются из серверного окружения:

| Переменная | Назначение |
|---|---|
| `META_ENABLED` | `false` по умолчанию; включает сбор только после маркетингового согласия |
| `META_PIXEL_ID` | `930260823500064`; по умолчанию пусто |
| `META_CAPI_ACCESS_TOKEN` | Только серверный секрет доступа к dataset; никогда не включать в frontend, Git, issue, URL или логи |
| `META_API_VERSION` | Версия Graph API, по умолчанию `v26.0`, сверена с официальным примером Meta при реализации |
| `META_TEST_MODE` | `true` по умолчанию; CAPI-запрос содержит `test_event_code` |
| `META_TEST_EVENT_CODE` | Код из Events Manager → Test Events; обязателен для серверной доставки в тестовом режиме |

Без валидного ID нет браузерной аналитики. Без токена/версии/тестового кода нет серверной доставки. События сохраняют режим создания: переключение в production не пересылает тестовую очередь. Перед запуском в production проверить очередь; не заменять IDs и не переигрывать историю.

В production секрет вводится через принятый механизм серверных переменных/игнорируемый `.env`, который уже подключён к контейнеру. Браузер получает только `enabled`, `pixelId`, `testMode`. Для исходящего CAPI нужен HTTPS-доступ к `graph.facebook.com`; браузеру нужны `connect.facebook.net` и `www.facebook.com`. Разрешение доменов не означает выдачу токена и не проверяет его права.

## Согласие и источник

Допустимо только `cookieConsent=accepted` или `cookieConsent=customized` вместе с `marketingConsent=true`. Согласие на аналитику само по себе недостаточно. Посетитель получает случайный HttpOnly cookie `meta_visitor` (90 дней, SameSite=Lax, Secure на HTTPS). Он переживает обычный вход и Google OAuth. Сервер также проверяет срок 90 дней с последнего обращения; ежедневная очистка удаляет просроченные рекламные метки и идентификаторы сопоставления. Без согласия контекст не сохраняется и Pixel не должен загружаться.

Первый размеченный переход фиксируется один раз; последний меняется только при новых UTM или реальном `fbclid`. Прямой визит ничего не стирает. Метки хранятся только как названия/ID кампаний: `[A-Za-z0-9_-]{1,100}`; адреса, URL, произвольный текст и email отбрасываются. Пустая метка не заменяется выдуманным источником. Для рекламных ссылок рекомендуются ID:

```
utm_source=meta&utm_medium=paid_social&utm_campaign={{campaign.id}}&utm_content={{ad.id}}&utm_term={{adset.id}}
```

Запись получает неизменяемый снимок первого/последнего источника и fbp/fbc. Новые кампании после записи не переписывают её оплату. Платёж наследует источник этой записи. Отказ/отзыв согласия очищает сохранённые метки/идентификаторы сопоставления посетителя и снимков и подавляет недоставленные события. Уже переданный Meta запрос нельзя отозвать этим механизмом; отзыв не является API удаления ранее полученных Meta данных.

## События и статусы

| Действие / статус | Событие | Что означает |
|---|---|---|
| Публичная страница | `PageView`, браузер | Просмотр страницы, не запись |
| `/torneo/{id}` | `ViewContent`, браузер | Просмотр конкретного события, не запись |
| `CONFIRMED`, `PARTICIPATED` | `EventRegistration`, браузер | Сохранённая подтверждённая запись |
| `WAITLIST`, `WAITLIST_INVITED` | `EventWaitlist`, браузер | Резерв; не подтверждённое участие |
| `PENDING_PARTNER`, `PARTNER_INVITED`, `PAIR_REGISTERED`, `SOLO_SEARCH`, `SOLO_ADD_LATER` | `EventRegistrationPending`, браузер | Незавершённый подбор/подтверждение пары; не оплаченный участник |
| `CANCELLED`, `SOLO_EXPIRED` | Нет нового успешного события | Отмена не становится конверсией |
| Регистрация аккаунта / клик / ошибка | Нет `EventRegistration` | Успех определяется сохранённой записью, не UI-кликом |
| Новый положительный прирост накопительной суммы в `PAID` | `Purchase`, сервер | Фактически подтверждённые деньги |

На одну запись и категорию выдаётся один постоянный UUID. Перевод из резерва в `CONFIRMED` создаёт `EventRegistration`, повторное сохранение или повторное подтверждение — нет. Для пары с двумя записями события относятся к каждому сохранённому участнику; гость без отдельной записи не превращается в выдуманный аккаунт.

## Оплаты, доплаты и участники

Сумма в существующей форме накопительная. Например: `PAID 400 ARS` → Purchase 400; затем `PAID 1000 ARS` → Purchase 600; повтор `1000` → ничего. До `PAID` сумма не считается подтверждённым поступлением. Используется фактический `Payment.amount`; цена мероприятия никогда не подставляется в `value`. Ноль/неизвестная сумма/неактивный платёж не дают Purchase. Валюты: ARS, USD, EUR, BRL, UYU, CLP, PYG, BOB, PEN, COP, MXN, GBP, CAD, AUD, CHF, JPY. USDT не маскируется под USD; пересчёта валют нет.

Уменьшение суммы не снижает максимальную ранее учтённую базу и не даёт нового Purchase. Смена валюты перебазирует запись без денежного события: нельзя считать изменение `1000 ARS → 10 USD` новым переводом. До доставки событие подавляется, если текущая сумма стала меньше соответствующего накопительного итога, статус перестал быть PAID или валюта изменилась. Уже доставленный Purchase не отменяется: для чистой выручки используется локальный отчёт. Реальное новое поступление после полного возврата следует оформить отдельной платёжной записью, не восстанавливать старую сумму ради повторной конверсии.

`num_items=1` обозначает одну платёжную строку/денежное поступление. `paid_participants` отдельно принимает 0 или 1: первый момент, когда сумма активных PAID по слоту достигает стоимости участия, зафиксированной при записи, в той же валюте. У частичного платежа значение 0, у закрывающей доплаты — 1. Для неизвестной/нулевой цены либо другой валюты полная оплата не выдумывается. Согласованные скидки и иной курс не выводятся из суммы автоматически — в отчёте используется зафиксированная стоимость, это ограничение метрики.

Пара с аккаунтами имеет две регистрации/платёжные строки. Гость-партнёр — отдельный слот той же регистрации, определяемый существующим маркером `PARTNER_PAYMENT`. У каждого независимая сумма и отметка полной оплаты. Если один банковский перевод оплачивает несколько игроков, организатор распределяет фактическую сумму между строками: нельзя записывать весь перевод каждому. Число Purchase отражает поступления по строкам, а не число банковских транзакций и не число участников. Для стоимости оплаченного участника используются уникальные полностью оплаченные слоты с подтверждённой регистрацией из экспорта, а не количество Purchase.

Миграция фиксирует исторические суммы как базу и не назначает старым записям новый рекламный источник. Никакой исторической выгрузки при включении нет. Суммы, наблюдавшиеся при выключенной интеграции, также не отправляются при последующем включении. Повтор старой формы без paymentId переиспользует существующую активную строку под блокировкой регистрации.

## Доставка и приватность

Purchase не отправляется из браузера: между браузером и CAPI нет двух копий одного Purchase. У браузерных событий серверный `eventId` передаётся как Meta `eventID`; у серверных `event_id` хранится в БД и не меняется при retry. `event_time` — исходное время, не время повтора. Очередь использует `FOR UPDATE SKIP LOCKED`, аренду на 2 минуты, ограниченный backoff. Успех — HTTP 200 **и** `events_received=1`; 429/408/сетевой сбой/5xx повторяются, прочие 4xx дают FAILED. Ответы и запросы с токенами/сопоставлением не логируются. Если Meta вернула `messages` при HTTP 200, журнал содержит только ID события, HTTP-код и число сообщений; такой ответ не доказывает показ в Test Events и не превращается в повторную отправку уже принятого события.

Meta дедуплицирует имя+ID в пределах 48 часов. Поэтому автоматическая доставка и выдача браузерных конверсий заканчиваются через 47 часов, затем EXPIRED; не возобновлять такие события новым ID. Это доставка с повторными попытками в окне дедупликации, а не гарантия приёма Meta. При утраченном ответе повтор сохраняет прежние идентификаторы.

Пользователь подтвердил два способа оплаты: перевод вне сайта и наличные на месте. Для `PaymentMethod.CASH` новое поступление получает `action_source=physical_store`; для банковских переводов (`BANK_TRANSFER`, `TRANSFERENCIA`), прочих и неизвестного способа — `other`. Реального веб-платёжного шлюза нет, поэтому ручная отметка в админке сама по себе не делает оплату событием `website`. Источник сохраняется в `marketing_events_db.action_source` при создании каждого прироста и не вычисляется заново из изменённого платежа при retry. Например, 400 наличными, затем увеличение итога до 1000 переводом дают 400 с `physical_store` и 600 с `other`; смена метода без прироста суммы не создаёт денежного события и не меняет прежний источник. Миграция v1.59 оставляет существующим событиям `other`, не пересчитывает историю и не запускает повторную отправку. Сопоставление — SHA-256 случайного ID посетителя — инициатора записи (у пары это может быть основной игрок, а не персональная идентичность гостя) и fbp/fbc, полученные с согласия в браузере участника. IP, User-Agent организатора, email, телефон, имя, исходный URL с query/токеном и UTM в CAPI не передаются. Для будущего настоящего веб-платежа нужен отдельный достоверный источник и требования website-events; нельзя просто заменить action_source на website без данных участника.

## API

| Метод | Путь | Доступ / результат |
|---|---|---|
| GET | `/api/marketing/config` | Публичный, только несекретная конфигурация |
| POST | `/api/marketing/context` | Публичный, CSRF + маркетинговое согласие; `{utm:{source,medium,campaign,content,term},fbclid,path,fbp}`; ответ — хешированный `externalId` для согласованного сопоставления Pixel/CAPI и реальный `fbc` |
| GET | `/api/marketing/events` | Согласие + HttpOnly cookie конкретного посетителя, его недоставленные браузерные события |
| POST | `/api/marketing/ack` | CSRF + согласие + тот же посетитель; `{eventId}`. Подтверждает постановку в Pixel, не приём Meta |
| GET | `/admin/marketing/export.csv?tournamentId=123` | Только управляющий этим турниром Owner, проверка `TournamentAccessService`; другой клуб/организатор отклоняется |

Ответы не кэшируются. CSV не содержит контактов/идентификаторов сопоставления. В нём запись, платёжная строка/слот, текущие статусы/сумма/валюта, признак полностью оплаченного подтверждённого слота, первый/последний источник и число созданных/доставленных Purchase. Считать DISTINCT `(registration_id, partner_slot)` по `fully_paid_slot=true`, не складывать признак по нескольким платежам одного слота. Расходы рекламы загружаются отдельно из Ads Manager по ID кампании/объявления; API рекламного кабинета эта интеграция не вызывает.

## Проверка через Meta Test Events

1. В тестовой среде задать Pixel ID, серверный токен с доступом к dataset, `META_ENABLED=true`, `META_TEST_MODE=true` и код из Events Manager → выбранный dataset → Test Events. Для наличных на месте (`physical_store`) выбрать канал «Офлайн»; код канала «Сайт» может отличаться. Источник не менять ради выбранного канала. Production не менять до ревью/мержа/разрешённого деплоя.
2. Открыть сайт из браузерного теста Events Manager с UTM. Отказать в маркетинговом согласии: Pixel не загружается, конверсий нет. Затем в новой тестовой сессии дать маркетинговое согласие.
3. Проверить PageView/ViewContent и фактически сохранённую тестовую запись. Резерв должен дать EventWaitlist, а не EventRegistration. Клик/ошибка/регистрация аккаунта не должны дать EventRegistration.
4. Организатор отмечает наличные 400 ARS, затем меняет итог на 1000 ARS: проверить два серверных Purchase (400 и 600), исходные event_id, сохранённый `action_source` и отдельный paid_participants. Отдельно проверить смену наличных на перевод при доплате: новый источник относится только к новому приросту. Повторить сохранение/перезагрузку — новых денежных событий нет.
5. Проверить пару, другой валютный платёж, отзыв согласия, временный сетевой отказ и повтор с тем же ID. Сопоставить Test Events и строки очереди/экспорта.
6. Тестовый код относится к CAPI; браузерный Pixel проверяется через браузерную сессию Test Events, в нём серверного токена/кода нет. Наличие HTTP 200 в локальном mock-тесте не доказывает приём Meta. Перед production отдельно согласовать отключение тестового режима и провести разрешённый выпуск.
7. HTTP 200 + `events_received=1` означает приём API, а не подтверждение обработки/показа в интерфейсе. Проверять `messages` и фактическую строку с исходным ID. В выполненной проверке один и тот же безденежный контроль с `website` появился в веб-сессии, а с `other` — нет; это не основание подменять источник перевода. Контроль `website` не проверяет браузерный Pixel и не заменяет Purchase.
8. `test_event_code` не считать гарантией исключения данных из рекламного измерения. Для изолированных массовых синтетических прогонов использовать отдельный dataset; не отправлять повторно новые ID вместо уже существующих событий.

Официальные источники, прочитанные при реализации: [параметры CAPI](https://developers.facebook.com/documentation/ads-commerce/conversions-api/parameters), [server event](https://developers.facebook.com/documentation/ads-commerce/conversions-api/parameters/server-event), [customer information](https://developers.facebook.com/documentation/ads-commerce/conversions-api/parameters/customer-information-parameters), [дедупликация](https://developers.facebook.com/documentation/ads-commerce/conversions-api/deduplicate-pixel-and-server-events), [использование API](https://developers.facebook.com/documentation/ads-commerce/conversions-api/using-the-api).

## Браузерная реализация и её проверка

Общий `meta-marketing.js` подключён через fragment cookie-consent, использует существующий CSRF-wrapper. Он загружает SDK только после маркетингового согласия, передаёт тот же хеш external_id, что CAPI, и отключает autoConfig. В Events Manager также оставить выключенными автоматический сбор событий/Automatic Advanced Matching: внедряемая схема не разрешает считывание контактов из форм.

Обрабатываются публичные страницы главной, каталога, клубов, рейтинга, событий и результатов; /players/dashboard может выдавать конверсии без PageView приватной страницы. Логин/регистрация аккаунта и токеновые/служебные страницы исключены. Любой неизвестный query, адрес/токен в query или небезопасный referrer блокирует SDK; валидные UTM/fbclid/lang сохраняются до очистки query через history.replaceState. Это сознательный приоритет приватности: часть посещений со служебными параметрами не имеет Pixel-просмотра.

Скрипт ожидает сохранения источника перед fetch/form-запросом регистрации, но не ожидает сети Meta. После успеха берёт события из журнала. Только постановка события в загруженный Pixel подтверждается `/ack`; это не подтверждение приёма Meta. При отказе SDK событие остаётся в очереди; при потере ack тот же eventID может повториться в пределах окна дедупликации. После отзыва уже загруженного SDK повторное согласие начнёт Pixel на следующей безопасной странице, не переиспользуя старую идентичность.

Проверки в настоящем Chromium с локальными API-стабами и подменённым SDK (не отправляют событий в Meta):

```bash
npm install --prefix /tmp/padel-meta-browser --no-audit --no-fund --ignore-scripts playwright-core@1.64.1
PLAYWRIGHT_MODULE=/tmp/padel-meta-browser/node_modules/playwright-core/index.mjs \
CHROMIUM_PATH=/usr/bin/chromium node --test tests/meta-marketing.browser.mjs
```

Это отдельный браузерный набор для существующего Thymeleaf-интерфейса, не изменение Expo-зависимостей. Backend-набор: `./mvnw -Dtest=MarketingIntegrationTest,MetaCapiClientTest test`; полный — `./mvnw verify` с отдельной PostgreSQL.

При включённой интеграции на странице управления платежами турнира есть ссылка «Выгрузить источники рекламы» (ES/RU/EN), ведущая в этот защищённый CSV.
