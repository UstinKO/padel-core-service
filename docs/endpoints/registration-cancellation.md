# История отмен участия — LFPT-0900

Это завершение недостающей части #900 поверх мягкой отмены #792. Регистрация остаётся CANCELLED/is_active=false, ID/платежи/атрибуция сохраняются. Отдельные неизменяемые события не пропадают при следующей записи на мероприятие с тем же регистрационным ID. Полная отмена пары — одно событие с двумя затронутыми рядами; выход одного участника сохраняет место второго и не продвигает резерв.

## Совместимость HTTP

Существующие маршруты, обязательные параметры и ответы success/message или PairTerms сохранены. Индивидуальная отмена остаётся доступной действующему мобильному клиенту; /app и исходники Expo не менялись.

| Маршрут | Изменение |
|---|---|
| POST `/players/tournaments/{tournamentId}/cancel` | Необязательный заголовок If-Registration-Version |
| POST `/players/tournaments/{tournamentId}/cancel-double` | Такой же заголовок для option=self/full; замена имеет прежний отдельный контракт |
| GET `/players/tournaments/{tournamentId}/my-registration` | Дополнительное поле cancellationVersion; прочие поля прежние |
| POST `/test/tournaments/{tournamentId}/remove-player/{playerId}` | Необязательный comment; инициатор берётся из Owner principal, не из тела запроса. Прежняя защита SUPER_ADMIN сохраняется |
| POST `/api/tournaments/double/{tournamentId}/pair-cancellation` | Повтор того же подтверждения возвращает сохранённый ответ без новой финансовой записи, письма или продвижения |

В TournamentRegistrationDto добавлено cancellationVersion. Версия увеличивается только при отмене; повтор успешной записи сохраняет счётчик. Заголовок сравнивается с активным циклом под блокировкой турнира. Запоздавший запрос прежней версии не отменяет новую активную заявку, отвечает прежним безопасным форматом ошибки с локализованным сообщением.

**Ограничение старых клиентов:** запрос без версии остаётся совместимым. Если он повторён уже после новой записи, сервер не может отличить его от нового пользовательского действия. Новые потребители должны передавать версию; кабинетный контракт #902 использует эту основу. Для PairTerms проверка состава/токена уже обязательна. Старые action-токены сбрасываются при реактивации; токен резервной заявки сам по себе не является доказательством владения аккаунтом.

Комментарий организатора — обычный текст до 255 символов, без разметки/недопустимых управляющих символов. Валидация не пишет событие и не отменяет заявку. Служебный reason старого кода не становится публичным комментарием. Системные ошибки отмены не раскрывают SQL/комментарий в HTTP-ответе.

## Запись и чтение

Существующие доменные входы делегируют переход RegistrationCancellationService: player self/full, организатор, Americano, резервная ссылка, замена участника и системная деактивация. Каждая операция остаётся в своей исходной модели допуска. Общий helper требует активную транзакцию; состояние, журнал и очередь фиксируются/откатываются вместе. Письма передаются существующему EmailService после commit. Долговременной очереди доставки это не добавляет.

Контекст формируется доверенным серверным входом. ActorKind: PLAYER/OWNER/SYSTEM/UNKNOWN; Scope: PARTICIPANT/PAIR. ReasonCode: PARTICIPANT_WITHDRAWAL/PAIR_WITHDRAWAL/ORGANIZER_REMOVAL/PLAYER_DEACTIVATED/PARTICIPANT_REPLACED/LEGACY_UNKNOWN. Подписи причин находятся в i18n ES/RU/EN. Передача actorId/actorKind/reasonCode пользовательским параметром ничего не меняет.

Внутренний batch-сервис forPlayer возвращает только события переданного аутентифицированного PlayerPadel в выбранных мероприятиях. forManager проверяет SUPER_ADMIN/ADMIN либо владельца/организатора события или CLUB_ADMIN соответствующего клуба через TournamentAccessService. Эти методы должны получать principal сервера; клиентский playerId не является полномочием. REST кабинета использует эту выборку. См. [Мои мероприятия](account.md#мои-мероприятия).

Безопасная Entry: eventId, tournamentId, registrationId, version, cancelledAt, initiator, scope, reasonCode, organizerComment. Нет actorId, контактов, служебного текста, токенов и финансового receipt. Данные комментария доступны только затронутому участнику и управляющему мероприятием; public event/live и посторонние игроки их не получают.

PairTerms receipt хранит SHA-256 запроса, ID игрока/строки/цикла и исходный расчёт без токена. Он записывается в той же транзакции до commit и не переписывается. Повтор разрешён только для того же игрока и отменённого цикла; реактивация/изменение состава не даёт применить прежний токен к новой записи. Это не меняет сохранённые денежные условия pair_cancellations_db.

## Данные и проверки

[Схема v1.71](../database-architecture.md#история-отмен-регистраций): registration_cancellations, registration_cancellation_members и счётчик исходной строки. Backfill фиксирует только известное: старое время либо NULL, UNKNOWN/LEGACY_UNKNOWN, без публичного копирования свободного cancellationReason. Удалённую ранее историю восстановить нельзя.

Проверки охватывают реактивацию, повтор/конкуренцию, rollback/ошибку БД, сохранение платежей/резерва, автора из проверенного пути, старые ссылки, HTTP-версию, права и комментарии, миграцию известных/неизвестных исторических данных. Реальные браузерные проверки используют только отдельную тестовую БД и синтетические аккаунты. Новая модель queued_at/participation_status/guest claim и интерфейс кабинета не входят в #900.

Ручная запись пары из `/test/tournaments` сохраняет ID отменённых регистраций и связывает оба активных профиля новым ID бронирования. Платежи, отмены и атрибуция сохраняют ссылки на исходные записи. Новый состав и созданные гостевые профили сохраняются вместе. При повторе гостевого запроса с тем же `Idempotency-Key` сервер сверяет содержимое и версии отмен участников, прежде чем вернуть результат. Тот же ключ не возобновляет позднее отменённую заявку. Ручная запись на индивидуальное мероприятие также сохраняет регистрационный ID.
