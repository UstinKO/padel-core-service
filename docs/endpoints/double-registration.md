# API: Парная регистрация — `/api/tournaments/double`

**Контроллер:** `DoubleTournamentRegistrationController`  
**Назначение:** Регистрация пары игроков на парный турнир.

**LFPT-0687:** игрок, регистрирующий пару, уже сам договорился с партнёром — регистрация
завершается немедленно (статус по занятости турнира, `CONFIRMED`/`WAITLIST`), без ожидания
email-подтверждения от партнёра и без действия координатора. Партнёр без аккаунта создаётся
сразу же (контакт — телефон и/или Telegram; email у партнёра теперь не обязателен и в форме
регистрации не запрашивается, см. `tournament-details.html`). Описанный ниже двухэтапный
email-flow (`POST /confirm`) остаётся только как легаси-путь для регистраций, созданных до
этого изменения.

---

## Сохранение истории при отмене и повторной регистрации

Отмена всей пары через личный кабинет и отмена администратором через
`POST /test/tournaments/{tournamentId}/remove-player/{playerId}` сохраняют оба регистрационных
ряда со статусом `CANCELLED` и `is_active=false`. Платежи, профиль игрока, другие мероприятия
и маркетинговая атрибуция сохраняются. Повторная парная/соло-регистрация и добавление
партнёра переиспользуют неактивный ряд, сохраняя его ID и платежи.

Отмены одного мероприятия сериализуются блокировкой строки турнира до чтения регистраций.
Повторная отмена не продвигает резерв и не создаёт новое письмо. Прежние правила
резерва и ограничения самостоятельной отмены сохраняются. Уведомления об отмене и
продвижении резерва передаются в существующий `EmailService` после commit;
при rollback они не отправляются. Это не добавляет долговременную очередь доставки:
сбой процесса между commit и вызовом `EmailService` остаётся ограничением текущей архитектуры.

## Письма о статусе пары

При самостоятельной записи или добавлении партнёра каждый участник с обычным email
получает письмо по итоговому статусу после фиксации регистрации. Для `WAITLIST` это
уведомление о резерве с известной позицией. Подтверждение участия отправляется после
перехода в `CONFIRMED`. При немедленном переводе через очередь используется письмо
о переводе из резерва.

## Флоу парной регистрации

```
Игрок 1: POST /register (партнёр — контакт по телефону/Telegram, без аккаунта)
           ↓ аккаунт партнёра создаётся сразу, обе регистрации — CONFIRMED или WAITLIST
           ↓ (по занятости турнира, как и для партнёра с уже существующим аккаунтом)
Готово — ожидания не требуется.

Легаси (регистрации, созданные до LFPT-0687): Игрок 1 → статус PARTNER_INVITED с токеном
           ↓ email партнёру со ссылкой
Игрок 2: клик по ссылке → GET /double-registration/complete?token=...  (PartnerRegistrationController, view)
           ↓ подтверждение
Игрок 2: POST /confirm?token=... → пара встаёт в конец очереди резерва (LFPT-0668)
```

## POST `/api/tournaments/double/{tournamentId}/register`

**Кто вызывает:** Авторизованный игрок (Игрок 1) с дашборда или страницы турнира; клиент 1Padel.App (LFPT-0707) — парная запись Americano/Team Americano внутри приложения, тот же контракт (партнёр — существующий игрок по ID либо новые данные без email, LFPT-0687).  
**Аутентификация:** `ROLE_PLAYER`.

### Алгоритм

1. Извлекает ID текущего пользователя из principal (только `PlayerPadel`, не `Owner`).
2. Загружает `TournamentDto` по `tournamentId`.
3. Вызывает `DoubleTournamentRegistrationService.registerForDoubleTournament(tournamentDto, currentUserId, partnerDto)`:
   - Проверяет, что игрок не регистрирует сам себя.
   - Если партнёр уже есть в системе (найден по `existingUserId`/email/телефону) — создаёт записи для обоих игроков немедленно, статус по занятости турнира (`CONFIRMED`/`WAITLIST`).
   - Если партнёра нет — **создаёт его аккаунт сразу** (`nombre`/`apellido`/`telefono`/`telegramUsername`/`email` из запроса, уровень `SIN_ESPECIFICAR`) и регистрирует пару тем же путём, что и для уже существующего партнёра (LFPT-0687) — без промежуточного статуса и без ожидания подтверждения.
4. Возвращает результат со статусом и позицией.

### Контракт

**Path param:** `tournamentId` — Long

**Request body** `application/json`:
```json
{
  "nombre":           "Ana (обязательно)",
  "apellido":         "López (обязательно)",
  "email":            "ana@example.com (опционально — партнёру email больше не обязателен, LFPT-0687)",
  "telefono":         "+54911111111 (опционально, если partnerDto.existingUserId указан)",
  "telegramUsername": "ana_padel (опционально, альтернатива/дополнение к телефону, LFPT-0687)"
}
```

**Response 200 OK** (LFPT-0687 — пара сформирована сразу, `status` уже финальный):
```json
{
  "success":         true,
  "message":         "Registro completado",
  "status":          "CONFIRMED",
  "position":        2,
  "waitlistPosition": null
}
```

**Response 400 Bad Request**:
```json
{
  "success": false,
  "message": "Ya estás registrado en este torneo o..." | "No puedes registrarte contigo mismo" | "..."
}
```

**Response 401 Unauthorized**:
```json
{
  "success": false,
  "message": "Usuario no autenticado"
}
```

**Response 500**:
```json
{
  "success": false,
  "message": "Error al procesar el registro: ..."
}
```

### Замечания (ревью)

> **[MINOR]** Ошибки `DataIntegrityViolationException` перехватываются и возвращают generic-сообщение. Полезно для безопасности, но при отладке не даст понять причину коллизии.

> **[MINOR]** Возвращается `200 OK` вместо `201 Created`.

## POST `/api/tournaments/double/confirm` (легаси, LFPT-0687)

**С LFPT-0687 новые регистрации этим путём не создаются** — `registerForDoubleTournament`,
`addPartnerToSoloRegistration` и `replacePlayerInPair` регистрируют партнёра без аккаунта сразу
же (см. выше). Этот endpoint остаётся рабочим только для регистраций в статусе
`PARTNER_INVITED`, созданных до деплоя этого изменения — им всё ещё нужно пройти по ссылке
из уже отправленного письма, чтобы не остаться зависшими навсегда.

**Кто вызывает:** `PartnerRegistrationController` (view-контроллер) после того, как Игрок 2 перешёл по ссылке.  
**Аутентификация:** Не требуется (токен из email является credential'ом).

### Алгоритм

1. Принимает одноразовый `token` из query param.
2. `DoubleTournamentRegistrationService.confirmPartnerRegistration(token)`:
   - Валидирует токен (не истёк, существует).
   - **LFPT-0668**: обе регистрации (Игрок 1 и Игрок 2) всегда ставятся в конец очереди резерва (`WAITLIST`, позиция = максимум + 1), затем вызывается `TournamentService.processWaitlistForTournament` — он подтверждает пару (`CONFIRMED`) немедленно, только если место свободно и очередь до неё дошла. Раньше при наличии свободного места пара подтверждалась сразу, без учёта уже ожидающих в резерве полностью сформированных пар — исправлено, чтобы вновь подтверждённая пара не обходила их очередь.
3. Возвращает DTO регистрации (с её итоговым статусом — `CONFIRMED` или `WAITLIST`).

### Контракт

**Request**: `POST /api/tournaments/double/confirm?token=<uuid>`

**Response 200 OK**: `TournamentRegistrationDto` обоих игроков (либо только текущего — нужно уточнить в сервисе).

**Возможные ошибки**: выбрасываются исключения без обработки → 500 если токен не найден.

### Замечания (ревью)

> **[закрыто, сверено с кодом 2026-10-16]** `TournamentRegistrationException` → 400 с сообщением, прочие ошибки → 500 с `success: false`.

> **[SECURITY — актуально на 2026-10-16]** Токен передаётся в query param — попадёт в Nginx access log и браузерную историю. Для подобных одноразовых ссылок это приемлемо, но стоит убедиться, что токен достаточно длинный и энтропийный (UUID — окей).

## Неполный резерв и готовые пары (LFPT-0759)

Режимы `SOLO_SEARCH` и `SOLO_ADD_LATER` принимаются при полном турнире. Оба статуса обозначают неполный резерв. Такая заявка не занимает место и не получает позицию среди готовых пар. Режим поиска сохраняется для списка кандидатов и предложений.

При добавлении согласованного партнёра в пару используются существующие одиночные заявки, если оба уже записаны. Обе строки получают общее время очереди `queued_at` по более ранней заявке. Готовые пары продвигаются по этому времени при наличии места, в одной транзакции под блокировкой турнира. В ожидании пара получает общую позицию, которая пересчитывается после изменения очереди.

Ручной перевод в основу допускается для готовой пары при наличии места. Возврат из основы обновляет время очереди у обоих участников, чтобы пара встала после ожидающих. Письмо сообщает итоговый статус.

### Self-service действия из email (без логина, по токену `partnerActionToken`)

| Method | URL | Описание |
|--------|-----|----------|
| GET | `/reserva/accion/confirmar?token=X` | No-op подтверждение, что заявка ещё актуальна — не меняет состояние, просто фиксирует отклик |
| GET | `/reserva/accion/cancelar?token=X` | Страница подтверждения отмены (превью турнира), без побочных эффектов |
| POST | `/reserva/accion/cancelar` (`token`) | Отменяет резервную регистрацию (`TournamentRegistration.cancel(...)`); идемпотентно для уже отменённой |
| GET | `/reserva/accion/resultado` | Redirect-target после `POST /reserva/accion/cancelar` (flash-сообщение success/error, тот же `waitlist-confirmation.html`) |

Токен действует для активной неполной заявки в `SOLO_ADD_LATER`, `SOLO_SEARCH` или историческом `WAITLIST`. При формировании пары токен отзывается.

### `SOLO_EXPIRED` — больше не назначается

Статус остался в `RegistrationStatus` для исторических записей. Новая неполная заявка находится в резерве с момента создания.

## Клиент 1Padel.App (LFPT-0707) — парная запись внутри приложения

Экран парной записи `mobile-app/` (раздаётся на `/app/`) для Americano с `modality: DOBLES` и `AMERICANO_TEAMS` переиспользует существующие эндпоинты без изменений в их контракте:
- `POST .../register` — «есть партнёр» (сразу, существующий игрок или новые данные без email).
- `POST .../register-solo` (`soloType: SEARCH|ADD_LATER`) — «ищу партнёра на месте» / «добавлю партнёра позже».
- `POST .../add-partner` — добавление существующего или нового партнёра к соло-регистрации (`SOLO_SEARCH`/`SOLO_ADD_LATER` либо исторический `WAITLIST` без партнёра); готовая пара получает `CONFIRMED` или `WAITLIST` с учётом очереди.
- `GET .../looking-for-partner` и `POST .../propose-pair/{targetRegistrationId}` — список игроков без пары и предложение объединиться (email-приглашение, как и на сайте; принятие предложения — только по ссылке из письма, в приложении не реализовано).

Собственный статус регистрации на конкретное событие клиент узнаёт через `GET /players/tournaments/{id}/my-registration` (расширен в LFPT-0706), не через этот контроллер.

Страница `/torneo/{id}` показывает действие «Добавить партнёра» для активной соло-заявки, включая исторический `WAITLIST` без партнёра. Запрос использует тот же `POST .../add-partner`; готовая пара получает место по действующей очереди резерва.

## Условия и полная отмена пары

- `GET /api/tournaments/double/{tournamentId}/pair-terms` — действующие условия записи команды Americano. Возвращает 204, если условия недоступны. Финальный POST записи передаёт полученный `pairTermsToken`. Сервер под блокировкой турнира сверяет условия и сохраняет их снимок от имени оформившего игрока.
- `GET /api/tournaments/double/{tournamentId}/my-pair-terms` — условия собственной активной заявки. `POST` на тот же путь с `{"token":"…"}` принимает новую версию за всю пару. Это действие доступно только установленному оформителю заявки с проверяемыми платежами.
- `GET /api/tournaments/double/{tournamentId}/pair-cancellation` — предпросмотр полной отмены, включая доступность выхода одного игрока. `POST` на тот же путь с `{"token":"…"}` повторно проверяет сумму и состав пары, затем отменяет заявку. При изменении условий или оплаты нужен новый предпросмотр. `legacy: true` означает прежние условия. `POST /players/tournaments/{tournamentId}/cancel-double?option=self` сохраняет место партнёру.

Предложение новой версии выключено по умолчанию (`app.pair-terms.enabled`). Условия, уже явно принятые для конкретной пары, читаются из её снимка.

До включения новых условий сайт и приложение напоминают участникам Team Americano заранее предупредить организатора и партнёра об изменении планов и приехать за 15 минут. Та же просьба включена в письмо подтверждения и в существующее email-напоминание примерно за пять часов.

Организатор фиксирует неявку (`POST /admin/tournaments/{tournamentId}/payments/pair-no-show`) и оплаченную замену (`POST /admin/tournaments/{tournamentId}/payments/pair-replacement`) на странице платежей. Замену можно подтвердить один раз и только при достаточной оплате новой пары. Запись об обязательстве и возврате обновляется для ручной сверки.

`POST /admin/tournaments/{tournamentId}/payments/pair-booker` позволяет организатору отметить проверенного оформителя старой заявки без непривязанных платежей. Отметка открывает оформителю возможность принять условия и не заменяет его согласие.


В приложении и личном кабинете сайта для Team Americano личный выход и снятие пары доступны после «Отказаться от участия». Выход одного участника и снятие пары подтверждаются отдельно. `POST /api/tournaments/double/{tournamentId}/replace-self` принимает `nombre`, `apellido` и `existingUserId` для найденного игрока или `telefono` для нового игрока в JSON. Возвращает 204. Подсказки по имени, фамилии и телефону используют существующий поиск партнёров. Игрок должен состоять в активной паре, турнир ещё не начался. Сервер переиспользует алгоритм замены сайта и сохраняет заявку пары, принятые условия и историю прежнего участника.

### Замена партнёра с сохранением места

`POST /api/tournaments/double/{tournamentId}/replace-partner` принимает идентификатор текущего партнёра и данные замены.

```json
{
  "currentPartnerId": 15,
  "replacement": { "nombre": "Ana", "apellido": "López", "existingUserId": 23 }
}
```

Для нового игрока вместо `existingUserId` передаётся `telefono`. Сервер проверяет авторизованного оформителя заявки Team Americano, состояние турнира и актуальность состава. Успешный ответ 204 означает, что замена уже вступила в силу. Сохраняются место или очередь, идентификатор заявки, условия и история платежей. Ответ 409 означает, что замена недоступна или состав изменился. Уведомление прежнему партнёру создаётся атомарно вместе с заменой. После завершения транзакции ему также отправляется письмо при наличии обычного email.

## Объединение заявок координатором

`POST /admin/tournaments/{tournamentId}/pair-solo` принимает ID двух активных заявок без пары из указанного парного турнира, включая одиночную заявку в резерве. Доступ проверяется по правам управления турниром. Пара наследует более раннее время одной из заявок. Оба игрока вместе остаются в резерве или переходят в основной состав по общим правилам очереди. Заявки сохраняют свои ID.

## Ответ после резерва или замены (LFPT-0760)

- `GET /api/players/me/participation` — запросы игрока и доступные ему запросы за гостевого партнёра.
- `GET /api/players/me/participation/{id}` — текущий статус и допустимые действия из кабинета.
- `POST /api/players/me/participation/{id}` с `{"decision":"CONFIRM"}` или `{"decision":"DECLINE"}` — ответ авторизованного игрока. Повтор возвращает сохранённое состояние.
- `GET /participacion/{id}` — просмотр по ссылке из письма. `POST /participacion/{id}` — явное действие с CSRF. Срок ссылки семь дней, после него доступ к запросу сохраняется из кабинета в пределах допустимого окна.
- `PUT /api/players/me/tournaments/{id}/replacement-search` с `{"enabled":true}` — включить поиск для участника, который удерживает место без партнёра.
- `GET /api/admin/tournaments/{id}/participation` — текущие ответы и признак «Нужна замена» для организатора с доступом к турниру.
- `POST /api/tournaments/double/decline-pair?token=…` — отказаться от предложения пары. Обе регистрации сохраняются. Состояния ответа `DECLINED`, `ACCEPTED`, `PAIR_FORMED`, `EXPIRED`.

Ответ не заменяет ручную отметку оплаты или посещаемости. После отказа одного участника место сохраняется за партнёром. При отказе последнего участника продолжают действовать финансовые условия записи, а место получает следующая готовая пара.

Кабинет `/players/dashboard` показывает запросы игрока и гостя отдельными карточками. Экран `/participacion/{id}` возвращает к запросу после входа и предлагает ответить из кабинета при истечении ссылки. В профиле `prod` письма с запросом участия включены. Настройка `PADEL_PARTICIPATION_RESPONSE_EMAIL_ENABLED=false` возвращает обычное уведомление о месте в основе.
