# Закрытый тестовый контур UI v2

Контур использует настоящее приложение и React из jar, собственные PostgreSQL и Mailpit. Данные синтетические; business-правила совпадают с действующим приложением. Production URL и `app.spa.routes` не переключаются. Контур #904 используется для [репетиции выпуска и отката](ui-v2-release.md); пользовательская приёмка #913 остаётся отдельной задачей.

## Подготовка и запуск

Нужны Docker Engine 28+ с Compose v2, Java и Maven wrapper проекта, Python 3.9+ и OpenSSL. Сборке нужен интернет для зависимостей; работающему приложению внешний доступ не предоставляется. Не подставляйте `.env` или доступы другой среды.

Из корня отдельного checkout:

```sh
python3 automation/ui-preview/preview.py init --port 18114
python3 automation/ui-preview/preview.py config
./mvnw verify
python3 automation/ui-preview/preview.py build
python3 automation/ui-preview/preview.py up
```

`verify` использует отдельно подготовленную тестовую БД по правилам проекта. `build` собирает jar с React и затем собственный runtime-образ; запуск Maven с `-DskipTests` внутри этой команды не заменяет обязательный `verify`. Docker-контекст содержит только jar. PostgreSQL, Mailpit, nginx и Java runtime закреплены digest; не смешивайте этот Compose с production Compose.

`init` создаёт случайное имя проекта и доступы в `automation/ui-preview/runtime/` с каталогом 0700; повторная инициализация существующего каталога запрещена. Файлы доступны container-процессам через явно перечисленные secrets, но родительский каталог закрыт для других пользователей хоста. Каталог целиком игнорируется Git и Docker build. Не публикуйте его содержимое, вывод `state.json`, конфигурацию с доступами или скриншоты этих файлов.

Точка входа: `http://127.0.0.1:18114/__preview`. Внешний Basic Auth использует имя `preview` и случайный `gateway_password` из локального `state.json`. После него действует обычный вход приложения. Синтетические аккаунты: `preview-admin@example.test` (SUPER_ADMIN), `preview-player-0@example.test` и ещё семь игроков, последний — guest. Их случайный пароль — `fixture_password` из того же файла. Текущие ID доступны защищённой диагностике, а не предполагаются заранее.

Авторизация gateway не заменяет роль приложения. Guest/player не получают `/preview/**`; его открывает SUPER_ADMIN. Проверяемые API используют обычную session/CSRF приложения. Внешний Basic Auth занимает заголовок Authorization и не является способом тестирования мобильного Bearer-входа; `/app/**` проверяется как существующая сборка, без изменения мобильных исходников.

## Изоляция

Только nginx публикует порт на `127.0.0.1`; отдельная входная сеть есть только у него. Приложение, БД и SMTP находятся в `internal` bridge с `gateway_mode_ipv4=isolated`: нет внешнего маршрута и адреса bridge для соединений с сервисами хоста. У приложения нет Docker socket, host network или опубликованных портов. nginx проксирует только фиксированные локальные upstream, не работает как произвольный forward proxy.

Basic Auth покрывает все пути, включая login, assets, API, health и Mailpit. `/__preview` явно помечен на ES/RU/EN. Ответы имеют `X-Environment: preview` и `X-Robots-Tag: noindex, nofollow, noarchive`. Readiness `/actuator/health/readiness` включает БД, liveness `/actuator/health/liveness` — состояние приложения; подробности health не раскрываются.

Профиль `preview` не допускает совмещения с другими профилями. Ранний EnvironmentPostProcessor запрещает внешний datasource/Liquibase URL, небезопасные настройки почты, включение scheduling/Telegram/Meta/OAuth/аналитики, внешнее логирование и SPA allowlist. До Liquibase дополнительно сверяется UUID-маркер выделенной БД. Пароли и JWT создаются только для контура. Новый профиль логирует в консоль с маскированием, без Loki/Telegram appenders.

Scheduled-обработчики в preview не регистрируются. В обычных профилях `app.scheduling.enabled` по умолчанию `true`. Письма от явных действий после commit продолжают поступать в Mailpit. Внешний OAuth не отображается в account-config и его маршруты отклоняются. Внешние callbacks, reCAPTCHA и обновление disposable-email списков выключены.

## Данные, диагностика и reset

```sh
python3 automation/ui-preview/preview.py status
python3 automation/ui-preview/preview.py mail
python3 automation/ui-preview/preview.py reset
```

Команды входят только в локальный gateway, затем используют синтетическую SUPER_ADMIN-сессию и CSRF. Перенаправление на другой origin запрещено, чтобы не отправить доступы наружу. `status` показывает среду, commit ревизию, ID собственных seed-сущностей; `mail` читает только локальный Mailpit.

Seed создаёт клуб, роли, King of Court, индивидуальный Americano, парные события, готовую пару, резерв, solo, guest-партнёра и отмену с историей. Повторный старт сохраняет текущие ID и не повторяет seed/письмо. Настройка и проведение форматов выполняются действующими средствами приложения; неподтверждённые правила #759/#760/#901 не моделируются.

Reset блокирует строку маркера и сверяет имя выделенной БД. Он удаляет только мероприятия по ID из сохранённого seed, связанные регистрации/платежи/историю и создаёт эти сценарии заново. Синтетические аккаунты/клуб сохраняются. Чужие мероприятия и их данные не удаляются, UUID и маркер не принимаются из тела запроса. При несовпадении маркера, ошибке ограничений или связи с другими данными транзакция откатывается; глобального TRUNCATE и удаления чужих volumes нет.

После обновления кода выполните `build`, затем `up`: образ и метка ревизии обновляются вместе. В CI ревизия соответствует проверяемому merge commit; локально собирайте опубликованную ревизию, если нужна точная воспроизводимость артефакта.

## Проверка и отключение

После запуска:

```sh
PLAYWRIGHT_MODULE_PATH="$PWD/frontend/node_modules/@playwright/test/index.mjs" python3 automation/ui-preview/check.py
python3 -m unittest discover -s automation/ui-preview -p 'test_*.py'
python3 automation/ui-preview/preview.py stop
```

Нужны Node и установленный Chromium соответствующей версии Playwright. Проверка использует только runtime этого checkout: тестирует сеть, ранние отказы при небезопасном старте, внешний барьер, session/CSRF, роли, deep link/refresh, React/legacy/Expo, SMTP и reset с посторонней контрольной записью. Временный JSON с доступами удаляется, скриншот маркированной точки входа остаётся в игнорируемом `target/ui-preview-qa/`. Те же проверки включены в PR Check, остановка выполняется даже при ошибке.

`stop` останавливает только проект с проверенным локальным именем, не делает `down -v`, не трогает чужие контейнеры и сохраняет выделенный volume/runtime для повторного запуска. После него входной порт закрыт. Для аварийного отключения достаточно этой же команды. Удаление сохранённых локальных данных — отдельная осознанная операция владельца; массовая очистка Docker не используется.

В текущую реализацию входит локальный контур. Удалённый доступ, TLS, DNS/VPN и выдача доступа заказчику готовятся отдельным согласованным шагом. Боевые конфигурации и сервер не меняются. Полная приёмка Safari/iPhone/Android, проверка всех экранов и deploy/rollback относятся к #913/#905.

## Последующие выпуски и восстановление

После первого `up` и успешной проверки используйте общий механизм выпуска:

```sh
python3 automation/ui-preview/preview.py release
python3 automation/ui-preview/preview.py rollback
python3 automation/ui-preview/preview.py recover
```

`release` берёт уже собранный jar из `target/`, проверяет manifest/Expo и создаёт неизменяемый образ. После появления `runtime/release-state/current.json` команда `build` обновляет только jar, сохраняя исходный образ для rollback; `up` запускает сохранённый снимок и собственные зависимости, не пересобирая приложение и не обходя pending-журнал. Это позволяет снова поднять контур после `stop`. `recover` восстанавливает предыдущую версию после незавершённого переключения, `rollback` возвращает предыдущий подтверждённый снимок. База/синтетические данные этими командами не пересоздаются. Каталог runtime со снимками и секретами не публикуется.

```sh
PLAYWRIGHT_MODULE_PATH="$PWD/frontend/node_modules/@playwright/test/index.mjs" \
  python3 automation/releases/rehearse.py
```

Репетиция строит два синтетических QA-выпуска с невидимым module probe, использует настоящий backend и браузер, проверяет старый lazy chunk после переключения, ручной откат, HTTP 404/503 и восстановление по журналу. Production runner отклоняет такие артефакты. Безопасный отчёт — `target/release-rehearsal/report.json`; в конце возвращается исходный снимок.

## Данные пилота PlayoffMatchingEngine

Повторяемый исходный прогон: `python3 automation/ui-preview/playoff-pilot.py run` сверяет запущенный jar и принятый эталон; пересоздаёт только пилот. `smoke --rehearse` проверяет общий browser/JWT и сохранность пяти турниров через репетицию выпуска/отката. `prepare --reset` готовит ручной набор; run/reset во время ручной проверки не выполнять. [Команды, ответы и ограничения](modular-monolith/phase-1/browser-baseline.md), [ручной журнал](modular-monolith/phase-1/manual-baseline.md).

После запуска контура SUPER_ADMIN может подготовить пилот запросом `POST /api/internal/ui-preview/playoff-pilot` с сессионной cookie и CSRF header. Повторный POST возвращает те же ID; GET только читает и до подготовки возвращает 404. `POST /api/internal/ui-preview/playoff-pilot/reset` пересоздаёт только пять турниров пилота. Общий `/api/internal/ui-preview/reset` пересоздаёт прежние шесть мероприятий, сохраняя метаданные пилота. Операции сериализуются блокировкой существующего UUID-маркера; отказ откатывает данные и метаданные вместе.

Набор содержит `roster-8`, `qualified-8`, `qualified-9`, `qualified-16`, `finished-8`. Квалификация проходит через настоящий сервис: у каждой команды два завершённых матча. `roster-8` позволяет начинать раннюю сетку и NO_SHOW с исходного состава; отдельные готовые сценарии этих действий создаются браузерной приёмкой #1048.

Аккаунты `pilot-manager@example.test` и `pilot-foreign@example.test` — CLUB_ADMIN своего и другого синтетического клуба; пароль берётся из локального `fixture_password`, в API не возвращается. Ответ содержит актуальные ID клубов, администраторов, 32 игроков, турниров и упорядоченных команд. Не подставляйте ID из чужого контура. Подробности и границы проверки: [исходный backend-отчёт](modular-monolith/phase-1/backend-baseline.md).

При откате на артефакт до появления пилота используйте обычные страницы турнира для чтения/продолжения. Старый preview-reset не знает о дополнительных метаданных пилота; не запускайте его до возврата новой версии. Это ограничение вспомогательной подготовки данных, а не миграция схемы.
