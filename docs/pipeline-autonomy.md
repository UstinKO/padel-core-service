# Автономный конвейер: от сообщения в Telegram до фичи на проде

Статус: **дорожная карта утверждена 2026-10-16; этапы 1–3 работают на проде, пилот (этап 4) пройден 2026-10-16** — см. §7.

Цель: сообщение в теме «AI Разработка» → спека → реализация (бэк и фронт) → PR → pr-check → **автоматический мерж** → деплой → сообщение в чат «задача реализована и влита, можно проверять». Человек в цепочке остаётся только там, где нужно бизнес-решение (открытые вопросы в спеке), и как получатель итога.

Предыстория: «Telegram → AI-конвейер» (`docs/telegram-ai-pipeline.md`, приватный, не в репозитории; как устроен вход), `specs/features/telegram-remote-pipeline.md` (как его строили), `.claude/commands/develop-feature.md` (канонические правила конвейера — роутина читает именно их).

## 2. Факты, которые определяют архитектуру

1. **У роутины может быть только один API-токен.** «Generating a new token revokes the previous one» ([docs](https://platform.claude.com/docs/en/api/claude-code/routines-fire)). Так умер вызов роутины из `deploy.yml` (06–16.10): для relay перевыпустили токен, старый в GitHub-секрете отозвался. Вывод: **запускать роутину может ровно один компонент — движок (relay)**. GitHub Actions роутину не дёргает.
2. **Лимиты запуска роутин** ([docs](https://code.claude.com/docs/en/routines#usage-and-limits)): 30 запусков/час на роутину, 100 API-запусков/час на аккаунт, сверх — `429` с `Retry-After` (запуск *не принят*, повтор безопасен). **Лимита на число одновременных сессий в документации нет** — реальный потолок параллельности задаёт расход подписки: каждая сессия тратит её как интерактивная (типичный прогон конвейера 15–40 минут).
3. **Токен роутины ничего не читает** — ни статус сессии, ни её результат. Узнать, что сессия закончила работу, можно только по её следам в GitHub. Вывод: **GitHub — шина событий конвейера** (метки, маркеры в PR, комментарии в issue).
4. **Мерж от `GITHUB_TOKEN` не запускает другие workflow** (защита GitHub от рекурсии). Если оркестратор вольёт PR своим токеном, `deploy.yml` по `push` не стартует. Вывод: оркестратор **сам запускает деплой** через `workflow_dispatch` (это событие `GITHUB_TOKEN` запускать может).
5. **Роутина действует от GitHub-аккаунта пользователя и пушит в ветки `claude/*`** (#568, #571 — `claude/great-mendel-*`). Именование `feature/LFPT-XXXX` в облаке не соблюдается — идентификация задачи только по заголовкам PR/коммитов (`LFPT-XXXX`), это уже так.
6. **Бот не видит сообщений, которые сам отправил.** Роутина, отправляя итог через `@padel_core_ai_bot`, не может «сообщить» relay — обратный канал только через GitHub.
7. **Пока фронт на Thymeleaf, фронт без бэка роняет приложение** (шаблон обращается к полю/эндпоинту, которого нет). Порядок мержа «бэк → деплой бэка → фронт» обязателен. После перехода на React ограничение ослабнет.

## 3. Целевая схема

```
Telegram ──► Движок задач (relay v2, прод-сервер, SQLite)
               │ очередь, лимит параллельности, 429-ретраи,
               │ статусы задач в чате, ответы на вопросы реплаем
               │ POST /fire  (единственный держатель токена роутины)
               ▼
           Роутина (облако) — /develop-feature, cloud-режим
               │ спека → бэк → фронт (ветка от бэка) → тесты
               │ PR(ы) с маркерами  Pipeline-Task / Depends-On
               │ ждёт pr-check, сама чинит красное (≤2 попыток)
               │ ставит метку pipeline:ready  — сессия свободна
               ▼
           GitHub
               │ pr-check (pull_request)
               ▼
           Оркестратор pipeline-merge.yml (GitHub Actions)
               │ берёт PR с pipeline:ready по одному,
               │ Depends-On выполнен? → verify на свежем master
               │ → squash-мерж → workflow_dispatch deploy.yml
               ▼
           deploy.yml — деплой, health-check, автооткат, archive-specs
               ▲
               │ движок опрашивает GitHub (PR, метки, прогоны)
Telegram ◄── «✅ Задача #N реализована и влита на прод — можно проверять»
```

Разделение ответственности:

| Компонент | Отвечает за | Не делает |
|---|---|---|
| Движок (relay v2) | Приём задач, очередь, запуск роутин, отслеживание жизненного цикла, **весь UI в чате** | Не мержит, не деплоит |
| Роутина | Спека, код, тесты, PR, доведение PR до зелёного pr-check | Не мержит, не пишет итог в чат (после этапа 4) |
| Оркестратор (`pipeline-merge.yml`) | Порядок и безопасность мержа, запуск деплоя, стоп при сбое деплоя | Не пишет в Telegram, не запускает роутину |
| `deploy.yml` | Деплой, откат, архивация спек | — |

## 4. Компоненты

### 4.1. Протокол «роутина ↔ GitHub ↔ движок»

**Маркеры в теле PR и issue** (отдельные строки, машиночитаемые):

```
Pipeline-Task: 4321          # telegram_launch_message_id задачи (или manual-<run>)
Depends-On: #580             # только у фронт-PR: номер бэк-PR той же задачи
```

**Метки** (создаются один раз, этап 1):

| Метка | Где | Кто ставит | Смысл |
|---|---|---|---|
| `pipeline` | PR, issue | роутина | Создано конвейером |
| `pipeline:ready` | PR | роутина | Работа по PR закончена, pr-check зелёный — можно вливать |
| `pipeline:needs-input` | issue | роутина | Гейт: открытые бизнес-вопросы (текст — в комментарии `🤖 pipeline-questions`) |
| `pipeline:failed` | issue/PR | роутина | Не смогла довести (причина — в комментарии) |
| `pipeline:conflict` | PR | оркестратор | Конфликт с master или verify на свежем master упал |
| `pipeline:deploy-failed` | PR | оркестратор | Деплой после мержа упал (откат сработал/не сработал — в комментарии) |
| `pipeline:halt` | issue | оркестратор / человек | Открытый issue с этой меткой останавливает весь автомерж |

**Сессия роутины свободна**, когда у всех PR задачи стоит `pipeline:ready` (или `pipeline:failed`), либо issue задачи помечен `pipeline:needs-input`.

**Побочные находки маркер задачи не получают** (LFPT-0626). Issue, которую роутина завела «на потом» (баг вне скоупа), — самостоятельная задача: без `Pipeline-Task` и без метки `pipeline`, со строкой `Найдено в: #<issue>, PR #<PR>`. Иначе движок видит открытую issue задачи без PR и держит задачу «в работе» (так застряла #5175: находки #619, #620).

### 4.2. Движок задач (relay v2)

Эволюция текущего `scripts/telegram-relay/relay.py` (вне git, прод-сервер). Остаётся на Python stdlib, состояние — SQLite рядом с `state.json` (переживает рестарт, в отличие от текущего буфера в памяти).

**Жизненный цикл задачи:**

```
QUEUED → RUNNING → PR_CHECKS → READY → MERGING → DEPLOYING → DONE
            │          │                    │           └──► DEPLOY_FAILED
            │          └──► FAILED          └──► CONFLICT
            └──► NEEDS_INPUT ──(ответ реплаем)──► QUEUED (продолжение)
            └──► STALLED (нет следов в GitHub > 3 ч)
```

**Когда задача `DONE`** (`derive_status` в `engine.py`): у каждой **открытой** issue с маркером есть PR с `Closes #<issue>`, и все PR задачи влиты, а их деплой прошёл (или не нужен — только `specs/`, `.claude/`, `docs/`). Закрытая без PR issue (закрыли руками как invalid) задачу не держит. Пока у открытой issue нет PR, задача в `RUNNING`: роутина могла ещё не дойти до фронт-PR.

**Страховка от «вечного STALLED»** (LFPT-0626, на сервере с 2026-10-19). Если все PR задачи влиты и задеплоены, а открытые issue без PR не меняются дольше `STALL_HOURS`, задача переходит в `DONE`, а не в `STALLED`, — в том числе из уже выставленного `STALLED`. Итоговое сообщение перечисляет эти issue отдельным списком («в задачу не вошли»). Цена: фронт-PR, который пишется дольше `STALL_HOURS` без единого следа в GitHub, закроет задачу раньше времени — раньше в этом случае был `STALLED`, то есть человек нужен всё равно.

- **Очередь и параллельность.** `MAX_PARALLEL` в `.env` (стартовое значение — **2**). Слот занят от `/fire` до момента «сессия свободна» (§4.1); мерж и деплой слот не занимают. Очередь — FIFO, рубильник `/admin/telegram-pipeline` ставит на паузу выдачу новых задач (fail-closed, как сейчас).
- **Ретраи.** `429` и `503` — повтор по `Retry-After`/backoff автоматически (запуск не принят). `500`/таймаут — без автоповтора (сессия могла создаться), задача в `FAILED` с кнопкой «Перезапустить».
- **Отслеживание.** Раз в минуту для активных задач: GitHub search (REST) по `"Pipeline-Task: <N>"` → PR/issue (только те, где маркер — отдельная строка тела, а не упоминание в тексте), их метки, состояние, прогоны `Deploy to Production` (по `run-name` с номером PR). Нужен fine-grained PAT **только на чтение** (Issues, Pull requests, Actions, Metadata) в `.env` движка.
- **Продолжение задачи.** Реплай на любое сообщение задачи в чате = продолжение именно этой задачи (ответы на вопросы, уточнение). Движок добавляет в текст `[продолжение задачи #N]` и контекст (issue, вопросы) — роутине не нужно гадать, новая это задача или ответ.

### 4.3. Интерфейс в чате

Принцип: **одна задача — одно «живое» сообщение-карточка**, которое движок редактирует по ходу жизненного цикла, плюс отдельные сообщения только там, где нужно внимание человека (вопросы, итог, сбой) — они приходят с уведомлением.

Карточка задачи (редактируется на месте):

```
🟡 Задача #4321 — в очереди (2-я)          [❌ Отменить]
🔵 Задача #4321 — в работе · сессия ↗
🟣 Задача #4321 — LFPT-0580 (бэк) PR #582 · LFPT-0581 (фронт) PR #583 · проверки…
🟢 Задача #4321 — вливается: #582 ✅ задеплоен, #583 в очереди на мерж
✅ Задача #4321 — готово
```

Сообщения с уведомлением (реплаем на исходное сообщение задачи):

```
❓ Задача #4321 — нужны ответы, чтобы продолжить:
   1. …
   2. …
   Ответьте реплаем на это сообщение.

✅ Задача #4321 реализована и влита на прод — можно проверять.
   LFPT-0580: Feature … (бэк) — PR #582
   LFPT-0581: Feature … (фронт) — PR #583
   Деплой: <ссылка на прогон>

⛔ Задача #4321 — деплой #583 упал, прод откатан на предыдущую версию.
   Автомерж остановлен (issue #590 pipeline:halt). Нужен человек.
```

Закреплённое сообщение-пульт: **▶️ Начать задачу** (сборка из нескольких сообщений, как сейчас) и **📋 Очередь** — сводка: что в работе, что в очереди, свободные слоты, статус автомержа (работает / остановлен halt-issue).

### 4.4. Оркестратор автомержа (`.github/workflows/pipeline-merge.yml`)

- **Триггеры:** `workflow_run` по «PR Check» и «Deploy to Production» (completed), `pull_request: labeled`, `schedule` раз в 15 минут (страховка), `workflow_dispatch`.
- **Сериализация:** `concurrency: pipeline-merge` и правило «пока идёт деплой — не мержить». Мерж и деплой строго по одному: следующий PR вливается только после завершения деплоя предыдущего. Это даёт и порядок «бэк → фронт», и отсутствие гонок, ценой ~10 минут на PR.
- **Выбор PR:** самый старый открытый с `pipeline` + `pipeline:ready`, без `pipeline:conflict`/`pipeline:deploy-failed`; если есть `Depends-On: #M` — #M влит **и** его деплой успешен.
- **Проверка на свежем master:** pr-check тестировал PR против master на момент своего запуска; с тех пор master мог уйти вперёд (другая задача). Перед мержем — повторный `mvn verify` на `refs/pull/N/merge` (pr-check выносится в переиспользуемый workflow). Упало → `pipeline:conflict` + комментарий; движок перезапускает роутину на починку.
- **Мерж:** `gh pr merge --squash` с заголовком PR (в нём `LFPT-XXXX` — нужен `archive-specs`), затем `gh workflow run deploy.yml -f pr=N`. PR, затрагивающий только `specs/**`, `.claude/**`, `docs/**`, вливается без деплоя (как `paths-ignore`).
- **Сбой деплоя:** PR → `pipeline:deploy-failed`, создаётся issue `pipeline:halt` со ссылкой на прогон. Автомерж стоит, пока человек не закроет issue.

Правки `deploy.yml`: `workflow_dispatch` с входом `pr`, `run-name` с номером PR, `concurrency: deploy-production`, `archive-specs` берёт заголовок коммита из `git log`, а не из `head_commit` (у dispatch его нет).

### 4.5. Изменения в процессе роутины (`develop-feature.md`)

- **Бэк и фронт — в одном прогоне.** Две задачи (две issue, как и сейчас по §1.4), но реализуются обе: бэк-ветка → PR; фронт-ветка **от бэк-ветки** → PR с `Depends-On: #<бэк-PR>`. Сейчас роутина часто делает бэк и только заводит фронт-задачу — это уходит.
- **Доведение до зелёного.** После PR — `gh pr checks --watch`; красный — починить и запушить (≤ 2 попыток), иначе `pipeline:failed` + причина.
- **Финал роутины** — метка `pipeline:ready` на каждом PR. Фраза «ревью и мерж — за пользователем» из PR убирается.
- **Вопросы** — `pipeline:needs-input` + комментарий `🤖 pipeline-questions` вместо сообщения в Telegram.
- **Telegram роутина больше не пишет** (после этапа 4 — UI целиком у движка). До этого — итог «PR открыт, вольётся автоматически после проверок».

## 6. Страховки (вместо ручного ревью)

| Риск | Чем закрыт |
|---|---|
| PR ломает сборку/тесты | pr-check + повторный verify на свежем master перед мержем |
| Две задачи конфликтуют | Мерж строго по одному, verify на актуальном master, `pipeline:conflict` → перезапуск роутины на починку |
| Фронт раньше бэка | `Depends-On` + «бэк задеплоен успешно» как условие мержа фронта |
| Приложение не стартует после деплоя | health-check `deploy.yml` + автооткат на `app.jar.backup`, затем `pipeline:halt` — автомерж стоит до человека |
| Необратимая миграция БД | Не закрыт автоматикой (откат jar не откатывает схему) — осознанно принятый риск, решение пользователя «ничего не держать на ревью». Смягчение: Liquibase-миграции только аддитивные (правило в `CODE_REVIEW.md` уже есть), Tester гоняет их на чистой БД |
| Поток мусорных задач / компрометация Telegram | Рубильник `/admin/telegram-pipeline` (останавливает приём), `pipeline:halt` (останавливает мерж), белый список `user_id` в relay |
| Расход подписки | `MAX_PARALLEL`, очередь вместо мгновенного запуска |

Стоп-краны: **приём задач** — `/admin/telegram-pipeline`; **мерж** — открыть issue с меткой `pipeline:halt`; **всё сразу** — `systemctl stop telegram-relay` + halt-issue.
